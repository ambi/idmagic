# 管理 API の認可

## 概要

この文書は、OAuth2 の管理 API の認可と、ロールポリシーの確認の仕様である。

| 項目 | 内容 |
| --- | --- |
| 責務 | 管理 API のクライアントのリソースごとのスコープによる認可、管理者が見えるロールポリシーの一覧 |
| 行為者 | 管理 API のクライアント、テナント管理者 |
| 扱わないもの | システム全体の認可は[認可設計](../../../design/security/authorization.md)が扱う |

## モデル

すべての認可の判定は AuthZEN の形式の `authorize()` ポートを通り、規則表が要件の論理積を評価する。
判定を返せない場合、事実が欠けている場合、ストアへ到達できない場合のいずれも、許可へ退避しない。

- **判断**：AuthZEN 型のポートを使う理由は、[ポリシーの境界をまたぐ認可の判断を AuthZEN 型のポートに通す](../decisions.md#ポリシーの境界をまたぐ認可の判断を-authzen-型のポートに通す)。

## 操作

### 管理 API のクライアントによる操作

#### REQ-OAUTH2-003 管理 API クライアントは OAuth リソースのスコープで許可された操作だけを実行できる

- 管理者の API アクセストークンで OAuth2 の管理 API を要求されたとき、OAuth2 は、`oauth-clients:read` で OAuth2 のクライアントの参照を、`oauth-clients:write` でその変更を、`authorization-detail-types:read` と `authorization-detail-types:write` で認可詳細の種類の参照と変更を、`mcp-resource-servers:read` と `mcp-resource-servers:write` で MCP のリソースサーバーとアプリ間アクセスの許可の参照と変更を許可する。
- 読み取りのスコープだけで変更を要求されるか、別のリソースのスコープで操作を要求された場合、OAuth2 は、403 と `insufficient_scope` で拒否する。
- トークンのテナントとリクエスト先のテナントが一致しない場合、OAuth2 は、401 と `invalid_token` で拒否する。
- `authorize()` のポートが判定を返せないか、事実が欠けているか、ストアへ到達できない場合、OAuth2 は、許可せずに拒否する。
- **例**：EX-OAUTH2-003-01、EX-OAUTH2-003-02、EX-OAUTH2-003-03、EX-OAUTH2-003-04

### 管理者によるロールポリシーの確認

#### REQ-OAUTH2-004 管理者は自身に可視なロールポリシーを確認できる

- `admin` か `system_admin` のロールを持つ管理者がロールポリシーの一覧を取得したとき、OAuth2 は、200 と、参照できるロール、権限、対応する HTTP のインターフェースを返す。
- デフォルトのテナントの管理者がデフォルトのテナントで一覧を取得したとき、OAuth2 は、システム全体のロールも含めて返す。
- `admin` も `system_admin` も持たない主体が一覧を要求した場合、OAuth2 は、403 と `access_denied` で拒否する。
- **例**：EX-OAUTH2-004-01、EX-OAUTH2-004-02

### 管理者による認可詳細の種類の管理

#### REQ-OAUTH2-051 管理者は認可詳細の種類を登録、更新、削除できる

- 管理者が認可詳細の種類を一覧か取得したとき、OAuth2 は、200 とテナントの種類を返す。
- 管理者が新しい名前の種類を作成したとき、OAuth2 は、201 と種類を返す。
- 管理者が種類を更新したとき、OAuth2 は、200 と更新した種類を返す。
- 管理者が種類を削除したとき、OAuth2 は、204 を返す。
- JSON として読めない本文か `type` のない作成を受けた場合、OAuth2 は、400 と `invalid_request` で拒否する。
- 同じ名前の種類がある作成を受けた場合、OAuth2 は、409 と `type_exists` で拒否する。
- 存在しない種類の取得か更新を受けた場合、OAuth2 は、404 と `type_not_found` で拒否する。
- 項目の規則を検証できないか、未知の項目の意味を含む種類を受けた場合、OAuth2 は、422 と `invalid_type` で拒否し、種類を保存しない。

### 管理者による MCP のリソースサーバーの管理

#### REQ-OAUTH2-052 管理者は MCP のリソースサーバーを登録、更新、削除できる

- 管理者が MCP のリソースサーバーを一覧か取得したとき、OAuth2 は、200 とテナントのリソースサーバーを返す。
- 管理者が新しい `resource` のリソースサーバーを作成したとき、OAuth2 は、201 とリソースサーバーを返す。
- 管理者がリソースサーバーを更新したとき、OAuth2 は、200 と更新したリソースサーバーを返す。
- 管理者がリソースサーバーを削除したとき、OAuth2 は、204 を返す。
- JSON として読めない本文か `resource` のない作成を受けた場合、OAuth2 は、400 と `invalid_request` で拒否する。
- 同じ `resource` のリソースサーバーがある作成を受けた場合、OAuth2 は、409 と `resource_exists` で拒否する。
- 存在しないリソースサーバーの取得か更新を受けた場合、OAuth2 は、404 と `resource_server_not_found` で拒否する。
- 検証を通らないリソースサーバーを受けた場合、OAuth2 は、400 と `invalid_resource_server` で拒否し、保存しない。

#### REQ-OAUTH2-064 管理者はリソースサーバーへ評価用のクライアントと規則を設定できる

- 管理者がテナントの機密クライアントの `client_id` と `access_rules` を指定して作成か更新をしたとき、OAuth2 は、それらを保存し、応答に含める。
- 管理者が `tool` を持つ規則を保存したとき、OAuth2 は、接続先内で一意な128文字以内のツール名、256文字以内の表示名、必要スコープ、対象抽出の整合を検証する。
- `tool` の名前か表示名が空であるか、ツール名が `:` か `#` を含むか、同じツール名が重複するか、対象別の型と関係を持つツールに対象引数がない場合、OAuth2 は、400 と `invalid_resource_server` で拒否し、保存しない。
- 従来の規則とツールを持つ規則が同じ対象型と関係へ対応する場合、OAuth2 は、400 と `invalid_resource_server` で拒否し、操作割当を迂回する対応を保存しない。
- 更新の本文に `client_id` か `access_rules` がないとき、OAuth2 は、その項目を変えない。
- `scopes` を省略か空の配列で作成したとき、OAuth2 は、`mcp` を登録の唯一のスコープとして保存する。
- **判断**：Gateway が執行する構成では、上流の MCP サーバーはスコープを検査せず、スコープは IdMagic の中だけで働く認証上限である。実行できる操作は操作割当が決めるので、管理者にスコープ名を考えさせない。サーバー自身がトークンを検査する構成では、サーバーが定めたスコープ名を指定する。
- `client_id` が、テナントにないクライアント、機密でないクライアント、同じテナントの別の登録に束縛済みのクライアントである場合、OAuth2 は、400 と `invalid_resource_server` で拒否し、保存しない。
- 規則の `resource_type` か `relation` が `^[a-z][a-z0-9_]*$` の形でないか 65 文字以上であるか、ツールを持たない規則で `resource_type` と `relation` の組が重複するか、`scopes` が空か登録の `scopes` の部分集合でないか、`requires_approved_operation` を持つ規則に `authorization_detail_type` がないか、規則が 100 件を超える場合、OAuth2 は、400 と `invalid_resource_server` で拒否し、保存しない。
- 規則の `condition` に `deny_when` と `require_approval_when` のどちらもないか、式が 1 KiB を超えるか、コンパイルできないか、真偽値を返さないか、内包が入れ子であるか、`require_approval_when` に `approval_detail_type` がないか、`approval_detail_type` だけがあるか、`require_approval_when` と `requires_approved_operation` を併せ持つ場合、OAuth2 は、400 と `invalid_resource_server` で拒否し、保存しない。
- 規則の `condition` を返すとき、OAuth2 は、内容から導いた `version` を含め、本文の `version` を読まない。
- 規則の `limits` が 9 件以上であるか、`by` が `agent`、`user`、`resource` 以外か重複を含むか、`max_requests` が 1 から 1000000000 の外であるか、`window_seconds` が 1 から 2592000 の外であるか、`by` の集合と `window_seconds` の組が重複する場合、OAuth2 は、400 と `invalid_resource_server` で拒否し、保存しない。

#### REQ-OAUTH2-085 ツールの削除と再登録で古い割当を再有効化しない

- 管理者がツールを新しく登録したとき、OAuth2 は、新しい操作の識別子を発行し、接続先に束縛した不透明な `assignment_resource_id` を返す。
- 公開中のツールを同名のまま更新したとき、OAuth2 は、操作の識別子を保持する。
- 管理者がツールを削除した後に同名で再登録したとき、OAuth2 は、新しい操作の識別子を発行し、削除前の割当を新しい操作の許可根拠にしない。
- 操作の識別子か割当参照を本文に指定されたとき、OAuth2 は、その値を使わず、サーバーが所有する操作の識別を使う。
- 登録を読んだ後に別の要求が登録を変更か削除した場合、OAuth2 は、409 と `resource_server_conflict` で古い更新を拒否し、操作、割当の識別、メタデータを上書きしない。

### 管理者による接続先の準備

#### REQ-OAUTH2-087 管理者は報告されたツールを公開中のツールと区別して確認できる

- 管理者が `GET /api/admin/v1/mcp-resource-servers/{id}/reported-tools` を要求したとき、OAuth2 は、200 と、最新の報告のツール、`complete`、`reported_at` を返す。
- 報告がまだない登録について要求されたとき、OAuth2 は、200 と空の `tools` を返し、`reported_at` を含めない。
- 存在しない登録について要求された場合、OAuth2 は、404 と `resource_server_not_found` で拒否する。
- 管理者が登録を削除したとき、OAuth2 は、その登録の報告も削除する。
- 管理コンソールで登録を編集するとき、OAuth2 は、報告にあって未公開のツールを、名前と表示名を入力済みの公開の候補として示し、管理者が選ぶまで公開しない。
- `complete` が真の報告にない公開中のツールを示すとき、OAuth2 は、そのツールを「接続先に見つからない」と表示し、自動で削除しない。
- 変更前の一覧を持つ登録について要求されたとき、OAuth2 は、`changes` に変更の時刻と、追加、削除、定義変更のツールを返す。
- 変更前の一覧が完全でない場合、OAuth2 は、差分に追加を示さない。
- 最新の報告が完全でない場合、OAuth2 は、差分に削除を示さない。
- 両方の一覧にあるツールの `title`、`description`、`arguments` のどれかが異なる場合、OAuth2 は、異なる項目の名前と変更前の定義を定義変更として示す。
- 変更前の一覧がない登録について要求されたとき、OAuth2 は、`changes` を含めない。
- 管理コンソールで登録を編集するとき、OAuth2 は、差分の各ツールを公開中かどうかとともに示し、公開設定を変えない。
- **判断**：差分の基準は直前の報告とし、管理者の確認状態を持たない。状態を増やさずに、公開後の説明や引数の変更に気付けるためである。

#### REQ-OAUTH2-088 管理コンソールは接続先の登録で評価用のクライアントを作成して束縛し、配置の設定を示す

- 管理者が接続先の登録で評価用のクライアントの新規作成を選んだとき、OAuth2 は、`client_credentials` のグラントを持つ機密のサービスクライアントを作成し、その `client_id` を束縛した登録を作成する。
- 管理者が既存のクライアントの利用を選んだとき、OAuth2 は、テナントの機密のサービスクライアントを名前で選ばせ、`client_id` の入力を求めない。
- 作成が完了したとき、OAuth2 は、`client_id`、一度だけ表示するクライアントシークレット、`resource`、realm の URL、`mapping.catalog: true` を含む Gateway の設定の例を、管理者が次の操作を始めるまで表示する。
- クライアントの作成後に登録の作成が失敗した場合、OAuth2 は、作成したクライアントを保持し、クライアントを再作成せず登録の作成だけを再試行できるようにする。
- 管理者が接続先を登録するとき、OAuth2 は、スコープの入力を「サーバー自身がトークンを検査する構成」の詳細設定に置き、デフォルトでは入力を求めない。
- 登録のスコープが一つだけのとき、OAuth2 は、ツールの行にスコープの選択を表示せず、そのスコープを必要なスコープにする。
- **判断**：二つの作成を画面で順に呼ぶ。資格情報の一体の作成（REQ-IDMANAGEMENT-104）と同じ部分失敗の扱いにし、新しい複合の API と組み立て地点を増やさないためである。

## セキュリティ上の考慮

管理 API では、API アクセストークンにロールに加えて、リソースごとのスコープを求める。
リソースをまたぐ流用はできず、あるリソースのスコープで別のリソースを操作することはない。

## 実現方式

### アーキテクチャ

#### 認可ポリシー（AuthZEN）

AuthZEN の要求ポートと管理ロール一覧の計算および HTTP 表示は [AccessControl](../../authorization/README.md) が担当する。
要求と結果、アクション、規則、操作の生成表は仕様バインディングに置き、ローカルとリモートの評価器は組み立て地点でポートへ結ぶ。

ポリシー境界をまたぐ認可判断には、AuthZEN 型の `authorize({subject, action, resource, context})` ポートを使う。ローカル実装は、アプリケーションが定めるアクションと要件の表、および名前付きのルール関数を Go で評価する。ロールポリシーの検査も同じ表を読み、表示する要件を実行時のローカル認可と一致させる。リモート AuthZEN アダプターは同じポートを実装し、組み立て時に選択する。ポリシーの失敗、未定義のアクション、不正なリモートレスポンス、利用できないリモート評価器では、許可へフォールバックせず保護対象の操作を拒否する。

Cedar は実行時ポリシーの正ではない。Go 実装は既存のリクエスト形式を評価できるが、スキーマバリデーターはまだ実験的 API である。実行時の評価だけを移すと、ロールポリシー検査用の Go の要件表が残る。検証機能に安定した互換性の契約があり、1 つのポリシー表現で、2 つ目の認可の正を導入せずに実行時ルールと検査用メタデータの両方を置き換えられるようになった場合だけ、Cedar を再検討する。
