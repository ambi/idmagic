# 管理 API の認可

## 概要

この文書は、OAuth2 の管理 API の認可と、ロールポリシーの確認の仕様である。

| 項目 | 内容 |
| --- | --- |
| 責務 | 管理 API のクライアントのリソースごとのスコープによる認可、管理者が見えるロールポリシーの一覧 |
| 行為者 | 管理 API のクライアント、テナント管理者 |
| 扱わないもの | システム全体の認可は[認可設計](../../../design/security/authorization.md)が扱う |

## モデル

すべての認可の判定は AuthZEN の形式の `authorize()` ポートを通り、規則表が要件の論理積を評価する。
判定を返せない場合、事実が欠けている場合、ストアへ到達できない場合のいずれも、許可へ退避しない。

- **判断**：AuthZEN 型のポートを使う理由は、[ポリシーの境界をまたぐ認可の判断を AuthZEN 型のポートに通す](../decisions.md#ポリシーの境界をまたぐ認可の判断を-authzen-型のポートに通す)。

## 操作

### 管理 API のクライアントによる操作

#### REQ-OAUTH2-003 管理 API クライアントは OAuth リソースのスコープで許可された操作だけを実行できる

- 管理者の API アクセストークンで OAuth2 の管理 API を要求されたとき、OAuth2 は、`oauth-clients:read` で OAuth2 のクライアントの参照を、`oauth-clients:write` でその変更を、`authorization-detail-types:read` と `authorization-detail-types:write` で認可詳細の種類の参照と変更を、`mcp-resource-servers:read` と `mcp-resource-servers:write` で MCP のリソースサーバーとアプリ間アクセスの許可の参照と変更を許可する。
- 読み取りのスコープだけで変更を要求されるか、別のリソースのスコープで操作を要求された場合、OAuth2 は、403 と `insufficient_scope` で拒否する。
- トークンのテナントとリクエスト先のテナントが一致しない場合、OAuth2 は、401 と `invalid_token` で拒否する。
- `authorize()` のポートが判定を返せないか、事実が欠けているか、ストアへ到達できない場合、OAuth2 は、許可せずに拒否する。
- **例**：EX-OAUTH2-003-01、EX-OAUTH2-003-02、EX-OAUTH2-003-03、EX-OAUTH2-003-04

### 管理者によるロールポリシーの確認

#### REQ-OAUTH2-004 管理者は自身に可視なロールポリシーを確認できる

- `admin` か `system_admin` のロールを持つ管理者がロールポリシーの一覧を取得したとき、OAuth2 は、200 と、参照できるロール、権限、対応する HTTP のインターフェースを返す。
- デフォルトのテナントの管理者がデフォルトのテナントで一覧を取得したとき、OAuth2 は、システム全体のロールも含めて返す。
- `admin` も `system_admin` も持たない主体が一覧を要求した場合、OAuth2 は、403 と `access_denied` で拒否する。
- **例**：EX-OAUTH2-004-01、EX-OAUTH2-004-02

### 管理者による認可詳細の種類の管理

#### REQ-OAUTH2-051 管理者は認可詳細の種類を登録、更新、削除できる

- 管理者が認可詳細の種類を一覧か取得したとき、OAuth2 は、200 とテナントの種類を返す。
- 管理者が新しい名前の種類を作成したとき、OAuth2 は、201 と種類を返す。
- 管理者が種類を更新したとき、OAuth2 は、200 と更新した種類を返す。
- 管理者が種類を削除したとき、OAuth2 は、204 を返す。
- JSON として読めない本文か `type` のない作成を受けた場合、OAuth2 は、400 と `invalid_request` で拒否する。
- 同じ名前の種類がある作成を受けた場合、OAuth2 は、409 と `type_exists` で拒否する。
- 存在しない種類の取得か更新を受けた場合、OAuth2 は、404 と `type_not_found` で拒否する。
- 項目の規則を検証できないか、未知の項目の意味を含む種類を受けた場合、OAuth2 は、422 と `invalid_type` で拒否し、種類を保存しない。

### 管理者による MCP のリソースサーバーの管理

#### REQ-OAUTH2-052 管理者は MCP のリソースサーバーを登録、更新、削除できる

- 管理者が MCP のリソースサーバーを一覧か取得したとき、OAuth2 は、200 とテナントのリソースサーバーを返す。
- 管理者が新しい `resource` のリソースサーバーを作成したとき、OAuth2 は、201 とリソースサーバーを返す。
- 管理者がリソースサーバーを更新したとき、OAuth2 は、200 と更新したリソースサーバーを返す。
- 管理者がリソースサーバーを削除したとき、OAuth2 は、204 を返す。
- JSON として読めない本文か `resource` のない作成を受けた場合、OAuth2 は、400 と `invalid_request` で拒否する。
- 同じ `resource` のリソースサーバーがある作成を受けた場合、OAuth2 は、409 と `resource_exists` で拒否する。
- 存在しないリソースサーバーの取得か更新を受けた場合、OAuth2 は、404 と `resource_server_not_found` で拒否する。
- 検証を通らないリソースサーバーを受けた場合、OAuth2 は、400 と `invalid_resource_server` で拒否し、保存しない。

#### REQ-OAUTH2-064 管理者はリソースサーバーへ評価用のクライアントと規則を設定できる

- 管理者がテナントの機密クライアントの `client_id` と `access_rules` を指定して作成か更新をしたとき、OAuth2 は、それらを保存し、応答に含める。
- 管理者が `tool` を持つ規則を保存したとき、OAuth2 は、接続先内で一意な128文字以内のツール名、256文字以内の表示名、必要スコープ、対象抽出の整合を検証する。
- `tool` の名前か表示名が空であるか、ツール名が `:` か `#` を含むか、同じツール名が重複するか、対象別の型と関係を持つツールに対象引数がない場合、OAuth2 は、400 と `invalid_resource_server` で拒否し、保存しない。
- 従来の規則とツールを持つ規則が同じ対象型と関係へ対応する場合、OAuth2 は、400 と `invalid_resource_server` で拒否し、操作割当を迂回する対応を保存しない。
- 更新の本文に `client_id` か `access_rules` がないとき、OAuth2 は、その項目を変えない。
- `scopes` を省略か空の配列で作成したとき、OAuth2 は、`mcp` を登録の唯一のスコープとして保存する。
- **判断**：Gateway が執行する構成では、上流の MCP サーバーはスコープを検査せず、スコープは IdMagic の中だけで働く認証上限である。実行できる操作は操作割当が決めるので、管理者にスコープ名を考えさせない。サーバー自身がトークンを検査する構成では、サーバーが定めたスコープ名を指定する。
- `client_id` が、テナントにないクライアント、機密でないクライアント、同じテナントの別の登録に束縛済みのクライアントである場合、OAuth2 は、400 と `invalid_resource_server` で拒否し、保存しない。
- 規則の `resource_type` か `relation` が `^[a-z][a-z0-9_]*$` の形でないか 65 文字以上であるか、ツールを持たない規則で `resource_type` と `relation` の組が重複するか、`scopes` が空か登録の `scopes` の部分集合でないか、`requires_approved_operation` を持つ規則に `authorization_detail_type` がないか、規則が 100 件を超える場合、OAuth2 は、400 と `invalid_resource_server` で拒否し、保存しない。
- 規則の `condition` の `deny_when` か `require_approval_when` が Unicode のコードポイント数で 1024 文字を超える場合、OAuth2 は、422 と `field_length_exceeded` で拒否し、`detail` に契約上のフィールド名と上限を示し、保存しない。
- 規則の `condition` に `deny_when` と `require_approval_when` のどちらもないか、コンパイルできないか、真偽値を返さないか、内包が入れ子であるか、`require_approval_when` に `approval_detail_type` がないか、`approval_detail_type` だけがあるか、`require_approval_when` と `requires_approved_operation` を併せ持つ場合、OAuth2 は、400 と `invalid_resource_server` で拒否し、保存しない。
- 規則の `condition` を返すとき、OAuth2 は、内容から導いた `version` を含め、本文の `version` を読まない。
- 規則の `limits` が 9 件以上であるか、`by` が `agent`、`user`、`resource` 以外か重複を含むか、`max_requests` が 1 から 1000000000 の外であるか、`window_seconds` が 1 から 2592000 の外であるか、`by` の集合と `window_seconds` の組が重複する場合、OAuth2 は、400 と `invalid_resource_server` で拒否し、保存しない。

#### REQ-OAUTH2-085 ツールの削除と再登録で古い割当を再有効化しない

- 管理者がツールを新しく登録したとき、OAuth2 は、新しい操作の識別子を発行し、接続先に束縛した不透明な `assignment_resource_id` を返す。
- 公開中のツールを同名のまま更新したとき、OAuth2 は、操作の識別子を保持する。
- 管理者がツールを削除した後に同名で再登録したとき、OAuth2 は、新しい操作の識別子を発行し、削除前の割当を新しい操作の許可根拠にしない。
- 操作の識別子か割当参照を本文に指定されたとき、OAuth2 は、その値を使わず、サーバーが所有する操作の識別を使う。
- 登録を読んだ後に別の要求が登録を変更か削除した場合、OAuth2 は、409 と `resource_server_conflict` で古い更新を拒否し、操作、割当の識別、メタデータを上書きしない。

### 管理者による MCP リソースサーバーの準備

#### REQ-OAUTH2-087 管理者はカタログのツールを公開中のツールと区別して確認できる

- 管理者が `GET /api/admin/v1/mcp-resource-servers/{id}/tool-catalog` を要求したとき、OAuth2 は、200 と、最新のカタログのツール、`complete`、`received_at` を返す。
- カタログがまだない登録について要求されたとき、OAuth2 は、200 と空の `tools` を返し、`received_at` を含めない。
- 存在しない登録について要求された場合、OAuth2 は、404 と `resource_server_not_found` で拒否する。
- 管理者が登録を削除したとき、OAuth2 は、その登録のカタログも削除する。
- 管理コンソールで登録を編集するとき、OAuth2 は、カタログにあって未公開のツールを、名前と表示名を入力済みの公開の候補として示し、管理者が選ぶまで公開しない。
- `complete` が真のカタログにない公開中のツールを示すとき、OAuth2 は、そのツールを「MCP サーバーに見つからない」と表示し、自動で削除しない。
- 変更前の一覧を持つ登録について要求されたとき、OAuth2 は、`changes` に変更の時刻と、追加、削除、定義変更のツールを返す。
- 変更前の一覧が完全でない場合、OAuth2 は、差分に追加を示さない。
- 最新のカタログが完全でない場合、OAuth2 は、差分に削除を示さない。
- 両方の一覧にあるツールの `title`、`description`、`arguments` のどれかが異なる場合、OAuth2 は、異なる項目の名前と変更前の定義を定義変更として示す。
- 変更前の一覧がない登録について要求されたとき、OAuth2 は、`changes` を含めない。
- 管理コンソールで登録を編集するとき、OAuth2 は、差分の各ツールを公開中かどうかとともに示し、公開設定を変えない。
- **判断**：差分の基準は直前のカタログとし、管理者の確認状態を持たない。状態を増やさずに、公開後の説明や引数の変更に気付けるためである。

#### REQ-OAUTH2-088 管理コンソールは MCP リソースサーバーの登録で評価用のクライアントを作成して紐付け、配置の設定を示す

- 管理者が MCP リソースサーバーの登録で評価用のクライアントの新規作成を選んだとき、OAuth2 は、`client_credentials` のグラントを持つ機密のサービスクライアントを作成し、その `client_id` を紐付けた登録を作成する。
- 管理者が既存のクライアントの利用を選んだとき、OAuth2 は、テナントの機密のサービスクライアントを名前で選ばせ、`client_id` の入力を求めない。
- 作成が完了したとき、OAuth2 は、`client_id`、一度だけ表示するクライアントシークレット、`resource`、realm の URL、`mapping.catalog: true` を含む Gateway の設定の例を、管理者が次の操作を始めるまで表示し、それぞれをコピーできるようにする。
- 作成が完了したとき、OAuth2 は、Gateway の設定ファイルの保存先と、保護する MCP サーバーの URL およびシークレットを置くファイルの指定方法を説明する。
- クライアントの作成後に登録の作成が失敗した場合、OAuth2 は、作成したクライアントを保持し、クライアントを再作成せず登録の作成だけを再試行できるようにする。
- 管理者が MCP リソースサーバーを登録するとき、OAuth2 は、スコープの入力を「サーバー自身がトークンを検査する構成」の詳細設定に置き、デフォルトでは入力を求めない。
- 登録のスコープが一つだけのとき、OAuth2 は、ツールの行にスコープの選択を表示せず、そのスコープを必要なスコープにする。
- **判断**：二つの作成を画面で順に呼ぶ。資格情報の一体の作成（REQ-IDMANAGEMENT-104）と同じ部分失敗の扱いにし、新しい複合の API と組み立て地点を増やさないためである。

#### REQ-OAUTH2-090 管理コンソールはツールの承認、上限、交換先、条件を行の入力欄で編集させる

- 管理者が MCP リソースサーバーの登録を作成か編集するとき、OAuth2 は、規則の行に、人の承認の要否、認可詳細の種類、実行回数の上限、交換先の `resource`、条件の式と承認に求める明細の種類の入力欄を示す。
- 管理者が行で規則を編集したとき、OAuth2 は、入力欄のない規則の項目を変えずに保存する。
- 管理者が条件の入力欄をすべて空にしたとき、OAuth2 は、その規則の `condition` を除いて保存する。
- 行で人の承認を求め、認可詳細の種類が空である場合、OAuth2 は、送信前に認可詳細の種類の欄へ不足を示し、保存させない。
- 行の条件の各式が Unicode のコードポイント数で 1024 文字を超える場合、OAuth2 は、送信前に該当する式の欄へ理由を示し、保存させない。
- 行の入力が REQ-OAUTH2-064 の組み合わせ（人の承認と承認の条件の併用、承認の条件と明細の種類の対、承認と交換先の併用、上限の範囲と重複、https でない交換先）に反する場合、OAuth2 は、送信前に該当する欄へ理由を示し、保存させない。
- 規則の承認、上限、交換先、条件のいずれかが入力欄で表せない型である場合、OAuth2 は、その規則の制約を行で読み取り専用に示し、JSON の入力で編集させる。
- **判断**：条件の式は CEL の文字列のまま入力させ、式のコンパイルは保存時にサーバーが行う。式を部品から組み立てる入力は表せる式を限り、表せない条件を増やすので採らない。

### 管理者による MCP 接続の確認

#### REQ-OAUTH2-094 管理コンソールは Agent の権限の材料で MCP 接続の確認項目と不足の案内を示す

- 管理者が Agent の権限の材料を表示したとき、OAuth2 は、MCP リソースサーバーごとに、登録、割当、トークンの上限、一覧の取得の確認項目の状態を示す。
- OAuth2 は、登録の項目で、登録が `Active` であることと、評価用のクライアントが紐付いていることを確認する。
- OAuth2 は、割当の項目で、Agent が `active` であることと、資格情報を束縛していることと、接続先が公開中のツールを持つことと、そのツール操作への Agent 自身への割当が一つ以上あることを確認する。
- 操作の関係が取得の上限の件数に達している間、OAuth2 は、割当の項目で、割当がないとは示さず、割当を確かめられないことを示す。
- OAuth2 は、トークンの上限の項目で、割当済みの各操作について、その操作が要求するスコープをすべて含む束縛クライアントがあることを確認する。
- OAuth2 は、違反時の扱いが `require_approval` の項目の違反と、ポリシー全体の `require_approval` を、トークンの上限の不足に数えない。
- OAuth2 は、一覧の取得の項目で、Gateway の報告か直接の取得で得たカタログの `received_at` があることを確認する。
- カタログの取得に失敗した場合、OAuth2 は、一覧の取得の項目で、カタログが届いていないとは示さず、取得に失敗したため確かめられないことを示し、他の接続先と他の項目の表示を続ける。
- OAuth2 は、トークンの上限の項目で、Agent 別とテナントのデフォルトの各層のガードレールについて、次の表の拒否を、拒否した層と種類で区別して示す（違反時の扱いの省略は [REQ-OAUTH2-073](guardrail.md#req-oauth2-073-agent-が関わるトークンの発行はグラントによらず関わるすべての-agent-のポリシーで評価される) と同じく `deny` とする）。

| 拒否の種類 | 不足とする条件 |
| --- | --- |
| 資源 | `allowed_resources` があり、この接続先の `resource` を含まず、違反時の扱いが `deny` である |
| 認可詳細の種類 | `allowed_authorization_detail_types` があり、割当済み操作の規則がトークンに求める認可詳細の種類のどれかを含まず、違反時の扱いが `deny` である |
| 期限 | `expires_at` があり、表示した時刻がその時刻以降で、違反時の扱いが `deny` である |

- 管理者が Agent の権限の材料を表示したとき、OAuth2 は、不足ごとに、不足している設定と、次の表の修正先を示す。

| 不足 | 修正先 |
| --- | --- |
| 登録が `Active` でない、評価用のクライアントがない、公開中のツールがない、カタログの `received_at` がない | MCP リソースサーバーの編集画面へのリンク。カタログについては、公開されたサーバーなら編集画面の取得を、閉域のサーバーなら Gateway の設定と上流への到達を案内する |
| Agent が `active` でない | Agent の編集画面へのリンク |
| 資格情報の束縛がない、スコープを含む束縛クライアントがない | Agent の資格情報の画面へのリンク |
| 割当がない、割当を確かめられない | Agent の割当の画面へのリンク |
| Agent 別のガードレールの拒否 | Agent のガードレールの編集画面へのリンク |
| テナントのデフォルトのガードレールの拒否 | 管理 API の `PUT /api/admin/v1/agent-guardrail-default`。管理コンソールに編集画面がないため、リンクを示さない |
| カタログの取得の失敗 | 画面の再読み込み。リンクを示さない |

- **判断**：権限の材料の表示では MCP サーバーへ接続しない。到達と認証は、管理者が編集画面で取得したとき（REQ-OAUTH2-095）にだけ確かめ、その結果をカタログの有無で読む。表示のたびに外へ接続すると、閲覧が外向きの作用と流量を生むためである。

### 管理者による MCP サーバーからの取得

#### REQ-OAUTH2-095 公開された MCP サーバーからの取得は PRM が IdMagic を信頼すると宣言した宛先へだけ一覧取得用のトークンを送る

- 管理者が `POST /api/admin/v1/mcp-resource-servers/{id}/tool-discovery` を要求したとき、OAuth2 は、登録の `resource` の Protected Resource Metadata（RFC 9728）を取得し、200 と、メタデータと一覧の取得の結果と、一覧取得用の主体の `client_id` を返す。
- メタデータを取得するとき、OAuth2 は、`resource` の origin の `/.well-known/oauth-protected-resource` に `resource` の path を継いだ URL を GET する。
- path を継いだ URL が 404 を返し、`resource` の path が空でない場合、OAuth2 は、続けて path を継がない URL を GET する。
- 応答が 200 の JSON オブジェクトで、`resource` が登録の `resource` と文字列として一致し、`authorization_servers` が文字列の配列であるとき、OAuth2 は、メタデータの `status` を `found` にし、`authorization_servers`、`scopes_supported`、テナントの issuer を含むかを返す。
- メタデータの `resource` が登録の `resource` と異なる場合、OAuth2 は、`status` を `resource_mismatch` にし、メタデータの値を返さない。
- メタデータの URL がすべて 404 を返した場合、OAuth2 は、`status` を `not_found` にする。
- メタデータの応答が 200 と 404 以外か、JSON オブジェクトでないか、`authorization_servers` が文字列の配列でない場合、OAuth2 は、`status` を `invalid` にする。
- メタデータへ接続できない場合、OAuth2 は、`status` を `unreachable` にする。
- メタデータが `found` で `authorization_servers` がテナントの issuer を含むとき、OAuth2 は、[REQ-OAUTH2-096](#req-oauth2-096-一覧取得用のトークンは登録の資源だけを宛先とし-idmagic-のどの入口でも受け付けない) のトークンを付けて、登録の `resource` へ 2026-07-28 版の `tools/list` を送り、`nextCursor` をたどる。
- メタデータが `found` でないか、`authorization_servers` がテナントの issuer を含まない場合、OAuth2 は、トークンを発行せず、`tools/list` を送らず、一覧の `status` を `skipped` にする。
- 一覧の一ページ目が成功したとき、OAuth2 は、[REQ-MCPGATEWAY-011](../../mcp-gateway/features/runtime.md#req-mcpgateway-011-カタログを参照する構成は起動後に上流のツールカタログを-idmagic-へ送る) と同じ項目、切り詰め、`complete` の規則で、取得したツールを登録の最新のカタログとして [REQ-OAUTH2-086](resource-access.md#req-oauth2-086-リソースサーバーはツールのカタログを送信できカタログは公開設定を変えない) と同じく保存し、一覧の `status` を `fetched` にして件数と `complete` を返す。
- 一ページ目が 401 を返した場合、OAuth2 は、一覧の `status` を `unauthorized` にし、カタログを変えない。
- 一ページ目が 403 を返した場合、OAuth2 は、一覧の `status` を `forbidden` にし、カタログを変えない。
- 一ページ目へ接続できない場合、OAuth2 は、一覧の `status` を `unreachable` にし、カタログを変えない。
- 一ページ目が 200 と 401 と 403 以外を返すか、JSON-RPC の結果でないか、REQ-OAUTH2-086 の上限を満たさないツール名を含む場合、OAuth2 は、一覧の `status` を `invalid_response` にし、カタログを変えない。
- 外へ接続するとき、OAuth2 は、HTTPS の登録の `resource` とその origin のメタデータの URL だけへ、名前解決したすべてのアドレスを接続時に検査して接続し、非公開アドレス、環境のプロキシを使わず、リダイレクトを追わない。
- 外へ接続するとき、OAuth2 は、メタデータの本文を 64 KiB、一覧の一ページの本文を 4 MiB、一回の要求を 10 秒、取得の全体を 30 秒、ページを 10 までとし、上限を超えた要求を失敗として扱う。
- 取得が失敗したとき、OAuth2 は、自動で再試行しない。
- 取得を終えたとき、OAuth2 は、操作した管理者、登録、メタデータと一覧の `status` を持つ `McpToolDiscoveryAttempted` を発行し、トークンと応答の本文をログ、イベント、応答に含めない。
- 登録が存在しない場合、OAuth2 は、404 と `resource_server_not_found` で拒否する。
- 登録が `Active` でないか、マネージド型であるか、`resource` が利用者情報、クエリ、フラグメント、非公開の IP リテラル、曖昧な path を持つ HTTPS の URL でない場合、OAuth2 は、400 と `invalid_resource_server` で拒否し、外へ接続しない。
- 同じ登録の取得が 60 秒に 6 回を超える場合、OAuth2 は、429 と `rate_limited` で拒否し、外へ接続しない。
- 流量制限を実行できない場合、OAuth2 は、503 で拒否し、外へ接続しない。
- 管理者が MCP リソースサーバーを編集するとき、OAuth2 は、セルフホスト型の登録に「MCP サーバーから取得」の操作を示し、取得の結果をメタデータと一覧に分けて示す。
- 取得の結果を示すとき、OAuth2 は、登録にないメタデータの `scopes_supported` を「MCP サーバーの Protected Resource Metadata」と出所を付けたスコープの候補として示し、管理者が選ぶまで登録を変えない。
- 一覧が `fetched` でないとき、OAuth2 は、状態ごとの理由と、MCP サーバーの運用者が許可する一覧取得用の `client_id` を示す。
- 一覧が `fetched` のとき、OAuth2 は、カタログを読み直し、REQ-OAUTH2-087 の候補と差分を示す。
- **判断**：取得は管理者の操作だけを契機にする。閲覧や登録のたびに外へ接続しないためである。定期的な取得は扱わない。
- **判断**：PRM が IdMagic を認可サーバーとして宣言した宛先へだけトークンを送る。MCP サーバーが IdMagic のトークンを検査すると宣言していない宛先へ、IdMagic のトークンを出さないためである。

#### REQ-OAUTH2-096 一覧取得用のトークンは登録の資源だけを宛先とし IdMagic のどの入口でも受け付けない

- REQ-OAUTH2-095 で一覧を取得するとき、OAuth2 は、`sub` と `client_id` を `urn:idmagic:mcp-tool-discovery`、`aud` を登録の `resource` だけ、スコープを空、寿命を 60 秒とし、`token_use` に `mcp_tool_discovery` を持つアクセストークンを発行する。
- メタデータの `dpop_signing_alg_values_supported` が `ES256` を含むとき、OAuth2 は、取得ごとに作る P-256 の鍵へトークンを束縛し、`DPoP` の方式と証明を付けて送り、取得を終えたら鍵を保存せず捨てる。
- メタデータの `dpop_signing_alg_values_supported` が `ES256` を含まないとき、OAuth2 は、トークンを `Bearer` の方式で送る。
- 一覧取得用のトークンを提示されたとき、OAuth2 は、`/introspect` に `active: false` を返し、トークン交換の `subject_token` と `actor_token`、資源アクセスの評価、管理 API と account API の Bearer 認証で、無効なトークンとして拒否する。
- OAuth2 は、`urn:idmagic:mcp-tool-discovery` の主体へ token エンドポイントからトークンを発行しない。
- **判断**：一覧取得用の主体は IdMagic 内部だけで使い、資格情報を持たない。MCP サーバーが受け取ったトークンを IdMagic で使えないようにし、外へ出したトークンが登録の資源の外で価値を持たないようにするためである。
- **判断**：DPoP は対応を宣言したサーバーにだけ使う。トークンは IdMagic でも他の資源でも受け付けられないので、DPoP に対応しないサーバーで一覧を得られなくなる損失のほうが大きいためである。

## セキュリティ上の考慮

管理 API では、API アクセストークンにロールに加えて、リソースごとのスコープを求める。
リソースをまたぐ流用はできず、あるリソースのスコープで別のリソースを操作することはない。

## 実現方式

### アーキテクチャ

#### 認可ポリシー（AuthZEN）

AuthZEN の要求ポートと管理ロール一覧の計算および HTTP 表示は [AccessControl](../../authorization/README.md) が担当する。
要求と結果、アクション、規則、操作の生成表は仕様バインディングに置き、ローカルとリモートの評価器は組み立て地点でポートへ結ぶ。

ポリシー境界をまたぐ認可判断には、AuthZEN 型の `authorize({subject, action, resource, context})` ポートを使う。ローカル実装は、アプリケーションが定めるアクションと要件の表、および名前付きのルール関数を Go で評価する。ロールポリシーの検査も同じ表を読み、表示する要件を実行時のローカル認可と一致させる。リモート AuthZEN アダプターは同じポートを実装し、組み立て時に選択する。ポリシーの失敗、未定義のアクション、不正なリモートレスポンス、利用できないリモート評価器では、許可へフォールバックせず保護対象の操作を拒否する。

Cedar は実行時ポリシーの正ではない。Go 実装は既存のリクエスト形式を評価できるが、スキーマバリデーターはまだ実験的 API である。実行時の評価だけを移すと、ロールポリシー検査用の Go の要件表が残る。検証機能に安定した互換性の契約があり、1 つのポリシー表現で、2 つ目の認可の正を導入せずに実行時ルールと検査用メタデータの両方を置き換えられるようになった場合だけ、Cedar を再検討する。
