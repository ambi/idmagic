# OAuth2 の重要な設計判断

この文書は、OAuth2 の設計判断のうち、代替案を比べたものと、見直す条件が要るものを扱う。
一つの要件やモデルだけを正当化する判断は、機能仕様のその要件またはモデルの判断の欄に置く。

## 認可とデバイスのライフサイクルを宣言的な遷移表で表す

### 背景

認可の要求とデバイスコードは、複数の段と拒否と期限切れを持つ。
クライアントに許す遷移の集合は、標準と安全性に直結する。

### 決定

認可の要求とデバイスコードのライフサイクルは、その場の条件分岐ではなく、宣言的な遷移表で表す。
ユースケースは遷移の論理を作り直さず、表を直接使う。
リフレッシュトークンのファミリーは対象の外とし、レコードの項目と失効の規則で表す。

### 検討した代替案

| 案 | 利点 | 欠点 | 採らない理由 |
| --- | --- | --- | --- |
| 遷移をユースケースの条件分岐に書く | 表の仕組みが要らない | クライアントに許す遷移の集合が、実装のたびに暗黙にずれる | 許す遷移を一か所で読めない |

### 結果と再検討の条件

機能仕様の状態遷移の表と、実装の許す遷移が一致する。
リフレッシュトークンの状態の空間は実質 `{active, revoked, rotated}` だけで、遷移の適否より親子のローテーションのグラフが重要なので、表には載せない。
遷移にガード以上の条件が要るようになった場合に見直す。

### 関連する要件

| 要件 | 機能仕様 |
| --- | --- |
| REQ-OAUTH2-005 | [認可](features/authorization.md) |
| REQ-OAUTH2-027 | [デバイス認可](features/device.md) |

## PKCE の必須化を公開クライアントと FAPI のクライアントに限る

### 背景

PKCE は認可コードの横取りを防ぐが、RFC 6749 の時代の confidential クライアントの多くは対応していない。

### 決定

PKCE は公開クライアントと FAPI 2.0 のクライアントでは設定によらず必須とする。
そのほかの confidential クライアントでは任意をデフォルトとし、クライアントごとの `require_pkce` で必須にできる。

### 検討した代替案

| 案 | 利点 | 欠点 | 採らない理由 |
| --- | --- | --- | --- |
| すべてのクライアントに PKCE を強制する | 横取りへの防御が一様になる | 既存の confidential クライアントに移行を強いる | PKCE 非対応の連携が多く、接続のために移行を必須にすると導入を妨げる |
| confidential もデフォルトで必須とし、必要な連携だけ緩和する | 設定を省略しても PKCE が必須になる | 非対応の連携ごとに管理者の設定が必要になる | PKCE 非対応の連携が多い利用環境では、接続時の調整が増える |

### 結果と再検討の条件

公開クライアントと FAPI のクライアントでは必須条件を維持しつつ、既存の confidential クライアントの移行を強いない。
confidential のクライアント認証だけでコード注入を防げるとは限らないため、PKCE の利用を推奨する。
任意設定でも、challenge を付けて開始した交換では verifier の照合を必須とする。
OAuth 2.1 の採用により、全クライアントへの PKCE の必須化を製品の要件にする場合に見直す。

### 関連する要件

| 要件 | 機能仕様 |
| --- | --- |
| REQ-OAUTH2-005 | [認可](features/authorization.md) |

## クライアントの認証から client_secret_jwt を除く

### 背景

クライアントの認証には、FAPI 級の非対称の方式から従来の共有シークレットまで、多くの方式がある。

### 決定

`private_key_jwt`、`tls_client_auth`、`none`、`client_secret_post`、`client_secret_basic` の 5 方式に対応し、`client_secret_jwt`（HMAC）は意図的に除く。

### 検討した代替案

| 案 | 利点 | 欠点 | 採らない理由 |
| --- | --- | --- | --- |
| `client_secret_jwt` にも対応する | 既存のクライアントの選択肢が増える | `private_key_jwt` を使える場合、対称鍵による代替は能力を増やさず、リスクだけを増やす | 新しいクライアントを最も強い選択肢へ誘導できない |

### 結果と再検討の条件

新しいクライアントは非対称の方式へ誘導され、既存の環境は共有シークレットのまま移行を続けられる。
`client_secret_jwt` しか使えない主要なクライアントが現れた場合に見直す。

### 関連する要件

| 要件 | 機能仕様 |
| --- | --- |
| REQ-OAUTH2-007 | [クライアント](features/client.md) |
| REQ-OAUTH2-028 | [クライアント](features/client.md) |

## アクセストークンを JWT にしリフレッシュトークンを不透明な参照にする

### 背景

アクセストークンは検証の頻度が高く、リフレッシュトークンは失効とローテーションの扱いが重要である。

### 決定

アクセストークンは自己完結した JWT、リフレッシュトークンはデータベースに保存する不透明な参照をデフォルトとする。
リフレッシュトークンは交換のたびにローテーションし、ローテーション済みのトークンが提示されたら、ファミリー全体を失効させる。

### 検討した代替案

| 案 | 利点 | 欠点 | 採らない理由 |
| --- | --- | --- | --- |
| どちらも不透明な参照にする | 失効が即時に効く | アクセストークンの検証のたびにストアを読む | 検証の頻度に合わない |
| どちらも JWT にする | ストアが要らない | リフレッシュトークンの失効とローテーションの再利用の検知ができない | 長寿命のトークンを止められない |

### 結果と再検討の条件

失効の時と検証の時の、異なるスケーリングの特性に合わせられる。
アクセストークンの即時の失効は、イントロスペクションと失効エポックで補う。
アクセストークンの即時の失効を、すべてのリソースサーバーで求める要件が出た場合に見直す。

### 関連する要件

| 要件 | 機能仕様 |
| --- | --- |
| REQ-OAUTH2-006 | [トークン](features/token.md) |
| REQ-OAUTH2-011 | [トークン](features/token.md) |

## 同意を subject と client_id の組ごとのスコープの集合として持つ

### 背景

同意の粒度は、クライアントごと、操作ごと、スコープごとなどが考えられる。

### 決定

同意は、クライアントごとや操作ごとではなく、`(subject, client_id)` ごとに付与済みのスコープの集合として永続化する。

### 検討した代替案

| 案 | 利点 | 欠点 | 採らない理由 |
| --- | --- | --- | --- |
| 操作ごとに同意を求める | 利用者が細かく制御できる | 同意の画面が増え、利用者が内容を読まずに同意するようになる | 同意疲れを招く |

### 結果と再検討の条件

要求したスコープが既存の同意で覆えるときは同意の画面を出さず、覆えないときだけ追加の同意を求めるので、暗黙のスコープの拡大と同意疲れを避けられる。
Agent の権限のように、スコープより細かい制約は `authorization_details` で表す。
同意の対象を、スコープより細かい単位で記録する要求が出た場合に見直す。

### 関連する要件

| 要件 | 機能仕様 |
| --- | --- |
| REQ-OAUTH2-008 | [同意](features/consent.md) |

## ポリシーの境界をまたぐ認可の判断を AuthZEN 型のポートに通す

### 背景

認可の判断は、ロール、スコープ、代行チェーン、プリンシパルの有効性、関係の事実を合わせて決まる。
外部の PDP へ差し替える可能性がある。

### 決定

ポリシーの境界をまたぐ認可の判断には、AuthZEN 型の `authorize()` ポートを使う。
ローカルの Go の規則表をロールポリシーの確認にも使い、外部の AuthZEN のサービスはリモートのアダプターの背後に隔離する。
Go のスキーマの検証器が実験の段階にあり、移行の後もロールポリシーの確認のための第二の Go の認可の情報源が残る間は、Cedar を採用しない。

### 検討した代替案

| 案 | 利点 | 欠点 | 採らない理由 |
| --- | --- | --- | --- |
| Cedar の方針言語を採る | 宣言的な方針と検証の道具が使える | Go のスキーマの検証器が実験の段階で、ロールポリシーの確認のための Go の情報源が残る | 認可の情報源が二つに分かれる |

### 結果と再検討の条件

判定を返せない場合、事実が欠けている場合、ストアへ到達できない場合のいずれも、許可へ退避しない。
Cedar の Go の検証器が安定し、ロールポリシーの確認も一つの情報源に移せるようになった場合に見直す。

### 関連する要件

| 要件 | 機能仕様 |
| --- | --- |
| REQ-OAUTH2-003 | [管理 API の認可](features/admin-access.md) |
| REQ-OAUTH2-004 | [管理 API の認可](features/admin-access.md) |

## Discovery Metadata を実行時に契約から組み立てる

### 背景

Discovery Metadata は、提供するエンドポイントと能力を広告する。
広告と実装が食い違うと、クライアントが誤った方式を選ぶ。

### 決定

Discovery Metadata は、手作業でもビルドの時でもなく、実行時に契約から組み立てる。

### 検討した代替案

| 案 | 利点 | 欠点 | 採らない理由 |
| --- | --- | --- | --- |
| 手作業で書く | 仕組みが要らない | 実装とずれる | 広告を信頼できない |
| ビルドの時に生成する | 実行時の処理が要らない | 手順の省略で、生成物が古くなる | 生成物の鮮度を保証できない |

### 結果と再検討の条件

広告は、実行中のプロセスの契約と常に一致する。
メタデータを外部の配信網から静的に配る要求が出た場合に見直す。

### 関連する要件

| 要件 | 機能仕様 |
| --- | --- |
| REQ-OAUTH2-014 | [プロトコルのエンドポイント](features/protocol-endpoints.md) |

## ユーザーの代理の行為を Token Exchange による委任で表す

### 背景

Agent はユーザーに代わって操作する。
Agent はアイデンティティとライフサイクルを持つが、独自の資格情報は持たず、既存の `OAuth2Client` の登録に関連付ける。

### 決定

ユーザーの代理の行為は OAuth 2.0 Token Exchange として実装し、偽装ではなく、元の `sub` と `act` の Agent を保つ委任をデフォルトとする。
Agent ごとの権限は、粗いスコープではなく RFC 9396 の `authorization_details` で表し、後続の Token Exchange では権限を狭めることだけを許す。

### 検討した代替案

| 案 | 利点 | 欠点 | 採らない理由 |
| --- | --- | --- | --- |
| Agent がユーザーとして振る舞う偽装のトークンを発行する | リソースサーバーが代理を意識しなくてよい | 誰が操作したかが、トークンからも監査からも分からなくなる | 代理の行為を本人の操作と区別できない |

### 結果と再検討の条件

監査とイントロスペクションは、同じ規則で委譲のモードを示す。
チェーンの深さはテナントの `max_delegation_depth` で制限する。
標準の委譲の表現が、`act` と `authorization_details` から別の形へ移った場合に見直す。

### 関連する要件

| 要件 | 機能仕様 |
| --- | --- |
| REQ-OAUTH2-048 | [トークン](features/token.md) |
| REQ-OAUTH2-049 | [トークン](features/token.md) |

## Agent の操作に対する人間の承認を CIBA で実装する

### 背景

`Supervised` な Agent の操作には、人間の承認が要る。
同意とステップアップ認証は、すでに別の目的で使っている。

### 決定

Agent の操作に対する人間の承認は、同意やステップアップ認証を置き換えず、OAuth 2.0 の上の承認の機能として CIBA で実装する。
`supervised` の Agent は、REQ-OAUTH2-050 により、この承認を経ずに新しいトークンを得られない。

### 検討した代替案

| 案 | 利点 | 欠点 | 採らない理由 |
| --- | --- | --- | --- |
| 同意の画面で承認を兼ねる | 新しい仕組みが要らない | 同意は付与済みのスコープの集合であり、操作ごとの判断を表せない | 同意と承認の意味が混ざる |

### 結果と再検討の条件

承認は、標準のバックチャネル認可要求として外部の Agent から使える。
配信のモードは `poll` だけとし、`user_code` は未対応として広告する。
`ping` や `push` の配信が要るクライアントが現れた場合に見直す。

### 関連する要件

| 要件 | 機能仕様 |
| --- | --- |
| REQ-OAUTH2-041 | [承認リクエスト](features/approval.md) |
| REQ-OAUTH2-050 | [承認リクエスト](features/approval.md) |

## sid のクレームに LoginSession の ID をそのまま使う

### 背景

一つのブラウザーのセッションに、複数の RP が参加する。
セッションを失効させたとき、影響するすべての RP へログアウトを伝えなければならない。

### 決定

`sid` のクレームには、ブラウザーのセッションに参加するすべての RP が共有する `LoginSession.id` そのものを使う。

### 検討した代替案

| 案 | 利点 | 欠点 | 採らない理由 |
| --- | --- | --- | --- |
| RP ごとに別の `sid` を採番する | RP の間でセッションを相関できない | 一回のセッションの失効から、影響する RP をたどる対応表が要る | 失効の伝播が複雑になる |

### 結果と再検討の条件

一回のセッションの失効から、影響するすべての RP をたどれる。
その代わり、RP の間で同じ `sid` が共有される。
RP の間でのセッションの相関を防ぐ要件が出た場合に見直す。

### 関連する要件

| 要件 | 機能仕様 |
| --- | --- |
| REQ-OAUTH2-025 | [ログアウト](features/logout.md) |

## ID-JAG の発行と償還を既存のトークン交換から分ける

### 背景

Identity Assertion JWT Authorization Grant（draft-ietf-oauth-identity-assertion-authz-grant-05）は、IdP への Token Exchange と、リソースの認可サーバーへの JWT Bearer グラントの 2 ホップである。
IdMagic はテナントごとに発行者が分かれるので、どちらの役割にもなる。

### 決定

発行は Token Exchange の `requested_token_type` で別のユースケースへ分け、償還は `jwt-bearer` と `jwt-dpop` のグラントとして新設する。
許可は OAuth2 が所有し、Application は割り当ての関門としてだけ関わる。
受け入れ側の信頼は、SSO に使う `IdentityProviderConnection` と `FederatedIdentity` の上に置く。
`actor_token` と `act` は draft が処理を定めないので、両ホップで拒否する。

### 検討した代替案

| 案 | 利点 | 欠点 | 採らない理由 |
| --- | --- | --- | --- |
| 既存の `ExchangeToken` へ分岐を足す | 入口が一つで済む | `act` 必須やスコープの部分集合という不変条件に例外が要る | 一方の緩和がもう一方へ漏れる |
| 許可を Application が所有する | 割り当てと一か所で管理できる | `audience`、リソース、スコープというプロトコルの語彙が入る | Application はプロトコル設定を中身に依存せず参照する |
| 受け入れ側の信頼を別に登録する | SSO と独立に設定できる | 同じ発行者の一覧が二つになる | draft は SSO で信頼する IdP を前提とする |

### 結果と再検討の条件

判定の共有は Agent の区分と付与の確認に限られ、draft の改訂の波及は OAuth2 の ID-JAG のユースケースに閉じる。
Internet-Draft なので `-05` に固定し、相互運用は主張しない。
RFC になったとき、または `actor_token` のプロファイルが定まったときに見直す。

### 関連する要件

| 要件 | 機能仕様 |
| --- | --- |
| REQ-OAUTH2-066 | [トークン](features/token.md) |
| REQ-OAUTH2-069 | [トークン](features/token.md) |

## MCP の接続先をサーバー単位で保ち集約ポータルを追加しない

### 背景

MCP ゲートウェイは、呼び出しごとに主体、操作と対象を評価し、許可した要求だけを上流へ送る。
一方、MCP サーバーポータルには、利用者が接続先と設定手順を探す画面と、複数サーバーの機能を一つの MCP エンドポイントへ集める実行機能という、別々の役割がある。
どちらの追加も、既存の認可と転送があることだけでは必要と決まらない。

同種の製品は、次のように公開の単位と接続管理を選んでいる。
調査日は 2026-11-29 であり、公式文書の本文と、記載した範囲の OSS の実装を読んだ。
実製品への接続や負荷を測定した結果ではない。

| 製品と出典 | 確認した扱い | 判断への示唆 |
| --- | --- | --- |
| [Cloudflare MCP server portals](https://developers.cloudflare.com/cloudflare-one/access-controls/ai-controls/mcp-portals/) | 概要、登録、上流 OAuth、同期、公開対象と別名、接続とセッション管理、Code Mode、ポリシー制約の本文。一つの MCP 接続先に複数サーバーを集約し、接続手順のホームページも提供する。 | 集約と接続案内は別に評価できる。公開対象の選択、本人の資格情報、認可の単位を確認してから比較する。 |
| [Azure API Management の既存 MCP サーバーの公開](https://learn.microsoft.com/en-us/azure/api-management/expose-existing-mcp-server) | 制約と登録手順の本文。サーバーごとに上流と経路の接頭辞を登録して公開 URL を得る。外部サーバーの tools と resources に対応し、prompts は対象にしない。 | サーバーごとの公開でも接続と統制を提供できる。すべての MCP 機能をそろえることは必須条件ではない。 |
| [IBM ContextForge の管理概念](https://ibm.github.io/mcp-context-forge/overview/ui-concepts/)と[仮想サーバーの登録処理](https://github.com/IBM/mcp-context-forge/blob/612778b87cefc96583c4af9375bca0ce436a1877/mcpgateway/services/server_service.py#L654) | Virtual Servers と Gateways の本文、および固定コミットの `register_server`。選択した tools、resources、prompts を仮想サーバーに関連付けて保存する。 | 集約は公開する集合の所有と更新を伴う。画面の追加だけでは完結しない。 |

### 決定

独立した MCP サーバーポータルは追加せず、既存ゲートウェイの一覧を操作割当と対応させ、接続案内と本人の接続の復旧を改善する。
マネージド型は、資源登録ごとの公開 URL と一つの上流設定を持つ構成を保つ。
閉域での配置が必要な場合は、別配布のセルフホスト型を使う。

現在の構成で扱う利用経路と、追加しない機能は次のとおりである。
「公開」は実行を許可する操作の登録を指す。
マネージド型とカタログを使う `proxy` は、公開と現在の操作割当を満たすツールの定義だけを一覧に残す。
一覧の表示は実行許可ではなく、対象、引数、条件、承認と上限は呼び出し時に再評価する。

| 利用経路または候補 | 現在の扱いと採否 |
| --- | --- |
| 管理者が接続先を準備する | MCP リソースサーバーの管理画面で配置方法を選び、マネージド型では公開 URL を得る。ツールのカタログを公開設定と分け、操作の割当と条件を管理する。 |
| Agent が許可された操作を呼ぶ | 接続先を指定し、その登録の規則、現在の割当、対象と引数、条件、上限と承認を評価する。複数の接続先を使う場合も、各登録の URL と認可を使う。 |
| 本人の上流 OAuth 資格情報を使う | TokenVault のコネクタを管理者が設定し、本人が外部サービス接続画面で接続、再連携、解除を行う。接続不足と更新拒否には、その画面への復旧の案内を返す。上流の 401 は資格情報の拒否として再連携と管理者の設定確認を案内し、接続の失効とは断定せず、自動再送しない。上流 DCR とクライアント内での認証の自動開始は行わない。 |
| 認証なしの上流や閉域の上流へ接続する | マネージド型の上流認証は Token Exchange と TokenVault に限る。資格情報を付けずに転送する構成や閉域の上流には、セルフホスト型を使う。Cloudflare のネットワーク接続基盤に相当する中継は追加しない。 |
| 利用者が接続の設定を得る | 管理者が登録結果と一覧の詳細から、保存済みの接続 URL、対応条件と準備手順を得て配る。本人向けのサーバー一覧は設けない。可視性を本人と Agent の実行権限と別に管理する状態を増やさず、配布先は管理者が決める。自分で接続先を探すセルフサービスは提供しない。 |
| 複数サーバーを一つの URL にまとめる | サーバーごとの URL と操作割当を使い、集約と用途別の公開集合、別名を追加しない。配布の一本化より、元の資源ごとの audience、承認と公開名の意味を直接保つことを選ぶ。公開集合、同名ツールの対応、上流ごとの部分障害を扱う追加の状態は持たない。URL の配布とクライアント設定はサーバー数に比例し、一つの URL しか使えないクライアントは対応対象外になる。 |
| 上流の機能を同期する | セルフホスト型のカタログ報告と公開 URL からの管理者による取得を使う。マネージド型では上流のツール名と必要な権限を管理者が登録し、スキーマを保存せず毎回の本人の一覧から最新の定義を返す。本人の接続で取得した部分集合をテナント全体のカタログにしない。管理者用の共有資格情報を持つ同期も提供せず、上流の追加や改名は管理者が反映する。 |
| ツール一覧を絞り込み、名前や説明を変える | マネージド型とカタログを使う `proxy` の一覧を現在の操作割当とスコープで絞る。定義とカーソルを保ち、名前と説明は書き換えない。応答本文を扱わない Envoy の `ext_authz` と独自マッピングの構成は絞り込みを提供しない。 |
| prompts、resources、MCP Apps を扱う | 業務操作とデータ取得を、公開したツールとその引数への認可で統制する範囲を採る。URI とテンプレートへの参照と購読、prompt の取得、アプリの埋め込みには別の認可と安全性のモデルが要るため提供しない。これらを必要とするサーバーは対応対象外になる。 |
| 2025 版と legacy SSE を扱う | 2026-07-28 の stateless HTTP と鏡写しヘッダーを使う Agent を対象にする。2025 の初期化、セッションと GET 通知を変換すると、認可した要求と変換後の実行の対応も所有する必要がある。毎回の本文の検査を保ち、現在の公式 SDK で接続を検証する。任意のデスクトップ製品の互換性は主張せず、対応条件を接続案内にも表示する。 |
| 検索と Code Mode でコンテキストを減らす | 現在の割当により候補を減らし、元のページングとクライアントの選択を使う。検索専用ツールと隠した定義の実行を仲介する別の契約は追加しない。ツール数による支障は測定してから検索を選ぶ。Code Mode は任意コードの隔離された実行基盤と、各上流呼び出しへの承認と監査を編成する責務を増やすため見送る。 |

本人の接続の選択と解除は TokenVault、資源登録と評価は OAuth2 が引き続き所有する。
ポータルの追加を前提にして、共有の管理者資格情報、自動公開、非 OAuth の資格情報、認証方式の追加を先行させない。
これらは、それぞれの必要性と保証から判断する。

### 検討した代替案

| 案 | 利点 | 欠点 | 採らない理由 |
| --- | --- | --- | --- |
| 既存ゲートウェイに複数上流の集約を加える | 一つの接続設定で複数の上流を使える | 公開名と元の操作の対応、資源と承認の束縛、上流ごとの認証、部分障害と一覧の整合が必要になる | サーバー単位の資源と割当を保ち、配布する URL の増加を受け入れる。用途別の集合という追加の許可層を持たない |
| 独立した集約ポータルを設ける | 資源登録を保ったまま、用途別の公開集合を独立に管理できる | 所属と別名、削除と失効、カタログ、セッションを所有する状態と公開契約が増える | 登録と認可は OAuth2、本人の接続は Vault が所有する。採用した案内と復旧は既存の所有者で完結する |
| 接続案内を既存画面に加える | 管理者が保存済みの値から手順を配り、再訪して確認できる | 管理者からの配布は残る。本人向けの発見はできない | 採用。新たな可視集合を所有せず、登録と復旧の既存経路を結べる |
| 上流を自動登録しカタログを同期する | 管理者の入力と上流の改訂を追う負担を減らす | DCR のクライアントと秘密の更新、共有の管理者接続、同期に使う主体の可視範囲を扱う必要がある | 本人の上流 OAuth 接続を Agent の代行にだけ使う設計を保つ。手動のツール公開とライブの定義の取得で呼び出せる経路を採る |
| URL elicitation で上流認可を自動継続する | MCP クライアント内から認証を進めやすい | 対話した本人、元の引数と単回使用の承認に束縛した継続を追加する必要がある | 現在は接続の不足を示すエラーと本人の画面へのリンクで復旧する。Agent は連携を開始せず、本人の対話セッションが既存の認可を開始する |

### 結果と再検討の条件

資源登録、操作割当、本人の接続、承認の境界を保ち、公開 URL と保存済み設定の移行を生じさせない。
上流ごとの呼び出しは独立するが、一つの API プロセスでの資源や障害の隔離を保証するものではない。
また、ゲートウェイを通さない直接接続の防止には、既存どおり上流の鍵の束縛、資格情報の管理、またはネットワークの制限が必要である。

次のいずれかが具体化したとき、追加する対象を選び直す。

- 管理者から URL を配る方法では運用できず、利用者が自身に見える接続先と設定を探す必要がある。その場合は、可視性と対象クライアントを定め、転送を持たない一覧から比較する。
- 一つの MCP 接続先しか設定できないクライアント、または用途別の公開集合を複数サーバーにまたがって配布する運用が必要になる。その場合は、各操作を元の登録へ対応付ける集約を比較する。
- 操作割当による絞り込みに加えて、用途別に候補を減らす必要があるか、ツール数とコンテキスト量が支障になる。その場合は、別の公開集合や検索を比較する。
- prompts、resources、上流の認証の誘導、別のプロトコルを必要とする実際の利用経路が確認される。その場合は、必要な機能と transport の対応を先に確かめる。

集約を選び直す場合も、ポータルの作成自体を新しいモジュールの根拠にしない。
公開集合やセッションを独立して更新する必要、状態の所有者、公開する契約、削除と失効の作用を、境界を選ぶ判断手順で比較する。
