# McpGateway の重要な設計判断

この文書は、McpGateway の設計判断のうち、代替案を比べたものと、見直す条件が要るものを扱う。

## 運用場所を段階的に増やす

### 背景

Okta Agent Gateway は Okta がホストし、導入側に配置の作業がない。
PingGateway は導入側が設置し、閉じたネットワークの MCP サーバーも保護できる。
IdMagic の Gateway は導入側が設置するので、初期構築の比較で Okta より重い。

運用場所によって、Agent が Gateway を迂回できない理由が変わる。

| 運用場所 | 運用者 | 迂回を防ぐ仕組み | 保護できる上流 |
| --- | --- | --- | --- |
| MCP サーバーの近く | MCP サーバーの運用者 | ネットワーク。上流をループバックか Gateway からだけ届く場所に置く | 自身が運用する上流 |
| 専用ホスト | 利用者の管理者 | 上流が Gateway の下流の鍵に束縛したトークンだけを受け付ける | IdMagic の発行したトークンを受け付ける上流 |
| IdMagic がホストする | IdMagic | 上流の資格情報を IdMagic だけが持つか、上流が IdMagic の下流の鍵に束縛したトークンだけを受け付ける | IdMagic から届く上流 |

### 決定

MCP サーバーの近くに置く構成と専用ホストの構成を、現行の Gateway で支える。
専用ホストの迂回の防止の条件は、[セキュリティ上の考慮](features/runtime.md#セキュリティ上の考慮)に置く。
IdMagic がホストする構成は採ると決め、設計と実装を別の作業項目で行う。

自前設置の構成で、設定を IdMagic から配信する仕組みは採らない。
管理画面は登録の直後に設定ファイルを示し、`mapping.catalog` によって操作の対応は IdMagic 側で変わるので、割当の変更で Gateway を再設定しない。
残る設定項目（`listen`、`upstream`、シークレットのファイル、`downstream` の鍵）は配置先でだけ決まり、配信しても入力は減らない。

### 検討した代替案

| 案 | 利点 | 欠点 | 採否 |
| --- | --- | --- | --- |
| 自前設置だけを保つ | 現行のまま。閉じたネットワークの上流も保護できる | 配置の作業が残る | 不採用。初期構築の比較で重いままになる |
| ホスト型だけにする | 配置の作業がない | 閉じたネットワークの上流へ届かない。業務データと上流の資格情報が IdMagic を通る | 不採用。データと資格情報を手元に置く選択がなくなる |
| ホスト型と導入側の中継を組み合わせる | 閉じたネットワークの上流にも配置なしに近い形で届く | 中継の配置が別に要り、構成が増える | 保留。ホスト型の利用を見てから判断する |
| 専用ホストで上流の到達をネットワークで止める | 上流を変えずに済む | 社外の上流はインターネットから届き、止められない | 不採用。上流の鍵の検査で防ぐ |

### 結果と再検討の条件

専用ホストは、IdMagic の発行したトークンを受け付け、`cnf.jkt` を検査できる上流に限られる。
API キーや独自の OAuth を求める上流を、Agent へ資格情報を渡さずに保護するには、ホスト型か、非 OAuth の資格情報の仲介が要る。
IdMagic 側で変える Gateway の設定項目が増え、配置後の再設定が利用者の作業になったときに、設定の配信を見直す。
