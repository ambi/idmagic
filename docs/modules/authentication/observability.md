# Authentication のオブザーバビリティ

この文書は、ログイン、多要素認証、フェデレーション、セッションが共有する、認証のイベントの記録と保持の仕組みを扱う。
監査の記録の検索は `Audit` が扱う。

## 認証のイベントの記録

認証のイベントは二つの系統で保持し、攻撃による急増で監査のストアが過負荷になったり、重要な兆候が埋もれたりすることを防ぐ。

| 系統 | 内容 |
| --- | --- |
| `authentication_events` | 個々の操作（成功、失敗、MFA、フェデレーション、セッションの開始）を 1 レコードずつ記録する |
| `authentication_event_buckets` | 同じ `(tenant, kind, keyHash)` から続く集中を 5 分単位で集約し、レコードを増やさず `count` を更新する |

アカウントまたは IP がログインの試行の制限値に達した後は、失敗ごとの `AuthenticationFailed` を発行せず、集計の側へ回す。
スロットルのカウンターと、テナントに固有のソルトを使った同じ `keyHash` を共有するので、平文を公開せずに両者を照合できる。

集計の閾値（5 分の時間の窓。デフォルトでアカウント 10 回、IP 50 回、テナント 1000 回の失敗。テナントごとに上書きできる）は、ふつうの打ち間違いを個別のイベントとして見えるように保つことと、本物の氾濫が延々とレコードを書き続けるのを許さないことの釣り合いを取る。
各時間の窓は、ちょうど一つの `AuthenticationEventAggregated` の管理用のイベントを発行し、同じ窓の以後の発生は `count` を増やすだけである。
管理者はその行から、同じ鍵についての個別の失敗の見本を最大 10 件までたどれる。

なりすましのイベント（`SessionImpersonationStarted` と `Ended`）は、集計へたたみ込まず、短い保持期間にも入れない。
管理者がユーザーとして振る舞ったことを記録するものであり、そのユーザーを守るために手を加えずに残すからである。

## 相関と保持

確定したアカウントに結び付くイベント（`UserAuthenticated` や OAuth2 の流れのイベント）は `user_id` で相関し、管理者がユーザー名で検索するときは、その場で `user_id` に解決する。
ユーザー名、IP、User-Agent、端末の指紋は、各イベントの通常の保持期間の間は平文で保存し、`AuthenticationFailed` のユーザー名も 30 日間保持する。
所在地は国コードだけを保存する。
`LoginThrottled` と集計では、テナントごとのソルトを使った `keyHash` を、スロットルと集計の鍵として使うが、監査の上の個人識別情報の項目としては扱わない。

`tenant_correlation_salts` はテナントごとのシークレットで、利用者名や IP の相関用のハッシュ（`SaltedHash`）と、スロットルや集計の `keyHash` の算出に使う。
相関がテナントをまたいで集約されることはない。
あらかじめ用意するのではなく、最初に使うときに生成する。

認証のイベントの監査の記録は、Audit が定める種類ごとの保持期間（[監査の記録の保持](../audit/features/event-retention.md#モデル)）だけ残る。
個別の失敗は 30 日、集計、セッションの終了、MFA は 90 日、成功となりすましはデフォルトの 365 日である。

Authentication が所有する記録は、`idmagic-batch retention-sweep` の冪等な一括の掃除で次の期間を過ぎたものを消す。

| 記録 | 保持期間 |
| --- | --- |
| 集計の窓（`authentication_event_buckets`） | 窓の開始から 90 日 |
| ログインセッション | 有効期限から 90 日 |
| 既知のサインイン端末 | 最後に見た時刻から 365 日 |

検索の性能は、掃除によるレコードの数の抑制、`(tenant_id, occurred_at)` の索引、クエリの `limit` で確保する。
