# パスワード

## 概要

この文書は、パスワードのポリシー、変更、有効期限、リセットの要求と引き換えの仕様である。

| 項目 | 内容 |
| --- | --- |
| 責務 | パスワードのポリシーの評価、本人による変更、有効期限による変更の強制、リセットの要求の流量の制限、メールのリンクによる再設定 |
| 行為者 | EndUser、本人 |
| 扱わないもの | パスワードによるログインそのものは[ログイン](sign-in.md)が扱う |

## モデル

パスワードのポリシーは NIST SP 800-63B-4 §3.1.1.2 に従う。

| 規則 | 内容 |
| --- | --- |
| 長さ | `min_length=12`、`max_length=128` |
| 識別子との照合 | ユーザー名、メールアドレス、その local part との大文字と小文字を無視した照合。誤検知を避けるため、4 文字未満の識別子は照合しない |
| 辞書 | 同梱するよくあるパスワードの辞書。任意で HIBP の k-匿名性による照合を重ねる |
| 履歴 | パスワードの変更は、直近 5 件（`history_depth=5`）のハッシュの再利用を拒否する。照合は変更のときだけで、初回の登録では行わない |
| 構成の規則と定期の変更 | 要求しない |

長さ、履歴の深さ、有効期限は、テナントごとに上書きできる（`PasswordPolicyOverride`）。
省いた項目は全体のデフォルトを継承し、パスワードの変更、リセット、管理者によるユーザーの作成のすべてで、解決後の同じポリシーを評価する。
上書きは厳しくする方向に限り、全体のデフォルトより短い `min_length`、長い `max_length`、浅い `history_depth` は拒否する。

パスワードの有効期限（`max_age_days`、30〜3,650 日）は、デフォルトで無効なテナント単位の選択であり、`max(password_changed_at, テナントのポリシーの更新時刻)` から測る。
期限切れでも認証自体は成功させ、`update_password` の必須の操作を付与し、変更またはリセットが成功すると解除する。
パスワードの資格情報を持たないユーザーは対象の外である。

- **判断**：構成の規則を設けない理由は、[パスワードに文字種の構成の規則を設けない](../decisions.md#パスワードに文字種の構成の規則を設けない)。
- **判断**：有効期限を測る起点にテナントのポリシーの更新時刻を含めるのは、設定を有効にした直後に既存のユーザーのパスワードが一斉に期限切れになることを防ぐためである。

## 操作

### 利用者によるログインの後の変更の強制

#### REQ-AUTHENTICATION-024 有効期限を過ぎたパスワードのユーザーは次回ログイン後にパスワード変更を強制される

- テナントが `max_age_days` を設定している間、`password_changed_at` とテナントのポリシーの更新時刻の遅い方から `max_age_days` を過ぎたパスワードの資格情報を持つ User が正しいパスワードでログインしたとき、Authentication は、ログインを成功させ、必須操作 `update_password` を付け、`UserRequiredActionSet` を発行し、変更を終えるまで認可を続けさせずにパスワードの変更の画面へ進ませる。
- `update_password` を持つ User がポリシーを満たす新しいパスワードへ変更またはリセットしたとき、Authentication は、`update_password` を外す。
- `max_age_days` を設定していないか、期限の前か、パスワードの資格情報を持たない User のログインでは、Authentication は、`update_password` を付けない。
- **例**：EX-AUTHENTICATION-024-01、EX-AUTHENTICATION-024-02、EX-AUTHENTICATION-024-03、EX-AUTHENTICATION-024-04、EX-AUTHENTICATION-024-05

### 本人によるパスワードの変更

#### REQ-AUTHENTICATION-010 ユーザーは現在のパスワードを確認して新しいパスワードへ変更できる

- ステップアップ認証が有効な間、本人が正しい現在のパスワードとポリシーを満たす新しいパスワードを送ったとき、Authentication は、パスワードを変え、`password_changed_at` を更新し、パスワードの履歴に加え、本人の信頼済みデバイスをすべて失効させ、204 を返し、`PasswordChanged` を発行する。
- パスワードを検証するとき、Authentication は、テナントの上書きを解決したポリシー（長さ 12 文字以上 128 文字以下、4 文字以上のユーザー名、メールアドレス、その local part を大文字と小文字を区別せずに含まない、同梱の辞書にない）を評価し、文字種の構成の規則と定期の変更を求めない。
- ポリシーに反する新しいパスワードを受けた場合、Authentication は、422 と `password_policy` で、違反した規則とともに拒否し、パスワードを変えない。
- 直近 5 件（テナントの `history_depth`）の履歴に一致する新しいパスワードを受けた場合、Authentication は、422 と `password_reuse` で拒否し、パスワードを変えない。
- 現在のパスワードが一致しない場合、Authentication は、403 と `access_denied` で拒否する。
- ステップアップ認証が有効でない場合、Authentication は、403 と `step_up_required` で拒否する。
- 認証済みのセッションがない場合、Authentication は、401 と `authentication_required` で拒否する。
- **例**：EX-AUTHENTICATION-010-01、EX-AUTHENTICATION-010-02、EX-AUTHENTICATION-010-03

### 利用者によるパスワードのリセット

#### REQ-AUTHENTICATION-016 ユーザーはメールのリセットリンクでパスワードを再設定する

- 利用者が登録済みのメールアドレスでリセットを要求したとき、Authentication は、30 分で期限の切れるトークンのリセットのリンクをそのアドレスへ送る。
- リセットのリンクの送信を試みたとき、Authentication は、送信の成否によらず、`purpose` を `password_reset`、`delivered` を送信の成否とする `EmailSent` を発行する。
- 利用者が未登録のメールアドレスでリセットを要求したとき、Authentication は、登録済みのアドレスと区別できない応答を返し、メールを送らない。
- リセットのリンクを `GET` か `HEAD` で読まれたとき、Authentication は、トークンを消費せず、パスワードを変えない。
- 利用者が有効なトークンとポリシーを満たす新しいパスワードを送ったとき、Authentication は、パスワードを変え、トークンを使用済みにし、200 を返し、`PasswordChanged` を発行し、以後の新しいパスワードのログインを成功させる。
- 期限切れか、不正か、確定済みか、別の用途で発行したトークンを受けた場合、Authentication は、410 と `invalid_reset_token` で拒否し、パスワードを変えない。
- ポリシーに反する新しいパスワードを受けた場合、Authentication は、422 と `password_policy` で違反した規則とともに拒否し、トークンを未使用のまま残す。
- 履歴に一致する新しいパスワードを受けた場合、Authentication は、422 と `password_reuse` で拒否する。
- **例**：EX-AUTHENTICATION-016-01、EX-AUTHENTICATION-016-02、EX-AUTHENTICATION-016-03、EX-AUTHENTICATION-016-04、EX-AUTHENTICATION-016-05、EX-AUTHENTICATION-016-06

#### REQ-AUTHENTICATION-008 パスワードリセットの要求は識別子と IP の組で流量制限される

- 利用者がパスワードのリセットを要求したとき、Authentication は、User が存在するかによらず 204 を返し、`PasswordResetRequested` を発行する。
- 同じ識別子と IP の組で、流量の時間枠の上限に達している場合、Authentication は、429 と `rate_limited` を `Retry-After` とともに返し、リセットのリンクを送らない。
- **例**：EX-AUTHENTICATION-008-01、EX-AUTHENTICATION-008-02

## セキュリティ上の考慮

パスワードを忘れた場合の流れのレスポンスは、メールアドレスが存在するか、未確認か、打ち間違いかによらず、すべて同じ `204` である。
メールの配送は最大限の努力であり、送信の失敗が呼び出し元に現れることはなく、記録だけに留まる。
復旧の流れが利用者名の存在を暴く手段にも、認証されていない側から SMTP の障害を探る手段にもならない。

リセットのトークンの拒否の理由（用途の違い、ダイジェストの不一致、期限切れ、消費済み）は、返るエラーの連鎖に残すが、外部のレスポンスでは区別しない。
理由を出し分けると、リセットのリンクが有効なアカウントを探る手段になるからである。

## 実現方式

### アーキテクチャ

パスワードを忘れた場合の処理は、単回限りの 32 バイトの乱数のトークンを発行し、`password_reset_tokens` には SHA-256 のハッシュとしてだけ保存する（`ttl=1800s`）。
トークンは共通のアクショントークンの核が発行し検証する（[バックエンド設計](../../../design/application/backend.md#アクショントークン)）。
このモジュールではパスワードという用途に固有の作用だけを実装し、目的の束縛、有効期限、ダイジェストだけの保存を自前で書かない。
引き換えでは、パスワードの変更と同じ検証、履歴、漏洩の一連の処理を通す。

`BreachedPasswordChecker` は、同梱の辞書に加えて HIBP の Range API を使える。
k-匿名性を保つため、外部へ送るのは SHA-1 の接頭辞だけである。
デフォルトは何もしないアダプターで、`breached_password_check_enabled=false` とするので、外部への依存を持ち込まない。

メールは `EmailSender` のポートを通じて配送する。
本番のアダプターは送信サービスごとの HTTP の SDK ではなく SMTP を使い、デフォルトで STARTTLS を求め、PLAIN の認証は TLS の上でだけ許す。
送信の前に CRLF と NUL を除き、HTML の本文へ差し込む値を無害化し、件名を RFC 2047 で符号化して、SMTP のヘッダーや HTML への注入を防ぐ。

### データ

履歴は、`password_hash` と同じ Argon2id の PHC の文字列として `password_histories` に保存する。
別の符号化にしても攻撃の費用は上がらず、二重の保守が増えるだけだからである。
履歴は登録時とパスワードの変更時の両方で書き込む（初回と同じ値への変更も検出できるようにするため）。

パスワードのハッシュの復号は、コスト、salt、digest の長さをすべて範囲に収めてから argon2 へ渡す。
`argon2.IDKey` は繰り返しの回数と並列度が 1 未満だとパニックし、鍵の長さが 0 だと内部で nil の blake2b の digest をつかんで落ちる。
保存済みのハッシュの 1 レコードが壊れているだけで、検証の経路が止まってはならない。

### 信頼性

トークンの使用済み化と、パスワードおよび履歴の保存は、一つのトランザクションで確定する。
分けると、同じリンクで二度パスワードが変わる状態か、パスワードの規則や履歴の照合で拒否された利用者がリンクだけを失う状態のどちらかが起きる。
後者は、正当な利用者から回復の手段を奪うという点で、拒否そのものより重い。
したがって、作用の前にトークンを消費せず、作用が失敗したときはトークンを未使用のまま残す。

漏洩の照合はフェイルオープンとし、タイムアウトや障害では資格情報の変更を止めず `breached=false` を返すが、障害自体は監査用に記録する。
