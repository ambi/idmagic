# 属性スキーマ

## 概要

この文書は、テナントごとのユーザー属性とグループ属性のカスタム定義の仕様である。
公開 API の分類、規範 ID とイベント名は Tenancy に残し、HTTP、更新の判断と保存の実装は IdManagement が担当する。

| 項目 | 内容 |
| --- | --- |
| 責務 | ユーザー属性スキーマとグループ属性スキーマの保存と取得 |
| 行為者 | テナント管理者 |
| 扱わないもの | 属性定義そのものの形式と、属性値の検証は `IdManagement` が扱う |

## モデル

ユーザー属性スキーマ（`TenantUserAttributeSchema`）とグループ属性スキーマ（`TenantGroupAttributeSchema`）は、テナントごとに一つずつあり、`Tenant` とは別に保存する。

- **判断**：グループ属性スキーマをユーザー属性スキーマと統合せず、別の Aggregate とする。`Group` には照合先となる組み込みのカタログが存在せず、User と Group の定義を別々に更新できるためである。
- **判断**：`Tenant` に埋め込まない理由は、[外装と属性スキーマを Tenant から独立した Aggregate にする](../decisions.md#外装と属性スキーマを-tenant-から独立した-aggregate-にする)。

## 操作

### テナント管理者によるユーザー属性スキーマの更新

#### REQ-TENANCY-002 管理者はテナント固有のユーザー属性スキーマを定義できる

- テナント管理者がユーザー属性スキーマを保存したとき、Tenancy は、カスタム属性の定義の全体を要求の定義で置き換え、200 と保存したスキーマを返し、保存した属性のキーの一覧を載せた `TenantUserAttributeSchemaUpdated` を発行する。
- テナント管理者がユーザー属性スキーマを保存したとき、Tenancy は、要求にない属性の定義を削除する。
- テナント管理者がユーザー属性スキーマを取得または保存したとき、Tenancy は、カスタム属性の定義（`attributes`）と組み込みの属性の定義（`builtin`）を別々に返す。
- カスタム属性を定義していないテナントでは、テナント管理者がユーザー属性スキーマを取得したとき、Tenancy は、`attributes` を空の配列で返す。
- 組み込みの属性とキーが衝突する定義、キーが重複する定義、`IdManagement` が定める属性定義の形式に反する定義を指定された場合、Tenancy は、422 と `invalid_attribute_schema` で拒否する。
- テナント管理者が属性を `unique` に変える保存をしたとき、Tenancy は、その属性の既存の値を、以後の保存が重複を拒否する一意性の対象に加える。
- 削除されていない二人以上の User が同じ値を持つ属性を `unique` に変える保存を要求された場合、Tenancy は、409 と `attribute_values_not_unique` で拒否する。
- 保存を拒否した場合、Tenancy は、スキーマを変えず、イベントを発行しない。
- **例**：EX-TENANCY-002-01

#### REQ-TENANCY-043 動的グループの規則が参照するユーザー属性は、削除も型の変更もできない

- 動的グループの規則が参照する属性を削除する保存と、その属性の型を変える保存を要求された場合、Tenancy は、409 と `attribute_referenced_by_dynamic_group` で拒否し、スキーマを変えず、イベントを発行しない。
- 動的グループの規則が参照しない属性を削除する保存と、その属性の型を変える保存を要求されたとき、Tenancy は、その保存を受け付ける。
- **例**：EX-TENANCY-043-01、EX-TENANCY-043-02、EX-TENANCY-043-03

### テナント管理者によるグループ属性スキーマの更新

#### REQ-TENANCY-020 管理者はテナント固有のグループ属性スキーマを定義できる

- テナント管理者がグループ属性スキーマを保存したとき、Tenancy は、カスタム属性の定義の全体を要求の定義で置き換え、200 と保存したスキーマを返し、保存した属性のキーの一覧を載せた `TenantGroupAttributeSchemaUpdated` を発行する。
- カスタム属性を定義していないテナントでは、テナント管理者がグループ属性スキーマを取得したとき、Tenancy は、`attributes` を空の配列で返す。
- キーが重複する定義と、`IdManagement` が定める属性定義の形式に反する定義を指定された場合、Tenancy は、422 と `invalid_attribute_schema` で拒否し、スキーマを変えず、イベントを発行しない。
- **例**：EX-TENANCY-020-01、EX-TENANCY-020-02

## 実現方式

### アプリケーション

IdManagement が、属性定義の型、組み込みの属性、管理 HTTP と更新ユースケースをまとめて担当する。
User と Group の各スライスが、自身の定義の検証と保存を行う。
User の更新ユースケースは、同じモジュールの Group の保存先から動的規則を読み、参照している属性の削除と型変更を拒否する。
HTTP は共有の管理者解決で admin または system_admin の有効ロールと要求テナントへの所属を確かめ、更新ではブラウザー要求も検証する。
参照の照会、変更の拒否、定義の検証、保存、イベントの発行という既存の順序を保つ。
イベントは保存の成功後に HTTP が発行し、既存の Tenancy のイベント型を使う。

### データ

保存先のテーブルとアダプターは IdManagement が所有する。
管理 API と User、Group、クレームの評価は同じ定義と保存先を使う。
スキーマの更新と動的 Group の参照検査を、一つの新しいトランザクションへまとめない。
