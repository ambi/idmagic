# リソース上限

## 概要

この文書は、テナントごとのリソース上限のデフォルト値、上書き、使用量の計数、超過時の拒否の仕様である。

| 項目 | 内容 |
| --- | --- |
| 責務 | 上限のデフォルト値と上書き、使用量の加算と減算、超過する作成の拒否 |
| 行為者 | System 管理者（上限の変更）、テナント管理者（自身の上限と使用量の参照）、リソースを作成する各モジュール（上限の確認） |
| 扱わないもの | 上限を確認する契機。各リソースを作成するモジュールが、作成のトランザクションの中で確認を呼び出す |

## モデル

リソースの作成には、テナントごとの上限を設ける。
共有基盤の上で、負荷の高い、または暴走した一つのテナントが及ぼす影響の範囲を抑えるためである。
上限は、強制の方法によって二つに分かれる。

| 種類 | リソース | 超過したとき |
| --- | --- | --- |
| Hard | `users`、`groups`、`agents`、`applications`、`oauth2_clients`、`active_sessions`、`consents`、`active_jobs`、`ssf_streams` | 作成のトランザクションの中で同期的に確認し、操作を拒否する |
| Soft | `audit_events_retained`、`export_artifacts_bytes` | 操作を成功させ、非同期の警告と監査イベントを発行する |

- **判断**：二つに分ける理由は、[リソース上限を Hard と Soft に分ける](../decisions.md#リソース上限を-hard-と-soft-に分ける)。
- **判断**：SSF ストリームの上限は、送信側と受信側で分けず、`SsfStream` のレコード数として一つの上限で数える。向きは同じ集合の属性でしかなく、上限を分けても、抑えたい資源（ストリーム 1 本ごとに増える配送先、鍵の取得先、保持する配送記録）は変わらないためである。

## 操作

### System 管理者による上限の更新

#### REQ-TENANCY-012 System管理者はテナントのクォータ上限を調整できる

- System 管理者がテナントの上限を更新したとき、Tenancy は、そのテナントの上限の上書きを保存し、200 と保存した上書きを返す。
- 上限の更新が成功したとき、Tenancy は、応答に `Cache-Control: no-store` を付ける。
- 上限を更新したテナントでは、Tenancy は、以後の作成の確認に新しい上限を使う。
- System 管理者がテナントの上限を更新したとき、Tenancy は、操作者、テナント、要求に含まれたリソースの名前を `changedFields` に載せた `TenantQuotaUpdated` を発行する。
- 上限の上書きを保存できなかった場合、Tenancy は、`TenantQuotaUpdated` を発行しない。
- **判断**：上限の値は記録しない。監査の目的は変更の事実と範囲の特定であり、現在の値はテナントの読み出しからいつでも得られる。更新は上書きの全体を置き換える（REQ-TENANCY-037）ので、`changedFields` は更新した後に上書きを持つリソースの一覧でもある。
- **例**：EX-TENANCY-012-01

#### REQ-TENANCY-046 クォータ更新の対象は realm で解決する

- System 管理者が realm を指定して上限を更新したとき、Tenancy は、その realm に属するテナントの上書きを保存し、保存先と `TenantQuotaUpdated` のテナントを内部 ID で識別する。
- 指定した realm が存在しない場合、Tenancy は、本文の妥当性によらず 404 と `tenant_not_found` で拒否し、上書きを保存せず、`TenantQuotaUpdated` を発行しない。
- **判断**：外部の識別子は realm に統一し、内部 ID を外部キーと監査の参照に用いる。

#### REQ-TENANCY-037 クォータの更新は上書きの全体を置き換える

- System 管理者がテナントの上限を更新したとき、Tenancy は、要求に含めたリソースの上書きを保存し、含めなかったリソースの上書きを消してデフォルト値へ戻す。
- 現在の使用量を下回る上限を指定されたとき、Tenancy は、その上限を保存し、既存のリソースと使用量を変えない。
- 負の上限を指定された場合、Tenancy は、400 と `invalid_request` で拒否し、どの上書きも保存せず、`TenantQuotaUpdated` を発行しない。
- **例**：EX-TENANCY-037-01、EX-TENANCY-037-02

### リソースの作成時の上限の確認

#### REQ-TENANCY-036 Hard Quota の実効値は、上書きがあればその値、なければデフォルト値である

- 上限の上書きのあるリソースでは、Tenancy は、上書きの値を実効値として使う。
- 上限の上書きのないリソースでは、Tenancy は、次の表のデフォルト値を実効値として使う。

| リソース | デフォルト値 |
| --- | --- |
| `users` | 10,000 |
| `groups` | 1,000 |
| `agents` | 100 |
| `applications` | 50 |
| `oauth2_clients` | 100 |
| `active_sessions` | 50,000 |
| `consents` | 10,000 |
| `active_jobs` | 10 |
| `ssf_streams` | 20 |

- 使用量に加算分を足した値が実効値以下の間、リソースを作成するとき、Tenancy は、作成を受け付け、使用量に加算分を足す。
- 使用量に加算分を足した値が実効値を超える場合、Tenancy は、作成を拒否し、使用量を変えない。
- 上書きが 0 のリソースでは、リソースを作成するとき、Tenancy は、作成を拒否する。
- Hard と [Soft](#req-tenancy-047-soft-quota-の超過は使用量の加算を拒否しない) のどちらにもないリソース名の確認を要求された場合、Tenancy は、確認を失敗させ、どのリソースの使用量も変えない。
- リソースを削除したとき、Tenancy は、使用量から減算分を引いた値と 0 の大きい方を、新しい使用量にする。
- **判断**：Hard の上限はデータベースの枯渇を防ぐために同期的に止める。詳細は[リソース上限を Hard と Soft に分ける](../decisions.md#リソース上限を-hard-と-soft-に分ける)。
- **例**：EX-TENANCY-036-01、EX-TENANCY-036-02、EX-TENANCY-036-03、EX-TENANCY-036-04

#### REQ-TENANCY-013 Hard Quota を超過したリソース作成は拒否される

- Hard Quota のリソースを一件作る要求が実効値を超える場合、Tenancy は、422 と `quota_exceeded` で拒否し、リソースを作らず、使用量を変えない。
- 作成を Hard Quota で拒否したとき、Tenancy は、テナントと超過したリソースの名前を載せた `QuotaExceeded` を発行する。
- **判断**：データエクスポートの開始が `active_jobs` を超える場合の応答は、[データエクスポート](../../identity-management/features/data-export.md)が 429 と `active_job_quota_exceeded` として定める。
- **例**：EX-TENANCY-013-01

### Soft Quota の使用量の計数

#### REQ-TENANCY-047 Soft Quota の超過は使用量の加算を拒否しない

- Soft Quota のリソースを加算したとき、Tenancy は、実効上限に関係なく使用量へ加算し、上限の超過を理由に作成を拒否しない。
- Soft Quota のリソースを減算したとき、Tenancy は、減算後の値と 0 の大きい方を使用量にする。
- Soft Quota の上書きがないリソースでは、Tenancy は、`audit_events_retained` に 1,000,000 件、`export_artifacts_bytes` に 1,073,741,824 バイトを警告の実効上限として使う。
- Soft Quota の上書きがあるリソースでは、Tenancy は、0 を含めて上書きの値を警告の実効上限として使う。
- 負の加算量、減算量または測定値を指定された場合、Tenancy は、操作をエラーで拒否し、保存した使用量を変えない。

### 保持期限バッチによる Soft Quota の照合

#### REQ-TENANCY-048 Soft Quota の照合は実データの使用量を保存し超過を警告する

- 保持期限バッチを実行したとき、Tenancy は、各テナントの保存済み監査イベントの件数と確定済み CSV 成果物および監査エクスポート成果物の合計バイト数を測り、Soft Quota の使用量の二列を置き換え、Hard Quota の使用量と上限の上書きを変えない。
- 測定値が実効上限より大きいリソースでは、照合したとき、Tenancy は、テナント、リソース、測定値、実効上限を警告ログへ残し、テナント、リソースと `hardLimit=false` を載せた `QuotaExceeded` を発行する。
- 測定値が実効上限以下のリソースでは、照合したとき、Tenancy は、警告ログと `QuotaExceeded` を発行しない。
- 同じ超過が続く間、照合したとき、Tenancy は、実行ごとに再び警告を発行する。
- テナントの測定または使用量の保存が失敗した場合、Tenancy は、そのテナントの使用量を置き換えず、警告を発行せず、残りのテナントを処理してからバッチの失敗を返す。
- **判断**：照合は各保存先を読んだ時点の測定であり、全体を同じ時点に固定しない。並行の作成、削除と警告自身の監査は、次の実行で反映する。CSV の入力、結果ページ、エクスポートは同じ不変ストアを占有するため、いずれも保存量に含める。配信の欠落は通常の監査経路の規則に従う。

### 保持期限バッチによる User の使用量の再集計

#### REQ-TENANCY-049 User の使用量の再集計は使用量を占める User の件数で使用量を置き換える

- 保持期限バッチを実行したとき、Tenancy は、各テナントについて IdManagement が数えた使用量を占める User の件数で `users` の使用量を置き換え、ほかのリソースの使用量と上限の上書きを変えない。
- 置き換える前の使用量と数えた件数が異なる場合、Tenancy は、テナント、置き換える前の使用量と件数を警告ログへ残す。
- 再集計の間に同じテナントの `users` を加算または減算する要求があった場合、Tenancy は、その加算または減算を置き換えた後の使用量へ適用する。
- 数えた件数が実効値を超える場合、Tenancy は、その件数で使用量を置き換え、既存の User を変えない。
- テナントの件数の測定または使用量の保存が失敗した場合、Tenancy は、そのテナントの使用量を変えず、残りのテナントを処理してからバッチの失敗を返す。
- **判断**：使用量を占める User は、完全削除されていない User と、完全削除の使用量の減算を終えていない Tombstone である。減算を終えていない Tombstone を数えるのは、完全削除の再実行が後でその分を減算するためである。
- **判断**：作成の加算と完全削除の減算は、上限の判定の近道として残し、User の保存と同じトランザクションにしない。その間の失敗で残ったずれを、この再集計が次の実行で回収する。作成は加算を確定してから User を保存するので、その間に数えた User は件数に入らず、使用量は次の再集計まで一つ少なくなる。経緯は[ユーザーの信頼性](../../identity-management/features/user.md#信頼性)を参照。

## セキュリティ上の考慮

上限を変更できるのは System 管理者だけである。
テナント管理者は、テナント設定の取得で自身の上限と使用量を参照できるが、変更はできない。
理由は、[管理の認可を所属テナント内の admin とテナントを越える system_admin の 2 段にする](../decisions.md#管理の認可を所属テナント内の-admin-とテナントを越える-system_admin-の-2-段にする)。
