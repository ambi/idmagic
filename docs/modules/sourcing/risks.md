# Sourcing のリスク

この文書は、Sourcing の既知の欠陥、技術的負債、受容したリスクを扱う。
脅威は[脅威モデル](../../design/security/threat-model.md)に置く。

| リスク | 現状 | 影響 |
| --- | --- | --- |
| 一つの永続化ポートが二つの root を扱う | 取り込み元との対応表である User の対応と Group の対応の二つを、一つのアダプターで実装したまま、ポートの側も分けていない。[設計ガイドライン](../../design/application/design-guidelines.md#一貫性の境界と永続化)の永続化ポートの粒度に反する | どの操作がどちらの対応表に属するかがインターフェースから読めず、呼び出し側は実装を読んで確かめることになる |
| 既存 Group の所属の一括変更は不可分でない | 複数の所属の変更は一件ずつ所有者の操作を呼び、途中の失敗では補償を試みる | 補償も失敗すると、一部の所属だけが変わる。確定前の変更と補償にもイベントと通知が伴う |
| 完全再同期の無効化と実行の進捗は不可分でない | User の無効化と候補の進捗は、それぞれの所有者で保存する。承認の途中の失敗は `applying` のまま保持して再送で回収する | User の保存後に進捗の保存や外向きの作用が失敗すると、無効化件数が過少になる窓がある。適用済みの User を巻き戻さない |
| 保留の管理者への通知は監査画面での確認を要する | 保留の監査イベントと実行の照会を提供し、メールはまだ送らない | 保留に気付くまで無効化が遅れる。メール通知全般の追加、拡充時には、この通知も対応対象に含める |
