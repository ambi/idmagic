# 鍵の提供元と健全性

## 概要

この文書は、署名鍵の提供元の選択と、制御面主体による提供元の健全性の一覧の仕様である。

| 項目 | 内容 |
| --- | --- |
| 責務 | 鍵素材を永続化する構成での提供元の明示の要求、提供元の健全性の観測、テナントを横断した健全性の一覧 |
| 行為者 | System 管理者（プロセスの起動、健全性の一覧）、テナント管理者（健全性の一覧の拒否） |
| 扱わないもの | 提供元に到達できないときのトークンの発行の停止は、`OAuth2` のトークンの発行が強制する |

## モデル

提供元に到達できないときのフェイルクローズは、このモジュール自身では強制しない。
このモジュールにはトークンを発行するインターフェースがないためである。
このモジュールは `provider_healthy` を観測できるシグナルとして返し、`OAuth2` のトークンの発行がそれを見て新しい署名を止める。
JWKS は、提供元に到達できない間も、取得できる範囲で返す。

鍵素材を永続化する構成（`PERSISTENCE=postgres`）では、`KEY_PROVIDER` の明示を求め、指定がなければ起動を拒否する。
`PERSISTENCE=memory` では鍵素材がプロセスの外へ出ないので、求めない。

- **判断**：明示を求める理由は、[鍵素材を平文で永続化する構成をデフォルトにしない](../design/decisions.md#鍵素材を平文で永続化する構成をデフォルトにしない)。

## 操作

### プロセスの起動による提供元の選択

#### REQ-SIGNINGKEYS-012 鍵素材を平文で永続化する構成は明示の選択を要する

- `PERSISTENCE=postgres` で `KEY_PROVIDER` を指定せずにプロセスを起動した場合、SigningKeys は、`KEY_PROVIDER` の明示を求める設定エラーで起動を拒否し、鍵の保管先を作らず、署名鍵も作らない。
- `PERSISTENCE=memory` でプロセスを起動したとき、SigningKeys は、`KEY_PROVIDER` の指定を求めない。
- **例**：EX-SIGNINGKEYS-012-01

### System 管理者による健全性の一覧

#### REQ-SIGNINGKEYS-008 KeyProvider の障害時は健全性を観測でき、JWKS は取得可能な範囲で返る

- 制御面主体が制御面テナントの経路で署名鍵の健全性を一覧したとき、SigningKeys は、テナントと用途ごとに、提供元、`active_kid`、JWKS の鍵の数、`provider_healthy` を 200 で返す。
- 提供元に到達できない間、健全性を一覧したとき、SigningKeys は、そのテナントの `provider_healthy` を `false` として返す。
- 提供元に到達できない間、クライアントが JWKS を取得したとき、SigningKeys は、取得できる範囲の鍵を返す。
- **例**：EX-SIGNINGKEYS-008-01

#### REQ-SIGNINGKEYS-009 制御面主体ではない管理者はシステムコンソールの署名鍵ヘルスにアクセスできない

- `system_admin` を持たないか、制御面テナントに所属しないか、要求先が制御面テナントでない利用者が健全性の一覧を要求した場合、SigningKeys は、403 と `access_denied` で拒否し、ほかのテナントの識別子、提供元、`active_kid`、鍵の数、到達性を返さず、テナント横断の収集を実行しない。
- **例**：EX-SIGNINGKEYS-009-01

## セキュリティ上の考慮

テナントを横断した健全性の一覧 `SystemKeyHealthRead`（`admin:keys_health_read`）は、制御面主体に限る。
制御面主体は、認証済みで有効な User のうち、制御面テナントに所属し、要求先も制御面テナントであり、Group 由来を含む有効ロールに `system_admin` を持つものである。
ロールの名前だけを条件にすると、ほかのテナントの管理の経路から、全テナントの識別子と鍵の運用の状態を読み出せてしまうためである。
