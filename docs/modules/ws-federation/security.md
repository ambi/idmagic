# WsFederation のセキュリティ

この文書は、WsFederation の発行の経路に共通するセキュリティの仕組みと、RP から届く入力の解析をどう確かめるかを扱う。
各エンドポイントの境界は、各機能仕様のセキュリティ上の考慮の節が扱う。

## テナント単位の署名

受動的な発行でも能動的な発行でも、発行のたびに、要求元のテナントの有効な `XmlFederationSigning` の資格情報を `SigningKeys` から取得する。
プロセスの起動時に保持した鍵では署名しない。
これにより、WS-Fed と SAML は XML 署名の資格情報のライフサイクルを共有しながら、OAuth2 と JWT の鍵から分離できる。

## 認可の境界

プロトコルのエンドポイントは管理者の認可を通らず、それぞれ別の境界を持つ。

| 経路 | 主体を決めるもの | 宛先の検証 |
| --- | --- | --- |
| メタデータと MEX | なし（公開の Discovery） | 該当なし |
| パッシブサインイン | ブラウザーのログインセッション | `wtrealm`、`wreply`、対象のユーザーの Application への割り当て |
| 能動的な STS | UsernameToken。照合、試行の制限、失敗の監査は Authentication のパスワード認証をログインの API と共有する | `AppliesTo` が登録した RP に解決できること、対象のユーザーの Application への割り当てとサインインポリシー |

いずれの経路でも、未登録の宛先にトークンを発行することはない。
メタデータと MEX は認証を要さない代わりに、公開する内容を発行者、エンドポイント、署名証明書に限る。

## パースの境界のファズテスト

パッシブサインインの `wreply` の解決と、WS-Trust の RST のエンベロープの解析は、Go のネイティブのファジングの対象である。

| 対象 | オラクル |
| --- | --- |
| `ValidateSignIn` | 返す返信先は、必ず RP に登録した集合の要素である。`wreply` を指定した要求が通ったなら、その値とバイト単位で一致する |
| `ParseRST` | 拒否したエンベロープから Username や `AppliesTo` を持ち出さない |

`wreply` の一致が、接頭辞の一致や正規化を伴う一致へ退行すると、攻撃者は RP のドメインの配下に見える別の宛先へトークンを配送できる。
XML の実体参照を展開しないことは、SAML と同じく回帰テストで押さえる。
