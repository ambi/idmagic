# アドミッションコントロール

## 概要

この文書は、キャパシティが足りないときに、API のプロセスが優先度の低い要求から拒否する仕様である。

| 項目 | 内容 |
| --- | --- |
| 責務 | 経路の優先度クラスへの分類、クラスごとの同時実行の入場の上限、上限を超えた要求の 503 による拒否、`RoutePriorityReference` の生成と乖離の検出 |
| 行為者 | APIConsumer（要求を送る呼び出し元）、Operator（参照文書の生成） |
| 扱わないもの | 縮退の順序は[キャパシティ設計](../../../design/performance/capacity.md#ロードシェディング順序)が、濫用を抑えるエンドポイントごとの流量の制限は各モジュールが扱う |

## モデル

要求は、経路の登録と同じ場所で、`interactive_auth`、`management`、`management_bulk`、`infrastructure` の四つの優先度クラスに分類する。
クラスごとの同時実行の入場の上限を超えた要求は、503 で拒否する。
拒否は、ルーティングの後、ハンドラーの手前で起きる。

どの経路がどのクラスに属するかは、散文に書かない。
分類はコードに一か所あり、そこから `ROUTE_PRIORITY.md` を生成する。

- **判断**：優先度クラスで拒否する理由は、[優先度クラスで低い要求から拒否する](../design/decisions.md#優先度クラスで低い要求から拒否する)。

## 操作

### API の利用者による要求

#### REQ-SYSTEM-018 飽和した API プロセスは優先度の低い要求から拒否する

- 優先度のクラスの実行中の要求の数が入場の上限に達している間、そのクラスの要求を受けたとき、System は、ハンドラーへ渡さず、`Retry-After` と `urn:idmagic:error:service_overloaded` の Problem Details を伴う 503 で拒否し、永続状態もドメインイベントも変えない。
- System は、`management_bulk` の上限を `management` の上限以下、`management` の上限をプロセス全体の上限以下に保ち、`management_bulk`、`management`、`interactive_auth` の順に拒否を始める。
- 要求を拒否するとき、System は、下位のクラスほど長い `Retry-After` を返す。
- System は、`infrastructure` のクラス（生存確認、受付可否、起動完了、指標）の要求を拒否しない。
- 分類のない経路の要求を受けたとき、System は、`interactive_auth` と同じ上限を適用する。
- 実行中の要求の数が上限に達していない間、要求を受けたとき、System は、ハンドラーへ渡して通常どおり処理する。
- **例**：EX-SYSTEM-018-01、EX-SYSTEM-018-02、EX-SYSTEM-018-03

### 運用者による経路の優先度の参照文書の生成

#### REQ-SYSTEM-019 RoutePriorityReference は分類の定義から生成され乖離を検出できる

- 運用者が経路の優先度の参照文書を生成したとき、System は、組み立て済みの各経路の経路のパターン、メソッド、優先度のクラスと、クラスごとの縮退のステージと上限を与える起動時設定のキーを書き出す。
- 生成物が定義と一致しない場合、System は、突き合わせを失敗させ、再生成すべきことを報告する。
- **例**：EX-SYSTEM-019-01、EX-SYSTEM-019-02

## 実現方式

### アーキテクチャ

アドミッションコントロールは一つのプロセスの中で完結し、ほかのレプリカとも共有のストアとも通信しない。
保証しているのは、次の三つである。

**上限を超えて同時に実行されることはない。**
ミドルウェアは要求の入口で実行中の数を 1 増やし、拒否でも完了でも減らす。
増やした直後に読んだ値が自分のクラスの上限以下であることが、ハンドラーへ進む条件である。
ある瞬間に上限を超える数の要求がハンドラーに入っているとすると、そのうち最後に増やしたものは、ほかの要求がすでに増やし終えてまだ減らしていない状態で読んだことになり、上限を超えた値を見て拒否されていたはずである。
したがって、そのような状態は生じない。

**上位のクラスの枠を下位が奪えない。**
上限はクラスごとに `management_bulk` ≤ `management` ≤ プロセス全体の順で並ぶ。
下位のクラスは自分の上限までしか実行中の数に寄与できないので、その差分は常に上位のクラスのために空いている。
要求 1 件が同時に握るデータベースの接続は高々 1 本なので、この差分はそのまま接続の予約になる。
接続プールを分けずにクラスごとの接続の予算が成り立つのは、このためである。

**拒否した要求はハンドラーへ到達しない。**
判定はルーティングの後、ハンドラーの手前で行う。
経路の分類にルートのパターンが要るのでルーティングより後に置き、状態を一切変えないためにハンドラーより前に置く。
ロードシェディングの順序のステージ 5 が求める「状態を部分的に更新しない」は、ここでは何も実行しないという形で成り立つ。

分類は経路の登録と同じ場所に定義し、実行時ではなく組み立ての時に決まる。
分類のない経路は、組み立てたルーターの全量に対する網羅性の検査が拒む。

### 信頼性

それでも実行時に分類のない経路へ到達した場合は、`interactive_auth` と同じ上限で扱う。
本番で誤って拒否するほうが、誤って通すより高くつくからである。
その到達自体は、指標に `unclassified` として現れ、[アドミッションコントロールの運用手順書](../../../runbooks/admission-control.md)が対応を定める。

上限は起動時設定から入り、実行中は変わらない。
したがって、縮退の強さを変えるには再起動が要る。
設定を実行中に変えられるようにしていないのは、飽和している最中に閾値を変える操作そのものが、原因の切り分けを難しくするためである。
