# HTTP API の共通の振る舞い

## 概要

この文書は、複数の API 操作に同じ内容でかかる HTTP の振る舞いの仕様である。

| 項目 | 内容 |
| --- | --- |
| 責務 | エラーの応答の形式、コレクションのページサイズとカーソルとページ送りのヘッダー、リクエストボディの大きさと文字列の長さの上限、セキュリティヘッダー、レートリミットの拒否の形式、クライアント IP の解決 |
| 行為者 | APIConsumer（汎用 API を呼ぶ呼び出し元） |
| 扱わないもの | 各操作のパス、パラメーター、状態コード、エラーの型は TypeSpec が、それを返す条件は各機能の要件が扱う。契約の書き方の規則は [API ガイドライン](../../../design/application/api-guidelines.md)が、経路の種類ごとの認可は [API の境界](api-boundary.md)が扱う |

## モデル

| 概念 | 内容 |
| --- | --- |
| 汎用 API | 管理 API（`/api/admin/v1/`）、アカウント API（`/api/account/v1/`）、ブラウザー API（`/api/auth/`）。各標準が形式を定めるプロトコルエンドポイントと、運用エンドポイントは含めない |
| 署名付きカーソル | 発行したテナントと、絞り込みと並び順の同一性を束縛し、署名したページ送りの位置 |
| 総件数を返すコレクション | 絞り込みに一致する正確な件数を、ページとともに返すコレクション |
| クライアント IP | 要求の送信元とみなすアドレス。ログインの抑制、レートリミット、アプリケーションの CIDR 条件、Negotiate の自動試行、監査の記録が使う |

この機能に対応するコードのディレクトリはない。
HTTP の共有ライブラリが Problem Details とエラーの書き出し、ページングとカーソル、セキュリティヘッダー、レートリミットの応答、クライアント IP の解決を担う。
文字列長は共通のランタイム契約に従って検証し、ボディ上限は起動処理が組み立てるミドルウェアで適用する。

## 操作

### API の利用者による要求の拒否

#### REQ-SYSTEM-013 バックエンド API のエラーは英語で返る

- バックエンドの API がエラーを返すとき、System は、表示言語によらず、エラーコードと HTTP の状態コードを変えずに、英語の `message`、`error_description`、`detail` を返す。
- **例**：EX-SYSTEM-013-01

#### REQ-SYSTEM-022 汎用 API の拒否は RFC 9457 の Problem Details で返る

- 汎用 API の操作がレートリミット以外の理由で要求を拒否するとき、System は、`Content-Type: application/problem+json` で、`type`、`title`、`status`、`detail`、`instance` を持つ本文を返す。
- 汎用 API の操作が要求を拒否するとき、System は、`type` に `urn:idmagic:error:` の後にエラーコードを続けた URN を、`status` に応答の状態コードを入れる。
- 汎用 API の操作が要求を拒否するとき、System は、`instance` に要求の相関 ID を入れる。
- **判断**：クライアントが処理するエラーの形式を一つにし、`type` のエラーコードから TypeSpec のエラーのモデルを特定できるようにする。

#### REQ-SYSTEM-023 汎用 API の内部障害は、実装の詳細を公開しない

- 汎用 API の操作が業務上の拒否または入力の不正として識別していないエラーで失敗した場合、System は、500 と `internal_server_error` の Problem Details で応答する。
- 汎用 API の操作が内部障害で失敗した場合、System は、SQL、DB の制約名、言語やライブラリの生のエラー文、スタックトレース、内部のパスと接続先を、応答本文とヘッダーに含めない。
- 汎用 API の操作が内部障害で失敗した場合、System は、原因を要求の相関 ID とともにサーバー側へ記録する。
- **判断**：`invalid_request` のようなエラーコードを割り当てるだけでは、内部障害が公開してよい拒否に変わることはない。

#### REQ-SYSTEM-034 プロトコルの内部障害は、説明欄に実装の詳細を公開しない

- プロトコルの操作が未分類のエラーまたは `server_error` で失敗した場合、System は、プロトコルのエラー形式を保ち、SQL、DB の制約名、言語やライブラリの生のエラー文、スタックトレース、内部のパスと接続先を、応答本文とヘッダーに含めない。
- プロトコルの操作が内部障害で失敗した場合、System は、原因を要求の相関 ID とともにサーバー側へ記録する。
- **判断**：プロトコルが説明欄を持つ場合も、内部障害の詳細を公開してよい理由にはならない。

### API の利用者によるコレクションの一覧

#### REQ-SYSTEM-024 汎用 API のコレクションのページサイズは、デフォルト 50 件、最大 200 件である

- 署名付きカーソルでページングするコレクションを一覧したとき、System は、`limit` の件数（デフォルト 50 件、最大 200 件）まで返す。
- 最大の件数を超える `limit` を受けたとき、System は、拒否せずに最大の件数まで返す。
- 0 以下か整数でない `limit` を受けた場合、System は、400 と `invalid_request` で拒否し、一覧を返さない。
- **判断**：過大な `limit` は内容の誤りではなく、応答の大きさの問題なので、拒否せずに上限へ丸める。

#### REQ-SYSTEM-025 ページ送りのカーソルは、発行したテナントと絞り込みの外では使えない

- 別のテナントで発行したカーソルか、異なる絞り込みで発行したカーソルを受けた場合、System は、400 と `invalid_request` で拒否し、一覧を返さない。
- 署名と一致しないカーソルか、形式の壊れたカーソルを受けた場合、System は、400 と `invalid_request` で拒否し、一覧を返さない。
- **判断**：カーソルを別のテナントや条件を変えた後のクエリへ流用させない。

#### REQ-SYSTEM-026 コレクションの一覧は、ページ送りの URL を `Link` ヘッダーで返す

- 前後のページのあるコレクションを一覧したとき、System は、`rel="prev"` と `rel="next"` の URL を RFC 8288 の `Link` ヘッダーで返す。
- ページ送りの URL を返すとき、System は、要求のクエリパラメーターを保ち、`cursor` だけを置き換える。
- 総件数を返すコレクションを一覧したとき、System は、`Pagination-Total-Items`、`Pagination-Total-Pages`、`Pagination-Current-Page`、`Pagination-Page-Size` ヘッダーを返す。
- 総件数を返すコレクションの先頭以外のページを一覧したとき、System は、`cursor` を除いた `rel="first"` の URL も返す。
- 総件数を返すコレクションの末尾以外のページを一覧したとき、System は、`rel="last"` の URL も返す。
- **判断**：クライアントが URL を組み立て直さずにページを送れるようにし、応答の本文の構造を変えずにページングの情報を足せるようにする。

### API の利用者によるリクエストボディの送信

#### REQ-SYSTEM-027 起動時設定の上限を超えるリクエストボディは 413 で拒否する

- `HTTP_MAX_BODY_BYTES`（デフォルト 1 MiB）を超えるリクエストボディを受けた場合、System は、ハンドラーへ渡さずに 413 で拒否し、状態を変えない。
- **判断**：汎用 API の JSON のリクエストボディにかかる 64 KiB の上限は、[REQ-PLATFORM-005](../../scenarios.feature.md) が定める。

#### REQ-SYSTEM-028 汎用 API の文字列の長さはコードポイントで数え、上限を超えると 422 で拒否する

- 汎用 API の要求の文字列のフィールドの長さを検証するとき、System は、UTF-8 のバイト数ではなく Unicode のコードポイントの数を数える。
- 汎用 API の要求の文字列のフィールドが長さの上限を超える場合、System は、422 と `field_length_exceeded` で拒否し、`detail` に契約上のフィールド名と上限を示し、対象を変えない。
- **判断**：バイト数で数えると、上限 100 の名前が英字なら 100 文字、日本語なら 33 文字になり、契約に書いた値が意味を失う。

### API の利用者への応答

#### REQ-SYSTEM-037 管理 API は条件付きの更新で古い表現の上書きを拒否する

- TypeSpec が ETag を宣言する管理 API の GET と PATCH がリソースを返すとき、System は、返す表現と保存状態に対応する強い ETag を返す。
- TypeSpec が If-Match を宣言する更新または削除を受けたとき、System は、現在の ETag と強い比較で一致するタグを含む要求だけを実行し、一致しない要求を 412 `precondition_failed` の Problem Details で拒否する。
- 対象の操作で If-Match を省略したとき、System は、この条件による拒否を行わずに通常の操作を実行する。
- If-Match に `*` を指定し、対象の表現が存在するとき、System は、条件を満たしたものとして扱う。
- If-Match に `*` を指定し、対象の表現が存在しないとき、System は、条件を満たさないものとして扱う。
- 不正な If-Match の構文を受けたとき、System は、400 `invalid_request` で拒否する。
- If-Match の不一致で拒否したとき、System は、対象の保存と削除、関連状態と使用量の変更、監査イベントの発行、外部への通知を行わない。
- 同じ ETag を条件に並行して更新を受けたとき、System は、その状態からの書き込みを一件だけ成功させる。
- 受信した表現を変換して保存する PUT が成功したとき、System は、ETag を返さない。
- 管理コンソールが対象を編集するとき、System は、編集元の表現に対応する ETag を If-Match で送信する。
- 管理コンソールが更新後の表現を採用するとき、System は、同じ応答の本文と ETag を一緒に採用し、PUT の成功後には GET でその組を取得する。
- 管理コンソールが 412 を受けたとき、System は、編集内容を無条件に再送せず、最新の値を読み直すよう利用者へ知らせる。
- **判断**：部分更新には PATCH、全体置換には PUT を使い、RFC 9110 §9.3.4 の変換する PUT の制約を維持する。GET を挟んだ場合も、本文と異なる時点の ETag を組み合わせない。

#### REQ-SYSTEM-036 管理 API の冪等キーは保存した応答を再生し、結果不明の要求を再実行しない

- TypeSpec が `Idempotency-Key` を宣言する管理 API の POST に、ヘッダーを省いた要求を受けたとき、System は、応答の保存と再生を行わずに通常の操作を実行する。
- 対象の POST に冪等キーを受けたとき、System は、空でない 255 バイト以内の ASCII 文字列を Structured Field の文字列形式で一つだけ受け付け、不正な形式、空文字列、長さの違反、複数のヘッダーを 400 `invalid_request` で拒否する。
- 冪等キー付きの要求を初めて受け付けたとき、System は、解決済みのテナント、認証した主体、キーの組を受付から 24 時間記録し、ハンドラーが返した状態コード、本文と応答の表現に必要なヘッダーを、5xx を含めて保存してから呼び出し元へ返す。
- 同じ組のキーと同じ要求を保持期間内に再び受けたとき、System は、操作を再実行せず、保存した応答を返す。
- 同じ組のキーと異なる要求を保持期間内に受けたとき、System は、422 `idempotency_key_reused` で拒否し、先行する応答を返さない。
- 同じ組のキーと同じ要求を保持期間内に受け、先行する操作が実行中か、停止または保存失敗により応答が残っていないとき、System は、409 `idempotency_key_in_progress` で拒否し、操作を再実行しない。
- 再送を受けたとき、System は、現在の認証、スコープ、ロール、テナントと CSRF の検証を通した主体だけに応答を再生する。
- 応答を保存するとき、System は、シークレットの有無によらずテナントの DEK を使うエンベロープ暗号で本文と保存対象のヘッダーを暗号化し、平文へ退避しない。
- 受付から 24 時間に達したとき、System は、キーを新しい要求に使えるものとして扱い、期限切れの記録を保持期間の sweep で削除する。
- **判断**：結果が不明な操作の再実行は二重発行を起こし得るため、保持期間内は拒否する。応答を失ったシークレットの自動回復は提供しない。保持期間を過ぎたキーの再利用に重複排除の保証はない。

同じ要求かどうかは、HTTP メソッド、テナントの接頭辞を除いた具体的なパス、クエリ、Content-Type とボディから判定する。
JSON は文字列の外の空白だけを除き、プロパティと配列の順序、数値と文字列の表記は保つ。
プロパティの順序を含め、空白以外を変えたボディは異なる要求として扱う。
CSV はバイト列を比較する。
再生するヘッダーは Content-Type、Cache-Control、Content-Disposition、Location、Retry-After とする。
相関 ID、Cookie とセキュリティヘッダーは保存した値で上書きしない。
Problem Details の `instance` は再送の相関 ID に合わせる。
キー付き要求の読み込みは JSON を 64 KiB、CSV を 64 MiB までとし、超過した要求は 400 `invalid_request` で拒否する。

この契約のヘッダー形式と重複要求の分類は [IETF draft-09](https://datatracker.ietf.org/doc/html/draft-ietf-httpapi-idempotency-key-header-09) に基づく。

#### REQ-SYSTEM-035 汎用 API の独自の列挙値は小文字のスネークケースで表す

- 汎用 API で `AuthorizationDetailTypeState`、`McpResourceServerState`、`SsfStreamDirection`、`ClientSecretCredentialStatus`、`KeyProvider`、`KeyUsage`、`SigningKeyState`、`RequiredAuthnStrength`、`RevocationReason` を送受信するとき、System は、TypeSpec が宣言する小文字のスネークケースを使う。
- **判断**：標準が定める値と、SharedSignals が SET 内で送る理由の表記は、それぞれの標準仕様に従う。

#### REQ-SYSTEM-029 バックエンドの応答はセキュリティヘッダーを伴う

- 自動送信のフォーム以外の応答を返すとき、System は、`X-Content-Type-Options: nosniff`、`Referrer-Policy: no-referrer`、`X-Frame-Options: DENY` と、`default-src 'none'; base-uri 'none'; frame-ancestors 'none'; form-action 'self'` を方針とする `Content-Security-Policy` を付ける。
- HSTS を有効にした構成では、System は、`max-age` に `HSTS_MAX_AGE_SECONDS` の値を入れた `Strict-Transport-Security` を付ける。
- HSTS とサブドメインへの適用を有効にした構成では、System は、`Strict-Transport-Security` に `includeSubDomains` を加える。
- HSTS を無効にした構成では、System は、`Strict-Transport-Security` を付けない。
- CSP の報告専用を有効にした構成では、System は、`Content-Security-Policy` の代わりに、同じ方針の `Content-Security-Policy-Report-Only` を付ける。
- CSP の報告先を設定した構成では、System は、方針に `report-uri` と `CSP_REPORT_URI` の値を加える。
- **判断**：HSTS のデフォルトは無効である。平文の `http` を使う開発環境に影響させず、TLS を終端する側が有効にする。
- **判断**：SAML と WS-Federation の自動送信のフォームの方針は、送信先と固定のスクリプトのハッシュだけを許す形で、それぞれの応答が上書きする。

### API の利用者によるレートリミットを超えた要求

#### REQ-SYSTEM-030 レートリミットの拒否は待機の秒数だけを示し、残量を示さない

- レートリミットで要求を拒否するとき、System は、429 と、`error` に `rate_limited`、`retry_after_seconds` に待機の秒数、`message` に英語の文を持つ JSON を、同じ秒数の `Retry-After` ヘッダーとともに返す。
- レートリミットを適用する経路で応答するとき、System は、`RateLimit`、`RateLimit-Policy`、`X-RateLimit-` で始まるヘッダーを付けない。
- **判断**：レートリミットを受ける相手には攻撃者も含まれ、残量を返すと制限に達しない送信の間隔を教えることになる。どの経路にどの閾値をかけるかは、[プロトコルエンドポイント](../../oauth2/features/protocol-endpoints.md)と[サインイン](../../authentication/features/sign-in.md)が定める。

### API の利用者の送信元の解決

#### REQ-SYSTEM-032 クライアント IP は、信頼する代理を設定した場合だけ X-Forwarded-For から解決する

- 信頼する代理を設定していない構成では、System は、直接の接続の相手のアドレスをクライアント IP として使い、`X-Forwarded-For` を読まない。
- 信頼する代理を設定した構成で要求を受けた場合、System は、直接の接続の相手から `X-Forwarded-For` の右端、左端へと順にたどり、`TRUSTED_PROXY_CIDRS` のどの範囲にも含まれない最初のアドレスをクライアント IP として使う。
- たどる途中に IP アドレスとして読めない値がある場合、System は、直接の接続の相手のアドレスをクライアント IP として使う。
- たどったアドレスがすべて信頼する代理の範囲に含まれる場合、System は、`X-Forwarded-For` の左端の値をクライアント IP として使う。
- **判断**：汎用 API に限らず、プロトコルエンドポイントを含むすべての経路に同じ規則をかける。ループバック、リンクローカル、プライベートのアドレスも、範囲として設定した場合だけ信頼する。社内のクライアントのアドレスを代理と取り違えると、その左にある偽装できる値を採るからである。代理の段数で数える方式は、構成の段数が変わると黙って別の値を採るので使わない。

## セキュリティ上の考慮

冪等キー付き要求では、保存した応答に発行直後のクレデンシャルが含まれ得る。
現在の認証と認可の後に、同じテナントと主体の記録だけを照合する。
保存先の暗号化と鍵の移行は [データベース設計](../../../design/data/database.md#可逆な秘密情報のエンベロープ暗号) に従う。

| 観点 | 内容 |
| --- | --- |
| テナント境界 | カーソルは発行したテナントに束縛するので、別のテナントの一覧の位置を推測して読ませない |
| 情報の開示 | エラーコードを割り当てていない失敗は、内部のエラーの文を応答へ写さない。レートリミットの残量は返さない |
| 埋め込み | `frame-ancestors 'none'` と `X-Frame-Options: DENY` により、ログイン、同意、ポータルの画面の埋め込みを拒む |
| 送信元の偽装 | 信頼する代理の範囲の外から届いた `X-Forwarded-For` は読まないので、IP 単位の防御を偽装した値で回避させない |
