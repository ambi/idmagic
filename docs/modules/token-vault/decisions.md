# TokenVault の重要な設計判断

この文書は、TokenVault の設計判断のうち、代替案を比べたものと、見直す条件が要るものを扱う。

## Vault が代理で実行する

### 背景

Agent は利用者に代わって外部 API を呼ぶ。上流のトークンが Agent へ渡ると、失効を IdMagic から効かせられず、漏洩の範囲も広がる。

### 決定

Agent はメソッド、URL、本文を Vault へ送り、Vault がトークンを付けて上流を呼ぶ。

### 検討した代替案

| 案 | 利点 | 欠点 | 採らない理由 |
| --- | --- | --- | --- |
| RFC 8693 で上流のトークンを渡す | Vault が外向きの要求を持たず、遅延も増えない | トークンが外へ出る | 渡した後の呼び出しを評価できない |
| 短命のハンドルを渡す | 認可と転送の入口を分けられる | 評価が二か所に分かれ、転送は結局 Vault が担う | 代理実行より利点が少ない |

### 結果と再検討の条件

Vault が外向きの HTTP と本文の上限を担う。大きな本文の転送やストリーミングが必要になり、代理実行の上限が利用を妨げるときに見直す。

### 関連する要件

REQ-TOKENVAULT-008、REQ-TOKENVAULT-010、REQ-TOKENVAULT-011

## 更新の単一飛行を行のリースで実現する

### 背景

更新トークンを回転する上流では、同じ更新トークンの再送が `invalid_grant` になり、接続が壊れる。API は複数のプロセスで動く。

### 決定

`refresh_lease_until` の条件付き更新でリースを取ったプロセスだけが上流を呼び、結果を `token_version` の条件付き更新で保存する。負けたプロセスは短く待って読み直す。

### 検討した代替案

| 案 | 利点 | 欠点 | 採らない理由 |
| --- | --- | --- | --- |
| 行ロックを保持して上流を呼ぶ | 実装が単純 | 外部 HTTP の間トランザクションと接続を占有する | 上流の遅延が DB の枯渇へ波及する |
| プロセス内の singleflight | 依存がない | プロセスをまたぐと競合する | 複数プロセスで保証にならない |

### 結果と再検討の条件

負けた要求は最大 10 秒待つ。リースの期限切れによる二重更新が実際に接続を壊すと観測したときに見直す。

### 関連する要件

REQ-TOKENVAULT-012、REQ-TOKENVAULT-013
