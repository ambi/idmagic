# Frontend の重要な設計判断

## 管理コンソールとアカウントポータルを BFF ではなく SPA の OIDC RP にする

### 背景

管理コンソールとアカウントポータルは、IdP 自身の API を呼ぶブラウザーのアプリケーションである。
IdP は、認可とトークンの発行の経路をすでに実装している。

### 決定

管理コンソールとアカウントポータルは、BFF の背後に置かず、ファーストパーティーの OIDC RP として扱う。
純粋な SPA の RP としてアクセストークンをブラウザーに保持することを受け入れ、短命なトークンと `no-store` で影響範囲を限る。
ファーストパーティーのセッションのログインを、緊急の経路として残す。

### 検討した代替案

| 案 | 利点 | 欠点 | 採らない理由 |
| --- | --- | --- | --- |
| BFF を挟み、トークンをサーバーの側に保持する | ブラウザーのスクリプトからトークンへ到達できない | 管理画面のためだけに、IdP の認可とトークンの発行の経路を二重化する。セッションの状態を持つ層が増える | IdP の可用性と復旧の経路が複雑になる |

### 結果と再検討の条件

スクリプトの実行が成り立てば、ブラウザーに保持したアクセストークンは持ち出されうる（[脅威モデル](../../design/security/threat-model.md)の THREAT-004）。
600 秒の有効期間、`no-store`、URL とログと DOM にトークンを置かないことで、露出の窓を狭める。
OIDC のクライアントや鍵の設定を壊したときにも、緊急の経路で直せる。
ブラウザーに保持したトークンの露出が受容できない運用の要件が出た場合に見直す。
