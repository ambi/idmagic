# 管理コンソールのリソース操作

## 概要

管理コンソールの一覧から作成、編集、更新へ進む操作と、入力欄の意味を揃える。
システムコンソールのテナント画面の、詳細から変更へ進む操作と確認も扱う。
業務上の認可と保存は、各 API の所有モジュールが判断する。

## 操作

### 管理者によるリソースの一覧と更新

#### REQ-FRONTEND-001 一覧は対象の件数と再取得の操作を共通の形式で示す

- 管理者がリソース一覧を開いたとき、System は、一覧上部に件数と更新操作を表示する。
- 総件数を取得した一覧では、System は、総件数と表示中の件数を区別する。
- 総件数を取得していない一覧では、System は、取得した件数を表示件数と明記する。
- 管理者が一覧を更新したとき、System は、現在のページと検索条件を保ってデータを再取得する。
- 再取得に失敗した場合、System は、直前の一覧を維持し、失敗を表示する。
- 管理者がロール一覧を開いたとき、System は、ロールの総数とロールごとの付与人数を区別する。
- 管理者がロールの付与人数を確認したとき、System は、ユーザーの先頭ページだけに切り詰めずに集計する。

### 管理者によるリソースの作成

#### REQ-FRONTEND-002 リソースの作成は専用画面へ遷移し、資格情報の用途を区別する

- 管理者が外部サービス連携の追加を選んだとき、System は、専用の作成画面へ遷移する。
- 管理者が未作成の認可モデルの作成を選んだとき、System は、専用の作成画面へ遷移する。
- 管理者が外部サービス連携の作成画面を開いたとき、System は、必須と任意の項目を区別し、機械用シークレットにログインパスワードと異なる自動補完の用途を指定する。
- 作成に失敗した場合、System は、作成画面と入力を維持し、失敗を表示する。
- 作成に成功したとき、System は、戻り先で保存結果を再取得し、成功を通知する。

### System 管理者によるテナントの確認と変更

#### REQ-FRONTEND-003 システムコンソールのテナントの変更は、読み取り専用の詳細から専用の変更画面へ遷移して行う

- System 管理者がテナントの詳細を開いたとき、System は、現在の値を読み取り専用で表示し、表示名とパスワードポリシー、上限、正規ロケーションのそれぞれの変更画面への入口を置く。
- System 管理者がテナントの作成を選んだとき、System は、専用の作成画面へ遷移する。
- テナントの作成に成功したとき、System は、作成したテナントの詳細へ遷移し、成功を通知する。
- System 管理者が変更画面で保存したとき、System は、その変更画面が扱う一つの API だけを要求する。
- 保存に成功したとき、System は、テナントの詳細へ戻って現在の値を再取得し、成功を通知する。
- 作成または保存に失敗した場合、System は、その画面と入力を維持し、失敗を表示する。
- **判断**：表示名とパスワードポリシーの更新と、上限の更新は別の API である。一つの保存で両方を送ると、片方だけが保存された状態を利用者に示す必要が生じるため、変更画面を API ごとに分ける。

#### REQ-FRONTEND-004 システムコンソールのテナントの無効化、再開、正規ロケーションの切替は、確認を経てから要求する

- System 管理者が一覧の行または詳細から無効化または再開を選んだとき、System は、対象の realm、操作の結果、取り消せるかを示す確認を表示し、要求をまだ送らない。
- System 管理者が正規ロケーションの切替を保存したとき、System は、発行者、WebAuthn の RP ID、Cookie の適用範囲が変わることを示す確認を表示し、要求をまだ送らない。
- System 管理者が確認を承認したとき、System は、要求を送り、一覧または詳細の状態を再取得する。
- System 管理者が確認を取り消した場合、System は、要求を送らず、テナントの表示を変えない。

## 実現方式

### アプリケーション設計

画面を跨ぐ表示と操作の規則は[ユーザーインターフェース設計](../../../design/application/user-interface.md)が定める。
ここには、管理コンソールに固有の画面の構成を書く。

#### 画面の構成の参考

管理コンソールは、Keycloak、Okta、Google Cloud IAM のような、ディレクトリを中心とする管理画面を参考にする。
左側のナビゲーションで管理対象を選び、一覧の表で検索、状態、主な権限を示し、同じ画面の流れの中で詳細と変更の手段を示す。

| 規則 | 内容 |
| --- | --- |
| 一覧を作業の中心にする | 検索、絞り込み、状態、MFA の設定、ロールを一覧の時点で確認できるようにする |
| 変更の前に確認できるようにする | 変更を確定する前に、詳細画面でユーザーの ID、認証の状態、割り当て済みの権限を確認できるようにする |
| 権限を明示的に変更する | 機微なロールの変更では、一覧の中での直接の編集を避ける。専用の画面で、追加と削除の差分を確定の前に示す |
| 資格情報は一度だけ表示する | クライアントシークレットのような資格情報は、作成したときに一度だけ表示する |
| 未実装の機能への入口を置かない | ナビゲーションは将来の機能を足せる構造にするが、まだない画面へのリンクは置かない |

参考にした管理画面は次のとおりである。

- [Keycloak Server Administration Guide](https://www.keycloak.org/docs/latest/server_admin/)
- [Okta Manage users](https://help.okta.com/en-us/content/topics/users-groups-profiles/usgp-people.htm)
- [Google Cloud IAM access management](https://cloud.google.com/iam/docs/granting-changing-revoking-access)

#### サイドバー

サイドバーは、ディレクトリ、エージェント、アプリケーション連携、アクセス制御、運用と設定の作業領域に分ける。
現在の画面を含む領域だけを展開し、その領域のページへ直接移動できるようにする。
ほかの領域は、ポインターを合わせると横に開くメニューから、目的のページへ一度のクリックで移動できるようにする。
クリックとキーボードでもメニューを開けるようにし、Escape で閉じたら起点へフォーカスを戻す。
一項目だけの領域は直接のリンクにする。
サイドバー全体をデフォルトで展開せず、高さの低い画面でもナビゲーションを本文と独立して操作できるようにする。

Directory Connector は、ディレクトリ同期のプログラムとして表示する。
エージェントによる外部 API の代理実行先は、エージェントの領域の「外部 API の代理実行」から管理する。

#### エージェントのアクセス権

日常の直接の付与は、対象とエージェントの選択から始める。
登録済みのツールの通常の利用の割り当ては、エージェントの「利用する接続先」から、接続先と操作の表示名を選んで編集する。
この通常の操作では、モデル、関係、タプル、対象の ID を入力させず、対象ごとの詳細な付与は別の編集として扱う。
認可モデル、関係データ、判定の調査は開発者向けの設定として区別し、通常の付与と同じ保存先を使う。
接続先を選べることを、関係データが接続先だけに隔離されていることの保証として表示しない。

#### API アクセストークン

API アクセストークンは、設定のタブから独立した管理画面に置く。
管理コンソールではテナント内の記録を、アカウントポータルでは本人の記録を扱う。
どちらも、トークンの主体は発行者本人であることを表示する。
管理コンソールの一覧は、テナント内の全発行者の記録であることを示し、発行の操作は「自分のトークンを発行」とする。
発行画面では、ログイン中の本人、操作対象のテナント、選ぶスコープを別々に示す。

#### 一覧の列と表示

ロールの一覧では、ロールごとの付与人数と権限数を表の列に置き、ロールの総数と区別する。
組み込み属性の表示名は画面の表示言語で翻訳し、API の属性キーを併記する。
テナントが定義したカスタム属性のラベルは、翻訳で上書きしない。

CSV のインポートにはファイルの取り込み、CSV のエクスポートにはファイルの書き出しを表すアイコンを使う。
テンプレートと生成済みのファイルのダウンロードには下向きの矢印を使い、取り込みと区別する。
