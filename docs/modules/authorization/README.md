# AccessControl

## 責務と境界

資源へのアクセスと管理権限の認可を扱う。
旧称は Authorization であり、既存の規範 ID、TypeSpec の名前空間、HTTP パスと参照先の互換性のため、仕様文書と TypeSpec の `authorization` の配置および識別子は維持する。
プロトコルに依存しない認可の要求契約と、管理ロール、権限、対応する HTTP 操作の表示を担当する。
テナントごとの認可モデル（リソース型と関係の定義）と関係タプル（`resource ⇄ subject` の事実）を持ち、それらをたどって「この主体はこのリソースに対してこの関係を持つか」を判定する。
関係に基づく判定は、粗いロールでは表せない「ユーザー U は文書 D を読めるか」に答える。

| 扱わないもの | 担当 |
| --- | --- |
| 最終的な認可の判断の合成（ロール、スコープ、代行チェーン、プリンシパルの有効性との論理積） | `Authorizer` を実装するローカルまたはリモートの評価器。ローカルは仕様バインディングの規則表を使う |
| 管理 API を誰が呼べるかというロールの認可 | 仕様バインディングの規則表と[認可設計](../../design/security/authorization.md) |
| `Agent` の状態 | `IdManagement` |
| OAuth の通信手順、同意、グラントとトークンの発行 | `OAuth2` |
| サインインの条件、認証強度と再認証の期限の評価 | 現在は `Application`。実際の認証と追加認証は `Authentication` |

このモジュールは、関係が成り立つかという事実を求め、評価器へ渡す。
外部の PDP へ差し替えても、合成の規則が重複しない。
要求と結果、アクションと規則の仕様バインディング、および HTTP 操作の生成表は `backend/shared/spec` を使い、管理権限と操作の対応、可視性、表示への変換はこのモジュールに閉じる。
管理ロールの表示は関係タプルの保存先を要求せず、関係グラフの評価から独立した操作として実装する。
管理ロールの計算は純粋な計算のパッケージ `internal/rolepolicy` に置き、HTTP への変換はハンドラーで行う。

## 主な流れ

| 流れ | 契機 | 実行する場所 | 詳細 |
| --- | --- | --- | --- |
| 管理 API | 解決済みのテナントの `/api/admin/v1/authorization/...` への要求 | `api` が、ハンドラーからユースケースを同期的に呼ぶ | 各機能仕様 |
| 判定と列挙 | 管理 API の診断の経路、またはデータ資源を提供する呼び出し側 | 呼び出したプロセスが、関係タプルを読みながら同期的に評価する | [関係の判定の設計](features/check.md#実現方式) |
| 管理ロールの一覧 | 管理者の `/api/admin/v1/policy/roles` への要求 | `api` が認証器で操作者を解決し、可視な権限と HTTP 操作を組み立てる | [管理ロールの仕様](../oauth2/features/admin-access.md#管理者によるロールポリシーの確認) |

## 設計の要点

| 方針 | 理由 |
| --- | --- |
| 関係の事実だけを求め、判断の合成は評価器に任せる | 外部の PDP へ差し替えても、合成の規則が重複しない。詳細は[判断](decisions.md#関係の事実を求め判断の合成を評価器に任せる) |
| 書き換え規則を和だけで組む | 評価が単調になる。詳細は[判断](decisions.md#書き換え規則を和だけで組み交差と差集合を入れない) |
| まず判定の正しさを優先し、列挙に索引を持たない | 詳細は[判断](decisions.md#リソースの列挙を上限付きの走査と-1-件ずつの判定で行う) |
