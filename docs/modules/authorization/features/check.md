# 関係の判定

## 概要

この文書は、主体がリソースに対して関係を持つかを判定し、許可されたリソースを列挙する仕様である。

| 項目 | 内容 |
| --- | --- |
| 責務 | 関係グラフの評価、代行チェーンの合成、判定不能のときの不許可、リソースの列挙、判定の監査 |
| 行為者 | テナント管理者（診断の HTTP の経路）、OAuth2 のリソースアクセスの評価（`RelationChecker` のポート） |
| 扱わないもの | ロールとスコープを含む最終的な判断は、認可ポートを実装する評価器が、仕様バインディングの規則表で合成する |

## モデル

`CheckAccess` は、次を論理積で合成する。

1. 主体（通常はアクセストークンの `sub`）が、対象のリソースに対して関係を持つ。
2. 代行チェーンの上のすべての actor が、同じ関係を持つ。
3. 代行チェーンの上のすべての actor が有効である。`Agent` の状態は `PrincipalStatusResolver` のポートで解決し、解決できなければ有効とみなさない。
4. 要求した関係に対応するスコープが、提示されたトークンのスコープの集合に含まれる。
5. 主体とリソースのテナントが一致する。

1〜3 はこのモジュールが事実として組み立て、4〜5 と合わせて AuthZEN の `resource:access` の規則が評価する。
事実が欠けたまま届いた要求は、規則 `relationship_facts_present` が不許可にする。

判定の結果は、たどった関係の名前だけを連ねた経路（`document#viewer` → `folder#viewer`）を持ち、オブジェクトの識別子と主体の識別子は含めない。

| 監査のイベント | 内容 |
| --- | --- |
| `FgaCheckEvaluated` | 判定の結果。リソースの識別子は、テナントと型を混ぜた SHA-256 の先頭 16 桁のダイジェストにする |
| `FgaResourcesEnumerated` | 列挙の全体を 1 件にまとめた結果 |

ダイジェストにより、同じ資源への繰り返しのアクセスは相関できるが、資源の名前そのものは監査ログから復元できず、テナントをまたいだ相関もできない。
タプルの内容と主体の識別子は、監査へ写さない。

列挙は、そのテナントとそのリソース型に現れる識別子を上限付きで走査し、1 件ずつの判定と同じ合成を通ったものだけを返す。
結果は必ず打ち切りの有無を伴う。

- **判断**：列挙に逆引きの索引を持たない理由は、[リソースの列挙を上限付きの走査と 1 件ずつの判定で行う](../decisions.md#リソースの列挙を上限付きの走査と-1-件ずつの判定で行う)。

## 操作

### 呼び出し元による関係の判定

#### REQ-AUTHORIZATION-003 判定は継承・グループ・親子関係をたどって関係の成否を決める

- 呼び出し元が主体、リソース、関係で判定を要求したとき、AccessControl は、直接のタプル、`computed_userset`、`tuple_to_userset`、subject set の成員をたどって関係が成り立つかを決め、許可か不許可と、たどった関係名だけの経路を返す。
- 判定の結果を返すとき、AccessControl は、経路にオブジェクトの識別子と主体の識別子を含めない。
- どの経路でも関係に到達しない場合、AccessControl は、許可しない。
- **例**：EX-AUTHORIZATION-003-01、EX-AUTHORIZATION-003-02、EX-AUTHORIZATION-003-03、EX-AUTHORIZATION-003-04

#### REQ-AUTHORIZATION-004 代行するエージェントは主体と自身の双方が関係を持つときだけ許可される

- 主体と代行チェーンのすべての actor が同じ関係を持ち、すべての actor が有効で、要求した関係に対応するスコープがトークンのスコープの集合に含まれ、主体とリソースのテナントが一致する間、代行チェーンを伴う判定を要求されたとき、AccessControl は、許可する。
- 主体と代行チェーンの actor のどれかが関係を持たないか、actor が有効でないか、actor の状態を解決できないか、スコープが足りないか、テナントが一致しない場合、AccessControl は、許可しない。
- **例**：EX-AUTHORIZATION-004-01、EX-AUTHORIZATION-004-02、EX-AUTHORIZATION-004-03、EX-AUTHORIZATION-004-04

#### REQ-AUTHORIZATION-009 判定の監査は非個人識別情報の要約だけを残す

- 判定を下したとき、AccessControl は、リソースの型、関係、許可か不許可、モデルのバージョン、関係名だけの経路、拒否の理由、代行チェーンの段数を持つ `FgaCheckEvaluated` を発行する。
- `FgaCheckEvaluated` を発行するとき、AccessControl は、リソースの識別子をテナントと型を混ぜた SHA-256 の先頭 16 桁のダイジェストにし、主体の識別子とタプルの内容を含めない。
- **例**：EX-AUTHORIZATION-009-01

#### REQ-AUTHORIZATION-006 他テナントの関係タプルは判定に寄与しない

- 呼び出し元が判定を要求したとき、AccessControl は、呼び出し元のテナントのタプルだけを読み、要求の本文が別のテナントの識別子を含んでも対象のテナントを変えない。
- 別のテナントで発行したか、壊れているか、ストアがまだ追いついていない整合トークンを提示された場合、AccessControl は、422 と `consistency_not_satisfied` で拒否する。
- **例**：EX-AUTHORIZATION-006-01、EX-AUTHORIZATION-006-02、EX-AUTHORIZATION-006-03

#### REQ-AUTHORIZATION-005 判定不能はフェイルクローズで不許可になる

- 探索の深さが上限（8）を超えるか、登録したモデルが宣言していない型か関係を指定された場合、AccessControl は、許可へ退避せず、拒否の理由を添えて不許可を返す。
- 関係の事実を組み立てないまま評価器へ要求が届いた場合、AccessControl は、規則 `relationship_facts_present` の名前を残して不許可を返す。
- タプルのストアへ到達できない場合、AccessControl は、エラーを返し、許可しない。
- **例**：EX-AUTHORIZATION-005-01、EX-AUTHORIZATION-005-02、EX-AUTHORIZATION-005-03、EX-AUTHORIZATION-005-04、EX-AUTHORIZATION-005-05

### 呼び出し元によるリソースの列挙

#### REQ-AUTHORIZATION-007 リソースの列挙は許可されたものだけを返し、打ち切りを隠さない

- 呼び出し元が主体、リソースの型、関係で列挙を要求したとき、AccessControl は、そのテナントとその型に現れる識別子を上限（デフォルト 500 件）まで走査し、判定と同じ合成で許可されたものだけを、モデルのバージョンと整合トークンとともに返す。
- 呼び出し元が列挙を要求したとき、AccessControl は、候補の数、許可した数、打ち切りの有無、モデルのバージョン、代行チェーンの段数をまとめた `FgaResourcesEnumerated` を 1 件だけ発行し、1 件ごとの `FgaCheckEvaluated` を発行しない。
- 走査が上限に達した場合、AccessControl は、打ち切りを示して返し、結果を完全な一覧として返さない。
- **例**：EX-AUTHORIZATION-007-01、EX-AUTHORIZATION-007-02

### 管理者による判定の説明

#### REQ-AUTHORIZATION-013 管理コンソールは判定の経路と理由を隠さずに示す

- 管理者が管理コンソールで判定の結果を見るとき、AccessControl は、許可か不許可、モデルのバージョン、たどった関係の順の経路を示す。
- 管理コンソールの判定の結果が拒否の理由を含むとき、AccessControl は、表示言語の辞書にある理由を説明として示す。
- 管理コンソールが表示言語の辞書にない理由を受けた場合、AccessControl は、その理由のコードをそのまま示す。
- 管理コンソールの列挙の結果が打ち切りを示す場合、AccessControl は、結果が完全な一覧でないことを示す。

## セキュリティ上の考慮

`CheckAccess` と `ListAccessibleResources` の HTTP の経路は、診断と内部の利用の接点である。
関係の有無そのものが情報になるので、これらも管理の権限を要する。
外部のリソースサーバーは、これらの経路ではなく、提示トークンから主体を導く [リソースアクセスの評価](../../oauth2/features/resource-access.md) を使う。
その評価は `accesscontrol/ports.RelationChecker` を通して同じ合成へ届き、主体が有効でなければ許可しない。

判定に用いる関係タプルの読み出しは、呼び出し元のテナントの境界で行う。
ほかのテナントへ書き込まれた関係タプルが判定へ寄与する経路はない。

## 実現方式

### アーキテクチャ

判定は、深さの上限付きの深さ優先の探索で行う。
訪問済みの `(オブジェクト, 関係)` の対を記録するので、モデルが循環していても探索は止まる。
深さの上限は 8 とし、上限の超過、循環、未知の型と関係、ストアの読み出しの失敗は、いずれも許可しない。
呼び出し側が判定不能を許可として扱えないよう、これらは通常の不許可と区別できる拒否の理由を付けて返す。

モデルが変わって `direct` の宣言から外れた既存の関係タプルは、判定でも数えない。

列挙のためだけの規則は持たない。
列挙は 1 件ずつの判定と同じ合成を通すので、列挙の結果と個別の判定の結果は食い違わない。

### データ

テナントごとに単調に増える書き込みのバージョンを持ち、関係タプルの書き込みとモデルの登録は、同じトランザクションでこれを進める。
書き込みは、テナントの識別子とバージョンを束縛した不透明な整合トークンを返し、判定は `minimum_consistency` としてそれを提示できる。
ストアのバージョンがトークンより古い場合と、トークンが別のテナントのものである場合は拒否する。

単一の PostgreSQL を使う現在の構成では、読み取りは強整合なので、このトークンは主に、書き込みの直後の管理の操作がその書き込みを参照できることの確認に使う。
読み取りの経路へキャッシュや複製を入れる場合に守るべき契約を、あらかじめ示す役割も持つ。

`authorization_models` はモデルのバージョンを追記だけで保持し、定義は JSONB に置く。
定義は外部から与えられる構造であり、結合や絞り込みの対象にならないためである。
`authorization_relation_tuples` は関係タプルをカラムに展開し、同じ組の再書き込みが冪等になり、判定の絞り込みが主キーの先頭から効くようにする。
主体の側からの走査のための索引も持つ。
