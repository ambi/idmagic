# SigningKeys Decisions

- 鍵の一覧と参照は `AdminKeysRead` (`admin:keys_read`)、ローテーションは `TenantKeysRotate` (`admin:keys_rotate`)、検証用鍵の無効化は `TenantKeysDisable` (`admin:keys_disable`) を要し、いずれも `admin` または `system_admin` ロールを持つ、有効かつ認証済みのユーザーが所属テナントに対して行える。テナント横断の健全性一覧 `SystemKeyHealthRead` (`admin:keys_health_read`) だけは制御面主体に限る。制御面主体は、認証済みで有効な User のうち、制御面テナントに所属し、要求先も制御面テナントであり、Group 由来を含む有効ロールに `system_admin` を持つものである。ロール名だけを条件にすると、他テナントの管理経路から全テナントの識別子と鍵運用状態を読み出せてしまうためである。
- 管理 API のレスポンスに秘密鍵素材を含めることは、いずれの権限でもできない。返すのは `kid`、状態、有効期間、証明書、フィンガープリントに限る。公開鍵を配る JWKS とフェデレーションメタデータは認証を要さず、テナントごとのエンドポイントで公開する。
- 署名鍵は、差し替え可能な `KeyProvider` の背後でテナントごとに分離する。システム全体で鍵を共有したり、各プロトコルのアダプターにプロバイダーを埋め込んだりしない。
- 鍵のローテーション間隔（最短 90 日）、公開の重複期間（最短 7 日）、保管期間（7 年）は固定の規範的なポリシー値であり、文書化されない設定にはせずここに記録する。
- 秘密鍵素材がどこに保存されるかは `KeyProvider` の選択で決まる。`Local` と `Database` は秘密 JWK を `signing_keys.private_jwk` に平文で置くため、PostgreSQL のバックアップにも平文で入る。`VaultTransit` は秘密鍵を Vault の外へ出さず、データベース側には公開鍵の写ししか残らない。[Database](../../database.md#envelope-encryption-for-reversible-secrets) のエンベロープ暗号化は可逆なシークレットの規範であって署名鍵の秘密鍵は対象ではない。署名鍵は読み出して復号するものではなく提供元の内側で署名に使うものであり、保護は暗号化ではなく提供元の選択で決まるからである。
- 鍵素材を平文で永続化する構成を既定にしない。鍵素材が永続化される配備、すなわち `PERSISTENCE=postgres` では `KEY_PROVIDER` の明示を要求し、指定が無ければ起動を拒否する（REQ-SIGNINGKEYS-012）。既定のまま起動できると、秘密鍵がバックアップに入る構成を誰も選ばないまま成立し、保存先を暗号化すべきかを運用者が判断する機会そのものが失われる。`PERSISTENCE=memory` では鍵素材がプロセスの外へ出ないので要求しない。
- 平文の鍵素材を含むバックアップの保存先を暗号化する責務は配備側に置き、製品からは強制しない。保存先のボリュームやバケットは製品の管理下に無いためである。製品が保証するのは、どの構成で鍵素材が平文になるかを構成から判別できることまでであり、それを超える保護を主張しない。取得と復元の手順は [バックアップ、復元、災害復旧のランブック](../../runbooks/backup-restore-dr.md) が持つ。
- 本番で `Local` と `Database` の提供元を拒否することは採らない。API と worker の起動時設定には環境の区別が無く、本番かどうかを判定できないからである（`SEED_ENVIRONMENT` は seeding の要求に閉じた値であり、プロセスの配備環境を表さない）。単一レプリカの配備では `Database` 提供元は正当な選択でもある。起動時設定へ配備環境の宣言を導入したときに再検討する。
- この Context を `Supporting` に分類する。署名処理そのものはライブラリへ委ねており、ここが持つのは鍵のライフサイクルと、テナントと用途による分離である。必要だが差別化しない。
