# System Decisions

- この Context 自身は業務データの認可を判断しない。どの経路へどの資格情報で到達できるかという、システム入口の境界を担う。
- ブラウザーの認証フロー (`/api/auth/*`) は認可トランザクションの Cookie で解決する。トランザクションの内容は常にサーバー側に保持し、HTML、URL、JavaScript から読めるアプリケーション状態には含めない。
- 管理 API (`/api/admin/*`) とセルフサービス API (`/api/account/*`) は、ログイントランザクションとは独立した認可を通る。ポータル境界のスコープ (`idmagic.admin` / `idmagic.account`) を要求し、アカウントポータルのトークンで管理 API を呼ぶ経路をフェイルクローズで塞ぐ。実際に何ができるかは、記録の正を持つ各 Context のロールとスコープが決める。
- 生存確認、受付可否、起動完了の各プローブは認証を要さないが、返すのは状態だけで、設定値や依存先の詳細は含めない。`/metrics` も認証を持たないため、公開先は折り返しアドレス、管理用ネットワーク、認証付きプロキシの背後に限る。
- 管理コンソールとアカウントポータルは、BFF の背後に置かずファーストパーティーの OIDC RP として扱う。IdP 自身が持つ認可とトークン発行の経路を、管理画面のためだけに二重化しないためである。
- 純粋な SPA RP としてアクセストークンをブラウザーに保持することを受け入れ、短命なトークンと no-store で影響範囲を限定する。BFF を挟むとセッション状態を持つ層が増え、IdP の可用性と復旧経路が複雑になるからである。
- ファーストパーティーのセッションログインを緊急経路として残す。OIDC クライアントや鍵の設定を壊すと、直す手段そのものが失われるからである。
- 管理・アカウントポータルの固定 `client_id` を含む内部生成の ID 列は、`TEXT` ではなく `UUID` 型とする。
- この Context を `Supporting` に分類する。起動、経路の組み立て、UI の合成はこの製品に固有だが、競合との差にはならない。`Generic` にしないのは、組み立てる対象がこの製品の Context 群そのものであり、既製の実装へ委ねられる部分が無いためである。
- この Context は Aggregate を持たない。起動と経路の組み立てだけを担い、記録の正はすべて各 Context に残る。
- 実行時に選択可能な機能は、composition root が静的に組み立てる `FeatureRegistry` を唯一の一覧とする。registry は API の安定性、標準の採否、テナント設定を所有せず、実行時選択と更新影響だけを保持する。常時提供する機能は登録せず、選択可能な機能が無いビルドでは空の registry を有効な状態として扱う。
- `FeatureRegistry` の成熟度は `experimental`、`preview`、`supported`、`deprecated`、更新方針は `rolling`、`recreate_on_version_change`、`recreate_always` の閉じた語彙とする。実験的機能は既定無効とし、非推奨機能を新たに既定有効へ変更できないよう registry 検証で拒否する。

## No dedicated event infrastructure

ドメインイベントの配信に、メッセージブローカー、イベントストア、ストリーム処理基盤のいずれも採らない。配信はこの Context が組み立てる 1 つの閉包が担い、発行元と同じプロセス、同じ goroutine で完了する。

採らない理由は 2 つある。第一に、公開イベントの消費者は監査記録とアカウントのセキュリティ通知の 2 つだけで、どちらも同じプロセスに同居している。プロセスを越えない配送のために、運用するデータストアを 1 つ増やすことは引き合わない。これは Jobs Context が永続キューを PostgreSQL に置いた[判断](../jobs/decisions.md)と同じ理由である。第二に、ブローカーを挟むと監査記録の成立が第二のシステムの可用性に依存する。監査を製品の重要な性質として扱う以上、記録が残る条件を増やす方向の変更には、それに見合う対価が要る。

却下したのは、専用の配信基盤を先に用意して将来の消費者に備える案である。現在の消費者はワイヤ表現の上だけで動き、発行元の Go の型を知らない。この形が保たれている限り、消費者を増やすこと自体は基盤を持たなくてもできるので、備えとしての先行投資は費用だけが先に出る。

**再検討する条件**は次のいずれかである。イベントの消費者がこのプロセスの外に現れたとき。イベントが失われないことを保証する必要が生じ、それが発行の意図を耐久的に残すことでしか達成できないと判明したとき。1 つのイベント種別に対する消費者が増え、配線を 1 か所の並びとして読めなくなったとき。

この判断は、状態の変更とイベントの発行が原子的でないことに答えるものではない。現在の保証と、保証されていない経路は [deployment.md](../../deployment.md#domain-event-delivery) が持つ。

## No API plane separation

認証・プロトコル系、ポータル系 (`/api/account/v1`)、管理系 (`/api/admin/v1`)、SCIM (`/scim/v2`)、Shared Signals の受信 (`/ssf`) を、1 つの API Deployment で提供する。分けうるものは 4 つあり、配備、プロセスが登録する経路の選択、公開入口、リリース成果物であるが、そのいずれも種別ごとに分けない。

分けない理由は、分割にしか得られない利得はあるが、それを必要とする条件がまだ示されていない一方で、費用は分割した瞬間から常時発生することにある。プロセス資源と停止の隔離、種別ごとに違うレプリカ数、片方だけの更新は配備を分けなければ得られず、入場制御でも自動スケールでも代わりにならない。しかしそれらを必要とする管理系、ポータル系、SCIM、Shared Signals の容量も、認証系への障害波及も、独立更新の要求も、まだ実測で示されていない。対して追加するプレーンは、自分の可用性下限レプリカ数、PodDisruptionBudget、容量モデル、監視、障害対応の手順を 1 組ずつ持ち、「分離した側の過小サイズ」という現在は存在しない障害の形を加える。IdP でこれが起きると、障害対応のために管理 API を使いたい局面で管理系が落ちているという組み合わせになりうる。到達範囲を狭める分離とリリース成果物の分離も、それを求める脅威モデル上の要件と、独立したデータ所有権、担当チーム、SLO が現在無いので採らない。

分離に固有の常時増分は総需要から生じない。総需要はどちらの構成でも同じで、増分は各プレーンの可用性下限、`ceil` の重複、種別間で余裕を融通できないことの 3 つから生じる。その下限は [capacity.md](../../capacity.md#sizing-rules) が算出する。

却下したのは 3 つである。**見積もりが無いことを利得の不在の証拠として、恒久的に分けないと決める案。** 判断材料の欠如から利得の不在は導けない。**見積もりをせずに分ける案。** 分離側の規模を知らないまま常時費用を確定させることになる。**判断せず問いを開いたままにする案。** 単一プロセスが判断なのか偶然なのかを読み取れない状態が残る。「将来分ける確率が高いなら今のうちに分けたほうが安い」も理由にしない。理由になるのは後からでは高くつく場合だけであり、確率が高いことはそれ自体では今実施する根拠にならない。

**再検討する条件**は次のいずれかである。配備を分けることについては、(a) 管理系、ポータル系、SCIM、Shared Signals のいずれかを含む混合負荷で認証系のサービス目標を満たせず、その種別へ上限を設ける、処理をワーカーへ移す、入場制御を入れる対処だけでは要求を満たせないとき、(b) 分離によって 1 レプリカ当たり持続処理能力が混合時より上がり、その改善が可用性下限と切り上げの重複を上回るとき、(c) 片方だけの更新または再起動を必要とした記録が生じ、長期間の版差を許容する運用要件が決まったときである。経路登録の選択と公開入口の分離については、公開側プロセスから特定種別のハンドラーを除く要件、または特定種別を一般利用者向けの公開入口から到達不能にする要件が脅威モデルに記載されたときである。リリース成果物の分離については、独立したデータ所有権、担当チーム、SLO、リリース成果物のいずれもが必要になったときである。

この判断は、容量が足りないときに何を先に捨てるかを決めるものではない。分離は総容量が足りている状況で種別ごとに資源を固定的に分け、入場制御は総容量が足りない状況で何を拒否するかを決める。効く状況が違うので、両者は代替ではない。縮退の順序は [capacity.md](../../capacity.md#degradation-order) が持つ。

この判断は、一括処理の一部が `idmagic-worker` にあること、入場制御と自動スケールが未実装であること、[capacity.md](../../capacity.md#reference-operating-profile) の参照運用プロファイルが現在の規模であること、ブラウザーから見える境界が同一オリジンであることに依存する。経路接頭辞と種別の対応には機械的な検査が無く、ゲートウェイの許可リストと実行時の経路表は現に一致していないので、分離の費用が低いままである保証も無い。
