# DataKeys の重要な設計判断

この文書は、DataKeys の設計判断のうち、代替案を比べたものと、見直す条件が要るものを扱う。
一つの要件やモデルだけを正当化する判断は、機能仕様のその要件またはモデルの判断の欄に置く。

## この Context を Generic に分類する

### 背景

ドメイン文書の索引は、各 Context を `Core`、`Supporting`、`Generic` のいずれかに分類する。
エンベロープ暗号は確立した形である。

### 決定

DataKeys を `Generic` に分類する。
AEAD と鍵セットの処理は Tink へ委ね、自作しない。

### 検討した代替案

| 案 | 利点 | 欠点 | 採らない理由 |
| --- | --- | --- | --- |
| `Supporting` に分類し、暗号処理をこの Context で実装する | 鍵の形式と暗号の方式を製品に合わせて選べる | 確立した暗号の実装を自作することになる | `Generic` の区分が指示する「自作しない」に反する |

### 結果と再検討の条件

AEAD と鍵セットの処理を Tink へ委ねる判断（[データベースの設計](../../../design/data/database.md)）は、`Generic` の区分が指示する「自作しない」を、この製品で最初に適用した例である。
この Context が持つのは、鍵のライフサイクルとメタデータだけになる。
Tink が必要な鍵の形式やプロバイダーを扱えなくなった場合に見直す。

### 関連する要件

この判断は分類であり、特定の要件を正当化しない。

## DEK のライフサイクルの操作を HTTP に公開しない

### 背景

DEK の生成、ローテーション、無効化、破棄は、テナントのすべての暗号化した項目の読み取りに影響する。
誤った無効化や破棄は、そのテナントのシークレットを読めなくする。

### 決定

ライフサイクルの操作は HTTP に公開せず、同じプロセスの中の内部インターフェースとしてだけ呼べるようにする。
管理 API は、制御面主体だけが呼べる健全性の一覧だけとする。

### 検討した代替案

| 案 | 利点 | 欠点 | 採らない理由 |
| --- | --- | --- | --- |
| テナントの管理 API としてライフサイクルの操作を公開する | テナント管理者が自分で鍵を入れ替えられる | テナント管理者が、自身のテナントのシークレットを読めなくする操作を直接起動できる | 誤操作の被害が、テナントのすべての暗号化した項目に及ぶ |

### 結果と再検討の条件

テナント管理者がライフサイクルの操作を直接起動する経路はない。
その代わり、運用者がローテーションを起動する経路も、現状はない（[DataKeys のリスク](risks.md)）。
定期的なローテーションや危殆化への対応を、製品の機能として提供する場合に見直す。

## 破棄の前の確認を項目を持つ Context の FieldMigrator に委ねる

### 背景

鍵素材を消せるのは、そのバージョンで暗号化した値が 1 件も残っていないことを確かめた後だけである。
暗号化した項目は、複数の Context のテーブルに散らばっている。

### 決定

破棄の前の確認と再暗号化は、項目を持つ各 Context が `FieldMigrator` として実装し、起動処理が登録する。
この Context は、登録したすべての `FieldMigrator` の未移行の件数が 0 のときだけ破棄する。

### 検討した代替案

| 案 | 利点 | 欠点 | 採らない理由 |
| --- | --- | --- | --- |
| この Context が、暗号化した項目を持つテーブルを直接調べる | 登録の手順が要らない | この Context が利用側のスキーマを知ることになる | 項目を持つ Context が増えるたびに、この Context を変えることになる |

### 結果と再検討の条件

この Context は、利用側のスキーマを知らないまま安全に破棄できる。
その代わり、暗号化した項目を新しく持つ Context は、`FieldMigrator` を実装して登録しなければならない。登録を忘れた項目は、破棄の確認から漏れる。
暗号化した項目の所在を、スキーマの宣言から機械的に列挙できるようになった場合に見直す。
