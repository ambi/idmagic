# テナントと用途による鍵の分離

## 概要

この文書は、署名鍵をテナント、用途、スコープで分離し、公開する仕様である。

| 項目 | 内容 |
| --- | --- |
| 責務 | テナントごとの JWKS、XML フェデレーションの署名の資格情報のテナントと用途による分離、ローテーションの間と再起動の後の検証の継続 |
| 行為者 | クライアントと RP（公開鍵の取得）、テナント管理者（ローテーション）、System 管理者（プロセスの再起動） |
| 扱わないもの | JWKS とメタデータの形式は `OAuth2`、`SAML`、`WS-Federation` が扱う |

## モデル

XML フェデレーションの鍵には、その公開鍵を含む自己署名の X.509 証明書を対応付ける。
証明書は公開のメタデータとして扱うが、秘密鍵は設定した提供元で保管する。
新しいメッセージには有効な鍵で署名し、期限内の検証用の証明書は、ローテーションの重複期間の間も SAML と WS-Federation のメタデータから参照できる。

- **判断**：パディングは用途で使い分け、JWT の署名には RSA-PSS を、XML Signature と X.509 の操作には PKCS#1 v1.5 を使う。後者のワイヤー形式が、RSA-PSS ではなく RSA-SHA256 を広告するからである。

## 操作

### クライアントによる JWKS の取得

#### REQ-SIGNINGKEYS-004 テナントごとの JWKS は互いに分離される

### テナントによる XML の署名

#### REQ-SIGNINGKEYS-005 XML フェデレーション署名資格情報はテナントと用途で分離される

### 管理者による XML フェデレーションの鍵のローテーション

#### REQ-SIGNINGKEYS-006 XML フェデレーション鍵のローテーション中も既存の信頼関係を検証できる

### プロセスの再起動

#### REQ-SIGNINGKEYS-007 XML フェデレーション署名資格情報は再起動後も同一である

## セキュリティ上の考慮

用途とスコープを分けることで、JWT 用の鍵が XML の Assertion に使われたり、ある SAML のプロファイルが別のプロファイルの資格情報を使ったりすることを防ぐ。
一つの SAML のプロファイルの鍵をローテーションしても、別のプロファイルや JWT の検証用の鍵は変わらない。

公開鍵を配る JWKS とフェデレーションメタデータは認証を要さず、テナントごとのエンドポイントで公開する。
