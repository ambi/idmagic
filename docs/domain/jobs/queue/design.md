# 永続キューの設計

この文書は、[永続キュー](README.md)の要件を保証する仕組みを扱う。

## アーキテクチャ

各レーンは、独自の並行数の上限を持つ独立した `Runner` を備え、空いている実行枠の数だけジョブを一括で取得して、ハンドラーを並行に実行する（デフォルトは 4 枠）。
1 つのプロセスで複数のレーンの `Runner` を同時に起動することもでき、これは `JOB_WORKER_LANES` が未設定の場合の互換の動作である。
本番のデフォルトは、一つのレーンの `Runner` だけを持つ専用の Deployment を並べる構成であり、`infra/k8s/base/worker.yaml` が `idmagic-worker-{latency-sensitive,default,bulk}` の三つを定義する。

取得は自分のレーンに限り、実行の時刻に達した `queued` のジョブと、リースの切れた `running` のジョブを対象にする。
PostgreSQL では `FOR UPDATE SKIP LOCKED` を同じ文の `running` への更新と組み合わせるので、二つの `worker` が同じジョブに有効なリースを同時に持つことはない。
実行中のハンドラーは、リースの期間の 3 分の 1 ごとにハートビートを送る。

`dedup_key` の一意性は、アプリケーションの検査ではなく部分一意索引が保証するので、同時に投入した二つの要求のうち片方だけがレコードを作る。

`worker` の中のライフサイクルワークフローの割り当ての処理は、定期のバッチではなく回復の経路である。
同じトランザクションで確定したものの Job と関連付けられなかった `WorkflowRun` を走査し直し、永続キューへ安全に引き渡す。

## 信頼性

失敗したジョブは、指数的に後ろ倒しした `run_at` とともに `queued` へ戻り、`max_attempts` に達すると `failed` として確定する。
取得の間隔、プロセスの中の並行度、リース、再試行の間隔はプロセス全体の設定である（`JOB_POLL_INTERVAL`、`JOB_WORKER_CONCURRENCY`、`JOB_LEASE_DURATION`、`JOB_BACKOFF_BASE`、`JOB_BACKOFF_CAP`）。
`JobKind` ごとの品質の制御も、利用側ごとの順序や流量の制限も提供しない。

SIGTERM や SIGINT を受けると、`worker` は取得をやめ、停止の猶予期間まで実行中のハンドラーを待つ。
猶予期間の後は終了し、回復は明示的な再投入ではなく、リースの自然な期限切れによって起こる。
`failed` のジョブをやり直す手段は提供しないので、原因を直した後は、投入したモジュールの操作から作業をやり直す。
