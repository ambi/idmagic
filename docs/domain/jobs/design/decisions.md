# Jobs の重要な設計判断

この文書は、Jobs の設計判断のうち、代替案を比べたものと、見直す条件が要るものを扱う。
一つの要件やモデルだけを正当化する判断は、機能仕様のその要件またはモデルの判断の欄に置く。

## 投入と取得の HTTP のエンドポイントを公開しない

### 背景

キューへ仕事を積む権限は、その仕事を要求した業務の操作の権限と同じものであるべきである。

### 決定

投入と取得の HTTP のエンドポイントは公開せず、同じプロセスの中の Go の呼び出しだけにする。

### 検討した代替案

| 案 | 利点 | 欠点 | 採らない理由 |
| --- | --- | --- | --- |
| 管理 API として投入を公開する | 運用者が任意のジョブを積める | キュー自体に第二の入口ができる | 業務の操作の権限と、キューへ積む権限の対応が崩れる |

### 結果と再検討の条件

テナント管理者や API アクセストークンから、キューへ仕事を積む経路はない。
その代わり、ジョブを投入するには、その仕事を要求する業務の操作を通る。
運用者が手で投入しなければならない保守の作業が定常的に生じた場合に見直す。

### 関連する要件

| 要件 | 機能仕様 |
| --- | --- |
| REQ-JOBS-006 | [永続キュー](../queue/README.md) |

## 管理 API を参照と取り消しに限る

### 背景

何が走っているか、なぜ失敗したか、止められるかを運用者が確かめられなければ、実行の基盤は観測できない箱のままである。

### 決定

参照と取り消しに限り、管理 API を公開する。
取り消しは、終端に達していないジョブだけを対象とする。
再試行、再実行、強制の完了は実装しない。

### 検討した代替案

| 案 | 利点 | 欠点 | 採らない理由 |
| --- | --- | --- | --- |
| 再試行と再実行を管理 API から行えるようにする | 失敗したジョブを、その場でやり直せる | 作用を再び起こす操作を、ハンドラーの冪等性の保証の外側から引き起こすことになる | 二重の作用を防げない |

### 結果と再検討の条件

運用者は、ジョブの状態を確かめ、止められる。
その代わり、やり直しは投入したモジュールの操作から行う。
ハンドラーが再実行の安全を宣言できる仕組みを入れる場合に見直す。

### 関連する要件

| 要件 | 機能仕様 |
| --- | --- |
| REQ-JOBS-012 | [ジョブの管理](../admin/README.md) |
| REQ-JOBS-013 | [ジョブの管理](../admin/README.md) |

## 永続キューを PostgreSQL に置き FOR UPDATE SKIP LOCKED でリースする

### 背景

並行する `worker` が、同じジョブを二重に取らずに取得しなければならない。

### 決定

永続キューは、専用のキューのミドルウェアではなく PostgreSQL に置き、`FOR UPDATE SKIP LOCKED` でリースする。

### 検討した代替案

| 案 | 利点 | 欠点 | 採らない理由 |
| --- | --- | --- | --- |
| 専用のキューのミドルウェアを使う | 大量のジョブの配送に向く | 運用するデータストアが増え、業務のデータとの整合を別に保つ必要がある | 現在の規模では、増える運用の負担に見合わない |

### 結果と再検討の条件

運用するデータストアを増やさずに、並行する `worker` が別々のレコードを安全に取得できる。
その代わり、キューの負荷はアプリケーションのデータベースにかかる。
キューの負荷が、データベースのキャパシティの計画を左右するようになった場合に見直す。

### 関連する要件

| 要件 | 機能仕様 |
| --- | --- |
| REQ-JOBS-004 | [永続キュー](../queue/README.md) |

## 実行レーンを呼び出し元ではなく JobKind の登録で決める

### 背景

遅延に敏感なジョブと、大量の一括のジョブが、同じ `worker` の実行枠を取り合う。

### 決定

実行レーンは、呼び出し元ではなく `JobKind` の登録が決める。

### 検討した代替案

| 案 | 利点 | 欠点 | 採らない理由 |
| --- | --- | --- | --- |
| 投入する側が、呼び出しごとにレーンや優先度を選ぶ | 同じ種類でも急ぎのものを先に回せる | 投入する側の判断で、隔離を破れる | レーンは呼び出しごとの優先度ではなく、キャパシティの隔離の単位である |

### 結果と再検討の条件

`bulk` の滞留が、`latency_sensitive` の実行枠を奪うことはない。
その代わり、同じ種類のジョブの中で急ぎのものを先に回すことはできない。
一つの種類の中に、遅延の要求の異なる作業が混ざるようになった場合に、種類を分けるか見直す。

### 関連する要件

| 要件 | 機能仕様 |
| --- | --- |
| REQ-JOBS-009 | [永続キュー](../queue/README.md) |
| REQ-JOBS-010 | [永続キュー](../queue/README.md) |

## 配送を少なくとも 1 回とし冪等性をハンドラーに任せる

### 背景

`worker` は、ハンドラーの実行の途中で異常終了しうる。

### 決定

配送は少なくとも 1 回とし、冪等性はハンドラーの責務とする。
停止の時の回復は、明示的な再投入ではなく、リースの自然な期限切れに任せる。

### 検討した代替案

| 案 | 利点 | 欠点 | 採らない理由 |
| --- | --- | --- | --- |
| ちょうど 1 回を基盤の側で保証する | ハンドラーが冪等性を気にしなくてよい | プロセスの異常終了と完了の報告の競合を塞ぎきれない | 保証できない約束になる |
| 停止の時に実行中のジョブを明示的に再投入する | 回復が速い | 停止の処理の打ち切りとハンドラーの完了が競合すると、二重の実行の余地を作る | 再投入がかえって重複を生む |

### 結果と再検討の条件

プロセスが止まっても、リースの期限が切れた後に別の `worker` がジョブを再取得する。
その代わり、すべてのハンドラーは、重複排除のキーと利用側の一貫性の境界で冪等にしなければならない。
冪等にできない外部の作用を、ジョブで起こす必要が出た場合に見直す。

### 関連する要件

| 要件 | 機能仕様 |
| --- | --- |
| REQ-JOBS-003 | [永続キュー](../queue/README.md) |
| REQ-JOBS-004 | [永続キュー](../queue/README.md) |

## 全テナントを対象とする定期の処理を永続ジョブに混ぜない

### 背景

保持期間の掃引や署名鍵のライフサイクルは、全テナントを対象に定期的に行う。

### 決定

全テナントを対象とする定期の処理は、永続ジョブに混ぜず、外部のスケジューラーが `idmagic-batch` を 1 回限りで起動する。

### 検討した代替案

| 案 | 利点 | 欠点 | 採らない理由 |
| --- | --- | --- | --- |
| 定期の処理を永続ジョブとして積む | スケジューラーを製品の中に持てる | 横断的な一掃には、テナントごとの作業の単位がない | キューの深さも、レーンの隔離も意味を失う |

### 結果と再検討の条件

キューには、テナントごとの作業だけが積まれる。
その代わり、配置する側が、定期の処理のスケジューラーを用意する。
製品が自身のスケジューラーを持つ必要が生じた場合に見直す。

### 関連する要件

この判断は処理の配置であり、特定の要件を正当化しない。
