# OAuth2 の重要な設計判断

この文書は、OAuth2 の設計判断のうち、代替案を比べたものと、見直す条件が要るものを扱う。
一つの要件やモデルだけを正当化する判断は、機能仕様のその要件またはモデルの判断の欄に置く。

## この Context を Core に分類する

### 背景

ドメイン文書の索引は、各 Context を `Core`、`Supporting`、`Generic` のいずれかに分類する。

### 決定

OAuth2 を `Core` に分類する。

### 検討した代替案

| 案 | 利点 | 欠点 | 採らない理由 |
| --- | --- | --- | --- |
| `Generic` として既製の認可サーバーに委ねる | 標準のプロトコルを自前で持たずに済む | 委譲、Agent の監督、トークン交換、承認リクエストは、標準の外にある製品の判断である | 製品の差別化が既製の実装に閉じ込められる |

### 結果と再検討の条件

規範の要件と採用する標準の量も最大であり、モデルの複雑さと差別化が同時に高い。
Agent と委譲を製品の主張から外す場合に見直す。

### 関連する要件

この判断は分類であり、特定の要件を正当化しない。

## 認可とデバイスのライフサイクルを宣言的な遷移表で表す

### 背景

認可の要求とデバイスコードは、複数の段と拒否と期限切れを持つ。
クライアントに許す遷移の集合は、標準と安全性に直結する。

### 決定

認可の要求とデバイスコードのライフサイクルは、その場の条件分岐ではなく、宣言的な遷移表で表す。
ユースケースは遷移の論理を作り直さず、表を直接使う。
リフレッシュトークンのファミリーは対象の外とし、レコードの項目と失効の規則で表す。

### 検討した代替案

| 案 | 利点 | 欠点 | 採らない理由 |
| --- | --- | --- | --- |
| 遷移をユースケースの条件分岐に書く | 表の仕組みが要らない | クライアントに許す遷移の集合が、実装のたびに暗黙にずれる | 許す遷移を一か所で読めない |

### 結果と再検討の条件

機能仕様の状態遷移の表と、実装の許す遷移が一致する。
リフレッシュトークンの状態の空間は実質 `{active, revoked, rotated}` だけで、遷移の適否より親子のローテーションのグラフが重要なので、表には載せない。
遷移にガード以上の条件が要るようになった場合に見直す。

### 関連する要件

| 要件 | 機能仕様 |
| --- | --- |
| REQ-OAUTH2-005 | [認可](../authorization/README.md) |
| REQ-OAUTH2-027 | [デバイス認可](../device/README.md) |

## PKCE の必須化を公開クライアントと FAPI のクライアントに限る

### 背景

PKCE は認可コードの横取りを防ぐが、RFC 6749 の時代の confidential クライアントの多くは対応していない。

### 決定

PKCE は全クライアントに一律で強制せず、公開クライアントと FAPI 2.0 のクライアントではデフォルトで必須、従来の confidential クライアントでは任意とする。

### 検討した代替案

| 案 | 利点 | 欠点 | 採らない理由 |
| --- | --- | --- | --- |
| すべてのクライアントに PKCE を強制する | 横取りへの防御が一様になる | 既存の confidential クライアントに移行を強いる | クライアントの認証がある confidential クライアントには、移行の費用に見合わない |

### 結果と再検討の条件

公開クライアントと FAPI のクライアントに最も強いデフォルトを適用しつつ、既存の confidential クライアントの移行を強いない。
OAuth 2.1 の採用により、全クライアントへの PKCE の必須化を製品の要件にする場合に見直す。

### 関連する要件

| 要件 | 機能仕様 |
| --- | --- |
| REQ-OAUTH2-005 | [認可](../authorization/README.md) |

## クライアントの認証から client_secret_jwt を除く

### 背景

クライアントの認証には、FAPI 級の非対称の方式から従来の共有シークレットまで、多くの方式がある。

### 決定

`private_key_jwt`、`tls_client_auth`、`none`、`client_secret_post`、`client_secret_basic` の 5 方式に対応し、`client_secret_jwt`（HMAC）は意図的に除く。

### 検討した代替案

| 案 | 利点 | 欠点 | 採らない理由 |
| --- | --- | --- | --- |
| `client_secret_jwt` にも対応する | 既存のクライアントの選択肢が増える | `private_key_jwt` を使える場合、対称鍵による代替は能力を増やさず、リスクだけを増やす | 新しいクライアントを最も強い選択肢へ誘導できない |

### 結果と再検討の条件

新しいクライアントは非対称の方式へ誘導され、既存の環境は共有シークレットのまま移行を続けられる。
`client_secret_jwt` しか使えない主要なクライアントが現れた場合に見直す。

### 関連する要件

| 要件 | 機能仕様 |
| --- | --- |
| REQ-OAUTH2-007 | [クライアント](../client/README.md) |
| REQ-OAUTH2-028 | [クライアント](../client/README.md) |

## アクセストークンを JWT にしリフレッシュトークンを不透明な参照にする

### 背景

アクセストークンは検証の頻度が高く、リフレッシュトークンは失効とローテーションの扱いが重要である。

### 決定

アクセストークンは自己完結した JWT、リフレッシュトークンはデータベースに保存する不透明な参照をデフォルトとする。
リフレッシュトークンは交換のたびにローテーションし、ローテーション済みのトークンが提示されたら、ファミリー全体を失効させる。

### 検討した代替案

| 案 | 利点 | 欠点 | 採らない理由 |
| --- | --- | --- | --- |
| どちらも不透明な参照にする | 失効が即時に効く | アクセストークンの検証のたびにストアを読む | 検証の頻度に合わない |
| どちらも JWT にする | ストアが要らない | リフレッシュトークンの失効とローテーションの再利用の検知ができない | 長寿命のトークンを止められない |

### 結果と再検討の条件

失効の時と検証の時の、異なるスケーリングの特性に合わせられる。
アクセストークンの即時の失効は、イントロスペクションと失効エポックで補う。
アクセストークンの即時の失効を、すべてのリソースサーバーで求める要件が出た場合に見直す。

### 関連する要件

| 要件 | 機能仕様 |
| --- | --- |
| REQ-OAUTH2-006 | [トークン](../token/README.md) |
| REQ-OAUTH2-011 | [トークン](../token/README.md) |

## 同意を subject と client_id の組ごとのスコープの集合として持つ

### 背景

同意の粒度は、クライアントごと、操作ごと、スコープごとなどが考えられる。

### 決定

同意は、クライアントごとや操作ごとではなく、`(subject, client_id)` ごとに付与済みのスコープの集合として永続化する。

### 検討した代替案

| 案 | 利点 | 欠点 | 採らない理由 |
| --- | --- | --- | --- |
| 操作ごとに同意を求める | 利用者が細かく制御できる | 同意の画面が増え、利用者が内容を読まずに同意するようになる | 同意疲れを招く |

### 結果と再検討の条件

要求したスコープが既存の同意で覆えるときは同意の画面を出さず、覆えないときだけ追加の同意を求めるので、暗黙のスコープの拡大と同意疲れを避けられる。
Agent の権限のように、スコープより細かい制約は `authorization_details` で表す。
同意の対象を、スコープより細かい単位で記録する要求が出た場合に見直す。

### 関連する要件

| 要件 | 機能仕様 |
| --- | --- |
| REQ-OAUTH2-008 | [同意](../consent/README.md) |

## ポリシーの境界をまたぐ認可の判断を AuthZEN 型のポートに通す

### 背景

認可の判断は、ロール、スコープ、代行チェーン、プリンシパルの有効性、関係の事実を合わせて決まる。
外部の PDP へ差し替える可能性がある。

### 決定

ポリシーの境界をまたぐ認可の判断には、AuthZEN 型の `authorize()` ポートを使う。
ローカルの Go の規則表をロールポリシーの確認にも使い、外部の AuthZEN のサービスはリモートのアダプターの背後に隔離する。
Go のスキーマの検証器が実験の段階にあり、移行の後もロールポリシーの確認のための第二の Go の認可の情報源が残る間は、Cedar を採用しない。

### 検討した代替案

| 案 | 利点 | 欠点 | 採らない理由 |
| --- | --- | --- | --- |
| Cedar の方針言語を採る | 宣言的な方針と検証の道具が使える | Go のスキーマの検証器が実験の段階で、ロールポリシーの確認のための Go の情報源が残る | 認可の情報源が二つに分かれる |

### 結果と再検討の条件

判定を返せない場合、事実が欠けている場合、ストアへ到達できない場合のいずれも、許可へ退避しない。
Cedar の Go の検証器が安定し、ロールポリシーの確認も一つの情報源に移せるようになった場合に見直す。

### 関連する要件

| 要件 | 機能仕様 |
| --- | --- |
| REQ-OAUTH2-003 | [管理 API の認可](../admin-access/README.md) |
| REQ-OAUTH2-004 | [管理 API の認可](../admin-access/README.md) |

## Discovery Metadata を実行時に契約から組み立てる

### 背景

Discovery Metadata は、提供するエンドポイントと能力を広告する。
広告と実装が食い違うと、クライアントが誤った方式を選ぶ。

### 決定

Discovery Metadata は、手作業でもビルドの時でもなく、実行時に契約から組み立てる。

### 検討した代替案

| 案 | 利点 | 欠点 | 採らない理由 |
| --- | --- | --- | --- |
| 手作業で書く | 仕組みが要らない | 実装とずれる | 広告を信頼できない |
| ビルドの時に生成する | 実行時の処理が要らない | 手順の省略で、生成物が古くなる | 生成物の鮮度を保証できない |

### 結果と再検討の条件

広告は、実行中のプロセスの契約と常に一致する。
メタデータを外部の配信網から静的に配る要求が出た場合に見直す。

### 関連する要件

| 要件 | 機能仕様 |
| --- | --- |
| REQ-OAUTH2-014 | [プロトコルのエンドポイント](../protocol-endpoints/README.md) |

## ユーザーの代理の行為を Token Exchange による委任で表す

### 背景

Agent はユーザーに代わって操作する。
Agent はアイデンティティとライフサイクルを持つが、独自の資格情報は持たず、既存の `OAuth2Client` の登録に関連付ける。

### 決定

ユーザーの代理の行為は OAuth 2.0 Token Exchange として実装し、偽装ではなく、元の `sub` と `act` の Agent を保つ委任をデフォルトとする。
Agent ごとの権限は、粗いスコープではなく RFC 9396 の `authorization_details` で表し、後続の Token Exchange では権限を狭めることだけを許す。

### 検討した代替案

| 案 | 利点 | 欠点 | 採らない理由 |
| --- | --- | --- | --- |
| Agent がユーザーとして振る舞う偽装のトークンを発行する | リソースサーバーが代理を意識しなくてよい | 誰が操作したかが、トークンからも監査からも分からなくなる | 代理の行為を本人の操作と区別できない |

### 結果と再検討の条件

監査とイントロスペクションは、同じ規則で委譲のモードを示す。
チェーンの深さはテナントの `max_delegation_depth` で制限する。
標準の委譲の表現が、`act` と `authorization_details` から別の形へ移った場合に見直す。

### 関連する要件

| 要件 | 機能仕様 |
| --- | --- |
| REQ-OAUTH2-048 | [トークン](../token/README.md) |
| REQ-OAUTH2-049 | [トークン](../token/README.md) |

## Agent の操作に対する人間の承認を CIBA で実装する

### 背景

`Supervised` な Agent の操作には、人間の承認が要る。
同意とステップアップ認証は、すでに別の目的で使っている。

### 決定

Agent の操作に対する人間の承認は、同意やステップアップ認証を置き換えず、OAuth 2.0 の上の承認の機能として CIBA で実装する。
`supervised` の Agent に承認を義務付けるかはガバナンスの層が決め、この Context では一律に強制しない。

### 検討した代替案

| 案 | 利点 | 欠点 | 採らない理由 |
| --- | --- | --- | --- |
| 同意の画面で承認を兼ねる | 新しい仕組みが要らない | 同意は付与済みのスコープの集合であり、操作ごとの判断を表せない | 同意と承認の意味が混ざる |

### 結果と再検討の条件

承認は、標準のバックチャネル認可要求として外部の Agent から使える。
配信のモードは `poll` だけとし、`user_code` は未対応として広告する。
`ping` や `push` の配信が要るクライアントが現れた場合に見直す。

### 関連する要件

| 要件 | 機能仕様 |
| --- | --- |
| REQ-OAUTH2-041 | [承認リクエスト](../approval/README.md) |
| REQ-OAUTH2-050 | [承認リクエスト](../approval/README.md) |

## sid のクレームに LoginSession の ID をそのまま使う

### 背景

一つのブラウザーのセッションに、複数の RP が参加する。
セッションを失効させたとき、影響するすべての RP へログアウトを伝えなければならない。

### 決定

`sid` のクレームには、ブラウザーのセッションに参加するすべての RP が共有する `LoginSession.id` そのものを使う。

### 検討した代替案

| 案 | 利点 | 欠点 | 採らない理由 |
| --- | --- | --- | --- |
| RP ごとに別の `sid` を採番する | RP の間でセッションを相関できない | 一回のセッションの失効から、影響する RP をたどる対応表が要る | 失効の伝播が複雑になる |

### 結果と再検討の条件

一回のセッションの失効から、影響するすべての RP をたどれる。
その代わり、RP の間で同じ `sid` が共有される。
RP の間でのセッションの相関を防ぐ要件が出た場合に見直す。

### 関連する要件

| 要件 | 機能仕様 |
| --- | --- |
| REQ-OAUTH2-025 | [ログアウト](../logout/README.md) |
