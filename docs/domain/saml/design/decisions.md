# Saml の重要な設計判断

この文書は、Saml の設計判断のうち、代替案を比べたものと、見直す条件が要るものを扱う。
一つの要件やモデルだけを正当化する判断は、機能仕様のその要件またはモデルの判断の欄に置く。

## この Context を Generic に分類する

### 背景

ドメイン文書の索引は、各 Context を `Core`、`Supporting`、`Generic` のいずれかに分類する。

### 決定

Saml を `Generic` に分類する。

### 検討した代替案

| 案 | 利点 | 欠点 | 採らない理由 |
| --- | --- | --- | --- |
| `Supporting` | 製品に合わせた語彙やモデルを足せる | SP は標準の語彙しか理解しない | SAML 2.0 への準拠が価値のすべてであり、独自の語彙やモデルを足す理由がない |

### 結果と再検討の条件

この Context では、標準と主要な SP の慣行に従うことを優先する。
SAML の上で製品に固有の機能を提供する要求が出た場合に見直す。

### 関連する要件

この判断は分類であり、特定の要件を正当化しない。

## 対応の範囲を Web Browser SSO Profile に限る

### 背景

SAML 2.0 には、多くのプロファイル、バインディング、形式がある。
SAML では、署名ラッピングの攻撃が知られている。

### 決定

対応の範囲を Web Browser SSO Profile に限り、ECP、暗号化した Assertion、SAML の SP としての動作は含めない。

### 検討した代替案

| 案 | 利点 | 欠点 | 採らない理由 |
| --- | --- | --- | --- |
| ECP と暗号化した Assertion にも対応する | より多くの SP と利用の形に対応できる | 対応するバインディングと形式が増える | 署名ラッピングの攻撃への露出が大きくなる |

### 結果と再検討の条件

対応するバインディングと形式を減らし、署名ラッピングの攻撃への露出を小さく保つ。
その代わり、暗号化した Assertion を必須とする SP とは連携できない。
暗号化した Assertion を必須とする SP への対応が求められた場合に見直す。

### 関連する要件

| 要件 | 機能仕様 |
| --- | --- |
| REQ-SAML-006 | [SAML の SSO](../sso/README.md) |

## IdP プロファイルを一つの共有できるモデルで表す

### 背景

一つのテナントの中で、SP ごとに別の entityID と署名の資格情報を見せたい場合がある。
一方で、多くの SP は一つの IdP を共有すれば足りる。

### 決定

SAML の IdP プロファイルは共有できる一つのモデルとし、専用のプロファイルを別の型にしない。
`dedicated` は、同じモデルに SP を一つだけ関連付けた状態として表す。

### 検討した代替案

| 案 | 利点 | 欠点 | 採らない理由 |
| --- | --- | --- | --- |
| 専用のプロファイルを別の型にする | 専用の場合の制約を型で表せる | プロトコル、永続化、管理の経路が、型ごとに分かれる | 信頼の境界の規則を、すべての経路で一つに保てない |

### 結果と再検討の条件

信頼の境界の規則は、プロトコル、永続化、管理のすべての経路で一つである。
その代わり、`dedicated` に SP を一つだけ割り当てる制約は、型ではなく Repository が保証する。
プロファイルの種類ごとに、異なる規則が要るようになった場合に見直す。

### 関連する要件

| 要件 | 機能仕様 |
| --- | --- |
| REQ-SAML-002 | [SAML の SSO](../sso/README.md) |
| REQ-SAML-004 | [IdP プロファイルとメタデータ](../idp-profile/README.md) |

## XML の処理と Assertion の組み立てを自作しない

### 背景

XML の正規化と署名は、実装の誤りがそのまま署名の迂回になる。
WS-Federation と WS-Trust は、すでに SAML の Assertion を組み立てて署名している。

### 決定

XML の構文解析、正規化、署名は自作せず、検証済みの第三者製のライブラリに委ねる。
Assertion の組み立てと署名には、WS-Federation の構築器と署名器を再利用する。

### 検討した代替案

| 案 | 利点 | 欠点 | 採らない理由 |
| --- | --- | --- | --- |
| SAML 専用に XML の処理と署名を実装する | SAML の要求に合わせて最適化できる | 正規化と署名の誤りを、自分で見つけて直すことになる | 署名の迂回の脆弱性を作り込む危険が大きい |

### 結果と再検討の条件

署名の処理は WS-Fed と共有し、この Context は SP 起点の流れに固有の入力だけを加える。
その代わり、ライブラリの制約（署名した要素を移動できないなど）に従う。
採用したライブラリの保守が止まった場合に見直す。

| --- | --- |
| REQ-SAML-006 | [SAML の SSO](../sso/README.md) |
