# SharedSignals の重要な設計判断

この文書は、SharedSignals の設計判断のうち、代替案を比べたものと、見直す条件が要るものを扱う。
一つの要件やモデルだけを正当化する判断は、機能仕様のその要件またはモデルの判断の欄に置く。

## 失効を Agent ごとの一つの時刻に集約する

### 背景

Agent を止めたとき、その Agent に発行済みのすべてのアクセストークンを、すぐに使えなくしなければならない。
発行済みのトークンは自己完結した JWT であり、数が多い。

### 決定

失効は、個々のトークンを追いかけて消すのではなく、Agent ごとの一つの時刻として持つ。
`OAuth2` の `Introspect` と保護された API は、アクセストークンの `issued_at` をこの時刻と比べ、それより前に発行されたトークンを無効と判定する。

### 検討した代替案

| 案 | 利点 | 欠点 | 採らない理由 |
| --- | --- | --- | --- |
| 失効したトークンの一覧を持つ | トークンごとに失効を選べる | Agent を止めるたびに、発行済みのトークンを列挙して記録する必要がある | 列挙の漏れが、失効の漏れになる |

### 結果と再検討の条件

発行済みのトークンを列挙せずに、すべてを一度に無効にできる。
その代わり、失効の後に発行したトークンだけを生かし、それより前のトークンを個別に残すことはできない。
Agent のトークンを、用途ごとに別々に失効させる要求が出た場合に見直す。

| --- | --- |

## ローカルの失効を外部への伝播より先に確定させる

### 背景

外部の受信側は、到達できなかったり遅かったりする。
IdMagic 自身の失効は、外部の状態に依らず即時に効かなければならない。

### 決定

失効エポックを進めて確定させた後に、外部への CAEP のイベントの配送を作る。
配送の作成に失敗しても、ローカルの失効の結果を変えない。

### 検討した代替案

| 案 | 利点 | 欠点 | 採らない理由 |
| --- | --- | --- | --- |
| 外部への配送が成功してから失効を確定させる | IdMagic と外部の受信側の状態がそろう | 受信側の障害が、IdMagic の失効を止める | 外部の障害で、止めるべき Agent が動き続ける |

### 結果と再検討の条件

受信側の障害や遅延が、ローカルの失効を妨げることはない。
その代わり、外部の受信側は、配送が届くまで失効を知らない。
外部への伝播の遅れの上限を、品質要件として約束する場合に見直す。

## 受信のエンドポイントを管理 API の認証ではなく SET の検証で守る

### 背景

受信のエンドポイントは、ブラウザーのセッションを持たない外部の送信側が呼ぶ。
受理した SET は、Agent の失効エポックを進める。

### 決定

受信のエンドポイントは管理 API の認証の経路に載せない。
SET の署名が受信側のストリームに登録した `trusted_issuer` の鍵で検証できること、`jti` が未使用であること、主体がストリームのテナントの中で解決できることを、すべて満たしたときにだけ受理する。

### 検討した代替案

| 案 | 利点 | 欠点 | 採らない理由 |
| --- | --- | --- | --- |
| 外部の送信側に API アクセストークンを発行し、管理 API と同じ経路で認証する | 認証の経路が一つで済む | 送信側ごとにテナントのトークンを配り、保管させることになる | SSF の送信側は SET の署名で自身を示すので、別の資格情報は要らない |

### 結果と再検討の条件

外部の送信側は、登録した発行者の鍵で署名するだけで、失効を伝えられる。
受理した SET が変えられるのは、対象の Agent の失効エポックだけである。
SSF の送信側の認証に、標準が別の方式を求めるようになった場合に見直す。
