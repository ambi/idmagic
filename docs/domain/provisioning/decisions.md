# Provisioning の設計判断

- 接続の登録、更新、削除、接続テスト、On-Demand Provision、Full Resync、Quarantine の解除、プロビジョニングタスクの一覧と再試行は、`admin` ロールを持つ、有効かつ認証済みのユーザーだけが所属テナントに対して行える。接続テスト、On-Demand Provision、Full Resync、Quarantine の解除、プロビジョニングタスクの再試行はいずれも下流を変えるため変更系に属する。
- 接続とプロビジョニングタスクはテナントを越えない。別テナントの接続 ID やプロビジョニングタスクの ID を指定した参照は、存在しないものとして拒否する。
- プロビジョニングタスクそのものは管理者の権限を借りない。`worker` が下流へ提示するのは接続に保存した資格情報だけであり、IdMagic 側の管理者権限が下流へ伝わることはない。下流の URL は登録時に HTTPS であることと、内部アドレスやリンクローカルアドレスを指さないことを検証する。
- Context の名前は向きを表す語ではなく能力から取り、プロトコルに依存しない中核と、`ProvisioningTargetClient` を実装するプロトコルごとの薄い機能単位に分ける。ドメインの形がほぼプロトコルに依存しないため、リポジトリで一般的な「厚い機能単位、薄い共通ルート」を意図的に反転させている。
- 内向きの SCIM (`Sourcing`) と通信の中核を共有しない。実際に重なるのは Discovery の構造体と RFC が定めるスキーマ URN だけで、いま共有すると双方を早すぎる段階で結合することになるからである。
- 下流への反映は、書き込み時の原子性ではなく、定期的な照合で保証する。記録の正を書き換える経路は LifecycleWorkflow、SCIM の取り込み、CSV インポートなど多数あり、経路ごとに捕捉を正しく呼ぶ前提は新しい経路が増えるたびに破れる。プロビジョニングタスクは実行の時点の User から属性を読む状態ベースの仕組みなので、あるべき状態と反映済みの状態を突き合わせれば、取りこぼしの原因を問わずに回収できる。書き込み時の捕捉は、反映の遅延を短くする近道として残す。
- 反映済みの状態は `RemoteResourceLink` に保持し、プロビジョニングタスクの行から都度求めない。照合のたびに接続の全タスクを読み、最後に成功した操作を選ぶ規則を持つことになるからである。
- この Context を `Supporting` に分類する。SCIM 2.0 という標準の上で、既存リソースとの対応付け、プロビジョニングタスクの再試行、隔離というプロダクトの判断を担うが、下流へライフサイクルを反映する能力自体は競合も等しく備えている。
