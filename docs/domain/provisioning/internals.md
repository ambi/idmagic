# Provisioning の内部設計

## 書き込み時の捕捉

`Provisioning` はプロビジョニングタスクを捕捉する公開ポートを提供する。
`IdManagement` のユーザー変更処理と `Application` の割り当て変更処理は、自身の変更をコミットした後でこのポートを呼び出す。
ポートは一致する有効な接続ごとに `pending` の `ProvisioningTask` 行を 1 件挿入する。
捕捉は反映の遅延を短くする近道であり、失敗しても発火元の変更は確定したまま残る。
捕捉の失敗や、捕捉を呼ばない経路による変更は、次の照合が回収する。
プロビジョニングタスクの冪等性には `(tenant, connection, source_type, source_id, source_version)` をキーとして使う。

## 照合

`worker` の定期ループは、`PROVISIONING_RECONCILE_INTERVAL`（デフォルト 5 分）ごとに、有効で隔離されていない接続をすべて照合する。
照合は接続ごとに、User のあるべき状態と、`RemoteResourceLink` が記録する反映済みの状態を突き合わせ、差分をプロビジョニングタスクにする。

| 読むもの | 意味 |
| --- | --- |
| テナントの User | あるべき状態。有効かどうか、`updated_at` によるバージョン |
| 接続のスコープ | `all_users` なら全 User、`assigned_only` なら割り当てのある User |
| `RemoteResourceLink` | 反映済みの状態。リンクの有無、下流で有効として反映したかを表す `active`、最後に反映したバージョン |
| `succeeded` 以外のプロビジョニングタスク | 決着を待つべき User |

| あるべき状態 | 反映済みの状態 | 作るもの |
| --- | --- | --- |
| スコープ内で有効 | リンクなし | `create` |
| スコープ内で有効 | リンクが無効 | `update`（再有効化） |
| スコープ内で有効 | リンクが有効、User のバージョンがリンクより新しい | `update` |
| スコープ内で無効 | リンクが有効 | `deactivate` |
| スコープ外 | リンクあり | `on_unassign` に従う。`deactivate` はリンクが有効なときだけ作る |
| 削除済み | リンクあり | `on_delete` に従う。`delete` で猶予期間があれば予約を作る |

いずれも接続の機能フラグが有効なときだけ作る。
`pending` または `in_flight` のプロビジョニングタスクがある User は飛ばす。
書き込み時の捕捉や前回の照合が同じ変更を扱っているためである。
`dead_letter` のプロビジョニングタスクがあり、そのバージョンが User のバージョン以上である User も飛ばす。
前回の失敗から User が変わっていないので、作り直しても同じく失敗するためである。

リンクは、下流へ送った `active` を記録する。
割り当ての解除では User の `updated_at` が変わらないので、バージョンだけでは、無効化を反映済みかどうかも、再割り当てで戻すべきかどうかも見分けられない。
User の `delete` を下流へ送ったら、リンクを消す。
リンクなしは「下流に何もない」を表す。

1 回の照合で 1 接続に作るものは 500 件までとし、User の ID の順に打ち切る。
残りは次の照合が拾う。
照合が作るプロビジョニングタスクのバージョンは照合の時刻とし、書き込み時の捕捉と同じ時間軸に乗せる。

## 猶予期間つき削除の予約

`DeprovisionPolicy.grace_period_days` が 1 以上の接続では、`on_delete=delete` へ変換された User の削除から `ProvisioningTask` を作らず、`ScheduledDeprovision` を保存する。
予約は接続、User、削除イベントのバージョン、期限（削除時刻に猶予日数を足した時刻）を持つ。
プロビジョニングタスクの行を作らないため、worker が期限前に下流へ DELETE を送ることはない。

| 状態 | 意味 | 遷移の契機 |
| --- | --- | --- |
| `scheduled` | 期限の到来を待っている。同じ接続と User に一件だけ置き、再度の削除通知は期限を延ばさない | 猶予期間を持つ接続への User の削除 |
| `materialized` | 期限に達し、同じバージョンの delete の `ProvisioningTask` を作った | ディスパッチャーの周期処理が期限に達した予約を見つけた |
| `cancelled` | 猶予期間中に対象が適用範囲へ戻ったため取り消した | 同じ Application への User の割り当て。予約より新しいバージョンの割り当てだけが取り消す |

ディスパッチャーは、未関連付けのプロビジョニングタスクへジョブを関連付ける前に、期限に達した予約をプロビジョニングタスクへ変える。
予約を `materialized` にする更新とプロビジョニングタスクの挿入は一つの SQL 文で行い、更新は予約が `scheduled` のときだけ成立する。
このため、取消と実体化が競合しても、取り消した予約からプロビジョニングタスクが作られることはない。
実体化が失敗した予約は `scheduled` のまま残り、次の周期で再び処理される。

予約は削除時点の接続設定で判断する。
期限の到来時に接続の状態や `on_delete` を再評価せず、接続を削除した場合だけ外部キーの連鎖で予約も消える。
