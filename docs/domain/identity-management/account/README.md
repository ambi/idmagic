# アカウントのセルフサービス

## 概要

この文書は、認証済みの本人が `/api/account/*` で自分の記録を参照し変更する機能の仕様である。

| 項目 | 内容 |
| --- | --- |
| 責務 | アカウントの概要、プロフィールの参照と更新、アカウントデータのエクスポート、メールアドレスの変更 |
| 行為者 | 認証済みの本人（ブラウザーのセッション）、本人に固定した API アクセストークンを提示するクライアント |
| コードの機能スライス | `backend/idmanagement/user` |
| 扱わないもの | パスワード、認証要素、セッションの本人操作は `Authentication` が、管理者による User の操作は[ユーザー](../user/README.md)が扱う |

## モデル

この機能が読み書きするのは、本人の `User` だけである。
属性は[ユーザー](../user/README.md#属性の定義)の定義に従い、本人が扱える範囲は次のとおりである。

| 操作 | 対象になる属性 |
| --- | --- |
| 書き込み | `editable_by_user` が `true` の属性 |
| 読み出し | 公開範囲が `self_readable` または `claim_exposed` の属性 |

## 操作

### API アクセストークンによる呼び出し

#### REQ-IDMANAGEMENT-002 account スコープの API トークンは、発行者本人の情報への操作だけを許可する

- `account:read` のスコープは、本人の概要、プロフィール、データエクスポートの参照だけを許可する。
- `account:write` のスコープは、本人のプロフィールの更新と、プライマリメールアドレスの変更の起票だけを許可する。
- `account:read` だけのトークンで変更を要求された場合は、AccessDeniedError で拒否する。
- トークンのテナントまたは `user_id` が操作の対象と一致しない要求を受けた場合は、AccessDeniedError で拒否する。
- **例**：EX-IDMANAGEMENT-002-01、EX-IDMANAGEMENT-002-03

### アカウントの概要の参照

#### REQ-IDMANAGEMENT-019 アカウントの概要は、認証済みの本人のデータだけを、ロールを含めずに返す

- 本人がアカウントの概要を参照したとき、認証済みの本人のデータだけを返す。
- アカウントの概要は、ロールを含まない。
- **例**：EX-IDMANAGEMENT-019-01

### プロフィールの更新

#### REQ-IDMANAGEMENT-016 本人によるプロフィールの更新は表示名を変え、本人が編集できない属性を拒否する

- 本人が表示名を更新したとき、更新後のプロフィールは新しい表示名を返す。
- `editable_by_user` が `false` の属性の更新を要求された場合は、拒否する。
- **例**：EX-IDMANAGEMENT-016-01

#### REQ-IDMANAGEMENT-051 本人によるプロフィールの更新は、属性をキーごとに併合する

- 本人がプロフィールを更新したとき、名前、名、姓は、指定した値を前後の空白を除かずに保存する。
- 本人がプロフィールを更新したとき、属性は指定したキーの値だけを上書きし、指定しなかったキーの値を残す。本人は属性を消せない。
- 本人が `attributes` を含む更新をしたとき、値が変わらなくても `UserUpdated` の `changed_fields` に `attributes` を載せ、`updated_at` を進める。
- 名前、名、姓のどれも変わらず `attributes` も含まない更新を要求された場合は、`UserUpdated` を発行しない。
- `editable_by_user` が `false` の属性を含む更新を要求された場合は、403 と `attribute_not_editable` で拒否し、どの項目も変えない。
- 定義されていない属性、または型の合わない値を含む更新を要求された場合は、422 と `invalid_attribute` で拒否し、どの項目も変えない。

### アカウントデータのエクスポート

#### REQ-IDMANAGEMENT-018 アカウントデータのエクスポートは、本人のプロフィールと同意の一覧を返す

- 本人がアカウントデータをエクスポートしたとき、本人のプロフィールと同意の一覧を返す。
- **例**：EX-IDMANAGEMENT-018-01

#### REQ-IDMANAGEMENT-052 本人に開示する属性は、本人が読める公開範囲のものだけである

- プロフィールの参照とアカウントデータのエクスポートは、公開範囲が `self_readable` または `claim_exposed` の属性の値だけを返す。
- プロフィールの参照とアカウントデータのエクスポートは、公開範囲が `admin_readable` または `private` の属性の値を返さない。
- アカウントデータのエクスポートのプロフィールは、プロフィールの参照と同じ内容である。

### メールアドレスの変更の起票

#### REQ-IDMANAGEMENT-053 メールアドレスの変更の起票は、ステップアップ認証の後に新しいアドレスへ確認のリンクを送る

- 本人がメールアドレスの変更を起票したとき、新しいアドレスへ確認のリンクを送り、`EmailChangeRequested` を発行し、204 を返す。プライマリメールアドレスはまだ変えない。
- 確認のリンクは `<発行者>/account/email/verify?token=<トークン>` であり、30 分で期限が切れる。
- 新しいアドレスは、表示名付きの形式から取り出したアドレスを小文字にして扱う。
- 本人が未確認の現在のアドレスと同じアドレスで起票したとき、受け付ける。
- 確認のメールの送信に失敗した場合も、204 を返す。
- 有効期限内のステップアップ認証を満たさない起票を受けた場合は、403 と `step_up_required` で拒否する。
- アドレスとして読めない値を指定された場合は、422 と `invalid_email` で拒否する。
- 確認済みの現在のアドレスと大文字と小文字を区別せずに同じアドレスを指定された場合は、422 と `email_unchanged` で拒否する。
- 同じテナントのほかの User のアドレスを指定された場合は、409 と `email_taken` で拒否する。
- 起票を拒否した場合は、確認のリンクを送らない。
- **例**：EX-IDMANAGEMENT-053-01、EX-IDMANAGEMENT-053-04

### メールアドレスの変更の確定

#### REQ-IDMANAGEMENT-017 メールアドレスの変更の確定は、未使用で期限内のトークンだけでプライマリメールアドレスを置き換える

- 確認のリンクのトークンで確定したとき、プライマリメールアドレスを新しいアドレスにし、トークンを使用済みにする。
- 確認のリンクを `GET` または `HEAD` で読んだとき、トークンを消費せず、アドレスを変えない。
- 確定済みのトークン、別の用途で発行したトークン、期限切れのトークンで確定を要求された場合は、InvalidRequestError で拒否し、アドレスを変えない。
- 別の用途で発行したトークンで確定を要求された場合は、無効なトークンへの応答と区別できない応答で拒否し、そのトークンを未使用のまま残す。
- 起票の後に新しいアドレスがほかの User のものになっていた場合は、ConflictError で拒否し、アドレスを変えず、トークンを未使用のまま残す。
- **判断**：トークンの使用済み化と確定を一つのトランザクションで行う。分けると、同じリンクで二度アドレスが変わる状態か、ほかの User が同じアドレスを先に取ったために拒否された本人がリンクだけを失う状態のどちらかが起きる。相手がアドレスを手放せば同じリンクを使えるよう、確定が失敗したときはトークンを未使用のまま残す。
- **例**：EX-IDMANAGEMENT-017-01、EX-IDMANAGEMENT-017-06

#### REQ-IDMANAGEMENT-054 メールアドレスの変更の確定は、アドレスを確認済みにして `EmailChanged` を発行する

- 確定したとき、`email_verified` を `true` にする。
- 確定したとき、その User の必須操作 `verify_email` を外し、`UserRequiredActionCleared` を発行する。
- 確定したとき、`EmailChanged` を発行し、`UserUpdated` を発行しない。
- 用途の違うトークン、期限切れのトークン、確定済みのトークン、存在しないトークンで確定を要求された場合は、410 と `invalid_email_change_token` で拒否する。

#### REQ-IDMANAGEMENT-003 メールアドレスの確認画面は、未認証でも CSRF 境界を確立し、一致しない確定を拒否する

- メールアドレスの確認の文脈を要求されたとき、未認証でも、CSRF トークンと、SameSite 属性を付けた Cookie を返す。
- その CSRF トークンと Cookie を添えた確定を受けたとき、受け付ける。
- CSRF トークンと Cookie が一致しない確定を受けた場合は、InvalidRequestError で拒否し、アドレスを変えず、トークンを未使用のまま残す。
- **例**：EX-IDMANAGEMENT-003-01、EX-IDMANAGEMENT-003-02

## セキュリティ上の考慮

| 観点 | 内容 |
| --- | --- |
| 本人の範囲 | アカウント API は、認証済みの本人の記録だけを読み書きする。他人の記録とロールを返さない |
| 確認のリンクの先読み | ブラウザーとメールのスキャナーはリンクを先読みするので、`GET` と `HEAD` では確定しない |
| 未認証の確認 | 確認のリンクは、起票したブラウザーと別の端末で開かれ得る。確認は未認証でも行え、CSRF の境界を確認の画面で確立する |
