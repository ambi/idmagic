# アカウントのセルフサービス

## 概要

この文書は、認証済みの本人が `/api/account/*` で自分の記録を参照し変更する機能の仕様である。

| 項目 | 内容 |
| --- | --- |
| 責務 | アカウントの概要、プロフィールの参照と更新、アカウントデータのエクスポート、メールアドレスの変更 |
| 行為者 | 認証済みの本人（ブラウザーのセッション）、本人に固定した API アクセストークンを提示するクライアント |
| コードの機能スライス | `backend/idmanagement/user` |
| 扱わないもの | パスワード、認証要素、セッションの本人操作は `Authentication` が、管理者による User の操作は[ユーザー](../user/README.md)が扱う |

## モデル

この機能が読み書きするのは、本人の `User` だけである。
属性は[ユーザー](../user/README.md#属性の定義)の定義に従い、本人が扱える範囲は次のとおりである。

| 操作 | 対象になる属性 |
| --- | --- |
| 書き込み | `editable_by_user` が `true` の属性 |
| 読み出し | 公開範囲が `self_readable` または `claim_exposed` の属性 |

## 操作

### API アクセストークンによる呼び出し

| 項目 | 内容 |
| --- | --- |
| 行為者 | 本人に固定した API アクセストークンを提示するクライアント |
| 入力 | アカウント API の要求 |
| 成功時の作用 | トークンのスコープが操作の要求するスコープを満たせば、要求した操作を実行する |
| 拒否 | スコープの足りない要求、トークンのテナントまたは `user_id` が操作の対象と一致しない要求（AccessDeniedError） |

#### REQ-IDMANAGEMENT-002 API トークンの発行者は account スコープで自身の情報だけを操作できる

- `account:read` のスコープは、本人の概要、プロフィール、データエクスポートの参照だけを許可する。
- `account:write` のスコープは、本人のプロフィールの更新と、プライマリメールアドレスの変更の起票だけを許可する。
- `account:read` だけのトークンによる変更の要求は、AccessDeniedError で拒否する。
- トークンのテナントまたは `user_id` が操作の対象と一致しない要求は、AccessDeniedError で拒否する。
- **担保手段**：`support_http.requiredAccountScope`、`support_http.hasRequiredAccountScope`
- **例**：EX-IDMANAGEMENT-002-01、EX-IDMANAGEMENT-002-03

### アカウントの概要の参照

| 項目 | 内容 |
| --- | --- |
| 行為者 | 認証済みの本人 |
| 成功時の作用 | 本人のアカウントの概要を返す |

#### REQ-IDMANAGEMENT-019 アカウント API は他人のリソースを返さない

- アカウントの概要は、認証済みの本人のデータだけを返す。
- アカウントの概要は、ロールを含まない。
- **担保手段**：`handlers_http.HandleGetAccountSummary`
- **例**：EX-IDMANAGEMENT-019-01

### プロフィールの更新

| 項目 | 内容 |
| --- | --- |
| 行為者 | 認証済みの本人 |
| 入力 | 名前、名、姓、属性 |
| 成功時の作用 | 指定した項目を保存する。属性はキーごとに併合する |
| 拒否 | 本人が編集できない属性（403 `attribute_not_editable`）、定義のない属性と型の合わない値（422 `invalid_attribute`）。どの拒否もどの項目も変えない |

#### REQ-IDMANAGEMENT-016 ユーザーは自分のプロフィール表示名を更新できる

- 本人は自分の表示名を更新でき、更新後のプロフィールは新しい表示名を返す。
- 本人は `editable_by_user` が `false` の属性を更新できない。
- **担保手段**：`usecases.UpdateUserProfile`
- **例**：EX-IDMANAGEMENT-016-01

#### REQ-IDMANAGEMENT-051 本人によるプロフィールの更新は、属性をキーごとに併合する

- 名前、名、姓は、指定した値をそのまま保存する。前後の空白を除かない。
- 属性は、指定したキーの値だけを上書きし、指定しなかったキーの値を残す。本人は属性を消せない。
- `editable_by_user` が `false` の属性を含む更新は、403 と `attribute_not_editable` で拒否し、どの項目も変えない。
- 定義されていない属性、または型の合わない値を含む更新は、422 と `invalid_attribute` で拒否し、どの項目も変えない。
- `attributes` を含む更新は、値が変わらなくても `UserUpdated` の `changed_fields` に `attributes` を載せ、`updated_at` を進める。
- 名前、名、姓のどれも変わらず `attributes` も含まない更新は、`UserUpdated` を発行しない。
- **担保手段**：`usecases.UpdateUserProfile`
- **要判断**：本人の更新は値の変わらない属性も変更として記録する。管理者の更新は変わったキーだけを記録する。本人の更新も変わったキーだけを記録するかを決める。

### アカウントデータのエクスポート

| 項目 | 内容 |
| --- | --- |
| 行為者 | 認証済みの本人 |
| 成功時の作用 | 本人のプロフィールと同意の一覧を返す。プロフィールは本人が読める公開範囲の属性だけを含む |

#### REQ-IDMANAGEMENT-018 ユーザーは自分のアカウントデータをエクスポートできる

- 本人のアカウントデータのエクスポートは、本人のプロフィールと同意の一覧を返す。
- **担保手段**：`handlers_http.HandleExportAccountData`
- **例**：EX-IDMANAGEMENT-018-01

#### REQ-IDMANAGEMENT-052 本人に開示する属性は、本人が読める公開範囲のものだけである

- プロフィールの参照とアカウントデータのエクスポートは、公開範囲が `self_readable` または `claim_exposed` の属性の値だけを返す。
- 公開範囲が `admin_readable` または `private` の属性の値は、本人の要求には返さない。
- アカウントデータのエクスポートのプロフィールは、プロフィールの参照と同じ内容である。
- **担保手段**：`usecases.SelfReadableAttributes`、`handlers_http.HandleExportAccountData`
- **要判断**：本人によるデータのエクスポートは個人データの開示の求めに応える経路だが、`admin_readable` と `private` の属性の値を含めない。エクスポートでは含めるかを決める。

### メールアドレスの変更

| 項目 | 内容 |
| --- | --- |
| 行為者 | 認証済みの本人が起票し、確認のリンクを開いた人が確定する |
| 入力 | 起票では新しいアドレス、確定では確認のトークンと CSRF トークン |
| 成功時の作用 | 起票は新しいアドレスへ確認のリンクを送る。確定はプライマリメールアドレスを新しいアドレスにして確認済みにし、`EmailChanged` を発行する |
| 拒否 | 起票：ステップアップ認証の不足、読めないアドレス、確認済みの現在のアドレスと同じアドレス、ほかの User のアドレス。確定：使えないトークン、確定の時点でほかの User のものになったアドレス、CSRF トークンと Cookie の不一致。どの拒否もアドレスを変えない |
| 冪等性 | 確定したトークンは再び使えない。拒否した確定はトークンを未使用のまま残す |

#### REQ-IDMANAGEMENT-017 ユーザーはメールアドレス変更を起票し確認リンクで確定できる

- 本人は新しいメールアドレスへの変更を起票でき、起票は新しいアドレスへ確認のリンクを送る。
- 確認のリンクのトークンで確定すると、プライマリメールアドレスを新しいアドレスにする。
- 確認のリンクを `GET` または `HEAD` で読んでも、トークンを消費せず、アドレスを変えない。
- 確定済みのトークン、別の用途で発行したトークン、期限切れのトークンでの確定は、InvalidRequestError で拒否し、アドレスを変えない。
- 別の用途で発行したトークンへの応答は、無効なトークンへの応答と区別できず、そのトークンを未使用のまま残す。
- 起票の後に新しいアドレスがほかの User のものになっていた場合、確定は ConflictError で拒否し、アドレスを変えず、トークンを未使用のまま残す。
- **判断**：トークンの使用済み化と確定を一つのトランザクションで行う。分けると、同じリンクで二度アドレスが変わる状態か、ほかの User が同じアドレスを先に取ったために拒否された本人がリンクだけを失う状態のどちらかが起きる。相手がアドレスを手放せば同じリンクを使えるよう、確定が失敗したときはトークンを未使用のまま残す。
- **担保手段**：`usecases.RequestEmailChange`、`usecases.ConfirmEmailChange`
- **例**：EX-IDMANAGEMENT-017-01、EX-IDMANAGEMENT-017-06

#### REQ-IDMANAGEMENT-053 メールアドレスの変更の起票

- 起票には、有効期限内のステップアップ認証を求める。満たさない起票は 403 と `step_up_required` で拒否する。
- 新しいアドレスは、表示名付きの形式から取り出したアドレスを小文字にして扱う。アドレスとして読めない値は 422 と `invalid_email` で拒否する。
- 確認済みの現在のアドレスと大文字と小文字を区別せずに同じアドレスは、422 と `email_unchanged` で拒否する。未確認の現在のアドレスと同じアドレスは受け付ける。
- 同じテナントのほかの User のアドレスは、409 と `email_taken` で拒否する。
- 確認のリンクは `<発行者>/account/email/verify?token=<トークン>` であり、30 分で期限が切れる。
- 確認のメールの送信に失敗しても、起票は 204 を返す。
- **担保手段**：`usecases.RequestEmailChange`、`handlers_http.HandleRequestEmailChange`
- **要判断**：確認のメールが届かなかったことを、起票した本人は知ることができない。送信の失敗を応答で伝えるかを決める。

#### REQ-IDMANAGEMENT-054 メールアドレスの変更の確定は、アドレスを確認済みにする

- 確定したアドレスは `email_verified` を `true` にする。
- 確定は、その User の必須操作 `verify_email` を外し、`UserRequiredActionCleared` を発行する。
- 確定は `EmailChanged` を発行し、`UserUpdated` を発行しない。
- 用途の違い、期限切れ、確定済み、存在しないトークンのどれでも、確定は 410 と `invalid_email_change_token` で拒否する。
- **担保手段**：`usecases.ConfirmEmailChange`

#### REQ-IDMANAGEMENT-003 メールアドレス確認画面は未認証でも CSRF 境界を確立できる

- メールアドレスの確認の文脈は、未認証でも取得でき、CSRF トークンと、SameSite 属性を付けた Cookie を返す。
- その CSRF トークンと Cookie を添えた確認は受け付ける。
- CSRF トークンと Cookie が一致しない確認は、InvalidRequestError で拒否する。
- **担保手段**：`handlers_http.HandleEmailVerifyContext`、`handlers_http.HandleConfirmEmailChange`
- **例**：EX-IDMANAGEMENT-003-01、EX-IDMANAGEMENT-003-02

## セキュリティ上の考慮

| 観点 | 内容 |
| --- | --- |
| 本人の範囲 | アカウント API は、認証済みの本人の記録だけを読み書きする。他人の記録とロールを返さない |
| 確認のリンクの先読み | ブラウザーとメールのスキャナーはリンクを先読みするので、`GET` と `HEAD` では確定しない |
| 未認証の確認 | 確認のリンクは、起票したブラウザーと別の端末で開かれ得る。確認は未認証でも行え、CSRF の境界を確認の画面で確立する |
