## アーキテクチャ

### 構成要素

| 構成要素 | 責務 | 依存先 |
| --- | --- | --- |
| 管理者のユースケース | 作成、更新、必須操作、無効化、削除の予約、復元、完全削除。状態の検査、イベントの発行、下流への通知を一つの操作にまとめる | `UserRepository`、`UserMutationCommitter`、`ProvisioningNotifier`、匿名化で消す記録を扱う他の Context のポート |
| フェデレーションのユースケース | 上流で検証済みの属性から User を作る | `UserRepository`、テナントのリソース上限 |
| 属性の検証 | 実効的な属性スキーマで `attributes` を検証する | `TenantUserAttributeSchemaRepository` |
| 管理 API のハンドラー | 管理者の認可、ページング、応答の型への変換 | 管理者のユースケース |

`UserMutationCommitter` は `IdGovernance` が実装する。
User の保存と、その変更から生まれるライフサイクルワークフローの実行を、同じトランザクションで確定する。
組み立てで配線しない構成（単体テスト）では、ユースケースは `UserRepository` へ直接保存する。

### 実行時の流れ：フェデレーションによる作成

フェデレーションのログインで User を作る経路は、通常の作成と同じ検証を通る。

| 検証 | 内容 |
| --- | --- |
| テナントのリソース上限 | User の件数の上限 |
| 一意性 | ユーザー名とメールアドレス |
| 属性スキーマ | 実効的な `UserAttributeDef` |
| イベント | `UserCreated` を発行する |

作る User にはパスワード資格情報を設定しない。
資格情報を後から加えるかは、テナントの明示的な設定で決める。

### 実行時の流れ：完全削除と匿名化

完全削除は、Aggregate を破棄せずにその場で Tombstone へ書き換える。

1. 再識別と再認証に使える項目を一度に消した Tombstone を保存する。
   `preferred_username` は `deleted:<sub>` になり、名前とメールアドレスは空になり、`email_verified` と `mfa_enrolled` は `false` に戻り、`password_hash` と `roles` は空になり、`attributes` は丸ごと消える。
2. 削除した User から以後たどれてはならない記録を、ストアごとに順に消す。
3. テナントの User の使用量を一つ減らす。
4. `UserDeleted` を、操作者、対象、理由、時刻とともに発行し、下流のプロビジョニングへ通知する。

手順 2 で消す記録は、同意、リフレッシュトークン、ログインセッション、パスワードの履歴、多要素認証の要素、記憶済みの端末、WebAuthn の資格情報、復旧コード、デバイス認可、承認要求である。
各記録は、それを所有する Context のポートを通して一つずつ消し、手順の全体を一つのトランザクションにまとめない。
ポートは呼び出しごとに確定し、複数のポートをまたぐトランザクションを提供しないからである。

## データ

| データ | 内容 |
| --- | --- |
| 認証の可否 | 認証を許可するのは `status` が `Active` の場合だけである。`Active` に解決されるゼロ値を含め、ほかの値はすべて拒否する |
| 属性の検証 | 保存の前に `ValidateAttributes` が、定義のないキー、欠けた必須の値、型の不一致を拒否する |
| 本人による属性の変更 | `editable_by_user` が `true` の属性だけを、キーごとに併合する。管理者が管理する属性を上書きしない |
| 本人への属性の開示 | `self_readable` と `claim_exposed` の属性だけを返す |
| 住所の属性 | 平坦なキー（`address_formatted`、`address_locality` など）で保存し、UserInfo と ID Token を作るときだけ入れ子の `address` クレームへ組み直す。`AttributeValue` を文字列、数値、真偽値、日付、文字列の配列の単純な直和型に保つためである |

状態の一次情報、Tombstone とユーザー名の索引、テナントの属性スキーマは、Context の[データ](../../design/data.md)が扱う。

## 信頼性

| 症状 | 原因 | 直し方 |
| --- | --- | --- |
| 完全削除がエラーを返した後も、User の関連する記録の一部が残る | Tombstone を保存した後に、手順 2 以降のどれかが失敗した | 再実行では直らない。削除済みの User の完全削除は何もせずに成功するので、残った記録は消えず、使用量も減らない。残った記録を、その User の `sub` についてストアごとに手作業で消す |
| テナントの User の使用量が実際の件数より多い | 手順 3 の前に完全削除が失敗した | 使用量を実際の件数に合わせて手作業で直す |

## リスク

完全削除を途中で失敗させると、再実行で回収できない。
Context の[リスク](../../design/risks.md)に載せる。
