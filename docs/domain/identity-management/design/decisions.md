# IdManagement の重要な設計判断

この文書は、IdManagement の設計判断のうち、代替案を比べたものと、見直す条件が要るものを扱う。
一つの規則やモデルだけを正当化する判断は、機能仕様のその規則またはモデルの判断の欄に置く。

## この Context を Core に分類する

### 背景

ドメイン文書の索引は、各 Context を `Core`、`Supporting`、`Generic` のいずれかに分類する。
分類は、どの Context に設計の労力を集中させるか、どの Context を外部の製品へ委譲できるかを左右する。

### 決定

IdManagement を `Core` に分類する。

### 検討した代替案

| 案 | 利点 | 欠点 | 採らない理由 |
| --- | --- | --- | --- |
| `Supporting` | 設計の労力を `Authentication` と `OAuth2` に集中できる | プリンシパルの台帳を、製品の差別化に寄与しない部品として扱うことになる | 人間と Agent を同じ台帳の主体として扱い、所有者、目的、ライフサイクルを与えることが製品の主張そのものである |
| `Generic` | 外部の製品へ委譲して、実装と保守を減らせる | 動的メンバーシップの規則、CSV の往復、Tombstone とカスケードを、外部の製品の制約に合わせることになる | 委譲できる相手が存在しない |

### 結果と再検討の条件

プリンシパルの台帳のモデル（動的メンバーシップの規則、CSV の往復、Tombstone とカスケード）に、他の Core の Context と同じ水準の設計と検証を求める。
人間と Agent を同じ台帳で扱うことが製品の主張から外れた場合、または台帳を委譲できる外部の製品が現れた場合に見直す。

### 関連する要件

この判断は分類であり、特定の規則を正当化しない。

## User、Group、Agent を機能ごとの縦割りのスライスで構成する

### 背景

IdManagement のコードは、当初 `domain`、`ports`、`usecases`、アダプターの層だけで分かれていた。
コードが 8,000 行を超えると、一つの層のディレクトリに `User`、`Group`、`Agent` の無関係なファイルが並び、どのファイルがどの Aggregate に属するかを読み取れなくなった。

### 決定

`User`、`Group`、`Agent` のそれぞれを、`domain`、`ports`、`usecases`、アダプターの層をそろえた機能スライス（`backend/idmanagement/<feature>/`）として構成する。
スライスが共有する CSV の仕組み、データエクスポート、ロールの割り当ての判定は、Context のルートの層に置く。

### 検討した代替案

| 案 | 利点 | 欠点 | 採らない理由 |
| --- | --- | --- | --- |
| すべての Context に一律で機能スライスの段を入れる | 規約が一つで済む | 機能が一つしかない Context では、Context と同じ名前の段が重なる | 小さな Context では段が増えるだけで、読みやすさが上がらない |
| `module.go` を機能ごとに分ける | 組み立ても機能ごとに読める | アプリケーションの組み立ての変更が広範になる | ソースの配置を読みやすくするという目的に対して、費用が大きい |
| HTTP の `Deps` を機能ごとの部分構造体に分ける | ハンドラーが使う依存を機能ごとに限定できる | 各ハンドラーが他の機能のポートを横断的に参照している | 部分構造体の間で依存が重複し、分けた効果がない |

### 結果と再検討の条件

一つの Aggregate の仕組みを、一つのディレクトリの下で読める。
機能仕様の機能ノード（`user`、`group`、`agent`）は、このスライスに対応する。
スライスの間の参照が増え、スライスが独立に読めなくなった場合に見直す。

### 関連する要件

この判断は構成であり、特定の規則を正当化しない。

## CSV の適用をプレビューで保存したペイロードに束縛する

### 背景

CSV のインポートは、プレビューで全行を検証してから、別の要求で適用する。
プレビューから適用までの間に、管理者が別の CSV を送ることも、他の管理者が同じ User や Group を変えることもある。

### 決定

適用は、成功したプレビューのジョブ ID だけを受け付け、プレビューで保存したペイロードを SHA-256 で照合して実行する。
変更の計画は、プレビュー時のものを使わず、適用の時点の状態に対して作り直す。

### 検討した代替案

| 案 | 利点 | 欠点 | 採らない理由 |
| --- | --- | --- | --- |
| 適用の要求でクライアントが CSV を送り直す | 成果物ストアが要らない | プレビューした内容と適用する内容が一致する保証がない | 管理者が確認していない内容を適用できる |
| プレビュー時に作った変更の計画をそのまま実行する | 適用で計画をやり直す費用が要らない | プレビューの後の同時の変更を上書きする | プレビューが暗黙の楽観的ロックの迂回路になる |

### 結果と再検討の条件

管理者が確認したペイロードだけが適用され、プレビューの後の変更は適用の時点で行のエラーとして見える。
その代わり、プレビューで成功した行が、適用で失敗することがある。
CSV 以外の一括変更の窓口（API の一括操作など）を設けて、プレビューの段を省く場合に見直す。

### 関連する要件

| 規則 | 機能仕様 |
| --- | --- |
| CSV のプレビューと適用の規則 | [ユーザー CSV](../user-csv/README.md)、[グループ CSV](../group-csv/README.md) |

## CSV に現れない Group とメンバーシップを変えない

### 背景

CSV のファイルは、転送ポリシーの上限に合わせた分割、一覧の絞り込み、途中で失敗した生成のどれでも、テナントの一部の Group やメンバーシップしか含まないことがある。
CSV のインポートには、ファイルを権威として扱い、ファイルにないものを消す同期（authoritative full-sync）の方式もあり得る。

### 決定

CSV のインポートは、行ごとに宣言した意図だけを実行する。
ファイルに現れない Group は削除せず、ファイルに現れない User の所属は変えない。
削除は `lifecycle_action=delete`、所属の解除は `membership_state=absent` を、行ごとに明示して表す。

### 検討した代替案

| 案 | 利点 | 欠点 | 採らない理由 |
| --- | --- | --- | --- |
| ファイルを権威とし、ファイルにない Group と所属を消す | 外部の一覧と完全に一致させられる | 分割したファイルや絞り込んだエクスポートが、そのまま大量の削除と解除になる | 「CSV にない＝不要」という解釈と結び付いた瞬間に、意図しない一括の削除になる |

### 結果と再検討の条件

ファイルの分割と絞り込みは安全であり、編集していないエクスポートの再適用は何も変えない。
その代わり、不要になった Group と所属は、行ごとに明示して消す必要がある。
ファイルの全体が権威であることを、ファイルとは別の手段で表明できるようになった場合に見直す。

### 関連する要件

| 規則 | 機能仕様 |
| --- | --- |
| REQ-IDMANAGEMENT-028、REQ-IDMANAGEMENT-030 | [グループ CSV](../group-csv/README.md) |

## 予約ロールを書き込みが新しく加える分だけで判定する

### 背景

`system_admin` は、制御面テナントの User と Group にだけ割り当てられる予約ロールである。
予約する前から、制御面テナント以外で `system_admin` をテナント固有の文字列として使ってきた環境があり得る。
CSV には、無編集のエクスポートを再適用すると全行が `unchanged` になるという往復の性質がある。

### 決定

予約ロールの判定は、保存後のロールの集合ではなく、その書き込みが新しく加えるロールだけを見る。
対象がすでに `system_admin` を持っていれば、同じ値を含む書き込みを拒否しない。

### 検討した代替案

| 案 | 利点 | 欠点 | 採らない理由 |
| --- | --- | --- | --- |
| 保存後のロールの集合で判定する | 予約ロールを持つべきでない対象を、書き込みのたびに必ず検出する | 既存の値を持つ対象の行が、無編集の再適用でも拒否される | CSV の往復の性質が壊れる |
| 移行で、制御面テナントの外の `system_admin` を消す | 判定を集合で行える | テナント固有の文字列として使っている環境から、値が無断で失われる | テナントのデータを製品の都合で消すことになる |

### 結果と再検討の条件

新しい割り当ての拒否、既存の値の保持、`roles` を明示して外す経路が同時に成り立つ。
その代わり、制御面テナントの外に既存の `system_admin` が残り続ける。
テナントをまたぐ能力は、所属テナントを要求する制御面の判定で別に無効にしている。
既存の値を持つテナントがなくなった場合、または制御面の判定がロール名だけに頼るよう変わる場合に見直す。

### 関連する要件

| 規則 | 機能仕様 |
| --- | --- |
| REQ-IDMANAGEMENT-032 `system_admin` は制御面テナントの User と Group にだけ割り当てられる | [ロール](../roles/README.md) |

## Agent を OAuth2Client に束縛する第 3 のプリンシパルとする

### 背景

業務用のエージェントは、人の User とも、一般的なマシン間連携の `OAuth2Client` とも違う扱いを要する。
所有者、目的、人の関与の度合い（区分）、緊急停止を、監査とポリシーで区別できなければならない。
一方で、資格情報と鍵の管理の仕組みは、すでに `OAuth2Client` にある。

### 決定

`Agent` を `User` と `OAuth2Client` に並ぶ第 3 のプリンシパルとし、独自の資格情報を持たせない。
Agent は既存の `OAuth2Client` に束縛してトークンを得て、所有権、目的、ライフサイクルの層だけを加える。

### 検討した代替案

| 案 | 利点 | 欠点 | 採らない理由 |
| --- | --- | --- | --- |
| エージェントの属性を `OAuth2Client` に加える | 新しい Aggregate が要らない | 監査とポリシーで、エージェントと一般的なマシン間連携のクライアントを区別できない | エージェントに固有の統制（所有者、緊急停止）を当てる対象を特定できない |
| Agent に独自の資格情報を持たせる | Agent の仕組みが `OAuth2` から独立する | 資格情報と鍵の管理の仕組みが二つになる | 攻撃面が倍になる |

### 結果と再検討の条件

資格情報と鍵の管理は `OAuth2Client` の一つの仕組みで済み、Agent はその上に所有者と状態を持つ。
その代わり、Agent のトークンの発行の可否は `OAuth2` の発行の境界が Agent の状態を読んで判定する必要があり、二つの Context にまたがる。
Agent に `OAuth2Client` では表せない資格情報（ワークロードの証明など）が要る場合に見直す。

### 関連する要件

| 規則 | 機能仕様 |
| --- | --- |
| REQ-IDMANAGEMENT-009、REQ-IDMANAGEMENT-074 | [エージェント](../agent/README.md) |

## User の削除を物理削除ではなく Tombstone で行う

### 背景

`AdminAuditEvent` などの追記専用の記録は、User の `sub` を参照する。
運用では、削除した User と停止しただけの User を区別する必要がある。

### 決定

User の完全削除は、レコードを消さずに、再識別と再認証に使える項目を消した `Deleted` の Tombstone へ置き換える。
`sub` は保持し、再利用しない。
関連する記録（同意、リフレッシュトークン、セッション、資格情報など）は、カスケードして消す。

### 検討した代替案

| 案 | 利点 | 欠点 | 採らない理由 |
| --- | --- | --- | --- |
| レコードを物理削除する | 個人情報を確実に残さない。保存領域を使わない | 追記専用の記録が参照する `sub` が、どの User も指さなくなる | 監査記録の参照を壊し、削除と停止の区別も失う |

### 結果と再検討の条件

匿名化した後も、監査記録から誰がいつ何を削除したかを再構成できる。
その代わり、Tombstone のレコードは残り続け、ユーザー名の一意性の索引は削除済みの User を除外する必要がある。
追記専用の記録が `sub` を参照しなくなった場合、または個人情報の保護の要件が Tombstone の保持を許さなくなった場合に見直す。

### 関連する要件

| 規則 | 機能仕様 |
| --- | --- |
| REQ-IDMANAGEMENT-013 管理者はユーザーを完全削除できる | [ユーザーのライフサイクルの操作](../user/lifecycle.md) |
| REQ-IDMANAGEMENT-050 User の完全削除は匿名化であり、削除済みの User には何もしない | [ユーザーのライフサイクルの操作](../user/lifecycle.md) |
