# IdManagement の設計判断

- 管理 API はプリンシパルの種類と操作ごとに権限を分ける。`User` は参照 (`admin:user_read`)、作成 (`admin:user_create`)、CSV インポート (`admin:user_import`)、更新 (`admin:user_update`)、削除 (`admin:user_delete`)、復元 (`admin:user_restore`)、完全削除 (`admin:user_purge`)、`Group` は参照 (`admin:groups_read`) と変更 (`admin:groups_write`)、`Agent` は `admin:agents_manage` を要する。いずれも `admin` ロールを持つ、有効かつ認証済みのユーザーに限る。Agent のキルスイッチを含むライフサイクル操作も、汎用の管理者権限ではなく `admin:agents_manage` で制御する。
- API アクセストークンでは、ロールに加えてプリンシパルの種類ごとのスコープを要求する。`users:*`、`groups:*`、`agents:*` がそれぞれに対応し、`read` が参照だけを、`write` が変更を許可する。種類をまたぐ流用はできない。
- 読み書きの境目は HTTP メソッドではなく、操作が対象を変更するかで決める。CSV エクスポートの開始、参照、ダウンロード、取り消しはいずれも対象データの読み出しの投影であり `User` も `Group` も変更しないため参照系に置く。データを読むだけのために変更権限を渡さずに済ませるためである。動的グループ規則のプレビューも同じ理由で参照系とする。逆に CSV インポートは `User` を変更するため変更系に置く。
- Agent のキルスイッチは `agents:write` に含める。Agent の削除は同じスコープにあり、キルより厳密に破壊的であるため、キルだけを外しても防御にならない。
- 対象は常に呼び出し元と同じテナントに属していなければならない。テナントをまたぐメンバーシップは無条件に拒否し、`AddMember` は対象 `User` を読み込んだうえで別テナントに属していれば拒否する。
- セルフサービス API (`/api/account/*`) は認証済み本人の記録だけに閉じる。本人が書き込めるのは `editable_by_user == true` の属性に限り、更新は対応表全体の置き換えではなくキーごとの併合とする。本人へ開示するのも `self_readable` と `claim_exposed` の属性だけで、`admin_readable` と `private` は読み出せない。
- 自己破壊は防ぐ。操作者と対象が同じプリンシパルで、その対象が `admin` または `system_admin` を持つ場合、削除は拒否する。管理者が自身の特権アカウントを消す経路は、どの対話フローにも必要ないからである。
- CSV インポートは、より強い上流の権威を上書きしない。取り込み元が管理する `User` と `Group` は `source_managed` として拒否し、所有権を確認できない場合も外部管理として扱って拒否する。
- CSV の転送ポリシー、解析器、可逆なセル変換、不変な成果物ストアは種別に依存しない 1 つの内側 module に実装し、`User` と `Group` が共有する。列の語彙と計画器は共有しない。不変な項目、外部規則、ライフサイクル操作は Aggregate ごとの不変条件であり、1 つに一般化すると両方の規則が読めなくなるからである。
- CSV による `Group` の削除は、目標状態の列ではなく書き込み専用の `lifecycle_action` 列で表す。エクスポートが出力する列を破壊的な意図の表現に流用すると、無編集のエクスポートを適用すると全行 `unchanged` になるという往復不変条件が失われ、フィルターや分割で一部の行だけを含むファイルが大量削除の発火源になるからである。
- CSV に現れない `Group` は削除しない。authoritative full-sync を採らないのは、分割ファイルや絞り込んだエクスポートが「CSV に無い = 不要」という解釈と結び付いた瞬間に、意図しない一括削除になるからである。再検討するのは、ファイル全体が権威であることを別の手段で表明できるようになったときとする。
- `Group.membership_type` は作成時にだけ選べ、CSV からも変更できない。手動所属と動的所属では既存メンバーシップの意味そのものが変わり、1 セルでそれを反転させると、どの経路で付いた所属なのかを後から復元できないからである。
- 動的規則の式と有効化は、行が与えた列と維持された相方を組み合わせた最終状態に対して検証する。列ごとに検証すると、どちらの列単体では不正に見えない組み合わせを通してしまうからである。
- `User`、`Group`、`Agent` は 1 つの平らなパッケージではなく、それぞれがドメイン、ポート、ユースケース、アダプターを持つ機能ごとの垂直分割として構成する。
- `disabled_at` は `deleted_at` とは別の、元に戻せる停止とする。停止した User は新規のサインイン、既存のセッション、トークンの再発行、UserInfo のいずれも拒否されるが、アカウントとその履歴は復帰のために残る。
- 管理レスポンスは `password_hash` を決して含まない専用の型を通す。汎用のドメイン型をそのまま返す経路を作らないのは、後から項目が増えたときに管理 API から漏れる形にしないためである。
- User の削除は行の物理削除ではなく、再識別できる項目を消した `Deleted` の Tombstone とする。`AdminAuditEvent` などの追記専用の記録が `sub` を参照しており、物理削除はその参照を壊すうえ、「削除済み」と「停止中」の運用上の区別も消してしまうからである。
- `User` の型付き中核は最小限に保ち、それ以外のプロフィール属性は 1 つの疎な `attributes` に置く。ほとんどのテナントが使わない約 25 個の任意項目を、すべてのユーザーの型と保存領域に追加しないためである。
- 組み込みの属性とテナント定義の属性を 2 つの仕組みに分けず、`UserAttributeDef` の 1 つのスキーマ機構 (組み込みカタログ ∪ テナントスキーマ) で統べる。管理者が向き合うスキーマの形を 1 つに保つためである。
- 属性の `pii` はデフォルトを `true` とする。テナントの利便より開示の上限を優先する、安全側のデフォルトである。
- CSV の適用は、クライアントが再送する CSV ではなく、サーバーが保持する成功済みのプレビューペイロードだけを対象とし、変更計画は現在の状態から作り直す。プレビューが暗黙の楽観的ロックの迂回路になることを防ぐためである。
- `Group.attributes` は `UserAttributeDef` / `TenantUserAttributeSchema` へ統合せず、別の `GroupAttributeDef` / `TenantGroupAttributeSchema` を使う。`Group` には共有できる組み込みカタログも、セルフサービスの編集画面も、クレーム開示の層もないからである。
- 実効ロールは `user.roles` と所属 Group のロールの単純な和集合とし、優先順位や減算の規則は設けない。平らな和集合で足りるところに deny を導入すると、評価順の複雑さだけが増えるからである。
- ロール語彙のうち `system_admin` だけを予約ロールとし、制御面テナントの User と Group にだけ新しく割り当てられるようにする。Agent にはどのテナントでも割り当てない。Agent は [認可](../../design/security/authorization.md) がシステム運用者とは別の主体として定義しており、制御面の管理 API が受け入れるのは User と ApiToken だけだからである。同じロール名を通常テナントの任意文字列としても使える状態を残すと、管理 UI、監査、将来の認可処理が、それを製品ロールとして扱うのかテナント固有ロールとして扱うのか判別できない。`admin` とテナント固有ロールは予約せず、語彙全体を閉じた列挙にもしない。
- 予約ロールの割当て規則は、字句の正規化ではなく製品上の割当て規則として別に判定する。正規化は Agent を含む全対象で共有しており、対象種別とテナントを知らないからである。判定はユースケース境界に置き、HTTP ハンドラーには置かない。ハンドラーに置くと CSV の適用時の再計画が検査を通らない。
- 予約ロールの判定は保存後のロール集合そのものではなく、その書き込みが新しく加える分だけを見る。絶対集合で判定すると、`system_admin` をテナント固有の文字列として使ってきた環境では、無編集のエクスポートを再適用すると全行 `unchanged` になるという CSV の往復不変条件が壊れる。差分で判定すれば、新規割当ての拒否、既存値の保持、`roles` を明示して外す除去経路が同時に成り立つ。
- 制御面テナントの外に保存済みの `system_admin` は移行で自動削除しない。テナント固有の文字列として使っている環境から値を無断で失わせないためであり、テナント横断の能力自体は所属テナントを要求する制御面の判定で先に無効化されているからである。
- `Agent` は `User` と `OAuth2Client` に並ぶ第 3 の第一級プリンシパル型とし、独自の資格情報や暗号インターフェースは定義せず既存の `OAuth2Client` にバインドする。エージェント固有の関心事を `OAuth2Client` に後付けすると監査とポリシーで一般的な M2M クライアントと区別できず、独立した資格情報を与えると攻撃面が倍増するからである。
- すべての `Agent` に所有者を必須とし、所有者のオフボーディングを配下の `Agent` へ伝播させる。孤立した非人間アイデンティティを残さないためである。
- この Context を `Core` に分類する。人間と Agent を同じ台帳の主体として扱い、所有者、目的、ライフサイクルを与えることがプロダクトの主張そのものであり、動的メンバーシップ規則、CSV の往復、Tombstone とカスケードを抱えてモデルも複雑である。委譲できる相手が存在しない。
- メールアドレス変更の確認トークンは共通のアクショントークン核が発行し検証する ([設計ガイドライン](../../design/application/design-guidelines.md))。この Context では、新しいアドレスという用途別のペイロードと、`User` の primary email を確定する作用だけを扱う。トークンの使用済み化とその確定は 1 つのトランザクションで行う。分けると、同じリンクで二度アドレスが変わる状態と、起票から確定までの間に別の利用者が同じアドレスを取ったために拒否された利用者がリンクだけを失う状態のどちらかが起きる。相手がアドレスを手放せば同じリンクがまだ使えるべきなので、作用が失敗したときはトークンを未使用のまま残す。
- `Group` は、メンバーシップと動的メンバーシップ規則を含めて 1 つの Aggregate とする。規則が指すグループが存在しない状態や、削除済みのグループにメンバーが残る状態は一瞬でも成立してはならないためである。`User` は別の Aggregate であり、メンバーシップにはその識別子だけを記録する。この向きにするのは、ユーザー 1 人の更新がその人の所属する全グループを直列化させないためである。
