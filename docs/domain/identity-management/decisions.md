# IdManagement の設計判断

- 管理 API はプリンシパルの種類と操作ごとに権限を分ける。`User` は参照 (`admin:user_read`)、作成 (`admin:user_create`)、CSV インポート (`admin:user_import`)、更新 (`admin:user_update`)、削除 (`admin:user_delete`)、復元 (`admin:user_restore`)、完全削除 (`admin:user_purge`)、`Group` は参照 (`admin:groups_read`) と変更 (`admin:groups_write`)、`Agent` は `admin:agents_manage` を要する。いずれも `admin` ロールを持つ、有効かつ認証済みのユーザーに限る。Agent のキルスイッチを含むライフサイクル操作も、汎用の管理者権限ではなく `admin:agents_manage` で制御する。
- API アクセストークンでは、ロールに加えてプリンシパルの種類ごとのスコープを要求する。`users:*`、`groups:*`、`agents:*` がそれぞれに対応し、`read` が参照だけを、`write` が変更を許可する。種類をまたぐ流用はできない。
- 読み書きの境目は HTTP メソッドではなく、操作が対象を変更するかで決める。CSV エクスポートの開始、参照、ダウンロード、取り消しはいずれも対象データの読み出しの投影であり `User` も `Group` も変更しないため参照系に置く。データを読むだけのために変更権限を渡さずに済ませるためである。動的グループ規則のプレビューも同じ理由で参照系とする。逆に CSV インポートは `User` を変更するため変更系に置く。
- Agent のキルスイッチは `agents:write` に含める。Agent の削除は同じスコープにあり、キルより厳密に破壊的であるため、キルだけを外しても防御にならない。
- 対象は常に呼び出し元と同じテナントに属していなければならない。テナントをまたぐメンバーシップは無条件に拒否し、`AddMember` は対象 `User` を読み込んだうえで別テナントに属していれば拒否する。
- CSV インポートは、より強い上流の権威を上書きしない。取り込み元が管理する `User` と `Group` は `source_managed` として拒否し、所有権を確認できない場合も外部管理として扱って拒否する。
- CSV の転送ポリシー、解析器、可逆なセル変換、不変な成果物ストアは種別に依存しない 1 つの内側 module に実装し、`User` と `Group` が共有する。列の語彙と計画器は共有しない。不変な項目、外部規則、ライフサイクル操作は Aggregate ごとの不変条件であり、1 つに一般化すると両方の規則が読めなくなるからである。
- `User`、`Group`、`Agent` は 1 つの平らなパッケージではなく、それぞれがドメイン、ポート、ユースケース、アダプターを持つ機能ごとの垂直分割として構成する。
- CSV の適用は、クライアントが再送する CSV ではなく、サーバーが保持する成功済みのプレビューペイロードだけを対象とし、変更計画は現在の状態から作り直す。プレビューが暗黙の楽観的ロックの迂回路になることを防ぐためである。
- ロール語彙のうち `system_admin` だけを予約ロールとし、制御面テナントの User と Group にだけ新しく割り当てられるようにする。Agent にはどのテナントでも割り当てない。Agent は [認可](../../design/security/authorization.md) がシステム運用者とは別の主体として定義しており、制御面の管理 API が受け入れるのは User と ApiToken だけだからである。同じロール名を通常テナントの任意文字列としても使える状態を残すと、管理 UI、監査、将来の認可処理が、それを製品ロールとして扱うのかテナント固有ロールとして扱うのか判別できない。`admin` とテナント固有ロールは予約せず、語彙全体を閉じた列挙にもしない。
- 予約ロールの割当て規則は、字句の正規化ではなく製品上の割当て規則として別に判定する。正規化は Agent を含む全対象で共有しており、対象種別とテナントを知らないからである。判定はユースケース境界に置き、HTTP ハンドラーには置かない。ハンドラーに置くと CSV の適用時の再計画が検査を通らない。
- 予約ロールの判定は保存後のロール集合そのものではなく、その書き込みが新しく加える分だけを見る。絶対集合で判定すると、`system_admin` をテナント固有の文字列として使ってきた環境では、無編集のエクスポートを再適用すると全行 `unchanged` になるという CSV の往復不変条件が壊れる。差分で判定すれば、新規割当ての拒否、既存値の保持、`roles` を明示して外す除去経路が同時に成り立つ。
- 制御面テナントの外に保存済みの `system_admin` は移行で自動削除しない。テナント固有の文字列として使っている環境から値を無断で失わせないためであり、テナント横断の能力自体は所属テナントを要求する制御面の判定で先に無効化されているからである。
- この Context を `Core` に分類する。人間と Agent を同じ台帳の主体として扱い、所有者、目的、ライフサイクルを与えることがプロダクトの主張そのものであり、動的メンバーシップ規則、CSV の往復、Tombstone とカスケードを抱えてモデルも複雑である。委譲できる相手が存在しない。
