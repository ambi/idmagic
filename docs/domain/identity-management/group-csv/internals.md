# グループ CSV の内部設計

## グループ CSV の不変条件と削除

`Group` の CSV は [CSV の往復変換](../internals.md#csv-の往復変換)の基盤をそのまま使い、その上に `Group` 固有の不変条件だけを載せる。`membership_type` は作成時に選べるが後から変えられない。既存の `Group` に現在値と異なる値を書いた行は、暗黙に変換せず安定したエラーで拒否する。手動所属と動的所属では既存メンバーシップの意味そのものが変わり、CSV の 1 セルでそれを反転させると、どの経路で付いた所属なのかを後から復元できないからである。

動的規則の式と有効化は 2 つの列に分かれるが、検証は片方だけを見ない。行が与えた列と維持された相方を組み合わせた最終状態を作り、それに対して規則をコンパイルする。片方だけの検証では「式を消して有効のまま」「手動グループに式だけを与える」といった、どちらの列単体では不正に見えない状態を通してしまう。式は動的グループが使う小さな CEL 環境でコンパイルし、参照属性も同時に確定する。規則の削除は CSV から行わない。`Group` Aggregate に規則の削除操作が無く、空欄を「規則なし」と解釈すると、列を落としたファイルと空欄のファイルの意味が入れ替わるためである。

削除は目標状態の列ではなく、`lifecycle_action` という書き込み専用の action 列で表す。エクスポートはこの列を常に空で出力するため、無編集の往復は全行 `unchanged` のままである。エクスポートが出力する列を破壊的な意図の表現に流用すると、フィルターや分割で一部の行だけを含むファイルがそのまま大量削除の発火源になる。`Group` には削除予約状態が無いので語彙は `delete` だけの閉じた集合とし、未知の値は既知の値へ丸めず拒否する。CSV に現れない `Group` は削除対象に入らない。これは authoritative full-sync ではなく、行ごとに宣言された意図だけを実行する経路である。

削除の意図と更新の意図は 1 行に同居できない。`delete` の行が現在状態に対して差分のある書き込み可能な列も持つ場合は、行ごと拒否する。`Group` は削除で消えるため、直前の更新を監査に残すと存在しなかった状態の記録になるからである。差分が無ければ、無編集のエクスポート行に `delete` だけを書いた形として受理する。対象を解決できない `delete` の行は作成に落ちず、拒否する。綴り誤りや古いファイルを `unchanged` として通すと、破壊的操作の直前にプレビューが与える情報が失われる。

削除の適用は、`Group` の削除、メンバーシップの cascade 解除、グループクォータの解放、監査記録を 1 行 1 トランザクションで確定する。プレビューは削除件数と巻き込まれるメンバーシップ件数を他の操作と分けて返し、管理 UI は削除を含む適用に明示の確認を要求する。削除は不可逆で、cascade により所属していた全 `User` の実効ロールを一度に変えるため、preview と apply の結合、現在状態からの再計画、閉じた語彙、明示確認、エクスポートでの常時空出力を多層で維持する。1 つでも欠けると、分割ファイルや編集ミスがそのまま権限の一括剥奪になる。

## グループ所属 CSV と明示的な望ましい状態

メンバーシップの CSV が変更できる `Group` は 1 つだけである。どの `Group` かを決めるのは URL の `group_id` であって、ファイルの中身ではない。CSV の `group_id` 列と `group_name` 列は、その行が本当に対象の `Group` の行かを確かめるためだけにあり、書き込みには使わない。別の `Group` を指す行はその行だけを拒否し、指された `Group` には何も書かない。もしファイルの中身が対象を選べるなら、1 つの `Group` を編集する権限が、そのファイルに書いた任意の `Group` を編集する権限になってしまう。

行が何をしたいかを表す列は `membership_state` だけである。`present` は「この `User` を所属させたい」、`absent` は「この `User` の手動の所属を外したい」を意味する。すでに望みどおりの状態なら、どちらも何もしない。値はこの 2 つに限り、空のセルも知らない値も、近い値へ丸めず拒否する。丸めるということは、追加と解除のどちらかを、ファイルが書いていないのに選ぶということだからである。

`membership_state` 列そのものが無いファイルも、ファイルごと拒否する。他の列は順序も部分集合も自由だが、この列だけは別扱いにする。この列が無いファイルは何ひとつ意図を表せない。それを「変更 0 件」として受理すると、管理者は自分の編集が読まれたうえで差分が無かったと受け取ってしまう。

CSV に書かれていない `User` は、何も変更しない。ここが authoritative full-sync を採らなかった理由である。「CSV に無い所属は消す」と解釈すると、転送ポリシーの上限に合わせたファイル分割、一覧のフィルター、途中で失敗した生成が、そのまま大量の所属解除になる。外したい所属は、行ごとに `absent` と書いて表す。プレビューは解除の件数を追加や変更なしとは分けて返し、管理 UI は解除を含む適用に明示の確認を求める。

対象の `User` は `user_id` で解決し、無ければテナント内で一意な `preferred_username` で解決する。両方が書かれていて別々の `User` を指す行は、どちらを選ぶかを決めずに拒否する。同じ `User` を複数の行が指すファイルも拒否する。どの行の意図が勝つかを、ファイルの並び順に委ねないためである。`source` と `created_at` は受理したうえで無視する読み取り専用の列である。

外部が所有している所属は、CSV から書き換えない。対象の `Group` が `dynamic` なら、ファイル全体を拒否する。手動の追加と解除は動的規則による評価と両立しないので、行ごとに拒否しても全行が同じ理由で落ちるだけであり、ファイルごと断るほうが管理者に伝わる。現在の所属の `source` が `dynamic_rule` である行は、`present` でも `absent` でも拒否する。`present` の側は何も書き込まないので受理してもよさそうに見えるが、規則が次に一致しなくなればその所属は消える。「変更なし」と答えると、管理者が受け取る保証と、その所属が実際に続く期間が食い違ってしまう。

取り込み元による所有は `Group` と `User` の両方について調べ、判定できない場合は所有されているものとして扱う。メンバーシップは `Group` と `User` を結ぶ関係なので、どちらか一方でも外部が所有していれば、その関係を決める権限も外部にあるとみなす。

エクスポートは、インポートと同じ機械キーの語彙、同じ転送ポリシー、同じ不変な成果物ストアを使い、`membership_state` を全行 `present` として出力する。そのため、編集していないエクスポートをそのままプレビューすれば全行が `unchanged` になる。適用が受け取るのは、成功したプレビューの ID とその SHA-256 だけであり、テナントと `Group` の両方が一致することを結合の条件にする。計画は現在の所属から作り直すので、プレビュー後に別の経路で行われた追加や解除も、そこで判定し直される。受理した行は、メンバーシップの追加または解除と監査記録を 1 行 1 トランザクションで確定する。ある行が失敗しても、すでに適用した行は巻き戻さない。
