# グループの設計判断

- `Group.membership_type` は作成時にだけ選べ、CSV からも変更できない。手動所属と動的所属では既存メンバーシップの意味そのものが変わり、1 セルでそれを反転させると、どの経路で付いた所属なのかを後から復元できないからである。
- `Group.attributes` は `UserAttributeDef` / `TenantUserAttributeSchema` へ統合せず、別の `GroupAttributeDef` / `TenantGroupAttributeSchema` を使う。`Group` には共有できる組み込みカタログも、セルフサービスの編集画面も、クレーム開示の層もないからである。
- 実効ロールは `user.roles` と所属 Group のロールの単純な和集合とし、優先順位や減算の規則は設けない。平らな和集合で足りるところに deny を導入すると、評価順の複雑さだけが増えるからである。
- `Group` は、メンバーシップと動的メンバーシップ規則を含めて 1 つの Aggregate とする。規則が指すグループが存在しない状態や、削除済みのグループにメンバーが残る状態は一瞬でも成立してはならないためである。`User` は別の Aggregate であり、メンバーシップにはその識別子だけを記録する。この向きにするのは、ユーザー 1 人の更新がその人の所属する全グループを直列化させないためである。
