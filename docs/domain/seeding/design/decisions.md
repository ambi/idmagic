# Seeding の重要な設計判断

この文書は、Seeding の設計判断のうち、代替案を比べたものと、見直す条件が要るものを扱う。
一つの要件やモデルだけを正当化する判断は、機能仕様のその要件またはモデルの判断の欄に置く。

## seed の計画と適用に HTTP のエンドポイントを設けない

### 背景

seed は、テナントをまたいで書き込める唯一の経路である。
本番に投入してよいデータは、稼働に必要な最小のデータに限られる。

### 決定

seed の計画と適用に HTTP のエンドポイントを設けない。
実行できるのは、`idmagic-seed` などのプロセスを起動できる運用者と自動化主体だけとし、実行環境そのものを権限の境界とする。
権限の代わりに、環境ポリシーが書き込みを制限する。本番が受け付けるのは `bootstrap` のプロファイルと `file` のシークレットの提供元だけで、それ以外はシークレットの解決も書き込みも行う前に拒否する。

### 検討した代替案

| 案 | 利点 | 欠点 | 採らない理由 |
| --- | --- | --- | --- |
| 管理 API として公開し、`system_admin` に限る | 運用者がブラウザーや API から seed を実行できる | テナントをまたぐ書き込みが、資格情報を持つ要求から到達できる経路になる | 資格情報の漏えいが、テナントをまたぐ書き込みに直結する |

### 結果と再検討の条件

テナント管理者やアプリケーションのトークンからは、seed に到達できない。
その代わり、seed を実行するには、運用者が実行環境へ入れる必要がある。
実行環境へ入らずに初期データを投入する要求（マネージドサービスとしての提供など）が出た場合に見直す。

## 投入の構成を独立した運用の Context に集約する

### 背景

初期データは、Tenancy、IdManagement、OAuth2、Application など複数の Context にまたがる。
本番に投入してよいかの判断は、Context をまたいで一か所で行う必要がある。

### 決定

投入の構成を各 Context へ分散させず、独立した運用の Context に集約する。

### 検討した代替案

| 案 | 利点 | 欠点 | 採らない理由 |
| --- | --- | --- | --- |
| 各 Context が自分の初期データを持つ | 各 Context の型と不変条件のそばに初期データを置ける | 環境ポリシーとシークレットの扱いが、Context ごとに散らばる | Context をまたぐ安全性を検証できる一つの地点が失われる |

### 結果と再検討の条件

環境ポリシー、マニフェストの文法、シークレットの扱いを一か所で検証できる。
その代わり、新しいリソースの種類を seed するたびに、この Context と `Contributor` を変える。
Context ごとに独立して配置し、独立して初期化する構成へ移る場合に見直す。

### 関連する要件

| 要件 | 機能仕様 |
| --- | --- |
| REQ-SEEDING-001 | [seed の計画と適用](../seed-run/README.md) |

## SQL フィクスチャを使わず記録の正を持つ Context の型を通して書き込む

### 背景

初期データにも、通常の作成の経路と同じ不変条件が成り立たなければならない。

### 決定

適用は、SQL フィクスチャではなく、記録の正を持つ Context のドメインの型とその保存の経路を通す。

### 検討した代替案

| 案 | 利点 | 欠点 | 採らない理由 |
| --- | --- | --- | --- |
| SQL フィクスチャで行を直接書き込む | 大量のデータを速く投入できる | 各 Context の不変条件を迂回する | 仕様が禁じる状態を作れてしまう |

### 結果と再検討の条件

seed で作るデータは、各 Context のドメインの型として組み立てられる。
ただし、現状の `Contributor` はユースケースではなく Repository を直接呼ぶので、ユースケースが守る不変条件は通らない（[Seeding のリスク](risks.md)）。
合成データの件数が、型を通した書き込みでは現実的な時間で投入できない規模になった場合に見直す。

### 関連する要件

| 要件 | 機能仕様 |
| --- | --- |
| REQ-SEEDING-006 | [seed の計画と適用](../seed-run/README.md) |

## マニフェストの文法から外部の値の取り込みを除外する

### 背景

マニフェストは、運用者が編集する YAML のファイルである。
読み込みの時点で外部の値を取り込める文法は、パストラバーサルと注入の余地を残す。

### 決定

マニフェストの文法から、マージキー、テンプレートの展開、リモートの URL、`${ENV}` の直接の展開を除外する。
シークレットは値ではなく参照で書き、解決の可否を環境ポリシーで制限する。

### 検討した代替案

| 案 | 利点 | 欠点 | 採らない理由 |
| --- | --- | --- | --- |
| テンプレートの展開と環境変数の展開を許す | 環境ごとの差分を一つのマニフェストで書ける | 読み込みの時点で外部の値が混ざり、計画からシークレットを伏せられることを保証しにくい | パストラバーサルと注入の余地が残る |

### 結果と再検討の条件

マニフェストは、ファイルの内容だけから計画が決まる。
その代わり、環境ごとの差分は、プロファイルごとのマニフェストと `include` で書き分ける。
環境ごとのマニフェストの重複が保守できない量になった場合に見直す。

| --- | --- |
| REQ-SEEDING-004 | [seed の計画と適用](../seed-run/README.md) |

## 進捗テーブルを使わず決定的な論理キーで冪等にする

### 背景

適用は複数の Context にまたがり、途中で失敗しうる。
Context をまたぐ一つのトランザクションは使えない。

### 決定

専用の進捗テーブルを設けない。
論理キーと ID をプロファイルと生成器の seed から決定的に導き、同じ要求の再実行は、未完了の分だけを適用する。

### 検討した代替案

| 案 | 利点 | 欠点 | 採らない理由 |
| --- | --- | --- | --- |
| 適用の進捗をテーブルに記録し、続きから再開する | どこまで進んだかを、データを読まずに知れる | 進捗と実際のデータの二つの正ができ、手動の変更でずれる | 投入の結果の正が 2 か所に生まれる |

### 結果と再検討の条件

部分的な失敗は、同じ要求の再実行だけで目的の状態へ収束する。
その代わり、計画のたびに現在の状態を読み直す。
合成データの件数が、計画のたびの読み直しでは現実的な時間に収まらない規模になった場合に見直す。

| REQ-SEEDING-006 | [seed の計画と適用](../seed-run/README.md) |

## この Context を Supporting に分類する

### 背景

ドメイン文書の索引は、各 Context を `Core`、`Supporting`、`Generic` のいずれかに分類する。

### 決定

Seeding を `Supporting` に分類する。
設計の投資先は投入の表現力ではなく、計画と適用の安全性に限る。

### 検討した代替案

| 案 | 利点 | 欠点 | 採らない理由 |
| --- | --- | --- | --- |
| `Generic` | 汎用のデータ投入の仕組みとして扱える | 環境ポリシーとプロファイルは、この製品の運用に固有である | 既製の投入の仕組みでは、環境ごとの安全性の検証を表せない |

### 結果と再検討の条件

環境ごとの投入は運用に固有だが差別化はせず、記録の正も管理しない。
初期データの構成を、利用者が製品の機能として編集するようになった場合に見直す。

### 関連する要件

この判断は分類であり、特定の要件を正当化しない。

## Aggregate を定義せず投入の結果を保存しない

### 背景

`SeedManifest` と `SeedPlan` は、1 回の実行の中でしか使わない。

### 決定

この Context では Aggregate を定義せず、状態を保存しない。

### 検討した代替案

| 案 | 利点 | 欠点 | 採らない理由 |
| --- | --- | --- | --- |
| 投入した結果をこの Context に保存する | 何を投入したかを、各 Context を読まずに知れる | 各 Context の記録と二重になる | 投入の結果の正が 2 か所に生まれる |

### 結果と再検討の条件

投入した業務データの記録の正は、各 Context に残る。
その代わり、何を投入したかは、計画を作り直して確かめる。
投入の履歴の監査が求められた場合に見直す。

### 関連する要件

この判断はモデルの構成であり、特定の要件を正当化しない。
