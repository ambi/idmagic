# Audit の設計判断

- 監査イベントの参照とエクスポートは `AdminAuditEventsRead` 権限 (AuthZEN action `admin:audit_events_read`) を要し、`admin` または `system_admin` ロールを持つ、有効かつ認証済みのユーザーだけが行える。書き込み経路は公開せず、イベントの追加は各 Context の発行経路だけが行う。API アクセストークンでは、ロールに加えて `audit:read` を要求する。対になる変更系のスコープは存在しない。書き込み経路そのものを公開しないためである。
- 問い合わせの範囲は入力ではなく経路が決める。テナント管理経路は呼び出し元のテナントへ固定し、全テナント横断の参照とエクスポートは制御面主体だけが到達できる専用のシステム経路に置く。範囲を切り替えるクエリを持たせないのは、テナント管理経路に横断能力が残っていると、経路を見ただけでは認可の範囲が分からなくなるからである。
- 検索フォームの選択肢を返す経路はシステム経路の双子を作らず 1 本で共有する。返すのは検索軸の語彙だけで、どのテナントの記録も含まないため、経路が範囲を表すという上の規則の対象にならない。
- カーソルは絞り込みの指紋に範囲の識別子を混ぜる。制御面主体はテナント管理経路でも所属テナントが制御面テナントであり、範囲を混ぜなければ両経路の指紋が一致して、テナント内で発行したカーソルが横断検索の続きとして読めてしまう。
- 監査レコードは GDPR 第 30 条 (処理活動の記録) を根拠に、追記のみで 7 年間保持する。削除やアーカイブのインターフェースは提供しない。これは SLO ではなく運用上の固定値なので、規範的シナリオではなくここに置く。
- この Context を `Supporting` に分類する。監査は必須だが、Read Model と検索属性の登録簿という形は他の製品と変わらない。差別化するのは記録される事実の側であり、それを持つのは事実を発生させる各 Context である。
