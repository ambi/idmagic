# 監査イベントの検索

## 概要

この文書は、管理者が監査イベントを検索、取得、エクスポートする仕様である。

| 項目 | 内容 |
| --- | --- |
| 責務 | 期間、種類、検索属性による絞り込み、ページ単位の閲覧、1 件の取得、エクスポート、検索の選択肢の提示 |
| 行為者 | テナント管理者（テナント管理の経路）、System 管理者（システムの経路） |
| 扱わないもの | 監査イベントの発行は各 Context が、記録の保持期間はデータのライフサイクルが扱う |

## モデル

検索の文法は、検索属性の登録簿（`AuditEventSearchRegistry`）が宣言する属性、演算子、変換の閉じた集合に限る。
任意の SQL や JSONPath は受け付けない。

| 演算子 | 意味 |
| --- | --- |
| `eq` | 完全一致。値は 1 個 |
| `in` | 値の集合のいずれかに一致 |
| `contains` | 生の文字列の部分一致。値は 1 個 |
| `time_range` | 発生時刻の期間。値は開始と終了の 2 個 |

フィルターの各式は論理積で結ぶ。
多値の属性は、いずれかの値が一致すればそのイベントが返る。
検索軸を持たないイベントは、その軸のどの値にも一致しない。

- **判断**：閉じた文法にする理由は、[検索の文法を登録簿の閉じた集合に限る](../design/decisions.md#検索の文法を登録簿の閉じた集合に限る)。

## 操作

### テナント管理者による監査イベントの検索

#### REQ-AUDIT-001 管理者は監査ログを期間で絞り込み参照・エクスポートできる

- 管理者が監査イベントを検索したとき、Audit は、呼び出し元のテナントの監査イベントのうち、`after` 以後、`before` 以前、`type`、`category`、`user_id`、`username`、`q`、`filter` のすべてに一致するものを、発生時刻の降順で返す。
- 管理者が監査イベントをエクスポートしたとき、Audit は、検索と同じ絞り込みに一致するイベントを最大 10,000 件、`Content-Disposition: attachment` の JSON で返す。
- 管理者がイベントの ID を指定して監査イベントを取得したとき、Audit は、呼び出し元のテナントのイベントを 200 で返す。
- 管理者が検索の選択肢を要求したとき、Audit は、`category` で絞り込める種類の和集合を昇順に並べた種類、結果、行為者の種類、委譲のモードの一覧を返し、どのテナントの記録も返さない。
- テナントのどの User にも解決しない `username` を指定された場合、Audit は、0 件の結果を返し、`username` の絞り込みを無視しない。
- 存在しない ID か、別のテナントのイベントの ID を指定された場合、Audit は、404 と `event_not_found` で拒否し、イベントの存在を示さない。
- RFC 3339 でない `after` か `before`、未知の `category`、負の数か整数でない `limit` を指定された場合、Audit は、400 と `invalid_request` で拒否する。
- `field:operator:value` の形でないか、登録簿にない属性か、その属性に許していない演算子の `filter` を指定された場合、Audit は、400 と `invalid_request` で拒否し、問い合わせを実行しない。
- `admin` または `system_admin` のロールを持たない利用者が検索、取得、エクスポート、選択肢を要求した場合、Audit は、403 と `access_denied` で拒否する。
- API アクセストークンで要求された場合、Audit は、ロールに加えて `audit:read` のスコープを求め、持たないトークンを 403 と `insufficient_scope` で拒否する。
- **例**：EX-AUDIT-001-01

#### REQ-AUDIT-002 worker プロセスが発行した業務イベントも管理者は監査ログで参照できる

- `idmagic-worker` のプロセスがドメインイベントを発行したとき、Audit は、`idmagic-api` のプロセスが発行したイベントと同じく監査イベントとして記録し、検索、取得、エクスポートの結果に含める。
- **例**：EX-AUDIT-002-01

#### REQ-AUDIT-003 管理者は workflow_id と run_id で LifecycleWorkflow の監査イベントを検索できる

- 管理者が `filter` に `workflow.id` または `workflow_run.id` を指定して検索したとき、Audit は、そのワークフローまたは実行に紐づく監査イベントだけを返す。
- LifecycleWorkflow の監査イベントを返すとき、Audit は、User の属性値とメールの本文を含めない。
- **例**：EX-AUDIT-003-01

#### REQ-AUDIT-004 管理者は監査ログをページ単位で閲覧でき、絞り込みを変えるとカーソルが無効になる

- 管理者が監査イベントを検索したとき、Audit は、`limit`（デフォルト 100 件、最大 999 件）の件数のページと、絞り込みに一致する正確な総件数、総ページ数、現在のページ、ページサイズを返す。
- 管理者が監査イベントを検索したとき、Audit は、`first`、`prev`、`next`、`last` のカーソルを `Link` ヘッダーで返す。
- 管理者がカーソルで次または前のページを取得したとき、Audit は、直前のページと重複も欠落もなく、発生時刻の降順のイベントを返す。
- 管理者が `last` のカーソルで最後のページを取得したとき、Audit は、端数のイベントを含む最後のページを返す。
- 絞り込みに一致するイベントがない場合、Audit は、空の一覧と、総件数、総ページ数、現在のページの `0 / 0 / 0` を返し、`Link` を一つも返さない。
- 正確な件数を取得できない場合、Audit は、0 件として成功させず、要求全体をサーバーエラーで失敗させる。
- `cursor` と `limit` 以外の絞り込みを変えて、元の絞り込みで発行したカーソルを送られた場合、Audit は、400 と `invalid_request` で拒否する。
- 別のテナントか別の経路で発行したカーソル、改ざんしたカーソル、有効期限を過ぎた旧方式のカーソルを送られた場合、Audit は、400 と `invalid_request` で拒否する。
- **例**：EX-AUDIT-004-01、EX-AUDIT-004-02、EX-AUDIT-004-03、EX-AUDIT-004-04、EX-AUDIT-004-05、EX-AUDIT-004-06

#### REQ-AUDIT-005 管理者はエージェントが代行した操作を本人の操作と区別して検索できる

- Agent が委任トークンで操作したとき、Audit は、行為者の種類 `agent`、エージェントの識別子、委譲の深さ、委譲のモードを検索属性として記録し、行為者の識別子を代行した側の識別子のまま残す。
- 管理者が Agent を登録または無効化したとき、Audit は、行為者を管理者として記録し、Agent をエージェントの識別子としてだけ記録する。
- 管理者が `actor.type`、`agent.id`、`actor.id` で絞り込んだとき、Audit は、行為者がその値に一致するイベントだけを返し、本人の操作と Agent が代行した操作を混ぜない。
- 管理者が検索属性で絞り込んだとき、Audit は、その属性を持たないイベントを、どの値にも一致させない。
- **例**：EX-AUDIT-005-01、EX-AUDIT-005-02、EX-AUDIT-005-03、EX-AUDIT-005-04

#### REQ-AUDIT-006 管理者は委譲チェーンの参加者から代行の連なりを横断検索できる

- Token Exchange で委譲したトークンで操作したとき、Audit は、委譲チェーンのすべての参加者の識別子を検索属性として記録し、ユーザー名を記録しない。
- 管理者が `delegation.actor` で絞り込んだとき、Audit は、その参加者がチェーンのどの位置にいるイベントも返す。
- 管理者が `delegation.mode` で絞り込んだとき、Audit は、同じ交換について REQ-OAUTH2-049 がイントロスペクションへ返すモードの値で照合する。
- **例**：EX-AUDIT-006-01

### 制御面主体によるシステム経路の検索

#### REQ-AUDIT-007 制御面主体はシステム経路で全テナントの監査ログを検索・エクスポートできる

- 制御面主体がシステムの経路で監査イベントを検索またはエクスポートしたとき、Audit は、テナント管理の経路と同じ絞り込みとページの規則で、すべてのテナントの監査イベントを発生時刻の降順で返す。
- 制御面主体がシステムの経路でイベントの ID を指定して取得したとき、Audit は、どのテナントのイベントも返す。
- 制御面主体がシステムの経路で検索したとき、Audit は、`admin` ロールを併せ持つかどうかで結果を変えない。
- `system_admin` を持たないか、制御面テナントに所属しないか、制御面テナント以外の経路でシステムの経路を要求された場合、Audit は、403 と `access_denied` で拒否し、どのテナントの監査イベントも返さない。
- テナント管理の経路で発行したカーソルをシステムの経路へ送られた場合、Audit は、400 と `invalid_request` で拒否し、続きとして読み替えない。
- **例**：EX-AUDIT-007-01、EX-AUDIT-007-02、EX-AUDIT-007-03

## セキュリティ上の考慮

監査イベントの参照とエクスポートは、`AdminAuditEventsRead` の権限（AuthZEN の action `admin:audit_events_read`）を要し、`admin` または `system_admin` のロールを持つ、有効かつ認証済みのユーザーだけが行える。
API アクセストークンでは、ロールに加えて `audit:read` を要求する。
対になる変更のスコープは存在しない。書き込みの経路そのものを公開しないためである。

問い合わせの範囲は、入力ではなく経路が決める。
テナント管理の経路は呼び出し元のテナントへ固定し、全テナントを横断する参照とエクスポートは、制御面主体だけが到達できる専用のシステムの経路に置く。
範囲を切り替えるクエリを持たせないのは、テナント管理の経路に横断の能力が残っていると、経路を見ただけでは認可の範囲が分からなくなるからである。

検索の選択肢を返す経路は、システムの経路に双子を作らず、1 本で共有する。
返すのは検索軸の語彙だけで、どのテナントの記録も含まないため、経路が範囲を表すという規則の対象にならない。

カーソルは、絞り込みの指紋に範囲の識別子を混ぜる。
制御面主体はテナント管理の経路でも所属テナントが制御面テナントであり、範囲を混ぜなければ両経路の指紋が一致して、テナントの中で発行したカーソルが横断の検索の続きとして読めてしまう。
