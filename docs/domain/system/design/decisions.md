# System の重要な設計判断

この文書は、System の設計判断のうち、代替案を比べたものと、見直す条件が要るものを扱う。
一つの要件やモデルだけを正当化する判断は、機能仕様のその要件またはモデルの判断の欄に置く。

## 管理コンソールとアカウントポータルを BFF ではなく SPA の OIDC RP にする

### 背景

管理コンソールとアカウントポータルは、IdP 自身の API を呼ぶブラウザーのアプリケーションである。
IdP は、認可とトークンの発行の経路をすでに実装している。

### 決定

管理コンソールとアカウントポータルは、BFF の背後に置かず、ファーストパーティーの OIDC RP として扱う。
純粋な SPA の RP としてアクセストークンをブラウザーに保持することを受け入れ、短命なトークンと `no-store` で影響範囲を限る。
ファーストパーティーのセッションのログインを、緊急の経路として残す。

### 検討した代替案

| 案 | 利点 | 欠点 | 採らない理由 |
| --- | --- | --- | --- |
| BFF を挟み、トークンをサーバーの側に保持する | ブラウザーのスクリプトからトークンへ到達できない | 管理画面のためだけに、IdP の認可とトークンの発行の経路を二重化する。セッションの状態を持つ層が増える | IdP の可用性と復旧の経路が複雑になる |

### 結果と再検討の条件

スクリプトの実行が成り立てば、ブラウザーに保持したアクセストークンは持ち出されうる（[脅威モデル](../../../design/security/threat-model.md)の THREAT-004）。
600 秒の有効期間、`no-store`、URL とログと DOM にトークンを置かないことで、露出の窓を狭める。
OIDC のクライアントや鍵の設定を壊したときにも、緊急の経路で直せる。
ブラウザーに保持したトークンの露出が受容できない運用の要件が出た場合に見直す。

### 関連する要件

| 要件 | 機能仕様 |
| --- | --- |
| REQ-SYSTEM-015 | [ホステッド UI とポータル](../hosted-ui/README.md) |

## テナント横断の操作の入口を一つにする

### 背景

制御面主体は、テナントの境界を越えて監査ログ、ジョブ、署名鍵の状態などを扱う。
`system_admin` の操作者は、テナント管理の経路も使う。

### 決定

テナントの境界を越える操作は、システムコンソール（`/system`）と、制御面主体の専用のシステム API だけに置く。
テナント管理コンソール（`/admin`）とテナント管理 API は、操作者が `system_admin` であっても要求先のテナントへ閉じる。
範囲は操作者のロールからも画面の切り替えからも決めず、どの経路を呼んだかだけで決まる。

画面だけを分けても足りない。
テナント管理 API に横断の能力が残っていれば、画面を経由しない直接の呼び出しでテナント管理の側から横断できるので、経路は認可の範囲を表さない。
したがって分けるのは画面と経路の両方であり、テナント管理の経路からは横断を求める入力そのものを消す。

どの操作が横断かは、この文書も含め、どの散文にも一覧しない。
経路と操作の記号が TypeSpec にあり、テナントの側とシステムの側は別の操作の記号として定義される。
散文に一覧を写すと、操作を足したときに写しだけが古くなる。

### 検討した代替案

| 案 | 利点 | 欠点 | 採らない理由 |
| --- | --- | --- | --- |
| テナント管理コンソールに横断の切り替えを残し、システムコンソールにも同じ画面を置く | 運用者が慣れた画面のまま横断できる | 入口が二つ残る | この判断が成り立たない |
| 画面だけを分け、両方から同じ API を呼ぶ | API を二組にせずに済む | 直接の呼び出しで横断できる | 経路が認可を表さない |
| システムコンソールを廃止し、テナント管理コンソールのロールの分岐へ統合する | コンソールが一つで済む | 横断の能力が各画面の条件分岐へ散らばる | 制御面にいることを、シェルと経路で確かめられなくなる |
| 一覧だけを移し、エクスポート、詳細の参照、取り消しをテナントの側へ残す | 移す範囲が小さい | 一覧で見つけた対象を操作するために、コンソールを往復することになる | 一つの作業の途中で経路を行き来する |

### 結果と再検討の条件

範囲を経路で固定すると、再読み込み、ページング、絞り込みの変更のたびに、操作者のロールから表示範囲を推定し直す必要がなくなる。
運用者の側から見ても、いま制御面にいるかどうかはシェルと URL で分かり、画面の中のチェックボックスを読む必要がない。
この判断は、制御面の操作へ到達できる資格情報の種類を決めるものではない。それは[認可設計](../../../design/security/authorization.md)で定める。

次のいずれかで見直す。

- テナントの境界を越えない操作を、システムコンソールへ置く要件が生じたとき。
- 制御面の操作を担う主体が、`system_admin` のロール以外の資格で識別されるようになったとき。
- 管理コンソールを制御面と別のホストへ移し、経路ではなくオリジンが範囲を表すようになったとき。

## 専用のイベントの基盤を持たない

### 背景

各モジュールはドメインイベントを発行し、監査の記録とアカウントのセキュリティ通知がそれを消費する。

### 決定

ドメインイベントの配信に、メッセージブローカー、イベントストア、ストリーム処理の基盤のいずれも採らない。
配信はこのモジュールが組み立てる一つの閉包が担い、発行元と同じプロセス、同じ goroutine で完了する。

### 検討した代替案

| 案 | 利点 | 欠点 | 採らない理由 |
| --- | --- | --- | --- |
| メッセージブローカーやイベントストアを置く | プロセスの外の消費者へ配送でき、失われない配送を作れる | 運用するデータストアが一つ増える。監査の記録の成立が、第二のシステムの可用性に依存する | 公開イベントの消費者は監査の記録とセキュリティ通知の二つだけで、どちらも同じプロセスに同居している |
| 専用の配信の基盤を先に用意して、将来の消費者に備える | 消費者が増えたときにすぐ使える | 費用だけが先に出る | 現在の消費者はワイヤ表現の上だけで動き、発行元の Go の型を知らないので、消費者を増やすこと自体は基盤なしでもできる |

### 結果と再検討の条件

プロセスを越えない配送のために、運用するデータストアを増やさない。
これは Jobs モジュールが永続キューを PostgreSQL に置いた[判断](../../jobs/design/decisions.md)と同じ理由である。
この判断は、状態の変更とイベントの発行が原子的でないことに答えるものではない。現在の保証と、保証されていない経路は[ランタイムアーキテクチャ](../../../design/architecture/runtime.md#通信)に書く。

次のいずれかで見直す。

- イベントの消費者が、このプロセスの外に現れたとき。
- イベントが失われないことを保証する必要が生じ、それが発行の意図を耐久的に残すことでしか達成できないと判明したとき。
- 一つのイベントの種類に対する消費者が増え、配線を一か所の並びとして読めなくなったとき。

### 関連する要件

この判断は基盤の選択であり、特定の要件を正当化しない。

## 優先度クラスで低い要求から拒否する

### 背景

キャパシティが足りないとき、何を先に捨てるかを決めなければならない。
IdP では、ログインとトークンの処理が止まることの影響が最も大きい。

### 決定

キャパシティが足りないとき何を先に捨てるかを、API のプロセス自身が決める。
要求を経路の登録と同じ場所で `interactive_auth`、`management`、`management_bulk`、`infrastructure` の四つの優先度クラスに分類し、クラスごとの同時実行の入場の上限を超えた要求を 503 で拒否する。
順序は[キャパシティ設計](../../../design/performance/capacity.md#ロードシェディング順序)のロードシェディングの順序が定め、機構は[アドミッションコントロールの設計](../admission-control/design.md)で説明する。

どの経路がどのクラスに属するかは、この文書も含め、どの散文にも書かない。
分類はコードに一か所あり、そこから `ROUTE_PRIORITY.md` を生成する。
散文に一覧を写すと、経路を足したときに写しだけが古くなり、しかもその食い違いは負荷が高いときにしか現れない。

| 選択 | 理由 |
| --- | --- |
| 飽和の判定にプロセスの中の実行中の要求の数を使う | 要求 1 件が高々 1 本のデータベースの接続を同時に握るので、この数がそのまま接続の競合の深さになり、レプリカの数を知らずに意味を持つ。レプリカが増えれば 1 プロセスあたりの実行中の数が下がり、どのプロセスも縮退しなくなるのは、判定のずれではなく正しい結果である |
| 拒否を 429 ではなく 503 で返す | 429 は濫用を抑えるエンドポイントごとの流量の制限に割り当てられている。目的の違う二つの機構が同じ状態コードを返すと、呼び出し側も指標も区別できない |
| ステージ 5 の拒否を `SLO-PRIMARY-ERRORS` の失敗として数える | 認証を受け付けられなかったことは失敗であり、数え方を変えて目標を守ることは[品質要求](../../../requirements/quality.md#証拠の区分)が禁じる、仕様の目標の暗黙の引き下げにあたる |
| クラスごとの接続の予算を、接続プールを分けずに入場の側で配分する | プールを分けると論理的な接続の予算がクラスの数だけ増え、空いているクラスの枠を上位のクラスへ融通できなくなる |
| 中間のクラスを `management_write` ではなく `management` と呼ぶ | 分類は経路の全量を覆う必要があり、管理 API とポータル API の読み取りは、書き込みでも一括の処理でもない。ステージ 4 が定めるのは「既存のセッションの認証とトークンの処理に不要」という性質であり、管理の読み取りにも当てはまる |
| `infrastructure` を分類の外に置かず四つ目のクラスにする | 受付可否のプローブを拒否すると、飽和した全レプリカが同時に負荷分散の対象から外れ、部分的な縮退が完全な停止になる。この経路を拒否しないことは、分類し忘れた結果ではなく、分類した結果でなければならない |

### 検討した代替案

| 案 | 利点 | 欠点 | 採らない理由 |
| --- | --- | --- | --- |
| 自動の水平スケールだけを入れる | 総キャパシティを増やせる | 判定の間隔と Pod の起動の間、ログインは管理と同じ待ち行列に並ぶ。束縛の条件がデータベースの側にあるときは、レプリカを増やすことが接続の競合を悪化させる | 飽和の間にログインを守れない |
| エンドポイントごとの流量の制限の閾値を下げる | 既存の仕組みで済む | 抑えたいのは正当な管理の操作の影響であって、それを拒否したいわけではない | 濫用の抑止にしか効かない |
| 分類を起動時設定に置く | 配置ごとに分類を変えられる | 経路と分類の対応が配置ごとに変わりうる。`interactive_auth` に入れるべき経路が `management_bulk` に入っているという最も重い誤りが、負荷の高いときにしか現れなくなる | 分類をコードに置けば、経路の全量に対する網羅性を検査できる |

### 結果と再検討の条件

飽和しても、ログインとトークンの処理は管理の操作より後まで受け付けられる。
次のいずれかで見直す。

- 飽和の判定に実行中の要求の数では足りないと、実測で示されたとき。
- アドミッションコントロールを入れてなお、混合の負荷で認証のサービスの目標を満たせないとき。これは[API のプレーンを分けない](#api-のプレーンを分けない)の再検討の条件 (a) でもある。
- 閾値のデフォルトの値が平常時に発動し、運用者が機構を無効にして運用する状態が生じたとき。

## API のプレーンを分けない

### 背景

認証とプロトコル、ポータル（`/api/account/v1`）、管理（`/api/admin/v1`）、SCIM（`/scim/v2`）、Shared Signals の受信（`/ssf`）は、負荷と要求の性質が違う。
分けうるものは、デプロイ、プロセスが登録する経路の選択、公開の入口、リリースの成果物の四つである。

### 決定

これらを一つの API の Deployment で提供し、四つのいずれも種別ごとに分けない。

分割にしか得られない利得はあるが、それを必要とする条件がまだ示されていない一方で、費用は分割した瞬間から常に発生する。
プロセスの資源と停止の隔離、種別ごとに違うレプリカの数、片方だけの更新はデプロイを分けなければ得られず、アドミッションコントロールでも自動スケールでも代わりにならない。
しかし、それらを必要とする管理、ポータル、SCIM、Shared Signals のキャパシティも、認証への障害の波及も、独立した更新の要求も、まだ実測で示されていない。
対して、追加するプレーンは、自分の可用性の下限のレプリカの数、PodDisruptionBudget、キャパシティのモデル、監視、障害対応の手順を一組ずつ持ち、「分離した側の過小なサイズ」という、現在は存在しない障害の形を加える。
IdP でこれが起きると、障害対応のために管理 API を使いたい局面で管理が落ちているという組み合わせになりうる。
到達範囲を狭める分離とリリースの成果物の分離も、それを求める脅威モデルの上の要件と、独立したデータの所有権、担当のチーム、SLO が現在ないので採らない。

分離に固有の常時の増分は、総需要から生じない。
総需要はどちらの構成でも同じで、増分は各プレーンの可用性の下限、`ceil` の重複、種別の間で余裕を融通できないことの三つから生じる。
その下限は[キャパシティ設計](../../../design/performance/capacity.md#サイジング計算式)が算出する。

### 検討した代替案

| 案 | 利点 | 欠点 | 採らない理由 |
| --- | --- | --- | --- |
| 見積もりがないことを利得の不在の証拠として、恒久的に分けないと決める | 判断が単純になる | 判断の材料の欠如から、利得の不在は導けない | 根拠のない恒久の決定になる |
| 見積もりをせずに分ける | 分離の利得をすぐ得る | 分離の側の規模を知らないまま、常時の費用を確定させる | 費用の根拠がない |
| 判断せず、問いを開いたままにする | 後で決められる | 単一のプロセスが判断なのか偶然なのかを読み取れない | 現在の構成の意図が残らない |

「将来分ける確率が高いなら、今のうちに分けたほうが安い」も理由にしない。
理由になるのは後からでは高くつく場合だけであり、確率が高いことは、それ自体では今実施する根拠にならない。

### 結果と再検討の条件

この判断は、キャパシティが足りないときに何を先に捨てるかを決めるものではない。
分離は総キャパシティが足りている状況で種別ごとに資源を固定的に分け、アドミッションコントロールは総キャパシティが足りない状況で何を拒否するかを決める。
効く状況が違うので、両者は代替ではない。
縮退の順序は[キャパシティ設計](../../../design/performance/capacity.md#ロードシェディング順序)で定める。

この判断は、一括の処理の一部が `idmagic-worker` にあること、アドミッションコントロールと自動スケールが未実装であること、[キャパシティ設計](../../../design/performance/capacity.md#想定ワークロード)の想定のワークロードが現在の規模であること、ブラウザーから見える境界が同一のオリジンであることに依存する。
経路の接頭辞と種別の対応には機械的な検査がなく、ゲートウェイの許可リストと実行時の経路表は現に一致していないので、分離の費用が低いままである保証もない。

デプロイを分けることは、次のいずれかで見直す。

- (a) 管理、ポータル、SCIM、Shared Signals のいずれかを含む混合の負荷で、認証のサービスの目標を満たせず、その種別へ上限を設ける、処理をワーカーへ移す、アドミッションコントロールを入れる対処だけでは要求を満たせないとき。
- (b) 分離によって 1 レプリカあたりの持続の処理能力が混合のときより上がり、その改善が可用性の下限と切り上げの重複を上回るとき。
- (c) 片方だけの更新または再起動を必要とした記録が生じ、長期間の版の差を許す運用の要件が決まったとき。

経路の登録の選択と公開の入口の分離は、公開の側のプロセスから特定の種別のハンドラーを除く要件、または特定の種別を一般の利用者向けの公開の入口から到達不能にする要件が、脅威モデルに記載されたときに見直す。
リリースの成果物の分離は、独立したデータの所有権、担当のチーム、SLO、リリースの成果物のいずれもが必要になったときに見直す。

### 関連する要件

この判断は配置であり、特定の要件を正当化しない。
