# アーキテクチャ上の判断

## Modular Monolith の採用

- 判断：単一の Go モジュール内に Bounded Context を置き、API、ワーカー、バッチで同じ実装を共有する。
- 理由：現在のデータ所有、担当、SLO は Context ごとの独立配備を要求せず、プロセス分割による通信と運用の費用が上回る。
- 見直し条件：独立したデータ所有、担当チーム、配備周期、SLO のいずれかが必要になった Context が現れる。

## 共有状態としての PostgreSQL

- 判断：永続状態とレプリカ間で共有すべき短命状態を PostgreSQL に集約する。
- 理由：ログイン制限、認可コード、再送防止などの正しさをレプリカ数から独立させ、二つ目のステートフル基盤を運用しないためである。
- 見直し条件：容量測定が PostgreSQL を律速点と示し、同じ整合性を保つ別の所有境界が必要になる。

## ブラウザーの同一オリジン境界

- 判断：ブラウザー向け UI と API はゲートウェイで同一オリジンにする。
- 理由：Cookie のスコープと `Origin` の検証がこの境界に依存する。
- 見直し条件：ブラウザーの認証と CSRF 防御を別の検証可能な機構へ移す。
