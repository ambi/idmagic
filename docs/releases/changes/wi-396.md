# WI-396: Shed load by request priority class when the API process saturates

作業項目は `wi-396-prioritize-login-under-saturation` である。

WI-396 は、API プロセスが飽和したときに何を先に捨てるかを、プロセス自身が決めるようにする。

登録済みのすべての経路を `interactive_auth`、`management`、`management_bulk`、`infrastructure` の 4 つの優先度クラスに分類し、クラスごとの同時実行の入場上限を超えた要求を、`Retry-After` と `urn:idmagic:error:service_overloaded` の Problem Details を伴う 503 で拒否する。

拒否はルーティングの後、ハンドラーの手前で起きるので、拒否された要求は永続状態もドメインイベントも変えない。

対話的な認証とトークン処理の経路は最後まで受け付ける。生存確認、受付可否、起動完了、メトリクスの経路は拒否しない。

閾値は `ADMISSION_CONTROL_ENABLED`、`ADMISSION_MAX_CONCURRENT_REQUESTS`、`ADMISSION_MANAGEMENT_MAX_CONCURRENT_REQUESTS`、`ADMISSION_MANAGEMENT_BULK_MAX_CONCURRENT_REQUESTS` で調整でき、縮退の順序を逆にする組み合わせは起動時に拒否される。

縮退の発動は `http_admission_decisions_total` と `http_admission_in_flight_requests` で観測でき、`ApiAdmissionSheddingInteractiveAuth`、`ApiAdmissionShedding`、`ApiAdmissionUnclassifiedRoute` のアラートと [入場制御が発動したとき](../../runbooks/admission-control.md) の手順が付く。

あわせて API の Deployment に HorizontalPodAutoscaler を入れ、固定レプリカ数をやめた。

**この変更は高可用性ではない。** PostgreSQL は依然として論理的に単一の正であり、共通の障害域は解消しない。

規範上の振る舞いは [REQ-SYSTEM-018](../../contexts/system/scenarios.feature.md#rule-req-system-018-飽和した-api-プロセスは優先度の低い要求から拒否する)、閾値の検証は [REQ-SYSTEM-016](../../contexts/system/scenarios.feature.md#rule-req-system-016-起動時設定の検証に失敗するとプロセスは部分起動せず集約エラーで停止する) が定める。
