# WI-532: FAPI 2.0 プロファイルの選択が実際に制約を課す

作業項目は `wi-532-fapi-security-profile-selection-applies-no-constraint` である。

WI-532 は、`fapi_profile` に `fapi_2_security_profile` を選んだクライアントへ FAPI 2.0 Security Profile の追加制約を実際に適用する。これまでこの値は保存され、管理 API と `/register` の応答に載り、管理画面にも表示されたが、値を読んで制約を掛ける箇所が 1 つも無かった。プロファイルを選んだクライアントは、PAR を経由しない認可リクエストを送り、共有シークレットで認証し、送信者制約の無いアクセストークンを受け取れた。プロファイルの選択は事実上、表示専用のラベルだった。

選択したクライアントには次の 3 つが課される。認可リクエストは PAR 経由に限られ、`request_uri` を伴わない `/authorize` は `invalid_request` で拒否される。クライアント認証は `private_key_jwt` と `tls_client_auth` に限られ、共有シークレットや `none` を宣言したクライアントは登録も更新もできない。アクセストークンは DPoP 証明か mTLS クライアント証明書による送信者制約を必要とし、どちらの証拠も無い `/token` の要求は拒否される。

**プロファイルを選んでいないクライアントの動作は変わらない。** 3 つの制約はいずれも `fapi_profile` の選択からのみ導かれ、既定にはならない。クライアント個別の `require_pushed_authorization_requests` はこれまでどおりプロファイルと独立に効く。

既にプロファイルを選んでいるクライアントを運用している場合は、設定の見直しが要る。共有シークレットで認証しているクライアントは、`private_key_jwt` の鍵を登録するか `tls_client_auth` へ移すまで更新が通らない。認可リクエストを PAR 経由へ、トークン要求を DPoP 付きへ変えるのはクライアント側の実装である。制約を受けたくない場合は `fapi_profile` を `none` へ戻す。

あわせて、`/register` が `private_key_jwt` のクライアントを 1 件も登録できなかった欠陥を直した。登録前の検証に使う候補が必須項目を欠いていたため、鍵が正しくそろっていても `invalid_client_metadata`（`private_key_jwt requires non-empty inline jwks`）で拒否されていた。鍵を伴わない要求が同じ理由で拒否される点は変わらない。

規範上の条件は `docs/contexts/oauth2/standards.md` の `FAPI2-PROFILE-SELECTION`、`FAPI2-PAR-PKCE`、`FAPI2-CLIENT-AUTH`、`FAPI2-SENDER-CONSTRAINT` が定める。
