# 監査エクスポートを非同期 API へ移行する

## デプロイ

スキーマを適用して `audit_export_artifacts` と `audit_export_chunks` を作り、同じリリースの API、Worker、Batch をデプロイする。
`bulk` レーンの Worker と `retention-sweep` の定期実行が必要である。
生成には一時ディスクも使用し、並行ジョブ数と `AUDIT_EXPORT_MAX_BYTES` の積を目安に空きを確保する。
デフォルトと設定の意味は[監査エクスポート](../../modules/audit/features/event-export.md)が定める。

## API の呼び替え

テナント内は `/api/admin/v1/audit-events`、横断は `/api/admin/v1/system/audit-events` を基底とする。
実際の URL には利用するテナントの `/realms/{realm}` を付ける。

1. 従来の `GET {基底}/export` を `POST {基底}/exports` へ変更する。絞り込みは同じクエリパラメーターで渡す。ページ位置とページ件数はエクスポート範囲を制限しない。
2. 202 応答の `id` を使い、`GET {基底}/exports/{id}` で状態を取得する。
3. `status=succeeded` かつ `downloadable=true` のとき、`GET {基底}/exports/{id}/download` から JSON を取得する。
4. 未完了の要求は `POST {基底}/exports/{id}/cancel` で取り消せる。

各操作に現在の権限と同じ要求者が必要である。
ブラウザーの作成と取消しには通常の CSRF 検証を適用する。
API アクセストークンには `audit:read` を要求する。
失敗理由が `event_limit_exceeded` または `byte_limit_exceeded` の場合は、日時などの条件を絞って再要求する。
期限切れの場合も新しく要求する。

## 同期経路の移行期間

同期経路は `Deprecation: @1792886400` と `Sunset: Mon, 25 Oct 2027 00:00:00 GMT` を返す。
削除は Sunset と初回公開から 12 か月の両方を満たした後に別の変更で行う。
互換経路は最大 10,000 件、16 MiB、プロセス全体で同時 2 件に制限される。
同時数超過は 429、バイト数超過は 422 となる。

## 後退

後退前に `audit_export` ジョブを完了または取消しへ進め、利用者を同期経路へ戻す。
旧 Worker は新しいジョブ種別を処理できない。
成果物表を残しても旧 API は参照せず、期限の掃引も行わないため、後退中の保存量を別途管理する。
