# WI-396: Hand API replica count to the autoscaler and review the shedding thresholds

作業項目は `wi-396-prioritize-login-under-saturation` である。

## 配備マニフェスト

WI-396 は `infra/k8s/base/hpa.yaml` に API の HorizontalPodAutoscaler を追加し、`infra/k8s/overlays/*/api.yaml` から `replicas` を取り除いた。

Deployment に `replicas` を残したオーバーレイを自前で持っている場合は取り除く。残すと、適用のたびにレプリカ数が固定値へ戻り、自動調整と綱引きになる。

下限は 3、上限は 30、判定は CPU 使用率 70% である。上限は [構成算出規則](../../design/performance/capacity.md#構成算出規則) の参照構成に由来し、レプリカ数はそのまま論理接続予算に乗るので、上げる前に PostgreSQL 側の利用可能接続数を確かめる。

Kubernetes 以外で配備している場合、この変更は何も要求しない。

## 入場制御の閾値

飽和時の入場制御は既定で有効である。既定の上限は同時実行 256 件（`interactive_auth`）、192 件（`management`）、128 件（`management_bulk`）で、[Admission control](../../contexts/system/internals.md#admission-control) が一覧を持つ。

**これらは Planning assumption であって実測値ではない。** 1 プロセスがこれより低い同時実行数で飽和する構成では、閾値を下げなければ縮退が間に合わない。逆に高い同時実行を捌ける構成では、平常時に拒否が出ないことを配備後に `http_admission_decisions_total` で確かめる。

`ADMISSION_MANAGEMENT_BULK_MAX_CONCURRENT_REQUESTS` ≤ `ADMISSION_MANAGEMENT_MAX_CONCURRENT_REQUESTS` ≤ `ADMISSION_MAX_CONCURRENT_REQUESTS` を満たさない設定はプロセスを起動させない。

## クライアントへの影響

飽和時に、管理 API、アカウントポータル API、SCIM、Shared Signals の受信、動的クライアント登録が 503 と `Retry-After` を返しうるようになった。これらを呼ぶ自動化は、503 を恒久的な失敗として扱わず `Retry-After` の秒数だけ待って再送する。

拒否された要求はハンドラーへ到達しないので、部分的に適用された状態は残らない。再送は安全である。

保存済みのデータ、スキーマ、認可の条件は変わらない。

後退すると入場制御と自動調整の両方が失われ、飽和時は先着順に戻る。`ADMISSION_CONTROL_ENABLED=false` は、配備を戻さずに入場制御だけを切る手段である。
