# WI-463: Remove stored system_admin outside the control plane

作業項目は `wi-463-reserve-system-admin-role-to-control-plane` である。

WI-463 は保存済みのロール文字列を変更せず、データ移行も行わない。

デプロイ後に変わるのは新しい書き込みだけで、制御面テナント外の `User` と `Group`、およびすべての `Agent` への `system_admin` の新規割当てが HTTP 422 `invalid_role` で拒否される。

## デプロイ前に確認する対象

| 対象 | 検出方法 | デプロイ後の扱い |
| --- | --- | --- |
| 制御面テナント外の `User` | `GET /api/admin/v1/users` を各テナントで実行し、`roles` に `system_admin` を含む `User` を集める | 値は残る。テナント横断の能力は WI-460 の時点で既に無い |
| 制御面テナント外の `Group` | `GET /api/admin/v1/groups` を各テナントで実行し、`roles` に `system_admin` を含む `Group` を集める | 値は残る。所属 `User` の有効ロールには現れ続ける |
| すべてのテナントの `Agent` | `GET /api/admin/v1/agents` を各テナントで実行し、`roles` に `system_admin` を含む `Agent` を集める | 値は残る |

## 手動での除去手順

除去は `roles` を明示的に指定する更新で行う。`roles` を省略した更新は既存値をそのまま保存するため、除去にはならない。

1. 対象の現在の `roles` から `system_admin` を除いた配列を作る。
2. `User` は `PATCH /api/admin/v1/users/{user_id}`、`Group` は `PATCH /api/admin/v1/groups/{group_id}`、`Agent` は `PATCH /api/admin/v1/agents/{agent_id}` へ、その配列を `roles` として送る。
3. 応答の `roles` に `system_admin` が無いことを確認する。

`User` と `Group` は CSV でも除去できる。`roles` 列から `system_admin` を除いた行を投入し、プレビューが対象行を `updated` と判定することを確認してから適用する。

## 既存の自動化への影響

通常テナントで `system_admin` をテナント固有のロール名として使っていた場合、その名前を新しく付与する自動化と CSV は 422 で失敗する。

既に保存されている対象への再送は通るため、無編集のエクスポートを適用する往復は影響を受けない。失敗するのは新しい対象へ同じ名前を広げる操作である。

該当する自動化では、テナント固有の用途に別のロール名を選ぶ。

## 後退

後退すると予約ロールの検査が消え、どのテナントの `User`、`Group`、`Agent` にも再び `system_admin` を保存できる。

保存済みデータは後退の前後で変わらないため、後退そのものにデータ上の手順は要らない。

許可と拒否の互換性境界、および拒否が何を変えないかは [REQ-IDMANAGEMENT-032](../../domain/identity-management/scenarios.feature.md#rule-req-idmanagement-032-system_admin-は制御面テナントの-user-と-group-にだけ割り当てられる) が定める。
