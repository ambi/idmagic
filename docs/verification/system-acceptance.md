# システム受入れ設計

受入れとは、要求を満たしたと判断してよいかを、システムの外から観測できる結果だけで決めることである。
判断の材料は、公開された入口へ実際に要求を送って返ってきた結果と、その後にシステムへ残った状態である。
内部の部品を直接呼んだ結果や、通ったテストの件数は材料にしない。

この文書は、システム境界でしか確かめられない受入れを扱う。
どの要求をどの証拠で確かめるかの全体は[検証設計](README.md#要求の群ごとの証拠)で、テストの水準と書き方は[テスト方針](../development/testing.md)で定める。

## 機能受入れ

次の領域について、利用者または連携先にとって意味のある結果に至る経路を代表として選び、実際の経路制御と依存の組み立てを通して確かめる。

| 領域 | 代表として選ぶ経路 |
| --- | --- |
| ログイン | 利用者が資格情報を提示し、セッションが成立するまで |
| トークン発行 | クライアントが認可を得て、アクセストークンを受け取るまで |
| 管理操作 | 管理者がテナントの設定または主体を変更し、変更が保存されるまで |
| 上流連携 | 外部の権威から取り込んだ情報が、主体の状態へ反映されるまで |
| 下流プロビジョニング | 主体の変更が、外部の受信者へ送信されるまで |
| 監査 | 上の各操作について、誰が何をしたかの記録が残るまで |

## 許可しないリクエストの確認対象

認証、認可、テナント境界、入力の規則が許さないリクエストは、操作を実行せずにエラーを返す。
認証を経ていないリクエスト、必要なスコープを持たないトークン、別テナントの資源を指す参照、規則に反する入力がこれにあたる。
依存先の障害や欠陥で操作を完了できなかった場合は、規則による判定を経ていないので、ここで扱うものではない。

確かめるのは、返したレスポンスと、その操作が成功していれば残ったはずのものが残っていないことである。
残ったはずのものとは、保存された状態、発行されたトークンやセッション、外部の受信者への送信である。
レスポンスだけを見る確認は、エラーを返しながら操作は実行してしまう誤りを見逃す。

監査記録は、残っていないことを確かめる対象に入れない。
許可しなかったリクエストを記録するかどうかは[監査](../domain/audit/README.md)が決める。

性能とキャパシティは、[品質要求](../requirements/quality.md)の `CAP-*` 条件と[キャパシティ設計](../design/performance/capacity.md)の運用プロファイルを使う。

## 可用性と復旧の試験

障害試験では、正常に動いている系へ意図的に障害を起こし、設計した対処が働くことを確かめる。
復元試験では、バックアップから戻し、復元後の確認一覧を満たすことを確かめる。
いずれも、実際に起きた障害への対応とは違い、起こす障害も確かめる範囲もあらかじめ決めておく。

対処そのものは[可用性設計](../design/reliability/availability.md)と[リカバリ設計](../design/reliability/recovery.md)で設計する。
この節が定めるのは、何を起こし、何を見て、何をもって合格とするかである。

| 起こす障害 | 観測対象 | 成功条件 | 実行環境 |
| --- | --- | --- | --- |
| `idmagic-api` の Pod の停止 | 残るレプリカの受け付け、振り分け先からの離脱、処理中リクエストの失敗数 | 停止した Pod が振り分け先から外れ、残るレプリカが受け付けを続け、失敗が停止した Pod の処理中リクエストにとどまる | 実環境が必要 |
| ワーカーの Pod の停止 | ジョブのリース期限と再取得、レーン別のキュー深度 | 期限切れのジョブを別のワーカーが取得し直し、他のレーンのキュー深度が伸びない | 実環境が必要 |
| ノードの喪失 | Pod の再配置、ゾーンをまたぐレプリカの残存 | 残るノードで受け付けを続け、再配置後に全レプリカが準備完了へ戻る | 実環境が必要 |
| PostgreSQL の primary の喪失 | `/readyz` の失敗、待機系への切り替え時間、切り替え後の受け付け再開 | 切り替え後に全 `idmagic-api` が準備完了へ戻り、切り替え前に確定した書き込みが失われない | 実環境が必要 |
| 外部の鍵管理サービスの停止 | 署名とアンラップの失敗、サーキットブレーカーの開閉、回復後の再開 | 失敗が鍵操作を要する経路にとどまり、回復後に人手を介さず再開する | 実環境が必要 |
| 上流の IdP と外部 HTTP 送信先の停止 | 外部連携のログイン、SCIM 送信、Shared Signals 送信の失敗と再試行 | 他の認証経路が影響を受けず、回復後に再試行が送信を完了させる | 実環境が必要 |
| データベースの喪失 | バックアップからの復元、[復元の順序](../design/reliability/recovery.md#復元の順序)の各確認、再開までの経過時間 | 復元後の確認一覧をすべて満たし、実行単位がロードシェディング順序の逆順で再開する | 縮小した形は `mise run restore-drill` がリポジトリ内で実行できる。本番相当のバックアップからの復元は実環境が必要 |

成功条件はいずれも、事象の最中の観測ではなく、試験の終了時点の状態で判断する。
経過時間は測って記録するが、[復旧目標](../requirements/quality.md#復旧目標)の RPO と RTO が未確定である間は合否の条件にしない。

ローカルの復元試験は Docker と PostgreSQL クライアントを要する。
`mise.toml` は PostgreSQL クライアントを固定していないため、これがインストールされていない環境では試験が走らない。

試験をいつ、誰が実施するかは[保守](../operations/maintenance.md#定期作業)の定期作業で定める。
