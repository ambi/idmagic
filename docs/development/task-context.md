# 作業文脈の導出

`brief` は作業項目の直接参照、作業種別、明示した変更対象から、最初に読む節と検証タスクの候補を返す。
対象を絞る起点は着手時に指定する。
読んだ範囲は作業項目に記録しない。

## 起点と追加取得

```console
mise run brief -- <work-item> --target tools/brief
mise run brief -- <work-item> --kind refactor --target backend/idmanagement/user --concern effects
```

作業種別は記録の `change_kind`、規範上の起点は `affected_spec` から取得する。
`--kind` は調査する作業種別を上書きし、`--target` はリポジトリ内の既存パスを追加する。
オプションは繰り返せる。
作業項目の名前、完全なファイル名、ファイルパスを受け付ける。
対象パスだけでは決まらない変更意図は、次の `--concern` で明示する。

| concern | 指定する変更 |
| --- | --- |
| `boundary` | モジュール、公開範囲、依存、所有者、組み立て地点 |
| `effects` | 永続化、通知、監査、イベントと、その確定の境界 |
| `contract` | 公開 HTTP 契約 |
| `security` | 認可と信頼境界 |
| `performance` | 性能と品質目標 |

最初の出力は候補の場所、参照元、読む理由と、最初の子見出しまでの本体の量を示す。
子節は名前と量だけを並べ、変更に当てはまるものだけを開く。
直接の規範参照は引き続き宣言と、その名前を含むファイルを表示する。
名前の言及は、実装済みまたは検証済みという証拠ではない。
名前を含むファイルがない場合も、実装の有無は別に調べる。

履歴は `--include history`、隣接モジュールの入口は `--include neighbors` で追加する。
隣接候補は、対象モジュールが名指す相手を責務表で解決したものであり、今回変更する依存とは限らない。
隣接モジュールの本文は取得しない。

## 一次情報からの導出

参照先と適用条件は [AGENTS.md](../../AGENTS.md#作業ごとの参照先) の同じ行で維持する。
条件は次の形の HTML コメントで書く。

```text
<!-- context: kinds=feature,bugfix targets=backend,frontend/src -->
<!-- context: concerns=effects -->
```

`kinds` は作業種別、`targets` は対象パスの接頭辞、`concerns` は明示した変更意図を選ぶ。
値をコンマで区切るといずれかの一致、異なるキーはすべての一致を求める。
`*` はそのキーを絞り込まない。
パスの接頭辞はディレクトリ区画で比較し、`tools` は `toolshed` と一致しない。
条件を付けていない行は自動候補に入らず、人が必要に応じて読む。
候補の理由は作業の列、場所は同じ行のリンクから取得する。
本文の規約をツールの中へ写さない。

検証タスクの条件は `mise.toml` の当該タスクの定義へ置く。
実行入口と説明はその TOML 定義から取得する。
引数が必要なタスクは、候補を見てから `mise tasks` とタスク定義で引数を確認する。
候補に出たすべてのタスクを各編集のたびに実行する必要はなく、選択した故障と変更層に合う局所検査を選ぶ。

```toml
[tasks.test-tools-file]
# context: targets=tools
```

所有モジュールは [モジュールの責務表](../modules/README.md#モジュール) のリンクと実装範囲から求める。
公開契約、割り当てられた品質要件、設計索引と TypeSpec を、そのモジュールの配置から候補にする。
TypeSpec は、`spec_impact: none` の変更では `--concern contract` を指定したときだけ候補にする。
モジュール名とパッケージ名の別名表を追加しない。
作用の変更では、設計索引の説明が確定、通知、監査、イベント、トランザクションを扱うリンクを追加する。
これは説明の語による推定であり、作用の所有文書を網羅する保証ではない。
索引にない所有関係は、候補を読んで得た参照から追加で調べる。

## 候補の区分

出力の `explicit` は参照表の直接リンク、`inferred` は配置または記述から推定した候補を示す。
参照先や節が存在しない場合は警告を表示し、読み取れたことにしない。
通常の見出しへのアンカーは規範要件への参照として扱わない。

## 対象別の追加資料

機能が満たすべき内容と判断は機能仕様、代表例は付録、複数の機能にまたがる仕組みと重要な判断はモジュールの内部設計から読む。
機能名は仕様、実装、テストでそろえ、文書の機能群と実装の層まで同じ深さにはしない。
共有ポート、横断設計、外側の配線テストは所有箇所に残し、機能ごとに複製しない。

必要な情報の所在は、ファイル全体ではなく該当箇所を返す `mise run spec-where <requirement-id-or-term>` で探す。
機能仕様に対応するコードは、`features/<feature>.md` と `backend/<module>/<feature>/` の名前の対応と、要件の ID を `//spec:covers` で名指すテストからたどる。
名前の対応から外れる機能は、モジュールの `README.md` の機能一覧が置き場所を示す。
例を直すときは一次情報のデータと実行するテストを、内部の判断を変えるときは設計を追加で読み、共有機構は所有文書へたどる。
