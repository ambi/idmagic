# エージェント向けの指示

この文書は、コーディングエージェントが読む指示（AGENTS.md と `.agents/skills/`）の置き場所、書く内容、skill の書き方を定める。
指示が定める作業の規則そのものは、それぞれの開発文書と設計文書が持つ。

## 置き場所

指示は、毎回読むものと必要なときだけ読むものに分けて置く。
毎回読む文章が長いと、どの作業でも読む量が増え、作業に関係する規則が埋もれるためである。

| 置き場所 | 書くもの | 読まれ方 |
| --- | --- | --- |
| AGENTS.md | 作業ごとの参照先の表と、どの作業にも効く短い規則（`mise` の使い方、ツールの選び方） | どの作業でも最初に読まれる |
| `.agents/skills/<name>/SKILL.md` | 一つの作業を完了する手順と、各段階で読む節 | description が依頼に合うときに読まれる |
| 開発文書と設計文書 | 規則、判断の基準、その理由 | 参照先の表、`brief`、skill から節単位で読まれる |

AGENTS.md の表は `brief` が読む一次情報でもある。
表の行の条件コメントは[作業文脈の導出](task-context.md)に従う。

AGENTS.md に製品の概要やリポジトリの構成の説明を足さない。
エージェントはそれらを README と `docs/` から読めるうえ、文脈ファイルの評価（Gloaguen ほか、arXiv:2602.11988）では、リポジトリの概要を書いても作業の成功率は上がらなかった。

### 毎回読む節を縮める

`brief` は節の本体を表示し、子節は名前と量だけを並べるので、子節へ移した文は当てはまるときだけ開かれる。
本体を縮めるときは、文を次のように扱う。

| 文の種類 | 扱い |
| --- | --- |
| 書く時点で守らなければ欠陥になり、検査では止まらない規則 | 本体に残し、いつ当てはまるか、何をするか、理由の一文に縮める |
| 検査が違反を拒否し、失敗の出力が直し方を示す規則 | 本体には規則と検査名を残し、検査の範囲と判定の説明を子節へ移す |
| 当てはまる作業が限られ、その作業が子節の名前から判別できる規則 | その名前の子節へ移してよい |
| 規則の由来、採らなかった案、出典 | 子節か、形式の理由へ移す |
| 別の文書が一次情報源として持つ規則 | その文書へのリンクに替える |

当てはまる場面が子節の名前から判別できない規則を子節へ移すと読まれなくなる。
時刻の分解能をそろえる規則は、DB アダプターの共有契約の節にあったために DB を使わないテストで読まれず、同じ CI の失敗を 3 回起こした。

## 書くものと書かないもの

指示に書くのは、このリポジトリに固有で、どのエージェントの実行環境でも成り立つ規約である。
次のものは書かない。

- 特定のエージェントのサンドボックスや権限の制限で起きる失敗とその回避。環境が変われば起きなくなり、別のエージェントには誤った指示になる。ただし、操作が必要とするもの（localhost の待受け、ブラウザーの起動）は環境によらない事実なので、AGENTS.md の `mise` の節のように、その事実を理由として書いてよい。
- どのリポジトリにも当てはまる一般的な注意。エージェントは既に知っており、書いても行動を変えない。
- 一度だけ起きた失敗。

同じ指摘を繰り返し受けたら、上の基準に当たるかを判断してから、その規則を所有する文書か skill へ書く。
機械で確実に判定できる規則だけを検査にし、誤検出しうる規則は文章に留める。
理由は[リポジトリ検査](../../tools/check/README.md#検査の判定基準)の判定基準と同じである。
繰り返したかどうかは、次の節の記録から判断する。

## 作業中の妨げの記録

エージェントのセッションは前のセッションを覚えていないので、同じ所で繰り返し迷っているかは、記録を残さなければ分からない。
正式コミットを作る作業では、コミットの前に一度、AGENTS.md、skill、開発文書、検査、`mise` タスクのうち、誤っていた、足りなかった、同じ作業を繰り返させたものがあったかを振り返る。
あれば、一件ごとにコミットのトレーラーを書く。
なければ書かない。

```text
Agent-Friction: docs/development/testing.md#テストダブル — DB を使わないテストで共有契約の節を読まず、時刻の分解能を誤った
Agent-Friction: mise run test-tools — 失敗の出力からどのテストが落ちたか読み取れなかった
```

- 値は「対象 — 起きたこと」とし、区切りには前後に空白を置いた「—」を使う。
- 対象は、リポジトリ相対のパス（見出しのアンカーを付けてよい）か `mise run <task>` にする。集計は対象の表記が一致するものを同じ対象として数えるので、自由記述だけにしない。どの文書にも書いていない前提は、最も近い文書のパスを対象にする。
- 起きたことには、何を読んで何を誤ったか、何が足りなかったかを書く。
- [書かないもの](#書くものと書かないもの)に当たる妨げ（特定の実行環境の制限など）は書かない。

### 記録から変更を決める手順

記録は `review-agent-friction` skill で振り返る。
利用者が振り返りを頼んだときに使い、月に一度程度を目安にする。

`mise run report-agent-friction` は、まだ判断していない記録を対象ごとに集計し、2 件以上の対象、1 件だけの対象、現在のツリーにない対象、形式に合わない値に分けて示す。
振り返りで判断した対象は、その振り返りのコミットより前の記録を数えない。
判断しなかった対象は全履歴から数えるので、1 件だけの記録は次の記録と合わさって 2 件になる。
引数に `git log` のリビジョン範囲（`v1..HEAD` など）を渡すと、その範囲のコミットだけを読む。

対象ごとに、記録された「起きたこと」と対象の現在の内容を読み、次の表で扱いを決める。

| 原因 | 扱い |
| --- | --- |
| 機械で確実に判定できる規則が守られていない | 検査へ昇格させ、昇格したら[毎回読む節を縮める](#毎回読む節を縮める)の表に従って文章を縮める |
| 文書、skill、タスクの記述が誤っている、または足りない | その規則を所有する文書か skill を直す |
| 規則はあるが、読まれる場所にない | [毎回読む節を縮める](#毎回読む節を縮める)に従って、当てはまる場面で読まれる節へ移す |
| [書かないもの](#書くものと書かないもの)に当たる、または記録の後の変更ですでに直っている | 何もしない |
| 現在のツリーにない対象 | 移動先を探し、記録が今も当てはまるかを読んで、上の行のどれに当たるかを決める |

1 件だけの対象は判断せず、次の記録を待つ。
同じ原因の 2 件以上の対象と一緒に直せるもの、1 件でも直す価値が明らかなものだけを判断に含める。

採るかどうかは利用者が決める。
採った変更は作業項目として起票し、集計の結果だけで指示を直接書き換えない。
判断した対象は、何もしないと決めたものも含めて、振り返りのコミットに一件ずつ次のトレーラーを書く。
値は `Agent-Friction:` と同じ対象の表記にし、アンカーまで一致させる。
起票がなくても、空のコミットにトレーラーを書く。

```text
Agent-Friction-Reviewed: docs/development/testing.md#テストダブル
Agent-Friction-Reviewed: mise run test-tools
```

後で扱うと決めた対象にはトレーラーを書かず、次の集計にも現れるようにする。

## srgn の引数の解釈

AGENTS.md のツール表にある srgn の呼び出しでは、どの引数も省かない。
`--stdin-detection force-unreadable` がないと、標準入力がパイプのときに `--glob` のファイルを無視し、何も変えずに終了コード 0 で終わる。
`--fail-none` は対象全体で一件でも一致すれば成功するので、一部のファイルだけの一致や同じ値への置換では止まらない。
適用後に `git diff --stat` を読むのは、これを見つけるためである。
`--glob` は一回しか指定できず、`{a,b}` の形は一致なしとして失敗する。
コメントの中だけを書き換えるときは、`--go comments` のような言語の範囲指定を足す。

`--literal-string` を付けても、検索値と置換値のバックスラッシュは解釈される。
単一引用符の中の `\\` はバックスラッシュ 1 文字、`\n` は改行、`\\n` はバックスラッシュと `n` の 2 文字を表し、`$1` は文字どおりに扱われる。
解釈を確かめられない値は、srgn を使わず編集ツールで前後の文脈を指定して書き換える。

## skill の書き方

skill の一般的な書き方は Anthropic の「Skill authoring best practices」に従う。
このリポジトリでは、それに加えて次のように書く。

- `name` は一度決めたら変えない。起動の名前であり、ほかの文書と skill が名前で参照するためである。
- `description` は、[文章の言語](writing-language.md)に従って日本語で、「〜する。〜のときに使う。」の二文にする。エージェントは description だけを読んで skill を選ぶので、使う場面を書かないと起動されない。
- skill は手順と、各段階で読む開発文書と設計文書の節へのリンクだけを持つ。規則とその理由は開発文書と設計文書に置き、skill へ写さない。写すと、規則を変えたときに skill が古くなる。
- `mise run` で呼ぶタスクは `mise.toml` に宣言されていなければならない。`check-agent-guidance` が検査する。
