# 作業項目のグループ

この文書は、未完了の作業項目を分けるグループの一覧である。
作業項目は前付けの `group` に、この表のグループを一つ書く。
`mise run check-work-items` は、未完了の記録が表にあるグループを持つことを確かめる。
完了と中止の記録は要約へ縮めるので、グループを持たない。

グループは、同じ領域の作業を並べて、重複と矛盾に気付きやすくするための単位である。
着手の順序を拘束するのは `depends_on` であり、グループは順序を決めない。

## 優先度の決め方

優先度の各段階の意味は[作業項目フォーマットの優先順位とリスク](../formats/work-item-format.md#優先順位とリスク)が定める。
表の「基準の優先度」は、そのグループの作業がふつう当たる段階である。
基準と違う優先度を付ける項目は、その理由を、表の「基準の理由」か記録の動機に書く。
同じグループの複数の項目に当たる理由は表に、一つの項目だけに当たる理由は記録に書く。

現在は未リリースであり、当面も未リリースを続ける。
そのため、公開後の互換性、実利用の負荷、外部の実環境を前提にする作業は、効果が出るのが初回リリースの後になるので p3 を基準にする。
初回リリースの時期と対象のデプロイ構成が決まったら、`release` と `scale-availability` の基準を見直す。

## グループの一覧

| グループ | 扱う作業 | 基準の優先度 | 基準の理由 |
| --- | --- | --- | --- |
| `spec-conformance` | 実装が規範に反する欠陥と、規範どうしの食い違いの是正。同じ Aggregate を変える経路の間の不一致を含む | p1 | 利用者、管理者、監査が誤った結果を受け取る。今は違反のない予防と、規範の側を直せば足りる可能性の高い項目は p2 にする |
| `api-contract` | TypeSpec と標準要件の宣言の漏れ、API ガイドラインへの追従、宣言と実装のずれを検出する検査 | p2 | 生成したクライアントと利用者が契約を読めない。振る舞いの誤りは `spec-conformance` が扱う。宣言する対象（beta の操作など）がまだない項目は p3 にする |
| `retention-and-audit` | 保持期間、消去、復元後の再消去、監査記録の確定の方式 | p2 | 設計が定めた保持と消去の規則に実装が届いていない。新しい方式の採否の検討は p3 にする |
| `system-console` | 制御面の運用者の画面と API、テナント横断の操作の監査と上限 | p2 | 既存の制御面に欠けた操作と防御を補う |
| `operations` | 監視、アラート、runbook、トレース、Probe、再試行、デプロイ構成ファイルの生成とローカルでの稼働確認 | p2 | 設計文書が定めた運用の仕組みに構成ファイルと実装が追いついていない |
| `scale-availability` | 大規模テナントの性能、データ層の分割、単一障害の無停止、負荷の実測 | p3 | 実利用の負荷も本番の実環境もまだない。脅威モデルが指すテナント間の可用性の分離は p2 にする |
| `release` | 成果物の署名と来歴、更新互換性、保存形式の互換性、本番準備の判定 | p3 | 未リリースの間は守る旧バージョンがない |
| `development-process` | 検証の手段（適合試験、プロパティ、モデル検査、反復実行、ミューテーション）と開発の進め方の文書 | p2 | 開発の検証の網を広げ、ほかの全グループの欠陥を見つけやすくする。比較や評価から始める項目と、今の動作に問題のない依存の更新は p3 にする |
| `design-conformance` | 設計文書が定めたコードと文書の規則への既存の記述の追従 | p2 | 規則に反する記述が残ると、新しい記述が同じ形を写す |
| `frontend-ui` | ユーザーインターフェース設計への画面の追従、アクセシビリティ、管理コンソールの見た目 | p2 | 設計が定めた画面の規則に既存の画面が届いていない。既存の画面の表現力を広げる項目は p3 にする |
| `lifecycle-workflow` | ライフサイクルワークフローの一覧、トリガー、テンプレート、通知、試験 | p2 | 既存の機能の運用に要る操作を補う。上書きの仕組みが既にある文面の拡張は p3 にする |
| `identity-management` | User と Group のモデルの拡張（入れ子のグループ、ゲスト、連絡先、セルフサービスの登録、CSV の操作） | p3 | 新しい概念を足す。既存の CSV に欠けた操作を足す項目は p2 にする |
| `tenant-configuration` | テナントの構成の書き出しと取り込み、カスタムドメイン | p3 | 新しい機能領域である |
| `authentication` | 認証の手段と強度（リスクベース、端末、OTP、パスワードレス、認証の水準、代理ログイン） | p3 | 新しい手段と概念を足す |
| `admin-governance` | 委任管理、特権の一時昇格、アクセスの申請とレビュー、権限の台帳、セキュリティの推奨 | p3 | 新しい機能領域である |
| `federation-protocols` | OAuth と OIDC の拡張、検証可能なクレデンシャル、SSF、アプリの統合テンプレート、レガシーなフォームへの代理認証 | p3 | 新しいプロトコルと機能を足す。既存の SSF の適合と画面は p2 にする |
| `directory-and-entra` | Directory Connector の拡張、AD への書き戻し、Entra との連携の自動化と実テナントでの確認 | p3 | 新しい機能と、外部の実環境が要る確認である |
| `scim-provisioning` | SCIM の受信側の拡張と、下流へのプロビジョニングの差分同期 | p3 | 標準の任意の機能と、規模が出てから効く改善である |
| `mcp-gateway` | MCP ゲートウェイと評価の入口の運用、接続の確認、承認、参照 PEP | p2 | 既存の MCP の執行を使える状態にする。採否の判断から始める項目は p3 にする |
| `agent-governance` | Agent の統制の拡張（責任者の移管、権限の申請、ラベル、行動の所見、検出信号、A2A、ID-JAG） | p3 | どれも採否の判断から始める |
| `workload-identity` | SPIFFE によるワークロードの認証と、その属性の引き継ぎ | p2 | 既存のアテステーションの交換の信頼性と追跡性を補う。新しい認証方式は p3 にする |
| `security-hardening` | デプロイの前提の自己検査、FIPS の運転モード、監査記録の改ざん検知 | p2 | 脅威モデルが指す欠落を塞ぐ。新しい運転モードと仕組みは p3 にする |

## グループを変えるとき

新しい作業項目がどのグループにも当たらないときは、この表に行を足してから起票する。
一つのグループの未完了の項目がなくなっても、行は残してよい。
同じ領域に二つのグループが育ったら、一つにまとめ、記録の `group` を書き換える。
