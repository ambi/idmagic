# 開発プロセスの計測

## 現在の判断

変更のリードタイム、デプロイ頻度、変更失敗率、復旧時間は、現時点では計測値として採用しない。Git と CI の履歴だけでは、本番へ配備した時刻、配備した版、配備に起因する障害、サービスを復旧した時刻を一意に対応付けられず、再現可能な Measurement を作れないためである。

数値を持たない現状は Planning assumption ではない。未実測の数値を構成計画へ使っていないためである。計測基盤を導入した後の実測だけを、[Capacity](../capacity.md#evidence-classes) と同じ Evidence classes に従う Measurement として記録する。

## 計測の目的

| 指標 | 判断に使うこと | 必要な事象 |
| --- | --- | --- |
| 変更のリードタイム | work item または変更単位が大きくなり、利用可能になるまでの時間が延びていないか | 変更の開始、既定ブランチへの統合、本番配備 |
| デプロイ頻度 | 小さなリリースを継続できているか | 環境、版、コミットを持つ配備完了 |
| 変更失敗率 | 配備の検証と段階的展開が失敗を本番全体へ広げていないか | 配備と、それに起因する後退、修正、障害の関連 |
| 復旧時間 | 変更による利用者影響を検知してから回復するまでが延びていないか | 影響の開始または検知、復旧確認、原因となった配備 |

## 採用条件

次の条件をすべて満たしたときに計測を再評価する。

1. リリース経路が、環境、版、Git コミット、成果物ダイジェスト、開始時刻、完了時刻、結果を保存する。
2. 後退と障害の記録が原因となった配備を参照し、検知時刻と復旧確認時刻を持つ。
3. 記録を後から同じ規則で再集計でき、除外条件を手作業で変えずに済む。
4. 指標ごとに、値が悪化したときに見直す対象を所有者が定める。

採用時は、Measurement に日付、対象期間、データ源、集計規則、結果の保存先を添える。指標を良く見せるために開始点、終了点、失敗の定義を変更しない。
