# リリース

## リリースの単位

API、各実行レーンのワーカー、バッチ、UI は、同じ Git コミットと版から作る一つのリリースとして扱う。実行単位ごとに展開時刻をずらしても、異なるコミットの成果物を一つのリリース名で混ぜない。

版は Semantic Versioning の `vMAJOR.MINOR.PATCH` タグで識別する。利用者に見える互換な機能追加は `MINOR`、互換性を壊す変更は `MAJOR`、互換な修正だけなら `PATCH` を上げる。固定した暦上の頻度は設けず、依存関係のない完了済み work item を不必要に束ねない。

このリポジトリには、成果物を公開するリリース用 CI がまだ無い。以下の手順は、同じコミットから不変なイメージダイジェストを作成して配備先へ渡せる外部のリリース経路を前提とする。その経路が用意されるまでは、版を付けても本番リリースは完了しない。

## 準備

1. リリースに含める完了済み work item を列挙し、未完了の依存関係が無いことを確認する。
2. `mise run verify`、`mise run check-api-compat`、`mise run spec-diff` を実行し、仕様と実装の差分を読む。
3. リリースする版を決め、`VERSION`、`GIT_COMMIT`、`BUILD_DATE` を同じコミットから全バックエンド成果物へ埋め込む。UI も同じコミットから作る。
4. `mise run update-api-baseline` で公開する OpenAPI の互換性ベースラインを固定し、差分があればリリース準備コミットに含める。通常の機能変更ではこのタスクを実行しない。
5. リリースコミットへ `vMAJOR.MINOR.PATCH` タグを付け、外部のリリース経路が生成した成果物のダイジェスト、コミット、版の対応を保存する。

## 段階的な展開

各段階では `/startupz`、`/readyz`、`/livez`、HTTP のエラー率とレイテンシー、ワーカーの失敗率とキュー深度を確認する。しきい値の正本は [Capacity](../capacity.md) と監視規則であり、この文書へ数値を複製しない。

| 段階 | 対象 | 観測時間 | 次へ進む条件 |
| --- | --- | --- | --- |
| ステージング | 本番と同じ実行単位。代表データと `mise run k6-smoke` を含む | 15 分 | プローブが成功し、リリースに起因するアラートとスモーク失敗が無い |
| 先行配備 | 本番の一部。通常より負荷の高いテナントを必ず含む | 15 分 | 新しいレプリカが受付可能で、認証、トークン、ジョブのアラートが発火しない |
| 25% | 本番トラフィックの 25% | 15 分 | 先行配備と同じ条件を満たす |
| 全体 | 本番の全レプリカ | 30 分 | すべての実行単位が新しいダイジェストで安定し、未処理ジョブが増え続けない |

いずれかの段階で条件を満たさなければ展開を止め、[リリースの後退](../runbooks/release-rollback.md) を開始する。機能フラグだけで影響を止められる変更は、配備の後退より先にフラグを戻す。

## 完了

全体展開後の観測時間を終えたら、版、コミット、各成果物のダイジェスト、展開時刻、結果、後退の有無をリリース経路の記録へ残す。OpenAPI の互換性ベースラインは、実際に公開したリリースだけを表す。
