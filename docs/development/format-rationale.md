# フォーマットの理由

この文書は、[文書ガイド](../formats/documentation-guide.md)、[仕様フォーマット](../formats/specification-format.md)、[設計フォーマット](../formats/design-format.md)の各規則を選んだ理由を書く。
形式文書は、書き手とエージェントが従う規則だけを書き、理由はこの文書に分ける。
規則を書くたびに理由を読む必要はなく、理由を読むのは規則を変えるときや、規則に疑問を持ったときだからである。
節の名前は、形式文書の対応する節にそろえる。

## 全体の方針

| 方針 | 理由 |
| --- | --- |
| 一つの事実は一か所にだけ手で書き、ほかの表示は生成する | 一つの事実を複数の場所に書くと、追加のたびに全箇所を同期させることになり、片方だけが更新される。手で書く場所の数が、作成と保守の費用を決める |
| 仕様には外部から観測できる振る舞いだけを書く | 観測できない内部の手順は、実装を変えるたびに文書の更新を求めるが、利用者にとっての正しさは変わらない |
| 「内部仕様が要る」状況を、仕様の漏れか実装の欠陥の信号として扱う | 外から観測できるのに決めていなかった振る舞いは、決めて要件にするか、実装を直して振る舞いごとなくすべきものである。文書で説明しても原因は残る |
| 仕様を短く書けない設計は直す | 同じ種類の操作が経路ごとに異なる振る舞いをすると、仕様はその差の分だけ長くなる。経路をまとめるほうが、仕様、実装、テストのすべてで安い |

この方針は、[OpenSpec](https://openspec.dev/) の現在の仕様と変更の差分を分ける考え方、[Kiro](https://kiro.dev/docs/specs/concepts) が採る EARS 記法、Cyrille Martraire の Living Documentation が説く「導けるものは生成する」という原則を参考にした。

## 文書ガイド

### 配置

- 配置図を文書ガイドに置くのは、配置図がどの内容をどの文書に書くかを図にしたものであり、仕様や設計の書式とは別の問いに答えるからである。仕様の書式の文書が設計や運用の文書の配置まで定めると、文書の名前が中身を表さなくなる。
- 仕様と設計の書式を別の文書にするのは、ISO/IEC/IEEE 29148 が要件仕様を、ISO/IEC/IEEE 42010 がアーキテクチャ記述を、別の情報項目として扱うのと同じく、外へ約束することと、それをどう実現するかが別の問いだからである。
- 生成物を `docs/` に置かないのは、`docs/` 配下をすべて人が書く文書に保つためである。

### README.md — 境界の宣言

- 読む順序はシステムではなくファイルを説明し、将来の計画はまだ存在しないシステムを説明するので、どちらも境界の宣言にならない。
- モジュールの一覧と公開範囲を責務表に一度だけ書くのは、別の索引や分類表を持つと、変更時に片方だけが古くなるからである。境界の選択は、情報隠蔽、要件と不変条件、検査される制約、変更の波及で比較する。
- 複数のモジュールの協調でだけ成り立つ振る舞いを `scenarios.feature.md` に置くのは、その流れをモジュールごとの断片に分けると、実際の保証を書く場所がなくなるからである。

## 仕様フォーマット

### 機能仕様

- 一つの機能について読み手が知りたいこと（モデル、状態遷移、操作の要件、その判断の理由）を一つの機能仕様にまとめるのは、ファイルを行き来せずに機能全体を読めるようにするためである。
- 節の並びを固定するのは、読み手が同じ問いを多数の機能に対して繰り返し投げるので、節の位置をそろえて探す手間を省くためである。
- エラーの節を置かないのは、エラーの形が TypeSpec に、返す条件が要件文にすでにあり、三か所目に書くと同期の対象が増えるだけだからである。
- 操作ごとの要約表を書かないのは、要約表の値が要件文の写しであり、要件を変えるたびに表も変える必要があったからである。一覧が要る場合は生成サイトが見出しから作る。
- 一つの H3 に一つの操作を置くのは、二つの操作が混ざると、要件がどちらの操作の義務なのかを読み手が要件ごとに判断することになるからである。
- 要件を正常の経路、状態による分岐、拒否の順に並べるのは、読み手がまず何が起きるかを知り、次に例外を知るためである。ID 順に並べると、書き起こした時期の順になり、操作の構造を映さない。
- 判断の理由を要件のそばに書くのは、離れた一覧に判断を並べると、どの要件を正当化する判断なのかを照合できないからである。

### 仕様の木

- 仕様を四つの階層の木に置くのは、一つのモジュールに数十の機能が並んでも、機能群の階層で全体を見渡せるようにするためである。
- 要件を機能スライスの仕様でだけ宣言するのは、どの機能にも入らない要件が親の階層へ溜まることを防ぐためである。
- 機能スライスの仕様のディレクトリをコードのディレクトリと同じ名前で対応させるのは、読み手とエージェントがパッケージのパスから仕様のディレクトリを一つに決められるようにするためである。
- 下位のノードが上位の要件を書き写すと片方だけが更新され、逸脱を宣言しなければ逸脱はコードにだけある暗黙の仕様になる。そのため、例外だけを、上位へのリンクとともに宣言する。

### 状態遷移

- 状態の表を置くのは、`From` 列と `To` 列から状態を導くと、どの遷移も到達しない状態が黙って失われ、各状態の意味も一行で示せないからである。
- `Guard` に空文字列を使わないのは、表と生成した図のどちらでも実行可能な条件に見えるからである。
- 状態遷移表（マトリクス形式）を置くのは、遷移の表が「起きる遷移」だけを並べ、「その状態でその操作を要求されたらどうなるか」を書く場所がないからである。IdManagement では、停止した Agent を削除できない、削除を予約した User の無効化が決まっていない、といった漏れが、実装と書き起こしの後になって見つかった。すべてのセルを埋める表では、空のセルが漏れとして見える。
- 時間を契機とする遷移を列に置くのは、誰がいつその遷移を起こすかが決まっていないと、「完全削除が一覧の取得のときにしか起きない」のように実装の都合がそのまま振る舞いになるからである。
- 手書きの状態図を保守しないのは、同じ状態機械の二つの写しが食い違うからである。

### 標準仕様

- `Adoption` と `Strength` を独立した軸にするのは、機能を提供するかは選べるが、提供した後に規則を守るかは選べないからである。
- 利用側の `optional` の行に条件と代わりに送る内容を書くのは、どちらも書かない行が常に送信する行と区別できないからである。
- `Statement` を標準の視点で書かないのは、標準の視点の行が、`Adoption` が反対を示していても、製品が受け入れた義務として読めてしまうからである。
- すべての ID をテストから参照するのは、実行するものがない行は製品が守る標準ではなく主張にすぎないからである。実装コードの参照を数えないのは、コメントだけで義務全体を担えてしまうからである。

### 要件と例

#### 用語の選択

- `REQ-*` の一件を「規則」ではなく「要件」と呼ぶのは、「規則」が検査の規則、Gherkin の `Rule`、ガイドラインの規則と区別できない一般的な語だからである。「要件」は ID の `REQ` と対応し、EARS や INCOSE の requirement と語がそろう。
- 機能仕様の H3 の単位を「操作」と呼ぶのは、ほかの候補がどれも既存の語とぶつかるからである。「ユースケース」は要求工学では利用者の目的を単位にした複数手順のシナリオを指し、「処理」は内部を連想させ、「機能」は機能スライスと、「振る舞い」は外部から観測できる振る舞いと、「コマンド」は読み取りを含まない点でぶつかる。

#### 仕様に書く範囲

- 仕様にない振る舞いを三つに分類するのは、見つけた振る舞いを全部書き写すと、実装の偶然まで仕様として固定し、文書の量が実装の量に比例して増えるからである。
- (b) の判断の基準は、その細部だけが異なる二つの実装をどちらも正しいと判断できるかである。コードから観測できるかではなく、将来の実装がその性質を維持する義務を負うかで決める。

#### 要件一件の書式

- 一行に一つの義務、曖昧な語の禁止、条件の表は、[INCOSE Guide to Writing Requirements](https://www.incose.org/docs/default-source/working-groups/requirements-wg/guidetowritingrequirements/incose_rwg_gtwr_v4_summary_sheet.pdf) の規則から、機械で検査できるものを採った。
- 番号付きの手順は、[WHATWG Infra Standard](https://infra.spec.whatwg.org/) が処理の順序を書く形に倣う。
- 担保手段の欄を書かないのは、要件からコードへの追跡はテストの `//spec:covers` が担い、手で書いたシンボルの一覧はコードの変更のたびに更新が要る写しだったからである。
- 要判断の欄を書かないのは、未決の点が現在の仕様の中に散らばると、仕様が「現在の挙動」と「決めるべき問い」を混ぜて書くことになるからである。未決の点は work item として扱い、決めた結果だけを要件にする。
- タイトルを結果の一文にするのは、能力の形（「〜できる」）は拒否や冪等性の要件に使えずタイトルの型が要件の種類ごとに分かれ、名詞句は何を保証するかを本文まで読まないと分からないからである。

#### EARS 形式

- EARS は Mavin らが提唱した要件文の型であり、型を選ぶことで、契機、状態、望まない入力のどれについての要件かが文の形から分かる。[EARS の規則](https://alistairmavin.com/ears/)は、要件が零個以上の前提、零個か一個の契機、ちょうど一つの主体、一つ以上の応答からなり、節を時間の順に並べることを求める。日本語の型もこの規則をそのまま写す。
- 主体を必須にするのは、主体のない常時の型「〈対象〉は、〈結果〉。」が、主語と述語のあるどの平叙文も受け入れ、型の制約を失わせるからである。主体にモジュール名を使うのは、仕様の木で応答に責任を持つ最小の単位がモジュールであり、名前がすでに `README.md` の H1 にあって、検査が文書の外の設定を読まずに済むからである。製品名に固定すると、すべての文で同じ語になり、主体を書く意味が型の検査の記号だけになる。
- 前置きの標識を型ごとに固定し、「場合」を望まない入力に限るのは、日本語では「〜場合」の一語で状態、契機、異常、構成のすべてを書けてしまい、それが日本語で EARS を書くときの最大の曖昧さだからである（[ISSOH の日本語テンプレートの解説](https://www.issoh.co.jp/tech/details/11489/)）。同じ解説が勧める「もし〜ならば」は採らない。曖昧さの原因は「場合」が型を問わず使われることなので、「場合」を一つの型に限れば同じ効果が得られ、既存の拒否の文の形を保てる。英語のキーワードを前置きに残す案も、文末の標識と二重になるので採らない。
- 応答を一つに限らないのは、Mavin の規則が一つ以上の応答を認めており、拒否の文の「観測する内容」と「変わらない内容」を別の行に分けても前置きを繰り返すだけだからである。代わりに応答の中に条件を書くことを禁じる。条件が応答へ入り込むと、どれが契機でどれが前提かが文の形から読めず、要件文が型のない自然言語に戻る。
- 義務を「しなければならない」で示さず現在形に限るのは、要件文が `REQ-*` の見出しの下にだけ現れ、そこに置いた文がすべて規範だからである。文末の統一は、能力（できる）、許可（てもよい）、推奨（望ましい）、定義（である、とする）の文末を禁じることで得る。
- 拒否の要件文に「変わらない内容」も書くのは、統制が働いたかを判断する読者には、操作が作用を起こさなかったことも必要だからである。
- セキュリティ統制の拒否を要件文に書くのは、どこにも拒否を記していない統制には検査対象となる規範がなく、実装が拒否をやめても違反する記述がないからである。

#### 横断的要件と値オブジェクト

- IdManagement の未決の点 15 件のうち 9 件は、同じ種類の操作が経路や Aggregate ごとに異なることから生じた（ユーザー名の大文字と小文字の扱い、メールアドレスの重複の扱い、冪等性、下流への通知）。横断的要件と値オブジェクトを一か所で定義すれば、この種類の漏れは構造的に生じない。

#### 例

- 例を任意にするのは、すべての要件に例を求めた結果、IdManagement では例の付録が文書の総行数の約 4 割を占め、その多くが要件文の言い換えになったからである。
- 例を置く場合でも、規則を本文で述べて例で裏付ける形を保つ。例の形でしか仕様を書かないと、要件が増えるほど全体を把握できなくなる。
- 親の要件だけを参照するテストでは子の例を一つも検査したことにならないので、要件を検査済みとみなすには子の例をすべて参照させる。
- 決定表の条件セルに `-` を使わないのは、公式の Markdown 照合器がハイフンだけのセルを含む行を表の区切りとして扱い、AST から除外するからである。
- 実装の出力を期待結果として自動採用しないのは、特性化した現状は、維持すべき約束と判断するまで望ましい仕様ではないからである。

### 旧形式の扱い

- 旧形式では、一つの機能を読むために四つのファイルを行き来する必要があり、どの機能にも入らない記述が種別ごとにモジュールのルートへ溜まった。
- モジュールの印を `design/README.md` の有無で決めるのは、履歴のリビジョンや一つのファイルだけを読む道具も、設定を読まずに同じ判定ができるようにするためである。
- 印のないモジュールを文書ごとに拒否するだけでなくモジュールごとに報告するのは、文書ごとの拒否からは、欠けているのが印だと読み取れないからである。
- 文書を移しても ID とタイトルを変えないのは、`spec-diff` が形式の変わった要件ではタイトルだけを比べるので、タイトルを変えずに移せば移動が仕様の変更として報告されないからである。
- `spec-diff` が旧形式を読み続けるのは、比較の基準になる main の履歴に旧形式の文書が残るからである。

## 設計フォーマット

### 設計領域

- 設計をどの階層でも同じ設計領域で構成するのは、読み手が階層をまたいでも同じ設計領域の名前で探す場所を決められるようにするためである。
- 設計領域と設計の記録は、合わせて arc42 の 12 章の内容を覆う。目標と関係者は `docs/requirements/product-overview.md`、制約、文脈と範囲、解決戦略、構成要素、実行時、配置はアーキテクチャ設計、横断的概念はアプリケーション、データ、セキュリティ、信頼性、オブザーバビリティの各設計と横断的概念の文書、設計判断は `decisions.md`、品質は要件文書の品質要件と性能設計と検証設計、リスクと技術的負債は `risks.md` と脅威モデル、用語は要件文書の `glossary.md` が扱う。
- 設計判断とリスクを設計領域に並べないのは、どちらも特定の設計領域の内容ではなく、複数の設計領域にまたがる記録だからである。arc42 は設計判断とリスクをアーキテクチャ記述の章とし、ISO/IEC/IEEE 42010 は判断とその根拠をアーキテクチャ記述の一部とする。
- 設計領域の索引をシステムとモジュールの設計の入口に置くのは、設計領域を欠かさず並べることで、書き漏らした設計領域が書き手と読み手の両方に見えるからである。
- 設計領域の順序を一つに固定するのは、索引の表と生成サイトの目次で並びが異なると、読み手が同じ設計領域を二つの順序で探すことになるからである。
- 機能の `design.md` に設計領域の索引を置かないのは、機能の階層では大半の設計領域が上の階層に従うだけであり、IdManagement では索引の行の多くが「該当なし：」で埋まり、内容のない記入欄になったからである。

### 重要な設計判断

- 手本は arc42 の第 9 章であり、重要で、覆すと高くつき、影響の広い判断だけを一か所に集める。
- 見出しに側面の名前を使わないのは、側面の名前が記入欄に見え、該当しない側面の文章を作るか、一つの判断を複数箇所へ分散させることになるからである。
- 再検討の条件のない判断は、見直す機会を読み手に残さない。

### 機能の設計

- ファイルとパッケージを列挙しないのは、コードを開けば分かり、コードと二重に保守すると片方が古くなるからである。
- 製品が守る値を要件に書くのは、`spec-diff` が内部設計を比較しないので、内部設計に書いた値を変えても仕様の変更として検出されないからである。

### 認可

- 認可をまとめるのは、認可を確認する人が必要とするのが、モジュールごとの断片ではなく製品全体の認可だからである。
- 操作とスコープの対応を文章で言い換えないのは、同じ対応の二つの写しは互いに差分検査できず、検査されない写しが古くなるからである。

### 脅威モデル

- ほかの文書は製品が実行する内容を書くので、実装されなかった統制は何とも矛盾しない。脅威モデルはこの欠落を見えるようにする。
- 統制のない行を同じ表に置くのは、一覧を最後まで読めば必ず目に入る形にするためである。再検討の条件のない受容は、放置へ名前を付けただけである。
- work item への前方参照を置かないのは、完了して移動した時点で古くなるからである。
- 網羅的でないことを明記するのは、完全な保証として読める脅威モデルが、検討していない脅威と退けた脅威を区別できなくするからである。
