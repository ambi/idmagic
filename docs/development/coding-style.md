# コーディングスタイル

この文書は、コードを書くときとレビューするときに用いる判断の視点を示す。
個人の好みではなく、読み手が理解し、変更し、検証する際の負担を基準にコードの形を選ぶ。

## 使い方

コードを書くときは、理解しやすさ、局所性、凝集性、カプセル化、テスト容易性、変更容易性、単純さの七つの視点から、名前、コメント、関数、制御構造、抽象化、依存関係、テストの形を決める。
実装後にも同じ視点で読み直し、意図がコードから伝わるか、変更に必要な知識が散らばっていないか、不要な仕組みが増えていないかを確かめる。

レビューするときも、この七つの視点から変更を読む。
単なる好みの違いを指摘するのではなく、どの視点で何が読みにくいか、どの変更が難しくなるか、どの情報が境界から漏れているかを理由とともに示す。

## 文書の範囲

この文書は、命名、コメントの内容、関数内の構成、局所的な抽象化、テストコードの読みやすさ、依存関係を追加する判断を扱う。
モジュールやサービスの境界、外部 API の契約、テスト水準、テストダブルは、それぞれの設計文書とテスト方針に従う。

公開された言語別スタイルガイドを、その言語の慣用を知るための出発点とする。
整形や構文上の慣用がプロジェクトの整形ツールまたは静的解析ツールと異なる場合は、機械検査の設定を優先する。

## 理解しやすさ（Comprehensibility）

### 意図を表す名前

- **指針**：名前には、その値または操作が現在の文脈で果たす役割を入れる。
  型、生成元、実装手段だけを繰り返す語や、プロジェクト外の読者に通じない略語は入れない。
  短いスコープでは、意味が一意なら短い名前を使ってよい。
- **理由**：型はエディターで確認できるが、値を何の判断に使うかは名前からしか分からない。
  一方、狭い範囲で説明語を重ねると、重要な差が名前の中に埋もれる。

頭字語の文字ケースは、言語の慣用に従う。
同じ概念でも、言語をまたいで表記を揃えるために片方の慣用を崩さない。

### 条件として読める真偽値と判定関数

- **指針**：真偽値は状態を、判定関数は成立する条件を表す名前にする。
  否定を重ねた名前や、何を判定するか分からない `check`、`flag`、`status` を避ける。
- **理由**：条件式では名前がそのまま分岐の前提になるため、呼び出し側で否定を解読させる名前は誤読を増やす。

### 作用を予測できる操作名

- **指針**：永続化、通知、ネットワーク、乱数、時刻、状態変更を伴う関数は、その作用を予測できる動詞を使う。
  何をするかを隠す `process`、`manage`、`do` は、プロトコルやフレームワークが名称を定める場合を除いて使わない。
- **理由**：呼び出し側は実装を開かずに、失敗、待機、再試行、状態変更の可能性を判断する必要がある。

### コードから復元できない情報を伝えるコメント

- **指針**：コメントには、選択理由、成立に必要な前提、外部契約、直感に反する境界、誤って変えやすい制約を書く。
  構文を自然言語へ置き換えた説明、名前の言い換え、変更履歴は書かない。
- **理由**：コードと同じ情報を持つコメントは、変更時に片方だけが古くなる。
  実装から導けない理由と前提は、コメントがなければ将来の変更で失われる。

## 局所性（Locality）

### 利用箇所に近い宣言

- **指針**：局所変数、説明変数、小さな定数は、最初に使う判断の近くで宣言する。
  複数の引数が一つの操作の入力を構成し、同じ組で受け渡される場合は入力型へまとめる。
- **理由**：値の定義と利用の間が長いほど、読者は途中の状態と再代入の有無を記憶しなければならない。
  関係する値を入力型へまとめると、呼び出し側と本体が同じ単位を読む。

### 読む順序に沿った配置

- **指針**：入口となる型と操作を先に置き、その実装だけが使う補助関数を後に置く。
  関数内では、正常系を追うために必要な前提を先に検査し、主要な計算を一方向に並べる。
- **理由**：読者が詳細を読むかどうかを入口で選べれば、変更に必要な範囲を狭められる。
  補助関数から入口を探させる並びは、読む順序を逆転させる。

## 凝集性（Cohesion）

### 一つの抽象水準を扱う関数

- **指針**：関数名が本体を一文で要約でき、本体の各部分がその要約と同じ抽象水準にある形を選ぶ。
  行数だけを理由に関数を分割しない。
- **理由**：短さだけを目的に分割すると、一度しか使わない薄い関数を往復しなければ全体を理解できない。
  一方、業務判断、表現変換、配線を同じ関数へ混ぜると、関数名が本体を要約できなくなる。

関数の長さは調査のきっかけにはなるが、分割の根拠にはならない。
分割するのは、名前で要約できない異なる判断が混ざっている場合、または一部だけが別の理由で変わる場合である。

### 前提を先に示す早期 return

- **指針**：関数の残り全体を実行できない条件は、冒頭の早期 return で終える。
  正常系の途中に多数の終了条件が散らばる場合は、入力検査または下位の判断へまとめられないかを検討する。
- **理由**：前提を先に除外すると、主要経路の入れ子が浅くなる。
  ただし、終了点を増やすだけでは複雑さを移動するにすぎない。

## カプセル化（Encapsulation）

### 必要な範囲に限った可視性

- **指針**：関数、型、定数は、現在の呼び出し側が必要とする最小の可視性にする。
  将来の再利用、テストからの直接呼び出し、名前空間の整理だけを理由に公開しない。
- **理由**：公開した名前は、変更時に調べる呼び出し側と互換性の範囲を増やす。
  テストのためだけの公開は、本番の境界とテストの境界をずらす。

### 所有者を曖昧にしない可変値

- **指針**：呼び出し後にも書き換えられる配列、スライス、map、オブジェクトを保持するときは、共有が契約でない限り境界で複製する。
  共有する場合は、誰が変更できるかを型またはコメントで示す。
- **理由**：別の所有者による後の変更が内部状態を変えると、値を作った操作の事後条件を再現できない。

## テスト容易性（Testability）

### 入力またはポートとして受け取る非決定要因

- **指針**：時刻、乱数、識別子生成、設定、永続化、通知を内部で取得せず、値またはポートとして受け取る。
  差し替える必要のない局所処理のためだけに、新しいポートを作らない。
- **理由**：同じ入力で判断を再現できれば、テストは待機、グローバル状態、実行順序へ依存しない。

### 条件、操作、観測結果が分かるテスト

- **指針**：テスト名は、対象だけでなく条件または観測結果を示す。
  前提値は操作の近くに置き、表駆動テストは同じ操作と表明を異なる入力で繰り返す場合に使う。
  失敗メッセージには実際値と期待値、または破られた事後条件を含める。
- **理由**：失敗したテストだけを読んで、何が壊れ、どの入力で再現するかを判断できなければ、診断のために実装を読み直すことになる。
  異なる表明を一つの表へ押し込むと、各事例が固定する振る舞いが隠れる。

## 変更容易性（Changeability）

### 同じ判断を繰り返すコードをまとめる

- **指針**：コードが似ているという理由だけで共通化しない。
  複数の記述が同じ判断または制約を表し、今後も同じ理由で変わる場合にまとめる。
  三つ目の類似箇所が現れた時点を、共通化すべきかを検討する目安にする。
  共有すべき不変条件または安全性条件は、箇所の数を問わず一つの実装へ集める。
- **理由**：早い共通化は、後に独立して変わる処理を一つの引数や分岐へ押し込み、呼び出し側へ両方の事情を漏らす。
  反対に、同じ判断を複数の場所で保つと、一部だけを変更する誤りが起きやすい。

三つ目という数は、自動的に共通化するための閾値ではない。
複数の記述が同じ知識を持つかを見直すきっかけとして使う。

### 新しい依存関係の利点と負担を比べる

- **指針**：新しい依存関係を追加する前に、言語機能、標準ライブラリ、既存の直接依存で目的を満たせないことを確認する。
  追加する場合は、置き換えられる自作コードと、保守状況、ライセンス、既知の脆弱性、推移依存、実行時と配布物への影響を比べる。
- **理由**：依存関係は実装量を減らす一方、更新、互換性、供給網、起動、配布に継続的な負担を加える。
  知名度や導入時の短さだけでは、その利点と負担の釣り合いを判断できない。

## 単純さ（Simplicity）

### 現在の要求に必要な仕組み

- **指針**：実在しない差し替えのためのインターフェース、呼び出しが一つだけの委譲関数、使われない設定、将来用の分岐を足さない。
  抽象化には、隠す判断または繰り返し発生する変更があることを求める。
- **理由**：仕組みを一つ増やすたびに、名前、入口、テスト、変更時の選択肢が増える。
  将来の要求が届く前には正しい境界を知れないため、先回りした仕組みは誤った結合を固定しやすい。

### 構造変更と振る舞いの変更を分ける

- **指針**：名前変更、移動、補助関数の抽出、条件の並べ替えなど、振る舞いを保つ構造変更（structural change）と、観測できる結果を変える変更（behavioral change）を分ける。
  構造変更と振る舞いの変更は別のコミットにし、可能であれば Pull Request も分ける。
  同じ Pull Request に含める必要がある場合は、既存テストが通る構造変更のコミットを先に置き、その後に振る舞いを変更する。
- **理由**：構造と振る舞いを同時に変えると、差分から意図を分けられず、失敗が移動によるものか新しい判断によるものかを特定しにくい。
  コミットを分ければ、レビュー、原因調査、差し戻しで構造変更と振る舞いの変更を独立して扱える。
