# テスト方針

テストは、仕様のどの振る舞いを、どの境界から、どの依存を実物として確かめるかで選ぶ。呼び名だけで水準を決めず、狭く決定的なテストを厚くし、外部プロセスとブラウザーを使うテストは下の水準では検出できない接続に限る。

| 水準 | 目的 | 境界と実物にするもの | 使いどころ |
| --- | --- | --- | --- |
| 単体 | 業務規則の判定とユースケースの分岐を短時間で確かめる | 1 パッケージまたは 1 モジュール。時刻、乱数、永続化、通知は明示した入力またはポートにする | 状態遷移、入力の検証、ポリシーの判定 |
| アダプター統合 | ポートの契約と具象アダプターの意味を確かめる | HTTP ハンドラー、メモリアダプター、PostgreSQL アダプターなど、対象の境界だけを実物にする | 直列化、SQL、HTTP 変換、永続化の往復 |
| 受け入れ | 規範シナリオを呼び出し側から観測する | 振る舞いを観測できる最も狭い公開境界 | `REQ-*` の正常系、代替経路、拒否が残した無作用 |
| E2E | 正式な外部入口から最終効果までの実配線と、必要ならブラウザー固有の挙動を確かめる | 設定、構成、API、経路制御、アダプター、必要な依存プロセス、ブラウザー | 利用者経路、外部送信、永続状態、Cookie、リダイレクト、同一オリジン、画面遷移、ローカライズ |
| 運用検証 | 配備資材と運用目標を確かめる | Kubernetes のレンダリング、監視規則、負荷生成、復元訓練 | スキーマ収束、容量受入れ、アラート、復旧 |

テスト名またはそれを実装するコードに、対応する `REQ-*`、規範 ID、脅威 ID を記す。Acceptance RED、Unit RED、主要ユースケース、拒否の無作用、プロパティテストの適用条件は [仕様先行の開発ワークフロー](specification-first-workflow.md) が定める。

実行するタスクは `mise tasks` から選ぶ。E2E を追加するときは、単体、アダプター統合、受け入れのいずれでも同じ失敗を検出できない理由をテストまたは work item に残す。

## 主要ユースケース

機能または標準対応の主要ユースケースは、その対応を実装済みと判断するために成功しなければならない中心的な利用経路である。入力の受理、列挙値の妥当性、成功ステータスだけを結果にせず、`REQ-*` または `standards.md` の規範 ID と、利用者、永続状態、外部境界のいずれかから観測できる最終結果を対にする。全分岐を主要ユースケースにする必要はなく、代替経路と拒否は仕様上のリスクに応じた水準へ置く。

主要ユースケースは単体テストと E2E テストの二つで固定する。単体テストは、変更するドメイン規則またはユースケースの分岐を公開されたモジュール境界から実行し、戻り値だけでなく状態遷移または外へ出す効果を表明する。E2E テストは、製品が対応すると宣言する正式な入口から開始し、対象機能を選ぶ設定、構成、アダプター、経路制御を迂回せず、最終結果を表明する。外部サービスをテストダブルにする場合も、送信先、方式、本文など、この製品が境界へ出した効果を検査する。

二つのテストは異なる故障を受け持つ。単体テストは内部判断を壊した代表的な誤実装を検出し、E2E テストは配線を外すか最終効果を無作用にした誤実装を検出する。直接構築した下位部品のテスト、行の実行、要求 ID の字面だけでは実配線の証拠にならない。完了時には、各主要ユースケースについて Unit RED と E2E RED を観測し、二種類の誤実装を実際に与えて対応するテストが失敗した結果を残す。

## テストダブル

どのテストダブルを選ぶかは、置き換える依存の効果を後から読み戻せるかで決まる。

効果を読み戻せる依存、すなわちポートとその永続化実装は、契約を実際に満たすフェイクで置き換える。`db_memory` の各実装がこれにあたる。この場合、表明するのは呼ばれ方ではなく読み戻した状態である。読み戻せる状態がありながら呼び出し回数を数えると、テストが実装の呼び出し方に縛られ、振る舞いを変えないはずのリファクタリングで落ちる。

効果を読み戻せない依存では、送り出した呼び出しそのものが観測できる唯一の効果になる。たとえば `fetch`、`navigator.credentials`、`navigator.clipboard`、`URL.createObjectURL`、`window.location`、外部の HTTP 相手、SMTP 送信、そして呼び出されたことだけが結果であるコールバック引数（React の `onSubmit`、`onChange` の類）がこれにあたる。ここでは呼び出しを記録するダブルを置き、回数と引数を表明してよい。表明の対象は、その境界を越えて出ていく値、つまり要求先、方式、本文であって、内部の何がそれを組み立てたかではない。フロントエンドの `mock()` と `spyOn()` の用法はこの型である。

回数そのものが仕様である場合は、読み戻せる依存でも回数を表明する。再試行の打ち切り、バッチの分割、キャッシュの命中、遮断器の閾値がこれで、「何回呼ばれたか」は実装の都合ではなく確かめるべき振る舞いである。`backend/shared/resilience` の再試行と `backend/datakeys` の再暗号化のテストがこの型である。この例外に寄りかかる前に、回数が仕様に書かれているかを確かめる。書かれていないなら、それは実装の呼び出し方である。

戻り値そのものが試験条件である依存、すなわち時刻、乱数、識別子の生成は、固定値を返すスタブでよい。これらは [仕様先行の開発ワークフロー](specification-first-workflow.md) が要求するとおり、ダブルを差し込むのではなく明示した入力またはポートとして受け取る。

Go 側にはモック生成ライブラリを入れていない。テストダブルは手書きで、置き換える対象の意味に合わせて書く。この状態を維持する。生成されたモックは、上の区別を利用者に意識させないまま呼び出し表明を既定にしてしまう。

### メモリアダプターと PostgreSQL アダプターの同値性は保証されていない

永続化を持つパッケージの多くは `db_memory` と `db_postgres` の 2 実装を対で持つが、両者が同じ振る舞いをすることを保証する共有の契約テストは存在しない。両者のテストは独立に書かれており、対象も件数も対応していない。したがって「メモリアダプターで通るテストは PostgreSQL アダプターでも通る」とは言えず、上位の水準でメモリアダプターをフェイクとして使ったテストは、PostgreSQL 固有の意味（トランザクション、一意制約、NULL と空文字列の区別、時刻の精度、並び順）について何も述べていない。

当面の扱いは、永続化の意味そのものを確かめるテストをアダプター統合の水準に置き、`db_postgres` を実物にすることとする。両実装を同じ契約テストへ通すことは未着手の負債である。
