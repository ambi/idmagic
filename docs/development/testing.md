# テスト方針

テストは、仕様のどの振る舞いを、どの境界から、どの依存を実物として確かめるかで選ぶ。
呼び名だけで水準を決めず、狭く決定的なテストを厚くし、外部プロセスとブラウザーを使うテストは下の水準では検出できない接続に限る。
いつ何を実行するかは[検証の進め方](specification-first-workflow.md#検証の進め方)、この文書はどのテストで何を判定するかを定める。

| 水準 | 目的 | 境界と実物にするもの | 使いどころ |
| --- | --- | --- | --- |
| 単体 | 業務規則の判定とユースケースの分岐を短時間で確かめる | 1 パッケージまたは 1 モジュール。時刻、乱数、永続化、通知は明示した入力またはポートにする | 状態遷移、入力の検証、ポリシーの判定 |
| アダプター統合 | ポートの契約と具象アダプターの意味を確かめる | HTTP ハンドラー、メモリアダプター、PostgreSQL アダプターなど、対象の境界だけを実物にする | 直列化、SQL、HTTP 変換、永続化の往復 |
| 受け入れ | 規範シナリオを呼び出し側から観測する | 振る舞いを観測できる最も狭い公開境界 | `REQ-*` の正常系、代替経路、拒否が残した無作用 |
| E2E | 正式な外部入口から最終効果までの実配線と、必要ならブラウザー固有の挙動を確かめる | 設定、構成、API、経路制御、アダプター、必要な依存プロセス、ブラウザー | 利用者経路、外部送信、永続状態、Cookie、リダイレクト、同一オリジン、画面遷移、ローカライズ |
| 運用検証 | デプロイの構成ファイルと運用目標を確かめる | Kubernetes のレンダリング、監視規則、負荷生成、復元試験 | スキーマ収束、キャパシティ受入れ、アラート、復旧 |

規範の被覆を主張する引用は[規範 ID の参照](specification-first-workflow.md#規範-id-をテストから参照する)に従う。
脅威 ID も対応するテストへ記す。
作業種別とリスクに応じた証拠の適用条件は[証拠の要件](specification-first-workflow.md#証拠の要件)が定める。

実行するタスクは `mise tasks` から選ぶ。
E2E を追加するときは、単体、アダプター統合、受け入れのいずれでも同じ失敗を検出できない理由をテストまたは work item に残す。

## 検証結果の区分

検査が終了コード 0 を返しても、対象のすべてが検証済みになるとは限らない。
静的検査は操作ごとに `verified`（解析できた範囲で差分なし）、`unverified`（解析対象外または部分解析）、`failed`（差分または検査失敗）を保存する。
未検証の操作が残る検査では件数を必ず表示し、`--list-unresolved` で理由を列挙する。
検証済みという区分も、その検査が比較する契約の範囲を越える保証には使わない。

テストへの参照、実行結果、検出能力は別の事実として扱う。
`check-spec` の規範 ID の検査は、ソースに引用が存在することだけを確かめる。
`test-go`、`test-go-race`、`test-go-package`、`test-go-test` は Go の JSON イベントから成功、失敗、スキップ、未実行を記録する。
規範を引く Go テストは package と関数名で実行結果へ結び付け、子テストのスキップや未終了を親の成功へ昇格させない。
これらのタスクは `-count=1` で結果キャッシュを無効にし、今回の実行を観測する。
ファイルの外の表、Go 以外のテスト、変更耐性の調査は、この Go 実行結果から推定しない。

PostgreSQL を起動できない環境でのスキップは、手元では未検証として残す。
`VERIFICATION_REQUIRE_DB=1` を指定すると、pgtest を使うパッケージの起動失敗、スキップ、未実行を失敗にする。
CI はこの必須モードを指定する。
選択したパッケージのテストタスクは、その実行対象についてだけ判定し、全体の DB 検証を代行しない。

### 変更操作の代替証拠

全体の Go テストタスクは、基準リビジョンから作業ツリーまでの製品の変更を調べる。
基準は `VERIFICATION_BASE_REVISION`、未指定なら上流ブランチ、上流がなければ `main` とする。
Go の変更は変更モジュールと、そのモジュールを推移的に使う側の操作を保守的に選ぶ。
未解決の経路は選択から落とさず、shared、構成入口、Go の依存宣言、TypeSpec、DB スキーマの変更は全操作を選ぶ。
テスト、文書、tools だけの変更では製品の変更操作を増やさない。
関数単位の影響を確定する解析ではないため、同じモジュールの無変更の操作も対象になり得る。

解析が不完全な変更操作には、同じ実行で成功した契約テストを要求する。
Go テストの直上に、操作 ID と観測する契約を次の形で記す。
本文のディレクティブが対象にするのは契約本文と状態コードの両方であり、単なる成功ステータスの表明には付けない。
静的検査で検出した違反を、このディレクティブで免除することはできない。

```go
//verify:operation CreateThing: 要求と成功応答の本文、拒否応答と状態コード
func TestCreateThingContract(t *testing.T) {
```

`mise run check-operation-references` は、コロンや観測内容の欠落、未知の操作 ID、直上のテストへ結び付かない宣言をファイルと行番号付きで診断する。
この検査は参照収集器と同じ処理を使い、`mise run check` と `mise run verify` に含まれる。
受理した参照数は、本文の表明の正しさやテストの実行成功を示さない。

この引用は、規範 ID を引く `//spec:covers` と独立に記す。
対応テストが未実行、失敗、スキップ、子テストの未終了の場合は代替証拠にしない。
成功と拒否の観測を複数のテストへ分ける場合は、同じ操作を宣言したすべてのテストの成功を要求する。
一つの成功で、ほかの対応テストの未実行、失敗、スキップを補うことはできない。
未解析の操作と読む候補のテストファイルは `mise run report-contract-evidence` で棚卸しできる。
この一覧の経路やファイル名の一致は候補にすぎず、本文の観測やテストの成功を示さない。
関係のない操作の解析対象外を理由に、検証できる範囲の実行まで停止しない。

変更する製品ファイルと参照不足を合わせて調べるときは、次の照合を使う。
`--target` は予定するファイルをリポジトリ相対パスで指定し、複数なら繰り返す。
まだ編集していないファイルも Git の差分へ加えて影響を選ぶため、着手時にも使える。

```console
mise run report-contract-evidence -- --changed --base-revision main --target backend/shared/security/token.go
```

結果は `.verification/contract-evidence-preflight.json` に保存し、比較基準、実際の変更ファイル、予定するファイル、影響する未解析操作とテスト参照、参照のない操作を示す。
影響の選択には全体の Go 検証と同じモジュール依存の解析を使い、所有元が分からない経路も候補に残す。
この照合はテストを実行せず、受理した宣言があっても実行証拠は `not-collected` のまま示す。
不正な参照の場所と理由は `check-operation-references` で調べる。
引数なしの棚卸しは `.verification/contract-evidence-inventory.json` へ出力する。

### 結果の参照

結果は Git リビジョン、追跡ファイルと未追跡ファイルの fingerprint、基準リビジョン、コマンド、DB モードとともに `.verification/` へ保存する。
生の Go イベントも JSON Lines で保存する。
実行中に入力が変われば検証を失敗にし、過去の結果を現在の証拠へ流用しない。
`mise run report-verification` は全体の race テストの結果を表示し、現在の入力と異なる結果を `stale` と明示する。
別のタスクの結果は `mise run report-verification -- .verification/test-go-package.json` のように指定する。
変更耐性は別に収集するため、通常の実行結果では `not-collected` と表示する。
その証拠は[ミューテーションテスト](#ミューテーションテスト)に従って作業項目へ残す。

## 主要ユースケース

機能または標準対応の主要ユースケースは、その対応を実装済みと判断するために成功しなければならない中心的な利用経路である。
入力の受理、列挙値の妥当性、成功ステータスだけを結果にせず、`REQ-*` または `standards.md` の規範 ID と、利用者、永続状態、外部境界のいずれかから観測できる最終結果を対にする。
全分岐を主要ユースケースにする必要はなく、代替経路と拒否は仕様上のリスクに応じた水準へ置く。

主要ユースケースのテストは、検出する故障から境界を選ぶ。
作業項目の `primary_use_cases` の `boundary` も、この選び方で決める。
業務規則は公開されたモジュール境界から状態と外向きの作用を観測し、アダプター固有の変換は統合テスト、正式な入口の配線は E2E で観測する。
独立した故障を検出する検査を残し、同じ規則の全ケースを単体と E2E の両方へ転記しない。
単体テストは、公開されたモジュール境界からドメイン規則またはユースケース分岐を実行する。
E2E テストは、正式な外部入口から始め、機能を選択する設定、構成、アダプター、ルーティングを含める。
行カバレッジを最終結果の表明の代わりにしない。
本番が設定で提供元またはハンドラーを選ぶ場合、そのコンポーネントを直接構築したテストは E2E の証拠にしない。
外部サービスのダブルは、送信先、方式、本文など製品が境界へ出した値を記録して検査する。

具体的な入力と期待結果は、[実行可能な具体例](../formats/specification-format.md#実行可能な具体例と派生表示)として文書表示と共有できる。
期待結果は仕様から独立に決め、製品コードから計算しない。
同じポートの複数実装には共有契約を実行する。
重複を除く変更では、被覆だけでなく、拒否後の無作用と宣言した故障の検出能力も比較する。

### 組み立てと経路差

必須依存の配線を変えるときは、本番と共通の組み立て部品から成功経路を実行し、必要な保存、投入、イベントを観測する。
拒否だけを通す部分的なフィクスチャは、成功経路の未配線を隠すため、その成功の証拠には使わない。
構築時の型検査で省略を拒否できない依存は、必須の配線を外す故障を、その配線を通る最小の境界で検出する。
必須引数の省略が型検査で止まる場合は、その同じ省略を再現する実行時のテストを増やさない。
拒否時の保存とイベントの無変更は、成功時の作用とは独立して観測する。

HTTP の契約を変えるときは、要件と TypeSpec から同じ操作の方式、デフォルトと realm、バインディング、入力の所在を列挙し、今回の故障が生じる経路を選ぶ。
同じ規則の全ケースを経路ごとに複製せず、アダプター固有の変換と正式な配線の故障を区別する。

| 差の種類 | 観測する最終結果 | 検出する故障の例 |
| --- | --- | --- |
| GET と POST、query と form | 要求した経路の状態コード、Content-Type、本文と state の返送 | GET だけ成功し、POST の form state が読まれない |
| 認可エラーの HTTP への変換 | 実際の拒否応答の状態コードとエラー本文、拒否後の無作用 | 認可拒否が汎用エラーへ変換され、500 になる |
| バインディングと署名後の直列化 | 返送された表現から取り出した署名の検証と対象の束縛 | 署名を生成した後の整形で、返送した署名が無効になる |
| デフォルトと realm のルート、成功時の生成器 | 選択した構成入口から返る応答と保存結果 | 別経路の未配線や、部分的なフィクスチャの生成器の省略 |

宣言と派生表示をまたぐ参照や正規化を変えるときは、一次情報から派生先へ到達する最小のテストを置く。
句読点、重複、インライン記法など、変換で違いが消える入力を選び、参照の到達先を表明する。
それぞれの正常例だけを検査しても表現間の解釈の差は検出できないため、共通の判断は一つの処理へ集める。

## レスポンスだけでは副作用を証明できない場合

大半の正常経路では、レスポンスを表明すれば十分である。
作成したレコードをボディとして返す、発行したトークンを次の呼び出しで使えるなど、レスポンスを作用から導出しているため、レスポンスを読むテストが作用も間接的に読んでいる。

この関係が成り立たない処理もある。
観測可能な応答を作用から導出せず、作用と並ぶ別の分岐で生成する場合は、レスポンスが正しくても作用を誤り得る。
そのような処理は、一つではなく二つの表明で検査する。

1. **呼び出し元が観測する内容**：ステータスとエラーの種類、または呼び出し元へ返す正常結果。
2. **実際に起きた内容**：状態を読み戻し、レコードを作成していないこと、値が以前のままであること、イベントを発行したことまたは発行していないことを表明する。

重要でありながら抜け落ちやすいのは、二つ目の表明である。

最も多いのは、**拒否する統制**である。
認可、テナント境界、CSRF と origin、スコープ、fail-closed の分岐が該当する。
ガードは独立した分岐で 403 を書くため、レスポンスだけを検査するテストは、「拒否」と書いてから操作を続行する統制でも通る。
レスポンスが報告しない書き込みや監査イベントも同じ構造である。
書き込み、発行、失効、スケジュールを行う各処理について、それが止まってもテストが通るかを確認する。

その処理に対応するシナリオをテストから参照し、仕様とテストを照合できるようにする。
拒否の有無にかかわらず、`mise run check` はすべての規範 ID がいずれかのテストから参照されることを求める。

呼び出し側がガードとして使う補助関数（`if err := guard(...); err != nil` の形で呼ぶもの）は、戻り値で拒否を報告する。
レスポンスを書いてからエラーを返す。
レスポンスの書き込みが返した値は nil であり、呼び出し側が処理を続けてしまうため、その値を返さない。
`mise run check` はこの形を拒否し、ガードとレスポンスの間にある補助関数も追跡する。
`writer` の戻り値を返すラッパーは、同じ欠陥が一回の呼び出しだけ離れた形である。

## Go の通常テストと race 検査

Go のテスト対象と `-race` の有無は別々に判断する。
純粋な計算や局所的な分岐を変え、共有状態や並行実行へ影響しないと確認できる場合は通常テストを使う。
`mise run test-go-test -- <package> <test>` は通常テストを実行し、テスト名へ `'.*'` を指定すればそのパッケージ全体を検査できる。
共有する可変状態、goroutine、同期、キャッシュ、並行リクエストの処理を変える場合や、その影響が不明な場合は race 検査を選ぶ。
`test-go-package` と `test-go-changed` は常に `-race` を付け、`test-go-race` は Go 全体を検査する。
race 検査でも、問題となる並行経路を実行するテストが必要である。
通常構成と race 構成のビルドキャッシュは別なので、race 検査が必要な局所検査にはその構成を使う。
キャッシュを揃える目的だけで、race 検査の必要性を決めない。

## 性質、ファジング、変異、特性化

例示テストは、既知の利用経路と拒否を具体的に固定する。
一方で、入力の組合せや境界条件を網羅する道具ではない。
対象の故障モデルに応じて、プロパティテストとファジング、ミューテーションテスト、[特性化テスト](specification-first-workflow.md#特性化テスト)を追加する。
テスト水準は手法の名前ではなく、どの公開境界と依存を実物にするかで選ぶ。

### プロパティテストとファジング

例ベースのテストは、分岐を書いた人と同じ問題の理解から書くため、その理解の盲点も引き継ぐ。
プロパティは仕様から記述し、誰も思いつかなかった事例を生成器が与える。

入力が信頼境界を越え、その入力について判断する前にデコード、解析、分割、正規化、比較を行う場合は、プロパティまたはファズ対象を使う。
同じく、既にこの検査を備えるライブラリを呼ばず手書きで解析する場合、エンコードとデコード、導出と検証、解析とシリアライズのように状態を往復する場合、一つの規則を複数の呼び出し箇所で言い換えている場合にも使う。
最後の場合は、ファズ対象を書くことで規則を一箇所へ集められる。
作用の編成、正しさがプロパティではなく方針で決まるワークフロー、正しさの判断にデータベースを必要とする処理には使わない。
被覆の割り当て目標は設けない。
ファズ対象の数は境界に従い、上流ですでに被覆している境界へ二つ目を置かない。

#### 判定基準

この検査の中心は判定基準である。
仕様から導いた不変条件、往復、順序、単調性、拒否後の無作用を判定基準に使う。
「panic しない」は判定基準にならず、すべてを受理するパーサーでも通ってしまう。
代わりに、次のいずれかを記述する。

- **往復**：正しく構築したものを受理し、それへ変更を加えたものを拒否する。
- **厳密性**：受理した値は、登録済みの値と正確に一致する。
  この条件だけでは、すべてを拒否する実装でも通るため、正当な入力を受理するという表明と組み合わせる。
  この組み合わせがない厳密性の検査は、強く見えても常に成立し得る空虚なテストになる。
- **構造上の上限**：展開後の大きさ、入れ子の深さ、セグメント数など、宣言した上限を超える入力を常に拒否する。
- **冪等性**：二回正規化しても結果が変わらない。

時間を判定基準にしない。
「N ミリ秒以内に返る」は、共有実行環境でも開発端末でも負荷によって数倍変動し、常に不安定な表明になる。
サービス拒否への耐性は構造上の上限として記述し、停止はファザー自体の検出に委ねる。
入力ごとに署名もしない。
ループ内で署名すると処理量が二桁から三桁下がり、探索が進まなくなるため、シードの段階で鍵と証明書を一度だけ構築する。
たとえばエンティティ参照を拒否するというように、入力によって変わらないプロパティはファズ対象ではなく表にする。

ファズ対象は HTTP `handler` ではなく解析する関数へ置く。
そうしなければ、失敗がルーティング、ミドルウェア、解析のどこで起きたか分からない。
作用は引数として渡す。
固定時刻、シードの段階で構築した鍵集合、検査対象ではないリプレイストアについて常に「初見」と報告するスタブなどが該当する。

#### 実行量

シードと保存したコーパスは通常のテストスイート内で実行し、所要時間をミリ秒に抑える。
この部分が日常的な価値を生む。
探索は独立した意図的な作業とし、変更対象に対して時間上限を設けてローカルで実行する。
一つのファズ対象には `mise run test-go-fuzz -- <package> <target> <time>`、一括実行には `mise run test-go-fuzz-all -- <time>` を使う。
探索を Pull Request のゲートへ入れない。
毎回異なる入力を試すため、いずれ発見内容と無関係な変更で失敗し、変更と無関係な理由で失敗するゲートは読まれなくなる。
クラッシュによって継続的に発生するコストはコーパスの項目である。
入力を最小化して名前付きの退行テストへ昇格し、生の発見を蓄積せず、同じ種類の入力を一項目へまとめる。

最後に、ほかのテストと同じく、現実的な誤実装を書いてファズ対象が検出することを確認する。
コード内で独立しているガードは、証拠でも分ける。
あるガードの事例を別のガードも検出する場合、最初のガードを削除しても結果が変わらず、表はそのガードについて何も示さない。
コスト検査を実行するための表が、前にある長さ検査によってすべて遮られ、変異の実行によって初めて表が空虚だと分かった事例がある。

### ミューテーションテスト

`mise run test-go-mutation -- <package directory>` は、一つの Go パッケージへ変異を加え、そのパッケージのテストで検出できなかった変異を報告する。
条件の否定、境界の移動、符号の反転、算術演算の変更といった構文上の空間を機械的に調べる。
一方、ツールは意味上の空間へ到達できず、この差は検出量の違いではない。
変異演算子は既存のトークンだけを書き換える。
増分同期を全件を正とする同期へ変えるループの追加、`switch` の `default` が返す値を置き換えて閉じた語彙を開く変更、読み取り専用列を書き込み可能にする列テーブルの変更、エクスポートがセルへ書く値の変更はできない。
これらは仕様が問題にする変異であり、手作業で加える。
ツールは構文を、手書きの障害モデルは意味を被覆する。

生き残った変異を読み、点数化しない。
検出率はテストを消すと上がることがあり（未被覆になった変異が分母から外れる）、閾値を設けると検出能力ではなく数値を上げるテストが増える。
障害モデルを読むときと同じように、生き残った変異を等価な変異と不足に分類し、両方を作業項目へ記録する。

生存した箇所は、本番入口からその入力と分岐へ到達できるかを、呼び出し元まで読んで確かめる。
本番から届かないゼロ値の補完、等価な変異、必要な観測の不足を区別し、未使用であることだけで等価と判定しない。
補完や分岐が仕様にない場合は、[仕様にない振る舞いの分類](specification-first-workflow.md#仕様にない振る舞いの分類)へ戻る。
変更していない行の不足と、今回変更した箇所の検出能力を分けて記録する。

ファジングの探索と同じく、ミューテーションテストは Pull Request のゲートへ入れない。
実行には数分かかり、固定費は検査対象のパッケージではなくワーカーごとにリポジトリ全体を複製することから生じる。
さらに、無関係な変更でも変異の集合が変わる。

#### 実行の引数

通常の調査は、対象のパッケージディレクトリを指定する。
デフォルトではワーカー数 2、5 種類の変異演算子、キャッシュなしで実行し、JSON の報告を一時領域へ書く。

```console
mise run test-go-mutation -- backend/idmanagement/group/domain
```

変更した行の検出能力だけを調べる場合は、実装前のリビジョンを比較基準として記録し、第 4 引数に報告のパス、第 5 引数にそのリビジョンを指定する。
変異を作る範囲だけを差分の行へ絞り、被覆の測定と基準のテストは対象パッケージ全体で実行する。
この結果から、変更していない行の検出能力は判断しない。
既存パッケージ全体の調査が必要なら、その理由と範囲を別に選ぶ。

```console
mise run test-go-mutation -- backend/oauth2/internal/handlers_http 2 off /tmp/idmagic-oauth-mutation.json main
```

同じ変更で生き残った変異を調べ直す反復に限り、第 3 引数へキャッシュファイルを指定する。
対象パッケージが import するパッケージを変更した後は、以前のキャッシュファイルを再利用しない。

```console
mise run test-go-mutation -- backend/idmanagement/group/domain 2 /tmp/idmagic-gomutants-cache.json
```

報告にある変異の安定した ID を指定して 1 件だけ再実行する場合は、キャッシュを使わない専用タスクを実行する。

```console
mise run test-go-mutation-mutant -- backend/idmanagement/group/domain '<mutant-id>'
```

ツールのバージョンを更新した後と、変更への耐性の証拠を作る前には、結果が分かっている固定の対象で、生存（`lived`）と構築不能（`not viable`）の分類を検算する。

```console
mise run check-go-mutation-tool
```

重い調査と集約検証の並行時に制限時間を超えた場合は、入力を保った単独再実行で、常に失敗する場合と区別してから制限の変更を判断する。

## テストダブル

どのテストダブルを選ぶかは、置き換える依存の効果を後から読み戻せるかで決まる。

効果を読み戻せる依存、すなわちポートとその永続化実装は、契約を実際に満たすフェイクで置き換える。
`db_memory` の各実装がこれにあたる。
この場合、表明するのは呼ばれ方ではなく読み戻した状態である。
読み戻せる状態がありながら呼び出し回数を数えると、テストが実装の呼び出し方に縛られ、振る舞いを変えないはずのリファクタリングで落ちる。

効果を読み戻せない依存では、送り出した呼び出しそのものが観測できる唯一の効果になる。
たとえば `fetch`、`navigator.credentials`、`navigator.clipboard`、`URL.createObjectURL`、`window.location`、外部の HTTP 相手、SMTP 送信、そして呼び出されたことだけが結果であるコールバック引数（React の `onSubmit`、`onChange` の類）がこれにあたる。
ここでは呼び出しを記録するダブルを置き、回数と引数を表明してよい。
表明の対象は、その境界を越えて出ていく値、つまり要求先、方式、本文であって、内部の何がそれを組み立てたかではない。
フロントエンドの `mock()` と `spyOn()` の用法はこの型である。

回数そのものが仕様である場合は、読み戻せる依存でも回数を表明する。
再試行の打ち切り、バッチの分割、キャッシュの命中、遮断器の閾値がこれで、「何回呼ばれたか」は実装の都合ではなく確かめるべき振る舞いである。
`backend/shared/resilience` の再試行と `backend/datakeys` の再暗号化のテストがこの型である。
この例外に寄りかかる前に、回数が仕様に書かれているかを確かめる。
書かれていないなら、それは実装の呼び出し方である。

戻り値そのものが試験条件である依存、すなわち時刻、乱数、識別子の生成は、固定値を返すスタブでよい。
[非決定要因の入力またはポート](coding-style.md#入力またはポートとして受け取る非決定要因)として受け取る。

Go 側にはモック生成ライブラリを入れていない。
テストダブルは手書きで、置き換える対象の意味に合わせて書く。
生成されたモックは、上の区別を利用者に意識させないまま呼び出し表明をデフォルトにしてしまうので、この状態を維持する。

### メモリアダプターと PostgreSQL アダプターの共有契約

同じ永続化ポートを実装する `db_memory` と `db_postgres` は、モジュールごとの `testing_contract` パッケージに置いた同じ契約本体を実行する。
契約本体は、保存した値の読み戻し、存在しない値、テナント分離、並び順、期限、単回消費、一意性、リビジョンの衝突など、そのポートが呼び出し側へ示す意味を検査する。
時刻を保存する契約では、PostgreSQL の分解能に切り捨てた入力を使い、読み戻した値の精度も共通の振る舞いとして扱う。

共有契約は PostgreSQL 固有の検査を置き換えない。
トランザクション境界、外部キーとカスケード、SQL のページング、NULL と空文字列の保存表現、暗号化された列、複数のレプリカ、メンテナンス処理は `db_postgres` のテストへ残す。
メモリ上のキャパシティ上限や退避規則など、`db_memory` だけが持つ性質も同じである。

`backend/shared/storage` はこの規則の対象外である。
同じ名前のディレクトリを持つが、メモリ側はキーセット方式のページングの純粋関数、PostgreSQL 側は接続と SQL 実行の基盤であり、両者が実装する共通ポートがない。
