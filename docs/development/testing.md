# テスト方針

テストは、仕様のどの振る舞いを、どの境界から、どの依存を実物として確かめるかで選ぶ。呼び名だけで水準を決めず、狭く決定的なテストを厚くし、外部プロセスとブラウザーを使うテストは下の水準では検出できない接続に限る。

| 水準 | 目的 | 境界と実物にするもの | 使いどころ |
| --- | --- | --- | --- |
| 単体 | 業務規則の判定とユースケースの分岐を短時間で確かめる | 1 パッケージまたは 1 モジュール。時刻、乱数、永続化、通知は明示した入力またはポートにする | 状態遷移、入力の検証、ポリシーの判定 |
| アダプター統合 | ポートの契約と具象アダプターの意味を確かめる | HTTP ハンドラー、メモリアダプター、PostgreSQL アダプターなど、対象の境界だけを実物にする | 直列化、SQL、HTTP 変換、永続化の往復 |
| 受け入れ | 規範シナリオを呼び出し側から観測する | 振る舞いを観測できる最も狭い公開境界 | `REQ-*` の正常系、代替経路、拒否が残した無作用 |
| E2E | 独立した構成要素の配線とブラウザー固有の挙動を確かめる | ブラウザー、UI、API、経路制御、必要な依存プロセス | Cookie、リダイレクト、同一オリジン、画面遷移、ローカライズを含む利用者経路 |
| 運用検証 | 配備資材と運用目標を確かめる | Kubernetes のレンダリング、監視規則、負荷生成、復元訓練 | スキーマ収束、容量受入れ、アラート、復旧 |

テスト名またはそれを実装するコードに、対応する `REQ-*`、規範 ID、脅威 ID を記す。Acceptance RED、Unit RED、拒否の無作用、プロパティテストの適用条件は [仕様先行の開発ワークフロー](specification-first-workflow.md) が定める。

実行するタスクは `mise tasks` から選ぶ。E2E を追加するときは、単体、アダプター統合、受け入れのいずれでも同じ失敗を検出できない理由をテストまたは work item に残す。
