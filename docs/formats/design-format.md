# 設計フォーマット

この文書は、設計の一次情報文書を書くときに従う形式を定める。
設計は、仕様が外へ約束することを、どの構造と仕組みで実現するかを書く。
*(checked)* と記した規則への違反はビルドを失敗させ、それ以外はレビューで判断する。
仕様の形式は[仕様フォーマット](specification-format.md)、どの内容をどの文書に書くかと `docs/` の配置は[文書ガイド](documentation-guide.md)が定める。
設計の記述は ISO/IEC/IEEE 42010 のアーキテクチャ記述と arc42 の章立てに倣う。
各規則を選んだ理由は[フォーマットの理由](../development/format-rationale.md#設計フォーマット)に書く。

## 1. 設計領域

システム設計は九つの設計領域を次の順序で構成する *(checked)*。
モジュール設計は共通設計をデフォルトにし、固有設計とデフォルトからの例外だけを同じ順序で記述する *(checked)*。
順序は、実現対象（アプリケーション、データ、インフラストラクチャ）、複数の実現対象へ作用する領域、検証の順である。

| 設計領域 | システム | モジュール | 書くこと |
| --- | --- | --- | --- |
| アーキテクチャ設計 | `architecture/` | なし（`README.md` の主な流れと設計の要点） | 文脈と範囲、制約、解決戦略、構成要素、実行時の流れ、配置 |
| アプリケーション設計 | `application/` | `application.md` | API と UI の方式、バックエンドとフロントエンドの構成 |
| データ設計 | `data/` | `data.md` | Aggregate と永続化、保持と削除、排他 |
| インフラストラクチャ設計 | `infrastructure/` | `infrastructure.md` | 実行基盤とネットワーク |
| セキュリティ設計 | `security/` | `security.md` | 認可の適用、秘密情報、脅威への対応 |
| 信頼性設計 | `reliability/` | `reliability.md` | 障害の検知、症状と直し方、復旧 |
| 性能設計 | `performance/` | `performance.md` | 品質要件を満たす方式、キャパシティの見積もり |
| オブザーバビリティ設計 | `observability/` | `observability.md` | ログ、指標、トレース |
| 検証設計 | `verification/` | `verification.md` | 品質要件と統制の確かめ方 |

設計判断とリスクは設計領域ではなく、アーキテクチャ記述に含める設計の記録である。
arc42 は設計判断（第 9 章）とリスクと技術的負債（第 11 章）を、ISO/IEC/IEEE 42010 は判断とその根拠を、どちらもアーキテクチャ記述の一部とする。

| 設計の記録 | システム | モジュール | 書くこと |
| --- | --- | --- | --- |
| 設計判断 | `architecture/decisions.md` | `decisions.md` | 代替案を比べた重要な判断 |
| リスク | `architecture/risks.md` | `risks.md`（任意） | 既知の欠陥、技術的負債、受容したリスク。脅威は脅威モデルに置く |

- 複数の機能が共有する仕組みは、その仕組みを一つの機能として設けた機能仕様の「実現方式」（CSV の転送など）か、最も関係の深い設計領域の文書の節に書く。一つの設計領域に収まらない仕組みのために、任意の名前の文書を置かない *(checked)*。
- 下の階層は、上の階層からの割り当てと例外だけを書く。同じ内容を二つの階層に書き写さない。

**素直な形をデフォルトにする。**
モジュールの内部は、開発者と運用者にとって最も素直な形（[バックエンド設計](../design/application/backend.md)の層と配置、機能とコードの名前の対応、共通設計）をデフォルトとし、文書に書かない。
そうでない構造を選んだときだけ、その構造と理由を書く。
外から観測できる振る舞いは、このデフォルトによらず、機能仕様と TypeSpec が漏れなく定める。

**設計領域の索引。**
システムの `docs/design/README.md` は九領域すべてを索引し、[共通設計の適用範囲](../design/README.md#共通設計の適用範囲)を定める。
モジュールの索引は、モジュールの `README.md` の最後の節 `## 文書` に置き、共通設計と異なる設計を書いた文書と、実現対象がない領域だけを並べる *(checked)*。
モジュールはアーキテクチャ設計の文書を持たない。モジュールの構成はシステムの論理アーキテクチャが割り当て、外から見た姿と主な流れは `README.md` が示す *(checked)*。
記載のない領域は共通設計に従い、実現対象がないと推定しない。
差分がなければモジュールの表は省略でき、九行の再掲を求めない。
モジュールに `<area>.md` の領域文書がある場合は、その領域の行から参照する *(checked)*。
既存の領域文書を索引から消して、共通設計への継承として隠すことはできない。

索引の列は `設計領域 | 文書 | 内容` とする *(checked)*。
設計領域は上の語彙を使い、同じ領域を重ねず、記載した領域の順序を保つ *(checked)*。
文書の列には、その領域を書いた節へのローカル Markdown リンクを、リンク先の題名を文字にして置く。
実現対象がない領域は文書の列を `—` にし、内容の列に理由を書いてリンクを置かない *(checked)*。
参照先のファイルと節の存在を検査する *(checked)*。
モジュールの `## 文書` の節は、索引の表の下に、設計領域以外のモジュールの文書（`glossary.md`、`standards.md`、`quality.md`、`decisions.md`、`risks.md` のうち置いたもの）を、この順に `文書 | 内容` の表で並べる。
モジュールの直下に置いた文書は、すべてこの節から辿れなければならない *(checked)*。

```markdown
## 文書

| 設計領域 | 文書 | 内容 |
| --- | --- | --- |
| データ設計 | [Demo のデータ](data.md#集約) | Aggregate とその関係 |
| 信頼性設計 | — | 依存先を持たず、障害の扱いは共通設計に従う |

| 文書 | 内容 |
| --- | --- |
| [用語集](glossary.md) | このモジュールでの語義 |
| [設計判断](decisions.md) | 代替案を比べた重要な判断 |
```

**品質要件の割り当て。**
宣言済みの `SLO-*` と `CAP-*` は、論理アーキテクチャの `品質要件 | 担当機能 | 設計 | 検証` の表に一度だけ割り当てる *(checked)*。
ID ごとに一行とし、複数の担当機能は同じ行へ記載する。
品質要件の列は宣言元の ID へのリンク、残る列は担当文書の節へのリンクを置く *(checked)*。
宣言した ID の割り当ての欠落、重複、未宣言の ID、参照の欠落を拒否する *(checked)*。
数値と測定境界は宣言元に保ち、割り当ての表へ複製しない。
数値を持たない品質特性の要件は宣言元が参照する共通設計と検証に従う。
設計と検証への参照は達成の証拠を意味しない。
実装状況と実測の有無は担当文書に記載する。

## 2. 設計ガイドライン

- `docs/design/application/design-guidelines.md` に、モジュールの境界、インターフェース、seam、アダプター、型の担当、作用、エラーに関するシステム全体の評価基準を書く。
- モジュールディレクトリに独自の写しを置かない。

## 3. 重要な設計判断（`decisions.md`）

- 代替案を比べた判断、成立条件や再検討する条件が要る判断だけを置く。それ以外の判断は、要件の判断の欄に書く。
- 判断ごとに H2 を置き、見出しには側面（`不変条件`、`失敗処理` など）ではなく判断そのものを書く。
- 各判断の下に、次の H3 をこの順で置く *(checked)*。

| 節 | 内容 |
| --- | --- |
| 背景 | 判断を迫った状況と制約 |
| 決定 | 何を決めたか |
| 検討した代替案 | 案、利点、欠点、採らない理由の表 |
| 結果と再検討の条件 | 決定によって何が成り立ち、何を諦めたか。どうなったら見直すか |
| 関連する要件 | この判断が正当化する要件の ID と、機能仕様へのリンク |

- 変更の経緯は work item に残し、この文書には現在の判断だけを書く。

## 4. 機能の設計（機能仕様の「実現方式」）

- 一つの機能に閉じた設計は、別のファイルにせず、機能仕様 `features/<feature>.md` の最後の節 `## 実現方式` に書く *(checked)*。節は任意であり、設計領域の索引は置かない。
- 機能について知るべき規則と仕組みを一つのファイルで読めるようにするため、仕様と設計を同じファイルの節で分ける。この考え方はモジュールの `README.md` と同じであり、仕様と設計の区別は[文書ガイド](documentation-guide.md#仕様と設計)が定める。
- 書くのは、コードから読み取れない仕組みと、壊れたときの直し方だけとする。H3 には設計領域の名前を使う。規則（`REQ-*`）はこの節に置かない。
- ファイルとパッケージの列挙、実装が踏む手順の説明は書かない。
- 製品が守る値や条件（有効期間の上限、件数の上限など）は、要件として機能仕様に書く。
- 内部設計には、変更履歴、計画、外部標準の要約、受け入れ例、リクエストとレスポンスの形、カラムと索引の定義、権限の割り当て、すべてのモジュールが従う規則を書かない。それぞれ、work item、`standards.md`、例の付録、TypeSpec、スキーマファイル、`docs/design/security/authorization.md`、システム文書で扱う。

## 5. 認可

- 認可は `docs/design/security/authorization.md` にまとめ、各モジュールの節に分割しない。プリンシパルの種類、スコープの名前空間、テナント境界、判断できない場合の規則を書く。
- 各モジュールが自身の操作について下した判断は、その要件の判断の欄に、代替案を比べた判断はそのモジュールの `decisions.md` に置く。
- TypeSpec には、API が認証付きか公開かと、操作ごとの権限またはスコープの注釈を付ける。
- 独自の認可 DSL を追加しない。きめ細かな認可は、テストを伴うアプリケーションの振る舞いとする。
- 操作とスコープの対応を文章で言い換えない。文章には、注釈で表せない内容（境界が受け入れるロールとプリンシパルの種類、レスポンスに含めない内容、権限の伝播、判断不能な場合の処理）を書く。

## 6. 脅威モデル

- `docs/design/security/threat-model.md` に、信頼境界と各境界で信頼しないもの、資産、脅威ごとの行と対応する統制を書く。
- 各脅威には安定した ID と、統制の有無を区別する閉じた集合の状態を付ける。境界と分類は ID に組み込まず列にする。
- 統制のない行も同じ表に置き、修正するか受容するかと、受容する場合の再検討の条件を書く。
- 何も対応していない脅威と、背後に規範のない統制（手順、デプロイ要件など）が対応する脅威を、統制の列で区別する。
- 脅威を修正する work item をこの文書から参照しない。work item から脅威 ID を参照する。
- 一覧が網羅的ではないことと、見直しが必要になる条件を書く。
- 既存の統制識別子（要件、採用した標準など）を参照し、二つ目の識別子を作らない。
- 起こり得ることを書き、再現手順、具体的なパラメーター、未修正経路の詳細は書かない。

## 7. 図

- 図は、読者が知りたい関係を本文や表だけでは読み取りにくい場合に置く。全ページへの設置や図種ごとの採用は求めない。
- 既存の図で足りない点があれば、同じ問いに答える図を併設せず、その図を改善または置き換える。
- 図種と粒度は、読者の問いから次の表で選ぶ。

| 読者の問い | 図種 | 粒度 |
| --- | --- | --- |
| システムと、外部の人やシステムの関係 | C4 のシステムコンテキスト図。人、IdMagic、外部システムを C4 の要素で区別し、関係に目的を書く | IdMagic を一つの要素とし、内部のプロセスと経路は描かない |
| 実行単位の配置と通信、処理の分岐 | `flowchart` | 実行単位、または判断の分岐を要素とする |
| 通信や処理の順序、確定の前後 | `sequenceDiagram` | 順序を観測できる参加者を要素とする |
| テーブルの関係と多重度 | `erDiagram` | テーブルを要素とし、カラムを描かない |
| 状態遷移 | 状態遷移の表から生成する状態図 | 手書きしない |

- C4 モデルの階層は粒度の目安として使い、価値のある階層だけを描く。C4 の Container は Docker のコンテナではなく、この文書群の実行単位にあたる。
- Mermaid の C4 図は関係のラベルの位置を自動では避けないため、`UpdateRelStyle` の位置の調整で要素や線との重なりを除き、生成サイトの明色、暗色、拡大表示で確かめる。
