# 文書ガイド

この文書は、要件、設計、開発、運用の内容をどの文書へ書くかと、`docs/` の配置を定める。
仕様の記述規則は[仕様フォーマット](specification-format.md)、設計の記述規則は[設計フォーマット](design-format.md)、変更の計画と証拠は[作業項目フォーマット](work-item-format.md)、実行手順は[仕様先行の開発ワークフロー](../development/specification-first-workflow.md)が定める。

フォーマットが決まっているものには、埋める場所だけを示した最小のテンプレートを置き、中身を書き込んだ実例は置かない。
実例は、この体系で書かれたリポジトリそのものを読む。

## 目的

現在の仕様と設計を、利害関係者の目的からシステム要件、アーキテクチャ、領域別設計、検証、運用へたどれる一次情報源として維持する。
文書は現在有効な状態だけを説明し、そこへ至った経緯は work item と Git の履歴に残す。

文書体系は、システムの目的を上位に置き、その要件を構成要素へ割り当てる順序で作る。
機能と品質は要件を分類する軸、アプリケーション、データ、インフラストラクチャ、ネットワークは実現対象、可用性、性能、セキュリティ、可観測性は複数の実現対象へ作用する設計領域である。
異なる軸を同じ階層へ並べず、要件の一次情報とそれを実現する設計を参照で結ぶ。
トップダウンは読む順序と責務の分解を定めるものであり、一方向の工程を意味しない。
実現可能性の検討や検証で制約が判明したら、親の要件と設計へ戻って更新する。

文書体系の全体は、次の方針に従う。

| 方針 | 理由 |
| --- | --- |
| 一つの事実は一か所にだけ手で書き、ほかの表示は生成する | 一つの事実を複数の場所に書くと、追加のたびに全箇所を同期させることになり、片方だけが更新される。手で書く場所の数が、作成と保守の費用を決める |
| 仕様には外部から観測できる振る舞いだけを書く | 観測できない内部の手順は、実装を変えるたびに文書の更新を求めるが、利用者にとっての正しさは変わらない |
| 「内部仕様が要る」状況を、仕様の漏れか実装の欠陥の信号として扱う | 外から観測できるのに決めていなかった振る舞いは、決めて要件にするか、実装を直して振る舞いごとなくすべきものである。文書で説明しても原因は残る |
| 仕様を短く書けない設計は直す | 同じ種類の操作が経路ごとに異なる振る舞いをすると、仕様はその差の分だけ長くなる。経路をまとめるほうが、仕様、実装、テストのすべてで安い |

## 一次情報源とディレクトリ構成

同じ定義、同じ数値、同じ一覧を二か所に置かない。
それぞれに一次情報源を一つ決め、ほかの場所からはそこを参照する。
どこに置くかがそのまま一次情報源の割り当てになるので、配置と割り当てを一枚の図で決める。

- 文書は対象ごとのファイルに分け、ファイル名が対象を表す。
- 仕様と設計は文の性質で区別し、ファイルでは分けない（[仕様と設計](#仕様と設計)）。たとえば機能に閉じた設計は、機能仕様の節「実現方式」に置く。
- 現在有効な仕様、設計、手順と記述規約は `docs/`、TypeSpec は `spec/`、変更時点の計画と履歴は `work-items/` に置く。
- リポジトリの入口とエージェント指示は root に置き、詳細な規則を担当文書へ委ねる。
- 実行できる振る舞いはアプリケーションコードとテスト、変更のたびに走る検査は CI、起動時設定の項目とデフォルト値と検証規則は宣言的な設定スキーマが一次情報源である。文書はこれらを書き写さず、参照する。
- 独立した ADR 台帳は設けない。現在有効な判断は、それを扱うファイルに、判断、理由、見直し条件として置き、変更時点の比較検討は work item に残す。

  モジュールの `quality.md` は固有の割り当てや例外を書く必要がある場合だけ置く。
- 固定された各設計ディレクトリには、その範囲、対象外、子要素、隣接する設計を宣言する `README.md` を置く。その配下には、配置図で責務を定めたファイルだけを置ける。
- `docs/development/`、`docs/runbooks/`、`docs/releases/` は開いた集合、`docs/operations/` と `docs/design/verification/` は固定された集合とする。
- 内容のないファイルは作らない。共通設計をデフォルトとし、固有設計と委譲の例外、対象外とその理由だけを親の索引へ記録する。
- 固定された各ディレクトリでは、ファイル名を検査する *(checked)*。許可された名前に近い誤記には意図した名前を、その他の名前には許可される名前の集合を報告する。
- モジュールの直下には配置図の名前だけを置く。機能の段の文書だけは、ケバブケースの機能名で始める。
- `main.tsp` は TypeSpec プログラムを構成する。モデル宣言は `models.tsp`、操作はモジュールの `main.tsp` に置く。

### 一次情報文書に共通する規則

- 各一次情報文書には H1 を一つだけ置く *(checked)*。frontmatter は設けない。
- 固定された節の集合を定めるのは、機能仕様（`features/<feature>.md`）と重要な設計判断（`decisions.md`）だけである。その他の文書では、H2 に内容に合う名前を付ける。
- `README.md` はディレクトリを開いたときに表示されるので、境界の宣言と索引の置き場所にする。

#### README.md による境界の宣言

- `README.md` には、そのディレクトリが扱うもの、扱わないものと代わりの担当を書く。所属を誤りやすい場合は、所属を決める基準も書く。
- 読む順序と将来の計画は書かない。予定している作業は work item に、採用しなかった判断は再検討する条件とともに `decisions.md` に書く。例外として、モジュール設計文書の入口には、モジュールを読み始める順序を書く。
- 宣言の下に、同じディレクトリのファイルを `| 文書 | 内容 |` の表で索引する。左の列を文書へのリンク、右の列を内容の説明にする。
- モジュールの一覧と実装の単位との対応は、モジュール設計文書の入口の責務表に一度だけ書く。ほかの文書は一覧を複製せず、責務表を参照する。

```markdown
# ディレクトリ
<!-- 良い例：担当、委譲、判断が難しい場合の基準を示す -->
X のライフサイクルと付随するメタデータを扱う。
暗号処理自体は扱わず、共有アダプターに委ねる。署名鍵は <別のモジュール> が扱う。
所属は通信の方向ではなく、永続的な外部の権威が存在するかで決めるため、管理者主導のインポートは <別のモジュール> が扱う。

<!-- 悪い例：文書の案内と計画になっている -->
この文書では A、B、C の順に説明する。
今後、このモジュールへ四つ目のソース種別を追加する。
```

### 一次情報文書に置かない内容

判断の基準は、その内容を変えると外部から観測できる振る舞い、または製品が保つべき境界が変わるかである。

| 内容 | 担当 |
| --- | --- |
| ライブラリまたはフレームワークの選定 | 開発文書、または `decisions.md` の一つの判断 |
| コーディングスタイル | `docs/development/coding-style.md` |
| セットアップ、リリース、デバッグの手順 | 開発文書または運用文書 |
| デザイントークンの値と翻訳済み文言 | リソースファイル |
| 画面ごとの URL、フィールド、状態 | 実装とコンポーネントカタログ |
| 環境変数の一覧 | 生成した設定リファレンス |

### 上位と下位の分かれ目

- `docs/README.md`、`docs/requirements/product-overview.md`、`docs/requirements/`、`docs/design/architecture/` の順に、目的、義務、構造を上から読む。
- `docs/design/` は、アーキテクチャが各構成要素へ割り当てた要件をどの機構で満たすかを書く。`docs/modules/<module>/` と TypeSpec がアプリケーションの詳細仕様を定め、上位文書はその内容を複製しない。
- `design/verification/` には要件を満たしたと判断する方法、`development/` には開発の進め方、`operations/` には稼働後の管理、`runbooks/` には作業中に実行する手順を書く。設計と作業手順が同じファイルに入ったら、設計を `design/` へ、手順を後三者へ分ける。一つの構成要素だけに関わる開発時の作業は、その構成要素の設計文書に含めてよい。
- `docs/` の外の、コードのディレクトリの `README.md`（`frontend/README.md` など）は、`docs/` の文書へのリンクとよく使うコマンドだけを載せる。`docs/` の文書は内容を「`README.md` を参照」と委ねず、必要な内容を自身に含める。

### 一次情報源の割り当て

- 機能要件と品質要件は `requirements/` に一度だけ書く。設計は対応する要件を参照し、数値や義務を再定義しない。
- 複数の構成要素へ作用する品質要件は、アーキテクチャで割り当てを示し、それぞれの設計領域で実現方式を定める。
- アーキテクチャには、外部との境界、論理的な構成要素、ランタイムの相互作用、デプロイ先との対応を書く。領域別設計は同じ構成を描き直さず、関心事に必要な部分だけを参照する。
- 現在の目標、設計上の仮定、実装済みの構成、測定または試験の結果、将来の案を区別する。確認できない本番構成は参照構成として書けるが、適用済みや検証済みとは書かない。

各文書種別の書き方は、次の節が定める。

| 文書種別 | 節 |
| --- | --- |
| モジュール設計文書 | [モジュール設計文書](#モジュール設計文書) |
| 要件文書と全体設計文書 | [要件文書と全体設計文書](#要件文書と全体設計文書) |
| 作業記録 | [変更の記録](#変更の記録) |
| リポジトリの入口、プロダクト概要、CONTRIBUTING、CHANGELOG | [導入文書](#導入文書) |
| 開発文書 | [開発文書](#開発文書) |
| 運用文書と運用手順書 | [運用文書](#運用文書) |

### 文書の見せ方

散文の段落を長く続けない。
読み手は規則や対応関係を探しながら読むので、段落の中に埋もれた規則は見落とされる。

| 内容の形 | 表記 |
| --- | --- |
| 複数の項目を同じ観点で比べる（対象ごとの役割、状態ごとの表示、案ごとの採否と理由） | 表 |
| 順序に意味がある（手順、判定の順、優先順位） | 番号付きリスト |
| 順序のない規則や条件の並び | 箇条書き |
| 規則の理由、判断の背景、機構の説明 | 段落 |

- 文書の冒頭は「この文書は」で書き出し、何についての文書かを、前提を知らない読み手にも分かるように書く。「本書は」「このファイルは」は使わない。
- 「持つ」「所有する」で関係を曖昧にせず、「定める」「書く」「扱う」「実装する」「保存する」など具体的な動詞を使う。実際の所有や保持を表す用法は変えない。
- 設計文書には目指す設計を書き、実装がまだ追いついていない部分は行ごとの実装状況として示す。追いつくための実装は work item として起票し、設計文書からその work item を参照しない。
- 節のタイトルは、その節が扱う対象を指す名詞句で書く。「〜を確かめる」のような動詞形と、動詞を「こと」で名詞化した形は使わない。末尾に句点を付けない。
- 小見出しの代わりに句点付きの太字の段落を置かない。区切りが要るなら見出しにする。
- 技術用語は、意味の広い一般的な日本語に置き換えず、定着したカタカナ語で書く。たとえば、version は「版」ではなく「バージョン」、title は「題名」ではなく「タイトル」、resource は「資源」ではなく「リソース」と書く。default は「既定」ではなく「デフォルト」、データベースの table は「テーブル」と書く。
- 訳語と分野の用語は一次資料（標準や主要製品の日本語ドキュメント）で確かめ、造語を作らない。層やコンポーネントの名前は既存の文書の名前を使う。「正本」は使わない。
- 「ない」はかなで書く。
- 表の見出しは名詞句（「判定内容」「失敗時の動作」）で書き、節や疑問の形（「確かめること」「状態を持つか」）にしない。一つの見出しに二つの概念を詰めない。セルを空にせず「なし」と書く。
- 「〜は書かない」のような文書についての断り書きを置かず、その内容がどこにあるかを書く。
- 他の文書の内容を「README を参照」で済ませず、読み手が必要な内容は文書の中に書く。他の文書の節を指すときは見出しをそのまま使う。

#### 設計文書からコードへの参照

設計文書がコードを参照してよいかは、参照の種類で決める。

| 参照 | 扱い |
| --- | --- |
| 検査が読む宣言（論理アーキテクチャの責務表のパッケージ、バックエンド設計とフロントエンド設計のコードの置き場所と依存の向き） | 書く。設計が配置そのものを定めている |
| 構成ファイル（`infra/`、`mise.toml`）を対象とする設計での、そのファイルへの参照 | 書く |
| 検査のタスク（`mise run <task>`） | 書く。違反を検出する仕組みとして名指す |
| Aggregate、公開するポート、ドメインイベントの名前 | 書く。モジュールの仕様が公開契約として宣言する語であり、実装の詳細ではない |
| コードの配置そのものを決める判断 | 書く。ただし対象は「モジュールの組み立て」のように責務で示し、任意のファイル名を固定しない |
| フレームワークが要求する命名規則（ファイルによる経路定義、生成から除外する接頭辞など） | 書く。任意の実装ファイルの指定ではなく、配置の規則である |
| 個々のソースファイル、関数、型、テストファイル、テスト補助 | 書かない。担当するパッケージ、責務、依存の向き、組み立ての境界とその理由を書き、どのコードが規則を実装するかは、コードのコメントから設計文書の節を参照する |
| 変更の際に開く実装の一覧 | 書かない。必要な場合だけ開発文書へ置き、コードから容易に復元できる一覧は作らない |
| 実装言語、ライブラリ、データベースの製品名 | 技術を選んだ文書（アーキテクチャの制約と判断、バックエンド設計、フロントエンド設計、データベース設計）には書く。ガイドラインでは規則の本文に書かず、選んだ技術に固有の理由は規則の後に補足する |

参照の向きをコードから文書へ限るのは、ファイルの移動や改名のたびに設計文書が古くなることを避けるためである。
この基準は機械検査せず、レビューで確かめる。

### 生成物

- 生成された OpenAPI、HTML、設定リファレンス、データベースの一覧は、一次情報源から導いた表示であり、手で書き換えない。一次情報として扱わない。
- 生成した OpenAPI は `spec/generated/`、文書サイトは `site/` に置き、Git で追跡しない。`docs/` には置かない。
- 利用者がリポジトリを開いて直接読む生成文書は例外とし、Git で追跡する。ルートの `CONFIGURATION.md` と `ROUTE_PRIORITY.md` がこれに当たる。追跡する生成文書も手で編集せず、一次情報の変更後に再生成し、ドリフト検査で一致を確かめる。
- 実行可能な具体例を使う付録だけは、一次情報への参照と生成区間を追跡する Markdown に含める。書式とドリフト検査は[仕様フォーマット](specification-format.md#実行可能な具体例と派生表示)が定める。
- 機械生成は、TypeSpec の形と列挙値、スキーマの項目、設定の定義、実装の配線など、入力から一意に復元できる範囲へ広げる。テストの期待結果には、独立した具体例または仕様から導いた性質を使い、実装から採集した現在値を正しさの証拠にしない。
- 一次情報源を一か所へ集めると、読み手には全体を見渡しにくくなる。一望性は生成した文書サイト `IdMagic ドキュメント` が与える。サイトは TypeSpec と一次情報の Markdown から、文書ごとのページ、要件一覧、操作の一覧、未決事項、状態図、API リファレンス、モデルカタログを作る。
- 設計と理由は本文に書き、別の判断記録へリンクして済ませない。リンクしてよい判断の記録は `decisions.md` だけであり、`decisions/` のような作業記録のディレクトリへのリンクは拒否する *(checked)*。

## モジュール設計文書

モジュール設計文書は、一つのモジュールの仕様（責務、公開契約、要件と不変条件、用語の意味）と、その実現方法である設計を、`docs/modules/<module>/` にまとめる。
システム全体の構造とモジュールへの割り当ては全体設計文書が定め、モジュール設計文書はその割り当てと例外だけを書く。
実装との対応と公開範囲は[モジュールの責務表](../modules/README.md#モジュール)が宣言し、境界は[境界を選ぶ判断手順](../design/application/design-guidelines.md#境界を選ぶ判断手順)で選ぶ。
仕様の文書の形式は[仕様フォーマット](specification-format.md#仕様文書)、設計の文書の形式は[設計フォーマット](design-format.md)が定め、この文書は再掲しない。

### 仕様と設計

モジュール設計文書の文には、仕様と設計の二種類がある。

| 種類 | 内容 | 例 |
| --- | --- | --- |
| 仕様 | 検証の対象になる規範 | 機能仕様の要件（`REQ-*`）、受け入れ例、横断シナリオ、`standards.md` の準拠と逸脱、品質要件の割り当て、TypeSpec の契約 |
| 設計 | 仕様を満たす構造、仕組み、判断の説明 | 設計領域の文書、機能仕様の「実現方式」、`decisions.md` |

この区別は、どの文書に置くかではなく、文が何を述べるかで決まる。
同じ責務の記述も、システムから見れば全体設計の割り当てであり、モジュールから見れば外への約束なので、ディレクトリで分けると置き場所の基準が見る位置によって変わる。
そのため、ファイルは対象（モジュール全体、設計領域、機能）で分け、一つのファイルに仕様と設計を同居させてよい。
規範であることは要件の見出しや受け入れ例の形式が示し、検査はその形式を読む。

### 適用範囲と置き場所

適用範囲が広い内容ほど上の階層へ置き、同じ内容を下の階層へ写さない。

| 適用範囲 | 置き場所 | 文書 |
| --- | --- | --- |
| すべてのモジュール | `docs/modules/` の直下 | 入口の責務表、共通用語集 `glossary.md`、横断シナリオ `scenarios.feature.md` |
| 一つのモジュール | `docs/modules/<module>/` の直下 | `README.md`、`glossary.md`、`standards.md`、`quality.md`、設計領域の文書、`decisions.md`、`risks.md` |
| 一つの機能 | `docs/modules/<module>/features/` | 機能仕様 `<feature>.md` と章、受け入れ例 `<feature>.feature.md` |

- 関係の深い機能は、モジュールの `README.md` の機能の表で機能群として並べる。機能群のディレクトリも、機能ごとのディレクトリも置かない。
- 共通用語集は、業務と外部契約の語に加え、モジュール、Aggregate、永続化の規約のように、各モジュールの仕様と設計が同じ意味で使う語を定める。要件用と設計用に用語集を分けない。
- 横断シナリオには、複数のモジュールの協調による保証と、複数のモジュールへ共通に適用する保証（CSRF の防御、JSON のデコードなど）を置き、参加するモジュールを名指す。一つのモジュールが単独で満たす振る舞いは、そのモジュールの機能仕様で定める。
- 複数のモジュールにまたがる呼び出し順序を、独立した文書として作らない。`When` と `Then` を繰り返す例として書くか、組み立て方の設計なら `architecture/runtime.md` へ書く。

## 要件文書と全体設計文書

要件文書と全体設計文書は、外部から見た目的と環境を入口にし、要件、アーキテクチャ、設計領域ごとの設計、検証へ分解する。
要件は「何を満たすか」、アーキテクチャは「どの構成要素へ割り当てるか」、設計領域ごとの設計は「どの機構で満たすか」、検証設計は「どの証拠で満たしたと判断するか」に答える。
requirement は「要件」と訳し、文書の区分にも機能仕様の `REQ-*` にも同じ語を使う。
実装の単位は「モジュール」と書き、Go の `context.Context` と同じ語を設計の単位に使わない。

| 文書 | 書くこと | 書かないこと |
| --- | --- | --- |
| `docs/README.md` | 要件文書、全体設計文書、モジュール設計文書、開発文書、運用文書、リファレンス、フォーマットの各区分を、区分名を入口へのリンクにした表で索引する。リファレンスの行は `spec/main.tsp` へリンクする | 製品の目的、モジュールの一覧、モジュール間の依存の辺 |
| `requirements/product-overview.md` | 解決する問題、対象ユーザー、対象外とその引き受け先。対象範囲は責務表を参照して宣言する | 機能の箇条書き、成功条件 |
| `requirements/functional.md` | 機能群、利用者が行えること、実現するモジュール | 個々の振る舞い（機能仕様の `REQ-*` が定める） |
| `requirements/quality.md` | 品質要件と測定境界。ISO/IEC 25010 の特性ごとに、要件と、規範と検証の場所を示す。SLO、キャパシティ受入、RPO、RTO などの数値の一次情報 | 設計文書が参照する数値の写し |
| `requirements/standards.md` | システム全体が準拠する外部規範 | モジュール共通の語彙と横断シナリオ |
| `design/architecture/` | `README.md` に制約と解決戦略、`system-boundary.md` に外部の主体と責任分界、`logical.md` にモジュールの責務表とアーキテクチャスタイル、`runtime.md` に実行単位と主要な相互作用、`deployment.md` に実行単位と配置先の対応、`decisions.md` に複数の文書に作用する判断 | 別のビューと同じ構成の再定義 |
| `design/application/backend.md`、`frontend.md` | パッケージの分類、層構成、アダプターの命名、モジュール間の依存規則と公開範囲、イベント、起動時の組み立て。フロントエンドはルーティング、状態の置き場所、ビルドと配信 | 通すだけの層を構造の改善と呼ぶこと |
| `design/application/api-guidelines.md` | 操作をまたいで同じでなければならない規則（命名、値の表現、メソッド、状態コード、エラー、ページング、冪等性、条件付き要求、長時間の操作、上限、互換性、非推奨）と、各規則が守っているもの | 個々の操作の形（TypeSpec が定める） |
| `design/application/user-interface.md` | 画面をまたいで揃える情報の順序、操作、表示状態、エラーの文言、国際化、アクセシビリティの実装手段 | 画面ごとの文言と見た目、アクセシビリティの規範（`standards.md` が定める） |
| `design/data/` | `database.md` に型の選択と制約の置き場所とテーブル一覧つきの ER 図、`schema-management.md` に拡張と縮小の段階による変更、`lifecycle.md` にデータが消えるまでの横断的な扱い | カラムと索引（スキーマファイルが定める） |
| `design/infrastructure/` | `platform.md` にコンピューティング、ストレージ、環境差、構成管理、`network.md` に入口、出口、名前解決、TLS 終端、隔離 | 信頼境界（セキュリティ設計が定める） |
| `design/security/` | `authorization.md` に主体、境界ごとの受け入れ、スコープ、テナント境界の規則とその検証手段、`threat-model.md` に信頼境界、資産、脅威と応える統制、`secrets.md` に鍵と証明書のライフサイクル | 操作とスコープの割り当て表（TypeSpec が定める）、是正を担う work item |
| `design/reliability/`、`design/performance/` | 障害単位、冗長化、復旧の順序、過負荷時の振る舞いと再試行の層、利用規模の見積もり、スケーリングの単位と律速点 | 目標値（品質要件が定める）、上限値だけを集めた一覧 |
| `design/observability/` | 相関 ID、シグナル間の関係、監視対象と通知、ログの扱い、トレースの伝播と標本化 | SLO の目標値、監査イベント名（TypeSpec が定める） |
| `design/verification/` | 要件ごとに必要な証拠の種類、標準タスク、証拠の保存先、合否条件 | テストコードと実行結果の写し |

## 変更の記録

変更固有の動機、候補の比較、計画、検証結果は `work-items/` の Markdown を一次情報にする。
現在有効な責務と規則は仕様と設計へ反映し、作業記録を読まなくても現在の状態が分かるようにする。
状態、仕様影響、着手時の読み取り範囲、完了の証拠と配置は[作業項目フォーマット](work-item-format.md)が定める。

## 導入文書

| 文書 | 書くこと | 書かないこと |
| --- | --- | --- |
| リポジトリの `README.md` | 一文のプロダクト説明、起動コマンド、`docs/requirements/product-overview.md`、`docs/README.md`、`CONTRIBUTING.md` へのリンク | 仕様 |
| `CONTRIBUTING.md` | 開発文書への案内 | 手順と CI の検査の一覧の写し |
| CHANGELOG | 利用者に影響するリリース済みの変更 | 非推奨の規則（`design/application/api-guidelines.md` が定める） |

## 開発文書

`docs/development/` には、開発環境の用意、標準タスク、変更と検証の進め方を書く。
製品の振る舞いと守るべき境界は、担当する仕様と設計へ書く。
書くべきものがない文書は作らない。

| 内容 | 書き方 |
| --- | --- |
| 手元で実行するもの | 開発環境の用意、ビルド、コード生成、成果物の作り方。ツールのバージョンを固定し、手元と CI で同じバージョンを使う。外部依存にはローカルの代替を用意し、本番の資格情報を手元へ置かない |
| CI が走らせるもの | 検査の一覧は CI に定義し、開発文書には方針と理由だけを書く。失敗した検査を恒常的に無効化せず、無効化するときは work item を作る。不安定なテストは期限内に直すか削除する |
| コーディングスタイル | [コーディングスタイル](../development/coding-style.md#文書の範囲)に一つのファイルでまとめ、指針ごとに理由を添える |
| テスト | 水準、実行境界、テストダブルは[テスト方針](../development/testing.md)が定める。テストデータに実顧客の個人データを使わない |
| 設定 | 起動時設定の項目、型、デフォルト値、検証規則を宣言的なスキーマへ書き、読み込みコードとリファレンス文書の双方をそこから導く |

検査がすべて通っても、保証されるのは文書どうしの整合である。
仕様が現実と合っているかを確かめるのはテストと実際の観測であり、検査の成功をその代わりにしない。

設定と呼ばれるものには、性質の異なる三つの面がある。

| 面 | 読者 | 一次情報源 | 変更経路 | 監査 |
| --- | --- | --- | --- | --- |
| 起動時設定 | 運用者 | 宣言的な設定スキーマ | リリース | 変更履歴 |
| テナント設定 | テナント管理者 | TypeSpec | 管理 API | 監査イベント |
| feature flag | 開発とリリースの担当 | flag の定義 | 実行時 | 変更履歴 |

feature flag は実験と段階的展開のためのものであり、作成日、所有者、削除条件を持たせる。
flag を消したときにデータが解釈できなくなるので、flag の状態を永続データへ書き込まない。

## 運用文書

`operations/` には稼働後のサービス管理と保守の責任、判断基準、設計を書く。
`operations/README.md` が入口となり、SLO の値、可用性と復旧の機構、リリース手順、障害対応手順を複製せず、それぞれの一次情報を運用の流れへ結び付ける。

| 内容 | 置き場所 |
| --- | --- |
| SLO、RPO、RTO の目標値と測定境界 | `docs/requirements/quality.md` |
| 可用性、冗長性、復旧の設計 | `docs/design/reliability/` |
| リリースと後退の手順 | `docs/development/` |
| 運用と障害対応の手順 | `docs/runbooks/<name>.md` |

- 運用手順書は、人が手で実行する運用作業一つにつき一つ置く。アラートへの対応、定期作業、手動の運用操作が同じ形に収まる。
- 運用手順書を、それが操作するインフラの構成ファイルの隣へ置かない。当番は、どのディレクトリの話かを知らない状態で呼び出される。
- `docs/runbooks/` の下をさらに分けない。索引が要るようになったら `docs/runbooks/README.md` に置く。
- SLO は、何を測るかとどう測るかを分けて書き、予算を使い切ったときに何をするかを目標値と同じ場所に書く。アラートは瞬間値ではなく予算の消費の速さで鳴らす。
- 障害の事後記録は、対策が恒久的な規則になった時点で、その規則を定める仕様へ反映する。個人の責任を問う書き方をしない。

運用手順書は次の形にする。

```markdown
# <作業またはアラートの名前>

## 着手条件
<いつこれを開くか。アラート名と、対応するSLO>

## 最初に確認すること
<影響範囲の切り分け。依存先の状態。直近の変更>

## 実施
<手順。一つずつ、戻せるかどうかを添えて>

## 確認
<終わったと言える条件>

## 失敗したとき
<誰へ、何分で上げるか>
```
