# 文書ガイド

この文書は、仕様、設計、開発、運用の内容をどの文書へ書くかを定める。
正確な配置と記述規則は[仕様フォーマット](specification-format.md)、変更の計画と証拠は[作業項目フォーマット](work-item-format.md)、実行手順は[仕様先行の開発ワークフロー](../development/specification-first-workflow.md)が定める。

フォーマットが決まっているものには、埋める場所だけを示した最小のテンプレートを置く。中身を書き込んだ実例は置かない。**実例はこの体系で書かれたリポジトリそのものを読む。**

各文書には、語彙や規則を借りている先がある。まとめて§11に挙げる。

## 1. 目的

現在の仕様と設計を、利害関係者の目的からシステム要求、アーキテクチャ、領域別設計、検証、運用へたどれる一次情報源として維持する。文書は現在有効な状態だけを説明する。そこへ至った経緯はwork itemに記録し、Git履歴からたどれる。

文書体系は、システムの目的を上位に置き、その要求を構成要素へ割り当てる順序で作る。機能と品質は要求を分類する軸、アプリケーション、データ、インフラ基盤、ネットワークは実現対象、可用性、性能、セキュリティ、可観測性は複数の実現対象へ作用する設計領域である。異なる軸を同じ階層へ並べず、要求の一次情報とそれを実現する設計を参照で結ぶ。

トップダウンは読む順序と責務の分解を定める。実現可能性の検討や検証で制約が判明した場合は、親要求と設計へ戻って更新するため、一方向の工程を意味しない。

## 2. 一次情報源とディレクトリ構成

同じ定義、同じ数値、同じ一覧を二か所に置かない。それぞれに一次情報源を一つ決め、他の場所からはそこを参照する。**どこに置くかがそのまま一次情報源の割り当てになる**ので、配置と割り当てを一枚の図で決める。

文書の種類はファイルで分け、ファイル名が内容の種類を表す。
現在有効な仕様、設計、手順と記述規約は `docs/` に集める。
TypeSpec は `spec/`、変更時点の計画と履歴は `work-items/` に置く。
リポジトリの入口とエージェント指示は root に置き、詳細な規則を担当文書へ委ねる。

`docs/` と `spec/` の正式な配置と、名前を固定した文書の一覧は[仕様フォーマット §1](specification-format.md#1-配置)が定める。リポジトリの検査が、人が読むそのツリーを `tools/workspace/src/document-layout.ts` と照合するので、この文書はツリーを再掲しない。

`README.md`はディレクトリを開いたときに表示されるため、境界の宣言と索引の置き場所として使う。

ツリーに現れない一次情報源が三つある。**実行できる振る舞い**はアプリケーションコードとテストで定める。**変更のたびに走る検査**はCIに定義する。**起動時設定の項目、デフォルト値、検証規則**は宣言的な設定スキーマで宣言する。文書はこれらを書き写さず、参照する。

独立したADR台帳は設けない。現在有効な判断は、それを扱うファイルに、判断、理由、見直し条件として置く。どのファイルが何を扱うかは上のツリーが示す。変更時点の比較検討はwork itemに残す。

### 上位と下位の分かれ目

`docs/README.md`、`docs/requirements/product-overview.md`、`docs/requirements/`、`docs/design/architecture/`の順に、目的、義務、構造を上から読む。`docs/design/`は、アーキテクチャが各構成要素へ割り当てた要求をどの機構で満たすかを書く。`docs/domain/<context>/`とTypeSpecでアプリケーションの詳細仕様を定め、上位文書はその内容を複製しない。

`design/verification/`には要求を満たしたと判断する方法を書く。`development/`、`operations/`、`runbooks/`には、それぞれ開発の進め方、稼働後の管理、作業中に実行する手順を書く。現在の設計と作業手順が同じファイルに入った場合は、設計を該当する`design/`へ、手順を後三者の該当先へ分ける。ただし、一つの構成要素だけに関わる開発時の作業（フロントエンドの依存の宣言や部品の追加など）は、その構成要素の設計文書に含めてよい。

各ディレクトリの`README.md`には、対象範囲、対象外の内容、子文書の索引、隣接する領域への参照を書く。対象システムに該当しない子文書は作らず、親の索引に適用対象外の理由を書く。

`docs/`の外にある、コードのディレクトリの`README.md`（`frontend/README.md`など）は、そのディレクトリの入口として、`docs/`の文書へのリンクとよく使うコマンドだけを載せる。`docs/`の文書は、内容を「`README.md`を参照」と委ねず、必要な内容を自身に含める。読み手が`docs/`の文書だけで設計の全体をつかめるようにするためである。

### 一次情報源の割り当て

機能要求と品質要求は`requirements/`に一度だけ書く。設計は対応する要求を参照し、数値や義務を再定義しない。可用性、セキュリティ、性能のように複数の構成要素へ作用する品質要求は、アーキテクチャで割当を示し、それぞれの設計領域で実現方式を定める。

アーキテクチャには、外部との境界、論理的な構成要素、ランタイムの相互作用、デプロイ先との対応を書く。領域別設計は同じ構成を別々に描き直さず、関心事に必要な部分だけを参照して説明する。

現在の目標、設計上の仮定、実装済みの構成、測定または試験の結果、将来の案を区別する。確認できない本番構成を参照構成として書くことはできるが、適用済みや検証済みとは記述しない。

### 文書の見せ方

散文の段落を長く続けない。読み手は規則や対応関係を探しながら読むので、段落の中に埋もれた規則は見落とされる。内容の形に合わせて、次の表記を選ぶ。

| 内容の形 | 表記 |
|---|---|
| 複数の項目を同じ観点で比べる（対象ごとの役割、状態ごとの表示、案ごとの採否と理由） | 表 |
| 順序に意味がある（手順、判定の順、優先順位） | 番号付きリスト |
| 順序のない規則や条件の並び | 箇条書き |
| 規則の理由、判断の背景、機構の説明 | 段落 |

- 文書の冒頭では、何についての文書かを、前提を知らない読み手にも分かるように書く。
- 文書の冒頭は「この文書は」で書き出す。「本書は」「このファイルは」は使わない。文書の中で自分自身を指すときも「この文書」と書く。
- 「持つ」「所有する」で関係を曖昧にせず、「定める」「書く」「扱う」「実装する」「保存する」など具体的な動詞を使う。否定も何がないかを明示する。実際の所有や保持を表す用法は変えない。
- 設計文書には目指す設計を書き、実装がまだ追いついていない部分は行ごとの実装状況として示す。「欠落」「未実装」とだけ書いて設計を空けない。追いつくための実装は work item として起票し、設計文書からその work item を参照しない。
- 節のタイトルは名詞形にする。「〜を確かめる」「〜したときに確認すること」のような動詞形と、動詞を「こと」で名詞化した形は使わず、「拒否の確認対象」「実行環境の区別」のように、その節が扱う対象を指す名詞句で書く。動詞形のタイトルは、その節が規則の説明なのか作業の手順なのかを曖昧にし、目次に並べたときに節どうしの関係も読めなくなる。
- 技術用語は、意味の広い一般的な日本語に置き換えず、定着したカタカナ語で書く。一般的な日本語にすると、読み手がそれを技術用語として認識できないためである。たとえば、version は「版」ではなく「バージョン」、title は「題名」ではなく「タイトル」、resource は「資源」ではなく「リソース」と書く。

### 生成物

生成された OpenAPI、HTML、設定リファレンス、データベースの一覧は、一次情報源から導いた表示であり、手で書き換えない。
実行可能な具体例を使う付録だけは、一次情報への参照と生成区間を追跡する Markdown に含め、通常の仕様差分とカバレッジ検査へ渡す。
書式とドリフト検査は[仕様フォーマット](specification-format.md#実行可能な具体例と派生表示)が定める。
人が維持するのは規則、判断理由、独立した期待結果であり、派生表示の行数は維持量に数えない。

機械生成は、TypeSpec の形と列挙値、スキーマの項目、設定の定義、実装の配線など、入力から一意に復元できる範囲へ広げる。
テストでは、その契約から入力、境界値、実行用の枠組みを生成できるが、期待結果には独立した具体例または仕様から導いた性質を使う。
実装から現在値を採集した参照やスナップショットは現状の記述であり、そのまま望ましい仕様や正しさの証拠にはしない。

一次情報源を一か所へ集めることは書き手を助けるが、読み手には負担になる。**一望性は生成した仕様サイトが与える**と決めておく。生成の仕組みを持てない体制では、複製を許して複製の検出を検査項目にする方が現実的である。

## 3. モジュールの仕様

モジュールの仕様は、責務、公開契約、要求と不変条件、用語の意味を定める。
実装との対応と公開範囲は[論理アーキテクチャの責務表](../design/architecture/logical.md#モジュールの責務)が宣言する。
境界は、変わりうる設計判断を内部へ隠すという情報隠蔽の基準と、[境界を選ぶ判断手順](../design/application/design-guidelines.md#境界を選ぶ判断手順)で選ぶ。

モジュールの一次情報文書の役割と形式、モジュール内の分割基準は、
[Specification Format §3–§6](specification-format.md#3-一次情報文書) が定める。
この文書は、同じテンプレート、表、規範 ID の文法を再掲しない。

一つの機能の要件は機能仕様へ、複数の機能にまたがる仕組みはモジュールの設計へ書く。
仕様の階層とコードとの対応は[仕様の木](specification-format.md#仕様の木)、操作と要件の形式は[機能仕様](specification-format.md#機能仕様--一つの機能について知るべきこと)が定める。

## 4. システム要求と設計

システム文書は、外部から見た目的と環境を入口にし、要求、アーキテクチャ、領域別設計、検証へ分解する。モジュールはアプリケーションの論理構造の一部であり、インフラ基盤、ネットワーク、観測基盤、運用者との責任分界も同じシステムの構成として扱う。

各文書は一つの問いに答える。要求は「何を満たすか」、アーキテクチャは「どの構成要素へ割り当てるか」、領域別設計は「どの機構で満たすか」、検証設計は「どの証拠で満たしたと判断するか」に答える。

### 4.1 README.md

`docs/README.md` を文書全体の入口にする。
要求、システムの設計、モジュール設計、開発、運用、生成リファレンス、フォーマットの各索引へリンクする。
製品の目的はプロダクト概要へ、モジュールの一覧、公開範囲、実装場所は論理アーキテクチャの責務表へ委ねる。
モジュール間の依存の辺はコードから抽出できるので、文書に手で書かない。

実装の単位は「モジュール」と書き、Go の `context.Context` と同じ語を設計の単位に使わない。文書とコードで同じ語が別の概念を指すと、読み手と検査の両方が取り違えるためである。

外部の主体とシステムとの責任分界は`design/architecture/system-boundary.md`で定める。責務表はアプリケーション内部のモジュールを示すため、外部環境と物理的な運用境界を同じ表に押し込まない。

共有機構は、その担当モジュールの仕様と設計で定める。
入口に別の一覧を作らず、該当する文書の索引からたどれるようにする。

### 4.2 requirements/

`requirements/product-overview.md`は、解決する課題、利用者、対象としない責務を記載する。

`requirements/functional.md`は、利用者と外部システムが必要とする機能を、担当するモジュールの規範シナリオとTypeSpecへ割り当てる。上位文書は個別の振る舞いを再掲せず、機能群と担当を書き、詳細仕様を参照する。

`requirements/quality.md`は、システムに求める品質と測定境界を一度だけ宣言する。品質の点検には採用したバージョンのISO/IEC 25010を使い、適用する特性と適用しない特性を理由付きで示す。SLO、キャパシティ受入、RPO、RTO、互換性、セキュリティ、利用時品質などの数値と義務はここを一次情報とし、設計文書は識別子を参照する。

### 4.3 design/architecture/

アーキテクチャ記述はISO/IEC/IEEE 42010の関心事、視点、ビュー、対応関係の考え方を借りる。規格が特定のファイル構成や作図法を要求しているとは扱わない。

`system-boundary.md`には利用者、外部システム、運用者、責任分界を、`logical.md`にはモジュールの責務表（公開範囲と組み立て地点を含む）を、`runtime.md`には実行単位と主要な相互作用を、`deployment.md`には実行単位と配置先の対応を書く。`decisions.md`には、複数の文書に作用する現在有効な判断と見直し条件を書く。

各ビューは、対象となる関心事、用いる表現、構成要素、要素間の関係、対応する要求を冒頭で示す。別のビューと同じ構成を再定義せず、対応表または参照で結ぶ。

### 4.4 structure.md

コード構成は、パッケージの分類、依存規則、層、起動時の組み立てを定める。
モジュールの一覧と公開範囲の宣言は論理アーキテクチャの責務表へ委ねる。

トップレベルのディレクトリの役割、モジュール内部の層構成、アダプターの命名規則、モジュール間の依存規則と公開範囲を定める。依存は仕様から実装へ流れ、ドメイン層とユースケース層がアダプターやランタイムへ逆向きに依存しないことを、境界検査ツールで機械検査する。

アーキテクチャスタイルもここへ置く。スタイルの実体がパッケージの切り方と依存の向きだからである。単一モジュールで境界を保つのか、サービスへ分けるのか、分けるとしたら何が起きたときかを書く。**現在の設計を示すものであり、将来も同じ構成を義務付けるものではない**と明示する。

層の数や名前を増やすことを構造の改善と呼ばない。判断の基準は、**その境界が隠している複雑さが、境界を越えるために払う手間に見合っているか**である。通すだけの層は、依存の向きを整えているように見えて、実際には呼び出しの段数を増やしているだけのことがある。

### 4.5 design/application/api-guidelines.md

外部に見える形を、すべてのエンドポイントで揃える規則を書く。個々の操作の形はTypeSpecで定義するので、ここに書くのは**操作を跨いで同じでなければならないこと**だけである。

| 項目 | 内容 |
|---|---|
| リソースの命名 | パスの形、コレクションと単一リソース、プロパティの記法と大文字小文字 |
| 値の表現 | 日時、期間、数値、列挙、識別子のフォーマット。`null`と省略の使い分け |
| HTTPメソッドの割り当て | 取得・作成・全体置換・部分更新・削除に、どのメソッドを使うか。選んだメソッドが負う義務をどう果たすか |
| ステータスコード | 成功と失敗に割り当てるコード。同じ意味に二つのコードを使わない |
| エラーレスポンス | デフォルトの形式と、相手側のプロトコルがエラーの形を定めているエンドポイントでの例外 |
| コレクションの操作 | ページング方式とカーソルが束縛するもの、絞り込み、並べ替え、部分レスポンス |
| 再送と重複防止 | 冪等キーの受け付けと保持期間、クライアントへの再試行の指示 |
| 条件付きリクエスト | `ETag`と`If-Match`によるバージョンの表し方と、更新の取りこぼしの防ぎ方 |
| 長時間かかる操作 | 受理の返し方、操作を表すリソースの形、進捗・完了・取り消しの見せ方 |
| CRUDに収まらない操作 | 動詞をどこに置くか、その形をどこまで許すか |
| 上限と流量 | 一括リクエストの最大件数、レート制限の伝え方、文字列長の単位と区分 |
| バージョンと互換性 | バージョンの付け方、後方互換な変更の定義、未知のフィールドの扱い |
| 非推奨 | 告知の方法（`Deprecation`と`Sunset`ヘッダー）、最短存続期間、削除するバージョン |

各項目には規則だけでなく**その規則が守っているもの**を書く。守っているものが無い規則は、状況が変わったときに緩めてよいか判断できない。

**メソッドを選ぶと、そのメソッドが負う義務も一緒に決まる。** RFC 9110は、`GET`と`HEAD`を安全（サーバーの状態を変えない）、`GET`・`HEAD`・`PUT`・`DELETE`を冪等（同じリクエストが何度届いても結果が変わらない）と定めている。呼び出し側とその間にあるプロキシやリトライ機構はこの性質を前提に動くので、**「このプロダクトの`PUT`は冪等ではない」という選び方はできない。** 冪等にできないなら、そのメソッドを使わない。

したがってこの文書に書くのは、性質そのものではなく、**義務を実装がどう果たすか**である。`POST`のように冪等でないメソッドを使う経路では、冪等キーを受け付けて重複を防ぐ。ネットワークの再送とクライアントの再試行は同じ形で届くので、区別せず同じ仕組みで受ける。

**長時間かかる操作は、操作そのものをリソースにする。** 受理を返して終わりにせず、進捗、結果、取り消しを表すリソースを返す（Google AIP-151の`Operation`が典型である）。呼び出し側が待ち方を選べないと、この判断は各エンドポイントで別々に発明される。

文字列長のように同じ数が契約・ドメイン検証・DB制約・UIの複数箇所に現れるものは、数を一度だけ決めたうえで、どこが唯一の強制点で、どこが最後の防壁で、どこが入力の補助かを書き分ける。

観点の抜けは、公開されているAPIガイドライン（§11）を一度通して確かめる。**採らないと決めた観点は、決めたと分かる形で残す。** 書かれていない観点は、判断した結果なのか見落としなのかを後から区別できない。

### 4.6 design/observability/

`README.md`には相関ID、シグナル間の関係、共通属性を書く。`monitoring.md`ではアプリケーション、基盤、ネットワーク、外部依存、観測基盤自体の監視対象、検知、通知を扱う。`logging.md`ではログの生成、収集、転送、保存、検索、アクセス制御、機微情報の除外、容量超過と収集停止時の動作を扱う。`tracing.md`では伝播、収集、標本化、保持を扱う。

**予期された業務上の失敗をERRORにしない。** 当番担当者を起こす根拠にならない失敗がERRORで日常的に出ていると、本当のERRORが埋もれる。

**件数を数えたいものはログではなく指標にする。** ログの集計で件数を出すと、保持期間を過ぎた時点で過去と比べられなくなる。指標のラベルは有限の集合に限り、値の種類に上限がないものをラベルにしない。

**属性の名前を自前で決めない。** シグナル（ログ、指標、トレース）を跨いで同じものを指す名前は、OpenTelemetryの意味規約に既存のものがあればそれを使い、無いものだけを自分で決めてここに書く。名前を自分で決めた分だけ、既製の可視化と分析が効かなくなる。

SLOの目標値は`requirements/quality.md`で定め、ここには測定の仕組みだけを書く。監査証跡はアプリケーションログではなく監査の仕組みへ記録し、監査イベント名と必須属性はTypeSpecで定義する。

### 4.7 architecture/deployment.mdとdesign/infrastructure/

「deployable unit」「container」ではなく**実行単位**と呼ぶ。C4のContainerはコンテナ技術のことではないが、この語をそのまま使うと誤読される。

実行単位ごとに、何を受け付け、何を独立に増やせるかを書く。**実行単位の一覧を別の台帳に設けず、エントリーポイントとビルド手順から導く。**

デプロイメントアーキテクチャでは、実行単位をどの環境とコンピューティングへ配置し、どの接続で結ぶかを定める。`design/infrastructure/platform.md`ではコンピューティング、ストレージ、環境差、構成管理、IaCの責任分界を、`network.md`では入口、出口、名前解決、ポート、TLS終端、隔離、管理接続を扱う。信頼境界そのものはセキュリティ設計で定める。

共有状態については、レプリカごとのプロセスメモリに置いてよいものと置いてはならないものを、**失われる保証の違い**で分ける。同じ「カウンターの喪失」でも、閾値がシステム全体で緩むものと、時間枠がリセットされるだけのものでは耐久性の要件が違う。

### 4.8 design/performance/とdesign/reliability/

`performance/capacity.md`には、設計が前提にする利用規模、負荷分布、リソースの見積もり、費用の前提を書く。`performance/scaling.md`には、スケーリングの単位、律速点、同時実行、待ち行列、再試行、アドミッションコントロールを書く。目標値は品質要求を参照し、ここには再掲しない。実測値が継続して仮定値を上回るなら、上限値とデプロイ構成を見直す。

個々の上限値——一括リクエストの最大件数、レート制限の閾値、文字列長——は、**それを課す仕組みの説明の隣に置く**。上限だけを集めた一覧を作らない。この文書に書くのは方針だけである。外部の標準が定める数をそのまま上限に使わないこと、上限を置かない選択が実際には下層の実装へ委ねることでしかないことを、理由とともに書く。

`reliability/availability.md`には、障害単位、冗長化、状態の共有、切り替え、ロードシェディングの順序を書く。冗長化は可用性を実現する手段であり、複製だけで論理破損や災害からの復元が成立するとは扱わない。`reliability/recovery.md`には、バックアップ、復元、災害復旧、復元の順序を書く。実行手順は運用手順書へ置く。

**過負荷のときに何が起きるかを、正常時の見積もりと同じ重さで書く。** 決めるのは、受け付けを絞る場所（入口か、下流の呼び出しか）、絞るときの優先順位、そして再試行の増幅をどう抑えるか（試行回数の上限、指数的な間隔、ばらつきの付与、下流が弱っているときに呼び出しを止める仕組み）である。再試行は、各層が善意で入れると層の数だけ掛け算になる。**どの層が再試行してよいかを一か所で決める。**

### 4.9 design/data/

**構造は宣言的なスキーマファイルで定義し、文書にはカラムも索引も書かない。**

| 知りたいこと | 見る場所 |
|---|---|
| 現在のカラム、型、索引、制約 | スキーマファイル（`infra/schema/`） |
| テーブルの存在と外部キーの関係 | `database.md`のカラムを省いたER図 |
| テーブルの役割、担当するモジュール | `database.md`のER図に添えたテーブル一覧 |
| 概念とその関係 | TypeSpecのモデル |
| 保持期間 | `standards.md`の該当行と、担当する機能の規則とその判断の欄 |
| 型の選び方、制約の置き方 | `database.md` |
| スキーマの変え方と適用の仕方 | `schema-management.md` |
| データが消えるまでの横断的な扱い | `lifecycle.md` |

ER図にはカラムを描かず、テーブルの存在と外部キーだけを描く。カラムを描けばスキーマファイルの複製になる。一方、テーブルの役割と書き込むモジュールはスキーマファイルからは読めないので、テーブル一覧として手で書く。テーブル一覧のうち、テーブル名の集合、テーブル種別（`LOGGED`か`UNLOGGED`か）、テナントカラムが主キーに含まれるかどうかはスキーマファイルから機械的に決まるので、両者の一致を検査する。

スキーマファイルに求める性質は三つある。フォーマットがDDLか、DBMS非依存のスキーマ言語かは本質ではない。

| 性質 | 理由 |
|---|---|
| 宣言的で収束する | マイグレーションの積み上げではなく現在の構造を書く。差分は工具が計算する |
| 空のデータベースからの収束をCIで検査できる | ファイルが現在の構造と一致していることを人の注意力に頼らない |
| DBMS固有の制約を表現できる | 部分索引、式を含む制約、レコード単位のアクセス制御 |

DDLと宣言的な差分適用ツールの組み合わせ、ORMやスキーマ定義言語のいずれもが最初の二つを満たしうる。三つ目で抽象化された言語は不利になり、表現できない制約の分だけ規則の強制点がアプリケーション側へ移る。

`database.md`では、型の選択、制約をどの層に置くか、テナントカラムを設ける条件を定める。制約に置いてよいのは長さのように安定した構造上の境界に限る。変わりうる入力規則を入れると、規則が変わるたびにすべてのデプロイ先でスキーマ移行が必要になり、「実装の不具合だけが落ちる場所」という役割が崩れる。

`schema-management.md`は、スキーマを変える人のための文書である。**構造の変更は、拡張と縮小の段階に分けて書く。** 先に新しい形を足して新旧の両方が動く状態を作り、書き込みを移し、読み出しを移し、最後に古い形を落とす。一段でやると、デプロイの途中で必ず新旧が同時に動く瞬間に耐えられない。後退できる範囲を、段ごとに明示する。構造差分で表現できないデータ移行の置き場所と実行の時点、適用をアプリケーションの起動から切り離す理由、差分適用ツールの性質から来る規則もここに置く。コマンドと実行順はスキーマファイルの隣の手順書に書く。

`lifecycle.md`では、個々の保持期間ではなく、データが入ってから消えるまでを横断して見たときにだけ現れる設計を扱う。データの区分ごとの消え方、削除と匿名化の判断基準、テナントの退去、暗号学的消去で消えるものと残るもの、そして削除したデータがバックアップの復元で戻る問題である。最後の問題はどの個別の文書にも属さないので、この文書で扱わなければどこにも書かれない。

### 4.10 design/security/authorization.md

認可はモジュールごとの小節ではなく独立したファイルにする。認可を確かめたい人は「このモジュールの認可」ではなくプロダクト全体の認可を知りたい。

主体の種類とその資格情報、境界ごとに受け入れる主体の制限、スコープの名前空間、テナント境界の規則を層ごとに書き、境界の一般規則も定める。テナント分離の規則はこの文書を一次情報源とし、層ごとに何をどう検証するかまで書く。

判断に使う要素を**主体・対象・行為・環境**の四つに分けて語彙を決めておく。属性による認可（ABAC）へ進むときも、役割だけで足りているときも、この分け方なら「役割の名前」と「その役割が実際に判断へ与える属性」を混同せずに済む。

**各規則に検証手段を併記する。** 認可の規則は、破れても正常系のテストが緑のまま通る種類の規則である。検証手段の書かれていない行は、守られているかどうかを誰も知らない。

**この文書には権限の割り当て表を書かない。** どの操作にどのスコープが要るかは契約データであり、TypeSpecの注釈で定める。散文へ写すと同じ対応表が二つになり、検査されない側が古くなる。網羅した割り当て表が必要なら注釈から生成する。ここに書くのは、操作名からスコープが自明でないものだけを理由とともに挙げた表である。

「最後の管理者は停止できない」のような業務上の判断は、認可の割り当てではなく、その機能の規則として置き、理由を判断の欄に書く。

### 4.11 design/security/threat-model.md

ほかの文書はプロダクトが何をするかを書く。だから実装された制御が正しく働いているかは照合できる。**応えるべき制御がそもそも無いとき、その欠落はどの記述とも矛盾しない。** シナリオが無く、規範が無く、テストが無く、負債の一覧にも載らない。何も落ちない。この文書はその一段上を引き受け、欠落を記述として存在させる。

§4.10が「認可の規則は破れても正常系のテストが緑のまま通る」と言うのと同じ構造が、一段上にもある。**制御が最初から無ければ、破れる規則すら無い。**

信頼境界と資産を先に置く。境界は**そこで何を信用しないか**とともに書く。信用しないものが書かれていない境界は線でしかなく、越えるときに何を検査すべきかを言えない。資産ごとに、失われた場合の影響と一次情報の所在を書く。この二つが、脅威を数え上げるときの網になる。

脅威は境界ごとに、分類の型を一度通して列挙する。**分類は網羅を保証しないが、見落としの偏りを減らす。** 一つの型を選び、その語彙を閉じた集合として決めておく。攻撃木や攻撃ライブラリは、網羅性の主張が弱いわりに維持の費用が高い。

各脅威に安定した識別子を与える。**境界や分類を識別子に埋めない。** どちらも系が変われば付け替わるもので、埋めた識別子はその時点で嘘になる。分類は列で持てば、付け替えは列の変更で済む。当てはまらなくなった脅威は削除せず、後継か理由を添えて退役させる。消すと、それを検討したという事実まで消える。

**応える制御は、既に存在する識別子で名指しする。** 規範シナリオ、採用した外部規範、別の一次情報文書の規則である。制御の側に第二の識別子を作らない。同じ制御が二つの名前を持てば、片方だけが更新される。

状態の語彙は閉じた集合にし、少なくとも「応える制御がある」「無い」「設けないと決めた」を区別する。さらに**「何も無い」と「あるが規範として書かれていない」を分ける。** 手順書の指示、デプロイへの要求、道具立ての性質として実在する保護は、規範ではないので検査やテストの対象にならないが、皆無とは違う。状態だけでは差を運べないので、制御の列に運ばせる。

**是正を担うwork itemをこの文書に書かない。** 現在状態の文書は今あるものを書く場所であり、まだ無い制御への前方参照は、そのwork itemが完了して移動した時点で腐る。対応はwork itemの側が脅威の識別子を名指すことで持ち、向きを一方向に保つ。

**応える制御が無い行を、別の負債ファイルへ出さない。** 欠落こそがこの文書の主な出力である。切り出すと、一覧を読み終えた人が欠落に気づかないまま読み終える。制御を設けないと決めた脅威には、**その決定を見直す条件**を必ず添える。条件の無い受容は、名前のついた放置である。

**網羅を主張しない。** 書かれていないことが「検討して問題なしと判断した」と読まれると、この文書は無いより悪くなる。冒頭でそう明示し、あわせて**見直しの契機**を定める。信頼境界や主体の種類が増えたとき、外部連携が加わったとき、新しい種類のシークレット、個人データ、後から証明を求められる記録を扱い始めたときである。契機を現在状態の同期の手順へ繋げられないなら、この文書は作らないほうがよい。書いた直後から古くなるからである。

**書くのは何が起こりうるかであって、どうやるかではない。** 再現手順、具体的なパラメーター、未対応の経路の詳細は仕様に置かない。

### 4.12 design/application/frontend.md、user-interface.md、design/security/secrets.md

`frontend.md`は、Webフロントエンド・アプリケーションの設計を記載する。冒頭で、対象がブラウザー上で動くアプリケーションであることと、対象の画面の種類を示す。「データをどこに置くか」のような記述は、前提がなければバックエンドの話として読まれるためである。記載するのは、コードの置き場所の判定基準、ルーティング、データの取得と画面の状態の置き場所、ビルドと配信、テスト、依存の宣言、開発時の作業である。ディレクトリの配置と依存の向きは`structure.md`に記載し、ここでは繰り返さない。主に使うライブラリは名前と選定理由を記載し、バージョンはパッケージの宣言に任せる。

`user-interface.md`は、画面を跨いで揃える情報の順序、操作、表示状態、フォーム、一覧、エラーの文言、国際化、アクセシビリティの実装手段を記載する。画面ごとの文言と見た目を複製せず、実装とローカライズ辞書を参照する。アクセシビリティの規範そのものは`standards.md`に置き、ここには規範の各行を満たす手段だけを書く。

二つを一つにしないのは読者が違うからである。UIの規範は画面を作る人が読み、コードの分け方はコードを足す人が読む。

`secrets.md`ではシークレット、暗号鍵、署名鍵、証明書の生成、保存、配布、利用、ローテーション、失効、廃棄、復旧を扱う。個別モジュールの鍵ライフサイクルはその詳細仕様を参照する。

### 4.13 verification/

検証設計では、要求ごとに静的解析、単体、結合、システム受入、負荷、障害試験、復元試験、運用確認のどの証拠を必要とするかを定める。テストコードや実行結果を写さず、標準タスク、証拠の保存先、合否条件を参照する。

機能の正常経路だけでなく、品質要求、構成要素間の接続、縮退、切替、復元をシステム境界で確認する。実環境が必要で未実施の検証は、設計上の仮定や参照構成と区別して残す。

### 4.14 scenarios.feature.md

一つのモジュールが単独で満たし検証できる振る舞いは、そのモジュールで定める。
複数のモジュールが協調して初めて成り立つ振る舞いだけをここへ置き、参加するモジュールを名指す。
システム全体のシナリオは、[仕様フォーマットの要件と例](specification-format.md#6-要件と例)が定める Gherkin 形式で書く。

モジュールごとの断片へ分割すると、本当の保証がどこにも書かれていない状態になる。

複数のモジュールにまたがる呼び出し順序を、独立した文書として作らない。それは`When`と`Then`を繰り返す例として書くか、組み立て方の設計なら`architecture/runtime.md`へ書く。**振る舞いを仕様化するのと同時に、同じファイルに書く。** 後から追加する成果物ではない。

## 7. 導入・プロダクト文書

### 7.1 リポジトリREADME

一文のプロダクト説明、起動コマンド、そして三つの入口（`docs/requirements/product-overview.md`、`docs/README.md`、`CONTRIBUTING.md`）へのリンクだけを置く。README自身に仕様を書かない。

### 7.2 product-overview.md

解決する問題、対象ユーザー、**対象外とその引き受け先**を書く。対象外は、担わないものと代わりに誰が担うかを対にする。

対象範囲は論理アーキテクチャの責務表を参照して宣言し、機能の箇条書きにしない。機能が増えるたびに一行増え、誰も消さないので実装済み機能の不完全な変更履歴になる。責務表なら、変わるのはモジュールが増減したときだけである。

成功条件を置かない。書かれる項目は、SLOと同じ事実か、リポジトリで検証できない事業側の指標のどちらかになる。

### 7.3 CONTRIBUTING と CHANGELOG

CONTRIBUTING は手順を再掲せず、開発文書を指す。
仕様影響の宣言、仕様から実装へ進む順序、生成物の更新、変更の記録は[仕様先行の開発ワークフロー](../development/specification-first-workflow.md)へ委ねる。
CI が走らせる検査の一覧は CI 定義に書き、ここへ複製しない。

CHANGELOGには利用者に影響するリリース済み変更だけを記録する。非推奨の規則は`design/application/api-guidelines.md`で定め、CHANGELOGはその告知である。

## 8. 開発文書

**配置:** `docs/development/`

開発文書には、開発環境の用意、標準タスク、変更と検証の進め方を書く。
製品の振る舞いと守るべき境界は、担当する仕様と設計へ書く。

内容は、手元で実行するもの、パイプラインが走らせるもの、コードの書き方、テストの水準、設定である。書くべきものが無いものは作らない。

### 8.1 手元で実行するもの

開発環境の用意、ビルド、コード生成、成果物の作り方を書く。ツールのバージョンは固定し、手元とCIで同じバージョンを使う。外部依存にはローカル代替を用意し、本番の資格情報を手元へ置かない。

生成文書は、入力となる一次情報と実行する標準タスクを示す。
生成物は手で編集せず、一次情報の変更後に再生成する。
Git で追跡する生成物は差分をコミットへ含め、`site/` と `spec/generated/` のように追跡しない出力は含めない。

### 8.2 CIが走らせるもの

一覧はCIに定義し、この文書は方針と理由だけを書く。この体系が要求する検査は次のとおり。

| 検査 | 内容 |
|---|---|
| 整形、静的検査、依存方向 | 構造上の規則違反 |
| 仕様の文法 | ファイルの構成、`Guard`のフォーマット、`Adoption`と`Strength`の値、後継IDの実在 |
| 識別子 | 一意性、退役IDの再利用、`affected_spec`の解決 |
| 状態遷移 | `State`列がTypeSpecの列挙値と一致すること、`Guard`の式が解析できること |
| 規範の証拠 | `standards.md`の各行に対応するテストが存在すること |
| 生成物の乖離 | 再生成した結果とコミット済み生成物の一致 |
| スキーマの収束 | 空のデータベースに対してスキーマファイルが収束すること |
| 単体、統合、契約 | 振る舞いの正しさ |
| アクセシビリティ | `standards.md`の該当行に対応する自動検査 |

失敗した検査を恒常的に無効化しない。無効化するときは対応するwork itemを作る。網羅率を単独の判定基準にせず、シナリオIDに対応するテストの存在を検査する。連続して不安定なテストには担当者と期限を定めたwork itemを作り、期限内に修復するか削除する。隔離したまま放置されたテストは、検査があるという誤った安心を与えるため削除する。

**これらの検査がすべて通っても、保証されるのは文書どうしの整合である。** 仕様が現実と合っているかを確かめるのはテストと実際の観測だけであり、検査の緑をその代わりにしない。

### 8.3 コーディングスタイル

`coding-style.md`を置く。
コードを書くときとレビューするときに共通して使う判断の視点を示し、命名、コメント、関数、制御構造、抽象化、テストコード、依存関係を扱う。

各指針には理由を添える。
理由があれば、状況が変わったときに指針を適用するか、見直すかを判断できる。

モジュールやサービスの境界は設計文書で、外部APIの契約はTypeSpecで、テスト水準とテストダブルはテスト方針で定める。
整形と静的検査は機械検査の設定を一次情報源とし、コーディングスタイルへ複製しない。

本文は特定のリポジトリに依存しない形で一つのファイルにまとめ、公開された言語別スタイルガイドを表で示す。
言語固有の命名、構文、整形はその表から原典を参照する。

### 8.4 テスト

要件は機能仕様に書き、受け入れの例は任意の付録として置く。
テストの水準、実行境界、実物にする依存、テストダブルは[テスト方針](../development/testing.md)が定める。
故障モデルから境界を選ぶ方法、RED と変更耐性の証拠、`//spec:covers` の形式は[仕様先行の開発ワークフロー](../development/specification-first-workflow.md)が定める。
この文書に別のテスト水準や被験境界を定義しない。
テストデータに実顧客の個人データを使わない。

### 8.5 設定

起動時設定は、**項目、型、デフォルト値、検証規則を宣言的なスキーマへ書き、読み込みコードとリファレンス文書の双方をそこから導く。** データベースのスキーマファイルと同じ関係である。設定を読む構造体にリファレンス用の注釈を足したものでもよい。人が書いた環境変数の一覧は複製であり、実装との乖離が必ず起きる。

宣言が一つであれば、次を機械が保証できる。

- 起動前にすべての値を検証し、欠落・フォーマット違反・範囲外・組み合わせの矛盾を**一度にまとめて**報告して起動を中止する
- `secret`と印を付けた値は、エラー、ログ、リファレンスのいずれにも出力しない
- リファレンス文書を宣言から生成し、乖離の検出を検査項目に含める

マルチテナントプロダクトでは性質の異なる三つの面が「設定」と呼ばれる。読者も一次情報源も変更経路も違うので最初に分ける。

| 面 | 読者 | 一次情報源 | 変更経路 | 監査 |
|---|---|---|---|---|
| 起動時設定 | 運用者 | 宣言的な設定スキーマ | リリース | 変更履歴 |
| テナント設定 | テナント管理者 | TypeSpec。**API契約そのもの** | 管理API | 監査イベント必須 |
| feature flag | 開発・リリース担当 | flag定義 | 実行時 | 変更履歴 |

feature flagは実験と段階的展開のためのものであり、恒久的な設定ではない。作成日、所有者、削除条件を持たせる。**flagの状態を永続データへ書き込まない。** flagを消したときにデータが解釈不能になる。

## 9. 運用文書

`operations/`では稼働後のサービス管理と保守の責任、判断基準、設計を扱う。SLOの値、可用性と復旧の機構、リリース手順、障害対応手順を複製せず、それぞれの一次情報を運用の流れへ結び付ける。

運用を担う人が読む文書は一か所に閉じない。品質目標は実装者も読み、リカバリ設計は開発と運用の両方を拘束するためである。`operations/README.md`が入口となり、要求、設計、開発手順、運用手順書を参照する。

| 内容 | それが変わると振る舞いか境界が変わるか | 置き場所 |
|---|---|---|
| SLO、RPO、RTOの目標値と測定境界 | 変わる。守ると約束した水準である | `docs/requirements/quality.md` |
| 可用性、冗長性、復旧の設計 | 変わる。目標を満たす機構である | `docs/design/reliability/` |
| リリースと後退の手順 | 変わらない。やり方の話である | `docs/development/` |
| 運用と障害対応の手順 | 変わらない | `docs/runbooks/<name>.md` |

`backup-and-recovery`のような名前が二か所に分かれるのは分割ではない。**もともと別の種類が一つのファイル名に同居していた**ということである。目標値は宣言であり、復元の手順は運用手順書である。

**運用手順書を、それが操作するインフラの構成ファイルの隣へ置かない。** 構成ファイルの隣は変更する人にとって近いが、**手順を探す人にとっては遠い。** 当番担当者は「どのディレクトリの構成ファイルの話か」を知らない状態で呼び出される。あるコンポーネントを動かすためのREADMEはそのコンポーネントの隣でよいが、運用手順書は**読み始める時点で対象が分かっていない**ことが前提である。

### 9.1 品質要求としてのSLO

可用性、遅延、適時性の目標値を定める。他の文書はSLO IDを参照し、数値を再掲しない。

```markdown
| ID | SLI | Good event | Objective | Window |
|---|---|---|---|---|
| SLO-<NAME>-<NNN> | <何を測るか> | <良い事象の定義> | <目標値> | <評価する期間> |
```

顧客と約束する値（SLA）と運用で目標にする値（SLO）は別の数字である。SLOをSLAより厳しくし、その差をerror budgetとして扱う。同一にすると、budgetを使い切った時点で契約違反になる。

**指標は「何を測るか」と「どう測るか」を分けて書く。** 前者（利用者から見た成功の定義）は滅多に変わらず、後者（どのデータをどこで集めるか）は計装のたびに変わる。分けずに書くと、集計方法を直しただけで約束が変わったように見える。遅延をどこからどこまでで測るか、分母に何を含めるか、計画停止を停止時間に数えるかは、後者として必ず添える。

**budgetを使い切ったときに何をするかを、目標値と同じ場所に書く。** 決めていないと、error budgetは達成率の飾りになる。アラートは瞬間値の閾値ではなく**消費の速さ**で鳴らし、速い消費と遅い消費で深刻度と対応先の運用手順書を分ける。

```markdown
| Alert | Condition | Severity | 運用手順書 |
|---|---|---|---|
| <名前> | <消費の速さ、または検査の失敗> | <深刻度> | <運用手順書のファイル名> |
```

### 9.2 リリースと後退

**配置:** `docs/development/`。手順であって宣言ではない。

段階的な展開の順序と、各段階で何を何分見るかを書く。先行デプロイには負荷のあるテナントを必ず含める。低トラフィックの対象だけでは、スロットリングや資源の枯渇を再現しない。

**後退の基準は、判断する人が迷わない形——数値と観測窓——で書く。** 「様子がおかしければ戻す」は基準ではない。判断に使う指標は、段階的な展開の最中に実際に見えているものに限る。flagで無効化できる変更は、デプロイの後退より先にflagを戻す。

### 9.3 バックアップと復旧

**配置:** 目標値（RPO / RTO）は`docs/requirements/quality.md`へ、復旧の設計と順序は`docs/design/reliability/recovery.md`へ、実際に手を動かす手順は`docs/runbooks/`へ置く。

データの種類ごとに、取得方式、RPO、RTO、復元試験の頻度を定める。復旧の順序は縮退の順序と逆にする。最後に落とすものを最初に戻す。復元試験では、`design/security/authorization.md`のテナント境界に従い、別テナントのデータが混在していないことを確認する。

**バックアップではなく復旧を設計する。** 取れていることは、戻せることを意味しない。**試験していない復旧経路は、無いものとして扱う。**

データを失う原因は障害だけではない。運用の誤りやアプリケーションの不具合による論理的な破損の方が多く、複製では守れない。壊れた状態もそのまま複製されるからである。守りを段で書く。**論理削除**（取り消せる猶予）、**バックアップと復元**（過去の一点へ戻す）、**早期検知**（壊れていることに気付く仕組み）の三段について、どの損失に備えるかを明示する。検知が無いと、保持期間を過ぎてから破損に気付き、戻す先が残っていないという結末になる。

### 9.4 運用手順書

**配置:** `docs/runbooks/<name>.md`。

運用手順書は障害時のものに限らない。**人が手で実行する運用作業一つにつき一つ置く。** アラートへの対応、定期作業、手動の運用操作が同じ形に収まる。

```markdown
# <作業またはアラートの名前>

## 着手条件
<いつこれを開くか。アラート名と、対応するSLO>

## 最初に確認すること
<影響範囲の切り分け。依存先の状態。直近の変更>

## 実施
<手順。一つずつ、戻せるかどうかを添えて>

## 確認
<終わったと言える条件>

## 失敗したとき
<誰へ、何分で上げるか>
```

障害対応では、**手順の前に体制を決めておく。** 誰が指揮を執り、誰が実作業をし、誰が記録と連絡を担当するか、そしてどの水準で宣言するか。これが決まっていないと、最初の数分が役割の調整に消える。役割は人ではなく役で書く。

ディレクトリ名が種類そのものなので、この下をさらに分けない。索引が要るようになったら`docs/runbooks/README.md`に置く。

障害の事後記録は、対策が恒久的な規則になった時点で、その規則を定める仕様へ反映する。記録そのものの形式は本ガイドで定めない。**個人の責任を問う書き方をしないこと**だけを決めておく。原因を人に帰す記録は、次から事実が出てこなくなる。

## 10. AIと人間の共同運用

### 10.1 文脈の経済

一つの変更のために仕様の全文を読ませない。読み始める資料はwork itemの`initial_context`に列挙し、**何を読まないか**も明示する。残りは要求IDや用語から場所を引く仕組みで到達する。

機能ごとに仕様を一つの文書へまとめているため、変更する機能の仕様だけを読めばよい。複数の機能にまたがる仕組みはモジュールの`design/`、代替案を比べた判断は`design/decisions.md`、規範は`standards.md`を開く。

仕様、実装、テストは機能名をそろえて対応させるが、文書の機能群と実装の層まで同じ深さにはしない。
共有ポート、横断設計、外側の配線テストはその所有箇所に残し、機能ごとに複製しない。
配置から生成した機能地図を入口にし、規則の変更、具体例の追加、内部の設計判断で読む範囲を分ける。

### 10.2 AIに任せやすい作業

- ファイルの構成に沿った初稿の作成
- 用語の不一致と、モジュール間の語義衝突の検出
- 境界を選ぶ判断手順に沿った入力の収集、制約の適用、候補の比較と記録
- 仕様、TypeSpec、スキーマ、テストの不整合候補の検出
- `Statement`が標準の側から書かれている行の指摘、正常系しかないシナリオへの`ALT`候補の提示
- コード変更から更新対象の仕様の候補を提示し、仕様の差分から完了記録の要約を作成

### 10.3 人間が担う作業

- プロダクトの目的、対象ユーザー、対象外の線引き
- 新しい業務概念の意味、原子性と認可の保証、境界を選ぶ判断手順が相談を求めるモジュールの分割と統合
- ドメイン用語と業務上の意味
- 外部規範の`Adoption`——どこまで従い、どこを提供しないか
- 許容するセキュリティ・運用リスク
- 現在の設計判断と見直し条件

### 10.4 レビューの確認項目

- `README.md`が境界の宣言になっているか。文書の案内や計画になっていないか
- `Statement`がプロダクトの側から書かれているか。テストがあるか
- `Guard`が評価できる式で書かれているか
- シナリオが一つの振る舞いだけを述べているか
- 判断の理由が、それが正当化する規則やモデルのそばに書かれているか。`design/decisions.md`の判断が代替案と再検討の条件を持ち、見出しが観点名になっていないか
- 設計の話題の索引で、「該当なし」の理由が実態と合っているか。設計がファイルの列挙になっていないか
- 機能仕様の操作が一つの H3 に一つずつ置かれ、要約表の値が規則文と一致しているか
- 権限の割り当てを、TypeSpecの注釈と散文の両方に定義していないか
- 実装から読み取れる情報を図や表に描き直していないか
- 変更時点の比較検討が仕様側へ流れ込んでいないか

## 12. 導入順序

1. README、product overview、開発環境とCIの最小構成
2. 論理アーキテクチャのモジュールの責務表と構成
3. 主要モジュールの`README.md`、TypeSpec、機能仕様と例の付録
4. work itemの形式と、仕様の文法検査
5. `docs/design/application/api-guidelines.md`、`docs/design/security/authorization.md`
6. 各モジュールの`standards.md`——プロトコル、アクセシビリティ、法令
7. スキーマファイルと`docs/design/data/database.md`
8. `docs/design/architecture/`と`docs/design/`の各領域、`docs/design/verification/`、`docs/operations/`、運用手順書
9. 設定リファレンスの生成、追跡ページの生成、機械検査

開発環境とCIを最初に置くのは、生成と検査の土台がないと仕様が単なる散文になるためである。work itemの形式を早く決めるのは、それが無いと変更時点の検討が仕様へ流れ込むためである。
