# リカバリ設計

この文書は、IdMagic のデータが失われたり壊れたりしたときに、何をどの手段で過去の状態へ戻すかを定める。
RPO と RTO の目標値は[品質要求](../../requirements/quality.md)、実際に手を動かす手順は[バックアップ、復元、災害復旧のランブック](../../runbooks/backup-restore-dr.md)が持つ。
物理障害に対する冗長性と切り替えは[可用性設計](availability.md)が持つ。

**取れていることは、戻せることを意味しない。**
この文書は、バックアップの取得ではなく復旧の経路を設計する。
試験していない復旧経路は、ないものとして扱う。

## 保護の三段

データの失われ方ごとに、受け持つ段が違う。
一つの段が他の段を代替することはない。
たとえばレプリカは物理障害への可用性を高めるが、誤操作やアプリケーションによる論理破損も複製するので、復元を代替しない。

| 段 | 受け持つ失われ方 | 現状 |
| --- | --- | --- |
| 論理削除 | 管理者または利用者の誤操作による削除 | 利用者だけが `PendingDeletion` の猶予期間を持つ。他のオブジェクトは物理的に削除するので、この段を持たない |
| バックアップと復元 | 論理破損、誤操作、データベースの物理的な喪失、リージョンの喪失 | 論理バックアップの経路は構成ファイルあり。PITR とリージョン外への複製は設計上の想定 |
| 早期検知 | 破損に、バックアップの保持期間内に気付くこと | ほぼ空である。下記を参照 |

削除と匿名化の使い分けは[データライフサイクル設計](../data/lifecycle.md#削除と匿名化の使い分け)が持つ。

### 早期検知の欠落

破損に気付くのが保持期間の後になると、戻す先のバックアップが残っていない。
早期検知の段は、次のどれも持たない。

- 稼働中のデータベースに対して、整合性の検査を定期的に実行する仕組み。`idmagic-batch restore-consistency-check` は復元の直後にだけ実行する。
- バックアップの取得の失敗と、復元ドリルの失敗を通知するアラート。
- 件数の急な減少のような、誤操作による大量削除の兆候を知らせる指標。

この欠落のため、論理破損と誤操作に対する保護は、利用者の猶予期間と、誰かが偶然気付くことに依存している。

## データの種類ごとの復旧

データの種類は[データライフサイクル設計](../data/lifecycle.md#データの区分と消え方)の区分に従い、構成を加える。
「現状」の区分は[可用性設計](availability.md#記述の区分)と同じである。

| データの種類 | 取得方式 | RPO / RTO | 復元試験 |
| --- | --- | --- | --- |
| 業務データ | `pg_dump` による論理バックアップ（構成ファイルあり）。本番はマネージドサービスの自動バックアップと PITR を正本とする（設計上の想定） | 未確定 | ローカルの `mise run restore-drill` で、テナント、利用者、クライアントが 0 件でないこと、各テナントの有効な署名鍵、ジョブの重複がないこと、一時テーブルが空であることを確かめる。本番のバックアップからの復元演習は未実施 |
| 短命な認証状態 | 取得しない。復元の直後に空にし、利用者の操作で再生成させる | 対象外。復元の時点で、認可の途中にあった利用者はやり直しになる | 整合性検査が、一時テーブルが空であることを確かめる |
| 監査イベント | 業務データと同じバックアップに含まれる | 業務データと同じく未確定。取得より後の監査イベントは、復元で失われる | 専用の検査はない |
| 署名鍵 | 鍵をデータベースに置く構成では、業務データのバックアップに含まれる。外部の鍵管理に置く構成では、鍵管理自身のスナップショット | 未確定 | 整合性検査が、各テナントが有効な署名鍵の行を持つことを確かめる。外部の鍵管理を含む演習は未実施 |
| データ暗号鍵 | ラップした DEK は業務データのバックアップに含まれる。マスター鍵は OpenBao 自身のバックアップ手段で別に保護する | 未確定 | 未実施 |
| 資産 | PostgreSQL に置くので、業務データと同じバックアップに含まれる | 業務データと同じく未確定 | 専用の検査はない |
| 構成 | 構成ファイルは Git が持つ。起動時シークレットは外部のシークレットストアが持つ。DNS と証明書は再設定する | 未確定 | 未実施 |

復元試験の頻度は次のとおりとする。

| 試験 | 頻度 | 現状 |
| --- | --- | --- |
| ローカルの復旧ドリル（`mise run restore-drill`） | 四半期に一回以上 | 2026-08-01 に一回実施し、結果をランブックに記録した |
| 本番のバックアップから使い捨ての環境への復元 | 月に一回 | 設計上の想定。未実施 |
| 外部の鍵管理を含む復元 | 本番の復元と同じ頻度 | 開発環境に鍵管理のサービスがないため未実施 |

ローカルの復旧ドリルの時間は、本番のデータ量、外部の鍵管理、ネットワーク、承認手順を含まない。
したがって、ドリルの結果を本番の RTO の根拠にしない。
本番の RPO と RTO は、高可用性の構成と復旧の手順を具体化した後に確定し、品質要求へ目標として加える。

バックアップの取得、保管先、保持期間の具体は[プラットフォーム設計](../infrastructure/platform.md#バックアップと復旧)が持つ。
バックアップの保持期間は、消去の要求との関係でも決まる。
復元すると取得より後に消去した利用者や破棄した DEK が戻る問題は、[データライフサイクル設計](../data/lifecycle.md#バックアップとの相互作用)が持つ。

## 鍵素材

鍵素材の喪失は、データベースの復元では取り戻せない。
データベースのバックアップが持つのは、署名鍵の公開鍵の写しと、マスター鍵でラップした DEK だけの場合があるためである。

| 失うもの | 結果 | 復旧の手段 |
| --- | --- | --- |
| データ暗号鍵のマスター鍵 | すべてのテナントのラップした DEK を恒久的にアンラップできなくなる。`DestroyTenantDataKey` が意図して実現する暗号学的消去と同じ結果が、事故として起きる | マスター鍵のバックアップから戻す以外にない。バックアップの取得も復旧ドリルも、PostgreSQL とは別に計画して実施する |
| 外部の鍵管理に置いた署名鍵 | その鍵で署名したトークンを検証できなくなる | 鍵管理のスナップショットから戻す。戻せなければ新しい鍵へ緊急に交代し、古い `kid` のトークンを失効扱いにする |
| データベースに置いた署名鍵 | 業務データと同時に失われる | 業務データと一緒に復元する |

鍵の喪失をデータベースの復元で隠さない。
署名鍵の整合性検査が失敗したら、データベースの復元が成功していても新しいトークンを発行しない。
鍵の区分と所有は[シークレットと鍵の設計](../security/secrets.md)が持つ。

## 復元の順序

復元は次の順に進める。
前の段が確認できるまで、次の段へ進まない。

1. 鍵管理へ到達できることを確かめる。
2. 空のデータベースへスキーマを適用し、その後にデータだけを戻す。
3. スキーマとバージョンを検査する。
4. 短命な認証状態のテーブルを空にする。
5. 署名鍵のメタデータと、鍵管理にある鍵のバージョンが一致することを検査する。
6. `idmagic-api` を起動し、JWKS とトークンの検証で認証の中核が動くことを確かめる。
7. ワーカーを `latency_sensitive`、`default`、`bulk` の順に起動する。
8. `idmagic-batch` の CronJob を再開する。

6 から 8 は、[ロードシェディング順序](../performance/capacity.md#ロードシェディング順序)の逆である。
最後まで守る認証の中核を最初に戻し、最初に止める `bulk` と保守処理を最後に戻す。
先に止めるものを先に戻すと、戻した処理が認証の中核とデータベースの接続を取り合い、復旧の途中で縮退が再び始まる。

現在のランブックは API とワーカーを同時に起動しており、6 から 8 の順に分けていない。

復元では、[テナント境界](../security/authorization.md)に従い、別のテナントのデータが混在していないことを確かめる。
整合性検査は、件数、署名鍵、ジョブの重複を確かめるが、テナントをまたぐ参照の検査はまだ持たない。

## 災害の範囲

| 範囲 | 設計 | 現状 |
| --- | --- | --- |
| データベースの喪失 | 直近のバックアップから、新しいデータベースへ復元する | 論理バックアップの経路は構成ファイルあり |
| 誤削除 | PITR で削除の直前へ戻した使い捨ての環境から、該当する行だけを本番へ戻す。全体を巻き戻さない | PITR は設計上の想定 |
| リージョンの喪失 | 別のリージョンへ複製したバックアップから、別のリージョンに環境を作り直す。複数リージョンで同時に稼働させる構成は採らない | 設計上の想定。リージョン外への複製の構成ファイルはない |
| 鍵管理の喪失 | [鍵素材](#鍵素材)を参照 | 未実施 |
