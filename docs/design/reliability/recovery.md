# リカバリ設計

この文書は、IdMagic のデータが失われたり壊れたりしたときに、何をどの手段で過去の状態へ戻すかを定める。
RPO と RTO の目標値は[品質要求](../../requirements/quality.md)で定め、実際に手を動かす手順は[バックアップ、復元、災害復旧のランブック](../../runbooks/backup-restore-dr.md)に書く。
物理障害に備える冗長化と切り替えは[可用性設計](availability.md)で扱う。

**取れていることは、戻せることを意味しない。**
この文書は、バックアップの取得ではなく復旧の経路を設計する。
試験していない復旧経路は、ないものとして扱う。

## データ保護の三つの手段

データが失われる原因によって、効く手段が違う。
ある手段で別の手段を代用することはできない。
たとえばレプリカは物理障害に対する可用性を高めるが、誤操作やアプリケーションによる論理破損もそのまま複製するので、バックアップからの復元の代わりにならない。

| 手段 | 防ぐデータ損失 | 実装状況 |
| --- | --- | --- |
| 論理削除 | 利用者の誤操作による削除 | 構成ファイルあり。利用者は猶予期間（`PendingDeletion`）を置いてから削除する |
| バックアップと復元 | 論理破損、誤操作、データベースの物理的な喪失、リージョンの喪失 | 論理バックアップの経路は構成ファイルあり。PITR とリージョン外への複製は設計上の想定 |
| 早期検知 | 破損に気付くのが遅れ、戻す先のバックアップが保持期間を過ぎて消えること | 未実装。下記を参照 |

論理削除は利用者にだけ適用し、ほかのオブジェクトは即座に物理削除する。
すべてのテーブルに削除済みの印を置くと、すべての問い合わせにその条件が必要になり、条件を書き忘れた問い合わせが削除済みの行を返すためである。
これはテナント境界の条件の書き忘れと同じ種類の誤りであり、防ぐ仕組みを二重に用意することになる。
管理者が誤って削除したオブジェクトは、PITR から該当する行だけを戻す（[災害の範囲](#災害の範囲)）。
削除と匿名化の使い分けは[データライフサイクル設計](../data/lifecycle.md#削除と匿名化の使い分け)で定める。

### 早期検知の仕組み

破損に気付くのが保持期間の後になると、戻す先のバックアップが残っていない。
そのため、破損と誤操作に次の仕組みで気付く。

| 仕組み | 検知するもの | 実装状況 |
| --- | --- | --- |
| 整合性検査の定期実行 | 復元の直後と同じ検査（件数、署名鍵、ジョブの重複）と、テナントをまたぐ参照を、稼働中のデータベースに対して毎日実行する。失敗したらアラートを出す | 未実装。`idmagic-batch restore-consistency-check` は復元の直後にだけ実行し、テナントをまたぐ参照は検査しない |
| 削除件数の指標 | リソースの種類ごとの削除件数を指標として記録し、平常時から大きく外れたらアラートを出す。誤操作や欠陥による大量削除の兆候を捉える | 未実装 |
| バックアップのアラート | バックアップの取得と、定期的な復元試験の失敗を知らせる | 未実装 |

## データの種類ごとの復旧

データの種類は[データライフサイクル設計](../data/lifecycle.md#データの区分と消え方)の区分に従い、構成を加える。
「実装状況」の区分は[可用性設計](availability.md#実装状況の区分)と同じである。

| データの種類 | 取得方式 | RPO / RTO | 復元試験 |
| --- | --- | --- | --- |
| 業務データ | `pg_dump` による論理バックアップ（構成ファイルあり）。本番はマネージドサービスの自動バックアップと PITR を正本とする（設計上の想定） | 未確定 | ローカルの `mise run restore-drill` で、テナント、利用者、クライアントが 0 件でないこと、各テナントに有効な署名鍵があること、ジョブの重複がないこと、一時テーブルが空であることを確かめる。本番のバックアップからの復元は試験していない |
| 短命な認証状態 | 取得しない。復元の直後に空にし、利用者の操作で作り直させる | 対象外。復元の時点で認可の途中にあった利用者は、最初からやり直す | 整合性検査が、一時テーブルが空であることを確かめる |
| 監査イベント | 業務データと同じバックアップに含まれる | 業務データと同じく未確定。取得より後の監査イベントは、復元で失われる | 専用の検査はない |
| 署名鍵 | 鍵をデータベースに保存する構成では、業務データのバックアップに含まれる。鍵管理サービスに保存する構成では、そのサービスのスナップショットで取得する | 未確定 | 整合性検査が、各テナントに有効な署名鍵の行があることを確かめる。鍵管理サービスを含む復元は試験していない |
| データ暗号鍵 | ラップした DEK は業務データのバックアップに含まれる。マスター鍵は OpenBao 自身のバックアップ機能で別に取得する | 未確定 | 試験していない |
| 資産 | PostgreSQL に保存するので、業務データと同じバックアップに含まれる | 業務データと同じく未確定 | 専用の検査はない |
| 構成 | 構成ファイルは Git で管理する。起動時シークレットは外部のシークレットストアに保存する。DNS と証明書は設定し直す | 未確定 | 試験していない |

復元試験の頻度は次のとおりとする。

| 試験 | 頻度 | 実装状況 |
| --- | --- | --- |
| ローカルの復元試験（`mise run restore-drill`） | 四半期に一回以上 | 2026-08-01 に一回実施し、結果をランブックに記録した |
| 本番のバックアップから使い捨ての環境への復元 | 月に一回 | 設計上の想定。未実施 |
| 鍵管理サービスを含む復元 | 本番の復元と同じ頻度 | 開発環境に鍵管理サービスがないため未実施 |

ローカルの復元試験の所要時間には、本番のデータ量、鍵管理サービス、ネットワーク、承認手順の影響が含まれない。
したがって、この試験の結果を本番の RTO の根拠にしない。
本番の RPO と RTO は、高可用性の構成と復旧の手順を具体化した後に確定し、品質要求へ目標として加える。

バックアップの取得方法、保管先、保持期間の具体は[プラットフォーム設計](../infrastructure/platform.md#バックアップと復旧)に書く。
バックアップの保持期間は、消去の要求との兼ね合いでも決まる。
復元すると、取得より後に消去した利用者や破棄した DEK が元に戻ってしまう。
この問題の扱いは[データライフサイクル設計](../data/lifecycle.md#バックアップとの相互作用)で定める。

## 暗号鍵の喪失

暗号鍵を失った場合は、データベースを復元しても取り戻せない。
構成によっては、データベースのバックアップに含まれるのが署名鍵の公開鍵の写しと、マスター鍵でラップした DEK だけになるためである。

| 失うもの | 結果 | 復旧の手段 |
| --- | --- | --- |
| データ暗号鍵のマスター鍵 | すべてのテナントのラップした DEK を、二度とアンラップできなくなる。`DestroyTenantDataKey` が意図して行う暗号学的消去と同じことが、事故として起きる | マスター鍵のバックアップから戻す以外に手段はない。バックアップの取得も復元試験も、PostgreSQL とは別に計画して実施する |
| 鍵管理サービスに保存した署名鍵 | その鍵で署名したトークンを検証できなくなる | 鍵管理サービスのスナップショットから戻す。戻せなければ新しい鍵へ緊急に切り替え、古い `kid` で署名したトークンは失効したものとして扱う |
| データベースに保存した署名鍵 | 業務データと同時に失われる | 業務データと一緒に復元する |

データベースの復元が成功したことで、鍵を失ったことを見逃さないようにする。
署名鍵の整合性検査が失敗したら、データベースの復元が成功していても新しいトークンを発行しない。
この表は復旧の経路を示す。
失った鍵ごとに何が読めなくなり、何が残るかは[シークレット設計](../security/secrets.md#鍵とシークレットの喪失)にあり、種類ごとの管理の責任もそこで定める。

## 復元の順序

復元は次の順に進める。
各手順の確認が済むまで、次の手順へ進まない。

1. 鍵管理サービスへ到達できることを確かめる。
2. 空のデータベースへスキーマを適用し、その後にデータだけを戻す。
3. スキーマとバージョンを検査する。
4. 短命な認証状態のテーブルを空にする。
5. 署名鍵のメタデータと、鍵管理サービスにある鍵のバージョンが一致することを検査する。
6. `idmagic-api` を起動し、JWKS とトークンの検証で認証の中核が動くことを確かめる。
7. ワーカーを `latency_sensitive`、`default`、`bulk` の順に起動する。
8. `idmagic-batch` の CronJob を再開する。

手順 6 から 8 は、[ロードシェディング順序](../performance/capacity.md#ロードシェディング順序)の逆である。
過負荷時に最後まで受け付ける認証の中核を最初に戻し、最初に止める `bulk` と保守処理を最後に戻す。
逆に、先に止めるものから戻すと、戻した処理が認証の中核とデータベースの接続を奪い合い、復旧の途中でロードシェディングがまた始まる。

復元では、[テナント境界](../security/authorization.md)に従い、別のテナントのデータが混ざっていないことを確かめる。
その確認は、[早期検知の仕組み](#早期検知の仕組み)の整合性検査が含むテナントをまたぐ参照の検査で行う。

## 災害の範囲

| 範囲 | 設計 | 実装状況 |
| --- | --- | --- |
| データベースの喪失 | 直近のバックアップから、新しいデータベースへ復元する | 論理バックアップの経路は構成ファイルあり |
| 誤削除 | PITR で削除の直前へ戻した使い捨ての環境から、該当する行だけを本番へ戻す。全体を巻き戻さない | PITR は設計上の想定 |
| リージョンの喪失 | 別のリージョンへ複製したバックアップから、別のリージョンに環境を作り直す。複数リージョンで同時に稼働させる構成は採らない | 設計上の想定。リージョン外への複製の構成ファイルはない |
| 鍵管理サービスの喪失 | [暗号鍵の喪失](#暗号鍵の喪失)を参照 | 未実施 |
