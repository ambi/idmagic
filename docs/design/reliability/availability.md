# 可用性設計

この文書は、IdMagic のどの部分が壊れうるか（障害単位）と、壊れたときに何が気付き、何が止まり、どう切り替わるかを定める。
可用性の目標値は[品質要求](../../requirements/quality.md)で定め、この文書には再掲しない。
構成要素の名前とデプロイプロファイルは[デプロイメントアーキテクチャ](../../architecture/deployment.md)に従う。

## 実装状況の区分

この文書は目指す設計を書き、各行の実装状況を次の三つで示す。
切り替え時間のような値も、どの区分の値かを行ごとに明示する。

| 区分 | 意味 |
| --- | --- |
| 構成ファイルあり | リポジトリの構成ファイルまたは実装が宣言している。適用した環境での稼働と障害試験は、リポジトリから確認できない |
| 設計上の想定 | デプロイプロファイルが（仮）として選んでいるが、構成ファイルがまだない |
| 未実装 | 設計は決まっているが、構成ファイルにも実装にもまだ反映していない |

単一障害時に無停止であることは、どの障害単位についても検証していない。
構成の具体化と障害試験は、まだ行っていない。

## 障害単位ごとの検知と対処

| 障害単位 | 検知 | 影響 | 対処 | 実装状況 |
| --- | --- | --- | --- | --- |
| `idmagic-api` のプロセスまたは Pod | kubelet が `/readyz` を 5 秒ごと、`/livez` を 10 秒ごとに呼ぶ | その Pod が処理中のリクエストだけが失敗する。状態はすべて PostgreSQL にあるので、残りのレプリカが同じリクエストを処理できる | Service が準備未完了の Pod を振り分け先から外し、kubelet が応答しないコンテナを再起動する。HorizontalPodAutoscaler の下限 3 と PodDisruptionBudget の `minAvailable: 1` で稼働数を保つ | 構成ファイルあり |
| `idmagic-worker` のプロセスまたは Pod | kubelet がメトリクス用リスナーの `/livez` を呼ぶ。ジョブ取得のループがポーリング間隔の 10 倍の時間回っていなければ失敗する | その Pod が実行中のジョブが、リースの期限（デフォルト 5 分）まで止まる。レーンごとに Deployment が分かれているので、ほかのレーンは影響を受けない | kubelet が止まったプロセスを再起動する。期限が切れたジョブは別のワーカーが取得し直す。`latency_sensitive` は 2 レプリカと PodDisruptionBudget で処理枠を一つ以上残す | リースによる再取得は構成ファイルあり。`/livez` は未実装 |
| `idmagic-batch` の実行 | CronJob の失敗をアラートで知らせる | 保持期間を過ぎたデータの削除や署名鍵の世代交代が遅れる。短命な認証状態の有効期間は読み取り時に判定するので、削除の遅れで有効期間は延びない | `backoffLimit: 3` まで再実行し、`concurrencyPolicy: Forbid` で重複実行を防ぐ。3 回失敗したら人が原因を調べる | 再実行は構成ファイルあり。アラートは未実装 |
| `idmagic-frontend` の Pod | kubelet が、Caddy が自分で応答する静的な経路を Probe として呼ぶ。`/health` は `idmagic-api` へ中継されるので使わない | 静的な画面と、API への中継が、その Pod の分だけ失われる | Service とロードバランサーが振り分け先から外す。PodDisruptionBudget の `minAvailable: 1` で、ノードの退避中も一つ以上残す | 本番 3 レプリカは構成ファイルあり。Probe と PodDisruptionBudget は未実装 |
| ノード | Kubernetes のノードコントローラー | そのノードに載っているすべての Pod | 別のノードへ再配置する。レプリカをノードとゾーンに分散させておき、一つのノードの故障で全レプリカを失わないようにする | 分散配置の制約は未実装 |
| 可用性ゾーン | Kubernetes のノードコントローラー | そのゾーンのノードと、ゾーンに固定されたストレージ | 残りのゾーンのレプリカで処理を続け、別のゾーンへ再配置する | Google Cloud プロファイルのリージョンクラスターは設計上の想定。ゾーンへの分散配置の制約は未実装 |
| PostgreSQL の primary | `/readyz` の問い合わせ（期限 1 秒）の失敗と、サーキットブレーカーの開放 | 全状態が PostgreSQL にあるため、読み取りを含むすべての API とジョブが止まる。全 `idmagic-api` が同時に準備未完了になる | 待機系へ自動で切り替える。[PostgreSQL の可用性](#postgresql-の可用性)を参照 | デプロイプロファイルによる |
| エッジ | ロードバランサー自身の監視 | すべての外部からのリクエスト | マネージドサービスの冗長化に任せる | 汎用 Kubernetes はクラスターの Ingress に任せ、構成ファイルは置かない。Google Cloud の外部アプリケーションロードバランサーは設計上の想定 |
| DNS と証明書 | クラスターの外からの外形監視と、証明書の残り日数のアラート | 名前解決の失敗または証明書の期限切れで、すべての外部クライアントが接続できなくなる | 人が設定を直す。証明書は期限の 21 日前にアラートを出し、切れる前に更新する | 未実装 |
| 外部の鍵管理サービス | 鍵操作の失敗と、サーキットブレーカーの開放 | 署名とデータ暗号鍵のアンラップが失敗する。署名鍵を鍵管理サービスに保存する構成ではトークン発行が止まる | 自動の切り替えはない。ブレーカーが開いている間は呼び出しを送らず、回復を待つ。失った場合は[リカバリ設計](recovery.md#暗号鍵の喪失)に従う | ブレーカーは未実装 |
| 上流の IdP と外部 HTTP の送信先 | 呼び出しの失敗 | 外部連携のログイン、SCIM の送信、Shared Signals の送信だけが失敗する。ほかの認証経路は影響を受けない | 送信はジョブと配信の再試行が引き受ける。[再試行とキュー](../performance/scaling.md#再試行とキュー)を参照 | 構成ファイルあり |
| 監視基盤 | つねに発火し続けるアラートを外部のサービスへ送り、届かなくなったら外部のサービスが通知する。スクレイプの失敗もアラートにする | アプリケーションは動き続けるが、この表の検知の多くが働かなくなる | 人が監視基盤を復旧する | 未実装 |

監視とアラートの設計は[監視設計](../observability/monitoring.md)で扱う。

### 生存確認で検知する範囲

`idmagic-api` の `/livez` は、プロセスが HTTP で応答できることだけを確かめる。
プロセス全体が応答しなくなれば、kubelet の Probe がタイムアウトで失敗し、コンテナを再起動する。

一部のリクエストだけが止まっている状態は、生存確認の失敗として扱わない。
そうした停止のほとんどは PostgreSQL や外部サービスの応答待ちであり、再起動しても待ち先は速くならず、処理中のリクエストを失うだけである。
その状態は、アドミッションコントロールの実行中数が上限に張り付くことで観測する。

ワーカーはリクエストを受けないので、HTTP で応答できることは処理が進んでいることを意味しない。
そのため、ワーカーの `/livez` はジョブ取得のループが回っていることを確かめる。

## PostgreSQL の可用性

PostgreSQL は IdMagic の唯一の永続化先であり、primary の障害は全体の停止を意味する。
可用性を上げる手段は三つあり、それぞれ提供するものが違う。

| 手段 | 提供するもの | 提供しないもの |
| --- | --- | --- |
| マネージドサービスの高可用性構成 | 別ゾーンの待機系への自動フェイルオーバー。切り替え時間はサービスの公称値に従う | 論理破損からの復元。待機系は誤った更新もそのまま複製する |
| オペレーターによるストリーミングレプリケーション | 待機系の自動昇格。昇格の判断と接続先の切り替えをオペレーターが行う | オペレーター自身の障害への耐性。論理破損からの復元 |
| 単一インスタンス | 構成の単純さ | primary の障害からの自動復旧。復旧はバックアップからの復元になる |

どれを採るかはデプロイ先で決まる。

| デプロイプロファイル | 採用する手段 | 実装状況 |
| --- | --- | --- |
| ローカル Docker Compose | 単一インスタンス | 構成ファイルあり |
| 汎用 Kubernetes | CloudNativePG が管理するクラスター | 設計上の想定 |
| Google Cloud | Cloud SQL for PostgreSQL の `REGIONAL` 構成 | 設計上の想定 |

フェイルオーバーの間、アプリケーションは次のように振る舞う。

- `/readyz` が失敗し、全 `idmagic-api` が振り分け先から外れる。準備未完了では再起動しないので、接続先が戻れば Pod はそのまま復帰する。
- サーキットブレーカーは、10 件以上の問い合わせのうち 50% 以上が失敗した時点で開き、30 秒間は問い合わせを送らずに失敗させる。値は `DB_BREAKER_*` の設定で変えられる。
- ブレーカーはプロセスごとに一つで、PostgreSQL へのすべての問い合わせで共有する。

複製では論理破損や誤操作を防げない。
過去の時点へ戻す手段は[リカバリ設計](recovery.md)で扱う。

## 健全性の確認と停止

- `/livez` は回復不能なプロセス状態だけで失敗し、一時的な依存先の障害では Pod を再起動させない。
- `/readyz` は PostgreSQL へ期限 1 秒で問い合わせ、受け付けられなければ 503 を返す。停止中と初期化中も 503 を返す。
- `/startupz` は初期化の完了後に成功する。kubelet は 3 秒間隔で 20 回まで待つ。
- 停止シグナルを受けると、`/readyz` を先に失敗させ、`DRAIN_GRACE_PERIOD_SECONDS`（デフォルト 5 秒）待ってから HTTP サーバーを停止する。Pod の終了猶予は 30 秒である。
- `/livez`、`/readyz`、`/startupz`、`/metrics` はアドミッションコントロールの対象外である。飽和したレプリカの `/readyz` を拒否すると、全レプリカが同時に振り分け先から外れ、一部のリクエストを拒否していただけの状態が全体の停止になるためである。

ロードバランサーの接続ドレインの時間と、ドレイン猶予、Pod の終了猶予の大小関係は[ネットワーク設計](../infrastructure/network.md)で定める。

## 共有状態

複数レプリカでは、セッション、認可コード、再送防止、流量制限、ログイン制限を PostgreSQL に置く。
API レプリカのプロセスメモリへ正となる状態を置かず、レプリカの再起動と増減でセキュリティ判断を変えない。
ログイン制限のストアへ到達できない場合はフェイルクローズとする。

プロセスメモリに置いてよいのは、失われても正しさが変わらないものだけである。

| プロセスメモリに置くもの | 失われたときの結果 |
| --- | --- |
| アドミッションコントロールの実行中数 | そのプロセスの実行中数が 0 から数え直される。処理中のリクエストはプロセスと一緒に終わっているので、数え直しても誤りにならない |
| サーキットブレーカーの状態 | 閉じた状態から判定し直す |

## ロードシェディング

処理能力が足りないときは、`bulk`、`default`、管理用の集計とエクスポート、動的登録、認証の中核の順に受け付けを絞る。
テナント境界、認証と認可、再送防止、流量制限、監査の完全性は、受け付けを絞るために弱めない。

順序の正本は[キャパシティ設計](../performance/capacity.md#ロードシェディング順序)のロードシェディング順序である。
順序を実現する仕組みは[スケーリング・負荷設計](../performance/scaling.md)で定める。
