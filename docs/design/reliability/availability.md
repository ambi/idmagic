# 可用性設計

この文書は、IdMagic のどの部分が壊れうるか（障害単位）と、壊れたときに何が気付き、何が止まり、どう切り替わるかを定める。
可用性の目標値は[品質要求](../../requirements/quality.md)が持ち、この文書は再掲しない。
構成要素の名前とデプロイプロファイルは[デプロイメントアーキテクチャ](../../architecture/deployment.md)に従う。

## 記述の区分

この文書の「現状」は、次の三つのどれかで書く。
切り替え時間のような値も、どの区分の値かを行ごとに明示する。

| 区分 | 意味 |
| --- | --- |
| 構成ファイルあり | リポジトリの構成ファイルまたは実装が宣言している。適用した環境での稼働と障害試験は、リポジトリから確認できない |
| 設計上の想定 | デプロイプロファイルが（仮）として選んでいるが、構成ファイルがまだない |
| 未実装 | どのデプロイプロファイルも手段を持たない |

単一障害時に無停止であることは、どの障害単位についても検証していない。
構成の具体化と障害試験は、まだ行っていない。

## 障害単位

### 検知、影響、対処

| 障害単位 | 検知 | 影響 | 対処 | 現状 |
| --- | --- | --- | --- | --- |
| `idmagic-api` のプロセスまたは Pod | kubelet が `/readyz` を 5 秒ごと、`/livez` を 10 秒ごとに呼ぶ | その Pod が処理中のリクエストだけが失敗する。状態はすべて PostgreSQL にあるので、残りのレプリカが同じリクエストを処理できる | Service が準備未完了の Pod を振り分け先から外し、kubelet が異常終了したコンテナを再起動する。HorizontalPodAutoscaler の下限 3 と PodDisruptionBudget の `minAvailable: 1` が稼働数を保つ | 構成ファイルあり。`/livez` は現在つねに成功するため、デッドロックしたプロセスは検知できない |
| `idmagic-worker` のプロセスまたは Pod | リース（デフォルト 5 分）の期限切れ | その Pod が実行中のジョブが、リースの期限まで止まる。レーンごとに Deployment が分かれているので、他のレーンは影響を受けない | 期限が切れたジョブを別のワーカーが取得し直す。`latency_sensitive` は 2 レプリカと PodDisruptionBudget で処理枠を一つ以上残す | 構成ファイルあり。ワーカーの Deployment は Probe を持たないため、応答しなくなったプロセスは再起動されない |
| `idmagic-batch` の実行 | CronJob の失敗履歴 | 保持期間を過ぎたデータの削除や署名鍵の世代交代が遅れる。短命な認証状態の有効期間は読み取り時に判定するので、削除の遅れは有効期間を延ばさない | `backoffLimit: 3` まで再実行し、`concurrencyPolicy: Forbid` で重複実行を防ぐ | 構成ファイルあり。CronJob の失敗を通知するアラートはない |
| `idmagic-frontend` の Pod | ロードバランサーのヘルスチェック（設計上の想定） | 静的な画面と、API への中継が、その Pod の分だけ失われる | ロードバランサーが振り分け先から外す | 構成ファイルあり（本番の overlay で 3 レプリカ）。Probe と PodDisruptionBudget は持たない |
| ノード | Kubernetes のノードコントローラー | そのノードに載っているすべての Pod | 別のノードへ再配置する。PodDisruptionBudget はノードの退避のような自発的な中断にだけ効き、ノードの故障には効かない | 未実装。Pod の分散配置の制約を持たないため、全レプリカが一つのノードに載りうる |
| 可用性ゾーン | Kubernetes のノードコントローラー | そのゾーンのノードと、ゾーンに固定されたストレージ | 別のゾーンのノードへ再配置する | Google Cloud プロファイルはリージョンクラスターを選んでいる（設計上の想定）。ゾーンをまたぐ分散配置の制約は未実装 |
| PostgreSQL の primary | `/readyz` の問い合わせ（期限 1 秒）の失敗と、サーキットブレーカーの開放 | 全状態が PostgreSQL にあるため、読み取りを含むすべての API とジョブが止まる。全 `idmagic-api` が同時に準備未完了になる | デプロイプロファイルによる。[PostgreSQL の可用性](#postgresql-の可用性)を参照 | デプロイプロファイルによる |
| エッジ | ロードバランサー自身の監視 | すべての外部からのリクエスト | マネージドサービスの冗長性に任せる | 汎用 Kubernetes はクラスターの Ingress に任せ、構成ファイルを持たない。Google Cloud は外部アプリケーションロードバランサー（設計上の想定） |
| DNS と証明書 | 外形監視 | 名前解決の失敗または証明書の期限切れで、すべての外部クライアントが接続できない | 手作業 | 未実装。外形監視も証明書の期限の監視もない |
| 外部の鍵プロバイダー | 鍵操作の失敗 | 署名とデータ暗号鍵のアンラップが失敗する。署名鍵を外部に置く構成ではトークン発行が止まる | 自動の切り替えはない。[リカバリ設計](recovery.md#鍵素材)に従う | 未実装。呼び出しは一回だけで、再試行も遮断も持たない |
| 上流の IdP と外部 HTTP の送信先 | 呼び出しの失敗 | 外部連携のログイン、SCIM の送信、Shared Signals の送信だけが失敗する。他の認証経路は影響を受けない | 送信はジョブと配信の再試行が引き受ける。[再試行とキュー](../performance/scaling.md#再試行とキュー)を参照 | 構成ファイルあり。送信先ごとの遮断は持たない |
| 監視基盤 | ない | アプリケーションは動き続けるが、この表の検知の多くが働かなくなる | 手作業 | 未実装。監視基盤自体の停止とスクレイプの失敗を知らせるアラートはない |

監視とアラートの設計は[監視設計](../observability/monitoring.md)が持つ。

### 欠落が守っていないもの

| 欠落 | 守られていないこと |
| --- | --- |
| `/livez` がつねに成功する | デッドロックしたプロセスがレプリカの枠を占め続け、その分だけ処理能力が下がる |
| ワーカーが Probe を持たない | 応答しなくなったワーカーが実行レーンの枠を占め、リースが切れるまでジョブが進まない |
| Pod の分散配置の制約がない | ノードまたはゾーン一つの障害で、`idmagic-api` の全レプリカが同時に失われうる |
| PostgreSQL の自動フェイルオーバーの構成ファイルがない | primary の障害がそのまま全体の停止になり、復旧が手作業の速さに縛られる |
| 外形監視がない | DNS、証明書、エッジの障害は、内部の指標が正常なまま進む |

## PostgreSQL の可用性

PostgreSQL は IdMagic の唯一の永続化先であり、その primary の障害は全体の停止を意味する。
可用性を上げる手段は三つあり、それぞれ提供するものが違う。

| 手段 | 提供するもの | 提供しないもの |
| --- | --- | --- |
| マネージドサービスの高可用性構成 | 別ゾーンの待機系への自動フェイルオーバー。切り替え時間はサービスの公称値に従う | 論理破損からの復元。待機系は誤った更新もそのまま複製する |
| オペレーターによるストリーミングレプリケーション | 待機系の自動昇格。昇格の判断と接続先の切り替えをオペレーターが行う | オペレーター自身の障害への耐性。論理破損からの復元 |
| 単一インスタンス | 構成の単純さ | primary の障害からの自動復旧。復旧はバックアップからの復元になる |

どれを採るかはデプロイ先で決まる。

| デプロイプロファイル | 選んでいる手段 | 現状 |
| --- | --- | --- |
| ローカル Docker Compose | 単一インスタンス | 構成ファイルあり |
| 汎用 Kubernetes | CloudNativePG が管理するクラスター | 設計上の想定。構成ファイルはない |
| Google Cloud | Cloud SQL for PostgreSQL の `REGIONAL` 構成 | 設計上の想定。構成ファイルはない |

フェイルオーバーの間、アプリケーションは次のように振る舞う。

- `/readyz` が失敗し、全 `idmagic-api` が振り分け先から外れる。準備未完了は再起動を伴わないので、接続先が戻れば Pod はそのまま復帰する。
- サーキットブレーカーは、10 件以上の問い合わせのうち 50% 以上が失敗した時点で開き、30 秒間は問い合わせを送らずに失敗させる。値は `DB_BREAKER_*` の設定で変えられる。
- ブレーカーはプロセスごとに一つで、PostgreSQL へのすべての問い合わせが共有する。

複製は論理破損や誤操作を防がない。
過去の時点へ戻す手段は[リカバリ設計](recovery.md)が持つ。

## 健全性と停止

- `/livez` は回復不能なプロセス状態だけで失敗し、一時的な依存障害では Pod を再起動させない。
- `/readyz` は PostgreSQL へ期限 1 秒で問い合わせ、受け付けられなければ 503 を返す。停止中と初期化中も 503 を返す。
- `/startupz` は初期化の完了後に成功する。kubelet は 3 秒間隔で 20 回まで待つ。
- 停止シグナルを受けると、`/readyz` を先に失敗させ、`DRAIN_GRACE_PERIOD_SECONDS`（デフォルト 5 秒）待ってから HTTP サーバーを停止する。Pod の終了猶予は 30 秒である。
- `/livez`、`/readyz`、`/startupz`、`/metrics` はアドミッションコントロールの対象外である。飽和したレプリカの `/readyz` を拒否すると、全レプリカが同時に振り分け先から外れ、部分的な縮退が全体の停止になるためである。

ロードバランサーの接続ドレインの時間と、ドレイン猶予、Pod の終了猶予の大小関係は[ネットワーク設計](../infrastructure/network.md)が持つ。

## 共有状態

複数レプリカでは、セッション、認可コード、再送防止、流量制限、ログイン制限を PostgreSQL に置く。
API レプリカのプロセスメモリへ正となる状態を置かず、レプリカの再起動と増減でセキュリティ判断を変えない。
ログイン制限のストアへ到達できない場合はフェイルクローズとする。

プロセスメモリに置いてよいのは、失われても正しさが変わらないものだけである。

| プロセスメモリに置くもの | 失われたときの結果 |
| --- | --- |
| アドミッションコントロールの実行中数 | そのプロセスの実行中数が 0 から数え直される。リクエストは失われたプロセスと一緒に終わっているので、数え直しは正しい |
| サーキットブレーカーの状態 | 閉じた状態から判定し直す |

## 縮退

資源が足りないときは、`bulk`、`default`、管理集計とエクスポート、動的登録、認証コアの順に受け付けを絞る。
テナント境界、認証と認可、再送防止、流量制限、監査の完全性を縮退のために弱めない。

順序の正本は[キャパシティ設計](../performance/capacity.md#ロードシェディング順序)のロードシェディング順序である。
順序を実現する機構は[スケーリング・負荷設計](../performance/scaling.md)が持つ。
