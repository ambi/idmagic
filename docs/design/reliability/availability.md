# 可用性設計

## 障害単位

API とワーカーのプロセスまたは Pod、ノード、可用性ゾーン、PostgreSQL の primary、ゲートウェイ、DNS、証明書、外部依存、監視基盤を別の障害単位として扱う。
現在の Kubernetes 資材は複数レプリカ、PodDisruptionBudget、HPA、NetworkPolicy を持つが、PostgreSQL の自動フェイルオーバーとゾーン配置を実装しない。
単一障害時の無停止を検証済みとは扱わず、具体化と障害試験は [wi-165](../../../work-items/wi-165-high-availability-and-failover-resilience-topology.md) が担う。

## 健全性と停止

- `/livez` は回復不能なプロセス状態だけで失敗し、一時的な依存障害では Pod を再起動させない。
- `/readyz` は PostgreSQL へ短い期限で問い合わせ、受付不能なら 503 を返す。
- `/startupz` は初期化の完了後に成功する。
- 停止シグナルを受けると readiness を先に落とし、負荷分散対象から外れる猶予を置いてから HTTP サーバーを停止する。

## 共有状態

複数レプリカでは、セッション、認可コード、再送防止、流量制限、ログイン制限を PostgreSQL に置く。
API レプリカのプロセスメモリへ正となる状態を置かず、レプリカの再起動と増減でセキュリティ判断を変えない。
ログイン制限のストアへ到達できない場合はフェイルクローズとする。

## 縮退

資源不足時は、`bulk`、`default`、管理集計とエクスポート、動的登録、認証コアの順に受付を制限する。
テナント境界、認証と認可、再送防止、流量制限、監査の完全性を縮退のために弱めない。
受付制限の実装は[拡張設計](../performance/scaling.md)が持つ。
