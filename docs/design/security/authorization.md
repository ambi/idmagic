# 認可設計

認可を確かめたい読み手が知りたいのは「このモジュールの認可」ではなくプロダクト全体の認可なので、モジュールごとの節ではなく独立した文書に置く。

**この文書には権限の割り当て表を書かない。** どの操作にどのスコープが要るかは契約データであり、一次情報は TypeSpec の operation に付く `x-api-token-scopes` である。全 admin operation が宣言を含むことと、宣言したスコープが `ApiTokenScope` 語彙と双方向に対応することは、リポジトリの検査が強制する。散文の側には対応表を設けない。同じ対応を 2 か所に書くと、照合できないまま片方が古くなるためである。

## 主体の種類

| 種別 | 表す対象 | 資格情報 |
|---|---|---|
| User | 人 | ブラウザーのログインセッション、またはポータルが提示する OAuth アクセストークン |
| ApiToken | テナント運用または本人のアカウント操作のための機械アクセス | `ApiTokens` が発行し、所属テナントと本人を主体に持つ JWT |
| Client | 登録済みの連携アプリケーション | `client_secret_basic`、`client_secret_post`、`private_key_jwt`、`tls_client_auth`、`self_signed_tls_client_auth` |
| Agent | 自律的に動く実行主体 | クライアント資格情報、または外部のアテステーション (`WorkloadIdentity`) |
| DirectoryConnector | 閉域のディレクトリから取り込む実行単位 | 登録した公開鍵で署名した短命の JWT (`Sourcing`) |
| 運用者 | プロセスを起動できる実行環境 | 権限ではなく実行環境そのものが境界 (`Seeding`) |

主体の種類は境界ごとに制限する。管理 API が受け入れるのは User と ApiToken であり、Client の資格情報だけで管理操作へ到達する経路は設けない。

## スコープの語彙

ポータル境界のスコープ (`idmagic.admin` / `idmagic.account`) はブラウザーのポータルが提示する通常の OAuth アクセストークンの境界であり、アカウントポータルのトークンで管理 API を呼ぶ経路をフェイルクローズで塞ぐ。API アクセストークンはポータル境界のスコープを持たず、代わりに対象 API のリソースと操作の粒度を持つ。したがって API アクセストークンでは、**呼び出し先の操作が要求する粒度スコープがポータル境界のスコープの代わりになる**。

粒度スコープは名前空間で区切り、`read` が参照だけを、`write` が変更を許可する。名前空間をまたぐ流用はできず、あるリソースのスコープで別のリソースを操作することはない。

`account:*` のスコープは、レルムの IdMagic API を資源とする。資源の識別子はレルムの発行者識別子であり、`resource` を指定せずに発行した account スコープのトークンと API アクセストークンは、どちらもこの値を `audience` に持つ。account リソースサーバーは、スコープに加えて `audience` がリクエスト先レルムの IdMagic API を含むことを確かめ、含まないトークンを 401 `invalid_token` で拒否する。別の資源へ宛てたトークンを、同じスコープ名を持つという理由だけで受けないためである。ポータル境界のスコープだけを持つトークンは、この検査の対象にしない。

| モジュール | 名前空間 |
|---|---|
| ApiTokens | `account:*` |
| Application | `applications:*`、`account:applications_read` |
| Audit | `audit:read` |
| Authentication | `sessions:*`、`users:write`、`audit:read` |
| IdGovernance | `lifecycle-workflows:*` |
| IdManagement | `users:*`、`groups:*`、`agents:*` |
| Jobs | `jobs:read`、`jobs:cancel` |
| OAuth2 | `oauth-clients:*`、`consents:*`、`authorization-detail-types:*`、`mcp-resource-servers:*` |
| Provisioning | `provisioning:*` |
| Saml | `saml:*` |
| SharedSignals | `shared-signals:*` |
| SigningKeys | `signing-keys:*` |
| Sourcing | `scim:users:*`、`scim:groups:*` |
| Tenancy | `settings:*`、`tenants:*` |
| WorkloadIdentity | `workload-identity:*` |
| WsFederation | `wsfed:*` |

値の一覧は TypeSpec の `ApiTokenScope` で定義する。読み書きの境目は HTTP メソッドではなく、操作が対象を変更するかで決める。

## 対話セッション限定の操作

本人による API トークンの発行、一覧、失効も対話セッションに限定する。
本人向けの発行では account スコープだけを許し、一覧と失効では認証した本人と所属テナントの両方を照合する。
管理者は管理経路からテナント内の記録を扱う。

操作ごとに 1 つ以上の許可スコープを対応付ける。対話セッション限定の操作は `interactive_session` を宣言する。この対応づけはフェイルクローズである。**どのスコープを要求するかが定まっていない管理 API へは、API アクセストークンからは到達できない。** この振る舞いは [REQ-APITOKENS-004](../../modules/api-tokens/features/authentication.md) が定める。スコープを対応付けていない操作を素通しさせると、新しい管理 API を足した時点で、その 1 本だけがすべてのスコープで通るようになるからである。同じ理由で、対話セッション限定と宣言した操作も、どのスコープでも到達できない。

操作を対話セッション限定にする理由は 2 種類ある。1 つは、既存のスコープ語彙に対応がなく、スコープを新設するよりも人間の管理者に閉じるほうが安全な場合である。ReBAC の認可モデルと関係タプル、テナント横断の DEK 健全性と緊急の操作が該当する。もう 1 つは、操作自体が権限の昇格経路になる場合である。たとえば、トークン発行は任意のスコープ集合を作成でき、外部 IdP の登録は任意のユーザーとしてサインインする経路を作成できる。どちらも既存のスコープへ割り当てると、そのスコープを持つトークンへ意図せず昇格能力を与えてしまう。

## 認証の保証

認証の保証は、水準（どの要素で認証したか。`acr` と `amr`）と新しさ（いつ認証したか。`auth_time`）で表す。
水準と新しさを求める仕組みは三つあり、所有するモジュールと評価する時点が異なる。
どれも、Authentication が記録した同じ認証の事実を読み、事実の解釈を各モジュールへ複製しない。

| 仕組み | 所有 | 評価する時点 | 決めること | 仕様 |
|---|---|---|---|---|
| サインインポリシー | SignInPolicy（外部の契約は Application） | アプリへのサインイン（フェデレーションの開始と IdMagic 自身の画面） | 必要な強さ（`Password` か `Mfa`）、記憶済みの端末で `Mfa` を満たしてよいか、再認証の期限、許可するネットワーク。アプリごとのポリシーはテナントのデフォルトを上書きする | [サインインポリシー](../../modules/application/features/sign-in-policy.md) |
| 認可の要求の水準と新しさ | OAuth2 | `/authorize` | クライアントが `acr_values`、`max_age`、`prompt=login` で求める水準と新しさ | [認可](../../modules/oauth2/features/authorization.md) |
| ステップアップ認証 | Authentication | 機微な操作の要求 | 操作の直前の再認証 | [下の節](#ステップアップ認証) |

記憶済みの端末（`amr` の `tdev`）は、第二要素を省いても `acr` の水準を `urn:idmagic:acr:mfa` に上げる。
記憶済みの端末を MFA の充足と認めないのは、サインインポリシーで `allow_trusted_device` を `false` にした規則（毎回の MFA）だけである。
ステップアップ認証は水準を問わず新しさだけを求め、記憶済みの端末で第二要素を省いたことをステップアップ認証の成立として記録しない（[REQ-AUTHENTICATION-029](../../modules/authentication/features/trusted-device.md)）。
リソースサーバーが RFC 9470 で `acr_values` と `max_age` を求めた再認可では、MFA の水準を求める再認証で記憶済みの端末を充足と認めず、登録済みのどの第二要素でも満たせるようにし、満たせなければトークンを発行しない。
この規則は未実装である（[リスクと技術的負債](../architecture/risks.md)）。

水準の語彙は `urn:idmagic:acr:pwd` と `urn:idmagic:acr:mfa` の二つで、サインインポリシーの `Password` と `Mfa` に一対一で対応する。

### ステップアップ認証

機微な操作は、認可に加えて直近の再認証を求める。
直近かどうかの根拠は、要求が届いた資格情報ごとに一つに決め、資格情報をまたいで記録を持ち込まない。
規範は [REQ-AUTHENTICATION-039](../../modules/authentication/features/account-portal.md#本人によるステップアップ認証) と [REQ-AUTHENTICATION-004](../../modules/authentication/features/account-portal.md#api-トークンの発行者による本人の認証情報の操作) が定める。

| 資格情報 | 直近の再認証の根拠 | 満たさないとき |
|---|---|---|
| ポータルが提示する OAuth アクセストークン | トークンの `auth_time` | RFC 9470 の 401 `insufficient_user_authentication` で再認可を求める |
| ブラウザーのログインセッション | セッションの認証時刻とステップアップ認証の時刻 | 403 `step_up_required` |
| 管理発行の API アクセストークン | トークンの保持 | 求めない |

アクセストークンの根拠に発行時刻を使わない。
リフレッシュのたびに新しくなるので、盗んだリフレッシュトークンで直近の再認証を偽れるからである。
リフレッシュで発行するトークンは、元の付与を得た認証の `auth_time` を引き継ぐ（[REQ-OAUTH2-006](../../modules/oauth2/features/token.md)）。
ポータルは機微な操作もベアラートークンで呼ぶので（[フロントエンド設計](../application/frontend.md#api-の呼び出し)）、ポータルの再認証は再認可でトークンを新しくすることで成り立つ。
ログインセッションの記録をトークンの判定へ持ち込む案と、アクセストークンにセッションを結び付ける案は採らない。
前者は二つの資格情報の整合を自前で保つことになり、後者はセッションの Cookie の値をリソースサーバーへ渡すことになる。

## 自動所属からのロール付与

自動所属によるロール付与は、属性や所属を書ける外部連携へ権限を委ねる境界でもある。
動的 Group と上流管理 Group から `admin` と `system_admin` を付与しない。
業務ロールは、対話セッションの管理者が現在のロール一覧と式に対して明示的に委任したものだけを加える。
この承認は特定の連携元へは限定されず、該当する属性や所属を書けるすべての上流を信頼する。
詳細は [REQ-IDMANAGEMENT-092 と REQ-IDMANAGEMENT-093](../../modules/identity-management/features/group.md#実効ロールの解決) が定める。

## テナント境界

テナント分離の規則はここを一次情報とする。
各層の規則に従う外部の振る舞いは、それを実装する機能の要件が宣言する（認可は [REQ-IDMANAGEMENT-014](../../modules/identity-management/features/admin-access.md)、ページングは [REQ-SYSTEM-025](../../modules/system/features/http-api.md)、テナントの解決は [REQ-TENANCY-009](../../modules/tenancy/features/resolution.md)）。

| 層 | 規則 |
|---|---|
| 認証 | `tenant_id` は認証コンテキストから決定する。URL、本文、クエリ文字列で与えられた `sub` や `tenant_id` を信頼しない |
| 認可 | 操作者と対象リソースのテナントが一致しなければ拒否する。ロールを持つだけでは足りず、呼び出し元が有効かつ認証済みであることも合わせて要求する |
| 実行 | 非同期の実行コンテキストはその Job の `tenant_id` に固定する。`worker` は全テナントのジョブを実行するが、1 件を処理する間に見えるのは 1 つのテナントの範囲だけである |
| ページング | カーソルはテナントと絞り込み条件を束縛する。別テナントで発行されたカーソルや条件が変わったカーソルは拒否する |
| レスポンス | 別テナントのリソースは存在しないものとして扱う |

テナントを越える操作は 2 つに限る。`system_admin` ロールとデフォルト (制御面) テナントへの所属を合わせて要求する制御面の操作と、HTTP に載せず実行環境そのものを権限の境界とする `Seeding` である。

`system_admin` は予約ロールであり、保存できる対象も制限する。新しく割り当てられるのは制御面テナントの `User` と `Group` だけである。`Agent` はロールを持たない。判定の条件は対象の所属テナントであり、操作者が持つロールではない。制御面テナントの外に保存済みの値は残るが、そこから制御面の能力は生じない。

テナント解決も認可境界の一部である。テナントは `endpoint_style` が指す正規ロケーションからだけ到達でき、もう一方の経路では不在として扱う。どの経路にも一致しないリクエストをデフォルトテナントへフォールバックさせない。

## その他の境界の規則

- MCP の操作割当は接続先の登録 ID とサーバーが発行する操作の識別子へ束縛する。同名ツールと同名スコープが別の接続先にあっても割当を共有せず、削除後の同名再登録でも古い割当を使わない。対象別の検査がある操作は、接続先の割当を根拠にその検査を省略しない
- 判断に必要な情報が得られない場合は拒否する。判定を返せない場合、事実が欠けている場合、ストアへ到達できない場合のいずれも、許可へ退避しない
- 権限の有無自体を漏らさない。権限のない対象と存在しない対象は同じレスポンスにする
- 権限は下流の呼び出しへ自動的に伝播しない。代行は明示的な交換を経て、要求する権限が元の権限の部分集合であることを求める
- 状態を変えるブラウザー経路は、セッションによる認証に加えて二重送信方式の CSRF トークンと、設定済みの公開発行者と一致する `Origin` ヘッダーを検証する（[REQ-PLATFORM-004](../../modules/scenarios.feature.md)）。セッション Cookie だけでは、そのリクエストが管理 UI から出たことを証明できない
- UI での非表示は認可判定ではない

## レスポンスが決して含まないもの

- 要求者が権限を持たないテナントの識別子、名前、件数。内部のテナント情報は公開しない
- 秘密鍵素材、DEK の鍵素材、クライアントシークレット。どの権限でも取得できない
