# シークレットと鍵の設計

## 対象範囲

この文書は、IdMagic が扱うシークレット、暗号鍵、署名鍵、証明書について、区分ごとの所有者と、生成から復旧までの各段階の振る舞いを定める。

ローテーションの間隔、有効期限、鍵長のような値は書かない。
値は各 Context の仕様と[設定リファレンス](../../../CONFIGURATION.md)が持っており、ここに書けば三つ目の正本ができる。
実際に手を動かす手順も書かない。
手順は[ランブック](../../runbooks/backup-restore-dr.md)が持つ。

区分ごとの鍵ライフサイクルの詳細は [DataKeys](../../contexts/data-keys/) と [SigningKeys](../../contexts/signing-keys/) が正本である。
エンベロープ暗号の仕組みは[データベース設計](../data/database.md#可逆な秘密情報のエンベロープ暗号)が持つ。
脅威と、それに応える制御の対応は[脅威モデル](threat-model.md)が持つ。

## この文書の読み方

区分ごとの節に、生成、保存、配布、利用、ローテーション、失効、廃棄、復旧の八段階を表で置く。
段階ごとに、担い手、その段階を通ったことで成立すること、失敗したときの動作を書く。

「失敗時の動作」の列を必ず置く。
鍵の設計で後から効くのは正常時の流れではなく、鍵へ到達できないときに何が起きるかである。

実装状況を示す語は[可用性設計](../reliability/availability.md#実装状況の区分)と同じ三つを使う。
「構成ファイルあり」はリポジトリの構成ファイルか実装が宣言しているもの、「設計上の想定」はデプロイプロファイルが（仮）として選んだが構成ファイルがまだないもの、「未実装」は設計が決まっていてどちらにも反映していないものである。

## 区分と所有

| 区分 | 正本と所有者 | 主な保護 |
| --- | --- | --- |
| 起動時のシークレット | デプロイ基盤の Secret 管理 | Git へ保存せず、必要な実行単位だけへ注入する |
| クライアント資格情報 | 所有する Context の Repository | 平文を保持せず、照合できる表現だけを保存する |
| データ暗号鍵 | [DataKeys](../../contexts/data-keys/) | テナント単位の DEK と、外部または起動時のマスター鍵を分離する |
| 署名鍵と証明書 | [SigningKeys](../../contexts/signing-keys/) | 用途とテナントを分け、公開鍵の配布と秘密鍵の利用を分離する |
| TLS 証明書 | デプロイ基盤 | DNS 名と更新を基盤が所有し、アプリケーションへ秘密鍵を渡さない構成を優先する |

## 区分ごとのライフサイクル

### 起動時のシークレット

対象は、プロセスが起動時の設定として環境変数から読むシークレットである。
接続文字列、外部の鍵サービスのトークン、SMTP のパスワード、ページネーションカーソルの署名鍵がこれにあたる。
どの環境変数がシークレットかの正本は[設定リファレンス](../../../CONFIGURATION.md)であり、値を記録しない項目としてそこに並ぶ。

| 段階 | 担い手 | 成立すること | 失敗時の動作 |
| --- | --- | --- | --- |
| 生成 | デプロイする側 | 値の強度と一意性は、その資格情報を発行する側（データベース、Vault、OpenBao、SMTP サーバー）が保証する | プロダクトは生成の正しさを検査しない。唯一の例外が `PAGINATION_CURSOR_SECRET` で、未設定のときプロセスごとに 32 バイトの乱数を起動時に作る |
| 保存 | デプロイプロファイルごとの供給元 | 値が Git の構成ファイルの外にある（[起動時シークレットの供給元](#起動時シークレットの供給元)） | ローカル Docker Compose では平文で構成ファイルに入る。この構成は開発者の手元の外へ出さない |
| 配布 | デプロイプロファイル | 必要な実行単位だけが環境変数として受け取る | 必須の値が欠けると、起動時設定の検証が集約したエラーでプロセスを停止する。一部だけ検証されない設定で起動する経路はない（REQ-SYSTEM-016） |
| 利用 | `idmagic-api`、`idmagic-worker`、`idmagic-batch`、`idmagic-seed` | 値は専用の型に包まれ、文字列化、`%v`、JSON、テキストのいずれでも `[REDACTED]` を返す。生成する設定リファレンスにも値は出ない | 包みを外した値をログやエラーに載せる経路は、型の側では防げない（REQ-SYSTEM-017） |
| ローテーション | デプロイする側 | 新しい値で全プロセスを起動し直すと、古い値は使われなくなる | 稼働中のプロセスが値を読み直す経路はない。入れ替えの単位はプロセスの再起動である |
| 失効 | 資格情報を発行した側 | 古い値がその発行元で使えなくなる | プロダクトから失効させる経路はない。発行元で失効させた後もプロセスが古い値を保持し続けるため、再起動するまで接続が失敗する |
| 廃棄 | ランタイム | プロセスの終了とともに、環境変数として渡した値が消える | コンテナのイメージやコアダンプへ値が写る経路は、この設計の対象外である |
| 復旧 | シークレットの供給元 | 供給元から同じ値を取り直せる | 業務データのバックアップには含まれない。データベースを復元しても起動時のシークレットは戻らず、設定し直す |

`PAGINATION_CURSOR_SECRET` は、未設定でも起動できる唯一のシークレットであり、失敗の形が他と違う。
複数レプリカのデプロイでこれを設定し忘れると、レプリカごとに別の値が生成される。
プロセスは正常に起動し、あるレプリカが発行したカーソルを別のレプリカが `InvalidRequestError` で拒否する形で、後から現れる。

### クライアント資格情報

対象は、OAuth2 のクライアントがトークンエンドポイントで提示する `client_secret` である。
`private_key_jwt` と mTLS のクライアントはこの区分を持たず、公開クライアントも持たない。

| 段階 | 担い手 | 成立すること | 失敗時の動作 |
| --- | --- | --- | --- |
| 生成 | プロダクト | 32 バイトの乱数を base64url で表した値を、クライアントの作成時と追加発行時にプロダクトが作る。管理者が値を選ぶ経路はない | 乱数の取得に失敗した場合はクライアントを作らない |
| 保存 | OAuth2 Context の Repository | 平文を保持せず、SHA-256 の 16 進表現だけを保存する。パスワードと違って利用者が選んだ値ではなく、推測できる入力を守るための鍵導出関数による伸長は行わない | 保存した表現から平文は戻せない |
| 配布 | プロダクト | 作成または発行のレスポンスで一度だけ返る（REQ-OAUTH2-035、REQ-OAUTH2-036） | 再表示の経路はない。受け取り損ねた資格情報は、追加発行するかローテーションして取り直す |
| 利用 | OAuth2 のトークンエンドポイント | 提示された値のハッシュを定数時間で照合する | 照合に失敗しても `client_id` の登録有無は明かさず、常に `401 invalid_client` を返す。未登録の `client_id` にも同程度の検証コストを課す |
| ローテーション | テナント管理者 | 猶予期間を指定したローテーションと、期限付きの追加発行の二つを持つ。どちらも新旧が同時に受理される期間を作り、無停止で入れ替えられる（REQ-OAUTH2-036、REQ-OAUTH2-037） | 有効な資格情報が上限に達している状態での追加発行は `ClientSecretLimitExceededError` で拒否し、既存の資格情報は変えない |
| 失効 | テナント管理者 | 資格情報を一つずつ失効できる。同じ資格情報を二度失効しても冪等に成功する（REQ-OAUTH2-036） | 失効した資格情報での認証は `InvalidClientError` になる。期限切れも同じ結果になる |
| 廃棄 | OAuth2 Context の Repository | 行は残り、失効した時刻が立つ。いつ発行し、いつ失効したかを後から参照できる | 資格情報を個別に物理削除するインターフェースは持たない。クライアントを削除すると、その資格情報も一緒に消える |
| 復旧 | テナント管理者 | 復旧しない。失った資格情報は追加発行して置き換える | バックアップから復元してもハッシュしか戻らないため、クライアント側に配る値は取り戻せない |

### データ暗号鍵

対象は、データベースに保存する可逆な秘密情報をエンベロープ暗号化するテナント単位の DEK と、それをラップするマスター鍵である。
現在ラップの対象になっているのは、TOTP のシードと、上流 IdP のクライアントシークレットである。

| 段階 | 担い手 | 成立すること | 失敗時の動作 |
| --- | --- | --- | --- |
| 生成 | DataKeys | テナントの初期化時に最初の版を `active` として作り、マスター鍵プロバイダーでラップする | プロバイダーへ到達できなければテナントは鍵を持たずに失敗する。ラップできない鍵を平文のまま暫定的に保持する経路はない |
| 保存 | DataKeys の Repository とマスター鍵プロバイダー | ラップした DEK だけがデータベースに入り、マスター鍵はプロバイダーの内側に留まる | データベースのバックアップだけでは DEK を復元できない |
| 配布 | プロセス内の `EnvelopeCrypto` ポート | 鍵素材はプロセスの外へ出ない。管理 API が返すのは有効な版、ステータス、プロバイダーへの到達性だけである | 鍵素材を返す管理経路を持たないため、権限の付け方によらず外へ出ない（REQ-DATAKEYS-006） |
| 利用 | 可逆な秘密情報を持つ各 Context | 追加認証データに `(tenant, context, table, record id, field)` と鍵の版を含めるため、暗号文を別のテナント、テーブル、フィールドへ複製しても復号できない | アンラップの失敗、プロバイダーへの未到達、追加認証データの不一致、改ざんの検知は、いずれもフェイルクローズで復号を拒否する。平文へ退避したり、その項目だけ読み飛ばして残りを返したりする経路はない |
| ローテーション | DataKeys。呼び出す経路は未実装 | 新しい版を `active` にし、直前の版を復号可能な `retiring` として残す。移行処理ごとに再暗号化ジョブを投入する | 本番でローテーションを起動する経路がない。管理 API も定期実行のジョブも持たないため、テナントの DEK は最初の暗号化操作で作られた後、入れ替わらない |
| 失効 | DataKeys | `retiring` の版を即時に無効化する。再暗号化の完了を待たない | 無効化した版で暗号化した値は読めなくなる。`active` な版は直接無効化できず、先にローテーションして退役させる |
| 廃棄 | DataKeys | すべての再暗号化処理が残件 0 を報告したときだけ、ラップした DEK を消す。行は消さないので、いつ有効化し、いつ退役し、いつ破棄したかは残る | いずれかの移行処理が残件を報告している間、破棄は `DataKeyStillReferencedError` で拒否される |
| 復旧 | マスター鍵プロバイダーと業務データのバックアップ | ラップした DEK は業務データのバックアップに含まれる。マスター鍵はプロバイダー自身のバックアップが正本である | マスター鍵を失うと、バックアップにあるラップ済み DEK は二度とアンラップできない（[鍵とシークレットの喪失](#鍵とシークレットの喪失)） |

ローテーションの行だけが「未実装」である。
再暗号化ジョブと、残件が残っている間は破棄を拒否する仕組みは実装してあるが、どちらもローテーションが呼ばれてはじめて意味を持つ。
定期実行の CronJob として構成ファイルが宣言しているのは、保持期限による削除と署名鍵のライフサイクルの二つだけで、DEK のローテーションはそこにない。

### 署名鍵と証明書

対象は、トークン、アサーション、ログアウトトークンに署名する鍵と、XML フェデレーション用の自己署名 X.509 証明書である。

| 段階 | 担い手 | 成立すること | 失敗時の動作 |
| --- | --- | --- | --- |
| 生成 | SigningKeys | テナント、用途、スコープの組が確定した時点で作る。デフォルトテナントにだけ初期鍵を事前作成することはしない | 組ごとに有効な鍵は 1 本だけであり、データベースでは部分一意インデックスが、Vault では鍵集合の識別情報がこれを保証する |
| 保存 | `KeyProvider` の選択 | `local` と `database` は秘密鍵 JWK をデータベースに平文で置き、`vault` は秘密鍵を Vault の外へ出さない | 鍵素材が永続化される `PERSISTENCE=postgres` では `KeyProvider` の明示を要求し、指定がなければ起動を拒否する。平文で永続化する構成を、誰も選ばないまま成立させないためである（REQ-SIGNINGKEYS-012） |
| 配布 | SigningKeys | 公開鍵と証明書は、認証を要さないテナントごとの JWKS とフェデレーションメタデータで配る | 管理 API のレスポンスに秘密鍵素材を含めることは、いずれの権限でもできない。返すのは `kid`、状態、有効期間、証明書、フィンガープリントに限る |
| 利用 | 各プロトコルのアダプター | 署名ポート越しにのみ鍵を使う。用途とスコープを取り違えた署名は、鍵の解決の時点で防ぐ | プロバイダーへ到達できないとき、SigningKeys 自身はフェイルクローズを強制せず、`provider_healthy` を偽として観測できるようにする。新しい署名を止めるのは OAuth2 のトークン発行である（REQ-SIGNINGKEYS-008） |
| ローテーション | 定期実行のジョブとテナント管理者 | 定期実行のジョブが最短間隔を過ぎた鍵を回す。管理者は即時のローテーションも要求できる。どちらも古い有効鍵を同じ処理内で検証用へ降格させ、重複期間を作る（REQ-SIGNINGKEYS-001） | ライフサイクルの設定が不正なバッチは起動しない（REQ-SIGNINGKEYS-003） |
| 失効 | テナント管理者 | ローテーション後の検証用の鍵だけを即時に無効化できる（REQ-SIGNINGKEYS-010） | 有効な鍵は直接無効化できない。先にローテーションして検証用へ降格させる。他テナントの鍵は要求できない（REQ-SIGNINGKEYS-011） |
| 廃棄 | 定期実行のジョブ | 重複期間を過ぎた鍵を JWKS から外し、監査保管へ移す。退役した鍵で署名した監査トークンを検証できるよう、鍵素材は保持する（REQ-SIGNINGKEYS-002） | 個別に完全削除するインターフェースは提供しない |
| 復旧 | `KeyProvider` の選択 | `local` と `database` は業務データのバックアップに含まれる。`vault` はプロバイダーのスナップショットが正本である | 復元の整合性検査で署名鍵を解決できなければ、データベースの復元が成功していてもフェイルクローズのまま新しいトークンを発行しない |

平文の鍵素材を含むバックアップの保存先を暗号化する責務は、デプロイする側に置く。
保存先のボリュームやバケットはプロダクトの管理下にないため、プロダクトが保証するのは、どの構成で鍵素材が平文になるかを構成から判別できることまでである。

### TLS 証明書

対象は、エッジで TLS を終端するための公開証明書とその秘密鍵である。
[ネットワーク設計](../infrastructure/network.md#dns-と証明書の管理責任)が、発行と更新をデプロイ基盤の責務と定めている。

| 段階 | 担い手 | 成立すること | 失敗時の動作 |
| --- | --- | --- | --- |
| 生成 | デプロイ基盤 | 基盤が CA から証明書を取得する。アプリケーションは要求にも取得にも関与しない | プロダクトからは生成の成否を観測できない |
| 保存 | デプロイ基盤 | 秘密鍵はエッジの内側に留まり、アプリケーションのプロセスへは渡らない | アプリケーションへ秘密鍵を渡す構成は選ばない |
| 配布 | デプロイ基盤 | エッジが証明書を提示し、クライアントが検証する | 証明書に載っていない DNS 名でアクセスされると、TLS ハンドシェイクの時点で失敗する |
| 利用 | エッジ | エッジで終端し、その内側は暗号化せずに運ぶ | 内側を暗号化するかどうかは未決定であり、内側へ入れるものを絞ることを前提にしている |
| ローテーション | デプロイ基盤 | マネージド証明書は基盤が自動で更新する。ワイルドカード証明書を使う構成では、自分で更新する（仮） | 自分で管理する証明書は、有効期限が近づいた時点で通知する（仮）。マネージド証明書は更新の失敗だけを通知する（仮） |
| 失効 | デプロイ基盤 | CA へ失効を要求する | プロダクトから失効させる経路はない |
| 廃棄 | デプロイ基盤 | 基盤が古い証明書を取り除く | プロダクトは関与しない |
| 復旧 | デプロイ基盤 | 証明書を発行し直して設定する。バックアップからの復元の対象ではない | DNS と証明書は、リージョンを作り直したときに設定し直す |

## 起動時シークレットの供給元

デプロイプロファイルごとに、起動時のシークレットをどこから持ってきて、どうプロセスへ渡すかを定める。
プロファイルの一覧は[デプロイメントアーキテクチャ](../../architecture/deployment.md#デプロイプロファイル)が持つ。

この対応の正本はこの文書とする。
シークレットをどう扱うかはデプロイ先の都合ではなくセキュリティ設計の判断であり、プロファイルが増えても判断は変わらないためである。
[プラットフォーム設計](../infrastructure/platform.md#シークレットと鍵)はここを参照する。

| プロファイル | 供給元 | プロセスへの渡り方 | 保存時の保護 | 実装状況 |
| --- | --- | --- | --- | --- |
| ローカル Docker Compose | Compose の構成ファイルに書いた開発専用の平文の値 | `environment` で環境変数に置く | 持たない。値は Git に入っているため、この構成を開発者の手元の外へ出さない | 構成ファイルあり |
| 汎用 Kubernetes | プラットフォームが先に作成した Kubernetes の Secret | `envFrom` の `secretRef` で環境変数へ展開する | Kubernetes の Secret。保存時に暗号化するかはクラスターの設定で決まり、マニフェストは指定しない | 構成ファイルあり |
| Google Cloud | Secret Manager | Kubernetes Secret へ同期し、`envFrom` で展開する。同期の仕組みは未決定である | Secret Manager と、クラスターのアプリケーション層のシークレット暗号化。どちらの鍵も共通のセキュリティ用プロジェクトへ置く（仮） | 設計上の想定 |

三つのプロファイルに共通する判断は次の三つである。

- シークレットは Git の構成ファイルへ書かず、デプロイの時点で注入する。ローカル Docker Compose だけがこの規則の外にあり、その代わりに外へ出さない。
- アプリケーションはシークレットを環境変数から読む。ファイルとしてマウントする方式は、そのままでは使えない。
- 実行単位ごとに、その単位が使うシークレットだけを渡す。これを権限として表した対応は[プラットフォーム設計](../infrastructure/platform.md#サービスアカウントと-iam)が持つ。

## 新旧を同時に受理する期間

新旧を同時に受理する期間は、**その鍵で保護されたものの最長寿命**から決まる。
期間をこれより短くすると、まだ寿命の残っているものが読めなくなるか、検証できなくなる。

値そのものはここに書かない。
書くのは、何がその期間を決めるかである。

| 区分 | 期間を決めるもの | 値の正本 |
| --- | --- | --- |
| 署名鍵 | その鍵で署名したメッセージの最長有効期限。アクセストークン、ID トークン、SAML アサーション、ログアウトトークンのうち最も長いもの | 最短の重複期間は [SigningKeys の設計判断](../../contexts/signing-keys/decisions.md)、各トークンの有効期限は[設定リファレンス](../../../CONFIGURATION.md) |
| データ暗号鍵 | 旧版を参照する暗号文の再暗号化が完了するまでの時間。期間として設定せず、残件が 0 になったことで判定する | 再暗号化処理の残件報告。[DataKeys の内部設計](../../contexts/data-keys/internals.md) |
| クライアント資格情報 | クライアント側でシークレットを入れ替えるのに要する時間。プロダクトには知りようがないため、要求した管理者が指定する | ローテーション要求の猶予日数と、追加発行の有効日数。範囲は REQ-OAUTH2-036 と REQ-OAUTH2-037 が定める |
| 起動時のシークレット | 該当しない。重複期間を持たず、プロセスの再起動で切り替わる | 該当しない |
| TLS 証明書 | 更新を前倒しする幅。証明書の有効期間そのものではなく、更新に失敗したときに残る猶予で決まる | デプロイ基盤 |

署名鍵とクライアント資格情報は、旧を残したまま新を有効にする。
データ暗号鍵は逆で、新を有効にしてから旧の参照を消していく。
この向きの違いは、署名鍵とクライアント資格情報では検証する側が外部にあり、データ暗号鍵では暗号文がすべてこちら側にあることから来る。

## 緊急ローテーション

漏洩が疑われるときのローテーションは、定期ローテーションとは別の設計として扱う。
定期ローテーションは重複期間を十分に取り、誰にも気付かせずに入れ替えることを目指す。
緊急ローテーションはその重複期間を捨てるので、入れ替えている間に何が拒否されるかを先に決めておく。

順序は次の原則で決める。

1. 漏洩した資格情報で新しい権限を得られる経路を先に止める。既に発行されたものの無効化は後でよい。
2. 入れ替えの範囲をテナント単位に絞れるものは絞る。全テナントを止める入れ替えは、マスター鍵に限る。
3. 既存のセッションとトークンの無効化は、新しい鍵が有効になってから行う。先に無効化すると、作り直そうとした利用者が古い鍵に当たる。

| 漏洩したもの | 先に止めるもの | 入れ替え中に拒否されるもの | 入れ替え後に無効化するもの |
| --- | --- | --- | --- |
| 署名鍵の秘密鍵 | 該当の鍵での新しい署名。有効な鍵は直接は無効化できないため、まずローテーションして検証用へ降格させ、続けて無効化する | 旧 `kid` で署名したトークンとアサーションの検証。重複期間を捨てるため、まだ有効期限の残るトークンも検証できなくなる | テナントの全セッションとリフレッシュトークン。ただし一括で失効させる経路はなく、利用者ごとの失効を繰り返すしかない（未実装）。自己完結型のアクセストークンには即時失効の経路がそもそもなく、最長で残存期間だけ有効なままになる |
| テナントの DEK | 該当の版での新しい暗号化。ローテーションで `retiring` へ落とし、続けて無効化する | その版で暗号化した値の復号。TOTP のシードと上流 IdP のクライアントシークレットが読めなくなるため、そのテナントの TOTP による多要素認証と外部フェデレーションのサインインが止まる | 該当しない。読めなくなることが目的であり、追加の無効化はいらない |
| マスター鍵 | 該当しない。プロバイダー側で版を入れ替えても、ラップ済み DEK を新しい版へ再ラップする経路をプロダクトが持たない（未実装） | 該当しない | 該当しない |
| クライアント資格情報 | 該当の資格情報。猶予なしのローテーションか、資格情報の個別の失効で止める | そのクライアントからのトークン取得。クライアント側の入れ替えが終わるまで続く | そのクライアントへ発行済みのリフレッシュトークン。クライアント単位でまとめて失効させる経路はない（未実装） |
| 起動時のシークレット | 該当しない。発行元で新しい値を作り、供給元を更新してから、その値を読む全プロセスを再起動する | 再起動の間のリクエスト。ローリング更新なら、新旧の値を持つプロセスが混在する時間がある | 該当しない |
| TLS 証明書の秘密鍵 | エッジでの旧証明書の提示。デプロイ基盤が入れ替える | 該当しない。エッジの入れ替えはプロダクトから見えない | 該当しない |

入れ替えに要する時間は未確定である。
署名鍵と DEK のローテーションはローカルでしか動かしておらず、本番規模のテナント数と暗号文の件数での所要時間を実測していない。
実測するまでは、緊急ローテーションの所要時間を前提にした運用の約束をしない。

漏洩の経路、鍵の保存場所、到達の手順はこの文書に書かない。
書くのは何が起こりうるかと何を守るかであり、どう操作するかは[ランブック](../../runbooks/backup-restore-dr.md)が持つ。

## 鍵とシークレットの喪失

鍵を失ったときに何が読めなくなるかは、失った鍵の区分で変わる。
ここでは失ったものごとに、読めなくなるものと残るものを書く。
そこから復旧する経路は[リカバリ設計](../reliability/recovery.md#暗号鍵の喪失)が持ち、鍵素材への到達性を復元試験の対象に含めている。

| 失ったもの | 読めなくなるもの | 残るもの |
| --- | --- | --- |
| データ暗号鍵のマスター鍵 | すべてのテナントのラップ済み DEK と、それで暗号化したすべての値。`DestroyTenantDataKey` が意図して行う暗号学的消去と同じことが、事故として起きる | 暗号化していない業務データ、DEK のライフサイクルの履歴、`KeyProvider` が `vault` の場合の署名鍵 |
| テナントの DEK の一つの版 | その版で暗号化した値だけ。同じテナントの他の版と、他のテナントの値は読める | その版がいつ有効化され、いつ退役し、いつ破棄されたかの履歴 |
| Vault に保存した署名鍵の秘密鍵 | その `kid` で署名したトークン、アサーション、監査トークンの検証 | データベースに残る公開鍵の写しと鍵のメタデータ。新しい鍵を発行して置き換えられる |
| データベースに保存した署名鍵の秘密鍵 | 業務データと同時に失われるため、単独では起きない | 業務データと一緒に復元する |
| クライアント資格情報 | 該当しない。保存しているのはハッシュだけであり、失っても読めなくなるものはない | クライアントの登録内容。資格情報は追加発行して置き換える |
| 起動時のシークレット | その資格情報が守っていた接続先。データベースの接続文字列を失えば業務データ全体へ到達できなくなる | データそのものは無事であり、供給元から値を取り直せば読める |

データベースの復元が成功したことで、鍵を失ったことを見逃さないようにする。
復元の整合性検査が署名鍵の解決に失敗したら、データベースの復元が成功していても新しいトークンを発行しない。
