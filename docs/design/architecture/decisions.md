# アーキテクチャ上の判断

この文書は、複数のアーキテクチャ文書に影響する判断、理由、見直し条件を記録する。

## Modular Monolith の採用

- 判断：単一の Go モジュール（`go.mod` が定める依存管理の単位）の中に、責務と公開契約で分けた複数のモジュールを置き、API、ワーカー、バッチで同じ実装を共有する。
- 理由：現在のデータ所有、担当、SLO はモジュールごとの独立デプロイを要求せず、プロセス分割による通信と運用の費用が上回る。
- 見直し条件：独立したデータ所有、担当チーム、デプロイ周期、SLO のいずれかが必要になったモジュールが現れる。

## モジュール間の依存を共通規則で検査する

- 判断：モジュール間の依存は、すべてのモジュールに同じ形で適用する共通規則で検査する。共通規則は、公開範囲（公開パッケージだけを import する）、モジュール単位の非循環、共有ライブラリがモジュールに依存しないこと、組み立て地点へ依存しないこと、テーブルへの書き込みの所有の五つである。「A から B への依存を個別に許可する一覧」は持たない。境界は、変わりうる設計判断を一つのモジュールへ隠すという情報隠蔽の原則で選ぶ。
- 理由：
  - 個別に許可する一覧では、一覧へ辺を書き足すだけで違反が消える。辺を認めてよいかの判断基準が別に要り、一覧そのものは境界の選択を説明しない。
  - 共通規則に加えて必要な、特定のモジュールの組だけを禁じる条件は、現在まで特定できていない。
  - 依存の辺はコードから抽出できる。一覧として文書に手で書くと、コードと一覧が別々に古くなる。
- 見直し条件：特定のモジュールの組の依存が、テナント分離、認可、原子性などの製品の保証を破ると分かった場合は、その保証を根拠に、その組を禁じる条件を共通規則に加える。

## 共有状態としての PostgreSQL

- 判断：永続状態とレプリカ間で共有すべき短命状態を PostgreSQL に集約する。
- 理由：ログイン制限、認可コード、再送防止などの正しさをレプリカ数から独立させ、二つ目のステートフル基盤を運用しないためである。
- 見直し条件：キャパシティ測定が PostgreSQL を律速点と示し、同じ整合性を保つ別の所有境界が必要になる。

## 現在の値の保存とイベントソーシングの不採用

- 判断：Aggregate は現在の値を保存する。状態をイベントの列から再構成するイベントソーシングは採らない。ドメインイベントは状態の一次情報ではなく、確定した変更の通知と監査の記録である。
- 理由：
  - 要件が求める履歴は、追記だけの監査の記録と、パスワードの履歴やワークフローの実行の記録のような機能ごとの履歴で足りる。任意の時点の状態の再現を求める要件はない。
  - 状態をイベントから再構成すると、イベントの型が永続化の形式になる。公開イベントの名前と項目を削除も改名もしない規則が、すべての Aggregate の内部の表現にまで及ぶ。
  - User の完全削除と保持期限の削除は、記録から個人データを消す。追記だけのイベントの列から消すには、暗号鍵の破棄のような別の仕組みが要る。
- 見直し条件：ある Aggregate の任意の時点の値を再現することが要件になり、監査の記録と機能ごとの履歴では答えられない。

## ブラウザーの同一オリジン境界

- 判断：ブラウザー向け UI と API はゲートウェイで同一オリジンにする。
- 理由：Cookie のスコープと `Origin` の検証がこの境界に依存する。
- 見直し条件：ブラウザーの認証と CSRF 防御を別の検証可能な機構へ移す。
