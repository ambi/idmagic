# アーキテクチャ上の判断

この文書は、複数のアーキテクチャ文書に影響する判断、理由、見直し条件を記録する。

## Modular Monolith の採用

- 判断：単一の Go モジュール内に複数のモジュールを置き、API、ワーカー、バッチで同じ実装を共有する。
- 理由：現在のデータ所有、担当、SLO はモジュールごとの独立デプロイを要求せず、プロセス分割による通信と運用の費用が上回る。
- 見直し条件：独立したデータ所有、担当チーム、デプロイ周期、SLO のいずれかが必要になったモジュールが現れる。

## モジュールの組ごとの依存の許可リストを持たない

- 判断：モジュール間の依存は、公開パッケージ、モジュール単位の非循環、共有ライブラリと組み立て地点の制約、テーブルへの書き込みの所有で検査し、モジュールの組ごとに依存を許す許可リストは持たない。境界は、変わりうる設計判断を一つのモジュールへ隠すという情報隠蔽の原則で選ぶ。
- 理由：公開範囲と非循環に加えて必要な、モジュールの組ごとの禁止条件を特定できていない。許可リストに辺を書き足せば違反が消えるので、辺を認める判断基準が別に必要になり、許可リストだけでは境界の選択を説明できない。依存の辺はコードから抽出できるので、文書に手で書くと正本と写しが独立に古くなる。
- 見直し条件：特定のモジュールの組の依存が製品の保証（テナント分離、認可、原子性など）を破ると分かった場合は、その保証を根拠に組ごとの禁止条件を追加する。

## 共有状態としての PostgreSQL

- 判断：永続状態とレプリカ間で共有すべき短命状態を PostgreSQL に集約する。
- 理由：ログイン制限、認可コード、再送防止などの正しさをレプリカ数から独立させ、二つ目のステートフル基盤を運用しないためである。
- 見直し条件：キャパシティ測定が PostgreSQL を律速点と示し、同じ整合性を保つ別の所有境界が必要になる。

## ブラウザーの同一オリジン境界

- 判断：ブラウザー向け UI と API はゲートウェイで同一オリジンにする。
- 理由：Cookie のスコープと `Origin` の検証がこの境界に依存する。
- 見直し条件：ブラウザーの認証と CSRF 防御を別の検証可能な機構へ移す。
