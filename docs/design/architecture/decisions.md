# アーキテクチャ上の判断

この文書は、複数のアーキテクチャ文書に作用する判断のうち、代替案を比べたものを記録する。
一つのモジュールに閉じた判断は、そのモジュールの `decisions.md` に置く。

## Modular Monolith を採る

### 背景

IdMagic は 26 のモジュールを持ち、API、ワーカー、バッチ、初期データの投入という複数の実行単位で動く。
現在のモジュールには、独立したデータ所有、担当チーム、デプロイの周期、サービス目標を要求するものがない。
一方、ログインからトークンの発行までの一つの要求は、複数のモジュールの状態を読む。

### 決定

一つの Go モジュール（`go.mod` が定める依存管理の単位）の中に、責務と公開契約で分けた複数のモジュールを置く。
API、ワーカー、バッチは同じ実装を共有し、モジュールの境界は公開パッケージと依存規則で保つ。

### 検討した代替案

| 案 | 利点 | 欠点 | 採らない理由 |
| --- | --- | --- | --- |
| モジュールごとにサービスへ分割する | モジュールごとに独立してデプロイし、スケールできる | モジュール間の呼び出しがネットワークを越え、失敗、再試行、バージョンのずれを扱う必要が生じる。運用する単位が増える | 独立したデプロイを求めるモジュールがなく、通信と運用の費用だけが増える |
| モジュールごとに Go モジュールを分ける | 依存の境界をコンパイラーが強制する | モジュール間の型の変更に、複数の `go.mod` のバージョンの更新が要る | 同じリリースで一緒に変わる実装に、互換性の管理の手間を持ち込む。境界は依存規則の検査で保てる |

### 結果と再検討の条件

モジュール間の呼び出しは関数呼び出しで済み、一つのトランザクションで複数のモジュールの状態を確定できる。
その代わり、境界はコンパイラーではなく `mise run check-boundaries` の検査で保つ必要がある。
利用者の環境へ別に配布する実行単位（Directory Connector、MCP Gateway）は、この判断の例外として公開 HTTP 契約で結ぶ（[境界を選ぶ判断手順](../application/design-guidelines.md#境界を選ぶ判断手順)の D9）。

独立したデータ所有、担当チーム、デプロイの周期、サービス目標のいずれかを必要とするモジュールが現れたら見直す。

[論理アーキテクチャ](logical.md#アーキテクチャ様式)、[ランタイムアーキテクチャ](runtime.md#実行単位)

## モジュール間の依存を共通の規則で検査する

### 背景

モジュール間の import を放置すると、境界が少しずつ崩れる。
境界を守る方法として、許す辺を一覧にする方法と、規則で判定する方法がある。
また、DDD はモデルの境界を Bounded Context として、実装の単位とは別に分類する。

### 決定

設計と実装の単位を Module に統一し、Bounded Context との二重の分類は行わない。
モデルを使う範囲は、各モジュールの設計で説明する。
依存は[バックエンド設計の共通規則](../application/backend.md#モジュール間の依存規則)で検査し、[モジュール間でのモデルの扱い](../application/design-guidelines.md#モジュール間でのモデルの扱い)は別に判断する。
個別の import を許す一覧は持たない。

### 検討した代替案

| 案 | 利点 | 欠点 | 採らない理由 |
| --- | --- | --- | --- |
| 許す辺を一覧にする | 許した依存がひと目で分かる | 一覧へ辺を書き足すだけで違反が消える。辺を認めてよいかの基準が別に要る | 一覧は境界の選択を説明せず、コードと一覧が別々に古くなる |
| Bounded Context を Module とは別に分類する | モデルの意味の違いを分類の名前で示せる | 同じモデルを使う処理でも、保存、画面の編成、起動時の組み立ては別々に分けられるので、分類と Module が一対一に対応しない | モデルの意味の違いは、相手のモデルを使うか、変換するか、一部を共同管理するかの判断で扱える。分類を増やすと、二つの単位の対応を保つ手間だけが増える |

### 結果と再検討の条件

依存の辺はコードから抽出し、規則で判定する。
モデルの関係は、[モジュールの間の依存](../../modules/README.md#モジュールの間の依存)の表が宣言し、[論理アーキテクチャ](logical.md#モジュールの関係)の Context Map が示す。
Context Map は節点に Module を置き、関係の種類だけを DDD から借りる。

依存が製品の保証を破る場合は、共通の規則へ制約を加える。
別々のモデルの間で共同管理する部分が必要になったら、Shared Kernel を比べる。

[バックエンド設計：モジュール間の依存規則](../application/backend.md#モジュール間の依存規則)

## 共有状態を PostgreSQL に集める

### 背景

API は複数のレプリカで動く。
ログインの試行回数の制限、認可コード、再送の防止は、どのレプリカが要求を受けても同じ結果を返す必要がある。

### 決定

永続状態と、レプリカの間で共有すべき短命な状態を PostgreSQL に集める。

### 検討した代替案

| 案 | 利点 | 欠点 | 採らない理由 |
| --- | --- | --- | --- |
| 短命な状態を Redis などのキーバリューストアに置く | 読み書きの遅延が小さく、期限切れの削除をストアに任せられる | 二つ目のステートフルな基盤の運用、バックアップ、障害の検知が要る。永続状態との整合を、別々の確定で保つ必要がある | 現在の負荷は PostgreSQL で足り、運用の費用だけが増える |
| 短命な状態をプロセスのメモリに置く | 外部の基盤が要らない | レプリカごとに状態が分かれ、再送の防止や試行回数の制限がレプリカ数に応じて緩む | 正しさがレプリカの数に依存する |

### 結果と再検討の条件

正しさがレプリカの数から独立し、運用するステートフルな基盤が一つで済む。
その代わり、PostgreSQL の障害は短命な状態を使う機能にも及び、期限切れの行の削除は自分で実装する必要がある。

キャパシティの測定で PostgreSQL が律速点となり、同じ整合性を保つ別の所有境界が必要になったら見直す。

[可用性設計：共有状態](../reliability/availability.md#共有状態)

## 現在の値を保存し、イベントソーシングを採らない

### 背景

監査、パスワードの履歴、ワークフローの実行のように、IdMagic は変更の履歴を必要とする。
状態をイベントの列として保存すれば、履歴と状態を一つの仕組みで扱える。

### 決定

Aggregate は現在の値を保存する。
状態をイベントの列から組み立て直すイベントソーシングは採らない。
ドメインイベントは状態の一次情報ではなく、確定した変更の通知と監査の記録である。

### 検討した代替案

| 案 | 利点 | 欠点 | 採らない理由 |
| --- | --- | --- | --- |
| イベントソーシングを採る | 任意の時点の状態を再現できる。履歴と状態が食い違わない | イベントの型が永続化の形式になり、公開イベントの名前と項目を削除も改名もしない規則が、すべての Aggregate の内部の表現に及ぶ。追記だけのイベントの列から個人データを消すには、暗号鍵の破棄のような別の仕組みが要る | 任意の時点の状態の再現を求める要件がない。User の完全削除と保持期限の削除が難しくなる |

### 結果と再検討の条件

要件が求める履歴は、追記だけの監査の記録と、機能ごとの履歴（パスワードの履歴、ワークフローの実行の記録）で満たす。
内部の表現は、公開イベントの互換性と切り離して変えられる。
その代わり、過去の任意の時点の状態は再現できない。

ある Aggregate の任意の時点の値を再現することが要件になり、監査の記録と機能ごとの履歴では答えられなくなったら見直す。

## ブラウザー向けの UI と API を同一オリジンにする

### 背景

ブラウザーの画面は、Cookie によるセッションで API を呼ぶ。
Cookie が送られる範囲と、`Origin` ヘッダーによる要求元の検証は、画面と API のオリジンの関係で決まる。

### 決定

ブラウザー向けの UI と API を、ゲートウェイで同一オリジンにする。

### 検討した代替案

| 案 | 利点 | 欠点 | 採らない理由 |
| --- | --- | --- | --- |
| UI と API を別のオリジンに置き、CORS で許す | UI と API を別々のドメインで配信できる | Cookie に `SameSite=None` が要り、クロスサイトの要求の防御を CORS の設定とトークンで別に組む必要がある | 防御が設定の正しさに依存し、誤った設定を検出しにくい |

### 結果と再検討の条件

Cookie のスコープと `Origin` の検証が、同一オリジンという一つの前提で成り立つ。
その代わり、UI と API を別のオリジンに置く構成はとれない。
この前提が崩れたデプロイは THREAT-012 として[脅威モデル](../security/threat-model.md#gateway-と-api-プロセス)に記録している。

ブラウザーの認証と CSRF の防御を、オリジンに依存しない検証可能な仕組みへ移すときに見直す。
