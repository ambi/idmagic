# キャパシティ設計

この文書は、システムの構成を決めるための負荷、データ量、処理能力の前提と、必要な構成の算出方法を定める。
サービス目標、測定境界、キャパシティ受入れ目標の一次情報は[品質要求](../../requirements/quality.md)であり、この文書には `SLO-*` と `CAP-*` の値を再掲しない。

## 仮定値と実測値

この文書の数値は、まだ測っていない**仮定値**である。
測った値を採用するときは、日付、ソースのバージョン、実行環境、データ分布、負荷構成、試験時間、結果の保存先を添えて**実測値**として記録する。
実測値が仮定値を下回っても、品質要求の目標を暗黙に引き下げない。
二つの語の定義は[品質要求](../../requirements/quality.md)にある。

## 想定ワークロード

**想定ワークロード**は、キャパシティを算出するために想定する利用規模と負荷である。
すべてのデプロイ先に要求する最小構成でも、プロダクトが超過を拒否する上限でもない。

### テナントと活動量の分布

| テナント区分 | テナント数 | テナント当たり利用者数 | 利用者数 | 値の種類 |
| --- | ---: | ---: | ---: | --- |
| 小規模 | 90,000 | 20 | 1,800,000 | 仮定値 |
| 中規模 | 9,000 | 500 | 4,500,000 | 仮定値 |
| 大規模 | 900 | 3,000 | 2,700,000 | 仮定値 |
| 超大規模 | 100 | 10,000 | 1,000,000 | 仮定値 |
| 合計 | 100,000 | — | 10,000,000 | 仕様目標 |

この分布では、テナント当たり利用者数の中央値が 20、p90 が 500、p99 が 3,000、最大が 10,000 となる。
10,000 人を超える単一テナントには、この分布とは別に大規模テナント向けの性能検証が要る。

| 活動量 | 値 | 値の種類 |
| --- | ---: | --- |
| 月間アクティブユーザー | 4,000,000 | 仮定値（全利用者の 40%） |
| 日間アクティブユーザー | 1,000,000 | 仮定値（全利用者の 10%） |
| 最繁 5 分に活動するテナント | 20,000 | 仮定値（全テナントの 20%） |
| ピーク時に有効なブラウザーセッション | 200,000 | 仮定値（全利用者の 2%） |
| 一日当たりの新規ブラウザーセッション | 500,000 | 仮定値 |

### オブジェクトと保持量

| オブジェクト | 件数または到着率 | 保持の前提 | 一行当たりの想定バイト数 |
| --- | ---: | --- | ---: |
| Tenant | 100,000 | 削除まで | 8 KiB |
| User | 10,000,000 | 削除と匿名化の方針に従う | 4 KiB |
| Application | 500,000 | 削除まで | 8 KiB |
| OAuth2 クライアント | 1,000,000 | 削除まで | 4 KiB |
| グループの所属 | 50,000,000 | 所属の解除まで | 256 B |
| 認証セッション | 500,000 件／日 | 失効または期限切れの後を含めて 90 日 | 1 KiB |
| リフレッシュトークン | 2,000,000 件／日 | 絶対期限の 30 日 | 512 B |
| 認証イベント | 1,000,000 件／日 | キャパシティの見積もりでは 365 日 | 1 KiB |
| 監査イベント | 5,000,000 件／日 | 2,555 日 | 1 KiB |

監査イベントの検索属性を 1 件当たり 6 行、1 行 128 B と仮定すると、本体と合わせた物理ストレージの初期予算は約 32 TiB となる。
物理ストレージの予算は `Σ(保持行数 × 実測の平均行バイト数) × 2.5 + 30 日分の物理的な増加量` 以上とする。
係数 2.5 はインデックス、MVCC、保守時の空き容量を含み、バックアップ、WAL の別保管、読み取りレプリカは含まない。
保持期間の一次情報は各 Context の仕様と[品質要求](../../requirements/quality.md)であり、保持期間を変えるときの順序は[データライフサイクル設計](../data/lifecycle.md#保持期間を変えるときの順序)で定める。

## ピーク時のリクエスト率

### 認証とトークン発行

次の値は、同じ最繁 15 分に API へ到達するリクエスト率の仮定値である。
キャッシュできる公開文書は、クライアント側のリクエスト率と API への到達率を分け、キャパシティの算出には API への到達率を使う。

| エンドポイント群 | クライアント側のピーク | API へ到達するピーク | 前提 |
| --- | ---: | ---: | --- |
| `/token` | 5,000 rps | 5,000 rps | キャッシュ不可 |
| `/authorize` | 1,000 rps | 1,000 rps | キャッシュ不可 |
| `/api/auth/login` | 600 rps | 600 rps | キャッシュ不可 |
| `/par` | 1,000 rps | 1,000 rps | キャッシュ不可 |
| `/introspect` | 20,000 rps | 20,000 rps | キャッシュ不可 |
| `/revoke` | 1,000 rps | 1,000 rps | キャッシュ不可 |
| `/userinfo` | 5,000 rps | 5,000 rps | キャッシュ不可 |
| `/register` | 50 rps | 50 rps | キャッシュ不可 |
| `/device_authorization` | 200 rps | 200 rps | キャッシュ不可 |
| 外部連携のコールバック | 200 rps | 200 rps | 上流の IdP とのトークン交換を含む |
| セッション一覧 | 200 rps | 200 rps | 先頭ページと後続ページを含む |
| Discovery | 20,000 rps | 2,000 rps | ゲートウェイまたは CDN のヒット率を 90% と仮定する |
| JWKS | 50,000 rps | 5,000 rps | ゲートウェイまたは CDN のヒット率を 90% と仮定する |

Discovery と JWKS のヒット率は保証値ではない。
キャッシュが空の状態でのキャパシティ検証では、API への到達率が表の 10 倍になる条件を含める。

### 管理と連携

管理コンソール、管理 API による自動化、アカウントポータル、SCIM、Shared Signals は、認証とトークン発行とは処理の性質が違うので、別に見積もる。
値はすべて仮定値であり、実測値はまだない。

| 種別 | 平常時 | 最繁時 | 一括実行時 | 見積もりを最も左右する要因 |
| --- | ---: | ---: | ---: | --- |
| 管理コンソール | 50 rps | 300 rps | — | 操作中の管理者の割合と、テナント当たりの管理者数 |
| 管理 API による自動化 | 140 rps | 210 rps | 1,100 rps | 同期の間隔と、一回の同期で送るリクエスト数 |
| アカウントポータル | 150 rps | 900 rps | — | ログイン後にポータルを開く割合と、一回の訪問で送るリクエスト数 |
| SCIM | 13 rps | 50 rps | 110 rps | SCIM を使うテナントの割合と、全件同期の規模 |
| Shared Signals | 30 rps | 90 rps | 300 rps | Shared Signals を使うテナントの割合と、イベントの発生率 |

最繁 15 分の合計は中央値で 1,550 rps、一括実行時の値を単純に足した上界は 2,710 rps である。
認証とトークン発行の 41,250 rps に対して到達率では 4–7% にとどまるが、一リクエスト当たりの費用が違うので、必要なリソースの比率には読み替えない。
管理 API による同期の規模と、SCIM の全件同期を、最初に実測する。

### Worker の実行レーン

| 実行レーン | ピーク時の到着率 | ハンドラー処理時間の p95 | 安全係数 1.5 で必要な枠数 |
| --- | ---: | ---: | ---: |
| `latency_sensitive` | 50 件／秒 | 200 ms | 15 |
| `default` | 20 件／秒 | 1 s | 30 |
| `bulk` | 2 件／秒 | 10 s | 30 |

### ドメインイベントの費用

ドメインイベントの監査記録は、発行元のリクエストまたはジョブの中で追記する。
そのため、発行一件当たり、本体一行と検索属性六行のデータベース書き込みと、5 ms の追加時間を仮定値として発行元の負荷に含める。
再生用のキューはない。
実行時の配信方式は[ランタイムアーキテクチャ](../architecture/runtime.md#通信)で定める。

## サイジング計算式

API の必要なレプリカ数は、エンドポイント `e` ごとに `ceil(API へ到達するピーク_e ÷ 一レプリカ当たりの持続処理能力_e × 1.5)` を計算した最大値とする。
一レプリカ当たりの持続処理能力には、想定ワークロードのデータと混合負荷の下で、該当する `SLO-*` を満たした実測値だけを使う。

実測するまでは、`/token` 250 rps、`/authorize` 100 rps、`/introspect` 1,000 rps と仮定する。
この仮定では API は 30 レプリカになるが、この数で目標を達成できると確かめたわけではない。
管理、ポータル、SCIM、Shared Signals を含む混合負荷で測り、置き換える。

実行レーン `l` の必要なワーカー枠は `ceil(ピーク時の到着率_l × ハンドラー処理時間の p95_l × 1.5)` とする。
一プロセス四枠のデフォルトでは、`latency_sensitive` は四レプリカ、`default` は八レプリカ、`bulk` は八レプリカになる。
レーン間で枠を融通せず、`bulk` の滞留を理由に `latency_sensitive` の枠を減らさない。

PostgreSQL の論理接続予算は、`API のレプリカ数 × API のプール上限 + ワーカーのレプリカ数 × ワーカーのプール上限 + 同時に動くバッチの数 × バッチのプール上限 + 運用のための予約` とする。
実測するまでは、API 一レプリカ 16 接続、ワーカー一レプリカ 8 接続、同時に動くバッチ四個で各 4 接続、運用のための予約 64 接続とし、この仮定では 720 接続になる。
論理接続予算は利用できる接続数の 70% 以下に保つので、この構成には少なくとも 1,029 接続を扱える PostgreSQL が要る。

プール上限は、構成ファイルが実行単位ごとに `DB_MAX_CONNS` で指定し、計算に使った値（API 16、ワーカー 8、バッチ 4）と一致させる。
起動時設定のデフォルト 20 はどの実行単位の仮定値とも一致しないので、構成ファイルで必ず上書きする。
汎用 Kubernetes の構成ファイルは、まだこの値を指定していない。

ストレージと接続数は、使用率 70% を継続的な上限として設計し、残りを障害時の偏り、保守、増加に充てる。
レプリカの上限を上げる前に、PostgreSQL の接続予算を計算し直す。
手順は[再計算の条件](#再計算の条件)で定める。
自動スケールの条件は[スケーリング・負荷設計](scaling.md#オートスケール)で定める。

## 仮定値の根拠

仮定値を実測値で置き換えるときは、二つを比べる。
仮定値の根拠が分からなければ、差が仮定の誤りによるのか、負荷の変化によるのかを区別できない。

| 仮定値 | 根拠 | 置き換えに使う実測値 |
| --- | --- | --- |
| テナント総数と利用者総数 | 仕様目標 | 置き換えない。規模の目標を変えるなら、先に[品質要求](../../requirements/quality.md)を変える |
| テナント区分ごとの利用者数 | 総数を、中央値 20、p90 500、p99 3,000、最大 10,000 の分布へ割り振った値 | テナントごとの利用者数の分位点 |
| 月間と日間のアクティブユーザー、最繁 5 分に活動するテナント、ピーク時のセッション | 利用者総数またはテナント総数に対する比率 | 比率そのもの。比率が変われば絶対値を計算し直す |
| 一日当たりの新規ブラウザーセッション | 記録された根拠はない | 一日当たりの新規セッション数 |
| オブジェクトの件数と到着率 | 利用者総数に対する比率と、根拠の記録がない値が混ざる | テーブルごとの行数と一日当たりの増加数 |
| 一行当たりの想定バイト数 | 記録された根拠はない | テーブルごとの平均行バイト数 |
| 保持期間 | 各 Context の仕様 | 置き換えない。値を変えるときは[データライフサイクル設計](../data/lifecycle.md#保持期間を変えるときの順序)に従う |
| 認証とトークン発行のピーク時のリクエスト率 | 記録された根拠はない。Discovery と JWKS は、キャッシュのヒット率 90% の仮定を掛けた値 | エンドポイントごとの最繁 15 分の API への到達率と、キャッシュのヒット率 |
| 管理と連携のリクエスト率 | 表の「見積もりを最も左右する要因」列の要因からの推定 | その列の要因 |
| Worker の到着率と処理時間 | 記録された根拠はない | レーンごとの `jobs_duration_seconds` の p95 と、ジョブの投入数 |
| ドメインイベントの費用 | 書き込み行数はスキーマの構造による。追加時間 5 ms は根拠の記録がない | 発行元のリクエストとジョブの処理時間の差 |
| 一レプリカ当たりの持続処理能力 | 記録された根拠はない | 混合負荷で `SLO-*` を満たした最大の到達率 |
| 接続プールの上限と運用のための予約 | 記録された根拠はない | デプロイ先の設定値 |
| 安全係数 1.5 と使用率の上限 70% | 障害時の偏り、保守、増加のために選んだ余裕 | 障害時と保守時に実際に生じた偏り |

根拠の記録がない仮定値は、最初の実測値でそのまま置き換える。
置き換えるときは、実測値の記録と一緒に、その値の根拠を書く。

## 再計算の条件

実測値が仮定値から外れたときは、次の表に従って計算し直す。
実測値が仮定値を下回っても、[品質要求](../../requirements/quality.md)の目標は下げない。

| 条件 | 計算し直すもの | 注意 |
| --- | --- | --- |
| リクエスト率が継続して仮定値を上回る | API のレプリカ数、論理接続予算 | 下記のレプリカ上限の手順に従う |
| リクエスト率が継続して仮定値を下回る | API のレプリカ数 | HorizontalPodAutoscaler の下限は可用性のために決めた値なので、下げない |
| 一レプリカ当たりの持続処理能力を測った | API のレプリカ数 | 仮定値の `/token` 250 rps、`/authorize` 100 rps、`/introspect` 1,000 rps を置き換える |
| レーンの到着率または処理時間が仮定値を上回る | そのレーンのワーカー枠とレプリカ数、論理接続予算 | ほかのレーンの枠を減らして賄わない |
| キャッシュのヒット率が 90% を下回る | Discovery と JWKS の API への到達率、API のレプリカ数 | キャッシュが空の状態での検証条件（表の 10 倍）も見直す |
| テーブルの行数、平均行バイト数、保持期間が変わった | 物理ストレージの予算 | 保持期間の変更は[データライフサイクル設計](../data/lifecycle.md#保持期間を変えるときの順序)の順序に従う |
| ストレージまたは接続数の使用率が 70% に近づいた | 物理ストレージの予算、論理接続予算 | 原因が仮定の誤りか、負荷の増加かを先に区別する |

レプリカの上限を上げるときは、次の順に進める。

1. 新しい上限で論理接続予算を計算する。
2. 論理接続予算が、PostgreSQL で利用できる接続数の 70% 以下に収まるかを確かめる。収まらなければ、先にデータ層を拡張する。
3. デプロイ先の `DB_MAX_CONNS` が、計算に使ったプール上限と一致することを確かめる。
4. HorizontalPodAutoscaler の上限を上げる。

この順序を逆にすると、足したレプリカの分だけ PostgreSQL の接続待ちが増え、処理能力を上げたつもりで遅延を増やす。
定期的な見直しの運用は[保守](../../operations/maintenance.md#キャパシティ見直し)で定める。

## ロードシェディング順序

処理能力が足りないときも、テナント境界、認証と認可の検証、再送防止、流量制限、監査イベントの完全性は弱めない。
状態を確認できないリクエストを成功として扱うこと、監査イベントを黙って捨てること、テナントをまたいでキャッシュや接続枠を共有することは、ロードシェディングの手段に含めない。

1. `bulk` レーンの新規取得と、保守のバッチを遅らせる。
2. `default` レーンの新規取得を遅らせ、`latency_sensitive` の専用枠を維持する。
3. 管理用の集計、エクスポート、再同期のように、対話的な認証に要らない高コストの処理を 429 または 503 で拒否する。
4. 動的クライアント登録のように、既存セッションの認証とトークン処理に要らない書き込みを拒否する。
5. `/authorize`、`/token`、`/introspect`、ログインを受け付けられない場合は、状態を部分的に更新せず 429 または 503 で拒否する。

ステージ 1 と 2 はワーカーの実行レーンで、ステージ 3 以降は API のアドミッションコントロールで実現する。
経路の優先度は [System Context の判断](../../domain/system/decisions.md#load-shedding-by-priority-class)で定める。
高可用性と障害時の切り替えは[可用性設計](../reliability/availability.md)で扱う。
