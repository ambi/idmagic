# スケーリング・負荷設計

この文書は、IdMagic の実行単位を負荷に応じてどう増減させるか（スケーリング）と、処理能力を超えるリクエストが来たときに何をどこで絞るか（負荷の制御）を定める。
負荷とデータ量の前提、必要なレプリカ数と接続数の算出、ロードシェディング順序は[キャパシティ設計](capacity.md)で定める。
目標値は[品質要求](../../requirements/quality.md)で定め、この文書には再掲しない。

## スケーリング単位

実行単位ごとに、独立して増減できる単位と、その数を決めるものが違う。

| 実行単位 | 増減の単位 | 数を決めるもの | 実装状況 |
| --- | --- | --- | --- |
| `idmagic-api` | ステートレスなレプリカ | HorizontalPodAutoscaler | 構成ファイルあり |
| `idmagic-worker` | 実行レーンごとの Deployment のレプリカ | overlay が固定値で指定する。本番は `latency_sensitive` 2、`default` 1、`bulk` 2 | 構成ファイルあり。自動スケールはしない |
| `idmagic-batch` | 保守処理ごとの実行 | CronJob のスケジュール。`concurrencyPolicy: Forbid` で同じ処理を重ねない | 構成ファイルあり |
| `idmagic-frontend` | レプリカ | overlay が固定値で指定する。本番は 3 | 構成ファイルあり |
| PostgreSQL | 未決定 | 未決定 | パーティショニング、読み取りレプリカ、接続プーラーの構成は決めていない |

### 律速点

律速点は PostgreSQL の接続である。
リクエスト 1 件とジョブ 1 件は、同時に高々 1 本の接続を使う。
接続プールはプロセスごとの上限と、全プロセスの合計（論理接続予算）を分けて予算化する。
アプリケーションのレプリカを足しても、接続が足りなければ PostgreSQL の側で待ちが増えるだけで、処理能力は上がらない。

## オートスケール

`idmagic-api` の HorizontalPodAutoscaler は次の条件で増減する。

| 項目 | 値 | 決め方 |
| --- | --- | --- |
| 指標 | CPU 使用率の平均 70% | サイジング計算式が求める一レプリカ当たりの持続処理能力を、まだ測っていないための代わり |
| 下限 | 3 | ノードの退避や再起動の最中も、複数のレプリカを残す可用性の下限 |
| 上限 | 30 | 想定ワークロードから計算した API のレプリカ数。論理接続予算に縛られる |
| 増やすとき | 安定化の待ち時間なし。30 秒ごとに最大 100% 増やす | 増えるまでの間は、アドミッションコントロールがリクエストを拒否して持ちこたえる。待ち時間を短くするほど、拒否の期間も短くなる |
| 減らすとき | 300 秒の安定化。60 秒ごとに最大 25% 減らす | 急いで減らすと、解消した飽和がまた起きて増減を繰り返す |

Deployment にはレプリカ数を書かない。
両方に値を書くと、構成ファイルを適用するたびに数が固定値へ戻り、自動スケールと取り合いになる。

上限を上げる前に、論理接続予算を計算し直す。
手順は[キャパシティ設計](capacity.md#再計算の条件)が定める。

### CPU 使用率が飽和を表さない場合

CPU 使用率は、処理が CPU で詰まる場合にだけ飽和を表す。
次の場合、飽和していても CPU 使用率は上がらず、レプリカは増えない。

| 状況 | 結果 | レプリカを増やさない理由 |
| --- | --- | --- |
| PostgreSQL の接続待ちで詰まっている | リクエストが接続を待つ間、CPU は使われない | レプリカを足すと接続の奪い合いが悪化する |
| 外部の IdP や鍵管理サービスの応答待ちで詰まっている | 同上 | 増やしても外部の応答は速くならない |

実行中数やアドミッションコントロールの拒否の割合は、オートスケールの指標に使わない。
CPU 使用率が低いまま実行中数が上限に張り付くのは、上の二つのように待ち先で詰まっているときであり、そこでレプリカを増やすと状況が悪くなるためである。
CPU で詰まって拒否が起きている場合は、CPU 使用率が上がるので、CPU の指標だけでレプリカは増える。

ワーカーのレーンは自動スケールしない。
レーンの枠数はサイジング計算式で決まり、枠を増やせば論理接続予算も増えるので、増やすかどうかを人が判断する。
滞留は `jobs_queue_depth` に現れ、`latency_sensitive` の滞留はアラートで知らせる。

## アドミッションコントロール

アドミッションコントロールは、`idmagic-api` のプロセスが、同時に処理しているリクエストの数を優先度クラスごとの上限と比べ、上限を超えたリクエストをハンドラーへ渡さずに拒否する仕組みである。
機構の正しさの論証は [System Context の内部設計](../../contexts/system/internals.md#admission-control)に書く。

| 項目 | 内容 |
| --- | --- |
| 何を測るか | そのプロセスで実行中のリクエスト数。他のレプリカとも共有ストアとも通信しない |
| 何と比べるか | 優先度クラスごとの上限。`ADMISSION_MAX_CONCURRENT_REQUESTS`（デフォルト 256）、`ADMISSION_MANAGEMENT_MAX_CONCURRENT_REQUESTS`（192）、`ADMISSION_MANAGEMENT_BULK_MAX_CONCURRENT_REQUESTS`（128）。デフォルト値はまだ測っていない仮定値である |
| 何を返すか | 503、`urn:idmagic:error:service_overloaded`、`Retry-After`。秒数は `management_bulk` 5、`management` 2、それ以外 1 |
| どこで判定するか | ルーティングの後、ハンドラーの前 |
| 上限の変更 | 起動時の設定からだけ入り、実行中は変わらない。変えるには再起動が要る |
| 無効化 | `ADMISSION_CONTROL_ENABLED=false`。誤った上限を、変更をデプロイせずに止めるためにある |

上限は `management_bulk` ≤ `management` ≤ プロセス全体の順に並び、起動時の設定の検証がこの順を強制する。
下位のクラスは自分の上限までしか実行中数に寄与できないので、その差分は上位のクラスのために空いている。
リクエスト 1 件は同時に高々 1 本の接続を使うため、この差分はそのまま上位のクラスのための接続の予約になる。

### 優先度クラス

| 優先度クラス | 対象 | ロードシェディング順序のステージ |
| --- | --- | --- |
| `management_bulk` | 集計、エクスポート、取り込み、全同期 | 3 |
| `management` | 管理 API、ポータル API、SCIM、Shared Signals の受信、動的クライアント登録 | 4 |
| `interactive_auth` | 対話的な認証とトークン処理 | 5 |
| `infrastructure` | `/livez`、`/readyz`、`/startupz`、`/metrics` | 対象外 |

クラスは経路の登録と同じ場所で決め、プロセスの組み立て時に確定する。
経路とクラスの対応の一覧 `ROUTE_PRIORITY.md` は、この登録から生成する。
クラスのない経路は、組み立てた経路表の全量に対する網羅性の検査が拒む。
それでも実行時にクラスのない経路へ到達した場合は `interactive_auth` と同じ上限で扱い、メトリクスに `unclassified` として記録する。
本番では、誤って拒否するほうが誤って通すより高くつくためである。

`infrastructure` を対象外にするのは、飽和したレプリカの `/readyz` を拒否すると、全レプリカが同時に振り分け先から外れ、一部のリクエストを拒否していただけの状態が全体の停止になるためである。

### ハンドラーの前で拒否する理由

拒否したリクエストは、何も実行しない。
ハンドラーの途中で拒否すると、認証、認可、テナント境界の判定、再送防止の記録のどれかだけが済んだ状態が残りうる。
たとえば再送防止の記録だけが済んだリクエストを拒否すると、クライアントが同じ値で再送したときに正当な再送まで拒否される。
ハンドラーの前で拒否すれば、[ロードシェディング順序](capacity.md#ロードシェディング順序)のステージ 5 が求める「状態を部分的に更新しない」が、何も実行しないという形で成り立つ。

### ロードシェディング順序との対応

| ステージ | 絞るもの | 実現する仕組み |
| --- | --- | --- |
| 1 | `bulk` レーンの新規取得と保守のバッチ | ワーカーの実行レーンの分離。`bulk` の滞留は他のレーンの枠を使わない |
| 2 | `default` レーンの新規取得 | 同上。`latency_sensitive` は専用の Deployment と PodDisruptionBudget で守る |
| 3 | 管理用の集計、エクスポート、再同期 | アドミッションコントロールの `management_bulk` の上限 |
| 4 | 動的クライアント登録などの管理系の書き込み | アドミッションコントロールの `management` の上限 |
| 5 | 対話的な認証とトークン処理 | アドミッションコントロールのプロセス全体の上限 |

ステージ 1 と 2 は、ステージ 3 以降と違って拒否ではなく遅延である。
ジョブはキューに残り、レーンに枠が空いた時点で取得される。

流量制限の状態は PostgreSQL で共有し、レプリカ数に応じて閾値を緩めない。

## 接続と本体の上限

公開する HTTP サーバーには、低速な接続と過大なリクエストが接続枠とメモリを枯渇させないための上限を置く（`gosec G112`、CWE-400）。
上限を超えた本体は 413 で拒否する。

| 変数 | デフォルト値 | 目的 |
| --- | --- | --- |
| `HTTP_READ_HEADER_TIMEOUT` | `10s` | リクエストのヘッダーを読む上限時間（slowloris の抑止） |
| `HTTP_READ_TIMEOUT` | `30s` | リクエスト全体を読む上限時間 |
| `HTTP_WRITE_TIMEOUT` | `60s` | レスポンスを書く上限時間 |
| `HTTP_IDLE_TIMEOUT` | `120s` | 持続接続の待機時間の上限 |
| `HTTP_MAX_BODY_BYTES` | `1048576` | リクエスト本体の最大バイト数（1 MiB） |

これは多層防御であり、境界プロキシの代わりではない。
大量のリクエストと TLS ハンドシェイクを悪用する攻撃には前段のリバースプロキシで対処する。
エッジでのレート制限は[ネットワーク設計](../infrastructure/network.md)で定める。

## バックプレッシャー

受け付けを絞ったことは、次の経路で上流へ伝わる。

1. PostgreSQL の接続が足りなくなると、リクエストは接続を待つ間、実行中数に数えられたまま残る。
2. 実行中数が上限に達すると、アドミッションコントロールが新しいリクエストを 503 と `Retry-After` で拒否する。
3. `idmagic-frontend` の Caddy は、拒否をそのままクライアントへ返す。Caddy の設定は再試行を指定していない。
4. クライアントは `Retry-After` の秒数だけ待ってから再送する。管理コンソールとポータルは自動では再送せず、エラーを表示する。

下位のクラスほど `Retry-After` を長くするのは、最初に拒否したクラスが最初に戻ってくると、ロードシェディングが終わらないためである。

ワーカーへの投入は、キューの長さでは拒否しない。
テナントごとの実行中ジョブ数のクォータを超えた投入だけを拒否する。
キューの滞留は実行を遅らせるが、投入元のリクエストを遅らせない。

## 依存先の障害に対するサーキットブレーカー

| 依存先 | サーキットブレーカー | 実装状況 |
| --- | --- | --- |
| PostgreSQL | プロセスごとに一つのサーキットブレーカー。10 件以上の問い合わせのうち 50% 以上が失敗すると開き、30 秒間は問い合わせを送らずに失敗させる。その後の半開状態で最初に完了した問い合わせが成功すれば閉じ、失敗すれば再び開く。値は `DB_BREAKER_*` の設定で変えられる | 構成ファイルあり |
| 外部の鍵管理サービス | PostgreSQL と同じ形の、プロセスごとに一つのサーキットブレーカー。開いている間は鍵操作を送らずに失敗させる | 未実装 |
| 上流の IdP、SCIM と Shared Signals の送信先、その他の外部 HTTP | サーキットブレーカーを置かない。送信の失敗は、ジョブと配信の再試行の間隔で抑える | 構成ファイルあり |

鍵管理サービスにブレーカーを置くのは、PostgreSQL と同じく全テナントが共有する一つの依存先だからである。
障害中の鍵管理サービスへの呼び出しが応答を待つ間、そのリクエストは実行中数を占め続ける。

外部 HTTP の送信先にブレーカーを置かないのは、送信先がテナントや接続ごとに違うためである。
プロセスごとのブレーカーにすると、一つの送信先の障害でほかのテナントの送信まで止まる。
送信先ごとのブレーカーにすると、送信先の数だけ状態が増え、しかもその状態をレプリカ間で共有できない。
送信はジョブと配信の中で行うので、再試行の間隔が障害中の送信先への負荷を抑える。

問い合わせには、`DB_QUERY_TIMEOUT`（デフォルト 5 秒）の期限を付ける。
期限がないと、障害中の PostgreSQL への問い合わせが実行中数を占め続け、アドミッションコントロールがすべてのリクエストを拒否するまで回復しない。

## 再試行とキュー

再試行するのは外側の一層だけとし、各層で掛け合わせない。
各層が善意で再試行を入れると、試行回数は層の数だけ掛け算になり、障害中の依存先への負荷を増やす。
回数の上限、指数的に伸びる間隔、全体の期限を設け、依存先の回復不能な拒否と認証上の拒否は再試行しない。

どの層が再試行するかは、次の表で決める。

| 層 | 再試行するか | 規則 |
| --- | --- | --- |
| ブラウザーと連携クライアント | する | `Retry-After` に従う。回数と間隔はクライアントの責任である |
| `idmagic-frontend` の Caddy | しない | 再試行を設定しない |
| `idmagic-api` のハンドラーとリポジトリ | しない | PostgreSQL と外部への呼び出しは一回だけ行う |
| PostgreSQL への接続の確立（起動時） | する | 5 回まで。間隔の上限は 500 ms から 2 倍ずつ、最大 5 秒 |
| ジョブの実行 | する | デフォルト 5 回まで。間隔の上限は 30 秒から 2 倍ずつ、最大 30 分。上限に達したジョブは dead letter へ移す |
| Shared Signals の配信 | する | ジョブと同じ形の間隔。上限は 30 秒から 2 倍ずつ、最大 30 分 |
| ジョブの中の外部 HTTP 呼び出し | しない | 失敗をジョブへ返し、ジョブの再試行に任せる |

どの再試行も、実際に待つ時間を 0 から間隔の上限までの一様乱数で決める。
ばらつきがないと、共通の依存先の障害で同じ時刻に失敗したジョブと配信が、回復の直後にも同じ時刻に再試行し、回復したばかりの依存先へ負荷が集中するためである。

| 再試行 | ばらつきの実装状況 |
| --- | --- |
| PostgreSQL への接続の確立 | 未実装。固定の間隔で待つ |
| ジョブの実行 | 未実装。固定の間隔で待つ |
| Shared Signals の配信 | 未実装。固定の間隔で待つ |

ワーカーの `latency_sensitive`、`default`、`bulk` は実行枠を分け、`bulk` の滞留で認証に近い処理を止めない。

## キャッシュ境界

Discovery と JWKS のように正本から再生成できる公開レスポンスだけをゲートウェイまたは CDN へキャッシュできる。
セッション、認可コード、再送防止、流量制限の正をキャッシュへ移さず、キャッシュを失っても正しさを変えない。
