# スケーリングと過負荷の設計

## スケーリング単位

API はステートレスなレプリカ、ワーカーは実行レーン、バッチは実行回数を独立した拡張単位にする。
PostgreSQL の接続プールはレプリカごとの値と総接続数を分けて予算化し、アプリケーションのレプリカ追加でデータベースの競合を増幅させない。
データ層のパーティショニング、読み取りレプリカ、接続プールの具体化は [wi-164](../../../work-items/wi-164-data-tier-scalability-partitioning-read-replica-pooling.md) が扱う。

## 入場制御

API は実行中リクエスト数が上限に達したとき、`management_bulk`、`management`、`interactive_auth` の順に低い優先度から 503 と `Retry-After` で拒否する。
ルート分類はコードから生成する `ROUTE_PRIORITY.md` が正本である。
既定の同時実行上限は構成スキーマが持ち、測定前の Planning assumption として扱う。

ハンドラーへ到達する前に拒否し、過負荷時にも認証、認可、テナント境界、再送防止の処理を部分的に実行しない。
流量制限の状態は PostgreSQL で共有し、レプリカ数に応じて閾値を緩めない。

## 接続と本体の上限

公開する HTTP サーバーには、低速な接続と過大なリクエストが接続枠とメモリを枯渇させないための上限を置く（`gosec G112`、CWE-400）。
上限を超えた本体は 413 で拒否する。

| 変数 | 既定値 | 目的 |
| --- | --- | --- |
| `HTTP_READ_HEADER_TIMEOUT` | `10s` | リクエストのヘッダーを読む上限時間（slowloris の抑止） |
| `HTTP_READ_TIMEOUT` | `30s` | リクエスト全体を読む上限時間 |
| `HTTP_WRITE_TIMEOUT` | `60s` | レスポンスを書く上限時間 |
| `HTTP_IDLE_TIMEOUT` | `120s` | 持続接続の待機時間の上限 |
| `HTTP_MAX_BODY_BYTES` | `1048576` | リクエスト本体の最大バイト数（1 MiB） |

これは多層防御であり、境界プロキシの代わりではない。
大量のリクエストと TLS ハンドシェイクを悪用する攻撃には前段のリバースプロキシで対処する。

## 再試行とキュー

再試行は外側の一層だけが所有し、各層で掛け合わせない。
回数の上限、指数的な間隔、ばらつき、全体の期限を持たせ、下流の回復不能または認証上の拒否を再試行しない。
ワーカーの `latency_sensitive`、`default`、`bulk` は別の実行枠を持ち、bulk の滞留で認証に近い処理を止めない。

## キャッシュ境界

Discovery と JWKS のように正本から再生成できる公開レスポンスだけをゲートウェイまたは CDN へキャッシュできる。
セッション、認可コード、再送防止、流量制限の正をキャッシュへ移さず、キャッシュを失っても正しさを変えない。
