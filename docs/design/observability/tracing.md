# トレース設計

## 対象範囲

この文書は、実行単位と外部依存をまたぐ因果関係と所要時間を観測するための、伝播、標本化、属性、保持を定める。
個別リクエストとジョブの事実は[ログ設計](logging.md)、継続的な状態判定とアラートは[監視設計](monitoring.md)が持つ。

現在の実装は、この文書が定める目標設計の一部しか満たしていない。
実装の現状を先に置き、目標設計を後に置く。
読む順序を逆にすると、目標を実装済みと読む誤りが起きる。

## 実装の現状

### 生成する範囲

スパンを生成するのは `idmagic-api` だけで、`OBSERVABILITY` を `otel` にしたときに限る。
デフォルトは `noop` であり、その場合はスパンを一つも作らない。

`idmagic-api` の中でも、スパンを作るのは OAuth 2.0 と OpenID Connect のエンドポイント群に限られる。
管理 API、画面が呼ぶ経路、ヘルスチェックは経路の分類に載らず、スパンを作らない。

`idmagic-worker` は OpenTelemetry の provider を組み立てない。
ジョブの実行はスパンを持たず、`idmagic-batch` の保守処理も同じである。

**`request_id` があることを、スパンが取れている根拠にしない。**
`X-Request-ID` は `OBSERVABILITY` の設定と無関係に常に付くため、両者の存在は連動しない。

### 伝播の現状

入口では W3C Trace Context と Baggage の伝播子でヘッダーを読み、有効なら継続し、無効または欠落なら新しいトレースを開始する。

クライアントが送る相関値はデフォルトで信用せず、信頼できる境界プロキシが生成または無害化する場合だけ受信値を使う。
受信する値には長さと文字種の制限を課す。

入口から先への伝播は無い。
データベース呼び出し、外部 HTTP 呼び出し、ジョブの投入と実行のいずれも計装していないため、一つのリクエストのトレースはスパン一つで終わる。
したがって現在のトレースは、リクエスト全体の所要時間しか示さず、その内訳を示さない。

### 標本化の現状

標本化の方式を構成していないため、SDK のデフォルトが働く。
親の判断があればそれに従い、無ければ常に採る。
結果として、`OBSERVABILITY=otel` の環境では全リクエストのスパンを記録する。

### 保存の現状

スパンは OTLP/HTTP でコレクターへ送る。
ローカル Docker Compose のコレクターは、トレースのパイプラインに出力先を一つだけ持ち、それは受け取った内容を自身のログへ書くものである。
**トレースを保存する先は無く、検索もできない。**
Grafana はトレースのデータソースを持たない。

Kubernetes の監視構成には OTLP コレクターが無い。
`OBSERVABILITY=otel` を設定しても、送信先が無いため送信は失敗し続ける。

## 目標設計

### 伝播

| 境界 | 引き継ぎ方 |
| --- | --- |
| 入口 | 受信した `traceparent` を検証し、有効なら継続、無効または欠落なら新しいトレースを開始する（現状の記述を維持する） |
| データベース呼び出し | 問い合わせごとに子スパンを作る。スパンには正規化した文を置き、束縛値は置かない |
| 外部 HTTP 呼び出し | 送信ヘッダーへ文脈を注入し、呼び出しごとに子スパンを作る。依存先は論理名で表す |
| ジョブの投入 | 投入した時点の文脈をジョブのレコードへ保存する。投入自体は呼び出し元のトレースの子スパンとする |
| ジョブの実行 | **新しいトレースを開始し、保存した文脈への link で結ぶ** |
| 保守処理 | 実行ごとに新しいトレースを開始する。継続元を持たない |

ジョブの実行を呼び出し元のトレースの子にしないのは、二つの理由による。
ジョブは投入から実行までレーンの待ち行列で待つため、同じトレースに入れると、トレースの所要時間が待ち時間に支配され、リクエストの所要時間として読めなくなる。
そして、ジョブは再試行されるため、一つの投入に対して実行が複数回起きる。
link で結べば、投入から実行をたどれる関係を保ったまま、実行ごとの所要時間を独立に読める。

### 標本化

**head sampling を採り、tail sampling は採らない。**
tail sampling はトレースが完了するまでコレクターがスパンを保持する必要があり、そのコレクターの可用性と保存容量を監視対象に加えることになる。
現在は保存先すら決まっていないため、先に増やす構成要素を最小にする。

| 決めごと | 内容 |
| --- | --- |
| 判断の位置 | トレースの起点で一度だけ行う |
| 判断の継承 | 親の判断を子がそのまま継ぐ。サービスごとに率を変えない |
| 判断の単位 | トレース単位とする。一つのトレースのスパンが部分的に欠けることを起こさない |
| 率の指定 | 構成で与える。コードの分岐で切り替えない |
| ローカルと検証環境 | 全件を採る |
| 本番の率 | 未決定。保存先とコストが決まってから定める（仮） |

head sampling では、エラーになったトレースや遅かったトレースを必ず採ることはできない。
採るかどうかを決める時点で、まだ結果も所要時間も分かっていないためである。
この制約を受け入れ、失敗の調査は `request_id` を軸にログからたどる経路で行う。
エラーを必ず採る必要が出たときは、tail sampling の導入を、コレクターの運用と合わせて改めて判断する。

### 属性と span 名

span 名は低カーディナリティに保つ。
登録済みのルートパターンまたは経路の分類名を使い、解決済みのパス、識別子、テナント名を span 名へ入れない。
span 名は検索と集計の軸であり、値ごとに名前が増えると集計できない。

属性は OpenTelemetry の意味規約にあるものを優先し、規約にある名前を自分で言い換えない。
この文書が持つのは、意味規約に無く、自分で決めた属性だけである。

| 属性 | 意味 | 置く理由 |
| --- | --- | --- |
| `request_id` | `X-Request-ID` の値 | トレースが無い環境と、利用者の問い合わせから同じ処理へたどる |
| `tenant_id` | 対象テナントの識別子 | 指標のラベルにできない切り分け軸を、トレース側に持つ |
| `job.lane` | ジョブのレーン | レーンの分離が効いているかを、トレースの所要時間で確かめる |

記録しないものはログと同じである。
資格情報、トークン、Cookie、認可コード、クライアントシークレット、秘密鍵、復号済みの秘密情報、完全な要求本文と応答本文を属性に置かない。
意味規約が定める `url.path` は、経路に識別子を含むエンドポイントでは不透明な ID を含む。
不透明な ID は許すが、そこへ利用者が読める値が入る経路を作らない。

### 保持とコスト

| 観点 | ローカル Docker Compose | 汎用 Kubernetes | Google Cloud |
| --- | --- | --- | --- |
| 保存先 | 持たない。コレクターがログへ書いて捨てる | 未決定。トレースを保存する構成要素を持たない（仮） | Cloud Trace（仮） |
| 保持期間 | 保持しない | 未決定（仮） | 未決定。マネージドサービスの上限の範囲で定める（仮） |
| 検索 | できない | 未決定（仮） | 未決定（仮） |

保存量は、トレース数、一トレースあたりのスパン数、標本化率、保持期間の積でおよそ決まる。
率と期間はどちらを下げても保存量に同じだけ効くが、失うものが違う。
率を下げると、どの時期の事象も一部しか見えなくなる。
期間を縮めると、直近は全部見えて、古い事象が全く見えなくなる。
障害調査は直近を厚く見るため、**先に期間を縮め、それでも足りないときに率を下げる**。

## 相関

`X-Request-ID` は `OBSERVABILITY` の設定と無関係に、常にレスポンスとログに残る。
これはトレースとは別の相関軸であり、トレースが無い環境での調査経路を保証する。

構造化ログは、スパンがあるときだけ `trace_id` と `span_id` を持ち、`request_id` は常に持つ。
このため調査は次の順でたどれる。

1. 利用者の報告または応答ヘッダーから `request_id` を得る。
2. `request_id` でログを絞り、そのリクエストが通った経路と失敗理由を読む。
3. ログに `trace_id` があれば、そこからトレースへ移り、内訳と外部依存の所要時間を読む。
4. 全体の異常かどうかは、[監視設計](monitoring.md)の指標で確かめる。

3 が使えない状態が、現在のデフォルトである。
その場合、内訳は得られないので、2 で読める境界の記録から推定する。

## 未確定事項

トレースの保存先が決まっていない。
保存先が決まるまで、本番の標本化率、保持期間、検索の手段は決められない。
これらが未確定である間、トレースを本番の調査手段として運用手順に組み込まない。

計装の範囲も未確定である。
データベース、外部 HTTP、ジョブの計装をどの順で入れるかは、上の目標設計が定める形を満たす限り、実装側の判断とする。
