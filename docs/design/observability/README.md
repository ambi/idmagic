# 観測可能性設計

## 目的

本書は、システム共通の観測可能性に必要な信号、相関、所有境界を定める。個別のメトリクス、ログ、トレースは子文書が所有し、サービス目標の値と運用手順はここへ複製しない。

## 信号モデル

| 信号 | 所有者 | 主な用途 |
| --- | --- | --- |
| Metrics | [監視設計](monitoring.md) | サービス目標、資源、依存先、キューの継続的な状態判定とアラート |
| Logs | [ログ設計](logging.md) | 個別リクエストとジョブの事実、障害理由、監査対象外の診断情報 |
| Traces | [トレース設計](tracing.md) | 実行単位と外部依存をまたぐ因果関係と所要時間 |

監査イベントは診断ログではなく、改ざん耐性と保持要件を持つ業務上の記録である。監査の意味と保持は [Audit](../../contexts/audit/README.md) と [データライフサイクル設計](../data/lifecycle.md) が所有する。

## 相関

API は入口で `traceparent` を検証し、有効ならトレースを継続し、無効または欠落なら新しいトレースを開始する。すべてのレスポンスへ `X-Request-ID` を返し、構造化ログには `request_id`、`trace_id`、登録済みのルートパターン、メソッド、状態コード、所要時間を含める。Worker と Batch はジョブまたは実行の識別子を持ち、HTTP リクエストから派生した処理では元の相関情報を伝播する。

テナント ID、ユーザー ID、クライアント ID などの高カーディナリティ値をメトリクスのラベルにしない。必要な調査軸はログまたはトレースに置き、資格情報、トークン、Cookie、認可コード、秘密鍵、復号済みの秘密情報をいずれの信号にも記録しない。

## 所有と流れ

アプリケーションは OpenTelemetry と構造化ログを生成し、Prometheus はメトリクスを収集する。現行のローカル監視構成では Promtail がコンテナログを Loki へ送り、Grafana が Prometheus と Loki を表示する。プロダクトコードは特定の可視化プロダクトへ依存せず、信号の意味と属性名を安定させる。

サービス目標の測定境界と値は [品質要求](../../requirements/quality.md) が、アラートからの対応手順は [Runbooks](../../runbooks/) が所有する。観測設計は、目標を計算できる信号と手順へ到達できる通知を提供する。

## 未確定事項

現行構成には分散トレースの本番向け収集・保持基盤、ログとトレースの保持期間、通知先とエスカレーションの本番設定が確定していない。これらは子文書に未確定事項として記録し、値が決まるまで暗黙の保証として扱わない。
