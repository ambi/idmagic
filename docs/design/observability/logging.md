# ログ設計

アプリケーションログは、障害の診断と個別の処理の追跡のための構造化記録である。
監査証跡、サービス目標、トレースの代替にはしない。

## 出力と共通フィールド

アプリケーションとミドルウェアは JSON Lines を標準出力へ書く。
プロセス自身はログファイルの回転、転送、保存を行わない。

各レコードは次のフィールドを持つ。

| フィールド | 用途 |
| --- | --- |
| `timestamp` | 事象が起きた時刻 |
| `level` | `DEBUG`、`INFO`、`WARN`、`ERROR` の重大度 |
| `event_name` | 同じ構造を持つ事象を表す安定した名前 |
| `message` | 人が最初に読む短い説明 |
| `service` | 発生源となった実行単位 |
| `trace_id`、`span_id`、`request_id` | 利用可能な範囲で処理を横断して結び付ける相関識別子 |

`event_name` は検索や集計に使うため、文言の一部や例外メッセージから作らない。
事象ごとに変わる値は構造化属性に置き、文字列へ埋め込まない。
OpenTelemetry のログデータモデルに合わせ、発生源に固定された値はリソース属性、個々の事象で変わる値は属性として扱う。

## 重大度と記録する事象

`ERROR` は、処理が失敗し、運用者の調査または復旧が必要な異常だけに使う。
予期された入力不備、認可拒否、存在しない資源への参照、利用者が取り消した処理は、必要な診断属性を持つ `INFO` または `WARN` とし、異常率の分母を汚さない。

| 種類 | 記録する事実 | 主な重大度 |
| --- | --- | --- |
| HTTP ミドルウェア | 登録済みルート、メソッド、状態コード、所要時間、相関識別子 | 成功は `INFO`、サーバー異常は `ERROR` |
| ジョブとバッチ | 種別、実行識別子、開始、終了、再試行、失敗理由 | 開始と終了は `INFO`、再試行は `WARN`、終了不能は `ERROR` |
| 外部依存 | 依存先の論理名、方式、所要時間、結果分類 | 一時的な失敗は `WARN`、回復不能な失敗は `ERROR` |
| 例外 | 例外型、失敗した処理、原因を追うための安全な文脈 | 捕捉して要求を失敗させるときは `ERROR` |
| 認証、認可、入力検証 | 成否または拒否理由の分類 | 通常は `INFO`、異常な頻度の判断はメトリクスとアラートが担う |

管理者権限の利用、認証失敗、認可拒否、入力検証失敗、設定変更、鍵の操作、インポートとエクスポートは、診断または監査のどちらが正本かを実装時に決める。
改ざん耐性、保持、検索を要求する事実は、必ず [Audit](../../contexts/audit/) の監査イベントへ記録する。

## ミドルウェアとアプリケーションの境界

HTTP ミドルウェアは入口と出口の一件を記録し、アプリケーションは業務上意味のある分岐、外部依存、非同期処理の結果を記録する。
同じ失敗を両方が `ERROR` として重複記録しない。
ミドルウェアが応答結果を、アプリケーションが失敗原因を所有する。

Worker と Batch は HTTP の属性を作らず、ジョブまたは実行の識別子を使う。
HTTP から派生した非同期処理では、受け取った相関情報を引き継ぐ。
例外は境界で一度だけ記録し、呼び出しの各層でスタックトレースを繰り返さない。

## 秘密情報、個人情報、容量

パスワード、トークン、Cookie、認可コード、クライアントシークレット、秘密鍵、TOTP シード、完全な要求本文、完全な応答本文、個人情報をログへ出さない。
URI のクエリ文字列と `Authorization` ヘッダーは既定で記録しない。
必要な識別子は、不透明な ID、列挙値、または安全に短縮した分類で表す。

`service` と `level` は有限集合のラベルとして扱う。
テナント ID、ユーザー ID、クライアント ID、相関識別子は高カーディナリティの構造化メタデータであり、メトリクスのラベルにしない。
繰り返し発生する成功ログと高頻度の拒否は、調査可能性を失わない範囲でサンプリングまたは集約できる。
サンプリングの規則は、事象名、対象、割合、例外を明示する。

件数と比率は [監視設計](monitoring.md) のメトリクスで測る。
ログ集計を SLO の正本にしない。
トレースを横断した所要時間と因果関係は [トレース設計](tracing.md) が持つ。

## 収集と未確定事項

ローカルの Docker Compose では Promtail が Docker のログを Loki へ送り、Kubernetes では DaemonSet が Pod ログを収集する。
保持期間、外部オブジェクトストレージ、閲覧権限、削除、容量超過時の挙動は配備環境に依存し、現在の本番設計としては未確定である。
開発用 Loki の単一レプリカとローカルファイル保存を、本番の可用性または保持保証として扱わない。
