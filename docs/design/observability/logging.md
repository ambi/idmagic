# ログ設計

アプリケーションログは、障害が起きたときに原因を調べ、個々の処理が何をしたかをたどるために残す記録である。
フィールドを決めて機械が読める形で出力するため、この文書ではその形と内容を定める。

同じ「記録」でも、次の三つの代わりにはならない。

- **監査証跡**：誰がいつ何をしたかを、改ざんできない形で保持する業務上の記録。[Audit](../../domain/audit/) で扱う。
- **サービス目標の測定**：成功率や所要時間を継続的に数え、SLO を満たしているかを判断する用途。[監視設計](monitoring.md)のメトリクスで扱う。
- **トレース**：一つの処理の内訳と、処理をまたぐ因果関係。[トレース設計](tracing.md)で扱う。

## 出力と共通フィールド

アプリケーションとミドルウェアのログは、JSON Lines 形式で標準出力へ出力される。
ログローテーション、転送、保存はプロセス自身が行わず、収集側が担う。

各レコードは次のフィールドを持つ。

| フィールド | 用途 |
| --- | --- |
| `timestamp` | 事象が起きた時刻 |
| `level` | `DEBUG`、`INFO`、`WARN`、`ERROR` のログレベル |
| `event_name` | 同じ構造を持つ事象を表す安定した名前 |
| `message` | 人が最初に読む短い説明 |
| `service` | 発生源となった実行単位 |
| `trace_id`、`span_id`、`request_id` | 利用可能な範囲で処理を横断して結び付ける相関 ID |

`event_name` は検索や集計に使うため、文言の一部や例外メッセージから作らない。
事象ごとに変わる値は構造化属性に置き、文字列へ埋め込まない。
OpenTelemetry のログデータモデルに合わせ、発生源に固定された値はリソース属性、個々の事象で変わる値は属性として扱う。

現在の実装は `timestamp`、`level`、`message`、`service`、`version` と、利用できる範囲の `trace_id`、`span_id`、`request_id` を出力する。
`event_name` を出力するレコードはまだ無く、同じ構造を持つ事象は `message` の文字列で区別されている。
以下の命名規約は、その値を出力するときに従う形を定める。

## `event_name` の命名規約

規約が決めるのは名前の作り方だけである。
名前の一覧はこの文書に書かない。
一覧を作ると、事象を足すたびに実装と文書の両方を変えることになり、片方だけが更新される。

名前は、階層をドット、語の区切りをアンダースコアにした小文字の並びとする。

```
<コンテキスト>.<対象>.<操作>[.<結果>]
```

| 位置 | 取る値 | 決め方 |
| --- | --- | --- |
| コンテキスト | `oauth2`、`authentication`、`saml` などの Bounded Context 名 | `docs/domain/` のディレクトリ名をそのまま使う |
| 対象 | 操作される概念の単数形 | その Bounded Context の用語集にある名前を使う |
| 操作 | 動詞の原形一語 | `issue`、`revoke`、`rotate`、`claim` のように、何をしたかを表す |
| 結果 | `succeeded`、`failed`、`rejected`、`skipped`、`timed_out` のいずれか | 成否で読み分ける事象だけに付け、分岐しない事象には付けない |

結果の語彙を閉じた集合にするのは、集計のためである。
成功率を数えるたびに「その事象では成功をどう綴っていたか」を調べ直す状態にしない。

名前に入れないものを次に挙げる。

- テナント ID、利用者 ID、クライアント ID、ジョブ ID、ホスト名のような、事象ごとに変わる値。属性に置く。
- 状態コード、エラーコード、例外型。属性に置く。同じ操作の失敗は一つの名前に集め、理由は属性で分ける。
- `error`、`warn` のようなログレベル。ログレベルは `level` に記録し、同じ名前の事象が状況によって別のログレベルを取ることがある。
- 「新しい」「暫定」のような、時期を表す語。名前は実装のバージョンではなく事象を指す。

一度出力した名前は、その事象の意味が変わらない限り変えない。
名前はダッシュボードの照会と保存済みの検索が参照するため、綴りの改善のためだけに変えると、過去のレコードが検索から外れる。
意味が変わったときは、古い名前を残さず新しい名前へ移し、変更を `docs/releases/changes/` のリリース文書へ記録する。

## サンプリング規則

サンプリングは、調査に使える記録を減らす代わりに、保存容量と照会時間を節約する判断である。
どの事象をどれだけ落としたかが分からないと、残ったレコードから割合を復元できない。
このため、サンプリングする事象は次の形で宣言し、宣言していない事象はサンプリングしない。

| 列 | 内容 |
| --- | --- |
| 事象名 | 対象となる `event_name` |
| 対象 | どの範囲を落とすか（全体か、特定のコンテキストまたは経路か） |
| 割合 | 残す比率 |
| 例外 | 割合にかかわらず必ず残す条件 |

現在サンプリングしている事象は無い。
すべてのレコードを出力し、`LOG_LEVEL` の下限だけが出力の有無を決める。

サンプリングを導入するときの制約は三つある。

- `WARN` と `ERROR`、および拒否と失敗を表す事象は落とさない。落とすのは成功した高頻度の事象だけとする。
- 同じ `trace_id` を持つレコードは、まとめて残すかまとめて落とす。一部だけを落とすと、トレースから辿った調査がレコードの欠落と失敗の区別を付けられなくなる。
- 落とした件数は、レコードの欠落ではなく[監視設計](monitoring.md)の指標で数える。ログの件数を母数にした比率を、サンプリング後に計算しない。

## ログレベルと記録する事象

`ERROR` は、処理が失敗し、運用者の調査または復旧が必要な異常だけに使う。
予期された入力不備、認可拒否、存在しない資源への参照、利用者が取り消した処理は、必要な診断属性を持つ `INFO` または `WARN` とし、異常率の分母を汚さない。

| 種類 | 記録する事実 | 主なログレベル |
| --- | --- | --- |
| HTTP ミドルウェア | 登録済みルート、メソッド、状態コード、所要時間、相関 ID | 成功は `INFO`、サーバー異常は `ERROR` |
| ジョブとバッチ | 種別、実行識別子、開始、終了、再試行、失敗理由 | 開始と終了は `INFO`、再試行は `WARN`、終了不能は `ERROR` |
| 外部依存 | 依存先の論理名、方式、所要時間、結果分類 | 一時的な失敗は `WARN`、回復不能な失敗は `ERROR` |
| 例外 | 例外型、失敗した処理、原因を追うための安全な文脈 | 捕捉してリクエストを失敗させるときは `ERROR` |
| 認証、認可、入力検証 | 成否または拒否理由の分類 | 通常は `INFO`、異常な頻度の判断はメトリクスとアラートが担う |

管理者権限の利用、認証失敗、認可拒否、入力検証失敗、設定変更、鍵の操作、インポートとエクスポートは、診断または監査のどちらが一次情報かを実装時に決める。
改ざん耐性、保持、検索を要求する事実は、必ず [Audit](../../domain/audit/) の監査イベントへ記録する。

## ミドルウェアとアプリケーションの境界

HTTP ミドルウェアは入口と出口の一件を記録し、アプリケーションは業務上意味のある分岐、外部依存、非同期処理の結果を記録する。
同じ失敗を両方が `ERROR` として重複記録しない。
レスポンスの結果はミドルウェアで、失敗の原因はアプリケーションで記録する。

Worker と Batch は HTTP の属性を作らず、ジョブまたは実行の識別子を使う。
HTTP から派生した非同期処理では、受け取った相関 ID を引き継ぐ。
例外は境界で一度だけ記録し、呼び出しの各層でスタックトレースを繰り返さない。

## 秘密情報、個人情報、保存容量

パスワード、トークン、Cookie、認可コード、クライアントシークレット、秘密鍵、TOTP シード、完全なリクエストボディ、完全なレスポンスボディ、個人情報をログへ出さない。
URI のクエリ文字列と `Authorization` ヘッダーはデフォルトで記録しない。
必要な識別子は、不透明な ID、列挙値、または安全に短縮した分類で表す。

`service` と `level` は有限集合のラベルとして扱う。
テナント ID、ユーザー ID、クライアント ID、相関 ID は高カーディナリティの構造化メタデータであり、メトリクスのラベルにしない。
繰り返し発生する成功ログと高頻度の拒否は、調査可能性を失わない範囲でサンプリングまたは集約できる。
その宣言の形と制約は[サンプリング規則](#サンプリング規則)で定める。

件数と比率は [監視設計](monitoring.md) のメトリクスで測る。
ログ集計を SLO の一次情報にしない。
トレースを横断した所要時間と因果関係は [トレース設計](tracing.md) で扱う。

## 収集経路

ローカルの Docker Compose では Grafana Alloy が Docker Engine API からコンテナログを読み、Loki へ送る。
Alloy はホストのログディレクトリを読まないため、ホストのログドライバーの設定に依存しない。
Kubernetes では Alloy の DaemonSet が同じノードの Pod ログを収集する。
どちらも `service` と `level` をラベルにし、`trace_id`、`span_id`、`request_id` を structured metadata にする。

ラベルにする値を二つに絞るのは、Loki のストリーム数がラベル値の組み合わせの数だけ増えるためである。
`request_id` や `trace_id` をラベルにすると、リクエストごとに新しいストリームができる。
structured metadata に置けば、ストリームを増やさずに、その値で絞り込める。

## 保持と閲覧権限

保持期間と閲覧権限はデプロイ先で決まる。
末尾の（仮）は、この文書が選んだ案であり、構成ファイルにまだ無いことを示す。

| 観点 | ローカル Docker Compose | 汎用 Kubernetes | Google Cloud |
| --- | --- | --- | --- |
| 保存先 | Loki コンテナの書き込み可能レイヤー。ボリュームを宣言しないため、コンテナを作り直すと消える | Loki の StatefulSet で宣言する PersistentVolumeClaim 一つ | Cloud Logging のログバケット（仮） |
| 冗長化 | 無い | 無い。レプリカ数は 1 で、ボリュームを失うと復元できない | マネージドサービスの冗長化に従う（仮） |
| 保持期間 | 設定しない。保存先が尽きるまで残る | 設定しない。保存先が尽きるまで残る | 未決定。診断ログの必要な遡及期間を決めてから設定する（仮） |
| 閲覧権限 | 設けていない。Grafana は匿名アクセスを有効にし、ログインフォームを無効にしているため、ポートへ到達できる者が全ログを読む | ネットワークのみで制限する。NetworkPolicy が Loki への到達を Alloy と Grafana に限る。Grafana に到達した者は全ログを読む | 未決定。IAM でログバケットの読み取り権限を分ける（仮） |
| 削除 | コンテナの破棄で消える | ボリュームの削除で消える | 未決定（仮） |

保持期間を設定していない状態は、無期限の保持を選んだという意味ではない。
保存先が尽きるまで残り、尽きた後は新しいレコードが入らないという意味である。
**保持期間の代わりに保存容量が上限になっている。**

開発用 Loki の単一レプリカとローカルファイル保存を、本番の可用性または保持保証として扱わない。

診断ログの閲覧権限を、監査イベントの閲覧権限の代わりにしない。
監査イベントは [Audit](../../domain/audit/) で扱い、改ざん耐性と保持要件を別に定める。

## 容量超過と収集停止時の動作

収集経路のどこが止まっても、アプリケーションは止まらない。
プロセスは標準出力へ書くだけで、転送も保存も行わないためである。
この非対称が意図であり、ログ基盤の障害がサービスの障害にならないようにしている。

| 起きたこと | アプリケーションへの影響 | ログへの影響 |
| --- | --- | --- |
| Loki が停止する | 無い。標準出力への書き込みは続く | Alloy が送信に失敗し、再試行の間に取得位置が進めば、その分が失われる |
| Loki の保存先が尽きる | 無い | Loki が書き込みを拒否し、Loki が停止したときと同じ経過をたどる |
| Alloy が停止する | 無い | ランタイムのログファイルがローテーションするまでは残り、ローテーションで消えた分は失われる |
| Alloy の Pod が作り直される | 無い | 取得位置は `emptyDir` にあるため失われ、再読み込みか読み飛ばしが起きる |
| ノードの保存容量が尽きる | ランタイムがコンテナのログファイルへ書けなくなる | 書けなかった分が失われる |

**ログの欠落をサービスの正常性と混同しない。**
上の表のどの行でも、アプリケーションは正常に動作し続けながらログだけが消える。
ログの件数が落ちたことを、リクエストが減った根拠として読まない。
リクエストが減ったかどうかは、[監視設計](monitoring.md)の指標で判断する。
収集の停止そのものを検知する判定は、[監視設計](monitoring.md)の「検知していない事象」に欠落として残っている。

## 未確定事項

外部オブジェクトストレージへの退避、保持期間の値、閲覧権限の分離は、デプロイ先が決まるまで確定しない。
現在の構成にこれらが無いことを、要らないと判断した結果として読まない。

保存容量の上限に達したときに古いレコードを消すか、新しいレコードを捨てるかも決めていない。
どちらを選ぶかは、診断で遡る期間と、直近の障害調査のどちらを優先するかで決まる。
