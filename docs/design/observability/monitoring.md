# 監視設計

## 監視する層

監視対象を、公開入口、API、ワーカー、PostgreSQL、外部依存、Kubernetes、監視基盤自体に分ける。
利用者に見える成功は[品質要求](../../requirements/quality.md)の SLO、内部の原因は各層の飽和、エラー、レイテンシー、スクレイプ状態で判断する。

API はルートパターン別のリクエスト数、状態コード、所要時間、処理中リクエスト数と、ログイン、トークン発行、流量制限、入場制御の指標を `/metrics` で公開する。
ワーカーは管理専用リスナーで、レーン別の取得待ち時間、実行時間、結果、再試行、キュー深度を公開する。
テナント ID、利用者 ID、クライアント ID、解決済みパスを指標ラベルにしない。

Prometheus ルールは SLO ID を注釈に持ち、ページ通知には runbook を対応付ける。
現行資材は認証とトークンのレイテンシーとエラー率、可用性、ジョブのゴールデンシグナルを持つ。
すべてのアラートに runbook を持たせる作業は [wi-290](../../../work-items/wi-290-alert-runbook-catalog-and-on-call-operations.md) が扱う。

Prometheus、Loki、収集エージェントの停止、保存容量、スクレイプ欠落も監視対象にする。
現在の資材がこの自己監視を十分に持つかは未検証であり、欠落をサービスの正常性と混同しない。
