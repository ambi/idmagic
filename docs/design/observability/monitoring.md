# 監視設計

## 対象範囲

この文書は、**何を検知したいか**と、**それをどのシグナルでどう判定し、どこへ通知し、どの手順へつなぐか**の対応を定める。

指標名、閾値の値、通知の宛先は構成ファイルが正本である。
ローカル Docker Compose は `infra/docker/prometheus.yml` と `infra/docker/prometheus-rules.yml`、Kubernetes は `infra/k8s/monitoring/prometheus-rule.yaml` と `infra/k8s/monitoring/operator/servicemonitor.yaml` が持つ。
この文書は同じ値を写さない。
写すと、計装のコードと構成ファイルに続く三つ目の複製になり、どれが正本か分からなくなる。

サービス目標の値と測定境界は[品質要求](../../requirements/quality.md)、アラートを受けた後の対応手順は [Runbooks](../../runbooks/) が所有する。
ログの内容とトレースの設計は[ログ設計](logging.md)と[トレース設計](tracing.md)が持つ。

## この文書の読み方

検知の一覧は二つの表に分かれる。
先の表は、判定するルールが構成ファイルに存在する検知である。
後の表は、検知したいが、判定できるシグナルまたは規則がまだ無いものである。
後の表の行は欠落の記録であり、「監視していない」ことをこの文書の中で見えるようにするために置く。

「通知」列の値は三つを取る。
**ページ**は当番担当者を呼び出す。
**通知**は呼び出さずに記録へ残し、翌営業日に見る。
**ダッシュボードのみ**は自動通知を持たず、人が見に行ったときだけ現れる。

## 監視する層

| 層 | 対象 | シグナルの入手経路 |
| --- | --- | --- |
| エッジ | ロードバランサーと Ingress | 取り込んでいない |
| `idmagic-frontend` | Caddy が返す静的資産と、API への中継 | 取り込んでいない |
| API | `idmagic-api` | `/metrics` の取得と構造化ログ |
| Worker | `idmagic-worker` のレーンごとのプロセス | 管理専用リスナーの `/metrics` と構造化ログ |
| Batch | `idmagic-batch` の保守処理 | 構造化ログのみ |
| PostgreSQL | 接続数、複製遅延、ディスク、長時間トランザクション | 取り込んでいない |
| 外部依存 | 外部 IdP、漏洩パスワード照合、メール送信 | 構造化ログのみ |
| Kubernetes | Pod の再起動、Probe 失敗、リソースの要求量と上限 | 取り込んでいない |
| 監視基盤 | Prometheus、Loki、Alloy、Grafana | 取り込んでいない |

利用者に見える成功は[品質要求](../../requirements/quality.md)の SLO で判断し、内部の原因は各層の飽和、エラー、レイテンシー、スクレイプ状態で判断する。

API は、ルートパターン別のリクエスト数、状態コード、所要時間、処理中リクエスト数と、ログイン、トークン発行、流量制限、アドミッションコントロールの指標を `/metrics` で公開する。
Worker は、レーン別の取得待ち時間、実行時間、結果、再試行、キュー深度を公開する。
どちらの公開も `OBSERVABILITY` の設定に依存せず、常に行う。

テナント ID、利用者 ID、クライアント ID、解決済みパスを指標のラベルにしない。
これらを軸にした調査はログまたはトレースで行う。

## 検知している事象

判定するルールは、ローカル Docker Compose と Kubernetes の両方に同じ内容で置く。
ページ通知を持つ行は、対応する runbook を必ず持つ。

| 検知したいこと | 層 | シグナル | 判断 | 通知 | runbook |
| --- | --- | --- | --- | --- | --- |
| トークンを発行できない | API | `/token` の 5xx 比率 | 5 分平均が閾値を超えた状態が 5 分続く | ページ | [トークンエンドポイントのエラー率](../../runbooks/token-endpoint-error-rate.md) |
| トークン発行が遅い | API | `/token` の所要時間 p99 | 5 分平均が閾値を超えた状態が 5 分続く | ページ | [トークンエンドポイントのレイテンシー](../../runbooks/token-endpoint-latency.md) |
| ログインできない | API | `/api/auth/login` の 5xx 比率 | 5 分平均が閾値を超えた状態が 5 分続く | ページ | [ログインのエラー率](../../runbooks/login-error-rate.md) |
| ログインが遅い | API | `/api/auth/login` の所要時間 p99 | 5 分平均が閾値を超えた状態が 5 分続く | ページ | [ログインのレイテンシー](../../runbooks/login-latency.md) |
| 認証情報の総当たりを受けている | API | ログイン流量制限の発動比率 | 5 分平均が閾値を超えた状態が 10 分続く | 通知 | [ログイン流量制限の発動率](../../runbooks/login-throttle-hit-ratio.md) |
| 対話的な認証を捨て始めた | API | アドミッションコントロールの拒否数のうち `interactive_auth` のもの | 拒否が 5 分間発生し続ける | ページ | [アドミッションコントロール](../../runbooks/admission-control.md) |
| 管理系のリクエストを捨て続けている | API | アドミッションコントロールの拒否比率のうち `management` と `management_bulk` のもの | 拒否が 10 分間発生し続ける | 通知 | [アドミッションコントロール](../../runbooks/admission-control.md) |
| 優先度クラスを宣言していない経路を配信している | API | アドミッションコントロールの判定数のうち `unclassified` のもの | 判定が 5 分間発生し続ける | 通知 | [アドミッションコントロール](../../runbooks/admission-control.md) |
| 遅延に敏感なジョブが着手されない | Worker | `latency_sensitive` レーンの取得待ち時間 p99 | 5 分平均が閾値を超えた状態が 5 分続く | ページ | [非同期ジョブ](../../runbooks/async-jobs.md) |
| 遅延に敏感なレーンの処理能力が足りない | Worker | `latency_sensitive` レーンのキュー深度 | 待機数が閾値を超えた状態が 10 分続く | 通知 | [非同期ジョブ](../../runbooks/async-jobs.md) |
| ジョブが繰り返し失敗している | Worker | レーン別の失敗比率 | 5 分平均が閾値を超えた状態が 10 分続く | 通知 | [非同期ジョブ](../../runbooks/async-jobs.md) |

記録ルールだけを持ち、自動通知を持たないシグナルもある。
ルート別のリクエスト数とエラー比率、ログイン結果の内訳、トークン発行のレート、ジョブの再試行率と実行時間、アドミッションコントロールの処理中リクエスト数がこれにあたる。
これらは「検知したいこと」が単独の閾値で表せないため、ダッシュボードで文脈とともに読む。

## 検知していない事象

各行は、検知したい事象と、それを今は判定できない理由の対である。
「検知に必要なもの」は作業の指示ではなく、その行が埋まる条件である。

| 検知したいこと | 層 | 現状 | 検知に必要なもの |
| --- | --- | --- | --- |
| エッジがリクエストを落としている | エッジ | ロードバランサーと Ingress の指標を取り込んでいないため、API へ届かなかったリクエストはどのシグナルにも現れない | エッジのリクエスト数、5xx、接続の切断を取り込む経路 |
| データベースが飽和している | PostgreSQL | 接続数、複製遅延、ディスク使用率、長時間トランザクションを表す指標が無い | PostgreSQL の exporter、または管理サービスが公開する指標の取り込み |
| 外部依存が劣化している | 外部依存 | 依存先の結果と所要時間はログにしか残らず、比率として判定できない | 依存先の論理名を軸にした結果と所要時間の指標 |
| 保守処理が失敗し続けている | Batch | 実行結果はログにしか残らず、成否と最終成功時刻を判定できない | 保守処理ごとの実行結果と最終成功時刻の指標 |
| 実行基盤がコンテナを再起動している | Kubernetes | Pod の再起動、OOM による停止、Probe 失敗を判定するルールを持たない | kube-state-metrics の取り込みと、それを使うルール |
| 可用性の SLO を割っている | API | SLO-OAUTH2-AVAILABILITY と SLO-TOKEN-AVAILABILITY はスクレイプ状態を測定に含めるが、それを評価する記録ルールもアラートも無い | スクレイプ状態を含めた可用性の記録ルール |
| ログインとトークン発行以外のエンドポイントが SLO を割っている | API | 記録ルールはルート別だが、アラートは `/token` と `/api/auth/login` だけを対象にしている | 残る SLO それぞれに対応するアラート |
| 署名鍵の有効期限が近づいている | API | 鍵の次回ローテーション期限を表す指標が無い | 鍵の状態を表す指標と、期限までの猶予で判定するルール |
| 監視基盤が止まっている | 監視基盤 | Prometheus、Loki、Alloy の停止、スクレイプ欠落、保存容量を判定するルールが無い | 監視基盤自身を対象にした記録ルールとアラート |

## 閾値の所有

閾値がどこから来るかで、変更してよい人と、変更の理由が決まる。

| 閾値の出どころ | 決めるもの | 変更してよい条件 |
| --- | --- | --- |
| SLO | `/token` と `/api/auth/login` のエラー率とレイテンシー | [品質要求](../../requirements/quality.md)の SLO を変えたときだけ追従する。監視側の都合で緩めない |
| キャパシティ設計 | キュー深度、アドミッションコントロールの判定 | [キャパシティ設計](../performance/capacity.md)の想定ワークロードを変えたときに見直す |
| 運用で観測した通常値 | ログイン流量制限の発動比率、ジョブの失敗比率 | 通常時の分布を測り直したときに見直し、見直した根拠を構成ファイルの変更に添える |

SLO 由来の閾値は、[品質要求](../../requirements/quality.md)が宣言する SLO ID を注釈に持つ。
`mise run check-slo-references` が、アラートの注釈に現れる SLO ID が宣言済みであること、runbook の参照先が実在することを検査する。

## ダッシュボードの構成

一枚目は、**利用者から見た成功**を先に置き、次に**飽和**を置く。
原因を先に置くと、症状が無い変動を追うことになる。

| 位置 | 置くもの | 読み方 |
| --- | --- | --- |
| 先頭 | ルート別のリクエスト数、エラー比率、所要時間 p99 | 利用者から見て何が壊れているかを決める |
| 二段目 | ログインの結果内訳、ログイン流量制限の発動比率、トークン発行のレート | 認証の経路のどこで失敗しているかを絞る |
| 三段目 | レーン別のキュー深度、取得待ち時間 p99、失敗比率、再試行率 | 非同期処理の滞留と失敗を見る |
| 四段目 | アドミッションコントロールの拒否率と処理中リクエスト数 | 過負荷時に何を捨てているかを見る |

テナント単位の切り分けは、指標では行わない。
テナント ID を指標のラベルにすると系列数がテナント数に比例して増え、Prometheus の保存量と照会時間が利用者の増加に連動する。
切り分けは、テナント ID を構造化メタデータとして持つログと、トレースの属性で行う。
したがってダッシュボードは、テナントを跨いだ全体の異常を示すところまでを担い、どのテナントかの特定はログとトレースへ引き継ぐ。

## 監視基盤自体の監視

監視基盤が止まると、シグナルの欠落が「異常が無い」と同じ見え方になる。
このため、欠落と正常を区別する判定を、サービスの判定とは別に持つ。

| 区別したいこと | 判定 |
| --- | --- |
| 対象が落ちている | 取得対象のスクレイプが失敗している |
| 監視基盤が落ちている | Prometheus、Loki、Alloy のいずれかが応答しない |
| 保存先が尽きた | 監視基盤の保存容量の残りが閾値を下回る |

現在の構成はこれらの判定を持たない。
判定が無い間、ダッシュボードの空白とアラートの沈黙を、サービスが正常である根拠として扱わない。

## 未確定事項

通知の宛先とエスカレーションは、デプロイ先で決まる。
ローカル Docker Compose と汎用 Kubernetes のどちらも Alertmanager を持たず、アラートは Prometheus が評価するところまでで止まる。
このため、「ページ」と「通知」の区別は現在のところ設計上の分類であり、実際に人を呼び出す経路はまだ無い。

判定の形も未確定である。
エラー率とレイテンシーのアラートは名前に誤差予算の消費を掲げているが、判定しているのは 5 分平均の瞬間値であり、消費の速さではない。
短い急変と長い劣化を同じ閾値で扱うため、瞬間的な跳ねで呼び出され、緩やかな劣化を見逃す。
複数の時間窓による消費速度の判定へ移すかどうかは、通知の宛先が決まった後に判断する。
