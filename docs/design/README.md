# 全体設計文書

この文書は、IdMagic が要件を実現する構造と仕組みを記載する全体設計文書の入口である。
製品の目的と要件は[要件文書](../requirements/README.md)を参照する。

全体設計は、システム全体の構造（アーキテクチャ）と、複数のモジュールに共通する仕組みを定め、要件を各モジュールへ割り当てる。
割り当てを受けた一つのモジュールの内側の設計は、[モジュール設計文書](../modules/README.md)が同じ設計領域の語彙で書き、この文書からの割り当てと例外だけを記載する。
この分け方は、SWEBOK V4 のソフトウェアアーキテクチャと構成要素の設計の区別に対応する。

## 設計領域

設計は次の設計領域で構成する。
並びは、実現対象（アプリケーション、データ、インフラストラクチャ）、複数の実現対象へ作用する領域、検証の順である。

| 設計領域 | 区分 | 参照先 | 内容 |
| --- | --- | --- | --- |
| アーキテクチャ設計 | 固有設計 | [担当文書](architecture/README.md#アーキテクチャ設計) | 制約、解決戦略、システム境界、論理構成、実行構成、配置、アーキテクチャ上の判断、リスクと技術的負債 |
| アプリケーション設計 | 固有設計 | [担当文書](application/README.md#アプリケーション設計) | API ガイドライン、設計ガイドライン、バックエンド設計、フロントエンド設計、ユーザーインターフェース設計 |
| データ設計 | 固有設計 | [担当文書](data/README.md#データ設計) | データの正、整合性、保存、移行、廃棄 |
| インフラストラクチャ設計 | 固有設計 | [担当文書](infrastructure/README.md#インフラストラクチャ設計) | コンピューティング、ストレージ、ネットワーク |
| セキュリティ設計 | 固有設計 | [担当文書](security/README.md#セキュリティ設計) | 資産、信頼境界、セキュリティ制御、脅威モデル |
| 信頼性設計 | 固有設計 | [担当文書](reliability/README.md#信頼性設計) | 障害、冗長性、縮退、復元 |
| 性能設計 | 固有設計 | [担当文書](performance/README.md#性能設計) | 負荷、資源、待ち行列、拡張 |
| オブザーバビリティ設計 | 固有設計 | [担当文書](observability/README.md#オブザーバビリティ設計) | メトリクス、ログ、トレース、検知 |
| 検証設計 | 固有設計 | [担当文書](verification/README.md#検証設計) | 要件を満たしたと判断するための証拠 |

設計判断とリスクは設計領域ではなく、アーキテクチャ記述に含める設計の記録である。
システム全体の判断は[アーキテクチャ上の判断](architecture/decisions.md)、既知のリスクと技術的負債は[リスクと技術的負債](architecture/risks.md)、脅威は[脅威モデル](security/threat-model.md)に記載する。

## 共通設計の適用範囲

上の九領域の共通設計は全モジュールに適用する。
アーキテクチャとアプリケーションは構成と公開契約、データは保存する状態、インフラストラクチャは実行単位、セキュリティは信頼境界と秘密情報を対象とする。
信頼性は依存先の障害と復旧、性能は割り当てた品質要件と資源配分、オブザーバビリティは要求と作用の信号、検証は宣言済みの保証の証拠を扱う。
各担当文書が定める対象に該当する仕組みに適用し、純粋な計算に永続化や独立した実行基盤を要求する意味にはしない。

モジュールの索引に記載がない領域には、この共通設計を適用する。
モジュールは固有設計、個別の委譲先、実現対象がない場合の対象外だけを書く。
対象外の宣言はそのモジュールの実現対象に限り、システム全体の品質要件と信頼境界の保証は維持する。
領域を横断して読む場合は、この表とモジュールの差分を合わせて参照する。

## 品質要件の担当と証拠

数値目標と測定境界は[品質要件](../requirements/quality.md)が宣言し、[論理アーキテクチャの割り当て](architecture/logical.md#品質要件の割り当て)が担当機能、設計、検証への参照を定める。
数値を持たない品質特性は、[品質特性ごとの要件](../requirements/quality.md#品質特性ごとの要件)が参照する共通設計と検証に従う。
割り当ては目標の担当を示し、実装済み、検証済み、達成済みのいずれも意味しない。
監視の実装状況は[検知していない事象](observability/monitoring.md#検知していない事象)、実測の有無は[品質要件の証拠の区分](../requirements/quality.md#証拠の区分)、検証に必要な環境は[要件の群ごとの証拠](verification/README.md#要件の群ごとの証拠)を参照する。

## 用語

| 用語 | 意味 | 詳細 |
| --- | --- | --- |
| デプロイ、デプロイメント | アプリケーションを実行環境へ配置し、稼働させること | [デプロイメントアーキテクチャ](architecture/deployment.md) |
| ランタイム | 稼働中のプロセス、その役割、プロセス間の接続 | [ランタイムアーキテクチャ](architecture/runtime.md) |
| プラットフォーム | コンピューティング、ストレージ、環境差、構成管理、IaC の責任範囲 | [プラットフォーム設計](infrastructure/platform.md) |
| コンピューティング | 構成要素を動かす CPU とメモリの提供元 | [プラットフォーム設計](infrastructure/platform.md#コンピューティング) |
| 構成ファイル | `infra/` の Docker Compose ファイル、Kubernetes マニフェスト、Terraform | [デプロイメントアーキテクチャ](architecture/deployment.md) |
| 共通トポロジー | デプロイ先によらず共通する実行単位と接続関係 | [デプロイメントアーキテクチャ](architecture/deployment.md#共通トポロジー) |
| デプロイプロファイル | 共通トポロジーを特定の製品とリソースで実現する構成例。実際に稼働中の環境を示すものではない | [デプロイメントアーキテクチャ](architecture/deployment.md#デプロイプロファイル) |
| シークレット | 認証情報、暗号鍵、トークンなど、漏えいを防ぐ必要があり、リポジトリへ保存しない設定値 | [シークレット設計](security/secrets.md) |
| キャパシティ | 処理能力とその算出。ストレージの量は「保存容量」と呼ぶ | [キャパシティ設計](performance/capacity.md) |
| 想定ワークロード | キャパシティ算出に用いる利用規模と負荷 | [キャパシティ設計](performance/capacity.md#想定ワークロード) |
| サイジング計算式 | レプリカ数と接続数を求める式 | [キャパシティ設計](performance/capacity.md#サイジング計算式) |
| ロードシェディング順序 | 飽和時に優先度の低い経路から受け付けを落とす順序 | [キャパシティ設計](performance/capacity.md#ロードシェディング順序) |
| アドミッションコントロール | 過負荷時にハンドラーの手前で受け付けを止める仕組み | [アドミッションコントロールの設計](../modules/system/features/admission-control.md#実現方式) |
| オブザーバビリティ | メトリクス、ログ、トレースと、それらの相関 | [オブザーバビリティ設計](observability/) |
| ガイドライン | 設計時に参照する判断基準 | [API ガイドライン](application/api-guidelines.md)、[設計ガイドライン](application/design-guidelines.md) |
