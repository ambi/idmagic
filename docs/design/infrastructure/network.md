# ネットワーク設計

## 通信経路

公開通信はゲートウェイで TLS を終端し、静的 UI と Go API へ同一オリジンで振り分ける。
API の直接公開は、Cookie、CSRF、セキュリティヘッダー、経路制御の前提を崩すため、同じ制御を別の境界で実装しない限り行わない。

API とワーカーの送信先は、DNS、PostgreSQL、構成された上流認証局、下流プロビジョニング先、通知先、OTLP コレクターに限定する。
Kubernetes の既定 NetworkPolicy は API への UI ゲートウェイと Prometheus からの受信、ワーカーへの Prometheus からの受信、DNS と PostgreSQL への送信を許可する。
外部連携を有効にする環境では、必要な宛先を明示的に追加する。

## 名前と証明書の所有

DNS、公開証明書、ワイルドカード証明書の発行と更新は配備基盤の責任である。
`TENANT_BASE_DOMAIN` を使うのは、ワイルドカード DNS と証明書を用意し、キャッシュキーへ Host を含めた場合に限る。
発行者 URL、Cookie のスコープ、WebAuthn の RP ID は名前の構成に依存するため、切替を単なる DNS 変更として扱わない。

## ポートと管理アクセス

公開入口、API、ワーカーの指標、PostgreSQL、監視基盤のポートは構成資材を正本とする。
`/metrics` はループバック、管理ネットワーク、または認証付きプロキシの背後に置く。
Loki、Grafana、Prometheus の管理画面を公開入口と同じ認証なしの経路へ載せない。
