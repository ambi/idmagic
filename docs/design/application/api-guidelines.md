# API ガイドライン

このファイルは、外部に見える HTTP インターフェースの形を、操作を跨いで揃える規則を持つ。
個々の操作の形、状態コード、エラーの直和は TypeSpec が持ち、ここには複数の操作で同じでなければならないことだけを書く。
認可とスコープの規則は[認可設計](../security/authorization.md)が持つ。

## 規則の書き方

各規則は次の 4 列で書く。

| 列 | 内容 |
| --- | --- |
| 規則 | 何をどう揃えるか |
| 守っているもの | この規則がないと何が壊れるか。規則を緩めてよいかを判断する根拠になる |
| 強制点 | 違反を拒否する場所。TypeSpec、Go の実装、PostgreSQL の制約、検査タスクのいずれか。拒否する場所がなければ「検査なし」と書く |
| 適用状況 | 全接点で従っているか。従っていない接点があれば名指しする |

規則は、今日有効な決定として書く。
現行の実装が従っていない接点は、規則を将来の案にするのではなく、適用状況の列で名指しする。
採らないと決めた観点も、採らない決定として同じ表に置く。

## 接点の分類

規則が及ぶ範囲は接点ごとに違う。

| 接点 | パス | 形を決めるもの |
| --- | --- | --- |
| 管理 API | `/api/admin/v1/` | このガイドライン |
| アカウント API | `/api/account/v1/` | このガイドライン |
| ブラウザー API | `/api/auth/` | このガイドライン。版を持たず、安定性区分は `internal` である |
| プロトコルエンドポイント | OAuth 2.0 と OIDC、Dynamic Client Registration、SAML、WS-Federation、SCIM、Shared Signals | 各標準。各 Context の `standards.md` が採用した版と差分を持つ |
| 運用エンドポイント | `/readyz`、`/startupz`、`/metrics` | 監視の慣習。命名と版の規則は及ばない |

以降の節で汎用 API と呼ぶのは、管理 API、アカウント API、ブラウザー API の 3 つである。

## リソースの命名

| 規則 | 守っているもの | 強制点 | 適用状況 |
| --- | --- | --- | --- |
| パスは、接点の接頭辞のあとに、複数形の名詞によるコレクションと `{識別子}` を交互に並べる | 呼び出し側がパスから資源の親子関係を読めること | 検査なし。TypeSpec のレビューで守る | 汎用 API の全コレクションが従う |
| テナントまたは主体に一つしかない資源は、単数形の名詞で置き、識別子を持たない（`/api/admin/v1/settings`、`/api/admin/v1/tenant/branding`、`/api/account/v1/profile`） | 存在しない識別子を呼び出し側に組み立てさせないこと | 検査なし | 全接点で適用済み |
| 固定のパス区間はケバブケースで書く（`identity-providers`） | 区切り方が混在すると、呼び出し側がパスを推測で書けないこと | 検査なし | 既存の 24 区間がスネークケースである（`audit_events`、`authentication_event_buckets`、`change_password`、`change_request`、`data_export`、`dry_run`、`endpoint_style`、`forgot_password`、`group_attribute_schema`、`lifecycle_workflow_runs`、`lifecycle_workflows`、`notification_preferences`、`notification_templates`、`password_reset_context`、`required_actions`、`reset_password`、`revoke_all`、`revoke_others`、`search_options`、`signin_activity`、`step_up`、`trusted_devices`、`user_attribute_schema`、`verify_context`）。パスの変更は破壊的変更なので、既存の区間は変えず、新しいパスに持ち込まない |
| パスパラメーター、クエリパラメーター、JSON のプロパティはスネークケースで書く（`created_at`、`{user_id}`） | 汎用 API の利用者は OAuth 2.0 と OIDC のスネークケースのメタデータも読むので、記法を一つに揃えること | 検査なし | 汎用 API の全プロパティが従う |
| プロトコルエンドポイントの記法は各標準に従う。SCIM は `userName` のようなキャメルケース、SAML と WS-Federation は XML の要素名である | 標準に従うクライアントとの相互運用性 | 各 Context の `standards.md` と、その標準の適合テスト | 全接点で適用済み |

## 値の表現

| 規則 | 守っているもの | 強制点 | 適用状況 |
| --- | --- | --- | --- |
| 時点は UTC の RFC 3339 `date-time` 文字列で表し、プロパティ名を `_at` で終える | タイムゾーンの解釈違い。文字列の辞書順と時刻順が一致すること | TypeSpec の `utcDateTime` 型 | 汎用 API の全時点が `utcDateTime` である。OIDC のクレーム `auth_time` はプロトコルエンドポイントの値で、標準に従い Unix 秒の整数とする |
| 暦日は RFC 3339 `full-date`（`2006-01-02` の形）で表す | 時点と暦日を取り違えないこと | Go の domain（`backend/idmanagement/user/domain/attribute_cell.go`） | 利用者属性の `AttributeValue.date` は、契約が `format: date` を持たない平の `string` として宣言している |
| 期間は単位を名前の末尾に付けた整数で表す（`retry_after_seconds`、`grace_days`）。単位は秒を基本とし、日の単位でしか意味を持たない設定だけを `_days` にする。ISO 8601 の期間表記は使わない | 単位の読み違い。ISO 8601 の期間は月と年の長さが一意でなく、言語ごとに解析器の対応も揃わないこと | 検査なし | 汎用 API の全期間が従う。OAuth 2.0 の `expires_in` と RFC 8628 の `interval` は、標準の名前のまま秒を表す |
| 件数、バイト数、秒数は JSON の整数で返し、文字列に包まない | 呼び出し側が数値として比較できること | TypeSpec の整数型 | 全接点で適用済み |
| 列挙値は小文字のスネークケースで書き、Go の定数をそのまま写す（`pending_deletion`）。標準が定める値は標準の表記のまま使う（`PS256`、`S256`、`DPoP`、グラントタイプの URN） | 列挙ごとに大文字小文字の規則を覚えさせないこと | 検査なし。値の出どころは[契約上のワイヤ本体](#契約上のワイヤ本体)が定める | 次の列挙がパスカルケースの値を返す。`AuthorizationDetailTypeState`、`McpResourceServerState`、`SsfStreamDirection`、`ClientSecretCredentialStatus`、`KeyProvider`、`KeyUsage`、`SigningKeyState`、`RequiredAuthnStrength`、`RevocationReason`。値の変更は破壊的変更なので、既存の値は変えず、新しい列挙に持ち込まない |
| IdMagic が採番する識別子は、UUID v4 の正規形（小文字、ハイフン区切り）の文字列とする。契約は `format: uuid` を宣言せず、呼び出し側は識別子を不透明な文字列として扱う | 採番の方式を変えても契約が変わらないこと | Go の `spec.NewUUIDv4()` と PostgreSQL の `UUID` 型 | 採番の規則が別に決まる値は除く。署名鍵の `kid` は JWK thumbprint、SCIM の `id` は 16 進 32 文字である。`authorization-detail-types/{type}` や `notification_templates/{template_key}` のような名前による鍵は識別子ではない |
| 値がないことはプロパティの省略で表し、レスポンスに `null` を書かない | 「ない」の表し方が 2 通りあると、呼び出し側が両方を扱う分岐を書くこと | TypeSpec は任意プロパティ（`?`）で表し、`| null` を持つモデルを置かない | 契約は全モデルで従う。Go のレスポンス構造体が `null` を書かないことは、`mise run check-contract-drift` がプロパティ名だけを比べるため検査していない |
| `PATCH` の本文で省略したプロパティは変更しない。`null` は省略と区別せず、値を消す意味を持たせない | 部分更新で、送っていないプロパティを消さないこと | Go のハンドラーがポインター型のフィールドで受ける | 利用者、アカウントのプロフィール、アプリケーションのプロトコル設定で確認している。ほかの `PATCH` は個別に確認していない |

## HTTP メソッドの割り当て

操作の種類ごとに、次のメソッドと成功時の状態コードを使う。

| 操作 | メソッドと対象 | 成功時の状態コード |
| --- | --- | --- |
| 取得 | コレクションまたは資源への `GET` | 200 |
| 作成 | コレクションへの `POST` | 201。本文に作成した資源を返す |
| 全体置換 | 資源への `PUT` | 200 で置換後の資源を返すか、本文なしの 204 |
| 部分更新 | 資源への `PATCH` | 200 で更新後の資源を返すか、本文なしの 204 |
| 削除 | 資源への `DELETE` | 204 |
| CRUD に収まらない操作 | 資源の下の動詞区間への `POST` | [CRUD に収まらない操作](#crud-に収まらない操作)が定める |
| 長時間かかる操作の開始 | コレクションへの `POST` | 202。[長時間かかる操作](#長時間かかる操作)が定める |

メソッドを選ぶと、RFC 9110 がそのメソッドに課す性質も一緒に決まる。
呼び出し側、プロキシ、再試行の仕組みはその性質を前提に動くので、性質を満たせない操作にはそのメソッドを使わない。

| 規則 | 守っているもの | 強制点 | 適用状況 |
| --- | --- | --- | --- |
| `GET` はサーバーの状態を変えない | プロキシ、先読み、再試行が `GET` を安全として扱うこと | 検査なし | 外部 IdP からの OIDC コールバック（`GET /api/auth/federation/oidc/callback`）はログインの状態を進める。認可レスポンスがリダイレクトで届くため、標準が `GET` を要求する |
| `PUT` は全体置換にだけ使い、同じ本文を再送すると同じ状態になる | 再送されても結果が変わらないこと | 検査なし | 汎用 API の全 `PUT` が全体置換である |
| `PATCH` の本文は `application/json` とし、JSON Merge Patch（RFC 7396）と JSON Patch（RFC 6902）のメディアタイプは受け付けない | 汎用 API の本文を一つのメディアタイプに揃えること。Merge Patch が `null` に持たせる削除の意味を持ち込まないこと | TypeSpec の `requestBody` の宣言 | 汎用 API の全 `PATCH` が従う。SCIM の `PATCH` は RFC 7644 の `PatchOp` を受ける |
| 作成は、作成した資源を 201 の本文で返す。`Location` ヘッダーは返さない | 呼び出し側が本文の `id` だけで次のリクエストを組み立てられること | TypeSpec の 201 のモデル | 全接点で適用済み |
| 外部の URI が鍵になる資源は、コレクションへの `POST` で作成または更新し（新規なら 201、既存なら 200）、`DELETE` ではクエリパラメーターで鍵を渡す | URI をパス区間へ埋め込むと二重のエンコードが要り、長さも 2048 に及ぶこと | TypeSpec の宣言 | SAML サービスプロバイダー（`entity_id`）と WS-Federation の証明書利用者（`wtrealm`）の 2 つがこの形である |

## 宣言する状態コード

| 規則 | 守っているもの | 強制点 | 適用状況 |
| --- | --- | --- | --- |
| 操作は、自身のハンドラーとその手前に立つ guard が書く状態コードをすべて宣言する。[契約上のワイヤ本体](#契約上のワイヤ本体)が本文に課す「契約に書くのはサーバーが実際に返すもの」という規則を、ステータス行にも及ぼす | 宣言にないコードが返ると、呼び出し側は分岐を持てない。宣言にあって返らないコードは、呼び出し側に到達しない分岐を書かせる | `mise run check-status-drift` | 下の「検査が読めない範囲」を参照 |
| 400 はリクエストを解析できないこと（不正な JSON、必須構造の欠落、未知のプロパティ）を、422 は解析できた内容が業務規則に違反すること（不正なロール、参照の不一致、ポリシー違反、長さの上限違反）を表す | 呼び出し側が、送り方の誤りと内容の誤りを分けて扱えること | 検査なし | 全接点で適用済み |
| 一意性と状態の衝突（名前の重複、別の資源から参照されている、状態が操作を許さない）は 409 で返す | 衝突を、内容の誤りと区別して扱えること | 検査なし | ハンドラーは利用者名、グループ名、エージェント名、トラストバンドルの名前と発行者、ライフサイクルワークフローの名前の重複に 409 を書く。利用者、グループ、エージェント、トラストバンドルの作成と更新、ライフサイクルワークフローの作成の契約は、409 を宣言していない |
| 403 を宣言する操作は 401 も宣言する。認証済みの主体を確定できなければ 401 とし、資格情報がなければ `authentication_required`、提示されたアクセストークンを検証できなければ `invalid_token` を返す。主体を確定できても権限が足りなければ 403 の `access_denied` または `insufficient_scope` とする | 片方だけを宣言すると、呼び出し側は認証の失敗を権限の不足として扱い、資格情報を取り直せば通るリクエストを諦める | 検査なし | 全接点で適用済み |
| 401 の本文は接点ごとの共有モデルを参照する。汎用 API は `IdMagic.Contract.AuthenticationRequiredResponse`（`AuthenticationRequiredError` と `InvalidAccessTokenError` の union）、OAuth 2.0 と OIDC は `IdMagic.Contract.OAuthUnauthorizedResponse`、SCIM は `IdMagic.Contract.ScimUnauthorizedResponse` である | 401 の本文候補は接点ごとに共通なので、操作ごとに書き写すと食い違うこと | TypeSpec の参照 | 全接点で適用済み |
| 403 は操作ごとのモデルを持つ | 本文が操作ごとに違うこと（`AccessDeniedError`、`InsufficientScopeError`、`MfaEnrollmentNotAllowedError`）。様式を揃えるための規則ではない | TypeSpec の宣言 | 全接点で適用済み |

次の 3 つは宣言しない。
いずれも、その操作のレスポンスではないためである。
ミドルウェアが返す 2 つだけは、契約ではなくこの表に書く。

| 宣言しないもの | 返す場所 | 宣言しない理由 |
| --- | --- | --- |
| 共通のエラーハンドラーが、どのハンドラーも写像しなかったエラーに書く 500 | 共通のエラーハンドラー | すべての操作に同じに出て、呼び出し側が操作ごとに変えられる対応もない。すべての操作に同じ 1 行を書いても分岐は増えない。ハンドラーが固有のエラーコードを添えて自分で書く 5xx（パスキーの依存先が使えないときの 503 `webauthn_unavailable` など）は、その操作固有の結果なので宣言する |
| 宿主名から解決できないテナントへの 404 `{"error": "tenant_not_found"}` | テナント解決ミドルウェア。ルーティングの手前で返る | 操作ごとに宣言すると、その操作自身の 404（資源がない）と同じ行に 2 つの意味が乗り、呼び出し側は本文を読み直してどちらかを判断することになる。経路にかかわらず 404 と `tenant_not_found` で返る |
| 飽和時の 503 `urn:idmagic:error:service_overloaded` | アドミッションコントロールミドルウェア。ルーティングのあと、ハンドラーの手前で返る | どの操作でも意味は「いまキャパシティが足りないので受け付けなかった」の 1 つで、呼び出し側の対応も `Retry-After` の秒数だけ待って再送することしかない。どの経路がどの順で拒否されるかは[キャパシティ設計](../performance/capacity.md#ロードシェディング順序)、機構は [System Context の内部設計](../../contexts/system/internals.md#admission-control)が持つ |

### 検査が読めない範囲

`mise run check-status-drift` は操作ごとに、契約が宣言する集合と、ハンドラーおよび guard が書くコードを突き合わせる。
エラー値からレスポンスを決めるヘルパー（`WriteAccountError` のような写像）は辿らない。
どの分岐に入るかはユースケースが返すエラーで決まり、ハンドラーの字面には現れないためである。
辿れなかった操作は合格とせず「読み残しあり」として数え、その件数を毎回出力する。
上の表で 409 の宣言漏れが残っているのは、この読み残しの中である。

## HTTP エラーレスポンス

| 規則 | 守っているもの | 強制点 | 適用状況 |
| --- | --- | --- | --- |
| 汎用 API のエラーは RFC 9457 Problem Details（`application/problem+json`、`type`、`title`、`status`、`detail`、`instance`）で返す。`instance` にはリクエスト相関用の `request_id` を載せる | 呼び出し側がエラーの形を一つだけ扱えばよいこと | TypeSpec の `IdMagic.Contract.ProblemDetails` と Go の `support_http.WriteProblem` | 下の 2 つの独自形状を除いて適用済み |
| 個々のエラーは `model <Name>Error is ProblemDetails;` と書き、対応する `type` URN の接尾辞（サーバーが返すエラーコード）を `@doc` で名指しする | 契約の読み手がエラーコードからモデルを引けること | TypeSpec の宣言 | 全接点で適用済み |
| プロトコルエンドポイントは各標準が定めるエラーを返し、Problem Details を適用しない。OAuth 2.0 と OIDC、Dynamic Client Registration（RFC 7591）は `IdMagic.Contract.OAuthError`（`error`、`error_description`、RFC 6749 §5.2）、SCIM は `IdMagic.Contract.ScimProtocolError`（RFC 7644 §3.12）を参照する | 標準に従うクライアントとの相互運用性 | TypeSpec の参照 | 全接点で適用済み |
| 境界はパッケージではなく接点ごとに引く。同じパッケージの中でも、ブラウザーや管理コンソールが呼ぶ操作は Problem Details を返し、標準が形を定める相手への操作だけが例外になる | パッケージの配置が本文の形を決めないこと | TypeSpec の宣言 | 全接点で適用済み |
| どちらにも当てはまらない独自形状は 2 つに限り、本文を直接宣言する。`EndpointRateLimitPolicy` の 429（`error`、`retry_after_seconds`、`message` と `Retry-After` ヘッダー）と、Shared Signals の受信エンドポイント（RFC 8935、`/ssf/streams/{stream_id}/events`）の拒否（`error`、`message`）である | 独自形状が増えると、呼び出し側が扱う形が増えること | TypeSpec の宣言 | この 2 つだけである |
| 同じエラーコードが接点によって別の本文で返るときは、`AccessDeniedError` と `OAuthAccessDeniedError` のように接点ごとにモデルを分ける。一つのモデルに 2 つの形を名乗らせない | モデルから本文の形が一意に決まること | TypeSpec の宣言 | 全接点で適用済み |
| エラー本文の文字列（`message`、`error_description`、`detail`、プレーンテキストの本文）は、`DisplayLanguage` にかかわらず英語で固定する。`Accept-Language` による切り替えも採らない | 同じ失敗が呼び出し側の設定次第で別の文字列になると、ログの照合と相互運用が壊れること | 検査なし | 全接点で適用済み |
| 翻訳は、安定したエラーコードを鍵として UI が行う。Problem Details では `type` の `urn:idmagic:error:` に続く部分が鍵である。辞書にないコードに出会った UI は、`detail` または `title` を英語のまま表示する | サーバーの文言を変えずに UI の言語を増やせること | UI の辞書 | 全接点で適用済み |

## コレクションの操作

| 規則 | 守っているもの | 強制点 | 適用状況 |
| --- | --- | --- | --- |
| 件数がテナントの規模や時間とともに増える一覧は、キーセット方式のカーソルで区切る。オフセットによるページングは採らない | 深いページでも問い合わせの費用が一定であること。ページを送る間に行が増減しても、行を飛ばしたり重複させたりしないこと | Go の `support_http.ParsePageRequest` | 区切らない一覧が 2 つある。`/api/admin/v1/tenants` と `/api/admin/v1/users/{user_id}/groups` である。`/api/admin/v1/authorization/relation-tuples` と `signin_activity` は `limit` だけを受け、先頭の件数で切る |

## 文字列長の上限

文字列フィールドの長さ上限は、公開契約、Go の検証、PostgreSQL の制約、UI の入力欄という 4 つの境界に同じ数で現れる。
数が同じでも数える単位が違えば別々の上限になるので、単位を先に固定する。

| 規則 | 守っているもの | 強制点 | 適用状況 |
| --- | --- | --- | --- |
| 長さは Unicode コードポイントで数える。TypeSpec の `@maxLength`、OpenAPI の `maxLength`、PostgreSQL の `char_length()`、Go の `utf8.RuneCountInString` はいずれもコードポイントを数える。zog の `String().Max(n)` は UTF-8 のバイト数を数えるので文字列フィールドに使わず、`backend/shared/spec` の `Chars` と `CharsAtMost` を使う | バイト数で数えると、上限 100 の名前が英字なら 100 文字、日本語なら 33 文字になり、契約に書いた数が意味を持たなくなること | Go の `spec.Chars` | 下の 2 つの例外を除いて適用済み |
| 例外の 1 つめは、準拠する標準自身がオクテットで上限を定めている値である。メールアドレスは RFC 5321 の 254 オクテット、realm は DNS ラベルの 63 オクテットである | 標準の数をそのまま使えること。どちらも形式を ASCII に限るので、実際の値ではコードポイント数と一致する | Go の domain | この 2 つである |
| 例外の 2 つめは、上限が守る資源そのものがバイトで測られる場合である。下の「索引の鍵の成分」がこれにあたる | btree が制限しているのはバイトであること | Go の `spec.KeyString` と PostgreSQL の `octet_length` | 下の表の列である |
| 上限を置く値は、下のデフォルトの区分から選ぶ。外部の標準も固定の表示面も関与しない値のために、新しい数を持ち込まない | 数が値ごとに増えると、どの数が正しいかを誰も判断できなくなること | 検査なし | 下の「区分の外に置く値」を除いて適用済み |
| 上限違反は 422 で返し、違反したフィールドと上限を `detail` に載せる | 利用者が何を短くすればよいかを判断できること | Go の domain | 汎用 API で適用済み。SAML、WS-Federation、OAuth 2.0、SCIM、WebAuthn のように相手側のプロトコルがレスポンスの形を定める接点では、長さの違反もそのプロトコルのエラーとして返す。AuthnRequest を送ってきた相手に Problem Details を返しても読めない |
| 資源の上限は書き込み経路にだけ課す。索引の鍵の成分を検索の条件として受け取る経路（`GET /Users/{id}` など）は、上限を超えた値を 422 ではなく通常の「見つからない」として扱う | 検索は索引行を作らないので、長い値で落とす理由がないこと | Go のハンドラー | 全接点で適用済み |
| `CHECK` に置くのは、長さのように安定した構造上の境界に限る。スキームの allowlist のような、変わりうる入力規則を DDL へ入れない | 規則が変わるたびにすべてのデプロイ先でスキーマ移行が要ること。利用者の入力誤りで落ちる規則をこの層に置くと、「実装の不具合だけが落ちる場所」という役割が崩れること | 検査なし | 全接点で適用済み。テナントのフッターリンクに `https` しか許さない規則は Go の domain が持ち、`CHECK` は長さだけを見る |

### 索引の鍵の成分

連携相手が値を決める識別子にも上限を置く。
上限を置かない選択は、実際には上限を PostgreSQL の btree に任せることでしかない。
btree v4 は索引行 1 件を 2704 バイトに制限するので、主キーや一意索引の成分になっている列は、宣言の有無にかかわらずそこで頭打ちになる。
宣言しなければ、超過は書き込み時の `SQLSTATE 54000` として現れ、どのフィールドをどこまで短くすればよいかを利用者に伝えられない。
索引タプルは値を圧縮しようとするため、その境界がどこに来るかは値の中身によっても動く。

そこで、索引の鍵の成分になる列には、性質の違う 2 つの上限を重ねる。

| 上限 | 単位 | 役割 |
| --- | --- | --- |
| 契約の上限 | コードポイント | 公開契約が示す数。TypeSpec の `@maxLength` と Go の `spec.Chars` が持つ |
| 資源の上限 | バイト | 索引行に収まることの保証。Go の `spec.KeyString` と PostgreSQL の `octet_length` が持つ |

契約の上限をコードポイントで置くだけでは足りない。
標準が 1024 文字と定める識別子でも、すべて 3 バイト文字なら 3072 バイトになり、宣言した契約を満たしたまま btree で落ちる。

複合鍵では、列ごとではなく鍵 1 件の合計が索引行に収まらなければならない。
鍵ごとにバイトの予算を持ち、その合計を 2400 バイト以下とする。
btree の 2704 バイトとの差は、索引タプル自身が使う領域と、将来列を足すための余白である。
この条件は `backend/shared/spec` のテストが守り、上限を後から広げて予算を超えたときにそこで分かる。

上限には、標準が定める数をそのまま使わない。
標準を超える値を出す実装は実在しうるので、標準の数は「上限が実運用で拘束的でないことの根拠」として記録し、上限そのものはその外側に置く。
これらは安全のために置く資源の境界であり、業務上望ましい長さではない。

| 列 | コードポイント | バイト | 理由 |
| --- | --- | --- | --- |
| `SamlServiceProvider.entity_id` | 2048 | 2048 | URI 区分。`saml-schema-metadata-2.0.xsd` の `entityIDType` は 1024 文字を定めるが、非準拠の SP を拒否しないためその外側に置く |
| SAML AuthnRequest の `ID` | 256 | 256 | 資源の上限。`xs:ID` に長さの規定はない |
| `WsFedRelyingParty.wtrealm` | 2048 | 2048 | URI 区分。WS-Federation は `wtrealm` を URI としか定めない |
| 外部 IdP の subject | 512 | 1024 | 資源の上限。OpenID Connect Core 1.0 §2 は `sub` を 255 ASCII 文字以下と定めるが、SAML の NameID には規定がない |
| 外部 IdP の SAML `Response` の `ID` | 256 | 256 | 資源の上限 |
| DPoP proof と client assertion の `jti` | 256 | 256 | 資源の上限。RFC 7519 に長さの規定はない |
| WebAuthn の credential ID | 2048 | 2048 | 資源の上限。WebAuthn は 1023 バイト以下と定めるので base64url で 1364 文字になる |

IdMagic が採番する鍵の成分にも上限を置くが、置く境界が違う。
SCIM の `id`（RFC 7643 が service provider の割り当てと定める値）、署名鍵の `kid`（RFC 7638 の JWK thumbprint）、発行したトークンの `jti` は、いずれも Handle 区分の 64 とする。
実値はそれぞれ 16 進 32 文字、base64url 43 文字、UUID であり、ASCII しか取らないので契約の上限と資源の上限が同じ数になる。
これらには Go 側の検査を置かず、`CHECK` だけを置く。
拒否すべき外部の入力がないためである。
超過するのは採番の実装が壊れたときだけで、それは利用者の誤りではないので 422 にしない。

鍵の成分ではない外部由来の値にも上限を置く。
btree の制約は受けないが、保存量を無制限にしてよい理由にはならない。
`tls_client_auth_subject_dn` は URI 区分の 2048、連携先の同期を隔離した理由を記録する文字列は Description 区分の 500 とする。
後者は利用者の入力ではなく連携先が返したエラー文なので、拒否せず書き込み側で切り詰める。
長いエラー文を理由に隔離そのものが失敗する方が高くつくためである。
外部入力を通らない固定長のダイジェスト（各種のトークンハッシュ）には上限を置かない。

### 4 つの境界の役割

4 つの境界は同じ数を持つが、役割は同じではない。

| 境界 | 役割 |
| --- | --- |
| TypeSpec の `@maxLength` | 公開契約。OpenAPI と生成ドキュメントが示す数の出どころ |
| Go の domain スキーマ | 唯一の強制点。ここを通らない書き込み経路を作らない |
| PostgreSQL の `CHECK (char_length(col) <= N)` | 最後の防壁。ここで落ちるのは実装の不具合であり、利用者向けエラーの発生源にしない。索引の鍵の成分では `octet_length(col) <= M` を同じ `CHECK` に併記する |
| UI の `maxLength` 属性 | 入力の補助。保証ではない |

UI だけは数える単位が違う。
HTML の `maxLength` が数えるのは UTF-16 のコード単位なので、基本多言語面の外にある絵文字などは 1 文字が 2 と数えられる。
UTF-16 のコード単位数はコードポイント数を下回らないため、ずれは必ず厳しい側に出る。
入力欄が通した値をサーバーが長さで拒むことはなく、逆に絵文字だけの入力では上限の手前で入力欄が止まる。
この不一致は許容する。
ブラウザーの `maxLength` にコードポイントを数えさせる方法はなく、自前で数え直して入力を書き換えると、入力中の変換や取り消しの邪魔になるためである。

## セキュリティレスポンスヘッダー

| 規則 | 守っているもの | 強制点 | 適用状況 |
| --- | --- | --- | --- |
| 境界ミドルウェアは、すべてのバックエンドのレスポンスに `X-Content-Type-Options: nosniff`、`Referrer-Policy: no-referrer`、`X-Frame-Options: DENY`、厳格な `Content-Security-Policy`（`default-src 'none'; base-uri 'none'; frame-ancestors 'none'; form-action 'self'`）を付ける | `frame-ancestors 'none'` と `X-Frame-Options: DENY` により、ログイン、同意、ポータルの画面の埋め込みとクリックジャッキングを防ぐこと。認可コードやトークンを含む URL を Referer で外部へ渡さないこと | Go の `support_http` のセキュリティヘッダーミドルウェア | 全接点で適用済み |
| CSP では `'unsafe-inline'` を使わない。IdMagic が出力する埋め込みスクリプトは SAML ACS と WS-Federation の POST バインディングで使う固定の自動送信処理だけなので、レスポンスごとに `script-src 'sha256-…'` で許可し、`form-action` も送信先エンドポイントに限る | 注入したスクリプトがセッションとトークンを持ち出さないこと | Go の SAML と WS-Federation のレスポンス生成 | 全接点で適用済み |
| CSP と `frame-ancestors` は IdMagic 自身が設定する | 経路ごとの判断が要るので、最小構成のプロキシの背後でも、プロキシがなくても保護が成立すること | Go のミドルウェア | 単一ページアプリケーションはゲートウェイが配信し、静的 HTML に `script-src 'self'` を含む CSP を設定する |
| HSTS は TLS を終端する側が設定する。`Strict-Transport-Security` はデフォルトで無効とし、TLS がこの区間かその手前で終端される場合にだけ有効にする（`HSTS_ENABLED`、`HSTS_MAX_AGE_SECONDS`、`HSTS_INCLUDE_SUBDOMAINS`） | 平文の `http` を使う開発環境に影響させないこと | 起動時設定 | デプロイ先の設定による |
| 画面を壊さずに CSP を厳しくするときは、`CSP_REPORT_ONLY=true` で `Content-Security-Policy-Report-Only` を出し、`CSP_REPORT_URI=<url>` で違反を集め、観察してから強制に戻す | 強制前に違反を観察できること | 起動時設定 | デプロイ先の設定による |

## インターフェースの安定性と版管理

管理 API とアカウント API は外部契約である。
外部インターフェースは次の 3 つの安定性区分に分ける。

| 安定性区分 | 意味 |
| --- | --- |
| `stable` | 版の付いた外部契約。下の互換性保証の対象 |
| `beta` | まだ互換性保証の対象でない外部契約 |
| `internal` | 外部契約に含まれない。ファーストパーティーのブラウザーセッションからだけ到達でき、API アクセストークンでは到達できない。予告なく変更する |

| 規則 | 守っているもの | 強制点 | 適用状況 |
| --- | --- | --- | --- |
| 後方互換な変更は、フィールドの追加、任意パラメーターの追加、新しいエンドポイントの追加である。破壊的変更は、フィールドの削除または名前変更、フィールドの型の変更、フィールドの必須化、エラーコードの変更、デフォルト値の変更である | 既存の呼び出し側が、版を上げずに動き続けること | `mise run check-api-compat` | 全接点で適用済み |
| 呼び出し側は、レスポンスの未知のフィールドを無視する | フィールドの追加を後方互換な変更として扱えること | 呼び出し側の責務 | ファーストパーティーの UI は従う |
| サーバーは、リクエストの未知のフィールドを 400 で拒否する | 綴りを誤ったフィールドが黙って無視され、設定したつもりの値が反映されないこと | Go の `support_http.DecodeJSON` | `echo` の `Bind` で復号する 5 つの操作（[上限と流量](#上限と流量)を参照）は未知のフィールドを無視する。このうち Dynamic Client Registration は、理解しないメタデータを無視することを RFC 7591 が求めている |
| `stable` と `beta` はパスで版を表す（`/api/admin/v1/...`、`/api/account/v1/...`）。版のない形は設けない。破壊的変更は既存のパスを変えず、新しい接頭辞で導入する。同時に提供する版は最大 2 つとする | 呼び出し側が版を明示して選べること | TypeSpec のルート | `stable`、`beta`、`internal` の区分は TypeSpec に注釈として宣言しておらず、パスの形だけが区分を表す。`/api/admin/v1/` と `/api/account/v1/` が `stable`、`/api/auth/` が `internal` であり、`beta` の操作はない |
| 管理 API の各操作は、到達を許す API アクセストークンのスコープを TypeSpec の `x-api-token-scopes` に宣言し、トークンで到達させない操作は `interactive_session` を宣言する。スコープを宣言しない操作には、API アクセストークンで到達できない | 対話セッション専用の操作に、API アクセストークンで到達させないこと | Go の `support_http` のスコープ判定と `mise run check-admin-scopes` | 管理 API の全操作が宣言する |
| プロトコルエンドポイント（OAuth 2.0 と OIDC、SAML、WS-Federation、SCIM、Shared Signals）には、パスの版を適用しない。互換性は各標準が規定し、Discovery Metadata（`/.well-known/...`）、`/scim/v2/ServiceProviderConfig`、SAML と WS-Federation のメタデータが正である | IdMagic 側でパスの版を重ねると、標準が定めた探索経路と食い違うこと | 各 Context の `standards.md` | 全接点で適用済み |

## 廃止

| 規則 | 守っているもの | 強制点 | 適用状況 |
| --- | --- | --- | --- |
| 非推奨の予定は TypeSpec に記録し、散文の側に一覧を持たない | 非推奨の一覧が二か所に分かれて食い違わないこと | TypeSpec | 非推奨の操作はない |
| `deprecated_since` を設定したインターフェースはレスポンスに `Deprecation` ヘッダー（RFC 9745）を付け、廃止時期が決まって `sunset_at` を設定したあとは `Sunset` ヘッダー（RFC 8594）も付ける | 呼び出し側が、実行時に非推奨を検出できること | Go の `support_http.DeprecationHeadersMiddleware` | ヘッダーを付けるミドルウェアはあるが、TypeSpec から `deprecated_since` と `sunset_at` を運ぶ経路がなく、`RuntimeContract.Deprecations` は常に空である |
| `sunset_at` は `deprecated_since` の最低 12 か月後とする | 呼び出し側に移行の期間を保証すること | 検査なし | 非推奨の操作はない |
| 破壊的変更は、TypeSpec から生成した OpenAPI と、実際に配布した内容を固定したリリースベースラインとの比較で検出する。ベースラインはリリース作業の一部としてだけ更新する | リリースせずに更新すると実際の後退を検出できなくなり、リリースしても更新しなければベースラインが古くなって同じ結果になること | `mise run check-api-compat` | 全接点で適用済み |

## 契約上のワイヤ本体

| 規則 | 守っているもの | 強制点 | 適用状況 |
| --- | --- | --- | --- |
| TypeSpec が `@body` に宣言する型は、サーバーが実際に受理し返す JSON そのものである。サーバーが送らない封筒を契約側で 1 段挟まない。ハンドラーが `map[string]any{"groups": ...}` のような封筒を書くときにだけ、契約もその封筒を持つ | 生成したクライアントと実際の通信が一致すること | `mise run check-contract-drift` | 検査は Go の変数に保持したレスポンスを型推論せず、辿れなかった操作を「読み残しあり」として数える |
| パスやクエリのパラメーターを、リクエスト本文のプロパティにしない | 契約上の置き場所と、サーバーが読む場所が一致すること | `mise run check-contract-drift` | [コレクションの操作](#コレクションの操作)の監査イベントの一覧が、クエリパラメーターを一つのオブジェクトとして宣言している |
| 本文が JSON でない接点（CSV のアップロード、SET の受信、XML のメタデータ、画像の配信、メトリクスの公開）は、そのメディアタイプと本文の型をそのまま宣言する | 呼び出し側が本文の形を契約から読めること | TypeSpec の宣言 | 全接点で適用済み |
| enum の値は member 名の複製ではなく、線上の値そのものを書く。標準が定める値は標準から、独自の値は Go の定数から写す | 契約の値と実際の値が一致すること | 検査なし | 全接点で適用済み |
| `unknown` は「任意の JSON 値」と読まれるので、実在する型やモデルがあればそれを書く。本当に任意でよい場合だけ、なぜ任意なのかを `@doc` に残す | 呼び出し側が型を推測しないこと | 検査なし | 全接点で適用済み |

## 採らない観点

公開されている API ガイドライン（Zalando RESTful API Guidelines、Microsoft Azure REST API Guidelines、Google AIP）の観点のうち、前の節で扱わなかったものの採否を決める。

| 観点 | 決定 | 理由 |
| --- | --- | --- |
| ハイパーメディア（HAL、JSON:API、HATEOAS） | 採らない | 汎用 API の呼び出し元はファーストパーティーの UI と、契約から生成したクライアントである。リンクを本文に埋めても、辿る側が存在しない。ページ送りのリンクだけは `Link` ヘッダーで返す |
| GraphQL | 採らない | 認可をスコープと操作の単位で宣言し、状態コードの宣言を検査する現在の仕組みが、単一のエンドポイントでは成り立たない |
| `X-HTTP-Method-Override` のようなメソッドの上書き | 採らない | 汎用 API の呼び出し元は、すべてのメソッドを送れる |
| 圧縮、`Accept` による内容交渉 | このガイドラインでは扱わない | 汎用 API の本文は JSON だけであり、圧縮はゲートウェイとプロキシの設定が持つ |
| Webhook による完了の通知 | 採らない | 長時間かかる操作の結果は資源への `GET` で問い合わせる。外部への事象の送信は Shared Signals が持つ |
