# API ガイドライン

この文書は、IdMagic が外部へ公開する HTTP API に共通して適用するルールを定める。
個々の API 操作のパス、パラメーター、ステータスコード、エラーの種類は TypeSpec で定義する。
この文書が扱うのは、複数の API 操作にまたがって統一すべき事項に限る。
認可とスコープのルールは[認可設計](../security/authorization.md)が定める。

## ルールの記述形式

各ルールは、見出しとルール本文に続けて、次の 3 項目を記載する。

| 項目 | 記載内容 |
| --- | --- |
| 目的 | ルールが防止する障害。ルールを緩和してよいかを判断する根拠になる |
| 担保手段 | 違反を検出または拒否する仕組み。TypeSpec の型、Go の実装、PostgreSQL の制約、検査タスクのいずれか。仕組みがなければ「なし」と記載する |
| 適用状況 | 全面適用か否か。未適用の API 操作があれば、その範囲を列挙する |

ルールは現時点で有効な決定として記載する。
実装が追随していない箇所は、ルールを将来の方針として書き換えるのではなく、適用状況に未適用として記載する。
採用しないと決定した事項も、採用しないというルールとして記載する。

## API 区分

適用するルールは API 区分ごとに異なる。

| API 区分 | パス | 準拠先 |
| --- | --- | --- |
| 管理 API | `/api/admin/v1/` | この文書 |
| アカウント API | `/api/account/v1/` | この文書 |
| ブラウザー API | `/api/auth/` | この文書。バージョンを持たず、安定性区分は `internal` とする |
| プロトコルエンドポイント | OAuth 2.0 と OIDC、Dynamic Client Registration、SAML、WS-Federation、SCIM、Shared Signals | 各標準。採用するバージョンと差分は各 Context の `standards.md` が定める |
| 運用エンドポイント | `/readyz`、`/startupz`、`/metrics` | 監視の慣行。この文書の命名とバージョンのルールは適用しない |

以降、管理 API、アカウント API、ブラウザー API の 3 区分を総称して汎用 API と呼ぶ。

## リソースの命名

### パスの構成

パスは、API 区分のプレフィクスに続けて、複数形の名詞で表すコレクションと `{識別子}` を交互に配置する。
テナントまたは主体ごとに一つしか存在しないリソースは、単数形の名詞で表し、識別子を付けない（`/api/admin/v1/settings`、`/api/admin/v1/tenant/branding`、`/api/account/v1/profile`）。

- **目的**：クライアントがパスからリソースの親子関係を読み取れるようにする。存在しない識別子をクライアントに組み立てさせない。
- **担保手段**：なし。TypeSpec のレビューで確認する。
- **適用状況**：全面適用。

### 静的パスセグメントの記法

パスパラメーター以外のパスセグメント（静的パスセグメント）は、ケバブケースで記述する（`identity-providers`）。

- **目的**：区切り文字の混在を防ぎ、クライアントがパスを類推で記述できるようにする。
- **担保手段**：なし。
- **適用状況**：未適用。次の 24 個の静的パスセグメントがスネークケースである。`audit_events`、`authentication_event_buckets`、`change_password`、`change_request`、`data_export`、`dry_run`、`endpoint_style`、`forgot_password`、`group_attribute_schema`、`lifecycle_workflow_runs`、`lifecycle_workflows`、`notification_preferences`、`notification_templates`、`password_reset_context`、`required_actions`、`reset_password`、`revoke_all`、`revoke_others`、`search_options`、`signin_activity`、`step_up`、`trusted_devices`、`user_attribute_schema`、`verify_context`。

### パラメーターとプロパティの記法

パスパラメーター、クエリパラメーター、JSON のプロパティは、スネークケースで記述する（`{user_id}`、`created_at`）。
プロトコルエンドポイントは各標準の記法に従う。
SCIM は `userName` のようなキャメルケース、SAML と WS-Federation は XML の要素名を用いる。

- **目的**：汎用 API のクライアントは OAuth 2.0 と OIDC のメタデータ（スネークケース）も扱うため、記法を統一する。プロトコルエンドポイントでは、標準準拠のクライアントとの相互運用性を確保する。
- **担保手段**：なし。
- **適用状況**：全面適用。

## 値の表現

### 日時と日付

日時は UTC の RFC 3339 `date-time` 形式の文字列で表し、プロパティ名の末尾を `_at` とする。
日付は RFC 3339 `full-date` 形式（`2006-01-02`）の文字列で表す。
OIDC のクレーム `auth_time` は、プロトコルエンドポイントの値であり、標準に従って Unix 時刻の整数で表す。

- **目的**：タイムゾーンの解釈の相違を防ぐ。日時の文字列の辞書順を時系列順と一致させる。日時と日付の混同を防ぐ。
- **担保手段**：TypeSpec の `utcDateTime` 型。日付は Go の domain（`backend/idmanagement/user/domain/attribute_cell.go`）が形式を検証する。
- **適用状況**：日時は全面適用。日付は未適用で、利用者属性の `AttributeValue.date` を TypeSpec が `format: date` を指定しない `string` として宣言している。

### 期間

期間は、単位を表す接尾辞をプロパティ名に付けた整数で表す（`retry_after_seconds`、`grace_days`）。
単位は秒を原則とし、日単位でのみ意味を持つ設定に限り `_days` を用いる。
ISO 8601 の期間表記（`PT30S`）は用いない。
OAuth 2.0 の `expires_in` と RFC 8628 の `interval` は、標準の名称のまま秒を表す。

- **目的**：単位の誤読を防ぐ。ISO 8601 の期間表記は月と年の長さが一意に定まらず、言語ごとにパーサーの対応状況も異なるため採用しない。
- **担保手段**：なし。
- **適用状況**：全面適用。

### 数値

件数、バイト数、秒数は JSON の整数で表し、文字列に変換しない。

- **目的**：クライアントが数値として比較できるようにする。
- **担保手段**：TypeSpec の整数型。
- **適用状況**：全面適用。

### 列挙値

列挙値は小文字のスネークケースで表し、Go の定数値と一致させる（`pending_deletion`）。
標準が定める値は、標準の表記をそのまま用いる（`PS256`、`S256`、`DPoP`、グラントタイプの URN）。

- **目的**：列挙ごとに大文字小文字の規則をクライアントに覚えさせない。
- **担保手段**：なし。値の転記元は[HTTP ボディの宣言](#http-ボディの宣言)が定める。
- **適用状況**：未適用。次の列挙がパスカルケースの値を返す。`AuthorizationDetailTypeState`、`McpResourceServerState`、`SsfStreamDirection`、`ClientSecretCredentialStatus`、`KeyProvider`、`KeyUsage`、`SigningKeyState`、`RequiredAuthnStrength`、`RevocationReason`。

### 識別子

IdMagic が採番する識別子は、UUID v4 の正規形（小文字、ハイフン区切り）の文字列とする。
TypeSpec は `format: uuid` を宣言せず、クライアントは識別子を不透明な文字列として扱う。
採番規則が別に定まる値はこのルールの対象外とする。
署名鍵の `kid` は JWK Thumbprint、SCIM の `id` は 16 進数 32 桁である。
`authorization-detail-types/{type}` や `notification_templates/{template_key}` のような名前によるキーは識別子に当たらない。

- **目的**：採番方式を変更しても API 契約を変更せずに済むようにする。
- **担保手段**：Go の `spec.NewUUIDv4()` と PostgreSQL の `UUID` 型。
- **適用状況**：全面適用。

### 値の不在

値が存在しないことは、プロパティの省略で表し、レスポンスに `null` を出力しない。
`PATCH` のリクエストボディで省略したプロパティは変更しない。
`null` は省略と区別せず、値の削除を意味しない。

- **目的**：不在の表現が 2 通りあると、クライアントが両方を処理する分岐を実装することになる。部分更新で、送信していないプロパティを消去しない。
- **担保手段**：TypeSpec は任意プロパティ（`?`）で表し、`| null` を持つモデルを置かない。Go のハンドラーは `PATCH` のリクエストボディをポインター型のフィールドで受ける。
- **適用状況**：TypeSpec は全面適用。Go のレスポンスが `null` を出力しないこと、および全 `PATCH` が省略と `null` を同一に扱うことは未検証である。`mise run check-contract-drift` はプロパティ名のみを比較する。

## HTTP メソッドの割り当て

操作の種類ごとに、次の HTTP メソッドとステータスコードを用いる。

| 操作 | メソッドと対象 | 成功時のステータスコード |
| --- | --- | --- |
| 取得 | コレクションまたはリソースへの `GET` | 200 |
| 作成 | コレクションへの `POST` | 201。レスポンスボディに作成したリソースを返す |
| 全体置換 | リソースへの `PUT` | 200 で置換後のリソースを返すか、ボディのない 204 |
| 部分更新 | リソースへの `PATCH` | 200 で更新後のリソースを返すか、ボディのない 204 |
| 削除 | リソースへの `DELETE` | 204 |
| カスタムメソッド | リソース配下の動詞セグメントへの `POST` | [カスタムメソッド](#カスタムメソッド)が定める |
| 長時間実行操作の開始 | コレクションへの `POST` | 202。[長時間実行操作](#長時間実行操作)が定める |

HTTP メソッドを選択すると、RFC 9110 がそのメソッドに課す性質（安全性と冪等性）も併せて確定する。
クライアント、プロキシ、再試行機構はその性質を前提に動作するため、性質を満たせない操作にそのメソッドを割り当てない。

### GET の安全性

`GET` はサーバーの状態を変更しない。

- **目的**：プロキシ、先読み、再試行機構が `GET` を安全なメソッドとして扱えるようにする。
- **担保手段**：なし。
- **適用状況**：外部 IdP からの OIDC コールバック（`GET /api/auth/federation/oidc/callback`）はログインの状態を進める。認可レスポンスはリダイレクトで到着するため、標準が `GET` を要求する。これ以外は全面適用。

### PUT の冪等性

`PUT` は全体置換にのみ用いる。
同一のリクエストボディを再送した場合、同一の状態になる。

- **目的**：再送によって結果を変化させない。
- **担保手段**：なし。
- **適用状況**：全面適用。

### PATCH のメディアタイプ

`PATCH` のリクエストボディは `application/json` とする。
JSON Merge Patch（RFC 7396）と JSON Patch（RFC 6902）のメディアタイプは受け付けない。
SCIM の `PATCH` は RFC 7644 の `PatchOp` に従う。

- **目的**：汎用 API のリクエストボディを単一のメディアタイプに統一する。JSON Merge Patch が `null` に与える削除の意味を持ち込まない。
- **担保手段**：TypeSpec の `requestBody` の宣言。
- **適用状況**：全面適用。

### 作成のレスポンス

作成操作は、作成したリソースを 201 のレスポンスボディで返す。
`Location` ヘッダーは返さない。

- **目的**：クライアントがレスポンスボディの `id` のみで後続のリクエストを組み立てられるようにする。
- **担保手段**：TypeSpec の 201 のモデル。
- **適用状況**：全面適用。

### URI をキーとするリソース

外部の URI をキーとするリソースは、コレクションへの `POST` で作成または更新する（新規なら 201、既存なら 200）。
`DELETE` では、キーをクエリパラメーターで渡す。

- **目的**：URI をパスセグメントに埋め込むと二重のパーセントエンコードが必要になり、長さも最大 2048 文字に及ぶ。
- **担保手段**：TypeSpec の宣言。
- **適用状況**：SAML サービスプロバイダー（`entity_id`）と WS-Federation の証明書利用者（`wtrealm`）がこの形式をとる。

## ステータスコード

### ステータスコードの宣言

API 操作は、そのハンドラーと、手前に位置するガードが返すステータスコードをすべて TypeSpec に宣言する。
[HTTP ボディの宣言](#http-ボディの宣言)がボディに課す「サーバーが実際に返すものだけを宣言する」というルールを、ステータスラインにも適用する。

- **目的**：宣言にないステータスコードが返ると、クライアントは分岐を実装できない。宣言にあって返らないステータスコードは、到達しない分岐をクライアントに実装させる。
- **担保手段**：`mise run check-status-drift`。この検査は、エラー値からレスポンスを決定するヘルパー（`WriteAccountError` など）を追跡しない。どの分岐に入るかはユースケースが返すエラーで決まり、ハンドラーの記述には現れないためである。追跡できなかった API 操作は合格とせず、部分解析として件数を毎回出力する。
- **適用状況**：[一意性違反と状態の競合](#一意性違反と状態の競合)に記載した 409 の宣言漏れがある。これは検査の部分解析の範囲に含まれる。

次の 3 つは、API 操作のレスポンスではないため宣言しない。
ミドルウェアが返す 2 つは、TypeSpec ではなくこの文書に記載する。

| 宣言しないステータスコード | 返却箇所 | 宣言しない理由 |
| --- | --- | --- |
| ハンドラーがマッピングしなかったエラーに対する 500 | 共通のエラーハンドラー | 全 API 操作で同一に発生し、クライアントが API 操作ごとに対応を変える余地もない。ただし、ハンドラーが固有のエラーコードを付けて返す 5xx（パスキーの依存先が利用できないときの 503 `webauthn_unavailable` など）は、その API 操作固有の結果として宣言する |
| ホスト名から解決できないテナントへの 404 `{"error": "tenant_not_found"}` | テナント解決ミドルウェア。ルーティングの前に返す | API 操作ごとに宣言すると、その API 操作固有の 404（リソースが存在しない）と同じ行に 2 つの意味が重なり、クライアントはレスポンスボディを見て判別することになる。経路にかかわらず 404 と `tenant_not_found` を返す |
| 過負荷時の 503 `urn:idmagic:error:service_overloaded` | アドミッションコントロールミドルウェア。ルーティングの後、ハンドラーの前に返す | どの API 操作でも「キャパシティ不足のため受け付けなかった」という単一の意味を持ち、クライアントの対応も `Retry-After` の秒数だけ待機して再送することに限られる。拒否する経路と順序は[キャパシティ設計](../performance/capacity.md#ロードシェディング順序)、機構は [System Context の内部設計](../../domain/system/internals.md#admission-control)が定める |

### 400 と 422 の区別

400 は、リクエストを解析できないこと（不正な JSON、必須構造の欠落）を表す。
422 は、解析したリクエストの内容が業務ルールに違反すること（不正なロール、参照の不整合、ポリシー違反、文字列長の上限違反）を表す。

- **目的**：クライアントが、送信形式の誤りと内容の誤りを区別して処理できるようにする。
- **担保手段**：なし。
- **適用状況**：全面適用。

### 一意性違反と状態の競合

一意性の違反（名前の重複）と状態の競合（他のリソースから参照されている、現在の状態では操作を実行できない）は 409 で返す。

- **目的**：競合を、内容の誤りと区別して処理できるようにする。
- **担保手段**：なし。
- **適用状況**：未適用。ハンドラーは利用者名、グループ名、エージェント名、トラストバンドルの名前と発行者、ライフサイクルワークフローの名前の重複に 409 を返すが、利用者、グループ、エージェント、トラストバンドルの作成と更新、およびライフサイクルワークフローの作成は、TypeSpec に 409 を宣言していない。

### 401 と 403

403 を宣言する API 操作は、401 も宣言する。
認証済みの主体を確定できない場合は 401 とし、クレデンシャルがなければ `authentication_required`、提示されたアクセストークンを検証できなければ `invalid_token` を返す。
主体を確定できても権限が不足する場合は、403 の `access_denied` または `insufficient_scope` を返す。

401 のレスポンスボディは、API 区分ごとの共有モデルを参照する。
汎用 API は `IdMagic.Contract.AuthenticationRequiredResponse`（`AuthenticationRequiredError` と `InvalidAccessTokenError` の union）、OAuth 2.0 と OIDC は `IdMagic.Contract.OAuthUnauthorizedResponse`、SCIM は `IdMagic.Contract.ScimUnauthorizedResponse` を参照する。
403 は、レスポンスボディが API 操作ごとに異なる（`AccessDeniedError`、`InsufficientScopeError`、`MfaEnrollmentNotAllowedError`）ため、API 操作ごとにモデルを定義する。

- **目的**：401 と 403 の一方だけを宣言すると、クライアントは認証の失敗を権限の不足として扱い、クレデンシャルを再取得すれば成功するリクエストを断念する。401 のレスポンスボディを API 操作ごとに記述すると、記述間に不整合が生じる。
- **担保手段**：TypeSpec の参照。
- **適用状況**：全面適用。

## エラーレスポンス

### エラーレスポンスの形式

汎用 API のエラーは、RFC 9457 Problem Details（`application/problem+json`、`type`、`title`、`status`、`detail`、`instance`）で返す。
`instance` には、リクエストの相関に用いる `request_id` を格納する。
個々のエラーは `model <Name>Error is ProblemDetails;` と宣言し、対応する `type` URN の接尾辞（サーバーが返すエラーコード）を `@doc` に記載する。

- **目的**：クライアントが単一のエラー形式のみを処理すればよいようにする。エラーコードから TypeSpec のモデルを特定できるようにする。
- **担保手段**：TypeSpec の `IdMagic.Contract.ProblemDetails` と Go の `support_http.WriteProblem`。
- **適用状況**：下記の標準準拠の例外と独自形式の 2 つを除き、全面適用。

### 標準準拠の例外

プロトコルエンドポイントは各標準が定めるエラー形式で返し、Problem Details を適用しない。
OAuth 2.0 と OIDC、Dynamic Client Registration（RFC 7591）は `IdMagic.Contract.OAuthError`（`error`、`error_description`、RFC 6749 §5.2）を、SCIM は `IdMagic.Contract.ScimProtocolError`（RFC 7644 §3.12）を参照する。
例外の境界は Go のパッケージ単位ではなく API 操作単位で定める。
同一パッケージ内でも、ブラウザーや管理コンソールが呼び出す API 操作は Problem Details を返す。

- **目的**：標準準拠のクライアントとの相互運用性を確保する。パッケージの配置によってエラー形式が決まらないようにする。
- **担保手段**：TypeSpec の参照。
- **適用状況**：全面適用。

### 独自形式のエラー

Problem Details と標準のいずれにも該当しない独自形式は、次の 2 つに限定し、レスポンスボディを TypeSpec に直接宣言する。

- `EndpointRateLimitPolicy` の 429。`error`、`retry_after_seconds`、`message` と `Retry-After` ヘッダーを返す。
- Shared Signals の受信エンドポイント（RFC 8935、`/ssf/streams/{stream_id}/events`）の拒否。`error`、`message` を返す。

同一のエラーコードを API 区分によって異なる形式で返す場合は、`AccessDeniedError` と `OAuthAccessDeniedError` のように区分ごとにモデルを分ける。
一つのモデルに 2 つの形式を定義しない。

- **目的**：クライアントが処理するエラー形式の増加を防ぐ。モデルからレスポンスボディの形式を一意に特定できるようにする。
- **担保手段**：TypeSpec の宣言。
- **適用状況**：全面適用。

### エラーメッセージの言語

エラーレスポンスの文字列（`message`、`error_description`、`detail`、プレーンテキストのボディ）は、`DisplayLanguage` にかかわらず英語に固定する。
`Accept-Language` による切り替えも行わない。
翻訳は、安定したエラーコードをキーとして UI が行う。
Problem Details では、`type` の `urn:idmagic:error:` に続く部分がキーである。
辞書にないエラーコードを受け取った UI は、`detail` または `title` を英語のまま表示する。

- **目的**：同一の障害がクライアントの設定によって異なる文字列になると、ログの突合と相互運用性が損なわれる。サーバーの文言を変更せずに UI の対応言語を追加できるようにする。
- **担保手段**：なし。
- **適用状況**：全面適用。

## コレクション操作

### ページング方式

件数がテナントの規模または時間の経過に応じて増加するコレクションは、キーセット方式のカーソルでページングする。
オフセット方式は採用しない。
件数が運用者の操作によってのみ増加する設定のコレクション（アイデンティティプロバイダー、署名鍵、MCP リソースサーバーなど）は、ページングしない。
直近の履歴を示すコレクション（サインイン履歴）は、最新の固定件数のみを返してよい。

- **目的**：ページが深くなってもクエリのコストを一定に保つ。ページ送りの間に行が増減しても、行の欠落や重複を生じさせない。
- **担保手段**：Go の `support_http.ParsePageRequest`。
- **適用状況**：未適用。`/api/admin/v1/tenants` と `/api/admin/v1/users/{user_id}/groups` はページングせず全件を返す。`/api/admin/v1/authorization/relation-tuples` は `limit` のみを受け付け、先頭から指定件数で打ち切る。

### カーソル

カーソルは署名とバージョンを持ち、テナント、クエリと並び順の同一性、方向、行の境界を束縛する。
束縛条件に一致しないカーソルは 400 で拒否する。

- **目的**：カーソルを他のテナントや条件変更後のクエリに流用させない。
- **担保手段**：Go の `support_http.CursorCodec`。
- **適用状況**：未適用。Jobs のコレクション（`/api/admin/v1/jobs`、`/api/admin/v1/system/jobs`）は独自のカーソルを用いる。

### ページングのレスポンスヘッダー

次ページと前ページは、RFC 8288 の `Link` レスポンスヘッダー（`rel="next"`、`rel="prev"`）で返す。
リンクは現在のクエリパラメーターを保持し、カーソルのみを置き換える。
総件数を返すコレクションは、`rel="first"` と `rel="last"` に加えて、`Pagination-Total-Items`、`Pagination-Total-Pages`、`Pagination-Current-Page`、`Pagination-Page-Size` ヘッダーを返す。
これらのレスポンスヘッダーは TypeSpec に宣言する。

- **目的**：クライアントが URL を再構成せずにページを送れるようにする。レスポンスボディの構造を変えずにページング情報を追加できるようにする。
- **担保手段**：Go の `support_http.SetPageLinks` と `SetPaginationLinks`。
- **適用状況**：未適用。TypeSpec はいずれのコレクションにも `Link` と `Pagination-*` ヘッダーを宣言していない。Jobs のコレクションは、次ページをレスポンスボディの `next_cursor` で返す。

### ページサイズ

`limit` は正の整数で受け付ける。
省略時はデフォルト値を用い、最大値を超える値は最大値に丸める。
デフォルト値は 50、最大値は 200 とする。
例外は、監査イベント（デフォルト値 100、最大値 999）、インポートの行エラー（デフォルト値 100、最大値 200）、サインイン履歴（デフォルト値 10、最大値 50）である。

- **目的**：過大な `limit` をエラーとせず、レスポンスのサイズのみを抑制する。
- **担保手段**：Go の `support_http.ParseLimit`。
- **適用状況**：全面適用。

### フィルタリング

フィルタリングは、API 操作ごとに名前を定めたクエリパラメーターで受け付ける（`status`、`kind`、`lane`）。
自由記述の検索は `q` または `query` で受け付ける。
汎用のフィルター言語は採用しない。
SCIM の `filter` は、RFC 7644 の文法を許可リストの範囲で受け付ける。
クエリパラメーターは TypeSpec に個別に宣言する。

- **目的**：受け付ける条件を API 契約に列挙し、インデックスのない条件をクライアントに組み立てさせない。
- **担保手段**：TypeSpec のクエリパラメーター。
- **適用状況**：未適用。監査イベントのコレクションとエクスポートは、条件を `query` という単一のオブジェクト型パラメーターとして宣言しており、サーバーが読み取る個々のクエリパラメーター（`type`、`category`、`user_id`、`after`、`before`、`q` など）と一致しない。

### ソート

並び順はコレクションごとに固定し、ソート条件を指定するパラメーターは採用しない。

- **目的**：キーセット方式のカーソルは並び順ごとにインデックスを必要とするため、任意の並び順を受け付けるとインデックスが並び順の数だけ必要になる。
- **担保手段**：なし。
- **適用状況**：全面適用。

### 部分レスポンス

レスポンスのプロパティを選択するパラメーター（`fields`）は採用しない。

- **目的**：API 操作ごとのレスポンスの構造を一つに保ち、API 契約の検査を単純に保つ。
- **担保手段**：なし。
- **適用状況**：全面適用。

## 冪等性と再試行

### 冪等キー

管理 API の次の `POST` は、任意指定の `Idempotency-Key` リクエストヘッダーを受け付ける。

- リソースの作成
- 長時間実行操作の開始
- クレデンシャルを発行するカスタムメソッド（クライアントシークレットのローテーションなど）

冪等キーはクライアントが生成する一意な文字列（UUID を推奨する）とする。
サーバーは、テナント、主体、冪等キーの組に対して、リクエストのフィンガープリントとレスポンスを 24 時間保存する。
同一の冪等キーで同一のリクエストを再送した場合は、保存したレスポンスを再生して返す。
同一の冪等キーで異なるリクエストを送信した場合は 422、先行するリクエストが処理中の場合は 409 を返す。
冪等キーを指定しないリクエストは、従来どおり処理する。
平文のシークレットを含むレスポンスは、[データベース設計](../data/database.md#可逆な秘密情報のエンベロープ暗号)の可逆な秘密情報と同じエンベロープ暗号で保存する。

- **目的**：ネットワークのタイムアウトが発生すると、クライアントは最初のリクエストが処理されたかを判別できない。冪等キーがなければ、再送によって API トークン、OAuth クライアント、クライアントシークレットが二重に作成される。IdP において、重複したクレデンシャルは管理されないまま有効であり続け、攻撃対象領域を拡大する。一意制約は自然キーを持つリソースにしか効かず、しかも再送が 409 を受け取ったクライアントは、自身の最初のリクエストが成功したのか、他者が先に作成したのかを判別できない。保存期間を 24 時間とするのは、クライアントの再試行が完了するのに十分であり、保存量を抑えられるためである。ヘッダーの意味は IETF の `draft-ietf-httpapi-idempotency-key-header` に従う。
- **担保手段**：なし。
- **適用状況**：未適用。汎用 API は `Idempotency-Key` を受け付けない。

### 自然キーによる重複の拒否

自然キーを持つリソースの作成は、一意制約によって重複を 409 で拒否する（利用者名、グループ名、エージェント名、ライフサイクルワークフローの名前、トラストバンドルの名前と発行者、MCP リソースサーバーのリソース識別子）。

- **目的**：冪等キーを指定しないクライアントの再送でも、自然キーの重複を防ぐ。
- **担保手段**：PostgreSQL の一意制約。
- **適用状況**：全面適用。409 の宣言漏れは[一意性違反と状態の競合](#一意性違反と状態の競合)に記載した。

### 非同期処理の冪等性

内部の非同期処理は、冪等キーによって同一の作用を二重に実行しない（Jobs の `dedup_key`、プロビジョニング配信の `(tenant_id, connection_id, source_type, source_id, source_version)`）。

- **目的**：At-least-once 配送のもとで、作用が一度だけ観測されるようにする。
- **担保手段**：PostgreSQL の一意制約。
- **適用状況**：全面適用。

### 再試行の指示

再試行までの待機時間は、`Retry-After` ヘッダーで秒数として返す。
レートリミットの 429 とアドミッションコントロールの 503 がこれを返す。
同時実行ジョブの上限を超えたエクスポートの 429（`active_job_quota_exceeded`）は、待機時間を算出できないため `Retry-After` を返さない。

- **目的**：クライアントに待機時間を推測させない。
- **担保手段**：Go の `support_http.WriteRateLimited` とアドミッションコントロールミドルウェア。
- **適用状況**：全面適用。

## 条件付きリクエスト

### ETag と If-Match による競合検出

管理 API の単一リソースに対する `GET` は、リソースのバージョンから算出した強い `ETag` を返す。
同じリソースに対する `PUT`、`PATCH`、`DELETE` は `If-Match` を受け付け、一致しなければ 412 を返す。
`If-Match` を省略したリクエストは無条件に処理する。
管理コンソールは、取得した `ETag` を常に `If-Match` で送信する。

- **目的**：複数の管理者が同一のリソースを同時に編集すると、後の書き込みが先の書き込みを通知なく上書きする（更新の消失）。ブランディング、属性スキーマ、サインインポリシーのように `PUT` で全体を置換する設定では、一方の管理者のセキュリティ設定の変更が気付かれないまま失われる。`PATCH` は送信したプロパティのみを変更するが、同一プロパティの競合は防げない。HTTP 標準（RFC 9110 §13）の仕組みを用いることで、バージョンのプロパティがない単一リソースにも同じ方式を適用でき、HTTP クライアントとライブラリの既存の支援も利用できる。`If-Match` を必須（428）としないのは、既存の自動化クライアントを壊さないためである。
- **担保手段**：なし。
- **適用状況**：未適用。汎用 API の更新は `If-Match` を受け付けない。

### ドメインのリビジョン

ライフサイクルワークフローの `expected_revision` は、条件付きリクエストとは別に維持する。
リビジョンは、どのリビジョンを有効化するかを他の API 操作から指定するドメインの概念であり、競合検出のためだけの値ではない。

- **目的**：ドメインのリビジョンと HTTP の競合検出を、それぞれの役割で使い分ける。
- **担保手段**：Go のユースケースが不一致を 409 `workflow_revision_conflict` で拒否する。
- **適用状況**：全面適用。

### キャッシュ検証

公開のブランディング（`GET /api/branding`）は、バージョンを `ETag` として返し、`If-None-Match` が一致すれば 304 を返す。

- **目的**：サインイン画面の表示のたびに同一のレスポンスボディを転送しない。
- **担保手段**：Go の `branding_handler.go`。
- **適用状況**：全面適用。

### SCIM のバージョン

SCIM のバージョン管理は RFC 7644 に従い、この文書のルールを適用しない。

- **目的**：標準準拠のクライアントとの相互運用性を確保する。
- **担保手段**：Sourcing Context の `standards.md`。
- **適用状況**：SCIM の `ServiceProviderConfig` は `etag.supported` を `false` として公開しており、SCIM のリソースは `ETag` を返さない。

## 長時間実行操作

### 開始と進捗の取得

1 回のリクエストで完了しない操作は、`POST` に 202 を返し、レスポンスボディにその操作のリソースを格納する。
リソースは `id` と `status` を持つ。
進捗と結果は、そのリソースへの `GET` で取得する。
202 のレスポンスは `Location` と `Retry-After` を返さない。

- **目的**：待機方法を API 操作ごとに独自に設計させない。接続を保持したまま待機させることで、タイムアウトとアドミッションコントロールの枠を長時間占有させない。
- **担保手段**：TypeSpec の 202 のモデル。
- **適用状況**：全面適用。CSV のエクスポート（`DataExportJob`）とインポート（`UserImportJobRef` など）が該当する。

### 取り消し

長時間実行操作の取り消しは、リソース配下の `POST .../cancel` で受け付ける。

- **目的**：取り消しを状態遷移として扱えるようにする。
- **担保手段**：TypeSpec の宣言。
- **適用状況**：エクスポートは専用の取り消しを持つ。インポートは専用の取り消しを持たず、リソースの `id` が Jobs のジョブ ID であるため、`POST /api/admin/v1/jobs/{job_id}/cancel` で取り消す。

### 操作リソースの形式

Google AIP-151 の `Operation` のような汎用の操作リソースは採用せず、操作ごとのリソースを公開する。
Jobs のコレクション（`/api/admin/v1/jobs`）は非同期処理の運用監視に用い、個々の操作の結果を返すリソースとしては扱わない。

- **目的**：結果の構造（エクスポートならファイル、インポートなら行ごとのエラー）は操作ごとに異なり、汎用のリソースに格納すると結果の型が `unknown` になる。操作の結果の構造を Jobs の汎用の構造に依存させない。
- **担保手段**：なし。
- **適用状況**：全面適用。

### 完了通知

完了を Webhook で通知する方式は採用しない。
結果はリソースへの `GET` で取得する。
外部へのイベント送信は Shared Signals が担う。

- **目的**：通知先の登録、再送、署名検証という別系統の API 契約を設けない。
- **担保手段**：なし。
- **適用状況**：全面適用。

## カスタムメソッド

### 動詞セグメント

CRUD で表現できない操作は、対象リソースの配下に動詞のパスセグメントを置き、`POST` で呼び出す（`/users/{user_id}/disable`、`/keys/rotate`、`/jobs/{job_id}/cancel`）。

- **目的**：操作の対象と段階の順序をパスから読み取れるようにする。状態遷移を、状態プロパティへの `PATCH` として偽装しない。

## 上限とレートリミット

### リクエストボディのサイズ

すべてのリクエストボディは `HTTP_MAX_BODY_BYTES`（デフォルト値 1 MiB）を上限とし、汎用 API の JSON のリクエストボディはさらに 64 KiB を上限とする。
ロードバランサーまたはリバースプロキシにもデプロイメント環境に応じた粗い上限を設けるが、アプリケーションの上限の代替にはしない。
前段は帯域と接続を入口で保護し、アプリケーションは直接接続や前段の設定差異にかかわらず API 種別ごとの契約を保証する。

- **目的**：単一のリクエストがデコードのためにメモリを枯渇させないようにする。
- **担保手段**：Echo の `BodyLimit` ミドルウェアと Go の `support_http.DecodeJSON`。
- **適用状況**：全面適用。

### 配列の要素数

複数件の要素を配列で受け付けるリクエストボディは、TypeSpec の `@maxItems` で要素数の上限を宣言する。

- **目的**：クライアントが 1 回に送信できる件数を API 契約から読み取れるようにする。
- **担保手段**：TypeSpec の `@maxItems`。
- **適用状況**：未適用。`WriteRelationTuples` の `writes`、`deletes`、`delete_objects` は要素数の上限を宣言しておらず、リクエストボディの 64 KiB の上限のみが件数を制約する。

### CSV の一括転送

CSV の一括転送は、1 ファイルあたり 100,000 行、64 MiB、1 フィールドあたり 64 KiB を上限とする。

- **目的**：単一の転送がジョブの実行時間とストレージを占有しないようにする。
- **担保手段**：Go の `CSVTransferPolicy`。
- **適用状況**：全面適用。

### レートリミットの適用範囲

レートリミットは、認証とトークン発行の経路に `EndpointRateLimitPolicy` として適用し、超過を 429 と `Retry-After` で通知する。
対象は、ログイン、トークン、PAR、デバイス認可、バックチャネル認証である。

- **目的**：クレデンシャルの総当たり攻撃と、トークン発行の濫用を抑止する。
- **担保手段**：Go の `support_http.CheckRateLimit`。
- **適用状況**：全面適用。管理 API とアカウント API には API トークン単位のレートリミットがなく、アドミッションコントロールのみが流入を制限する。

### レートリミットの残量ヘッダー

レートリミットの残量を示すヘッダー（`RateLimit`、`RateLimit-Policy`、`X-RateLimit-*`）は返さない。

- **目的**：レートリミットの対象である認証とトークン発行の経路では、制限を受ける相手は攻撃者でもある。残量を返すと、制限に達しない送信間隔を攻撃者に教えることになる。`RateLimit` ヘッダーは IETF で Internet-Draft（`draft-ietf-httpapi-ratelimit-headers`）の段階にあり、標準として確定していない。管理 API には通知すべき API トークン単位のレートリミットが存在しない。
- **担保手段**：なし。
- **適用状況**：全面適用。

## 文字列長の上限

文字列フィールドの長さの上限は、API 契約、Go の検証、PostgreSQL の制約、UI の入力欄という 4 つの箇所に同じ値で現れる。
値が同じでも計数単位が異なれば別の上限になるため、計数単位を先に固定する。

### 計数単位

文字列長は Unicode のコードポイント数で数える。
TypeSpec の `@maxLength`、OpenAPI の `maxLength`、PostgreSQL の `char_length()`、Go の `utf8.RuneCountInString` は、いずれもコードポイント数を数える。
zog の `String().Max(n)` は UTF-8 のバイト数を数えるため文字列フィールドには用いず、`backend/shared/spec` の `Chars` と `CharsAtMost` を用いる。

例外は次の 2 つである。

1. 準拠する標準がオクテット数で上限を定める値。メールアドレスは RFC 5321 の 254 オクテット、realm は DNS ラベルの 63 オクテットである。いずれも ASCII に限定されるため、実際の値ではコードポイント数と一致する。
2. 上限が保護するリソース自体がバイト数で計測される値。[インデックスキーの構成列](#インデックスキーの構成列)が該当する。

- **目的**：バイト数で数えると、上限 100 の名前が英字なら 100 文字、日本語なら 33 文字になり、API 契約に記載した値が意味を失う。
- **担保手段**：Go の `spec.Chars`。
- **適用状況**：全面適用。

### 上限値の区分

上限値は、次のデフォルトの区分から選択する。
外部の標準も固定の表示領域も関与しない値のために、新たな上限値を導入しない。

| 区分 | 上限 | 適用対象 |
| --- | --- | --- |
| Handle | 64 | IdMagic が採番する Aggregate の ID、および関係名や型名のような語彙的な名前 |
| Name | 100 | 一行の名前 |
| DisplayName | 200 | 利用者に表示する表示名とメールの件名 |
| ExternalID | 256 | クライアントのリソース空間に由来する識別子 |
| Description | 500 | 数文の説明、パターン、表示テンプレート |
| URI | 2048 | URL と URI |
| Expression | 4096 | CEL などの式 |
| PlainBody | 8000 | プレーンテキストの本文 |
| RichBody | 20000 | HTML の本文 |

外部の標準または固定の表示領域によって上限が定まる値は、区分の対象外とする。

| フィールド | 上限 | 根拠 |
| --- | --- | --- |
| メールアドレス | 254 | RFC 5321 が定めるパスの上限 |
| `Tenant.realm` | 63 | DNS ラベル |
| `WorkloadTrustBundle.trust_domain` | 255 | DNS 名 |
| `client_id` | 128 | UUID を格納したうえで、他の認可サーバーから移行した値も受け入れられる長さ |
| パスワード | 128 | `PasswordPolicy` のデフォルトの上限 |
| ブランディングの短いラベル | 80 | サインイン画面とメールの固定枠に収まる長さ |
| ブランディングの補足テキスト | 280 | サインイン画面とメールの固定枠に収まる長さ |

- **目的**：値ごとに上限値が増えると、どの値が妥当かを判断できなくなる。
- **担保手段**：なし。
- **適用状況**：全面適用。

### インデックスキーの構成列

外部の連携先が値を決める識別子にも上限を設ける。
上限を設けないことは、実質的に上限を PostgreSQL の B-tree に委ねることを意味する。
B-tree（バージョン 4）はインデックスタプル 1 件を 2704 バイトに制限するため、主キーや一意インデックスのキーを構成する列は、宣言の有無にかかわらずその値で頭打ちになる。
上限を宣言しなければ、超過は書き込み時に `SQLSTATE 54000` として発生し、どのフィールドをどこまで短縮すればよいかを利用者に通知できない。
インデックスタプルは値の圧縮を試みるため、境界の位置は値の内容によっても変動する。

そこで、インデックスキーの構成列には、性質の異なる 2 つの上限を併せて課す。

| 上限 | 計数単位 | 役割 |
| --- | --- | --- |
| 契約上限 | コードポイント | API 契約に記載する値。TypeSpec の `@maxLength` と Go の `spec.Chars` が保持する |
| リソース上限 | バイト | インデックスタプルに収まることの保証。Go の `spec.KeyString` と PostgreSQL の `octet_length` が保持する |

契約上限をコードポイント数で設けるだけでは不十分である。
標準が 1024 文字と定める識別子でも、すべて 3 バイト文字であれば 3072 バイトになり、API 契約を満たしたまま B-tree の上限を超える。

複合キーでは、列単位ではなくキー 1 件の合計がインデックスタプルに収まる必要がある。
キーごとにバイト数の予算を定め、その合計を 2400 バイト以下とする。
B-tree の 2704 バイトとの差は、インデックスタプル自体が使用する領域と、将来の列追加のための余裕である。
この条件は `backend/shared/spec` のテストが検証し、上限を後から拡大して予算を超過した時点で検出する。

上限には標準が定める値をそのまま用いない。
標準を超える値を送る実装も存在しうるため、標準の値は「上限が実運用で制約とならない根拠」として記録し、上限自体はその外側に設ける。
これらは安全のために設けるリソースの境界であり、業務上望ましい長さではない。

| 列 | コードポイント | バイト | 根拠 |
| --- | --- | --- | --- |
| `SamlServiceProvider.entity_id` | 2048 | 2048 | URI 区分。`saml-schema-metadata-2.0.xsd` の `entityIDType` は 1024 文字を定めるが、非準拠の SP を拒否しないためその外側に設ける |
| SAML AuthnRequest の `ID` | 256 | 256 | リソース上限。`xs:ID` に長さの規定はない |
| `WsFedRelyingParty.wtrealm` | 2048 | 2048 | URI 区分。WS-Federation は `wtrealm` を URI としか定めない |
| 外部 IdP の subject | 512 | 1024 | リソース上限。OpenID Connect Core 1.0 §2 は `sub` を 255 ASCII 文字以下と定めるが、SAML の NameID には規定がない |
| 外部 IdP の SAML `Response` の `ID` | 256 | 256 | リソース上限 |
| DPoP proof と client assertion の `jti` | 256 | 256 | リソース上限。RFC 7519 に長さの規定はない |
| WebAuthn の credential ID | 2048 | 2048 | リソース上限。WebAuthn は 1023 バイト以下と定めるため、base64url で 1364 文字になる |

IdMagic が採番するインデックスキーの構成列にも上限を設けるが、設ける箇所が異なる。
SCIM の `id`（RFC 7643 がサービスプロバイダーによる割り当てと定める値）、署名鍵の `kid`（RFC 7638 の JWK Thumbprint）、発行したトークンの `jti` は、いずれも Handle 区分の 64 とする。
実際の値はそれぞれ 16 進数 32 桁、base64url 43 文字、UUID であり、ASCII のみで構成されるため、契約上限とリソース上限が同じ値になる。
これらには Go の検証を設けず、`CHECK` 制約のみを設ける。
拒否すべき外部入力が存在しないためである。
上限を超えるのは採番の実装に不具合がある場合に限られ、利用者の誤りではないため、422 を返さない。

インデックスキーを構成しない外部由来の値にも上限を設ける。
B-tree の制約は受けないが、保存量を無制限にしてよい理由にはならない。
`tls_client_auth_subject_dn` は URI 区分の 2048 とする。
連携先の同期を隔離した理由を記録する文字列は Description 区分の 500 とし、利用者の入力ではなく連携先が返したエラーメッセージであるため、拒否せずに書き込み時に切り詰める。
長いエラーメッセージのために隔離自体が失敗するほうが、損失が大きいためである。
外部入力を経由しない固定長のダイジェスト（各種トークンのハッシュ）には上限を設けない。

- **目的**：インデックスタプルの上限超過を、原因の分からない書き込みエラーではなく、フィールドと上限を示す検証エラーとして通知する。
- **担保手段**：Go の `spec.KeyString`、PostgreSQL の `CHECK (char_length(col) <= N AND octet_length(col) <= M)`、`backend/shared/spec` のテスト。
- **適用状況**：全面適用。

### 各箇所の役割

4 つの箇所は同じ上限値を持つが、役割は異なる。

| 箇所 | 役割 |
| --- | --- |
| TypeSpec の `@maxLength` | API 契約。OpenAPI と生成ドキュメントが示す値の出典 |
| Go の domain のスキーマ | 唯一の検証箇所。これを経由しない書き込み経路を設けない |
| PostgreSQL の `CHECK (char_length(col) <= N)` | 最終防衛線。ここで失敗するのは実装の不具合であり、利用者向けエラーの発生源としない。インデックスキーの構成列では、`octet_length(col) <= M` を同じ `CHECK` 制約に併記する |
| UI の `maxLength` 属性 | 入力の補助。保証ではない |

UI のみ計数単位が異なる。
HTML の `maxLength` は UTF-16 のコードユニット数を数えるため、基本多言語面の外にある絵文字などは 1 文字を 2 と数える。
UTF-16 のコードユニット数はコードポイント数を下回らないため、差異は常に厳しい側に生じる。
入力欄が受け付けた値をサーバーが長さを理由に拒否することはなく、絵文字のみの入力では上限に達する前に入力欄が入力を止める。
この差異は許容する。
ブラウザーの `maxLength` にコードポイント数を数えさせる方法はなく、独自に数え直して入力値を書き換えると、IME による変換や取り消し操作を妨げるためである。

- **目的**：利用者向けのエラーを Go の検証に一元化し、PostgreSQL の制約を実装の不具合の検出に限定する。
- **担保手段**：Go の domain のスキーマ。
- **適用状況**：全面適用。

### 上限違反のエラー

上限違反は、解析したリクエストの内容が業務ルールに違反する場合に該当するため、422 で返し、違反したフィールドと上限を `detail` に記載する。
SAML、WS-Federation、OAuth 2.0、SCIM、WebAuthn のように、相手方のプロトコルがレスポンスの形式を定める API 区分では、長さの違反もそのプロトコルのエラーとして返す。
AuthnRequest を送信した相手に Problem Details を返しても解釈されない。
リソース上限は書き込み経路にのみ課す。
インデックスキーの構成列を検索条件として受け取る経路（`GET /Users/{id}` など）は、上限を超える値を 422 ではなく、通常の「存在しない」として扱う。
検索はインデックスタプルを生成しないため、長い値を拒否する理由がない。

- **目的**：利用者が、どのフィールドをどこまで短縮すればよいかを判断できるようにする。
- **担保手段**：Go の domain。
- **適用状況**：全面適用。

### CHECK 制約の範囲

`CHECK` 制約に設けるのは、長さのように安定した構造上の境界に限る。
スキームの許可リストのような、変更されうる入力ルールを DDL に含めない。
たとえば、テナントのフッターリンクに `https` のみを許可するルールは Go の domain が保持し、`CHECK` 制約は長さのみを検証する。

- **目的**：入力ルールを DDL に含めると、ルールの変更のたびにすべてのデプロイ先でスキーマの移行が必要になる。利用者の入力誤りで失敗するルールをこの層に置くと、「実装の不具合のみが失敗する箇所」という役割が崩れる。
- **担保手段**：なし。
- **適用状況**：全面適用。

## セキュリティレスポンスヘッダー

### 共通のセキュリティヘッダー

境界ミドルウェアは、すべてのバックエンドのレスポンスに `X-Content-Type-Options: nosniff`、`Referrer-Policy: no-referrer`、`X-Frame-Options: DENY`、厳格な `Content-Security-Policy`（`default-src 'none'; base-uri 'none'; frame-ancestors 'none'; form-action 'self'`）を付与する。

- **目的**：`frame-ancestors 'none'` と `X-Frame-Options: DENY` によって、ログイン、同意、ポータルの画面の埋め込みとクリックジャッキングを防ぐ。認可コードやトークンを含む URL を、Referer によって外部へ送出しない。
- **担保手段**：Go の `support_http` のセキュリティヘッダーミドルウェア。
- **適用状況**：全面適用。

### インラインスクリプト

CSP では `'unsafe-inline'` を用いない。
IdMagic が出力するインラインスクリプトは、SAML ACS と WS-Federation の POST バインディングで用いる固定の自動送信処理のみであるため、レスポンスごとに `script-src 'sha256-…'` で許可し、`form-action` も送信先エンドポイントに限定する。

- **目的**：注入されたスクリプトによるセッションとトークンの持ち出しを防ぐ。
- **担保手段**：Go の SAML と WS-Federation のレスポンス生成処理。
- **適用状況**：全面適用。

### CSP の設定主体

CSP と `frame-ancestors` は、経路ごとの判断を要するため IdMagic 自身が設定する。
シングルページアプリケーションはゲートウェイが配信し、静的 HTML に `script-src 'self'` を含む CSP を設定する。

- **目的**：最小構成のリバースプロキシの背後でも、リバースプロキシがない場合でも保護を成立させる。
- **担保手段**：Go のミドルウェアとゲートウェイの設定。
- **適用状況**：全面適用。

### HSTS

HSTS は TLS を終端する側が設定する。
`Strict-Transport-Security` はデフォルトで無効とし、TLS がこの区間またはその手前で終端される場合にのみ有効にする（`HSTS_ENABLED`、`HSTS_MAX_AGE_SECONDS`、`HSTS_INCLUDE_SUBDOMAINS`）。

- **目的**：平文の `http` を用いる開発環境に影響させない。
- **担保手段**：起動時設定。
- **適用状況**：デプロイ先の設定に依存する。

### CSP の段階的な強化

画面を壊さずに CSP を強化する場合は、`CSP_REPORT_ONLY=true` で `Content-Security-Policy-Report-Only` を出力し、`CSP_REPORT_URI=<url>` で違反を収集し、影響を確認してから強制モードに戻す。

- **目的**：強制する前に違反を観測する。
- **担保手段**：起動時設定。
- **適用状況**：デプロイ先の設定に依存する。

## インターフェースの安定性とバージョン管理

管理 API とアカウント API は外部契約である。
外部インターフェースは、次の 3 つの安定性区分に分類する。

| 安定性区分 | 意味 |
| --- | --- |
| `stable` | バージョンを持つ外部契約。後方互換性の保証の対象 |
| `beta` | 後方互換性の保証の対象となる前の外部契約 |
| `internal` | 外部契約に含まれない。ファーストパーティーのブラウザーセッションからのみ到達でき、API アクセストークンでは到達できない。予告なく変更する |

### 安定性区分の宣言

各 API 操作の安定性区分は TypeSpec に宣言する。
`/api/admin/v1/` と `/api/account/v1/` は `stable`、`/api/auth/` は `internal` とする。

- **目的**：安定性区分をパスの形式からの推測ではなく、API 契約から確定できるようにする。
- **担保手段**：なし。
- **適用状況**：未適用。TypeSpec は安定性区分を宣言しておらず、パスの形式のみが区分を表す。`beta` の API 操作は存在しない。

### 後方互換性

後方互換な変更は、フィールドの追加、任意パラメーターの追加、エンドポイントの追加である。
破壊的変更は、フィールドの削除または名称変更、フィールドの型の変更、フィールドの必須化、エラーコードの変更、デフォルト値の変更である。

- **目的**：既存のクライアントが、バージョンを更新せずに動作し続けられるようにする。
- **担保手段**：`mise run check-api-compat`。
- **適用状況**：全面適用。

### 未知のプロパティ

クライアントはレスポンスに含まれる未知のプロパティを無視し、サーバーはリクエストに含まれる未知のプロパティを無視する。
既知のプロパティに不正な型または値が指定された場合は拒否する。
プロトコルエンドポイントでは、適用する標準が未知のフィールドの拒否を要求する構造に限り、その標準を優先する。
このデフォルトは汎用 API のエンドポイントごとに切り替えず、厳格さが必要な閉じた構造だけを型固有の検証で例外化する。

- **目的**：フィールドの追加を後方互換な変更として扱い、クライアントとサーバーを独立して更新できるようにする。クエリパラメーターと JSON プロパティで、未知の名前に対するデフォルトの扱いを統一し、クライアントがエンドポイントごとの差異を覚える必要をなくす。
- **担保手段**：Go の `support_http.DecodeJSON`。
- **適用状況**：全面適用。

### URI バージョニング

`stable` と `beta` はパスでバージョンを表す（`/api/admin/v1/...`、`/api/account/v1/...`）。
バージョンのないパスは設けない。
破壊的変更は既存のパスを変更せず、新しいプレフィクスで導入する。
同時に提供するバージョンは最大 2 つとする。
プロトコルエンドポイントにはパスのバージョンを適用しない。
その互換性は各標準が規定し、Discovery Metadata（`/.well-known/...`）、`/scim/v2/ServiceProviderConfig`、SAML と WS-Federation のメタデータが正となる。

- **目的**：クライアントがバージョンを明示的に選択できるようにする。プロトコルエンドポイントにバージョンを重ねると、標準が定める探索経路と食い違う。
- **担保手段**：TypeSpec のルート定義。
- **適用状況**：全面適用。

### API アクセストークンのスコープ宣言

管理 API の各 API 操作は、到達を許可する API アクセストークンのスコープを TypeSpec の `x-api-token-scopes` に宣言する。
トークンでの到達を許可しない API 操作は `interactive_session` を宣言する。
スコープを宣言しない API 操作には、API アクセストークンで到達できない。

- **目的**：対話セッション専用の API 操作に、API アクセストークンで到達させない。
- **担保手段**：Go の `support_http` のスコープ判定と `mise run check-admin-scopes`。
- **適用状況**：全面適用。

## 非推奨化と廃止

### 非推奨の宣言

非推奨の予定は TypeSpec に記録し、文書側には一覧を設けない。
`deprecated_since` を設定したインターフェースは、レスポンスに `Deprecation` ヘッダー（RFC 9745）を付与する。
廃止時期が確定して `sunset_at` を設定した後は、`Sunset` ヘッダー（RFC 8594）も付与する。
`sunset_at` は `deprecated_since` から 12 か月以上後とする。

- **目的**：非推奨の一覧の二重管理による不整合を防ぐ。クライアントが実行時に非推奨を検出できるようにする。クライアントに移行期間を保証する。
- **担保手段**：Go の `support_http.DeprecationHeadersMiddleware`。
- **適用状況**：未適用。ヘッダーを付与するミドルウェアは存在するが、TypeSpec から `deprecated_since` と `sunset_at` を伝達する経路がなく、`RuntimeContract.Deprecations` は常に空である。現在、非推奨の API 操作は存在しない。

### 破壊的変更の検出

破壊的変更は、TypeSpec から生成した OpenAPI と、配布した内容を固定したリリースベースラインとの比較で検出する。
ベースラインはリリース作業の一環としてのみ更新する。

- **目的**：リリースせずにベースラインを更新すると実際の後退を検出できなくなり、リリースしても更新しなければベースラインが陳腐化して同じ結果になる。
- **担保手段**：`mise run check-api-compat`。
- **適用状況**：全面適用。

## HTTP ボディの宣言

### 実際のボディの宣言

TypeSpec が `@body` に宣言する型は、サーバーが実際に受理し返却する JSON と一致させる。
サーバーが送信しないエンベロープを TypeSpec 側で追加しない。
ハンドラーが `map[string]any{"groups": ...}` のようなエンベロープを出力する場合に限り、TypeSpec でもそのエンベロープを宣言する。
パスパラメーターとクエリパラメーターを、リクエストボディのプロパティとして宣言しない。
ボディが JSON でない API 操作（CSV のアップロード、SET の受信、XML のメタデータ、画像の配信、メトリクスの公開）は、そのメディアタイプとボディの型をそのまま宣言する。

- **目的**：生成したクライアントと実際の通信を一致させる。
- **担保手段**：`mise run check-contract-drift`。この検査は Go の変数に保持したレスポンスを型推論しないため、追跡できなかった API 操作を部分解析として件数で出力する。
- **適用状況**：[フィルタリング](#フィルタリング)に記載した監査イベントのクエリパラメーターを除き、全面適用。

### 列挙値と任意の値の宣言

enum の値には、メンバー名の複製ではなく、実際に送受信する値を記述する。
標準が定める値は標準から、IdMagic 独自の値は Go の定数から転記する。
`unknown` は「任意の JSON 値」と解釈されるため、該当する型やモデルがあればそれを記述する。
真に任意の値でよい場合に限り、その理由を `@doc` に記載する。

- **目的**：API 契約上の値と実際の値を一致させる。クライアントに型を推測させない。
- **担保手段**：なし。
- **適用状況**：全面適用。

## 採用しない方式

公開されている API ガイドライン（Zalando RESTful API Guidelines、Microsoft Azure REST API Guidelines、Google AIP）が扱う事項のうち、前節までに記載していないものについて、採否を次のとおり定める。

| 方式 | 決定 | 理由 |
| --- | --- | --- |
| ハイパーメディア（HAL、JSON:API、HATEOAS） | 採用しない | 汎用 API のクライアントは、ファーストパーティーの UI と、TypeSpec から生成したクライアントである。レスポンスボディにリンクを埋め込んでも、それを辿るクライアントが存在しない。ページングのリンクのみ `Link` ヘッダーで返す |
| GraphQL | 採用しない | スコープを API 操作単位で宣言し、ステータスコードの宣言を検査する現在の仕組みが、単一のエンドポイントでは成立しない |
| `X-HTTP-Method-Override` によるメソッドの上書き | 採用しない | 汎用 API のクライアントは、すべての HTTP メソッドを送信できる |
| レスポンスの圧縮と `Accept` によるコンテンツネゴシエーション | この文書では扱わない | 汎用 API のボディは JSON のみであり、圧縮はゲートウェイとリバースプロキシの設定が担う |
