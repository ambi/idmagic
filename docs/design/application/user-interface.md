# ユーザーインターフェース設計

このファイルは、ホステッド認証画面、アカウントポータル、管理コンソール、システムコンソールに共通する利用者向けの規範を持つ。
コードの分け方、データの取得、配信は[フロントエンド設計](frontend.md)が持つ。
画面ごとの URL、表示項目、文言、色や余白の値は実装とローカライズ辞書から導けるため、この文書に一覧として複製しない。
デザイントークンの値とテーマは実装が持つ。

外部から観測できる振る舞い（キーボードだけで認証を完了できること、表示言語の解決順序、既知のエラーコードを翻訳して表示すること）は仕様が持つ。
この文書が持つのは、その振る舞いを崩さずに画面を作るための取り決めである。
UI ライブラリを入れ替えたときに変わるものはこの文書に、変わらないものは仕様に置く。

## 設計の指針

- **信頼できる情報を示す**：落ち着いた配色、サービスの明確な識別、現在の操作とセキュリティ状態の説明によって、利用者が認証してよいかを判断できるようにする。
- **重要な情報を先に示す**：認証と同意の画面では、ページの題名、要求元、共有する情報、次の操作、取り消し方をこの順で示す。
- **主な操作を一つにする**：画面ごとの主な操作を一つに絞り、拒否や取り消しと見た目で区別する。UI の都合で OAuth と OIDC のフォームの名前、送信値、遷移の契約を変えない。
- **業務利用に合う情報密度を保つ**：過剰なアニメーションや装飾を避け、余白、タイポグラフィ、境界線、状態色を揃えて情報を構造化する。
- **情報を失わずにレスポンシブにする**：デスクトップでは補足情報を表示し、モバイルでも、サービスの識別と安全上の警告を省かずに認証操作を優先する。
- **共有部品で揃える**：色、角丸、フォーカスリング、無効状態を画面ごとに実装せず、`frontend/src/components/ui/` の部品を使う。

## 情報構造

画面は、利用者が対象テナント、対象資源、現在の状態、実行できる操作、操作の結果を、この順に識別できる構成にする。
画面の外枠（ヘッダー、サイドバー、パンくずリスト、コンテンツ幅、操作の配置）は、管理コンソールでは `AdminShell`、アカウントポータルでは `AccountShell`、システムコンソールでは `SystemShell`、認証画面では `AuthShell` で揃える。
ブラウザーのタブの題名は、画面の種類から現在地が分かる形（「ユーザー | IdMagic 管理コンソール」）にし、`frontend/src/routes/-page.tsx` の `PAGE_TITLES` が画面の種類ごとに決める。

管理コンソールは、Keycloak、Okta、Google Cloud IAM のようなディレクトリ中心の管理画面を参考にする。
左側のナビゲーションで管理対象を選び、一覧の表で検索、状態、主な権限を示し、同じ文脈で詳細と変更の手段を出す。

- **表を作業の中心にする**：一覧を主な作業場所とし、検索、絞り込み、状態、MFA の設定、ロールを一覧の時点で確認できるようにする。
- **変更の前に確認できるようにする**：変更を確定する前に、詳細の画面でプリンシパル ID、認証の状態、割り当て済みの権限を確認できるようにする。
- **権限を明示的に変更する**：機微なロールの変更ではその場での編集を避け、追加と削除の差分を確定前に示す専用の画面を使う。
- **資格情報を一度だけ表示する**：クライアントシークレットのような資格情報は、作成したときに一度だけ表示する。
- **未実装の機能を操作できるように見せない**：ナビゲーションは将来の機能を収容できる構造にするが、まだない画面への入口は置かない。
- **仕様の語彙を使う**：画面の用語は仕様の語彙に合わせる。たとえば「監査ログ」ではなく「監査イベント」と書く。`AuditEvent` と一致させるためである。

参考にした管理画面：[Keycloak Server Administration Guide](https://www.keycloak.org/docs/latest/server_admin/)、[Okta Manage users](https://help.okta.com/en-us/content/topics/users-groups-profiles/usgp-people.htm)、[Google Cloud IAM access management](https://cloud.google.com/iam/docs/granting-changing-revoking-access)

## ナビゲーション

管理コンソールとアカウントポータルに共通して適用する。

- **詳細を確認してから編集する**：読み取り専用の詳細を先に表示し、明示的な「編集」の操作から専用の編集の経路（`/admin/users/$id/edit`、`/account/profile/edit`）へ移る。
- **主要な資源の作成と編集にモーダルを使わない**：ブラウザーの「戻る」とディープリンクを保つためである。確認ダイアログと、ステップアップ認証のような操作の途中で求める入力はこの対象ではない。
- **一覧の操作を行内に出す**：詳細、編集、削除をケバブメニューへ隠さない。管理作業では、その行に何ができるかが一覧の時点で分かることを、見た目の整理より優先する。

## 表示状態

画面は、次の状態をそれぞれ区別して表示する。
どの状態でも、失敗や権限の不足を成功したように見せない。

| 状態 | 表示 |
| --- | --- |
| 読み込み中 | 画面の遷移中は、遷移先のデータが揃うまで直前の画面を表示し続け、空の画面や骨組みだけの画面を挟まない。画面内の操作の実行中は、その操作のボタンを無効にし、実行中であることを文言で示す |
| 空 | 一覧が空であることと、次に取れる操作（検索語や絞り込みの変更、作成）を文章で示す。空の表だけを表示しない |
| エラー | 画面の中で、失敗した操作の近くに `Alert` で表示し、利用者が閉じるか次の操作をするまで残す。画面そのものを表示できない失敗は、ルーターのエラー画面で表示し、再ログインやポータルへの戻り方を示す |
| 権限なし | サーバーが 403 を返した操作は、権限が足りないことを文言で示し、変更が反映されていない状態の表示を保つ。ステップアップ認証を要求された操作は、再認証のダイアログを表示し、成立した後に元の操作を一度だけ再試行する |
| 部分的な失敗 | CSV の取り込みのように複数の項目を一度に処理する操作は、成功と失敗の件数を示し、失敗した項目を行、列、エラーコードで特定する。パスワードのようなシークレットは、失敗の表示にも含めない |
| 成功 | 画面の配置を押し下げない一時的な通知（`Toast`）で数秒だけ示す。結果として画面に表示する内容が変わる場合は、その変更を画面に反映する |

エラーを一時的な通知で示さないのは、利用者が読む前に消えると、失敗したことを知る手段がなくなるためである。

## 破壊的な操作

削除、無効化、失効、全セッションの取り消しのように、利用者や連携先の動作を止める操作を**破壊的な操作**と呼ぶ。
破壊的な操作は、通常の閲覧用の表示から見た目で分け、ボタンには `variant="destructive"` を使う。

破壊的な操作は、実行する前に確認ダイアログを表示する。
確認ダイアログには、対象の識別名、操作の結果、取り消せるかどうかを含める。
取り消せる操作（削除の予約など）と取り消せない操作（完全削除など）は別の操作として表示し、取り消せない操作では、そのことを警告として文言に含める。
連携先に影響する操作（クライアントの削除など）は、影響する連携先を確認させたうえで実行させる。

確認にはブラウザーの `window.confirm` を使わず、画面の部品として作ったダイアログを使う。
`window.confirm` は、対象と結果を構造立てて示せず、画面の文言と同じ見た目や言語で表示されないためである。
現行では、通知テンプレートの初期化、エンドポイントの形式の変更、ジョブの取り消し、全セッションの取り消しが `window.confirm` を使っている。

## フォームと検証

入力の検証は、送信できるかどうかの判定として画面が行い、受け付けるかどうかの判定はサーバーが行う。
画面が行う検証は、必須項目の未入力や形式の誤りのように入力だけで判定できるものに限る。
そうした不備があるあいだは送信ボタンを無効にし、該当する入力欄に `aria-invalid` を付ける。

サーバーが検証の失敗（422）や競合（409）を返したときは、フォームの近くに `Alert` で表示し、入力した値を消さない。
サーバーが返す `detail` は違反したフィールドと上限を含む英語の文であり、既知のエラーコードでなければそのまま表示する。

入力欄の `maxLength` は、`frontend/src/lib/lengthLimits.ts` の `LENGTH` から値を取る。
これは入力の補助であり、保証ではない。
上限の値と各箇所の役割は [API ガイドライン](api-guidelines.md#各箇所の役割)が持つ。
パスワードの入力欄には `maxLength` を付けない。
パスワード管理ソフトから貼り付けた長い値が黙って切り詰められると、利用者は短くなったことに気付かないまま登録してしまうためである。

## 一覧

ページングする一覧は、ページ送りの操作に `PageNavigation` を使い、先頭、前、次、末尾への移動と、総件数と現在のページを表示する。
移動できない方向のボタンは隠さずに無効にし、操作の位置が画面ごとに変わらないようにする。
ページングの方式とカーソルの意味は [API ガイドライン](api-guidelines.md#ページング方式)が持つ。

絞り込み条件とページの位置は URL の検索パラメーターに持たせ、再読み込みと「戻る」で同じ一覧を表示する。
絞り込み条件を変えたときは先頭のページに戻す。
カーソルが無効になったときは、エラーを表示せずに先頭のページを表示する。
並べ替えと絞り込みはサーバーの問い合わせで行い、画面の中で取得済みの行だけを並べ替えたり絞り込んだりしない。
取得済みの行だけを対象にすると、表示されていないページの行が結果から漏れるためである。

## エラーの文言

サーバーのエラーの文言は英語に固定されている（[API ガイドライン](api-guidelines.md#エラーメッセージの言語)）。
画面は、安定したエラーコードを辞書で引いて表示する文言を決める。
共通のエラーコードの対応は `frontend/src/lib/i18n/errorMessage.ts` が持ち、画面に固有のエラーコードはその画面の辞書が持つ。
辞書にないエラーコードを受け取ったときは、サーバーが返した英語の文言を変えずに表示する。
文言を推測して翻訳すると、サーバーが意図した内容と異なる説明を表示するおそれがあるためである。
レート制限のエラーは、再試行できるまでの秒数を文言に含める。

## 国際化

ホステッド認証画面とアカウント管理の画面が対応する言語は、日本語（`ja`）と英語（`en`）だけである。
製品のデフォルトは英語であり、明示されたロケールもブラウザーのロケールも使えないときの最後のフォールバックは、ビルド時の `VITE_DEFAULT_LOCALE` で選ぶ。
未設定または無効な値のときは英語を使う。
別途仕様として決めない限り、ロケールを追加しない。

利用者に見える文言は、その機能スライスの `*.i18n.ts` の辞書に置き、`ja` と `en` の値を同じ変更で用意する。
辞書は `defineDictionary` で定義し、一方のロケールにだけキーがある状態を型検査で拒否する。

日時と数値は、`frontend/src/lib/i18n/context.tsx` の `useFormatters` が返す `formatDate`、`formatDateTime`、`formatNumber` で、現在のロケールに合わせて表示する。
現行では、多くの画面が `toLocaleString` を直接呼んで日時を整形しており、アカウントポータルのアプリケーション一覧は日本語の形式に固定している。

フロントエンドのテストは英語をデフォルトのロケールとし、通常の振る舞いのテストは英語の文言で検証する。
日本語の表示を確かめるテストは、その目的を名前に含め、`renderWithRouter` に `{ locale: 'ja' }` を渡すなどして明示的にロケールを指定する。
テストの期待値には、翻訳後の文字列を直接書かず、辞書の値を参照する。

## アクセシビリティ

アクセシビリティの規範は、[全体の標準仕様](../../standards.md)の WCAG 2.2 の節が持つ。
画面は、規範の各行を次の手段で満たす。

| 規範 | 実装の手段 |
| --- | --- |
| `WCAG22-KEYBOARD` | 見出し、表、フォーム、ボタン、リンクを、見た目の似た別の要素で代用しない。すべての操作をキーボードだけで実行できるようにし、ドラッグによる並べ替えにはキーボードとスクリーンリーダーの代替操作を用意する |
| `WCAG22-FOCUS` | 基本部品が持つフォーカスリングを消したり上書きしたりしない |
| `WCAG22-LABELS-ERRORS` | 入力欄に `Label` を関連付け、不備のある入力欄に `aria-invalid` を付け、エラーを文章で示す |
| `WCAG22-STATUS` | エラーの `Alert` を `role="alert"`、成功の通知を `role="status"` として、フォーカスを動かさずに支援技術へ伝える |

標準仕様に対応する行はないが、アニメーションは動きを減らす利用者の設定に従い、文字と背景と状態色のコントラストを読める水準に保つ。
