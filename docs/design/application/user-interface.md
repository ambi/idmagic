# ユーザーインターフェース設計

この文書は、IdMagic の Web フロントエンド・アプリケーションが表示する画面について、画面を跨いで揃える表示と操作の規範を定める。
対象の画面は、認証画面、アカウントポータル、管理コンソール、システムコンソールの四種類である（[フロントエンド設計](frontend.md)の冒頭の表を参照）。

この文書と他の文書の分担は次のとおりである。

| 内容 | 記載する場所 |
| --- | --- |
| 画面を跨いで揃える表示と操作の規範 | この文書 |
| SPA のコードの分け方、データの取得、ルーティング、配信 | [フロントエンド設計](frontend.md) |
| 外部から観測できる振る舞い（キーボードだけで認証を完了できること、表示言語の解決順序、既知のエラーコードを翻訳して表示すること） | 各 Context の仕様と[全体の標準仕様](../../standards.md) |
| 画面ごとの URL、表示項目、文言、色や余白の値、デザイントークン | 実装とローカライズ辞書 |

この文書と仕様のどちらに書くかは、UI ライブラリを入れ替えたときに変わるかどうかで判断する。
変わるものはこの文書に、変わらないものは仕様に書く。

## 設計の指針

| 指針 | 内容 |
| --- | --- |
| 信頼できる情報を示す | 落ち着いた配色、サービスの明確な識別、現在の操作とセキュリティ状態の説明によって、利用者が認証してよいかを判断できるようにする |
| 重要な情報を先に示す | 認証画面と同意画面では、ページのタイトル、要求元、共有する情報、次の操作、取り消し方をこの順に示す |
| 主な操作を一つにする | 画面ごとの主な操作を一つに絞り、拒否や取り消しの操作と見た目で区別する。UI の都合で OAuth と OIDC のフォームの名前、送信値、遷移の契約を変えない |
| 業務利用に合う情報密度を保つ | 過剰なアニメーションや装飾を避け、余白、タイポグラフィ、境界線、状態色を揃えて情報を構造化する |
| 情報を欠かさずにレスポンシブにする | デスクトップでは補足情報を表示する。モバイルでも、サービスの識別と安全上の警告を省かずに、認証操作を優先する |
| 共通の部品で揃える | 色、角丸、フォーカスリング、無効状態を画面ごとに実装せず、`frontend/src/components/ui/` の部品を使う |

## 画面の構成

### 情報の順序

画面は、利用者が次の順に情報を識別できるように構成する。

1. 対象のテナント
2. 対象のリソース（ユーザー、グループ、アプリケーションなど）
3. 現在の状態
4. 実行できる操作
5. 操作の結果

### 外枠とタイトル

| 画面 | 外枠の部品 |
| --- | --- |
| 認証画面 | `AuthShell` |
| アカウントポータル | `AccountShell` |
| 管理コンソール | `AdminShell` |
| システムコンソール | `SystemShell` |

- ヘッダー、サイドバー、パンくずリスト、コンテンツの幅、操作の配置は、外枠の部品で揃える。
- ブラウザーのタブのタイトルは、現在地が分かる形（「ユーザー | IdMagic 管理コンソール」）にする。画面の種類ごとのタイトルは `frontend/src/routes/-page.tsx` の `PAGE_TITLES` で定義する。
- 画面の用語は仕様の語彙に合わせる。たとえば「監査ログ」ではなく「監査イベント」と書き、`AuditEvent` と一致させる。

### 管理コンソール

管理コンソールは、Keycloak、Okta、Google Cloud IAM のような、ディレクトリを中心とする管理画面を参考にする。
左側のナビゲーションで管理対象を選び、一覧の表で検索、状態、主な権限を示し、同じ画面の流れの中で詳細と変更の手段を提供する。

| 規範 | 内容 |
| --- | --- |
| 一覧を作業の中心にする | 検索、絞り込み、状態、MFA の設定、ロールを一覧の時点で確認できるようにする |
| 変更の前に確認できるようにする | 変更を確定する前に、詳細画面でユーザーの ID、認証の状態、割り当て済みの権限を確認できるようにする |
| 権限を明示的に変更する | 機微なロールの変更では、一覧の中での直接編集を避ける。専用の画面で、追加と削除の差分を確定前に示す |
| 資格情報は一度だけ表示する | クライアントシークレットのような資格情報は、作成したときに一度だけ表示する |
| 未実装の機能への入口を置かない | ナビゲーションは将来の機能を追加できる構造にするが、まだない画面へのリンクは置かない |

参考にした管理画面：

- [Keycloak Server Administration Guide](https://www.keycloak.org/docs/latest/server_admin/)
- [Okta Manage users](https://help.okta.com/en-us/content/topics/users-groups-profiles/usgp-people.htm)
- [Google Cloud IAM access management](https://cloud.google.com/iam/docs/granting-changing-revoking-access)

## ナビゲーション

管理コンソールとアカウントポータルに適用する。

1. **詳細を確認してから編集する。** 読み取り専用の詳細画面を先に表示し、「編集」の操作から専用の編集画面の URL（`/admin/users/$id/edit`、`/account/profile/edit`）へ移る。
2. **主要なリソースの作成と編集にモーダルを使わない。** ブラウザーの「戻る」とディープリンクを使えるようにするためである。確認ダイアログと、ステップアップ認証のように操作の途中で求める入力は、この規則の対象外とする。
3. **一覧の操作を行の中に表示する。** 詳細、編集、削除をケバブメニューへ隠さない。管理作業では、その行で何ができるかが一覧の時点で分かることを、見た目の簡潔さより優先する。

## 表示状態

画面は次の状態を区別して表示する。
どの状態でも、失敗や権限の不足を成功のように見せない。

| 状態 | 表示方法 | 使う部品 |
| --- | --- | --- |
| 読み込み中（画面の遷移） | 遷移先のデータが揃うまで直前の画面を表示し続ける。空の画面や骨組みだけの画面を挟まない | なし（ルーターの動作） |
| 読み込み中（画面内の操作） | 操作のボタンを無効にし、実行中であることを文言で示す | `Button` |
| 空 | 一覧が空であることと、次に取れる操作（検索語や絞り込みの変更、作成）を文章で示す。空の表だけを表示しない | 各画面の空状態 |
| エラー（操作の失敗） | 失敗した操作の近くに表示し、利用者が次の操作をするまで残す | `Alert` |
| エラー（画面を表示できない） | エラー画面を表示し、再ログインやポータルへの戻り方を示す | ルーターのエラー画面 |
| 権限なし | API が 403 を返した操作について、権限が不足していることを文言で示す。変更が反映されていない状態の表示を保つ | `Alert` |
| ステップアップ認証の要求 | 再認証のダイアログを表示し、再認証が成立したら元の操作を一度だけ再試行する | `StepUpDialog` |
| 部分的な失敗 | CSV の取り込みのように複数の項目をまとめて処理する操作で、成功と失敗の件数を示し、失敗した項目を行、列、エラーコードで特定する。パスワードのようなシークレットは表示に含めない | 各画面の結果表示 |
| 成功 | 画面の配置を押し下げない一時的な通知で、数秒だけ表示する。表示内容が変わる場合は画面にも反映する | `Toast` |

エラーを一時的な通知で表示しないのは、利用者が読む前に消えると、失敗したことに気付く手段がなくなるためである。

## 破壊的な操作

**破壊的な操作**とは、削除、無効化、失効、全セッションの取り消しのように、利用者や連携先の動作を止める操作である。
破壊的な操作は、次の規則に従う。

1. 通常の閲覧用の表示から見た目で分け、ボタンには `variant="destructive"` を使う。
2. 実行する前に確認ダイアログを表示する。確認には `window.confirm` を使わず、画面の部品として作ったダイアログを使う。`window.confirm` は、対象と結果を構造立てて示せず、画面と同じ見た目や言語で表示されないためである。
3. 確認ダイアログには、次の三つを含める。
   - 対象の識別名
   - 操作の結果
   - 取り消せるかどうか
4. 取り消せる操作（削除の予約など）と取り消せない操作（完全削除など）は別の操作として表示する。取り消せない操作では、そのことを警告として示す。
5. 連携先に影響する操作（クライアントの削除など）では、影響する連携先を確認させてから実行する。

## フォームと検証

### 検証の分担

| 検証 | 担当 | 例 | 不備があるときの表示 |
| --- | --- | --- | --- |
| 入力だけで判定できる検証 | SPA | 必須項目の未入力、形式の誤り | 送信ボタンを無効にし、該当する入力欄に `aria-invalid` を付ける |
| 業務ルールの検証（422） | API | 不正な値、上限の超過、ポリシー違反 | フォームの近くに `Alert` で表示し、入力した値を残す |
| 競合（409） | API | 名前の重複、他のリソースからの参照 | フォームの近くに `Alert` で表示し、入力した値を残す |

API が返す `detail` は、違反したフィールドと上限を含む英語の文である。
既知のエラーコードでなければ、そのまま表示する（[エラーの文言](#エラーの文言)）。

### 文字列長の上限

- 入力欄の `maxLength` には、`frontend/src/lib/lengthLimits.ts` の `LENGTH` の値を使う。
- `maxLength` は入力の補助であり、上限を保証するのは API である。上限の値と各箇所の役割は [API ガイドライン](api-guidelines.md#各箇所の役割)に記載している。
- パスワードの入力欄には `maxLength` を付けない。パスワード管理ソフトから貼り付けた長い値が黙って切り詰められると、利用者は短くなったことに気付かないまま登録してしまうためである。

## 一覧

| 規則 | 内容 |
| --- | --- |
| ページ送り | `PageNavigation` を使い、先頭、前、次、末尾への移動と、総件数と現在のページを表示する |
| 移動できない方向 | ボタンを隠さず無効にし、操作の位置が画面ごとに変わらないようにする |
| 条件の保持 | 絞り込み条件とページの位置を URL の検索パラメーターに入れ、再読み込みと「戻る」で同じ一覧を表示する |
| 条件の変更 | 絞り込み条件を変えたら先頭のページに戻る |
| 無効なカーソル | エラーを表示せず、先頭のページを表示する |
| 並べ替えと絞り込み | API の問い合わせで行う。取得済みの行だけを SPA で並べ替えたり絞り込んだりすると、表示していないページの行が結果から漏れるためである |

ページングの方式とカーソルの意味は [API ガイドライン](api-guidelines.md#ページング方式)に記載している。

## エラーの文言

API のエラーの文言は英語に固定されている（[API ガイドライン](api-guidelines.md#エラーメッセージの言語)）。
画面に表示する文言は、次の手順で決める。

1. API が返した安定したエラーコードを、辞書で引く。共通のエラーコードは `frontend/src/lib/i18n/errorMessage.ts`、画面に固有のエラーコードはその画面の辞書で定義する。
2. 辞書にあれば、その文言を表示する。レート制限のエラーでは、再試行できるまでの秒数を文言に加える。
3. 辞書になければ、API が返した英語の文言をそのまま表示する。推測で翻訳すると、API が意図した内容と異なる説明を表示するおそれがあるためである。

## 国際化

### 対応する言語

- 対応する言語は日本語（`ja`）と英語（`en`）だけである。仕様として決めない限り、言語を追加しない。
- 製品のデフォルトの言語は英語である。
- 明示されたロケールもブラウザーのロケールも使えないときの言語は、ビルド時の環境変数 `VITE_DEFAULT_LOCALE` で選ぶ。未設定または無効な値なら英語を使う。

### 辞書

- 利用者に見える文言は、その機能スライスの `*.i18n.ts` に書く。
- `ja` と `en` の値を同じ変更で追加する。
- 辞書は `defineDictionary` で定義する。一方の言語にしかないキーは、型検査で拒否される。

### 日時と数値

日時と数値は、`frontend/src/lib/i18n/context.tsx` の `useFormatters` が返す関数で、現在のロケールに合わせて表示する。

| 関数 | 表示するもの |
| --- | --- |
| `formatDate` | 日付 |
| `formatDateTime` | 日付と時刻（分まで） |
| `formatNumber` | 数値 |

### テストのロケール

1. 単体テストのデフォルトのロケールは英語とする。通常の振る舞いのテストは英語の文言で検証する。
2. 日本語の表示を確かめるテストは、その目的をテスト名に含め、ロケールを明示する（`renderWithRouter` に `{ locale: 'ja' }` を渡すなど）。
3. テストの期待値には翻訳後の文字列を直接書かず、辞書の値を参照する。

## アクセシビリティ

アクセシビリティの規範は、[全体の標準仕様](../../standards.md)の「Web Content Accessibility Guidelines 2.2」の節で定めている。
画面は、各規範を次の手段で満たす。

| 規範 | 実装の手段 |
| --- | --- |
| `WCAG22-KEYBOARD` | 見出し、表、フォーム、ボタン、リンクを、見た目の似た別の要素で代用しない。すべての操作をキーボードだけで実行できるようにし、ドラッグによる並べ替えには、キーボードとスクリーンリーダーによる代替の操作を用意する |
| `WCAG22-FOCUS` | 基本部品のフォーカスリングを消したり上書きしたりしない |
| `WCAG22-LABELS-ERRORS` | 入力欄に `Label` を関連付け、不備のある入力欄に `aria-invalid` を付け、エラーを文章で示す |
| `WCAG22-STATUS` | エラーの `Alert` は `role="alert"`、成功の通知は `role="status"` として、フォーカスを動かさずに支援技術へ伝える |

標準仕様には対応する規範がないが、次の二点も守る。

- アニメーションは、動きを減らす利用者の設定に従う。
- 文字と背景、状態色のコントラストを、読める水準に保つ。
