# バックエンド設計

この文書は、IdMagic のバックエンドの設計を定める。
バックエンドは `backend/` の Go のコードであり、モジュール、共有ライブラリ、実行単位の入口（`backend/cmd/`）からなる。
この文書が定めるのは、モジュール内部の層、パッケージの種類、モジュール間の依存規則と公開範囲、モジュール間イベント、HTTP ルーティング、起動時の組み立てである。

## モジュールの内部構造

モジュールは、[モジュール設計文書の責務表](../../modules/README.md#モジュール)に宣言した責務と、その実装、仕様の文書、TypeSpec の対応を一つの単位として呼ぶ名前である。
実装の範囲は、責務表の実装パスの列が宣言する。
バックエンドのモジュールには、`backend/` 直下の `cmd` と `shared` を除いたディレクトリを一つずつ割り当てている。
Go パッケージを持たない Frontend は公開 HTTP 契約で接続し、この文書の Go の公開範囲と組み立て地点には含めない。
この割り当ては既存の構成を検査するための初期値であり、ディレクトリがあることは境界が妥当であることを示さない。

モジュールは通常、次の 4 層で構成する。

```text
backend/<module>/
  domain/            # エンティティ、値オブジェクト、状態遷移、純粋な検証
  usecases/          # 仕様で定めた操作を行うアプリケーションロジック
  ports/             # Repository、ストア、外部サービスの抽象
  handlers_http/     # 受信 HTTP アダプター
  db_memory/         # メモリ実装の Repository アダプター
  db_postgres/       # PostgreSQL 実装の Repository アダプター
```

アダプターはそれが属するモジュールまたは機能の直下に置き、snake_case の `<role>_<technology>` で命名する。

`<technology>` の位置には、外部技術の名前のほか、相手のモジュールの名前も入る。
ほかのモジュールの公開契約を、自分のポートの語彙へ変換するアダプターがこの形を取る。

変換の意味は、変換した結果を使う利用側のモジュールが所有する。
そのため、提供側を import する変換のアダプターは利用側に置く。
ただし、提供側がすでに利用側を import していて、利用側から提供側を import すると循環する場合は、アダプターを組み立て地点に置く。
依存の向きだけからは変換の意味の所有者を決められないので、配置は[設計ガイドライン](design-guidelines.md#境界を選ぶ判断手順)の手順で比べる。

変換する語彙の差がなければ、変換のアダプターを置かない。
利用側がポートを宣言し、提供側のユースケースがそのポートを直接満たし、組み立て地点で結ぶ。
アダプターを挟んでも、委譲するだけの浅いパッケージが残るためである。

たとえば、下流へ送るモジュールが主体を管理するモジュールの User を読む場合を考える。

| 状況 | 置き方 |
| --- | --- |
| 送る側が、User を自分の送信用の属性の形へ写す | 送る側が変換を所有するので、送る側に `source_<提供側>` のアダプターを置く |
| 主体を管理する側が、送る側に取り込みの有無を問い合わせる必要がある | 送る側はすでに主体を管理する側を import しているので、問い合わせる側（主体を管理する側）がポートを宣言し、組み立て地点で送る側の操作を結ぶ |
| 送る側が必要とする値が、提供側の公開操作の戻り値そのままである | アダプターを置かず、送る側が宣言したポートを提供側が直接満たす |

現在のモジュールの組ごとの結び方は、利用側のモジュールの「責務と境界」に書く。

起動時設定と実行時に選択可能な機能の定義は一点に集める。
すべてのバックエンドプロセス（API、Worker、Batch、Seed）は、共通の起動処理が定義する単一の設定を通して環境を読み、その外で環境変数を直接読まない。
選択できる機能の登録簿は実行時選択と更新影響だけを持ち、各モジュールの API、標準対応、テナント設定を複製しない。
読み取り点や選択規則が散らばると、あるプロセスだけが検証されない値または異なる機能集合を持つ状態が作れてしまうためである。
運用者向けの設定リファレンスと機能メタデータはこれらの定義から生成し、手書きの一覧を併存させない。
利用者の閉域で動く Directory Connector は IdMagic の構成を持たないので、共通の起動処理を使わず、自分の設定ファイルだけを読み、環境変数を読まない（[Directory Connector の実行環境](../../modules/directory-connector/features/runtime.md#設定)）。

具象のドメインイベントの構造体は、それが属するモジュールの `domain` パッケージに置く。共有ライブラリ `backend/shared/spec` にはイベントのエンベロープとなるインターフェースと、そのワイヤ表現への変換だけを置く。イベントがモジュールの境界を越えるときに何が契約になるかは [モジュール間イベント](#モジュール間イベント) で定める。

2 つ以上の独立した機能を持つモジュールは、4 層の構成に機能ごとの垂直分割を追加してよい：`backend/<module>/<feature>/{domain,ports,usecases,<role>_<technology>}/`。
機能ごとの垂直分割はモジュールの内部構造であり、別のモジュールではない。
機能が 1 つしかないモジュールは分割しない。

```text
backend/<module>/
  *.go                      # ルートパッケージ：モジュールごとに 1 つの組み立て
  domain/                   # 機能間で共有する型と計算だけ
  ports/                    # 機能間で共有するポートだけ
  usecases/                 # 機能をまたぐユースケース補助とエラー値だけ
  db_memory/  db_postgres/  # 機能間で共有するポートのアダプター
  handlers_http/            # ルート登録と機能をまたぐ統合テスト
  <feature-a>/  <feature-b>/  # 各機能の domain、ports、usecases、アダプター
```

機能をまたぐ層に置いてよいのは、複数の機能が同じ意味で使う語彙と機構に限る。
たとえば、二つの機能が同じ CSV の取り込みの仕組みを使うなら、解析器と転送の規則は機能をまたぐ層に置く。
一方、どの列を受け付けるかは Aggregate ごとの不変条件なので、各機能に残す。

### パッケージの三種類

`backend/` の本番パッケージは、次の三種類のどれかに属する。

| 種類 | 範囲 | 依存の扱い |
| --- | --- | --- |
| モジュール | 責務表に宣言した実装範囲 | [モジュール間の依存規則](#モジュール間の依存規則)に従う |
| 組み立て地点 | 責務表の System 行が列挙するパッケージ接頭辞。`backend/cmd`、`backend/shared/http/server_http`、`backend/shared/http/testing_stack`、`backend/shared/testing/fixtures_postgres` | 結線に必要な依存を持てる。モジュール間の循環の集計に含めず、公開範囲は公開方式に従う |
| 共有ライブラリ | `backend/shared` のうち組み立て地点を除いたもの | どのモジュールにも依存しない |

接頭辞はディレクトリ区画で照合し、同名で始まる別のディレクトリを含めない。
`testing_stack` を組み立て地点に含めるのは、テスト用の HTTP スタック全体を `_test.go` ではないファイルで組み立てており、実態が `server_http` と同じ結線だからである。
`testing/fixtures_postgres` は、PostgreSQL テストの FK の親行を各所有モジュールのアダプターから投入する。
テストの前提を結線するための組み立て地点であり、本番の入口は利用しない。
同じ接頭辞の重複した割り当て、責務表にないモジュール、どれにも分類できない本番パッケージは検査を失敗させる。

`backend/shared` は、複数のモジュールが実際に共有する技術的な能力のための場所である。
モジュールの型も業務上の意味も必要としない規則だけを置き、モジュール間の依存規則を迂回する中継点にはしない。
型名を文字列へ変えて依存を消しても、業務上の意味を共有しているなら共有ライブラリの条件は満たさない。

組み立て地点へ追加するパッケージには、結線する対象と、業務判断を含まない根拠が必要である。
業務処理を組み立て地点へ移しても依存規則の違反は解消しない。

### モジュール間の依存規則

モジュール間の依存は、すべてのモジュールに同じ形で適用する次の共通規則で検査する。
A から B への依存を個別に許可する一覧は持たない。
特定のモジュールの組だけを禁じる条件は、それを必要とする製品の保証が判明したときに、その保証を根拠に追加する。
この判断の理由と見直し条件は[アーキテクチャ上の判断](../architecture/decisions.md#モジュール間の依存を共通の規則で検査する)に記す。

| 規則 | 違反の種類 | 防ぐ故障 |
| --- | --- | --- |
| モジュールは、ほかのモジュールの公開パッケージだけを import する | `private-import` | 非公開の実装を直接参照する変更 |
| モジュール単位の import 依存は循環しない | `module-cycle` | 異なる内部パッケージを経由するモジュール間の相互参照 |
| 共有ライブラリはモジュールに依存しない | `shared-dependency` | 共有ライブラリを経由して、モジュールが別のモジュールへ到達する依存 |
| モジュールと共有ライブラリは組み立て地点に依存しない | `composition-import` | 結線用の例外を業務処理への迂回路として使う変更 |
| モジュールの sqlc クエリは、ほかのモジュールが所有するテーブルへ書き込まない | `table-write` | 二つのモジュールが同じテーブルの不変条件を別々に保ち、片方の変更がもう片方の保証を破る状態 |

公開パッケージを経由した非循環の依存は、ドメインモデルの独立性を示さない。[モデルの扱い](design-guidelines.md#モジュール間でのモデルの扱い)は別に判断し、依存規則の免除には使わない。
ドメインイベントを送受信する関係は、それだけでは Go の import を生まない。
依存グラフは本番の `.go` から抽出し、`_test.go` は循環の集計に含めない。

`shared-dependency` は、原因である共有ライブラリのパッケージとモジュールの組ごとに一件と数える。
共有ライブラリを経由して到達するモジュールの数だけ同じ import を数えると、違反の数が原因の数を表さないためである。

`domain` は決定論的な計算と状態遷移だけを持つ。時刻の型を保持するための `time` は利用できるが、現在時刻を得る `time.Now`、乱数を得る `crypto/rand` と `math/rand`、OS、ネットワーク、データベースへの直接アクセスは行わない。必要な値と作用は `usecases` から引数または `ports` として注入する。
URL、メールアドレス、IP アドレスの構文解析（`net/url`、`net/mail`、`net/netip`）は入力だけで結果が決まり、名前解決も接続も行わないので、ネットワークへのアクセスに当たらず `domain` で使える。
乱数は、共有ライブラリが定める乱数源の抽象として受け取る。
本番ではユースケースが `crypto/rand` を使う乱数源を渡し、テストは固定のバイト列を返す乱数源を渡す。
`domain` の作用の禁止は、計算の結果をテストで固定できない状態を防ぐ。
`mise run lint-go` の depguard（`domain-effects` の規則）が作用を持つパッケージの import を、forbidigo が `time.Now` の参照を、`domain` の本番ファイルについて拒否する。
起動設定を共通の起動処理の外で読むこと（`os.Getenv`、`os.LookupEnv`、`os.Environ` の参照）も forbidigo が拒否する。
例外は共通の起動処理、実行時の locator を解決する `*_env` アダプター、`testing` と `testing_*` の区画のテスト支援、入口が読み取り関数を共通の設定読み込み処理へ渡す箇所だけであり、`.golangci.yml` の除外規則に置く。
`domain` と `usecases` の外向き依存の禁止とフロントエンドからバックエンドへの import の禁止は、モジュール間の依存規則と同じ境界検査が判定する。
禁止先がパスの途中に任意のモジュール名を挟み、depguard の接頭辞の一致では表せないためである。

`table-write` の対象と限界は[データベース設計](../data/database.md#所有と書き込みの境界)が定める。

#### 依存の向きを選ぶ基準

依存は、利用側から必要な機能へ向ける。
目安となる順は、テナント設定と基盤、主体の状態、アプリケーションの割り当てとポリシー、認証、連携プロトコル、それらを利用する管理機能である。
この順は固定のモジュールの階層ではなく、状態の所有者と利用側の知識を分けるための目安である。
責務表の区分が「基盤」でも、依存先は機能の用途で選ぶ（管理用のトークンが、プロトコルの署名と検証を利用するなど）。

この順と逆向きの機能が必要になったら、次のどれかで依存の向きを保つ。

| 方法 | 使う場面 |
| --- | --- |
| 機能を状態の所有者へ移す | 逆向きに必要な機能が、実は所有者の状態の規則である |
| 利用側がポートを宣言し、組み立て地点で所有者の公開操作を結ぶ | 利用側が必要とするのが、所有者の操作の一部だけである |
| 所有者の結果を、利用側の読み取り専用の入力契約へ写す | 利用側が所有者の判断の結果だけを読み、所有者の知識を複製したくない |

現在のモジュールの組ごとの選択は、利用側のモジュールの「責務と境界」に書く。
依存の事実は[論理アーキテクチャの Context Map](../architecture/logical.md#モジュールの関係)、残る違反は[検査と負債](#検査と負債)で確かめる。

向きを変えるときは、公開操作ごとに、再入、成功と失敗の順、トランザクションへの参加、イベント、通知を比べる。
import をなくすことだけを根拠に、一括のトランザクションや非同期の通知へ置き換えない。
操作を切り出しても所有者の保証を保てないなら、[境界を選ぶ判断手順](design-guidelines.md#境界を選ぶ判断手順)へ戻り、担当と仕様を見直す。
入力型や結果を複製し、委譲を増やして import を消しても、変更時の波及は減らない。

### 公開範囲と `internal/`

非公開の実装は Go の `internal/` に置く。
Go のツールチェーンは `internal/` の親ディレクトリの外からの import を拒否する。
ただし、外側に残したパッケージの公開目的は判定しないため、責務表と照合する検査を併用する。

モジュールの構成は次のとおりである。

| 配置 | 置くもの | 利用できる側 |
| --- | --- | --- |
| `backend/<module>/` | ルートパッケージ。モジュールの組み立てと HTTP ルートの登録 | 組み立て地点だけ |
| 公開パッケージ | ほかのモジュールが使う型と操作、ほかのモジュールが実装するポート。`internal/` の外に置き、責務表の公開パッケージの列へ完全なパスを列挙する | ほかのモジュールと組み立て地点 |
| `backend/<module>/internal/` | ユースケース、アダプター、内部の型など、それ以外のすべて | 同じモジュールの内側だけ |

`internal/` はモジュールの配下全体から見えるので、機能スライスどうしの分離は保証しない。

責務表の公開方式は `internal` である。
公開パッケージは責務表に列挙したパッケージだけで、外側の本番パッケージはルートか公開パッケージでなければ拒否する。
組み立て地点も、ほかのモジュールのルートパッケージと公開パッケージだけを import できる。
存在しないパッケージと `internal/` 配下の公開宣言は拒否する。

組み立て地点が使う永続化アダプターや HTTP のアダプターは、ルートパッケージの操作（永続層ごとのモジュールの生成、経路の登録）にする。
ルートパッケージが返すモジュールの値は `internal/` の型をフィールドに持ってよい。組み立て地点は型を名指さずに値を受け渡せる。
組み立て地点が型を名指す必要があるときは、ルートパッケージに型の別名を置く。ルートパッケージは組み立て地点だけが import できるので、ほかのモジュールの本番コードへの公開は増えない。
機能スライスは `backend/<module>/internal/<name>/` に置き、検査は `internal` の区画を飛ばして `<name>` を機能スライスの名前として読む。
完了した work item が記録したテストのパスは書き換えない。検査は、なくなった `backend/<module>/<rest>` を `backend/<module>/internal/<rest>` として読む。
禁止された `internal/` への import は製品のビルドとテストのコンパイルで拒否される。
公開目的と責務表の整合は、次節のリポジトリ検査で確かめる。

### 検査と負債

これらの規則は `mise run check-boundaries` が検査する。
宣言の欠落、重複、未知の参照、解析できない SQL は入力の診断であり、負債として記録できない。
既存の違反は境界検査の負債台帳に具体的な違反 ID と理由を記録する。
`mise run check-boundary-debt-ratchet` は基準 revision のソースにも同じ規則を当て、基準になかった違反 ID を拒否するので、台帳へ書き足しても新しい違反は通らない。
解消した違反は台帳から同時に削除する。
宣言を広げれば形式上の違反は消えるので、公開パッケージ、組み立て地点、テーブルの所有者の変更にも[境界を選ぶ判断手順](design-guidelines.md#境界を選ぶ判断手順)を適用する。

## モジュール間イベント

モジュール間でドメインイベントに関わる関係は、性格の異なる 2 つの機構で実現している。どちらもイベントバスではなく、メッセージ基盤も介さない。

**ライフサイクルの通知は、ドメインイベントを運ばない。**
状態の所有者が通知の語彙とポートを公開し、通知を受けるモジュールがそれを実装する同期の呼び出しである。
ポートが所有者の公開契約に含まれ、受ける側が実装するので、公開イベントによる関係ではない。
所有者の保存と受ける側の作業を同じトランザクションで確定するか、所有者の確定の後に受ける側が自分のトランザクションで作業を作るかは、ポートの契約が定める。
現在の通知は、主体の変更から LifecycleWorkflow の実行と下流へのプロビジョニングへの二つであり、契約は [IdManagement の責務と境界](../../modules/identity-management/README.md#責務と境界)が定める。

**監査の事実は、組み立て地点に 1 つだけある配信点を通る。**
共通の起動処理が組み立てる発行の閉包が、イベントの出力先への出力、アカウントのセキュリティ通知のディスパッチ、監査記録の追記を順に行う。
ドメインイベントを発行するモジュールはこの閉包だけを関数として受け取り、監査にも通知にも依存しない。
逆に消費する側も発行元の Go の型を知らず、後述のワイヤ表現の上だけで動く。
したがってこの関係に import は存在せず、依存の向きはどちらの側にも生じない。

### 確定と作用の順序

業務状態の保存と、その後の配信点の呼び出しは、同じトランザクションで確定しない。
ユースケースは業務状態を保存してから、同じ要求の中で配信点を同期で呼ぶ。
保存したイベントを後から配信する Transactional Outbox も、メッセージ基盤も持たない。

このため、保存の後に配信点の処理が失敗するか、保存と配信の間にプロセスが止まると、業務状態だけが残り、そのイベントによる作用が欠ける。
欠けた作用の扱いは、作用の種類ごとに決めている。

| 作用 | 欠けたときの扱い |
| --- | --- |
| 監査の記録 | 欠落を許容し、検知した失敗を指標とログへ残す（[REQ-AUDIT-008](../../modules/audit/features/event-search.md)） |
| アカウントのセキュリティ通知 | 送信を配信点から切り離した最大限の努力とし、再送しない（[Authentication の設計判断](../../modules/authentication/decisions.md#セキュリティ通知を配送の基盤なしの最大限の努力にする)） |
| 下流へのプロビジョニングの通知 | 呼び出し元の確定の後に、通知を受けるモジュールが自分のトランザクションで作業を作る。User の通知の失敗はログに残して成功を返す（[IdManagement のオブザーバビリティ](../../modules/identity-management/observability.md)） |

欠けると整合が崩れる作用は、配信点に任せず、業務状態と同じトランザクションへ参加する所有者の公開操作で確定する（[一貫性の境界と永続化](design-guidelines.md#一貫性の境界と永続化)の、一つのトランザクションで確定する類型）。
複数の保存先にまたがる操作は一つのトランザクションにせず、保存先ごとに確定し、冪等な再実行と照合で途中の失敗を回収する。

### イベントの公開契約

イベントが境界を越えるときの契約は、payload の全体ではない。`AdminAuditEventResponse.payload` は意図して不透明な JSON であり、モジュールの内部でしか読まれない項目はそのモジュールのものである。契約になるのは次の 2 つに限る。

- **エンベロープ**：共通のイベント直列化処理が必ず載せるイベント種別名と発生時刻。監査の記録、管理 API のレスポンス、セキュリティ通知のディスパッチがすべてこの形の上で動く。
- **公開項目の語彙**：他のモジュールが名前で読む payload の項目。監査の検索属性の抽出器がこれを検索軸へ写し、セキュリティ通知が宛先と送信条件をここから解決する。

どちらも `spec/modules/system/models.tsp` の `DomainEventEnvelope` と `DomainEventPayload` が一次情報である。配信点を担う System で定義し、消費者である Audit では定義しない。発行する側が消費する側の契約に従う倒立を避けるためである。

宣言を置くだけでは、読み取り側と静かに食い違う。項目名を変えてもコンパイルは通り、監査の絞り込みが空を返すようになるだけだからである。`mise run check-event-contract` が、宣言された語彙と Go の読み取り点の集合が一致することを確かめる。

### 公開イベントの互換性

公開したイベント種別名と公開項目の名前は、削除も改名もしない。監査記録は追記のみで種類ごとの保持期間（デフォルト 365 日）のあいだ残るので、名前を変えても既存のレコードは書き換えられず、古いレコードだけが新しい軸から見えなくなる。項目の追加と、まだ誰も読んでいない内部項目の変更は、この規則の対象ではない。

リリース済みベースラインとの互換性は判定しない。公開イベントの消費者はこのリポジトリの中にしかおらず、外部の消費者がいない契約にベースラインを敷いても守る相手がいないためである。この判断は、外部に配信する Security Event Token には及ばない。あちらは RFC 8417 が別の契約を定めている。

## アクショントークン

メールのリンクで一度だけ実行される操作（パスワードの再設定、メールアドレスの変更の確定など）は、共有ライブラリのアクショントークンの共通核を通す。
共通核は、目的の束縛、有効期限、ダイジェストだけの保存という同じ安全性条件を、用途ごとに書き直させないための差し替え点である。

| 共通核が実装するもの | 用途を担当するモジュールに残すもの |
| --- | --- |
| 用途を閉じた集合として識別する型 | 用途別のペイロード |
| 生のトークンを保持しない保存表現 | 業務の作用 |
| 発行と検証という二つの決定的な計算 | 作用とトークンの使用済み化を一つのトランザクションで確定すること |

- 共通核は用途別のペイロードと業務の作用を知らない。
- 実行時にハンドラーを登録する仕組みは設けず、用途はコードの列挙としてのみ増える。新しい用途が安全性条件のどれかを書き忘れても、共通の検証を通れないようにするためである。

## 値の検証

ドメイン型の検証は、共有の検証ライブラリが定める規則で、フィールドの値を型の付いたまま受け取り、違反を一つのエラーにまとめる。
フィールド名を文字列の鍵とするスキーマやリフレクションは使わない。フィールドの名前と型の誤りを、実行時ではなくコンパイル時に検出するためである。
どのフィールドに何を課すかは各ドメイン型の検証が一次情報であり、この節は規則の種類と意味だけを定める。

### 必須と任意

| フィールドの扱い | 値がないとき | 値があるとき |
| --- | --- | --- |
| 必須 | `is required` だけを報告し、ほかの規則を評価しない | 課した規則をすべて評価する |
| 任意 | 未設定として受け付ける | 課した規則をすべて評価する |
| 必須の集まり | 要素がなければ `is required` を報告する | 各要素に、任意のフィールドと同じ扱いで規則を課す |
| 任意の集まり | 受け付ける | 各要素に、任意のフィールドと同じ扱いで規則を課す |

値がないとは、Go の型のゼロ値（空文字列、0、時刻のゼロ値）か、省略可能な値の不在である。
規則は最初の違反で止めず、満たさないものをすべて報告する。

### 規則の種類

| 規則 | 受け付ける値 |
| --- | --- |
| 識別子 | IdMagic が採番する[識別子](api-guidelines.md#識別子)の形。UUID バージョン 4 の正規形（小文字、ハイフン区切り）だけ |
| URL | スキームとホストを持つ URL |
| メールアドレス | [値オブジェクト](../../modules/identity-management/data.md#値オブジェクト)が定める書式 |
| 文字数 | コードポイント数が下限と上限の間にある文字列（[文字列長の検証](#文字列長の検証)） |
| 索引の鍵 | コードポイント数と UTF-8 のバイト数が、それぞれの上限以下の文字列 |
| 数の範囲 | 下限より大きい、または下限以上の整数 |
| 列挙 | 定めた値のいずれか |
| 述語 | モジュールが定める条件を満たす値。モジュール固有の書式に使う |
| 整合 | 特定のフィールドに属さない、複数のフィールドの組み合わせの条件 |

### エラーの形式

違反は `wire 名: 文言` の形にし、辞書順に並べて `; ` で結ぶ。
wire 名は Go のフィールド名を snake_case にしたもので、入れ子の値は `.`、要素は `[i]` で区切る。
文字数と索引の鍵の違反を含むエラーは長さの違反として区別し、HTTP 層はそれを [422](api-guidelines.md#400-と-422-の区別) に写像する。
長さ以外の違反は区別せず、保存済みデータの破損をサーバーの不具合として扱う余地を残す。

### 文字列長の検証

[API ガイドライン](api-guidelines.md#文字列長の上限)が定める上限を、Go で次のように数える。

| 対象 | 数え方 |
| --- | --- |
| 契約上限 | コードポイント数。Go の `utf8.RuneCountInString` と PostgreSQL の `char_length()` は、TypeSpec の `@maxLength` と同じくコードポイント数を数える |
| リソース上限 | UTF-8 のバイト数。PostgreSQL の `octet_length()` と同じ単位で数える |

- 文字列長の検証は、共有の検証ライブラリの文字数と索引の鍵の規則を使う。キーごとのバイト数の予算の合計が上限に収まることも、そのライブラリのテストが確かめる。
- Go の `len` は UTF-8 のバイト数を数えるため、文字列フィールドの契約上限の判定には使わない。

## HTTP ルーティング

HTTP ルーティングは、サーバーの組み立て地点で組み立てる。
テナント単位のルートをデフォルトのテナントと `/realms/:tenant_id` の両方に登録する。
制御面のテナント横断操作も同じグループに登録し、制御面テナントへの限定はルーティングの接頭辞ではなくハンドラー側の制御面主体の判定が担う。

各モジュールの経路は、そのモジュールの `handlers_http` パッケージがハンドラーとともに登録する。正確なエンドポイントの一覧は TypeSpec と生成した経路のリファレンスが示す。新しい HTTP API は、それが属するモジュールの `handlers_http` に登録する。モジュール固有の Repository とルーティングの接続はモジュールのルートパッケージに集約し、中央のルーターはそのモジュールを呼ぶだけにする。

クライアント IP の信頼の範囲は、経路の組み立て時に一度設定し、各 HTTP ハンドラーが同じ解決結果を使う。
アクセス条件を判定するユースケースには、HTTP の要求や代理の設定を渡さず、解決済みの IP を渡す。
解決の規則は [REQ-SYSTEM-032](../../modules/system/features/http-api.md) が定める。

## 起動時の組み立て

共通の起動処理は、HTTP 層へ渡す依存を一つの値に集約し、メモリ、PostgreSQL、コンソール、OpenTelemetry など実行時の実装選択を吸収する。
モジュール固有の Repository はモジュールのルートパッケージがまとめ、組み立て地点とサーバーはそのモジュールを受け取る。
ポートを追加する変更は、ポート、メモリと PostgreSQL の各アダプター、スキーマ、組み立て地点の永続層ごとの構築を同じ変更で揃える。
