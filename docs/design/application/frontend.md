# フロントエンド設計

この文書は、IdMagic の Web フロントエンド・アプリケーションの設計を定める。
Web フロントエンド・アプリケーションは、ブラウザー上で動く React の SPA（Single Page Application）と、それを配信するゲートウェイからなる。
コードは `frontend/` にある。

SPA は次の四種類の画面を提供する。

| 画面 | 利用者 | URL の接頭辞 |
| --- | --- | --- |
| 認証画面 | OAuth 2.0 と OIDC でサインインする利用者。ログイン、同意、MFA、パスワードの再設定などの画面 | `/login`、`/consent`、`/totp` など |
| アカウントポータル | 自分のアカウントを管理する利用者 | `/account` |
| 管理コンソール | テナントを管理する管理者 | `/admin` |
| システムコンソール | 制御面テナントでテナント全体を管理する管理者 | `/system` |

この文書が定めるのは、SPA のコードの分け方、画面が表示するデータの取得と保持の方法、ルーティング、ビルドと配信、テスト、開発時の作業である。
関連する内容は次の文書が定める。

| 内容 | 文書 |
| --- | --- |
| `frontend/src/` のディレクトリ構成と依存の向き | [構造](../../domain/structure.md#フロントエンドのコンポーネント構造)の「フロントエンドのコンポーネント構造」 |
| 画面を跨いで揃える表示と操作の規範 | [ユーザーインターフェース設計](user-interface.md) |
| Frontend gateway の実行単位としての位置付け | [ランタイムアーキテクチャ](../../architecture/runtime.md#実行単位) |
| API の形とエラーの形式 | [API ガイドライン](api-guidelines.md) |
| ライブラリのバージョン | `frontend/package.json` と `frontend/bun.lock` |

## 全体構成

ブラウザーから API までの構成要素は次のとおりである。

| 構成要素 | 本番 | 開発時 | 役割 |
| --- | --- | --- | --- |
| SPA | ビルド済みの静的ファイル | Vite の開発サーバーが変換して配信する | 画面を描画し、API を呼び出す |
| ゲートウェイ | Caddy（`frontend/Caddyfile`） | Vite の開発サーバーのプロキシ（`frontend/vite.config.ts`） | SPA を配信し、API とプロトコルのエンドポイントへのリクエストを API へ中継する |
| API | `backend/cmd/idmagic` | 同じ | 業務状態を保持し、認可を判定する |

この構成は次の方針に基づく。

- **SPA と API を同一オリジンで公開する。** ブラウザーセッションの Cookie と CSRF の防御を、オリジンを跨ぐ設定なしに成立させるためである。
- **SPA は正となる業務状態を保持しない。** 保持するのはブラウザーセッションだけである。権限の判定も API が行い、SPA の判定は表示の切り替えに限る。
- **中継する経路の集合を、本番と開発時で一致させる。** 経路を足すときは `Caddyfile` と `vite.config.ts` を同じ変更で更新する。一致を確かめるテストは `frontend/src/devProxy.test.ts` だけで、公開する連携エンドポイントの一部しか確かめていない。
- **テナントの経路は二通りで受け付ける。** デフォルトテナントの経路と、`/realms/:tenant_id` を接頭辞とする経路である。現在の URL が `/realms/:tenant_id` で始まるとき、SPA はその部分をルーターの基底パスにし、API の URL にも同じ接頭辞を付ける。

## 採用するライブラリ

ライブラリは次の優先順位で選ぶ。
既存のライブラリで要件を満たせないときにだけ、新しいライブラリを入れる。

1. アクセシビリティ
2. バンドルサイズ
3. 保守性
4. 見た目をリポジトリの側で決められること
5. API 契約を変えずに済むこと

| ライブラリ | 用途 | 選定理由 |
| --- | --- | --- |
| React、TypeScript | ビューと型 | ログイン画面から管理コンソールまで、同じコンポーネント境界と型で書ける |
| Vite | 開発サーバー、本番ビルド | 静的な成果物を生成し、ルート単位のコード分割を提供する |
| TanStack Router | ファイルベースのルーティング | 経路のパラメーターと検索パラメーターを型で扱え、ローダーとコード分割を経路の単位で書ける |
| Tailwind CSS | スタイル、デザイントークン | 状態、レスポンシブ、フォーカスのスタイルを部品ごとに揃えられる |
| Base UI | 見た目を含まない UI 部品 | キーボード操作と ARIA の振る舞いを提供し、スタイルは Tailwind CSS で書ける |
| shadcn/ui の構成に倣ったローカル部品 | ボタン、入力欄、カードなどの基本部品 | リポジトリ内のソースとして保守するので、実行時の依存を増やさずに監査と変更ができる |
| dnd kit | 並べ替え | ドラッグ操作に、キーボードとスクリーンリーダーによる代替の操作がある |
| Tabler Icons | アイコン | 線の太さが揃っており、状態と操作の補助表示に足りる数がある |
| Class Variance Authority、clsx、Tailwind Merge | クラス名の合成 | スタイルの変種を型で表し、競合する Tailwind CSS のクラスを実行時に解消する |
| Biome | 整形、静的解析 | 整形と静的解析を一つのツールで高速に実行できる |
| Bun test、Happy DOM、Testing Library | 単体テスト | 実行環境とテストランナーを Bun に揃え、DOM を伴う描画の検証を別のランタイムへ分けない |
| Knip | 依存宣言の検査 | ソース、CSS、設定、スクリプトの参照から、直接依存の過不足を判定する |

### 採らなかった案

| 案 | 採らない理由 | 再検討の条件 |
| --- | --- | --- |
| サーバー状態のキャッシュライブラリ | 画面の多くは、一人の管理者がある時点のテナントの状態を見て変更するもので、複数の画面で同じデータを同期させる必要が少ない | 同じデータを複数の画面が同時に表示し、互いの更新を反映させる必要が生じたとき |
| 汎用のデータグリッド | 並べ替えと絞り込みは API の問い合わせで行うため、SPA の側で表を操作する層が要らない | SPA の側で表を操作する要件が生じたとき |
| Vite を外し、Bun を開発サーバーと本番のバンドラーにする | 試作して測った結果、下の三つの問題があった | 三つの問題が上流で解消されたとき |

Bun へ移す案で確認した問題は次のとおりである。

1. TanStack Router の自動コード分割が Bun 向けの入口を公開していない。公開されている生成器とコード分割器はプラグインのコンテキストを共有できないため、ルート単位の遅延読み込みが失われる。
2. Bun の CSS バンドラーは `url()` の参照先を必ず data URI として埋め込む。そのためフォントが内容ハッシュ付きの静的アセットにならず、配信時の `font-src 'self'` と衝突する。
3. Bun の開発サーバーが `@tanstack/router-core` 内部の循環 import を解決できず、画面が起動しない。

再検討するときは、次の二点も確かめる。
どちらもビルド自体は成功するため、成否だけを見る検査では気付けない。

- `bun-plugin-tailwind` は Tailwind CSS のコンパイラーを同梱しており、`package.json` で固定したバージョンとは別のバージョンで CSS を生成しうる。
- `Bun.build` は `target: "browser"` でも `process.env.NODE_ENV` を置き換えない。明示しなければ、React の開発ビルドが本番の成果物へ入る。

## 機能スライスの境界

SPA のコードは、機能ごとに `frontend/src/features/<feature>/` へまとめる。
このまとまりを**機能スライス**と呼ぶ。
一つの機能を変更するときに読むファイルを一つのディレクトリに集め、変更の影響を機能の内側に閉じるためである。
ディレクトリ名を `slices/` としないのは、Go 標準の `slices` パッケージと紛れるためである。

### コードの置き場所

コードの置き場所は、次の表を上から順に照らして決める。

| 置くコード | 置き場所 |
| --- | --- |
| API を呼び出す関数と、そのリクエストとレスポンスの型 | `frontend/src/api/`、`frontend/src/types.ts` |
| 経路の定義、検索パラメーターの検証、ローダー、認証の要否 | `frontend/src/routes/` |
| 画面の外枠（`AdminShell`、`AccountShell`、`AuthShell`、`SystemShell`）と、どの機能にも属さない再利用部品 | `frontend/src/components/` |
| 見た目の基本部品 | `frontend/src/components/ui/` |
| どの機能にも属さず、描画を含まない補助（ロケール、辞書、日時の整形、ナビゲーションの定義、文字列長の上限） | `frontend/src/lib/` |
| 上のどれにも当たらないもの（ビュー、その機能だけで使う部品、表示ロジック、検証、テスト、辞書 `*.i18n.ts`） | `frontend/src/features/<feature>/` |

機能スライスの中の部品や補助は、二つ目の機能が使い始めた時点で `components/` または `lib/` へ移す。
将来の再利用を見越して、先に移すことはしない。
移した部品を変更すると全機能に影響しうるため、一つの機能の中で変更を完結できなくなるからである。

### 依存の向き

| 参照元 | 参照してよい先 |
| --- | --- |
| `routes/` | `features/`、`components/`、`lib/`、`api/` |
| `features/<feature>/` | 同じ機能スライスの中、`components/`、`lib/`、`api/` |
| `components/` | `lib/`、`api/` |
| `lib/` | `api/` |
| `api/` | `lib/i18n/`（エラーのデフォルトの文言を、現在のロケールで返すため） |

機能スライスは、別の機能スライスを参照しない。
参照したくなったものは、二つ目の機能が使い始めたものとして、上の規則で `components/` か `lib/` へ移す。
スライス間の参照を許すと、あるスライスの内部を変えたときの影響範囲を、そのディレクトリを読むだけでは判断できなくなる。

依存の向きを機械的に検査する仕組みは、現在はない。

### 機能スライスの例

`admin-users` の構成を示す。
すべての機能スライスは `frontend/src/features/` を見れば分かるため、一覧は載せない。

```text
frontend/src/features/admin-users/
├── AdminUsersListPage.tsx        # 一覧のコンテナ
├── AdminUserDetailPage.tsx       # 詳細のコンテナ
├── AdminUserCreatePage.tsx       # 作成のコンテナ
├── AdminUserEditPage.tsx         # 編集のコンテナ
├── AdminUserImportPage.tsx       # CSV 取り込みのコンテナ
├── AdminUserImportResult.tsx     # 取り込み結果の表示部品
├── AdminUserAttributeEditor.tsx  # 属性の入力部品
├── AdminUserDialogs.tsx          # 削除などの確認ダイアログ
├── AdminUsersPrimitives.tsx      # このスライスだけで使う小さな表示部品
├── AdminUsersShared.tsx          # 複数の画面で使う表示ロジックとセクション
├── AdminUsersPage.i18n.ts        # ja と en の辞書
└── *.test.ts(x)                  # 上の各ファイルの単体テスト
```

経路 `/admin/users` は `frontend/src/routes/admin/users.tsx` で定義され、このスライスの `AdminUsersPage` を描画する。

### 機能スライスと Bounded Context の対応

機能スライスは、Bounded Context と一対一に対応しない。
Bounded Context はドメインモデルの一貫性の単位であり、機能スライスは利用者が一続きに操作する画面の単位だからである。

たとえば `account` スライスは、一つのアカウントポータルとして次の Context の API を使う。

| 画面の内容 | API を担当する Context |
| --- | --- |
| プロフィール、メールアドレス | IdManagement |
| MFA、セッション、サインイン履歴 | Authentication |
| 同意、承認リクエスト | OAuth2 |

画面が使う API の所有者は、`frontend/src/api/` の呼び出し先のパスから TypeSpec をたどって特定する。

## ルーティング

経路は TanStack Router のファイルベースルーティングで定義し、`frontend/src/routes/` のファイル配置がリクエストのパスに対応する。
Vite のプラグインがビルド時と開発時に `frontend/src/routeTree.gen.ts` を生成し、ローダーとコンポーネントを経路ごとに分割して遅延読み込みにする。
生成物は手で編集しない。

### ファイルの種類

| ファイル | 例 | 役割 |
| --- | --- | --- |
| レイアウトの経路 | `admin/route.tsx`、`account/route.tsx` | `<Outlet>` を描画するだけ |
| 末端の経路 | `admin/users.tsx` | 検索パラメーターの検証、ローダー、API の呼び出し、パスパラメーターの処理を書き、機能スライスのビューを描画する |
| 一覧を介さない詳細の経路 | `admin/users_/$id.tsx`（`/admin/users/$id`） | 末尾にアンダースコアを付けたディレクトリに置く |
| 経路の補助 | `-guards.ts`、`-page.tsx` | `-` で始まるファイルは経路の生成から除外される |
| ルート | `__root.tsx` | すべての経路の外枠 |

### 規則

1. 経路ファイルは機能スライスのビューを呼び出し、ビューは経路ファイルを参照しない。ビューが経路の型に依存すると、経路なしでビューを単体テストできなくなるためである。
2. 画面内の移動には `<Link>` を使い、移動先のローダーだけを実行する。
3. 認証フロー（ログイン、同意、コールバック、OIDC のリダイレクト）の遷移は、ページ全体の遷移にする。認可サーバーとの間でブラウザーのリダイレクトを経るため、SPA の内部状態を持ち越せないためである。
4. 画面を描画する経路は、`-page.tsx` の補助を通して、描画した画面の種類を `<meta name="idmagic:page">` として DOM に書き出す。E2E テストは、ローダーの完了と画面の切り替わりを、待ち時間ではなくこの値で検出する。
5. 認証が必要な経路は、ローダーの先頭で `-guards.ts` の `requirePortalAccount` を呼び出す。ローダーに置くのは、初回の読み込みと画面内の移動の両方で同じ判定を通すためである。

`requirePortalAccount` は次のように動く。

1. 未ログインなら、ログインを開始する。ログインが完了すると、元の経路へ戻る。
2. ログイン済みなら、アカウントの情報と CSRF トークンを返す。ローダーはこれを画面へ渡す。
3. 手元のトークンが API で受け付けられなければ、保持している状態を破棄して一度だけ再認可する。

### 読み込み中とエラー

- ローダーの実行中は、読み込み中の画面を表示せず、直前の画面を表示し続ける。
- ローダーが失敗すると、ルーターのデフォルトのエラー画面を表示する。エラー画面の表示内容は[ユーザーインターフェース設計](user-interface.md#表示状態)が定める。

## データの取得と画面の状態

### API の呼び出し

- API を呼び出す関数は `frontend/src/api/` に置き、`frontend/src/api.ts` がまとめて公開する。
- `frontend/src/api/core.ts` が、ベアラートークンの付与、テナントの基底パスの付与、エラーレスポンスの解釈を一か所で行う。
- エラーレスポンスは `AuthenticationAPIError` に変換する。安定したエラーコードは `code` に、API が返した英語の文言は `message` に入る。
- リクエストとレスポンスの型は、`frontend/src/types.ts` と各 `api/` モジュールに手で書いている。TypeSpec からは生成しておらず、TypeSpec との一致を検査する仕組みもない。API の形を変えるときは、TypeSpec と同じ変更でこれらの型を更新する。

### 状態の置き場所

サーバー状態のキャッシュライブラリは使わない（[採らなかった案](#採らなかった案)）。
状態は、種類ごとに次の場所に置く。

| 状態 | 置き場所 | 理由 |
| --- | --- | --- |
| 一覧の絞り込み条件、ページのカーソル | URL の検索パラメーター | 再読み込み、URL の共有、ブラウザーの「戻る」で同じ一覧を復元するため |
| API から取得した表示内容 | 経路のローダーの結果と、それを受け取ったコンテナの `useState` | キャッシュを使わないため |
| 入力中の値、開いているダイアログ、送信中かどうか | コンテナまたはセクションの `useState` | 画面を離れたら破棄してよいため |
| ロケール | `LocaleProvider` のコンテキスト | すべての画面で共有するため |

更新操作の後は、コンテナがレスポンスの内容で自身の状態を置き換えるか、経路を再読み込みする。

### 一覧のページング

1. API が返したカーソルを検索パラメーター `cursor` に入れ、経路を遷移させる。
2. 遷移先のローダーが、そのカーソルで次のページを取得する。
3. カーソルが無効になったとき（絞り込み条件を変えた後など）は、ローダーがカーソルなしで取得し直し、URL からカーソルを外す。

ページ送りの操作部品は `frontend/src/components/ui/page-navigation.tsx` の `PageNavigation` である。

## コンテナと表示用コンポーネント

画面は、データの取得と作用を担うコンテナと、描画だけを担う表示用コンポーネントに分ける。
描画を作用から切り離し、単体テストできるようにするためである。

1. **コンテナ**：公開する `XxxPage` は薄いコンテナにする。`useState`、API の呼び出し、作用を書き、画面の外枠を直接配置する。コンテナの全状態を props で受け取る単一の表示用コンポーネントでページ全体を包むことはしない。複雑さを別の層へ移すだけだからである。
2. **抽出の単位**：独立してテストする価値のある単位で、表示用コンポーネントを抽出する。自身の検証を含むフォーム、項目の一覧、対話的な状態を含むカードが該当する。静的で読み取り専用のマークアップはコンテナに残してよい。
3. **props の範囲**：表示用コンポーネントの props は、そのセクションに必要な値と、実行する操作のコールバックに限る。props が 10 個を超えそうなら、props を増やさず、セクションをさらに分ける。
4. **作用の禁止**：表示用コンポーネントには、`fetch` や `api` の呼び出し、`useEffect`、画面遷移を書かない。セクションが自身の状態を管理して純粋なフォームへ委譲する場合は、そのセクション専用の小さなコンテナに書いてよい。

## ビルドと配信

### ビルド

- `vite build` は、`index.html`、内容ハッシュ付きの JavaScript、一つにまとめた CSS、フォントなどの静的アセットを出力する。
- CSS を一つにまとめるのは、経路ごとの遅延読み込みでスタイルの読み込みが遅れ、描画の途中でレイアウトが崩れることを避けるためである。
- `VITE_` で始まる環境変数は、ビルド時に成果物へ埋め込まれる。配信後には変更できない。
- コンテナイメージは `frontend/Dockerfile` で作る。Bun でビルドし、成果物を Caddy のイメージへ複製する。

### 配信

ゲートウェイは、パスに応じて次のように応答する。

| パス | 応答 | キャッシュ | ゲートウェイが付けるセキュリティヘッダー |
| --- | --- | --- | --- |
| API とプロトコルのエンドポイント | API へ中継する | API が決める | なし |
| `/assets/` 配下 | 静的アセット | 1 年間、不変 | `X-Content-Type-Options` |
| その他 | 該当ファイルがなければ `index.html` | `no-store` | Content Security Policy、`Referrer-Policy`、`X-Content-Type-Options`、`X-Frame-Options` |

- API へ中継したレスポンスには、API 自身が境界のミドルウェアで同じ種類のヘッダーを付けるため、ゲートウェイは付けない。二か所で付けると、どちらの値が有効なのかをレスポンスから判断できなくなる。
- SPA の Content Security Policy は、スクリプト、スタイル、フォント、接続先を同一オリジンに限り、インラインのスクリプトとスタイルを許可しない。

## テスト

| テスト | 置き場所 | 実行するタスク |
| --- | --- | --- |
| ビュー、表示用コンポーネント、補助関数の単体テスト | 対象と同じディレクトリの `*.test.ts`、`*.test.tsx` | `mise run test-ui-unit` |
| 経路の検索パラメーターの検証とガードの単体テスト | `frontend/src/routes/` の `-*.test.ts` | `mise run test-ui-unit` |
| 単体テストが共有する DOM の登録、後片付け、ルーター付きの描画補助 | `frontend/src/test/` | なし |
| ブラウザーから API までを通す E2E テスト | `frontend/tests/e2e/` | `mise run test-ui-e2e` |

- 単体テストは、Happy DOM を DOM として登録し、Testing Library で描画する。
- `AccountShell`、`AdminShell`、`AuthShell` を含むコンポーネントは `Link` を使うため、描画にルーターのコンテキストが必要である。これらのテストは `frontend/src/test/renderWithRouter.tsx` の `renderWithRouter` で描画する。
- テストのロケールの扱いは[ユーザーインターフェース設計](user-interface.md#国際化)が、テストダブルの選び方は[テスト方針](../../development/testing.md#テストダブル)が定める。

### E2E テスト

E2E テストは、`bun test` と Bun に組み込まれた `Bun.WebView` で動く。
macOS では WKWebView を、Linux と Windows では CDP 経由で Chrome を使うため、ブラウザー自動化フレームワークやドライバーを別に用意する必要はない。
`PATH` に必要なのは `go` と `bun` だけである。

テストの実行時には、次の三つのプロセスを自動で起動し、停止する。

| プロセス | ポート | 役割 |
| --- | --- | --- |
| Go の API | `:8081` | `memory` モードで起動する。CSRF の検査を通すため、`ISSUER` をブラウザーのオリジン（`http://localhost:5173`）に合わせる |
| Vite の開発サーバー | `:5173` | SPA を配信し、API とプロトコルのエンドポイントへのリクエストを `:8081` へ中継する |
| 模擬のコールバックサーバー | `:3000` | `development` の seed が登録するデモクライアント（クライアント ID `00000000-0000-4000-8000-000000000021`）の `redirect_uri`（`http://localhost:3000/callback`）で認可コードを受け取る |

この構成で、主要な経路（`/authorize`、ログイン、同意、コールバック）の遷移と、オリジンを跨ぐリダイレクトで `code` と `iss` のパラメーターが保たれること（RFC 9207）を確かめる。
テストの書き方と拡張時の規則は `frontend/tests/e2e/README.md` に記載している。

## 開発時の作業

### よく使うタスク

| 作業 | タスク |
| --- | --- |
| 開発サーバーの起動 | `mise run dev-ui`（API と合わせて起動するなら `mise run dev`） |
| UI の変更の検証 | `mise run verify-ui` |
| 単体テスト | `mise run test-ui-unit`、1 ファイルだけなら `mise run test-ui-unit-file -- <file>` |
| E2E テスト | `mise run test-ui-e2e` |
| 依存宣言の検査 | `mise run check-ui-dependencies` |
| 基本部品の追加 | `mise run add-ui-component -- <component>...` |

- `mise run verify-ui` は、依存宣言の検査、整形の検査、静的解析、型検査、単体テスト、ビルドを実行する。同じ検査がリポジトリ全体の `mise run verify` と CI にも含まれる。
- API 契約を変更したときは、Go の HTTP の E2E テストも実行し、Cookie、CSRF の防御、OAuth のリダイレクト、JSON スキーマが正しいことを確かめる。
- Vite の CLI は `#!/usr/bin/env node` で始まるが、開発とビルドのスクリプトは `bun` で CLI の JavaScript を直接実行する。Node.js のランタイムを必要とせず、実行するプロセスを Bun に統一するためである。

### 依存の宣言

`frontend/package.json` のパッケージは公開するライブラリではなく、互換範囲を利用者へ伝える必要がない。
そのため、依存のバージョンを次のように固定する。

- 直接依存は、範囲指定をせずにバージョンを固定する。推移依存は `bun.lock` で固定する。
- 更新は Renovate か明示的な保守作業で行う。
- 協調して動くパッケージ（React と型定義、TanStack Router と Vite のプラグイン、Tailwind CSS と Vite のプラグインなど）は、同じ更新でバージョンを揃える。

依存の区分は次のとおりである。

| 区分 | 含めるもの |
| --- | --- |
| `dependencies` | ブラウザー向けのソースから参照され、Vite が成果物へ組み込むもの |
| `devDependencies` | ビルド、生成、整形、静的解析、型検査、テストのためだけに実行するもの |

`shadcn` は `src/styles.css` へ CSS を提供し、部品を生成する CLI も提供するが、どちらもビルド時にしか動かないため `devDependencies` に入れる。

`mise run check-ui-dependencies` は Knip で依存宣言を検査する。

- 直接依存の要否を、TypeScript の import だけでなく、CSS の `@import`、Vite と Biome の設定、Bun のテストの preload、パッケージのスクリプト、ルートの生成器からも判定する。
- 使われていない直接依存と、宣言せずに推移依存に頼っている依存の両方を失敗として報告する。
- 検査の入口は `knip.jsonc` に書き写さず、実在する設定ファイルから Knip のプラグインが読み取る。

### 基本部品の追加

基本部品は `mise run add-ui-component -- button card` のように追加する。

- `devDependencies` に固定したバージョンの shadcn CLI を使い、`components.json` の設定に従って `src/components/ui` へ生成する。
- `npx shadcn@latest` は使わない。実行のたびに取得するバージョンが変わり、Bun に統一した実行環境からも外れるためである。
- 生成されたソースと、それが必要とする直接依存は、通常の差分としてレビューする。
