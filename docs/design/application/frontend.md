# フロントエンド設計

このファイルは、ブラウザー向け画面のコードをどう分け、データと状態をどこに持たせ、どう配信するかを持つ。
ディレクトリの配置と依存の向きは[構造](../../structure.md#フロントエンドのコンポーネント構造)が、画面を跨いで揃える利用者向けの規範は[ユーザーインターフェース設計](user-interface.md)が持つ。
依存の版は `frontend/package.json` と `frontend/bun.lock` が、開発時に実行する手順は `frontend/README.md` が持つため、ここには書かない。

## 実行単位とゲートウェイ

画面は、[ランタイムアーキテクチャ](../../architecture/runtime.md#実行単位)の Frontend gateway が配信する静的な SPA である。
ゲートウェイは Caddy で、ビルド成果物を配信し、API とプロトコルのエンドポイントへのリクエストを API の実行単位へ中継する。
画面と API を同一オリジンで公開するのは、ブラウザーセッションの Cookie と CSRF の防御を、オリジンを跨ぐ設定なしに成立させるためである。

中継する経路は、本番の `frontend/Caddyfile` と開発時の `frontend/vite.config.ts` のプロキシ設定に同じ集合として書く。
テナントの経路は、デフォルトテナントの経路と `/realms/:tenant_id` 配下の経路の両方を中継する。
画面は、現在の URL が `/realms/:tenant_id` で始まるときにその部分をルーターの基底パスにし、API の URL にも同じ接頭辞を付ける。
二つの設定の一致は、`frontend/src/devProxy.test.ts` が公開する連携エンドポイントについてだけ確かめている。
経路を足すときは両方を同じ変更で更新する。

画面は、ブラウザーセッション以外に正となる業務状態を持たない。
権限の判定もサーバーが行い、画面側の判定は表示を切り替えるための補助に限る。

## 採用するライブラリ

ライブラリは、アクセシビリティ、バンドルサイズ、保守性、見た目を自分たちで持てること、API 契約を変えずに済むこと、の順で選ぶ。
既存のもので要件を満たせないときにだけ新しいライブラリを入れる。

| ライブラリ | 役割 | 選定理由 |
| --- | --- | --- |
| React と TypeScript | ビューと型 | ログイン画面から管理コンソールまで、同じコンポーネント境界と型で書ける |
| Vite | 開発サーバーと本番ビルド | ゲートウェイから配信できる静的な成果物を生成し、ルート単位のコード分割を提供する |
| TanStack Router | ファイルベースのルーティング | 経路のパラメーターと検索パラメーターを型で扱え、ローダーとコード分割を経路の単位で持てる |
| Tailwind CSS | スタイルとデザイントークン | 状態、レスポンシブ、フォーカスのスタイルを部品ごとに揃えられる |
| Base UI | 見た目を持たない部品 | キーボード操作と ARIA の振る舞いを提供し、スタイルは Tailwind CSS の側で持てる |
| shadcn/ui の構成に倣ったローカル部品 | ボタン、入力、カードなどの基本部品 | リポジトリ内のソースとして保守し、監査と変更を実行時依存なしに行える |
| dnd kit | 並べ替え | ドラッグ操作にキーボードとスクリーンリーダーの代替経路がある |
| Tabler Icons | アイコン | 線の太さが揃い、状態と操作の補助表示に足りる数がある |
| Class Variance Authority、clsx、Tailwind Merge | クラスの合成 | スタイルの変種を型で表し、競合する Tailwind CSS のクラスを実行時に解消する |
| Biome | 整形と静的解析 | 整形と静的解析を一つの道具で高速に適用できる |
| Bun test、Happy DOM、Testing Library | 単体テスト | 実行環境とテストランナーを揃え、DOM を伴う描画の検証を別のランタイムへ分けない |
| Knip | 依存宣言の検査 | ソース、CSS、設定、スクリプトの参照から直接依存の過不足を判定する |

サーバー状態のキャッシュライブラリと汎用のデータグリッドは使わない。
理由は[サーバー状態と画面状態](#サーバー状態と画面状態)に書く。

Vite を外し、Bun を開発サーバーと本番のバンドラーにも使う案は、試作して測ったうえで採らなかった。
TanStack Router の自動コード分割は Bun 向けの入口を持たず、公開されている生成器とコード分割器がプラグインのコンテキストを共有できないため、ルート単位の遅延読み込みが失われる。
Bun の CSS バンドラーは `url()` の参照先を必ず data URI として埋め込むので、フォントが内容ハッシュ付きの静的アセットにならず、配信時の `font-src 'self'` と衝突する。
Bun の開発サーバーは `@tanstack/router-core` 内部の循環 import を解決できず、画面が起動しない。
この三つが上流で解消されたときに再検討する。
再検討では、`bun-plugin-tailwind` が同梱する Tailwind CSS のコンパイラーが `package.json` の固定版と異なりうることと、`Bun.build` が `target: "browser"` でも `process.env.NODE_ENV` を置き換えず、明示しなければ React の開発ビルドが本番成果物へ入ることも確かめる。
どちらもビルド自体は成功するので、成否だけを見る検査では気付けない。

## 機能スライスの境界

画面のコードは、機能ごとに `frontend/src/features/<feature>/` へまとめる。
このまとまりを**機能スライス**と呼ぶ。
一つの機能を変更するときに読むファイルを一つのディレクトリへ集め、変更の影響を機能の内側に閉じるためである。
ディレクトリ名に `slices/` を使わないのは、Go 標準の `slices` パッケージと紛れるためである。

コードをどこへ置くかは、次の順に判定する。

| 判定内容 | 置き場所 |
| --- | --- |
| バックエンドの HTTP API を呼ぶ関数と、その要求と応答の型 | `frontend/src/api/` と `frontend/src/types.ts` |
| 経路の定義、検索パラメーターの検証、ローダー、認証の要否 | `frontend/src/routes/` |
| 画面の外枠（`AdminShell`、`AccountShell`、`AuthShell`、`SystemShell`）と、どの機能にも属さない再利用部品 | `frontend/src/components/` |
| 見た目の基本部品 | `frontend/src/components/ui/` |
| どの機能にも属さない、描画を持たない補助（ロケール、辞書、日時の整形、ナビゲーションの定義、文字列長の上限） | `frontend/src/lib/` |
| 上のどれにも当たらないもの（ビュー、その機能だけで使う部品、表示ロジック、検証、テスト、辞書 `*.i18n.ts`） | `frontend/src/features/<feature>/` |

二つ目の機能が使い始めた時点で、その部品や補助は機能スライスから `components/` または `lib/` へ移す。
一つの機能でしか使っていないものを、将来の再利用を理由に先に出さない。
出した時点で、その部品の変更は全機能に波及しうる変更になり、機能の内側で完結しなくなるためである。

依存は次の向きに限る。

- `routes/` は `features/`、`components/`、`lib/`、`api/` を参照する。
- `features/` は `components/`、`lib/`、`api/` を参照する。
- `components/` は `lib/` と `api/` を参照する。
- `lib/` は `api/` を参照する。
- `api/` は `lib/i18n/` の辞書とロケールだけを参照する。エラーのデフォルトの文言を現在のロケールで返すためである。
- `components/`、`lib/`、`api/` は `features/` と `routes/` を参照しない。

機能スライスは、別の機能スライスを参照しない。
参照が必要になったものは、二つ目の機能が使い始めたものとして上の規則で外へ出す。
スライス間の参照を許すと、あるスライスの内部を変えたときに影響する範囲が、そのディレクトリを読むだけでは分からなくなる。
この向きを検査する仕組みはない。

### 機能スライスの実例

`admin-users` は次のファイルを持つ。
全スライスの一覧は `frontend/src/features/` の内容そのものであり、ここには置かない。

```text
frontend/src/features/admin-users/
├── AdminUsersListPage.tsx        # 一覧のコンテナ
├── AdminUserDetailPage.tsx       # 詳細のコンテナ
├── AdminUserCreatePage.tsx       # 作成のコンテナ
├── AdminUserEditPage.tsx         # 編集のコンテナ
├── AdminUserImportPage.tsx       # CSV 取り込みのコンテナ
├── AdminUserImportResult.tsx     # 取り込み結果の表示部品
├── AdminUserAttributeEditor.tsx  # 属性の入力部品
├── AdminUserDialogs.tsx          # 削除などの確認ダイアログ
├── AdminUsersPrimitives.tsx      # このスライスだけで使う小さな表示部品
├── AdminUsersShared.tsx          # 複数の画面で使う表示ロジックとセクション
├── AdminUsersPage.i18n.ts        # ja と en の辞書
└── *.test.ts(x)                  # 上の各ファイルの単体テスト
```

経路 `/admin/users` の定義は `frontend/src/routes/admin/users.tsx` にあり、そこからこのスライスの `AdminUsersPage` を描画する。

### 機能スライスと Bounded Context の対応

機能スライスの名前は、Bounded Context の名前と一致しない。
Bounded Context はモデルの一貫性の単位であり、機能スライスは利用者が一続きに操作する画面の単位だからである。
たとえば `account` は一つのアカウントポータルとして、IdManagement が所有するプロフィール、Authentication が所有する MFA とセッション、OAuth2 が所有する同意を並べて扱う。
画面が呼ぶ API の所有者は、`frontend/src/api/` の呼び出し先の経路から TypeSpec をたどって特定する。

## ルーティング

経路は TanStack Router のファイルベースルーティングで、`frontend/src/routes/` のファイル配置がリクエストパスに対応する。
ビルド時と開発時に Vite のプラグインが `frontend/src/routeTree.gen.ts` を生成し、ローダーとコンポーネントを経路ごとに分割して遅延読み込みにする。
生成物は手で編集しない。

- `admin/route.tsx` と `account/route.tsx` は `<Outlet>` を描画するだけのレイアウトとする。末端の経路ファイルが、自身の検索パラメーターの検証、ローダー、API の呼び出し、パスパラメーターを持つ。
- 一覧を介さずに描画する詳細の経路には、末尾にアンダースコアを付けたディレクトリを使う。`/admin/users/$id` は `admin/users_/$id.tsx` である。
- `-` で始まるファイル（`-guards.ts`、`-page.tsx` など）は経路の補助であり、経路の生成から除外される。
- 経路ファイルは機能スライスのビューを呼び、ビューは経路ファイルを参照しない。ビューが経路の型に依存すると、ビューを経路なしで単体テストできなくなるためである。
- 画面内の移動には `<Link>` を使い、移動先のローダーだけを実行する。
- 画面を描画する経路は、`frontend/src/routes/-page.tsx` の補助を通して、描画した画面の種類を `<meta name="idmagic:page">` として DOM へ示す。E2E テストが、ローダーの完了と画面の切り替わりを待ち時間ではなくこの値で検出するためである。
- ログイン、同意、コールバック、OIDC のリダイレクトからなる認証フローの遷移は、ページ全体の遷移にする。認可サーバーとの間でブラウザーのリダイレクトを経るため、SPA の内部状態を持ち越せないためである。

認証が要る経路は、ローダーの先頭で `frontend/src/routes/-guards.ts` の `requirePortalAccount` を呼ぶ。
ガードをローダーに置くのは、初回の読み込みと画面内の移動の両方で同じ判定を通すためである。
未ログインのときは、ガードがログインを開始し、完了後に元の経路へ戻す。
ガードが返したアカウントの CSRF トークンを、ローダーの結果として画面へ渡す。

ローダーが失敗したときは、ルーターのデフォルトのエラー画面が表示される。
読み込み中の表示は持たず、ローダーが解決するまで直前の画面を表示し続ける。

## サーバー状態と画面状態

バックエンドの API を呼ぶ関数は `frontend/src/api/` に置き、`frontend/src/api.ts` がそれらをまとめて公開する。
`frontend/src/api/core.ts` が、ベアラートークンの付与、エラー応答の解釈、テナントの基底パスの付与を一か所で行う。
エラー応答は `AuthenticationAPIError` に変換し、安定したエラーコードを `code` に、サーバーが返した英語の文言を `message` に持たせる。

要求と応答の型は `frontend/src/types.ts` と各 `api/` モジュールに手で書いている。
TypeSpec から生成しておらず、TypeSpec との一致を検査する仕組みもない。
API の形を変えるときは、TypeSpec と同じ変更でこれらの型を更新する。

サーバー状態のキャッシュライブラリは使わない。
画面に表示するサーバーの状態は、経路のローダーが取得してビューへ渡す。
更新操作の後は、ビューが応答の内容で自分の状態を置き換えるか、経路を再読み込みする。
画面の多くは、ある時点のテナントの状態を一人の管理者が見て変更するものであり、複数の画面で同じデータを共有して同期させる必要が少ないためである。
同じデータを複数の画面が同時に表示し、互いの更新を反映させる必要が生じたら再検討する。

状態は次のように分けて持つ。

| 状態 | 持つ場所 | 理由 |
| --- | --- | --- |
| 一覧の絞り込み条件、ページのカーソル | URL の検索パラメーター | 再読み込み、共有、ブラウザーの「戻る」で同じ一覧を復元するため |
| サーバーから取得した表示内容 | 経路のローダーの結果と、それを受け取ったコンテナの `useState` | キャッシュを持たないため |
| 入力中の値、開いているダイアログ、送信中の表示 | コンテナまたはセクションの `useState` | 画面を離れたら破棄してよいため |
| ロケール | `LocaleProvider` のコンテキスト | 全画面で共有するため |

一覧のページングは、サーバーが返すカーソルを検索パラメーター `cursor` に入れて経路を遷移させる。
ページ送りの操作は `frontend/src/components/ui/page-navigation.tsx` の `PageNavigation` が持つ。
カーソルが無効になったとき（絞り込み条件の変更後など）は、ローダーがカーソルなしで取得し直し、URL からカーソルを外す。
汎用のデータグリッドを使わないのは、並べ替えと絞り込みをサーバー側の問い合わせが持つため、クライアント側で表を操作する層が要らないためである。

## コンテナと表示用コンポーネントの分割

画面は、データ取得と作用を持つコンテナと、描画だけを持つ表示用コンポーネントに分ける。
描画を作用から切り離して単体テストできるようにするためである。

- 公開する `XxxPage` は薄いコンテナとし、`useState`、API の呼び出し、作用を持ち、画面の外枠を直接配置する。コンテナの全状態を props で受け取る単一の表示用コンポーネントでページ全体を包まない。複雑さを別の層へ移すだけだからである。
- 表示用コンポーネントは、独立してテストする価値がある単位で抽出する。自身の検証を持つフォーム、項目の一覧、対話的な状態を持つカードが該当する。静的で読み取り専用のマークアップはコンテナの中に置いてよい。
- 表示用コンポーネントの props は、そのセクションに必要な値と、実行する操作のコールバックに限る。props が十を超えそうなら、props を広げずにセクションをさらに分ける。
- 表示用コンポーネントは、`fetch` や `api` の呼び出し、`useEffect`、画面遷移を持たない。セクションが自身の状態を持って純粋なフォームへ委譲する場合は、そのセクション専用の小さなコンテナに置いてよい。

## ビルドと配信

`vite build` の成果物は、`index.html`、内容ハッシュ付きの JavaScript、一つにまとめた CSS、フォントなどの静的アセットである。
CSS を一つにまとめるのは、経路ごとの遅延読み込みでスタイルの読み込みが遅れ、描画の途中でレイアウトが崩れることを避けるためである。
`VITE_` で始まる環境変数はビルド時に成果物へ埋め込まれ、配信後には変えられない。

ゲートウェイは、`/assets/` 配下を長期間キャッシュできる不変の資源として配信し、それ以外の経路には `index.html` を返す。
ゲートウェイがセキュリティヘッダーを付けるのは、自身が配信する SPA の HTML と静的アセットだけである。
Content Security Policy とフレームの禁止は HTML に付け、静的アセットには MIME スニッフィングの禁止だけを付ける。
API へ中継した応答には、API 自身が境界のミドルウェアで同じ種類のヘッダーを付けるため、ゲートウェイは重ねて付けない。
二か所で付けると、どちらの値が効いているかを応答から判断できなくなる。
SPA の Content Security Policy は、スクリプト、スタイル、フォント、接続先を同一オリジンに限り、インラインのスクリプトとスタイルを許さない。

## テストの置き場所

| テスト | 置き場所 |
| --- | --- |
| ビュー、表示用コンポーネント、補助関数の単体テスト | 対象と同じディレクトリの `*.test.ts` または `*.test.tsx` |
| 経路の検索パラメーターの検証とガードの単体テスト | `frontend/src/routes/` の `-*.test.ts` |
| 全テストが共有する DOM の登録、後片付け、ルーター付きの描画補助 | `frontend/src/test/` |
| ブラウザーから API までを通す E2E テスト | `frontend/tests/e2e/` |

`AccountShell`、`AdminShell`、`AuthShell` を含むコンポーネントは `Link` を使うため、描画にルーターのコンテキストが要る。
これらのテストは `frontend/src/test/renderWithRouter.tsx` の `renderWithRouter` で描画する。
テストダブルの選び方は[テスト方針](../../development/testing.md#テストダブル)が持つ。
