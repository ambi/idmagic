# 設計ガイドライン

この文書は、モジュールの境界、依存の向きと差し替え点、アダプター、型と不変条件、一貫性の境界、作用、エラーを設計するときの判断基準を定める。
各節は、何を守るかを示す原則、守れている状態と反している状態を比べる判定基準、原則の理由を示す根拠の順に書く。根拠が挙げる出典は末尾の[出典](#出典)にまとめる。
ディレクトリ、依存規則、公開範囲は[バックエンド設計](backend.md)、個別の判断はモジュールの `design/decisions.md`、コードから復元できない仕組みは設計領域ごとの `design/<area>.md` と機能の `design.md` で扱う。
現在のコードがこの基準から外れている箇所は、ガイドラインには書かず、[リスクと技術的負債](../architecture/risks.md)とモジュールの `design/risks.md` に記録する。

## モジュールの深さと情報隠蔽

### 原則

モジュールは、変わりうる設計判断を一つ内部へ隠し、呼び出し側が正しく使うために学ぶインターフェースに対して十分な振る舞いを提供する。
ここでいうインターフェースは型シグネチャだけではなく、不変条件、呼び出し順序、エラー、必要な設定、性能特性を含む。

### 判定基準

| 観点 | 守れている状態 | 反している状態 |
| --- | --- | --- |
| 深さ | 小さなインターフェースの内側へ判断と変換が集まり、呼び出し側は少ない学習量で多くの機能を使える | インターフェースと実装がほぼ同じ複雑さで、モジュールを削除すると委譲だけが消えて呼び出し側が単純になる |
| 隠蔽 | モジュールを削除すると、隠していた複雑さが複数の呼び出し側へ現れる | 呼び出し側が正しく使うために内部設計の文書を読む必要があり、実装の知識が公開契約から漏れている |
| 測り方 | 呼び出し側が学ぶインターフェースの量に対して得られる振る舞いで評価する | 実装の行数や、内部設計の文書の有無で深さを判断する |

### 根拠

変わりうる判断を一つのモジュールに閉じると、その判断を変えるときの変更箇所と検証箇所が一か所に収まる。
分割の基準を「変わりうる設計判断を隠す」に置くのは Parnas の情報隠蔽の考え方であり、インターフェースの量に対する振る舞いの量で深さを測るのは Ousterhout の深いモジュールの考え方である。

## 境界を選ぶ判断手順

### 判断の三分類

設計の判断は、入力の種類によって三つに分かれ、分類ごとに誤りを見つける手段が異なる。
この手順が扱うのは三つ目の「証拠を比較する判断」である。

| 分類 | 定義 | 例 | 誤ったときに何が起きるか |
| --- | --- | --- | --- |
| 機械抽出する事実 | ソース、仕様の識別子、Git の履歴と抽出条件から決まる値。手で書き写さない | import の辺、パッケージのパス、SQL の明示的な書き込み先、要件参照の解決結果、共変更 | 抽出の誤りは fixture で検証し、抽出できない入力は診断する |
| 検査される宣言 | 人またはエージェントが書き、検査が整合または規則の判定に使う値 | 責務表のパッケージと公開方式、組み立て地点、公開パッケージ、テーブルの所有モジュール | 未宣言、重複、未知の参照、規則違反を検査が拒否する。宣言の意味の正しさはレビューで確かめる |
| 証拠を比較する判断 | 要件の意味、不変条件、変更シナリオと事実を使って候補を選ぶ判断 | 新しい処理の担当、公開操作、依存の逆転、モジュールの分割と統合 | 入力、該当する制約、候補、採否、未確認の仮定を work item に記録し、レビューする |

- 機械検査の入力となる欄を足すときは、その欄が変える検査の結果を同時に定める。
- 要件の理由、責務、用語の意味、隠す設計判断は、検査できなくても判断に必要な一次情報として残す。
- 検査が示すのは宣言への適合であり、宣言を変更しただけで設計上の問題が解決したことにはならない。

### 原則

境界を守るのは[バックエンド設計](backend.md#モジュール間の依存規則)の検査であり、境界を選ぶのはこの手順である。
手順を適用するのは、モジュールの追加、分割と統合、公開範囲の拡大、モジュール間の依存の追加、テーブルの所有者または組み立て地点の変更である。
境界を変えない局所的な変更には適用しない。

配置と依存を変えるときは、次の順に入力をそろえ、候補を比べる。
複数の制約が該当するときは、すべてを満たす候補だけを残す。

1. 変更する要件、不変条件、用語の意味を仕様の参照で特定する。
   既存の要件 ID の接頭辞は現在の担当を引く入口として使うが、境界変更を禁じる根拠や、新しい要件の担当を決める根拠にはしない。
2. 状態とその更新元を調べ、直接の SQL、ポート越しの更新、外部キーの cascade、動的な SQL、トランザクションの開始と確定、イベントと通知の呼び出しを記録する。
   import グラフと実行時の作用の流れは別々に扱う。
3. 隠す設計判断を具体的に挙げる。
   保存表現、正規化規則、外部プロトコルの変換などについて、呼び出し側が知る必要のある条件と、内部に閉じられる条件を分ける。
4. 下の表の制約を適用し、現状を維持する案と、必要な範囲の変更案を比べる。
   制約を満たす候補がなければ、宣言の変更やポートの追加で検査を通さず、要件と担当の見直しへ戻る。
5. 残る候補を変更シナリオで比べる。
   実際に発生した変更、または今回の要件が生む変化を入力とし、各案で変わる実装、利用側、契約、検証範囲を列挙する。
   同じ保証を保つ候補の間では、公開する内部知識と利用側への波及が少なく、不要なポート、型、設定を増やさない案を選ぶ。
6. 入力の不足、相反する利点、保証を変えうる未決事項が残れば、候補と判断に必要な問いを利用者へ示す。
   新しい業務概念の意味、原子性、認可の保証は、エージェントが推測して確定しない。

### 判定基準

| ID | 入力の事実または要件 | 制約と候補の絞り込み |
| --- | --- | --- |
| D1 | 既存の仕様と一つの状態所有者の責務を拡張する | まずそのモジュールを候補にする。編成だけを行う処理と状態の更新は分けて配置できる |
| D2 | 所有者が異なる状態を更新する | 各所有者に不変条件の検証と更新を残す。編成する側には、必要な操作、拒否、作用の契約を公開する。保存型や任意の SQL を公開して代用しない |
| D3 | 別のモジュールの非公開の処理が必要になる | 必要な振る舞いを公開操作で表せるか、現在の公開操作の合成で足りるか、そもそも担当が正しいかを比べる。非公開の関数をそのまま公開する案を最初の候補にしない |
| D4 | import の循環ができる | 操作を要求する側が必要最小限のポートを定義し、実装する側が従い、組み立て地点で結ぶ案を比べる。実行時の再入と作用の循環、失敗時の順序、原子性を別に確かめる |
| D5 | 複数のモジュールが同じ技術的な規則を必要とする | モジュールの型も業務上の意味も必要としない場合に限り、共有ライブラリを候補にする。型名を文字列へ変えただけでは条件を満たさない |
| D6 | 提供側の表現を利用側のポートへ変換する | 変換の意味は利用側が所有する。提供側を import する具象のアダプターは利用側へ置くか、D4 のために組み立て地点へ置く。依存の向きだけから意味の所有者を決めない |
| D7 | 複数の状態の部分的な確定を禁止する要件がある | 原子性を定める仕様と失敗例を参照し、参加する更新、トランザクションの所有者、再試行、コミット後の通知を示す。モジュールの数や Aggregate の数から原子性を決めない |
| D8 | 新しいモジュールを作る、または分割、統合する | 隠す判断、状態と契約の担当、独立して変えたい変更シナリオを示す。import、SQL、作用の流れ、利用側への波及を比べ、履歴があれば共変更を補助に使う |

- 新しいモジュールを作ることと、新しい状態の一貫性の境界を作ることは別の判断である。同じトランザクションに参加することだけを理由にモジュールを統合せず、import を非循環にすることだけを理由にモジュールを分割しない。
- `mise run report-change-coupling` は、Git の履歴から同じコミットで変わったモジュールの組と回数を、走査条件と双方の分母とともに出力する。同じコミットに入ることは同じ変更理由を示さず、一括整形や作業のまとめ方でも回数は増える。共変更が少ないことも独立性を示さない。このため、レポートは D8 で変更シナリオを探す補助に限り、合否の判定には使わない。
- 判断の記録は、境界に関わる work item の設計の節に書く。記録するのは、入力の参照、適用した D1〜D8、候補ごとの制約への適合、変更シナリオの波及、採否と理由、残る仮定である。全モジュールの判断を独立した台帳へ複製しない。

### 根拠

モジュールの境界は、ドメイン駆動設計の境界づけられたコンテキストから導かず、隠す設計判断と変更シナリオで選ぶ。
語彙の違いや業務の区切りは、同じ設計判断を共有するかどうかを示さないためである。

## 依存の向きと差し替え点

### 原則

ドメインとユースケースは外部の技術に依存せず、永続化、通知、外部サービスへはポートを通して依存する。
ポートは呼び出す側が定義し、アダプターが実装し、組み立て地点で結ぶ。

差し替え点（Seam）は、呼び出し側を変更せずに実装を差し替えられるインターフェースであり、モジュールの境界とは別の概念である。
差し替え点は、二つ以上のアダプターまたは呼び出し方式が同じ振る舞いを必要とした時点で設ける。

### 判定基準

| 観点 | 守れている状態 | 反している状態 |
| --- | --- | --- |
| 駆動されるポート | 永続化、通知、外部サービスなど、アプリケーションが呼び出す先を `ports/` のインターフェースで表す | ユースケースがデータベースや外部 API のクライアントを直接使う |
| 駆動する側のインターフェース | 複数の呼び出し方式や差し替え可能な実装が実在し、具象ユースケースへの依存を切る必要が生じた場所にだけ置く | 一つのアダプターしかない場所に、将来の差し替えだけを理由とするインターフェースを足す |
| 共通の安全性条件 | 複数の用途が同じ安全性条件を必要とするとき、その条件を一つの共通核に実装し、用途を閉じた集合として列挙する（例：[アクショントークン](backend.md#アクショントークン)） | 用途ごとに目的の束縛、有効期限、保存表現を書き直し、新しい用途がそのどれかを書き忘れる |

現在の HTTP アダプターが具象ユースケースを直接呼ぶ構成は、呼び出し方式が一つである限り、この基準に反しない。

### 根拠

依存を内側へ向けると、外部の技術を差し替えても業務の判断が変わらず、業務の判断を外部の技術なしにテストできる。
内側へ向く依存は Martin の Clean Architecture、ポートとアダプターによる隔離は Cockburn の Hexagonal Architecture、呼び出し側を変えずに振る舞いを差し替える場所としての Seam は Feathers の用語に倣う。
差し替えの必要が実在してから Seam を設けるのは、使われないインターフェースが、呼び出し側の学ぶ量だけを増やすためである。

## アダプターと表現

### 原則

アダプターは外部表現とアプリケーション内部の表現を変換し、HTTP、SQL、外部プロトコルの規則をドメインとユースケースへ持ち込まない。
入力の構文検査、外部のエラー形式、永続化形式の都合はアダプターが引き受け、ドメインは業務上の意味を検証する。

### 判定基準

| 観点 | 守れている状態 | 反している状態 |
| --- | --- | --- |
| 型の共有 | 外部契約とドメインモデルで同じ型を使うのは、JSON の形、SQL の NULL、外部プロトコルの省略規則がドメインのインターフェースに現れない場合に限る。現れる場合はアダプター固有の型を置いて変換する | 外部形式の変更だけで、ドメイン型や呼び出し側を連鎖的に直す必要が生じる |
| 一次情報 | 型を再利用しても、外部契約の一次情報は TypeSpec のままである | 再利用したドメイン型を、外部契約の一次情報として扱う |

### 根拠

外部表現の変更をアダプターに閉じると、外部の契約とドメインの判断を別々に変えられる。
アダプターが変換を引き受ける構成は、Hexagonal Architecture のアダプターの役割に倣う。

## 型の所有と不変条件

### 原則

TypeSpec は、HTTP を含む外部境界の型、制約、エラー和、認証方式の一次情報である。
ドメイン型は内部の状態と操作の一次情報であり、TypeSpec から生成せず、アダプターが両者を対応付ける。
不変条件は、最も狭い場所で強制する。

### 判定基準

| 条件の種類 | 強制する場所 |
| --- | --- |
| 一つの値の妥当性、複数フィールドの整合 | ドメイン型の構築または状態遷移 |
| 操作後に成立する条件 | 事後条件 |
| 永続データの一意性と参照整合性 | データベース制約 |
| 外部から観測できる保証 | 機能仕様の要件と `scenarios.feature.md` |

| 観点 | 守れている状態 | 反している状態 |
| --- | --- | --- |
| 別名型と構築関数 | 値の取り違えを防ぐか、一つの検証済み表現を作る場合に使う | すべての識別子を一律に別名型にする。文字列から業務上の意味を分離できない別名を増やす |
| 条件の重複 | 一つの条件に一つの一次情報があり、ほかの場所はそれを参照する | 同じ条件を TypeSpec、実装、SQL、散文へ重複して書き、変更時にどれが一次情報か決められない |

### 根拠

不変条件を構築と状態遷移で強制すると、不正な状態を作れる経路が減り、呼び出し側が事前条件を確かめる必要がなくなる。
事前条件、事後条件、不変条件で操作の約束を表す考え方は、Meyer の契約による設計に倣う。

## 一貫性の境界と永続化

### 原則

何を一つの Aggregate にまとめるかは、同時に変わるかどうかではなく、**同時に正しくなければならないかどうか**で決める。
一つのトランザクションが更新する範囲は、原子性を定める要件から決める（境界を選ぶ判断手順の D7）。
永続化ポートは、Aggregate root 単位に置く。

### 判定基準

| 観点 | 守れている状態 | 反している状態 |
| --- | --- | --- |
| Aggregate の範囲 | 同時に正しくなければならない状態だけを一つにまとめる（例：`Tenant` に外装や属性スキーマを埋め込まず別の Aggregate とする判断、[Tenancy の重要な設計判断](../../modules/tenancy/design/decisions.md)） | 同時に変わるだけのものをまとめ、競合しない更新どうしが一つの境界の中で直列化される |
| トランザクションの範囲 | 複数の Aggregate を一つのトランザクションで変更するのは、片方だけが残った状態を外部が観測できてはならない場合に限り、その判断と理由を規則の判断の欄か、モジュールの設計に記録する | モジュールの数や Aggregate の数から原子性を決める |
| 永続化ポートの粒度 | 一つの永続化ポートが一つの root を扱い、どの操作がどの一貫性の境界に属するかがインターフェースから読める | 一つのポートが複数の root を扱い、呼び出し側が境界を知るために実装を読む |
| ポート名 | 永続化ポートが Aggregate を扱うかどうかを、ポートが保存する型、不変条件、仕様で判断する | ポート名の接尾辞（`Repository`、`Store`）から推測する。`Store` を名乗るポートには、Aggregate を保存するもの、不透明な鍵で引く短命なプロトコル状態を保存するもの、Aggregate に属さない資産を保存するものがある |

単回消費と削除について、一つのトランザクションで複数の状態を変更する類型は現在二つあり、どちらの保証も維持する。

| 類型 | 片方だけが残った場合 | 記録 |
| --- | --- | --- |
| User の削除が、同意、リフレッシュトークン、ログインセッションなどへ一つのトランザクションでカスケードする | 削除した User に属する記録の一部が残る | [ユーザーの設計](../../modules/identity-management/user/design.md) |
| アクショントークンの使用済み化と、そのトークンが認可した用途別の作用 | 同じリンクで作用が二度成功するか、利用者が正当な回復手段だけを失う | [Authentication のパスワードの判断](../../modules/authentication/password/design.md)、[メールアドレスの変更の規則](../../modules/identity-management/account/README.md#メールアドレスの変更の確定) |

### 根拠

一貫性の境界を「同時に正しくなければならないもの」に絞ると、境界の中の不変条件は常に成り立ち、境界の外の整合は結果整合として明示的に組める。
Aggregate の語と、ルートの識別子で外部から参照する形は、Evans の *Domain-Driven Design* から借りる。
借りるのはこの一貫性の境界の意味だけであり、モジュールの境界はドメイン駆動設計から導かない（[用語集](../../requirements/glossary.md)）。

## 作用の境界

### 原則

ユースケースは永続化、通知、時刻、乱数、識別子生成、設定などの作用を編成し、決定可能な計算へ値またはポートとして渡す。

### 判定基準

| 観点 | 守れている状態 | 反している状態 |
| --- | --- | --- |
| 計算の決定性 | ドメインの計算が作用を内部で作らず、同じ入力から同じ判断を再現できる | ドメインの計算が現在時刻や乱数を内部で取得し、呼び出し側が結果を制御できない |
| 配置と保証 | 作用がないことを、計算の入力と出力の型で確かめる | `domain/` という配置だけから作用がないと仮定する |

### 根拠

作用を計算の外に置くと、テストはインターフェースを通して振る舞いを検証でき、時刻や乱数を差し替えずに判断を再現できる。
決定可能な計算を内側に、作用の編成を外側に置く構成は、Bernhardt の Functional Core, Imperative Shell に倣う。

## エラーと拒否

### 原則

入力から生じうる失敗は値として返し、部分関数とパニックを通常の分岐に使わない。
ドメインでは業務上成立しない状態を、ユースケースでは操作の拒否と作用の失敗を、アダプターでは外部入力の不正と外部向けエラー表現を扱う。

### 判定基準

| 観点 | 守れている状態 | 反している状態 |
| --- | --- | --- |
| 拒否の検証 | 拒否したという結果と、実行しなかった作用を組にして検証できる | 失敗時に永続化や通知が起きたかを、呼び出し側が確認できない |
| 拒否の判別 | 業務上の拒否を、型または値で判別できる | アダプターがエラーメッセージを解析して業務上の拒否を推測する |

### 根拠

拒否を値として返すと、どの失敗がどの層の責任かが型に現れ、拒否の後に作用が残らないことをテストで確かめられる。

## 仕様に書ける振る舞い

### 原則

設計は、外部から観測できる振る舞いを短い仕様で書き切れる形にする。
仕様を短く書けない設計は、仕様を書き足すのではなく設計を直す。

### 判定基準

| 指針 | 反している状態 |
| --- | --- |
| 同じ種類の操作（作成、更新、削除）は、経路が異なっても一つの共有の仕組みで検証、正規化、通知、記録する | 管理者による作成、CSV の適用、別のモジュールからの作成が、それぞれ別のコードで重複を判定し、結果が経路ごとに異なる |
| 値の正規化と比較は、値オブジェクトで一か所に定義する | ユーザー名の大文字と小文字の扱いが Aggregate ごとに異なる |
| 状態を変える操作は冪等にする。すでにその状態なら成功を返し、作用を起こさない | 同じ停止の要求を繰り返すたびに時刻が進み、イベントが重なる |
| 読み取りの操作に副作用を加えない | 一覧の取得が、期限を過ぎたデータの削除を兼ねる |
| 時刻の経過で起きる遷移は、その遷移を起こす主体（定期ジョブなど）を設ける | 期限を過ぎた状態が、たまたま別の操作が呼ばれるまで残る |
| 途中で失敗した操作は、再実行で完了できるようにする | 一部の作用だけが残った後、再実行しても何もせずに成功を返す |
| 順序と時刻に暗黙に依存しない | 結果の順序が map の反復順や並行処理の完了順で決まる |

### 根拠

仕様に書いていない振る舞いを実装が生むと、その振る舞いは誰も決めないまま利用者に依存され、後から仕様の漏れとして見つかる。
経路ごとに異なる振る舞いは、その差の分だけ仕様を長くするので、経路をまとめるほうが仕様、実装、テストのすべてで安い。

## 確立した実装への委譲

### 原則

暗号、署名、プロトコルの解析など、確立した実装がある処理は自作しない。
どこまで検証するかは work item の `risk` と[脅威モデル](../security/threat-model.md)が決め、モジュールの責務の性格によって検証の強度を変えない。

### 判定基準

| 観点 | 守れている状態 | 反している状態 |
| --- | --- | --- |
| 委譲 | 確立した実装に処理を委ね、その使い方だけを書く（例：AEAD と鍵セットの処理を [Tink](https://developers.google.com/tink) に委ね、nonce、認証タグ、追加認証データの組み立てを自作しない、[データベース設計](../data/database.md#可逆な秘密情報のエンベロープ暗号)） | 暗号の組み立てやプロトコルの解析を自作する |
| 文書の厚み | 代替案を比べた判断は `design/decisions.md` に、コードから復元できない機構はその設計領域の設計文書に、一つの機能に閉じた機構は機能の `design.md` に書き、書くべき機構がないときは文書を作らない | 書くべき内容のない設計文書を、形式をそろえるためだけに作る |

### 根拠

確立した実装は、自作した実装より多くの利用者と検証を経ている。
暗号とプロトコルの誤りは正常系のテストでは見つからず、悪用されるまで気付かないことが多いためである。
