# 設計ガイドライン

この文書は、プロダクト全体の設計で、モジュールの境界の選び方、Aggregate の境界、モジュールのインターフェース、Seam、型、作用、エラーをどう評価するかを定める。ディレクトリ、依存規則、公開範囲は [構造](../../domain/structure.md)、個別の判断と理由は各 `decisions.md`、コードから復元できない仕組みは各 `internals.md` に書くので、この文書には重ねて書かない。

## 判断の三分類

設計の判断は、入力の種類によって三つに分かれる。
分類ごとに、誤りを見つける手段が異なる。

| 分類 | 定義 | 例 | 誤ったときに何が起きるか |
| --- | --- | --- | --- |
| 機械抽出する事実 | ソース、仕様の識別子、Git の履歴と抽出条件から決まる値。手で書き写さない | import の辺、パッケージのパス、SQL の明示的な書き込み先、要件参照の解決結果、共変更 | 抽出の誤りは fixture で検証し、抽出できない入力は診断する |
| 検査される宣言 | 人またはエージェントが書き、検査が整合または規則の判定に使う値 | 責務表のパッケージと公開方式、組み立て地点、公開パッケージ、テーブルの所有モジュール | 未宣言、重複、未知の参照、規則違反を検査が拒否する。宣言の意味の正しさはレビューで確かめる |
| 証拠を比較する判断 | 要求の意味、不変条件、変更シナリオと事実を使って候補を選ぶ判断 | 新しい処理の担当、公開操作、依存の逆転、モジュールの分割と統合 | 入力、該当する制約、候補、採否、未確認の仮定を work item に記録し、レビューする |

機械検査の入力となる欄を足すときは、その欄が変える検査の結果を同時に定める。
要求の理由、責務、用語の意味、隠す設計判断は、検査できなくても判断に必要な一次情報として残す。
検査が示すのは宣言への適合であり、宣言を変更しただけで設計上の問題が解決したことにはならない。

## 境界を選ぶ判断手順

境界を守るのは [構造](../../domain/structure.md#モジュール間の依存規則) の検査であり、境界を選ぶのはこの手順である。
手順を適用するのは、モジュールの追加、分割と統合、公開範囲の拡大、モジュール間の依存の追加、テーブルの所有者または組み立て地点の変更である。
境界を変えない局所的な変更には適用しない。

配置と依存を変えるときは、次の順に入力をそろえ、候補を比べる。
複数の制約が該当するときは、すべてを満たす候補だけを残す。

1. 変更する要求、不変条件、用語の意味を仕様の参照で特定する。
   既存の要件 ID の接頭辞は現在の担当を引く入口として使うが、境界変更を禁じる根拠や、新しい要求の担当を決める根拠にはしない。
2. 状態とその更新元を調べ、直接の SQL、ポート越しの更新、外部キーの cascade、動的な SQL、トランザクションの開始と確定、イベントと通知の呼び出しを記録する。
   import グラフと実行時の作用の流れは別々に扱う。
3. 隠す設計判断を具体的に挙げる。
   保存表現、正規化規則、外部プロトコルの変換などについて、呼び出し側が知る必要のある条件と、内部に閉じられる条件を分ける。
4. 下の表の制約を適用し、現状を維持する案と、必要な範囲の変更案を比べる。
   制約を満たす候補がなければ、宣言の変更やポートの追加で検査を通さず、要求と担当の見直しへ戻る。
5. 残る候補を変更シナリオで比べる。
   実際に発生した変更、または今回の要求が生む変化を入力とし、各案で変わる実装、利用側、契約、検証範囲を列挙する。
   同じ保証を保つ候補の間では、公開する内部知識と利用側への波及が少なく、不要なポート、型、設定を増やさない案を選ぶ。
6. 入力の不足、相反する利点、保証を変えうる未決事項が残れば、候補と判断に必要な問いを利用者へ示す。
   新しい業務概念の意味、原子性、認可の保証は、エージェントが推測して確定しない。

| ID | 入力の事実または要求 | 制約と候補の絞り込み |
| --- | --- | --- |
| D1 | 既存の仕様と一つの状態所有者の責務を拡張する | まずそのモジュールを候補にする。編成だけを行う処理と状態の更新は分けて配置できる |
| D2 | 所有者が異なる状態を更新する | 各所有者に不変条件の検証と更新を残す。編成する側には、必要な操作、拒否、作用の契約を公開する。保存型や任意の SQL を公開して代用しない |
| D3 | 別のモジュールの非公開の処理が必要になる | 必要な振る舞いを公開操作で表せるか、現在の公開操作の合成で足りるか、そもそも担当が正しいかを比べる。非公開の関数をそのまま公開する案を最初の候補にしない |
| D4 | import の循環ができる | 操作を要求する側が必要最小限のポートを定義し、実装する側が従い、組み立て地点で結ぶ案を比べる。実行時の再入と作用の循環、失敗時の順序、原子性を別に確かめる |
| D5 | 複数のモジュールが同じ技術的な規則を必要とする | モジュールの型も業務上の意味も必要としない場合に限り、共有ライブラリを候補にする。型名を文字列へ変えただけでは条件を満たさない |
| D6 | 提供側の表現を利用側のポートへ変換する | 変換の意味は利用側が所有する。提供側を import する具象のアダプターは利用側へ置くか、D4 のために組み立て地点へ置く。依存の向きだけから意味の所有者を決めない |
| D7 | 複数の状態の部分的な確定を禁止する要求がある | 原子性を定める仕様と失敗例を参照し、参加する更新、トランザクションの所有者、再試行、コミット後の通知を示す。モジュールの数や Aggregate の数から原子性を決めない |
| D8 | 新しいモジュールを作る、または分割、統合する | 隠す判断、状態と契約の担当、独立して変えたい変更シナリオを示す。import、SQL、作用の流れ、利用側への波及を比べ、履歴があれば共変更を補助に使う |

新しいモジュールを作ることと、新しい状態の一貫性の境界を作ることは別の判断である。
同じトランザクションに参加することだけを理由にモジュールを統合せず、import を非循環にすることだけを理由にモジュールを分割しない。

`mise run report-change-coupling` は、Git の履歴から同じコミットで変わったモジュールの組と回数を、走査条件と双方の分母とともに出力する。
同じコミットに入ることは同じ変更理由を示さず、一括整形や作業のまとめ方でも回数は増える。
共変更が少ないことも独立性を示さない。
このため、レポートは D8 で変更シナリオを探す補助に限り、合否の判定には使わない。

判断の記録は、境界に関わる work item の設計の節に書く。
記録するのは、入力の参照、適用した D1〜D8、候補ごとの制約への適合、変更シナリオの波及、採否と理由、残る仮定である。
全モジュールの判断を独立した台帳へ複製しない。

## 確立した実装への委譲

暗号、署名、プロトコルの解析など、確立した実装がある処理は自作しない。
「AEAD と鍵セットの処理は [Tink](https://developers.google.com/tink) に委ね、nonce、認証タグ、追加認証データの組み立てを自作しない」（[データベース設計](../data/database.md#可逆な秘密情報のエンベロープ暗号)）が、この規則で説明できる既存の判断である。
どこまで検証するかは work item の `risk` と [脅威モデル](../security/threat-model.md) が決める。
モジュールの責務の性格によって検証の強度を変えない。

文書の厚みは、書くべき内容があるかで決まる。
判断とその理由は `decisions.md` に、コードから復元できない機構は `internals.md` に書き、書くべき機構がないのに `internals.md` を作らない。

## モジュールの深さと情報隠蔽

モジュールは、呼び出し側が正しく使うために知る必要があるインターフェースに対して、十分な振る舞いを隠す。ここでいうインターフェースは型シグネチャだけではなく、不変条件、呼び出し順序、エラー、必要な設定、性能特性を含む。

モジュールの深さは実装行数では測らず、呼び出し側が学ぶインターフェースの量に対して得られる振る舞いで評価する。小さなインターフェースの内側へ判断と変換を集めると、呼び出し側は少ない学習量で多くの機能を使え、保守では変更箇所と検証箇所の局所性が高まる。

モジュールを削除したとき、隠していた複雑さが複数の呼び出し側へ現れるなら、そのモジュールは役割を果たしている。削除によって委譲だけが消え、呼び出し側が単純になるなら、インターフェースと実装がほぼ同じ複雑さを持つ浅いモジュールである。

`internals.md` の存在だけではモジュールの浅さを示さない。しかし、呼び出し側がモジュールを正しく使うために `internals.md` を読まなければならないなら、実装の知識がインターフェースから漏れている。

## 差し替え点とポート

差し替え点（Seam）は、呼び出し側を変更せずに実装を差し替えられるインターフェースである。
モジュールの境界とは別の概念である。

`ports/` は、永続化、通知、外部サービスなど、アプリケーションが呼び出す駆動されるポートを持つ。駆動する側のインターフェースは、複数の呼び出し方式や差し替え可能な実装が実在し、具象ユースケースへの依存を切る必要が生じた場所に置く。

一つのアダプターしかない場所に、将来の差し替えだけを理由とするインターフェースは足さない。二つ以上のアダプターまたは呼び出し方式が同じ振る舞いを必要とした時点で Seam を設けるため、現在の HTTP アダプターが具象ユースケースを直接呼ぶ構成も許される。

メールのリンクで一度だけ実行される操作は、`backend/shared/security/actiontoken` の共通核を通す。共通核には、用途を閉じた集合として識別する型、生トークンを保持しない保存表現、そして発行と検証という二つの決定的な計算だけを実装する。用途別のペイロードと業務作用は担当するモジュールに残り、共通核はそれらを知らない。実行時にハンドラーを登録する仕組みは設けず、用途はコードの列挙としてのみ増える。これは、目的の束縛、有効期限、ダイジェストだけの保存という同じ安全性条件を用途ごとに書き直させないための Seam であり、新しい用途がそのどれかを書き忘れても共通の検証を通れないようにするためである。

## Aggregate 境界と Repository

Aggregate は一貫性の境界である（語の定義は [用語集](../../domain/glossary.md)）。何を 1 つの Aggregate にまとめるかは、同時に変わるかどうかではなく、**同時に正しくなければならないかどうか**で決める。同時に変わるだけのものをまとめると、競合しない更新どうしが 1 つの境界の中で直列化される。`Tenant` に外装や属性スキーマを埋め込まず別の Aggregate とする判断（[Tenancy の重要な設計判断](../../domain/tenancy/design/decisions.md)）は、この基準を適用した結果である。

一つのトランザクションが更新する範囲は、原子性を定める要求から決める（境界を選ぶ判断手順の D7）。モジュールの数や Aggregate の数からは決めない。複数の Aggregate を一つのトランザクションで変更するのは、片方だけが残った状態を外部が観測できてはならない場合であり、その判断と理由は、その規則の判断の欄か、そのモジュールの設計（`design/decisions.md` と話題ごとの設計）に記録する。単回消費と削除について現在ある類型は 2 つであり、どちらの保証も維持する。User の削除が `Consent`、`RefreshTokenRecord`、`LoginSession` などへ 1 つのトランザクションでカスケードする（[ユーザーの設計](../../domain/identity-management/user/design.md)）。もう 1 つは、アクショントークンの使用済み化と、そのトークンが認可した用途別作用である（[Authentication のパスワードの判断](../../domain/authentication/password/design.md)、[メールアドレスの変更の規則](../../domain/identity-management/account/README.md#メールアドレスの変更の確定)）。片方だけが残る状態は、同じリンクで作用が二度成功するか、利用者が正当な回復手段だけを失うかのどちらかになる。

Repository は Aggregate root 単位に置く。1 つの Repository が複数の root を扱うと、どの操作がどの一貫性の境界に属するかがインターフェースから読めなくなり、呼び出し側は境界を知るために実装を読むことになる。反している状態は現在 1 つある。`backend/sourcing/scim/ports` の `ScimRepository` が `ScimUserRef` と `ScimGroupRef` の 2 つを扱っており、これは取り込み元との対応表という同じ役割の 2 つを 1 つのアダプターで実装したまま、ポートの側も分けなかったものである。

ポート名の `Repository` と `Store` は、扱うものの種類を区別しない。`Store` を名乗るもののうち `SessionStore`、`ApprovalRequestStore`、`RefreshTokenStore`、`KeyStore` は Aggregate を保存し、`PARStore`、`DeviceCodeStore`、各 `ReplayStore` は不透明な鍵で引く短命なプロトコル状態を保存する。`ApplicationIconStore` や `TenantBrandingAssetStore` は Aggregate に属さない資産を保存する。したがって、ある永続化ポートが Aggregate を扱うかどうかを接尾辞から推測してはならない。ポートが `Save` に受け取る型は調べる入口になるが、その型が Aggregate か、境界が妥当かは、不変条件と仕様で判断する。

## アダプターと表現

アダプターは外部表現とアプリケーション内部の表現を変換し、HTTP、SQL、外部プロトコルの規則をドメインとユースケースへ持ち込まない。入力の構文検査、外部のエラー形式、永続化形式の都合はアダプターが引き受け、ドメインは業務上の意味を検証する。

外部契約とドメインモデルで同じ Go 型を再利用しても、その型が外部契約の一次情報になるわけではない。再利用によって JSON の形、SQL の NULL、外部プロトコルの省略規則がドメインのインターフェースに現れる場合は、アダプター固有の型を置いて変換する。

反している状態は、外部形式の変更だけでドメイン型や呼び出し側を連鎖的に直す必要が生じる状態である。既存の HTTP アダプターにはドメイン型をレスポンス型のフィールドへ直接使う箇所が残るため、配置だけから変換の分離を仮定できない。

## 型の所有と不変条件

TypeSpec は、HTTP を含む外部境界の型、制約、エラー和、認証方式の一次情報である。Go のドメイン型は、内部の状態と操作の一次情報であり、TypeSpec から生成せず、アダプターが両者を対応付ける。

別名型や構築関数は、値の取り違えを防ぐか、一つの検証済み表現を作る場合に使う。すべての識別子を一律に別名型へする規則は設けず、文字列から業務上の意味を分離できない別名も増やさない。

不変条件は、最も狭い場所で強制する。一つの値の妥当性と複数フィールドの整合はドメイン型の構築または状態遷移で、操作後に成立する条件は事後条件で、永続データの一意性と参照整合性はデータベース制約で強制する。外部から観測できる保証は `scenarios.feature.md` で定める。

反している状態は、同じ条件を TypeSpec、Go、SQL、散文へ重複して書き、変更時にどれが一次情報か決められない状態である。既存のドメイン構造体には構築後の `Validate` を必要とするものもあるため、「不正な状態を型だけでは構築できない」ことをリポジトリ全体の性質とはしない。

## 作用の境界

ユースケースは永続化、通知、時刻、乱数、識別子生成、設定などの作用を編成し、決定可能な計算へ値またはポートとして渡す。計算が作用を内部で作らなければ、同じ入力から同じ判断を再現でき、テストはインターフェースを通して振る舞いを検証できる。

反している状態は、ドメインの計算が現在時刻や乱数を内部で取得し、呼び出し側が結果を制御できない状態である。現在はその例外が残るため、`domain/` という配置だけでは作用がないことを保証しない。

## エラーと拒否

入力から生じうる失敗は値として返し、部分関数とパニックを通常の分岐に使わない。ドメインでは業務上成立しない状態を、ユースケースでは操作の拒否と作用の失敗を、アダプターでは外部入力の不正と外部向けエラー表現を扱う。

拒否は、拒否したという結果だけでなく、実行しなかった作用と組にして検証できるインターフェースを持つ。反している状態は、アダプターがエラーメッセージを解析して業務上の拒否を推測する状態、または失敗時に永続化や通知が起きたかを呼び出し側が確認できない状態である。

## 仕様に書ける振る舞い

設計は、外部から観測できる振る舞いを短い仕様で書き切れる形にする。仕様を短く書けない設計は、仕様を書き足すのではなく設計を直す。仕様に書いていない振る舞いを実装が生むと、その振る舞いは誰も決めないまま利用者に依存され、後から仕様の漏れとして見つかる。

| 指針 | 反している状態 |
| --- | --- |
| 同じ種類の操作（作成、更新、削除）は、経路が異なっても一つの共有の仕組みで検証、正規化、通知、記録する | 管理者による作成、CSV の適用、別のモジュールからの作成が、それぞれ別のコードで重複を判定し、結果が経路ごとに異なる |
| 値の正規化と比較は、値オブジェクトで一か所に定義する | ユーザー名の大文字と小文字の扱いが Aggregate ごとに異なる |
| 状態を変える操作は冪等にする。すでにその状態なら成功を返し、作用を起こさない | 同じ停止の要求を繰り返すたびに時刻が進み、イベントが重なる |
| 読み取りの操作に副作用を加えない | 一覧の取得が、期限を過ぎたデータの削除を兼ねる |
| 時刻の経過で起きる遷移は、その遷移を起こす主体（定期ジョブなど）を設ける | 期限を過ぎた状態が、たまたま別の操作が呼ばれるまで残る |
| 途中で失敗した操作は、再実行で完了できるようにする | 一部の作用だけが残った後、再実行しても何もせずに成功を返す |
| 順序と時刻に暗黙に依存しない | 結果の順序が map の反復順や並行処理の完了順で決まる |
