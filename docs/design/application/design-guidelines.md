# 設計ガイドライン

この文書は、モジュールの境界、依存の向き、アダプター、型と不変条件、一貫性の境界、作用、失敗を設計するときの判断の基準を定める。
各節は、守ること（原則）、守れているかの見分け方（判定基準）、そうする理由（根拠）の順に書く。
根拠が挙げる出典は、末尾の[出典](#出典)にまとめる。

ほかの文書との分担は次のとおりである。

| 内容 | 文書 |
| --- | --- |
| ディレクトリ、依存規則、公開範囲 | [バックエンド設計](backend.md) |
| モジュールごとの、代替案を比べた判断 | モジュールの `decisions.md` |
| コードから読み取れない仕組み | 設計領域の文書と、機能仕様の「実現方式」 |
| 現在のコードがこの基準から外れている箇所 | [リスクと技術的負債](../architecture/risks.md)と、モジュールの `risks.md` |

## モジュールの深さと情報隠蔽

### 原則

モジュールは、変わりうる設計判断を一つ内側に隠す。
呼び出し側が学ぶインターフェースは小さく、そこから得られる振る舞いは多くする。
ここでのインターフェースは、型のシグネチャのほか、不変条件、呼び出しの順序、エラー、必要な設定、性能の特性を含む。

### 判定基準

| 観点 | 守れている状態 | 反している状態 |
| --- | --- | --- |
| 深さ | 判断と変換がインターフェースの内側に集まり、呼び出し側は少し学ぶだけで多くの機能を使える | インターフェースと実装の複雑さがほぼ同じで、モジュールを消すと委譲が消えるだけで呼び出し側が単純になる |
| 隠蔽 | モジュールを消すと、隠していた複雑さが複数の呼び出し側に現れる | 呼び出し側が正しく使うために、内部の設計の文書を読む必要がある |

深さは、実装の行数や内部の文書の有無ではなく、学ぶインターフェースの量に対する振る舞いの量で測る。

### 根拠

変わりうる判断を一つのモジュールに閉じると、その判断を変えるときに直す場所と確かめる場所が一か所で済む。
変わりうる判断を隠すことを分割の基準にするのは Parnas の情報隠蔽、インターフェースの量に対する振る舞いの量で深さを測るのは Ousterhout の深いモジュールの考え方である。

## 境界を選ぶ判断手順

### 判断の三分類

設計で扱う値は、どう決まるかで三つに分かれる。
分類ごとに、誤りを見つける手段が異なる。

| 分類 | 決まり方 | 例 | 誤りの見つけ方 |
| --- | --- | --- | --- |
| 機械が抽出する事実 | ソース、仕様の識別子、Git の履歴から決まる。手で書き写さない | import の辺、SQL の書き込み先、要件の参照の解決結果 | 抽出の誤りは fixture で確かめ、抽出できない入力は診断として報告する |
| 検査される宣言 | 人またはエージェントが書き、検査が整合を判定する | 責務表の公開パッケージ、組み立て地点、テーブルの所有モジュール | 未宣言、重複、未知の参照、規則の違反を検査が拒否する。宣言の意味が正しいかはレビューで確かめる |
| 証拠を比べる判断 | 要件の意味、不変条件、変更シナリオ、事実から候補を選ぶ | 新しい処理の担当、公開する操作、依存の逆転、モジュールの分割と統合 | 入力、当てはまる制約、候補、採否、確かめていない仮定を作業項目に記録し、レビューする |

この手順が扱うのは三つ目の「証拠を比べる判断」である。
検査が示すのは宣言に適合していることであり、宣言を変えただけでは設計の問題は解決しない。
機械検査の入力となる欄を足すときは、その欄で検査の結果がどう変わるかも同時に定める。

### 原則

境界を守るのは[バックエンド設計](backend.md#モジュール間の依存規則)の検査であり、境界を選ぶのはこの手順である。
手順は、モジュールの追加、分割と統合、公開範囲の拡大、モジュール間の依存の追加、テーブルの所有者または組み立て地点の変更に適用する。
境界を変えない局所的な変更には適用しない。

次の順に入力をそろえ、候補を比べる。

1. 変える要件、不変条件、業務の概念と用語の適用範囲を、仕様の参照で特定する。
   要件 ID の接頭辞は現在の担当を探す入口として使い、担当を決める根拠にはしない。
2. 実行単位ごとに、配布先、更新する主体、バージョンがずれる期間、互換性を保つ公開契約を調べる。
   D1 より先に D9 を適用する。
   別々にビルドまたは起動するだけでは、独立した配布物とみなさない。
3. 状態と、それを更新する箇所を調べる。
   直接の SQL、ポート越しの更新、外部キーの cascade、トランザクションの開始と確定、イベントと通知の呼び出しを記録する。
   import の向きと、実行時に作用が流れる向きは別に扱う。
4. 隠す設計判断を具体的に挙げる。
   保存の表現、正規化の規則、外部プロトコルとの変換について、呼び出し側が知る必要のある条件と、内側に閉じられる条件を分ける。
5. 下の表の制約を当て、現状を保つ案と、必要な範囲で変える案を比べる。
   制約を満たす候補がなければ、宣言の変更やポートの追加で検査を通さず、要件と担当の見直しへ戻る。
6. 残った候補を変更シナリオで比べる。
   実際に起きた変更か、今回の要件が生む変化について、案ごとに変わる実装、利用側、契約、検証の範囲を挙げる。
   同じ保証を保つ候補の間では、公開する内部の知識と利用側への波及が少なく、不要なポート、型、設定を増やさない案を選ぶ。
7. 入力が足りない、利点が相反する、保証を変えうる未決事項が残る、のいずれかなら、候補と判断に要る問いを利用者へ示す。
   新しい業務概念の意味、原子性、認可の保証は、エージェントが推測で確定しない。

### 判定基準

| ID | 入力となる事実または要件 | 制約と候補の絞り込み |
| --- | --- | --- |
| D1 | 既存の一つの状態の所有者の責務を広げる | D9 を確かめた後、まずそのモジュールを候補にする。編成だけをする処理は、状態の更新と別に置いてよい |
| D2 | 所有者が異なる状態を更新する | 不変条件の検証と更新は各所有者に残す。編成する側には、必要な操作、拒否、作用の契約を公開する。保存型や任意の SQL の公開で代用しない |
| D3 | ほかのモジュールの非公開の処理が要る | 公開操作で表せるか、既存の公開操作の組み合わせで足りるか、そもそも担当が正しいかを比べる。非公開の関数をそのまま公開する案を最初の候補にしない |
| D4 | import が循環する | 操作を求める側が最小のポートを定義し、実装する側がそれを満たし、組み立て地点で結ぶ案を比べる。実行時の再入、作用の循環、失敗時の順序、原子性は別に確かめる |
| D5 | 複数のモジュールが同じ技術的な規則を使う | モジュールの型も業務の意味も必要としない場合に限り、共有ライブラリを候補にする。型名を文字列に変えただけでは条件を満たさない |
| D6 | 提供側の表現を利用側のポートへ変換する | 変換の意味は利用側が所有する。提供側を import する変換のアダプターは利用側に置くか、D4 のために組み立て地点に置く。依存の向きだけから意味の所有者を決めない |
| D7 | 複数の状態の一部だけが確定することを禁じる要件がある | 原子性を定める仕様と失敗の例を参照し、参加する更新、トランザクションの所有者、再試行、確定後の通知を示す。モジュールや Aggregate の数から原子性を決めない |
| D8 | モジュールを新しく作る、分割する、統合する | 隠す判断、状態と契約の担当、独立して変えたい変更シナリオを示す。import、SQL、作用の流れ、利用側への波及を比べる。履歴があれば、一緒に変わったファイルを補助に使う |
| D9 | 別々に配布、更新され、バージョンがずれる実行単位を、公開契約だけで結ぶ | 別のモジュールにし、公開契約の互換性を保って独立に更新できるようにする。相手のドメイン型、Repository、非公開の実装を import しない。契約から生成した型は、配布物ごとのアダプターで内部の表現へ変換する |

- D9 に当たるのは、利用者の環境へ配布する Connector のように、サーバーと同時に更新できない実行単位である。
  API、Worker、Batch のように同じリリースで更新するプロセスは、起動やスケールが別というだけでは分割しない。
  ローリング更新中のバージョンの混在は、内部の状態の互換性として別に確かめる。
- 新しいモジュールを作ることと、新しい一貫性の境界を作ることは別の判断である。
  同じトランザクションに参加するだけでモジュールを統合せず、import の循環をなくすだけでモジュールを分割しない。
- 履歴は、対象のパスを指定した `git log --first-parent --name-status` で、実際の変更の理由と利用側への波及を読む。
  同じコミットに入ったことは同じ変更の理由を示さないので、一緒に変わった回数を境界の合否に使わない。
- 判断は、境界に関わる作業項目の設計の節に記録する。
  記録するのは、入力の参照、適用した D1〜D9、候補ごとの制約への適合、変更シナリオの波及、採否と理由、残る仮定である。
  全モジュールの判断を、独立した台帳へ写さない。

依存を追加するときは、既存の負債台帳が許す範囲でもこの手順を適用する。
台帳に載っていることは、非公開の実装を呼ぶ判断や、共有ライブラリへ置く判断が妥当であることを示さない。
共有のコードを使う側が本番かテストかを調べ、型と変換の担当を特定したうえで、所有側での変換、利用側のポートへの適合、テスト専用の組み立てを D4〜D6 で比べる。
必要な変換を、委譲にすぎないとして削らない。

### モジュール間でのモデルの扱い

設計と実装の単位は Module に統一する。
各モジュールは、担当する[ドメインモデル](../../modules/glossary.md#モデルと実装の単位)、守る規則、公開する操作を定める。
Bounded Context による分類や、Module との対応表は設けない。
モデルと用語が同じ意味で通じる範囲は、各モジュールの設計で説明する。

ほかのモジュールのモデルとの関係は、次の三つから選ぶ。
関係の名前は、DDD の Context Map が使う名前に対応する。

| 関係 | 選ぶ条件と責任 | Context Map での名前 |
| --- | --- | --- |
| 相手のモデルを使う | 相手の意味と規則が自分の用途にも合う。相手の公開型と操作を使い、規則の変更と状態の更新は相手に任せる | Conformist、Customer/Supplier |
| 自分のモデルへ変換する | 同じ言葉でも、意味や状態の変わり方が異なる。外部の「削除」を内部の「利用停止」として受け付けるなど、対応の仕方は利用側が決める | Anti-Corruption Layer |
| モデルの一部を共同で管理する | 別々に変えるモデルの一部を、同じ意味と実装で保つ必要がある。共有する範囲、変更時の合意、双方の結合の検証、共有をやめる条件を定める。汎用の関数を共用することは含まず、状態の更新の所有者も増やさない | Shared Kernel |

使う相手のモデルと、その規則と状態の更新を担うモジュールは、利用側の `docs/modules/<module>/README.md` の「責務と境界」に書く。
モジュールの組ごとの関係は、[モジュールの間の依存](../../modules/README.md#モジュールの間の依存)の表に宣言する。

### 根拠

モジュールの境界は、モデルの適用範囲を確かめたうえで、隠す設計判断と変更シナリオで選ぶ。
同じモデルの管理と編成を別のモジュールに分けることもあり、モデルの境界だけでは実装の分割が決まらないためである。
別々に更新される配布物が内部の型を共有すると、片方の内部の変更が相手の更新も要求する。
配布物の境界を先に確かめ、通信に要る知識を公開契約に限れば、内部の表現を互換性の約束から切り離せる。

## 依存の向きと差し替え点

### 原則

ドメインとユースケースは外部の技術に依存せず、永続化、通知、外部サービスへはポートを通して依存する。
ポートは呼び出す側が定義し、アダプターが実装し、組み立て地点で結ぶ。

**差し替え点**（Seam）は、呼び出し側を変えずに実装を差し替えられるインターフェースであり、モジュールの境界とは別の概念である。
差し替え点は、二つ以上のアダプターまたは呼び出し方が同じ振る舞いを必要とした時点で設ける。

### 判定基準

| 観点 | 守れている状態 | 反している状態 |
| --- | --- | --- |
| 呼び出す先のポート | 永続化、通知、外部サービスなど、アプリケーションが呼び出す先をポートのインターフェースで表す | ユースケースがデータベースや外部 API のクライアントを直接使う |
| 呼び出される側のインターフェース | 呼び出し方や実装が実際に複数あり、具象のユースケースへの依存を切る必要がある場所にだけ置く | アダプターが一つしかない場所に、将来の差し替えだけを理由にインターフェースを足す |
| 共通の安全性条件 | 複数の用途が同じ安全性条件を必要とするとき、条件を一つの共通核に実装し、用途を閉じた集合として列挙する（例：[アクショントークン](backend.md#アクショントークン)） | 用途ごとに目的の束縛、有効期限、保存の表現を書き直し、新しい用途がそのどれかを書き忘れる |
| 必須の作用 | 仕様が求める保存、投入、イベント、監査の依存を、構築関数の必須の引数にし、構築時に欠けを拒否する | 省略できるフィールドや「nil なら省く」分岐で、呼び出し元ごとに必須の作用を外せる |

作用を省略してよいのは、その条件を仕様か公開契約が定める場合に限る。
Go では、nil のポインタをインターフェースに包むと nil との比較で未配線を判定できないので、組み立てる側で値の有無を確定してから渡す。
同じ操作の呼び出し元を追加するときは、既存の呼び出し元と、公開の経路、構築の条件、必須の作用を比べ、差があればその根拠を確かめる。
HTTP のアダプターが具象のユースケースを直接呼ぶ構成は、呼び出し方が一つである限りこの基準に反しない。

### 根拠

依存を内側へ向けると、外部の技術を替えても業務の判断が変わらず、業務の判断を外部の技術なしにテストできる。
内側へ向く依存は Martin の Clean Architecture、ポートとアダプターによる隔離は Cockburn の Hexagonal Architecture、差し替え点（Seam）の語は Feathers に倣う。
差し替えの必要が実際に生じてから差し替え点を設けるのは、使われないインターフェースが呼び出し側の学ぶ量だけを増やすためである。

## アダプターと表現

### 原則

アダプターは外部の表現と内部の表現を変換し、HTTP、SQL、外部プロトコルの規則をドメインとユースケースに持ち込まない。
入力の構文の検査、外部のエラーの形、永続化の形式の都合はアダプターが引き受け、ドメインは業務の意味を検証する。

### 判定基準

| 観点 | 守れている状態 | 反している状態 |
| --- | --- | --- |
| 型の共有 | 外部契約とドメインが同じ型を使うのは、JSON の形、SQL の NULL、外部プロトコルの省略の規則がドメインのインターフェースに現れない場合に限る。現れるならアダプター用の型を置いて変換する | 外部の形式を変えただけで、ドメインの型や呼び出し側を次々に直す必要が生じる |
| 一次情報 | 型を共有しても、外部契約の一次情報は TypeSpec のままである | 共有したドメインの型を、外部契約の一次情報として扱う |

### 根拠

外部の表現の変更をアダプターに閉じると、外部の契約とドメインの判断を別々に変えられる。
アダプターが変換を引き受ける構成は、Hexagonal Architecture のアダプターの役割に倣う。

## 型の所有と不変条件

### 原則

TypeSpec は、HTTP を含む外部境界の型、制約、エラー、認証方式の一次情報である。
ドメインの型は、内部の状態と操作の一次情報である。
ドメインの型を TypeSpec から生成せず、両者の対応はアダプターが取る。
不変条件は、成り立たせられる最も狭い場所で強制する。

### 判定基準

| 条件の種類 | 強制する場所 |
| --- | --- |
| 一つの値の妥当性、複数のフィールドの整合 | ドメインの型の構築と状態遷移 |
| 操作の後に成り立つ条件 | 事後条件 |
| 永続データの一意性と参照の整合 | データベースの制約 |
| 外部から観測できる保証 | 機能仕様の要件と `scenarios.feature.md` |

| 観点 | 守れている状態 | 反している状態 |
| --- | --- | --- |
| 別名の型と構築関数 | 値の取り違えを防ぐか、検証済みの表現を一つに決めるときに使う | すべての識別子を一律に別名の型にする |
| 条件の重複 | 一つの条件に一次情報が一つだけあり、ほかはそれを参照する | 同じ条件を TypeSpec、実装、SQL、文章に重ねて書き、変えるときにどれが一次情報か分からない |
| 複数の更新の入口 | すべての入口に共通の不変条件を所有者の公開操作で強制し、HTTP に固有のデコードと応答への変換だけをアダプターに残す | 管理 API だけが検査し、バッチや取り込みが保存型と Repository を直接使って検査を迂回する |

不変条件を足すか移すときは、同じ状態を更新する既存の入口を調べ、どれも所有者の同じ検査を通るかを確かめる。
import の向きが許されていることは、更新時の保証が守られている証拠にならない。

### 根拠

不変条件を構築と状態遷移で強制すると、不正な状態を作れる経路が減り、呼び出し側が事前条件を確かめる必要がなくなる。
事前条件、事後条件、不変条件で操作の約束を表すのは、Meyer の契約による設計に倣う。

## 一貫性の境界と永続化

### 原則

何を一つの Aggregate にまとめるかは、同時に変わるかではなく、**同時に正しくなければならないか**で決める。
一つのトランザクションで更新する範囲は、原子性を定める要件から決める（[境界を選ぶ判断手順](#境界を選ぶ判断手順)の D7）。
永続化のポートは Aggregate root ごとに置く。

### 判定基準

| 観点 | 守れている状態 | 反している状態 |
| --- | --- | --- |
| Aggregate の範囲 | 同時に正しくなければならない状態だけを一つにまとめる | 同時に変わるだけのものをまとめ、競合しない更新どうしが一つの境界の中で待たされる |
| トランザクションの範囲 | 複数の Aggregate を一つのトランザクションで変えるのは、片方だけが残った状態を外から観測されてはならない場合に限る。その判断と理由を、要件の判断の欄かモジュールの設計に書く | モジュールや Aggregate の数から原子性を決める |
| 同時の更新 | Aggregate の一部の値だけを記録する処理と自動の状態遷移は、[同時の更新と排他](../data/database.md#同時の更新と排他)の形で書く | 先に読んだ Aggregate を、外部への取得の後や別のモジュールから丸ごと保存し、その間の無効化や編集を書き戻す |
| ポートの粒度 | 一つの永続化のポートが一つの root を扱い、どの操作がどの一貫性の境界に属するかをインターフェースから読める | 一つのポートが複数の root を扱い、境界を知るために実装を読む必要がある |
| ポートの名前 | ポートが Aggregate を扱うかは、保存する型、不変条件、仕様で判断する | 名前の接尾辞（`Repository`、`Store`）から推測する |

複数の状態を一つのトランザクションで確定する保証は、その保証を必要とする機能仕様の「信頼性」または「実現方式」に、片方だけが残ったときに何が起きるかとともに書く。
複数の公開操作を一つにまとめても、それだけでは原子性は増えない。
ポートをまたぐ操作は保存先ごとに確定し、途中の失敗は冪等な再実行で回収する。

### 根拠

一貫性の境界を「同時に正しくなければならないもの」に絞ると、境界の中では不変条件が常に成り立ち、境界の外の整合は結果整合として明示的に組める。
Aggregate の語と、外からは root の識別子で参照する形は、Evans の *Domain-Driven Design* に倣う。

## 作用の境界

### 原則

ユースケースは、永続化、通知、時刻、乱数、識別子の生成、設定などの作用を編成し、計算には値またはポートとして渡す。
計算は作用を自分で作らず、同じ入力から同じ結果を返す。

### 判定基準

| 観点 | 守れている状態 | 反している状態 |
| --- | --- | --- |
| 計算の決定性 | ドメインの計算が作用を内部で作らず、同じ入力から同じ判断を再現できる | ドメインの計算が現在時刻や乱数を内部で取得し、呼び出し側が結果を制御できない |
| 保証の根拠 | 作用がないことを、計算の入力と出力の型で確かめる | `domain/` に置いたことだけから、作用がないと仮定する |
| ゼロ値の意味 | ゼロ値を省略として扱う条件を仕様か公開契約で定め、時刻などの補完は作用を編成する側で行う | 本番では届かない入力の補完をドメインに置き、その分岐をテストだけで固定する |
| ストレージの時刻 | ストレージのアダプター（`db_memory`、`db_postgres`）は、期限の判定にも時刻の記録にも、ポートの引数で受け取った時刻を使う。SQL の `now()` は `SET` と `VALUES` で記録する値にだけ使う | 呼び出し側が判定の時刻を持つのに、アダプターが実時計や SQL の `now()` と期限を比べ、固定の時刻を渡すテストが日付の進みで失敗する |

### 根拠

作用を計算の外に置くと、時刻や乱数を差し替えずに判断を再現でき、テストはインターフェースを通して振る舞いを確かめられる。
計算を内側に、作用の編成を外側に置く構成は、Bernhardt の Functional Core, Imperative Shell に倣う。

## 失敗の表し方

### 原則

操作が成功しない場合は、次の三つに分かれる。

| 種類 | 意味 | 例 |
| --- | --- | --- |
| 入力の不正 | 要求の形が契約に合わない | 必須の項目がない、値の形式が違う |
| 規則による拒否 | 要求の形は正しいが、業務の規則または認可により、操作を実行しないと判断した | 権限がない、名前が重複する、今の状態からその遷移はできない |
| 作用の失敗 | 操作を実行しようとしたが、保存や外部の呼び出しが失敗した | データベースへの接続が切れた、外部のサービスが応答しない |

入力から起こりうる失敗は値として返し、パニックを通常の分岐に使わない。
入力の不正はアダプターが、規則による拒否はドメインとユースケースが、作用の失敗はユースケースが扱う。
外部へ返すエラーの形への変換はアダプターが行う。

### 判定基準

| 観点 | 守れている状態 | 反している状態 |
| --- | --- | --- |
| 拒否の後の作用 | 拒否したことと、保存や通知が起きなかったことを組にしてテストで確かめられる | 拒否したときに保存や通知が起きたかを、呼び出し側が確かめられない |
| 拒否の判別 | 規則による拒否を、型または値で判別できる | アダプターがエラーメッセージの文字列を解析して、拒否の種類を推測する |

### 根拠

失敗を種類ごとに値として返すと、どの失敗がどの層の責任かが型に現れ、拒否の後に作用が残らないことをテストで確かめられる。
規則による拒否と作用の失敗を混ぜると、利用者に直してほしい要求と、再試行すれば通る障害を区別できなくなる。

## 仕様に書ける振る舞い

### 原則

外から観測できる振る舞いを、短い仕様で書き切れる設計にする。
仕様が短く書けないときは、仕様を書き足すのではなく設計を直す。

### 判定基準

| 指針 | 反している状態 |
| --- | --- |
| 同じ種類の操作（作成、更新、削除）は、経路が違っても一つの仕組みで検証、正規化、通知、記録する | 管理者の作成、CSV の取り込み、別のモジュールからの作成が別々のコードで重複を判定し、経路ごとに結果が違う |
| 値の正規化と比較は、値オブジェクトで一か所に定義する | ユーザー名の大文字と小文字の扱いが Aggregate ごとに違う |
| 状態を変える操作は冪等にする。すでにその状態なら、作用を起こさずに成功を返す | 同じ停止の要求を繰り返すたびに時刻が進み、イベントが重なる |
| 読み取りの操作に副作用を加えない | 一覧の取得が、期限切れのデータの削除を兼ねる |
| 時刻の経過で起きる遷移には、それを起こす主体（定期ジョブなど）を設ける | 期限を過ぎた状態が、たまたま別の操作が呼ばれるまで残る |
| 途中で失敗した操作は、再実行で完了できるようにする | 一部の作用だけが残った後、再実行しても何もせずに成功を返す |
| 順序と時刻に暗黙に依存しない | 結果の順序が、map の反復の順や並行処理の完了の順で決まる |

### 根拠

仕様にない振る舞いを実装が生むと、誰も決めないまま利用者がそれに依存し、後から仕様の漏れとして見つかる。
経路ごとに振る舞いが違えば、その差の分だけ仕様が長くなる。
経路をまとめると、仕様、実装、テストのどれも短くなる。
