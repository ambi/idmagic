# データライフサイクル設計

この文書は、一つのデータがシステムに入ってから消えるまでを、Context とテーブルを横断して見たときにだけ現れる設計を扱う。
個々の保持期間の値と、個々のテーブルの削除規則は扱わない。
それらは各 Context の `standards.md` と `decisions.md`、[品質要求](../../requirements/quality.md)が定め、テーブルの意味は[データベース設計](database.md)が説明する。

## データの区分と消え方

データは、消え方の違いで次の五つに分かれる。
同じ「削除」でも、区分によって消えた後に何が残るかが違う。

| 区分 | 代表的なテーブル | 消え方 | 消えた後に残るもの |
| --- | --- | --- | --- |
| 業務データ | `users`、`groups`、`applications`、`oauth2_clients` | 管理操作で消える。利用者だけは猶予期間を経て匿名化する | 匿名化した利用者の行と識別子 |
| 短命な認証状態 | 認可コード、チャレンジ、再送検知、流量制御の回数 | `expires_at` を過ぎた時点で無効になり、掃除で行が消える | なし |
| 監査イベント | `audit_events`、`authentication_event_buckets` | 種別ごとの保持期間を過ぎたものだけが一括で消える | 保持期間内の記録 |
| 鍵素材 | `signing_keys`、`tenant_data_encryption_keys` | 世代交代で退役し、DEK は鍵素材だけを破棄する | バージョンとライフサイクルの履歴 |
| 資産 | `tenant_branding_assets`、`application_icons`、`csv_artifacts` | 設定の置き換えや親の削除で消える | 親が残る限り、置き換えられていない資産 |

短命な認証状態では、有効かどうかを読み取り時に `expires_at` で判定する。
掃除が遅れても有効期間は延びず、掃除は保存容量のためだけに行う。

監査イベントは、削除やアーカイブのインターフェースを提供しない（[Audit Context の判断](../../contexts/audit/decisions.md)）。
保持期間を過ぎたものの一括削除だけが、監査イベントを消す経路である。

資産のうち `csv_artifacts` は、インポートが完了しても消える経路がない。
CSV の入力には利用者の個人識別情報が含まれるため、[削除と匿名化](#削除と匿名化の使い分け)が利用者の行を匿名化しても、成果物の中に元の値が残る。

## 削除と匿名化の使い分け

行を物理的に消すか、行を残して個人識別情報だけを書き換えるかは、**その行が監査イベントの主体として参照される個人か**で決まる。

| 条件 | 選ぶ方法 | 例 |
| --- | --- | --- |
| 個人識別情報を含み、監査イベントが行為者や対象として識別子を参照する | 匿名化する。識別子は永久に残し、再利用しない | 利用者（`sub`） |
| 個人識別情報を含まない | 物理的に削除する | グループ |
| 利用者に従属する資格情報、セッション、同意 | 利用者の匿名化と同時に物理的に削除する | パスワード履歴、MFA 要素、WebAuthn 資格情報、回復コード、信頼済み端末、セッション、同意、リフレッシュトークン、デバイスコード、承認要求 |

利用者を物理的に削除しないのは、監査イベントの `sub` が指す先を失うと「誰が何をいつ行ったか」を再構成できなくなり、「削除済み」と「停止中」の区別も消えるからである。
グループは監査イベントから参照されても、指す先の行が消えるだけで個人の情報は残らないので、匿名化を必要としない。
利用者の削除は、猶予期間のある `PendingDeletion` を経て `Deleted` へ進む（[IdManagement の状態遷移](../../contexts/identity-management/states.md)）。
消去が満たすべき規範は [`GDPR-ERASURE`](../../standards.md) が定める。

## テナントの退去

現在、テナントの物理削除は提供していない（[Tenancy の状態遷移](../../contexts/tenancy/states.md)）。
テナントを退去させる手段は無効化だけであり、無効化してもテナントのデータはすべて残る。

テナントの物理削除を設計するときは、スキーマの次の性質が順序を決める。

| 性質 | 帰結 |
| --- | --- |
| 設定、短命な状態、従属する行のテーブルは、`ON DELETE CASCADE` の外部キーで `tenants` を参照する | `tenants` の行を消すと、それらのテーブルの行も同じトランザクションで消える |
| 利用者、グループ、エージェント、アプリケーション、クライアント、ジョブ、署名鍵、DEK などのテーブルは、`ON DELETE RESTRICT` の外部キーで `tenants` を参照する | それらの行が一つでも残っている間は、`tenants` の行を消せない |
| 監査イベント、その検索属性、相関用ソルトのテーブルは、外部キーで `tenants` を参照しない | `tenants` の行を消しても残り、それぞれの保持期間に従って消える |
| 可逆な秘密情報は、テナントの DEK で暗号化している | DEK を破棄すれば、行を消す前でも秘密情報は読めなくなる |

`RESTRICT` で参照するテーブルの行は、`tenants` の行より先に、所有する Context が消しておく必要がある。
このため、退去は無効化、DEK の破棄、各 Context による行の削除、`tenants` の行の削除の順に進めることになる（仮）。
DEK の破棄を行の削除より先に置くのは、削除の途中で止まっても秘密情報が読めない状態にしておくためである。
監査イベントは法的な保持義務の根拠なので、テナントの削除と同時には消さない（仮）。

## 暗号学的消去

DEK を破棄すると、`tenant_data_encryption_keys` の行は残り、`wrapped_dek` だけが `NULL` になる（[データベース設計](database.md#可逆な秘密情報のエンベロープ暗号)）。
その結果、そのバージョンの DEK で暗号化した値は二度と復号できなくなる。

現在 DEK で暗号化しているのは、MFA 要素のシークレットと外部 IdP 接続のシークレットだけである。
利用者の属性やメールアドレスなどの個人識別情報は DEK で暗号化していないので、DEK の破棄はそれらを消さない。
暗号学的消去は秘密情報を無効にする手段であり、テナントのデータ全体を消去する手段ではない。

## バックアップとの相互作用

バックアップは取得した時点のデータを保持するので、その後に行った削除を知らない。
取得より後に消去した利用者や破棄した DEK は、そのバックアップから復元すると消去前の状態で戻る。
DEK については、マスター鍵が残っている限り、戻った `wrapped_dek` を再びアンラップできる。

| 戻るもの | 結果 |
| --- | --- |
| 匿名化より前の利用者の行 | 消去した個人識別情報が再び読める |
| 物理的に削除した資格情報とセッション | 消去済みの利用者の資格情報が再び存在する |
| 破棄より前の `wrapped_dek` | 暗号学的に消去した秘密情報が再び復号できる |

この問題の扱いは二つの組み合わせになる。
一つは、バックアップの保持期間を、`GDPR-ERASURE` が求める消去の期限の内側に収めることである。
保持期間を過ぎたバックアップが消えれば、消去前のデータもいずれ消える。
もう一つは、復元した後に、復元時点より後に行った消去をもう一度適用することである。

現在は、どちらも決まっていない。
バックアップの保持期間は未確定であり（[復旧設計](../reliability/recovery.md)）、復元後に消去を再適用する仕組みはない。
復元の手順は、再生成できる短命なテーブルを空にするが、消去の再適用は行わない。

## 保持期間を変えるときの順序

保持期間は、保存容量、プライバシー、復旧に同時に影響する。
延ばせば保存容量の見積もりが変わり、消去の期限までにデータが消えなくなることがあり、短くすれば復元や調査で遡れる範囲が狭まる。

このため、保持期間は次の順で変える。

1. 対象 Context の `standards.md` または `decisions.md` と、[品質要求](../../requirements/quality.md)の値を変える。
2. [キャパシティ設計](../performance/capacity.md)の見積もりを、新しい値で見直す。
3. 一括削除の実装を、新しい値へ合わせる。
4. バックアップの保持期間が、新しい値と消去の期限の両方と矛盾しないことを確かめる。
