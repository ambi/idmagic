# スキーマ管理

この文書は、PostgreSQL の構造をどう宣言し、どう変え、どこで適用するかを定める。
読み手は、スキーマを変える開発者と、それをデプロイする運用者である。
テーブルの意味と型の選び方は[データベース設計](database.md)が、コマンドと実行順は [`infra/schema/README.md`](../../../infra/schema/README.md) が説明する。

## 宣言的スキーマ

`infra/schema/postgres.sql` は、マイグレーションの積み上げではなく現在の構造を宣言する。
既存のデータベースとの差分は、適用時に `psqldef` が計算する。

マイグレーションを積み上げないのは、積み上げた結果と実際のデータベースが一致していることを、誰も確かめられないからである。
積み上げ方式では、現在の構造を知るために全マイグレーションを頭の中で再生する必要があり、途中で手作業の修正が入った環境との乖離は残り続ける。
宣言方式では、現在の構造が一つのファイルで読め、どの環境でも「ファイルと一致しているか」を `psqldef` のプレビューで確かめられる。

| 置くもの | 置く場所 | 理由 |
| --- | --- | --- |
| テーブル、列、索引、制約 | `postgres.sql` | 現在の構造の正本である |
| デフォルトテナントなどの必須の行 | アプリケーションが起動時に収束させる | 構造差分の計算に行の有無を混ぜない |
| 既存の行の変換、バックフィル、改名 | `infra/schema/data-migrations/` | 構造差分では表現できない（[構造差分で表現できない変更](#構造差分で表現できない変更)） |
| 構造を選んだ理由 | [データベース設計](database.md)とこの文書 | DDL の中の説明は、正本の設計から離れても検出できない |

## 収束の検査

スキーマの正しさは、二つの時点で別々のことを確かめる。

| 時点 | 確かめること | 方法 |
| --- | --- | --- |
| 変更をマージする前（CI） | `postgres.sql` が空のデータベースに対して収束する | `mise run check-schema` が、適用、プレビュー、再適用、プレビューの順に実行し、二度のプレビューが空であることを求める |
| 環境へ適用するとき | その環境のデータベースに対する差分が、意図した変更だけである | 適用前のプレビューを人がレビューし、適用後の `--check` が保留中の DDL なしを返すことを求める |

CI の検査は、`psqldef` の不具合でファイル自体が収束しない状態（再適用のたびに DDL が出る状態）を捕まえる。
一回のプレビューを人が読むだけでは、対応する追加を伴わない暗黙の `DROP CONSTRAINT` のような差分を見落としやすいからである。

一方、CI は直前のリリースのスキーマから新しいスキーマへの差分を検査しない。
破壊的な差分や長時間のロックを取る差分は、環境へ適用する前のプレビューのレビューで止める。

## 拡張と縮小

ローリング更新の途中では、新旧のアプリケーションが同じデータベースを読み書きする（[デプロイの不変条件](../../architecture/deployment.md#デプロイの不変条件)）。
このため、片方のバージョンしか解釈できない形へ一度に変えることはできず、構造の変更は次の四段階に分ける。

| 段階 | 行うこと | 新旧が同時に動く間に守られること | 後退できる範囲 |
| --- | --- | --- | --- |
| 1. 拡張 | 新しいテーブルや列を、`NULL` 許容またはデフォルト値付きで追加する | 旧バージョンは追加された形を読まず、書き込みも失敗しない | アプリケーションを戻すだけでよい。追加した形は残してよい |
| 2. 書き込みの移行 | 新バージョンが新旧両方の形へ書く | 旧形がまだ正本なので、旧バージョンの読み出しは正しい | 旧バージョンへ戻せる |
| 3. 読み出しの移行 | 既存の行をバックフィルし、新バージョンが新しい形から読む | 両方の形へ書き続けているので、どちらのバージョンが読んでも同じ値になる | 両方への書き込みが続いている間は旧バージョンへ戻せる |
| 4. 縮小 | 次のリリースで、旧い形への書き込みと旧い形そのものを消す | 旧バージョンはもう動いていない | 戻せない。消した列のデータは失われる |

四段階が必要になるのは、次のように旧バージョンが解釈できない形を作る変更である。

- テーブルや列の改名、列の型の変更
- 既存の行があるテーブルへの `NOT NULL` の追加、`CHECK` の許容値の縮小
- テーブルや列の削除

新しいテーブルや `NULL` 許容の列の追加だけで済む変更は、段階 1 で完了する。
縮小の段階だけは、プレビューに `DROP` が現れ、`--enable-drop` を付けて適用する必要がある。
自動化されたデプロイは `--enable-drop` を付けないので、縮小は人が承認した適用として行う。

## 構造差分で表現できない変更

`psqldef` は望ましい構造と現在の構造を比べるだけなので、行の値と改名を扱えない。
たとえばテーブルを改名すると、`psqldef` は古いテーブルの `DROP` と新しいテーブルの `CREATE` を出し、保存済みの行を失う。
こうした変更は、`infra/schema/data-migrations/` に一回限りの SQL として置く。

| 項目 | 規則 |
| --- | --- |
| ファイル名 | `YYYY-MM-DD-<変更内容>.sql` とし、日付の順に実行する |
| 実行する時点 | スキーマ適用の前か後かを、ファイル冒頭のコメントに書く。許容値を狭める変更や改名は、スキーマ適用の前に実行する |
| 冪等性 | 何度実行しても結果が同じになるように書く。二度目の実行は何も変えない |
| 後退 | 逆向きに戻せるか、戻せないならその理由を、ファイル冒頭のコメントに書く |
| 失敗時 | スキーマ適用へ進まない。冪等なので、原因を取り除いてから同じファイルを再実行する |

現在、データ移行をデプロイ工程から自動で実行する仕組みはない。
運用者が、リリースに含まれるデータ移行をスキーマ適用の前後に実行する。
後退するかどうかは、そのリリースの DDL を承認した者が、上の四段階の表に書かれた後退の範囲をもとに判断する。

## 適用する地点

スキーマは、デプロイ工程で新しい `idmagic-api` を動かす前に適用し、アプリケーションの起動時には適用しない。
起動時に適用すると、同時に起動した複数のレプリカが同じ DDL を並行して実行するうえ、アプリケーションの接続ロールに DDL の権限を与えることになるからである。

一つのリリースでの順序は次のとおりである。

1. スキーマ適用の前に実行するデータ移行を実行する。
2. 適用前のプレビューを出し、差分をレビューする。
3. スキーマを適用し、`--check` が保留中の DDL なしを返すことを確かめる。
4. スキーマ適用の後に実行するデータ移行を実行する。
5. 新しいアプリケーションを動かす。

デプロイプロファイルごとに誰が適用を実行するかは、[プラットフォーム設計](../infrastructure/platform.md#スキーマ適用と初期データ投入)が定める。

復元では、空のデータベースへ `postgres.sql` を適用してから、バックアップのデータだけを戻す（[復旧設計](../reliability/recovery.md)）。
データだけを戻すので、適用する `postgres.sql` はバックアップを取得したリリースのものでなければならない。
新しいリリースのスキーマへ古いデータを戻すと、追加された `NOT NULL` の列が値を受け取れずに復元が失敗したり、データ移行を経ていない値が制約に違反したりすることがある。
現在の復元スクリプトは、このバージョンの一致を確かめない。

## `psqldef` の性質から来る規則

次の規則は、SQL として正しくても `psqldef` の差分計算を壊す書き方を避けるためにある。
破ったときの多くは `mise run check-schema` が検出するが、検査は規則の代わりにはならない。

| 規則 | 理由 |
| --- | --- |
| 同じ列への `CHECK` は一つの制約にまとめる | 二つ並べると差分が収束しない |
| 複数列を対象とする制約には、PostgreSQL のデフォルト名（`<table>_<column>_key`、`<table>_<column>_check`）と衝突しない明示名を付ける | 衝突すると `psqldef` が制約を自動生成とみなし、再適用のときに対応する追加なしで削除する |
| `CHECK (col IN (...))` の値はアルファベット順に並べる | 順序だけが違う制約の作り直しを出さず、プレビューを実際の変更の信号に保つ |
| PostgreSQL の列挙型を使わない | 値の追加に `ALTER TYPE` が必要で、宣言的な差分計算と合わない |
| テーブルと列の改名は、データ移行で先に行う | `psqldef` は改名を検出できず、削除と作成として扱う |
| 自動化されたデプロイで `--enable-drop` を使わない | 破壊的な変更を、人のレビューなしに流さない |
| CI、開発環境、デプロイで `psqldef` のバージョンを固定する | バージョンによって生成する差分が変わり、CI で確かめた収束が本番で成り立たなくなる |
