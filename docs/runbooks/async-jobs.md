# 非同期ジョブのランブック

## 概要

IdMagic の長時間処理（利用者の一括取り込み、動的グループの再計算、ライフサイクルワークフローの実行、データ暗号鍵の再暗号化など）は、PostgreSQL 上の永続キューに積まれ、`idmagic-worker` プロセスが取り出して実行します。API プロセスはジョブを投入するだけで実行せず、`worker` はジョブを実行するだけで HTTP を提供しません。

キューへ仕事を積む HTTP のエンドポイントはありません。管理 API が提供するのは参照と取り消しだけです。再試行、再実行、強制完了は提供しません。いずれも副作用をもう一度起こす操作であり、ハンドラーが保証する冪等性の外側から引き金を引くことになるためです。

## 実行レーン

ジョブの種別（`JobKind`）は、登録の時点でちょうど 1 つの実行レーンに固定されます。投入する側はレーンを選べません。

| レーン | 用途 |
|---|---|
| `latency_sensitive` | 遅延がそのまま利用者の待ち時間になる配信処理 |
| `default` | 上のどちらでもない処理 |
| `bulk` | 長時間かつ大量の処理。一括取り込みや再暗号化 |

レーンが与えるのは順序ではなく容量の隔離です。`bulk` にどれだけ滞留しても、`latency_sensitive` の実行枠を奪うことはありません。本番では `infra/k8s/base/worker.yaml` が定義する `idmagic-worker-{latency-sensitive,default,bulk}` の 3 つの Deployment を並べ、それぞれ `JOB_WORKER_LANES` で 1 レーンに固定します。

## worker の起動と設定

`worker` は次の環境変数で調整します。既定値と完全な一覧は [CONFIGURATION.md](../../CONFIGURATION.md) が持ちます。

| 変数 | 意味 |
|---|---|
| `JOB_WORKER_LANES` | このプロセスが取得するレーン。本番は 1 つだけ指定します |
| `JOB_WORKER_CONCURRENCY` | レーンごとの並行実行数。レーン別の上書きもできます |
| `JOB_POLL_INTERVAL` | 取得を試みる間隔 |
| `JOB_LEASE_DURATION` | 取得したジョブに対して保持するリースの長さ |
| `JOB_BACKOFF_BASE` / `JOB_BACKOFF_CAP` | 失敗後の再試行までの待ち時間と、その上限 |
| `DRAIN_GRACE_PERIOD_SECONDS` | SIGTERM を受けてから実行中のジョブを待つ秒数 |

Kubernetes への適用は `mise run deploy-k8s` で行います。

## スケール

レーンごとに独立した Deployment なので、滞留しているレーンだけを増やします。

```
kubectl scale deployment/idmagic-worker-bulk --replicas=6
```

同時実行数を増やす方法もありますが、まずレプリカ数で調整してください。並行数を上げるとプロセスあたりのデータベース接続も増え、滞留の原因がデータベース側にある場合は事態を悪化させます。

滞留しているレーンは `jobs_queue_depth{status="queued"}` で判断します。実行中の件数は同じ指標の `status="running"` です。

## 停止と退避

SIGTERM または SIGINT を受けると、`worker` は新しいジョブの取得をやめ、実行中のハンドラーが終わるのを `DRAIN_GRACE_PERIOD_SECONDS` まで待ちます。猶予を過ぎると、実行中のジョブを残したまま終了します。

このとき残ったジョブは失われません。リースが自然に期限切れになると、別の `worker` が同じジョブを取り直します。**明示的な再投入はしないでください。** 停止処理の打ち切りとハンドラーの完了は競合しうるので、再投入は二重実行の余地を作ります。

Kubernetes の `terminationGracePeriodSeconds` は `DRAIN_GRACE_PERIOD_SECONDS` より長くしてください。逆だと、退避の途中で SIGKILL が届きます。

## ジョブを確認する

管理コンソールの「ジョブ」画面、または管理 API で確認します。

```
GET  /api/admin/v1/jobs?status=failed&lane=bulk
GET  /api/admin/v1/jobs/{job_id}
POST /api/admin/v1/jobs/{job_id}/cancel
```

参照には `jobs:read`、取り消しには `jobs:cancel` のスコープが必要です。ブラウザーのセッションで呼ぶ場合は `admin` ロールを要します。

参照できるのは自テナントのジョブだけです。全テナント横断は、`system_admin` ロールを持つ利用者が制御面（default）テナントの経路から `all_tenants=true` を明示した場合に限られます。

**応答には `params`、`result`、`dedup_key` は含まれません。** どれも投入した Context が意味を決める不透明な値で、Jobs は中身を検証しません。検証していない値を管理画面へ流すと、個人情報が混ざっていないことを主張できないまま公開することになります。ハンドラーへの入力そのものを見る必要がある場合は、投入した機能の側の画面か、その機能が残す監査イベントを見てください。

## 失敗したジョブを調べる

1. **配信不能を洗い出す。** 一覧を `status=failed` で絞ります。ここに並ぶのは、試行上限に達して確定したものだけです。再試行の途中で一時的に失敗しているジョブは `queued` のまま、`run_at` が未来に置かれています。
2. **失敗理由を読む。** 詳細画面の `error` に、ハンドラーが最後に報告した内容が入ります。`attempts` と `max_attempts` から、何回試して確定したかが分かります。
3. **範囲を判断する。** 同じ `kind` の失敗が一斉に増えているなら、そのハンドラーが依存する外部（SCIM の宛先、SMTP、鍵の提供元）を先に疑います。単発なら、その 1 件の入力を疑います。
4. **監査ログを引く。** ジョブの id で監査イベントを検索すると、`JobStarted` / `JobFailed` / `JobRetried` の連なりが読めます。`JobFailed` は試行ごとの理由を保持します。
5. **再実行が必要なら、投入元からやり直す。** 管理 API に再試行はありません。取り込みなら取り込みをもう一度実行する、というように、その仕事を要求した業務操作の側から投入し直してください。冪等性は `dedup_key` とハンドラー自身が担保します。

## ジョブを取り消す

終端に達していない（`queued` または `running` の）ジョブだけを取り消せます。

実行中のジョブを取り消しても、**ハンドラーはその場では止まりません。** 取り消しがリースを外すので、次のハートビートか完了報告が失敗し、ハンドラー自身が処理をやめます。したがって、取り消しから実際に処理が止まるまでには最大でハートビート 1 回分の間隔があります。**すでに確定した副作用は元に戻りません。** 半分だけ書き込まれた状態が残りうることを前提に、取り消した後の整合性は投入元の機能の側で確認してください。

すでに終端に達したジョブの取り消しは、成功として黙認せず `409` で拒否します。止めるよう頼んだ運用者にとって、すでに終わっていたのか止まったのかは別の事実だからです。

## 監視

`worker` は API プロセスとは別の `/metrics` を公開します（管理専用のリスナー）。

| 指標 | 読み方 |
|---|---|
| `jobs_queue_depth{lane,status}` | レーンごとの滞留（`queued`）と実行中（`running`）の件数 |
| `jobs_claim_latency_seconds{lane}` | `run_at` を過ぎてから取得されるまでの待ち時間 |
| `jobs_duration_seconds{lane,outcome}` | ハンドラーが 1 回の試行に要した時間 |
| `jobs_outcome_total{lane,outcome}` | 確定した成否の件数。`outcome="failed"` は配信不能の件数 |
| `jobs_retry_total{lane}` | 再試行へ戻した回数 |

待ち時間と実行時間は別の指標です。片方だけを見ても、遅いのが滞留なのか処理そのものなのかを分けられません。待ち時間が長く実行時間が短ければ実行枠が足りず、逆なら処理そのものかその依存先が遅い、という読み方をします。

ラベルに `tenant_id` や `job_id` は載りません。値の種類に上限がないためです。個々のジョブを追うときはメトリクスではなく、構造化ログと管理 API を使ってください。配信不能の確定は `jobs: job dead-lettered` として `job_id`、`tenant_id`、`kind`、`lane`、`attempts` とともにログに残ります。

既定のアラートは `infra/k8s/monitoring/prometheus-rule.yaml` にあります。`latency_sensitive` の取得遅延、失敗率、滞留件数を見ています。

## 保持期間

ジョブの記録は 30 日で削除されます。それより古い失敗を追う必要がある場合は、ジョブそのものではなく監査イベント（追記のみ、7 年保持）を参照してください。
