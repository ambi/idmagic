# 制御面の運用者の MFA の復旧手順書

## 概要

システムコンソールとシステム API は、`system_admin` の運用者に MFA で成立した認証を求める。
MFA の端末と復旧コードの両方を失った運用者は、システムコンソールへ入れない。
この手順書は、デフォルトのテナント（制御面のテナント）の管理者による認証器のリセットから、運用者が MFA の認証を取り戻すまでを扱う。

認証器のリセットは、デフォルトのテナントの `admin` ロールを持つ利用者だけが行える。
`system_admin` だけでは行えない。

## 予防

復旧の手段が成り立つかは、構成で決まる。運用を始める前に次を満たす。

- デフォルトのテナントに、`admin` ロールを持つ利用者を二人以上置く。一人が MFA を失っても、もう一人がリセットできる。
- 運用者は、登録のときに表示される復旧コードを、端末とは別の場所に保管する。復旧コードは MFA の要素として数えるので、端末を失っても入れる。
- 端末を二つ以上（TOTP と WebAuthn、または複数の WebAuthn）登録する。

## 復旧の手順

### 別の管理者がリセットする

運用者が `system_admin` だけを持つ場合、またはデフォルトのテナントのサインインポリシーが IdMagic 自身の画面に MFA を求める場合は、この手順を使う。

1. 別の管理者が、デフォルトのテナントの管理画面（`/admin`）の利用者の一覧から運用者を開き、「認証器をリセット」で TOTP、WebAuthn、復旧コードをすべて選んでリセットする。
2. リセットの応答が `reenrollment_required` を示し、登録の許可が一度だけ発行される。
3. 運用者がパスワードでログインする。デフォルトのポリシーが MFA を求めていれば、ログインは再登録の画面へ進む。新しい TOTP を登録すると、元の画面へ戻る。
4. デフォルトのポリシーが MFA を求めていない場合は、ログインは再登録を求めずに完了する。運用者はアカウントの画面（`/account/security`）で新しい TOTP を登録する。
5. 運用者がシステムコンソールを開く。システムコンソールが MFA の水準を求める再認可を行い、新しい TOTP を求められる。入力すると MFA で成立した認証になる。
6. 新しい復旧コードを生成して保管する。

### 自分でリセットする

運用者が `admin` も持ち、デフォルトのテナントのサインインポリシーが IdMagic 自身の画面に MFA を求めていない場合は、自分でリセットできる。

1. 運用者がパスワードでデフォルトのテナントの管理画面へ入る。
2. 利用者の一覧から自分を開き、「認証器をリセット」ですべての要素をリセットする。
3. 上の手順の 4 から 6 を行う。

## 復旧できない構成

次の構成では、現在の仕組みで復旧できない。予防の項を満たして避ける。

- デフォルトのテナントで `admin` を持つ利用者が、MFA を失った運用者自身だけであり、デフォルトのサインインポリシーが IdMagic 自身の画面に MFA を求めている。運用者は管理画面へ入れず、ほかにリセットできる人もいない。
- デフォルトのテナントに `admin` を持つ利用者がいない。

この状態から戻すには、データベースへの直接の操作が要る。手順は定めていない。

## 確認事項

- 復旧の後、運用者のアカウントの画面のセッションの一覧で、現在のセッションの認証の方式に `otp` が含まれる。
- システムコンソールで、テナントの一覧が表示される。
- 監査イベントに、`AuthenticatorResetRequested`、`AuthenticatorResetCompleted`、`MfaEnrollmentBypassIssued` が残る。
