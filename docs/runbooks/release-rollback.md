# リリースの後退

## 着手条件

段階的な展開中または展開後に、次のいずれかが成立したらこの runbook を開始する。

- 新しいレプリカの `/startupz` または `/readyz` が 5 分間成功しない。
- `TokenErrorRateBudgetBurn`、`TokenLatencyBudgetBurn`、`LoginErrorRateBudgetBurn`、`LoginLatencyBudgetBurn`、`JobsFailureRatioBudgetBurn` のいずれかが新しいリリース後に発火する。
- テナント境界、認証、認可、署名、再送防止が破られた事象を 1 件確認する。この場合は観測窓を待たず、直ちに展開を止める。
- 新しいリリース後にワーカーの未処理件数が 10 分間増え続け、同じ時間内に減少へ転じない。

## 最初に確認すること

1. 配備先の環境、現在の版、Git コミット、成果物ダイジェスト、直前の安定版を確認する。
2. 影響する実行単位とテナント、最初に失敗した時刻、直近の設定変更を記録する。
3. 機能フラグだけで影響を止められるか、後退不能なデータ移行を含むかを確認する。
4. 作業担当者と記録担当者を分け、同じ配備先へ同時に変更を加えない。

## 実施

1. 残っている段階的展開を停止する。
2. 機能フラグで安全に無効化できる変更は、配備を戻す前にフラグを直前の値へ戻す。
3. リリース経路が保存した直前の安定版ダイジェストを API、各ワーカー、バッチ、UI に設定し、環境のオーバーレイを再適用する。Kubernetes の Deployment だけを直ちに戻す必要がある場合は、変更したものに対して `mise run rollback-k8s <deployment>` を使う。
4. データ移行を含む場合は、旧版が現在のスキーマを読めることを確認してからアプリケーションを戻す。確認できなければアプリケーションだけを戻さず、移行用の手順へエスカレーションする。

Kubernetes の主な Deployment 名は `idmagic-api`、`idmagic-frontend`、`idmagic-worker-latency-sensitive`、`idmagic-worker-default`、`idmagic-worker-bulk` である。`rollout undo` は CronJob のイメージを戻さないため、バッチを含むリリースでは直前のダイジェストを持つオーバーレイの再適用を完了条件とする。

## 確認

- `/startupz`、`/readyz`、`/livez` が直前の安定版で成功する。
- 着手条件になったアラートが解消し、エラー率、レイテンシー、ジョブの未処理件数が後退前の範囲へ戻る。
- 代表テナントでログイン、トークン発行、ワーカー処理を 1 回ずつ確認する。
- 稼働する各実行単位の版とダイジェストが、記録した直前の安定版と一致する。

## 失敗したとき

後退開始から 15 分以内に受付可能な API レプリカを復元できない場合、またはセキュリティ境界の侵害が継続する場合は、障害対応の指揮担当者へ引き継ぐ。データ整合性または鍵の問題を伴う場合は配備を繰り返さず、[バックアップ、復元、災害復旧](backup-restore-dr.md) の整合性確認へ進む。
