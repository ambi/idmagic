# 監査の記録への書き込み失敗

## 発火条件と意味

`AuditRecordWriteFailed` は、API または Worker の共通配信点が、監査の記録への変換または追記の失敗を検知したときに発火する。
判定式は [Docker Compose の監視規則](../../infra/docker/prometheus-rules.yml) と [Kubernetes の監視規則](../../infra/k8s/monitoring/prometheus-rule.yaml) が所有する。

通常の業務変更は、監査へ書く前に確定している。
そのため、このアラートから業務変更の失敗を推定しない。
追記の応答がタイムアウトした場合など、保存されたか不明な結果も含むので、失敗件数をそのまま欠落件数として数えない。

現行の監視構成は Prometheus の評価までを提供し、Alertmanager と人への通知先を持たない。
デプロイ先に通知を接続していない場合は、Prometheus のアラート画面と構造化ログで確認する。

## 最初に確認すること

1. アラートの `job`、`instance`、`stage` から、対象の API または Worker と失敗した段階を特定する。
2. 同じプロセスのエラーログから、`audit_stage`、`event_type`、`occurred_at`、`error` を読む。
   `append` には `tenant_id` と `audit_event_id` もあるので、権限を持つ管理者が監査の検索または取得で保存の有無を確認する。
   調査のためにイベントの本文や資格情報をアプリケーションログへ追加しない。
3. `conversion` の失敗では、直列化できないイベントの値や識別子生成のエラーを確認し、イベントを発行する実装と実行環境を調べる。
   `append` の失敗では、PostgreSQL への接続、クエリの期限、空き容量、直近のデプロイを確認する。
4. 最初と最後の失敗の時刻、該当するプロセス、ログから確認できたテナントとイベントの種類を障害記録へ残す。
   確認できない範囲は不明として記録する。

## 対応

配信点は、一度失敗しても後続イベントの記録を停止せず、各イベントで通常の書き込みを試みる。
一過性の障害が解消すれば、運用者による再開操作なしに後続イベントを記録できる。
特定のイベントだけ変換に失敗する場合、他の正常なイベントの記録は継続する。
障害が続く場合は、依存先を復旧させるか、変換できないイベントを発行する実装を修正する。
監査だけを埋めるために業務操作を再実行すると、業務の作用が重複するため、行わない。
現在の業務状態から過去の行為者や変更内容を推測して監査へ書かない。

この経路には自動照合や補充の機能がない。
後続イベントの正常な記録と、過去の記録の回復を別々に扱い、回復を証明できない記録は欠落の可能性が残るとして障害記録へ残す。

## 対応後の確認

新しい失敗がログへ出ず、失敗件数の増加が止まったことを確認する。
その後の通常の業務イベントが監査の検索へ現れることを、発生元の事実と突き合わせて確認する。
障害期間に保存結果が不明だった記録については、確認できた結果と未確認の範囲を障害記録へ追記する。

## 検知の限界

業務保存後にイベントを渡す前の停止や、イベントを発行し忘れる実装では、このアラートは発火しない。
失敗後、指標のスクレイプやログの収集の前にプロセスが停止すると、観測も失われ得る。
最初の失敗までにゼロ値の系列が収集されていなければ、増加として検知できないこともある。
アラートが無いことと失敗件数がゼロであることを、監査の完全性の証明に使わない。
通常経路と専用の保存境界の違いは [イベントと監査の記録](../modules/identity-management/design/audit-events.md) に従う。
