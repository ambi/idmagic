# 待ち時間と構成の単純さを保って Go race 検査を自動実行へ戻す

## 動機

[wi-31758](../done/wi-31758-reduce-full-ci-feedback-time.md)では CI を高速化するため、Go 全体テストを通常構成へ切り替える。
race の実行と停止を履歴や経過日数で切り替える仕組みは、CI の構成を複雑にするため採らない。
通常テストは並行アクセスの検査を代行しないので、簡潔な構成で race を自動実行へ戻したい。

## 対象範囲

- Go の通常テストと race テストの所要時間、検出する故障、必要な DB と契約証拠を比較する。
- 毎回の独立ジョブ、対象を限定した実行、変更がなくても動く定期実行などの候補から、費用と故障の検出時点を比較して実行方針を選ぶ。
- 選んだ方針を CI へ接続し、失敗を観測して修復できる状態を作る。
- 通常テストと race の実行結果を区別し、CI の所有文書へ方針と再現方法を書く。

## 対象外

- race のために通常の全体テスト、DB 必須モード、同じ実行の契約証拠を削ること。
- 成功履歴や経過日数の問い合わせを導入することを初期案の前提にすること。
- ビルドキャッシュからテストの成功を推定すること。

## 設計

まず、履歴取得を要求しない固定の実行条件を比較する。
定期実行は push がなくても起動する費用を、毎回の実行は push の待ち時間をそれぞれ含めて判断する。
対象を限定する場合は共有状態と逆依存、未知の入力の扱いを確定し、選択漏れの検査を計画する。
日数や頻度に技術的な最適値があるとは扱わず、push の頻度と検出の遅れを許容する範囲から決める。
作るものを変える実行条件と失敗の扱いは実装前に確定する。

## 計画

1. wi-31758 の最終構成と CI の計測結果を確認する。
2. 候補ごとに待ち時間、runner 使用時間、構成の複雑さ、検出が遅れる範囲を比較し、採用案を確定する。
3. 最小の配線の検査で失敗を観測し、自動実行と証拠保存を実装する。
4. Actions で成功と故意の race の失敗を確認し、運用方法を文書へ反映する。

## 検証

- `mise run test-go-race` で選んだ対象の race 検査を実行する。
- CI の配線に適した局所テストと故障注入で、race の検出と終了コードが伝わることを確かめる。
- `mise run lint-repo`、`check-command-map`、`check-work-items`、`check-links` で CI と記録を検査する。
- 自動実行の発火条件と成功および失敗は Actions の実行で確認する。

## リスク

- 再導入まで CI は data race を自動検出しない。
  必要な局所変更では手元の `mise run test-go-race` などを使い、通常テストの成功を race の検証済みと扱わない。
- 対象や頻度を絞ると、対象外の故障の発見が遅れる。
  その範囲と失敗後の修復方法を採用案に明記する。
