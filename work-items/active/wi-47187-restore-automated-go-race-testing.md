# main に対する Go race 検査を定期実行し、唯一の自動の race 検査にする

## 動機

[wi-31758](../done/wi-31758-reduce-full-ci-feedback-time.md)では CI を高速化するため、Go 全体テストを通常構成へ切り替えた。
通常テストは並行アクセスの検査を代行しないので、data race を自動で検出する仕組みがない。

2026-10-29 に、手元の race 検査の方針も決めた。
race 付きの全体テストは約 106 秒で、通常の全体テスト（約 69 秒）の約 1.5 倍かかり、ビルドのキャッシュも別になる。
1,309 コミットの履歴に、race 検出器が見つけた data race を直したコミットはない。
そのため、手元の検証（`verify-changed`、`verify-integration`、`verify`）では race を既定にせず、並行処理そのものを作る作業だけが明示して選ぶ（wi-57328、wi-52813）。
main への定期実行を、唯一の自動の race 検査にする。

## 対象範囲

- main の全体を race 付きで検査する定期実行の CI ジョブを作る。手動の起動もできるようにする。
- 失敗したら、どのコミットまでが race 検査を通ったかが分かる形で結果と証拠を残す。
- 通常テストと race の実行結果を区別し、CI の所有文書へ方針と再現方法を書く。

## 対象外

- push ごとの race 実行と、変更から対象を絞った race 実行。push の待ち時間を増やし、絞り込みは手元の `verify-changed` が担う。
- 成功履歴や経過日数の問い合わせで実行を切り替えること。CI の構成を複雑にする。
- race のために通常の全体テスト、DB 必須モード、同じ実行の契約証拠を削ること。
- ビルドキャッシュからテストの成功を推定すること。
- 手元のタスクの race の既定の変更（wi-52813）。

## 設計

- 実行条件は固定の schedule と手動の起動だけにし、履歴を読まない。
- 頻度は、main への push の頻度と、見落としを見つけるまでの遅れの許容から決める。初期値は一日一回とし、push のない日も同じ構成で実行する。
- 失敗は、直前に成功した定期実行のコミットから失敗したコミットまでの範囲を示す。範囲を二分して原因のコミットを探す手順を文書に書く。

## 計画

1. wi-31758 の最終構成と CI の計測結果を確認し、頻度と runner の使用時間を確定する。
2. 最小の配線の検査で失敗を観測し、定期実行と証拠保存を実装する。
3. Actions で成功と故意の race の失敗を確認し、運用方法を文書へ反映する。

## 検証

- `mise run test-go-race` で全体の race 検査を実行する。
- CI の配線に適した局所テストと故障注入で、race の検出と終了コードが伝わることを確かめる。
- `mise run lint-repo`、`check-work-items`、`check-links` で CI と記録を検査する。
- 定期実行の発火と成功および失敗は Actions の実行で確認する。

## リスク

- 定期実行の間隔だけ、data race の発見が遅れる。失敗時に範囲を示し、原因のコミットを探す手順を用意する。
- 定期実行が失敗し続けても誰も見ないと保険にならない。失敗を通知する経路を設計で決める。
