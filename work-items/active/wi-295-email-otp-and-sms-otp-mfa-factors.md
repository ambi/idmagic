# メールと SMS のワンタイムコードを、テナントが明示して有効にする制限付きの第二要素として加える

## 動機

第二要素の種類は `totp`、`webauthn`、`hwk`、`swk` だけである（`MfaFactorType`）。
強い要素は揃っているが、摩擦の小さい代わりの手段がない。
認証アプリも passkey も使えない利用者がいるテナントは、MFA の強制を諦めるか、その利用者を例外にするしかない。
認証器を失った利用者の復旧の手段も、復旧コードと管理者の操作に限られる。

NIST SP 800-63B は、SMS とメールのワンタイムコードを制限付き（restricted）の認証器として扱う。
強い要素より弱いことを明示したうえで、テナントが選べる手段にする。

## 対象範囲

- 第二要素の種類に、メールのワンタイムコードと SMS のワンタイムコードを加える。登録には検証済みの宛先を求める。
- テナントの設定で、使える第二要素の種類を選べるようにする。二つの種類はデフォルトで無効にする。
- アプリのサインインポリシーで、制限付きの要素を認めないことを表せるようにする。フィッシング耐性の判定には含めない。
- コードの生成、ハッシュだけの保存、期限、試行回数の上限、再送の間隔を持つ。送信の応答は、宛先の有無で変えない。
- 電話番号の登録と、SMS のコードによる検証（E.164 への正規化を含む）。
- SMS の送信のポートと、コンソールと送信しない実装を同梱する。SMS の送信の手段がないデプロイでは、SMS の要素を有効にできない。
- アカウントポータルの登録と削除、ログインのコードの入力（残りの試行回数、再送の待ち時間）、管理コンソールの設定を加える。

## 対象外

- プッシュ通知型の MFA と音声通話のコード。
- 商用の SMS ゲートウェイの具体的な実装の同梱と、配信の到達率の監視。
- 一次要素としてのパスワードレスのメールログイン。wi-88 が扱う。ワンタイムコードの仕組みは同じ形なので、先に完了したほうが置き、後のほうは作り直さない。

## 設計

着手時に、コードの桁数、期限、試行回数と再送の間隔、トークンの AMR の値（RFC 8176 の `sms`、`otp`、`mfa`）、制限付きの要素だけを持つ利用者に強い要素の登録を促す扱いを決め、Authentication の判断に書く。

## 検証

- 未検証の宛先で登録できないこと、テナントで無効な種類は登録も認証もできないこと、期限切れと試行回数の上限で拒否されることを観測する受け入れのテスト。
- `mise run verify-ui`
- `mise run verify`

## リスク

SMS は SIM の乗っ取りで奪われる。
デフォルトで無効にし、有効にする画面で弱さを示し、フィッシング耐性を求めるポリシーでは認めない。
