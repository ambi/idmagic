# 主要ユースケースの準備から利用結果までを証拠として要求する

## 動機

AI エージェントのデモで、CIBA のグラントを持つクライアントの登録が HTTP 入力検証に拒否された。
CIBA の処理と公開契約は存在したが、登録 API に独自の古い許可リストが残っていた。
既存の CIBA テストと初期データはクライアントを直接保存しており、利用に必要な準備が公開入口から成立することを検証していなかった。
直接の不具合は[登録検証の修正](../done/wi-91126-accept-supported-client-registration-grants.md)で対処したが、別の機能でも同じ構造の漏れが起こり得る。

[テスト方針](../../docs/development/testing.md#外部契約と設定の利用)には、設定を作る正式な入口から利用結果まで観測する規則がすでにある。
不足しているのは、個々の作業で準備経路を選び、その経路を省略したテストを機能全体の証拠として扱わず、実際に必要な故障を検出するまで適用する仕組みである。
規則の追記だけで完了せず、複数の代表経路への適用を同じ作業の受け入れ条件にする。

## 対象範囲

- 既存の `primary_use_cases` を使い、利用の前提、前提を作る公開入口、最終結果、fixture で省略する境界と理由を確認できる証拠契約を定める。
- 作業項目の形式、実装スキル、着手時の文脈と完了検査を、同じ契約へ接続する。
- [機能要件](../../docs/requirements/functional.md)から代表経路を選び、準備から利用結果まで既存テストが実際に通っているか棚卸しする。
- 下表の初回適用対象について、不足する受け入れテストを追加または既存テストを修正し、標準の検証タスクと CI から実行する。
- 手順書の実行入力をテストと対応させ、静的検査、部分実行、通し実行の成功を区別して報告する。
- 主要な設定値や許可条件の独自の複製を、触れる経路で調べる。共通の所有者の判断を使える箇所は統一し、公開契約から独立に選んだ入力で検証する。

## 対象外

- 製品機能の追加や、仕様と異なる実装を新しい仕様として追認すること。
- 全機能、全プロトコル、全入力、全永続化構成の直積を E2E にすること。
- テスト本文の意味や経路の完全性を、宣言と参照の存在だけで機械的に証明すること。
- 全テストの fixture、初期データ、直接保存を禁止すること。
- 外部サービス全般の適合性、障害復旧、移行の検証。[外部契約の検証](wi-422-external-contract-and-failure-verification.md)が扱う。

## 設計

### 証拠契約の扱い

既存の規則を具体化し、別の機能台帳や第二の規範仕様は作らない。
`primary_use_cases` で利用前の状態を誰がどの入口から作るかを表し、公開入口を通すテスト、内部判断だけを検査するテスト、初期基盤を準備する fixture の役割を区別する。
着手時に記入して終わらせず、実装と完了の段階で、実際のテストの準備と照合する。
書式を増やす場合は、欠落を具体的に検出できる最小の構造に限り、既存の未完了項目への移行範囲を明示する。

形式検査が保証するのは必須情報、参照、標準タスクへの接続など、実際に検査できる事実までとする。
準備経路を通っていることや最終結果の表明は、実行するテストと、該当する準備入口を壊す故障注入で確かめる。
記述を整えただけの項目を、利用経路の検証済みへ昇格させない。

### 初回適用する代表経路

各行について、公開の準備入口、利用時の入口、観測する成功と拒否、既存テスト、足りない境界を先に対応付ける。
現在のテストで満たしていれば実行して再利用し、名前や `spec:covers` の存在だけでは充足としない。

| 経路 | 準備から観測する結果 | 主な規範の参照 |
| --- | --- | --- |
| 人のログインと OAuth | クライアントと利用者を構成し、ログイン、認可コードと PKCE、トークン交換、本人 API の利用、リフレッシュと失効まで到達する | REQ-OAUTH2-005、REQ-OAUTH2-001、REQ-OAUTH2-006 |
| アプリケーションへのサインオン | アプリケーションと連携設定、割り当てを作り、割り当てがある主体はサインオンでき、解除後は拒否される。OIDC、SAML、WS-Federation の別実装の入口を個別に棚卸しし、共通規則の検証と方式固有の変換の検証を分ける | REQ-APPLICATION-011 |
| 自律エージェントとリソース認可 | クライアント、公開鍵、Agent と束縛、認可モデル、関係、リソースを登録し、トークンを取得して許可と拒否を観測する。同じトークンで関係の削除と Agent の停止後に拒否へ変わる | REQ-IDMANAGEMENT-074、REQ-OAUTH2-055、REQ-OAUTH2-062、REQ-PLATFORM-001 |
| 人の監督下のエージェント | CIBA を含むクライアントと supervised の Agent を登録して束縛し、承認前の保留、人の承認、トークン取得、一回限りの交換を観測する | REQ-OAUTH2-035、REQ-OAUTH2-041、REQ-OAUTH2-050 |
| 利用者から Agent への委譲 | 利用者と Agent、クライアント、必要な同意と権限を正式な入口で作り、トークン交換後の主体と行為者、利用時の権限、付与のない委譲の拒否を観測する | REQ-OAUTH2-060 |
| 外部ワークロードの認証 | Agent と信頼設定を登録し、制御した外部発行者のアテステーションを交換する。未登録の信頼や停止した Agent では取得できない | REQ-WORKLOADIDENTITY-001、REQ-WORKLOADIDENTITY-006 |
| 上流からの SCIM の取り込み | 接続と資格情報を構成し、外部から利用者とグループを作成、変更、無効化して、管理側の状態とアクセスに反映される | REQ-SOURCING-002、REQ-SOURCING-005、REQ-PLATFORM-001 |
| 下流へのプロビジョニング | アプリケーション、割り当て、接続と属性の対応を作り、変更を起点に正式な worker の実行経路を通して下流の作成と無効化を観測する | REQ-PROVISIONING-002、REQ-PROVISIONING-003、REQ-PROVISIONING-004、REQ-PLATFORM-003 |

規範の本文は各モジュールの機能仕様と[横断シナリオ](../../docs/modules/scenarios.feature.md)を参照し、表へ複製しない。
鍵の登録、API トークン、テナント境界、ジョブ、監査は、上の経路が実際に依存するものを通し、必要な拒否と外向きの作用を観測する。
単一テナントの成功だけで別テナントの拒否を保証したり、メモリ構成だけで worker と PostgreSQL の接続を保証したりしない。

### テスト境界と費用

受け入れでは、対象の準備入口と利用時の入口を含む最小の正式な組み立てを使う。
ユーザーや業務設定を作ったことにする直接保存は、その作成可能性を証明する経路では使わない。
テナントの初期管理者などの基盤準備は省略できるが、その省略を証拠の範囲に含めない。
ブラウザー固有のセッション、ステップアップ、画面遷移を確かめる場合だけブラウザー E2E を使い、決定的な業務条件は狭いテストで確かめる。
外部 IdP と下流 SCIM は、独立に決めた要求と応答を持つローカルの相手で代替し、秘密情報や実サービスの契約を CI に求めない。

全ケースを長い E2E にする案は、同じ故障の重複と実行費用を増やすため採らない。
CIBA だけを追加する案は、異なる準備経路へ規則を適用できることを示せないため採らない。
宣言欄を足すだけの案は、今回の欠落を記述上の充足で隠せるため採らない。

## 計画

既存の[初回実装を改善する WI](wi-98584-reduce-follow-up-refactor-and-bugfix-items-at-first-implementation.md)が扱う一般的な配線と契約参照の改善は再実装せず、本項目は準備から利用結果までの接続に限定する。
最初に上表の対応を調べ、CIBA の実例を使って証拠契約と検査の限界を具体化する。
続いて他の代表経路へ同じ契約を適用し、特定の API や fixture にしか適用できない規則になっていないことを確かめる。
本番コードの欠陥を発見した場合は、意図した振る舞いを決めて別の修正 WI に分け、対応する経路を成功済みと扱わない。
不足を列挙して別 WI に移しただけでは本項目を完了しない。
初回対象の経路が成立し、選んだ故障を検出でき、標準検証から実行できることを完了条件とする。

## 検証

- 着手時の `mise run brief` で対象ごとの仕様と実行タスクを選び、規範 ID を固定する。テストの追加前に対応する `primary_use_cases` を記入する。
- 形式と検査器の変更は、最小 workspace の fixture で欠落と正しい対照を実行し、検査を外す故障を検出する。
- 製品の経路は `mise run test-go-one`、`test-go-package`、ブラウザー依存だけ `test-ui-e2e-file` を使い、初回から必要な実行権限で確認する。
- 故障注入の対象は経路の接続であり、必要なときだけ手動注入する。既存の `test-go-mutation` で扱える局所条件は同じ故障を二重に検証しない。
- `mise run check-work-items`、`check-links`、`check-agent-guidance` と、変更したツールのテストを実行する。
- 初回対象の全行について、準備入口から最終結果までの実行と対応する故障の検出がそろうまで、全体を検証済みと報告しない。

## リスク

欄の追加だけでは、誤ったテストの選択を防げない。
形式、実行結果、故障の検出を別の事実として扱い、機械検査の保証を過大に表現しない。
対象の組み合わせを増やしすぎないよう、同じ故障の重複を避け、公開の準備経路や信頼境界が異なる場合に検証を分ける。
追加する文書は既存の一次情報へ集約し、CIBA 固有の注意書きを全開発の規則として増やさない。
