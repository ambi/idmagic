# 生成した文書サイトのナビゲーションと、開発文書とフォーマット文書の構成を整える

## 動機

HTML にした文書を通して読むと、ナビゲーションの不揃いと、文書の重複、冗長、形式の不統一が目立つ。

| 対象 | 観察 | 原因 |
| --- | --- | --- |
| サイドバーの ApplicationCatalog | ほかのモジュールより左にずれる | 子のない枝を `details` なしで出すので、開閉の印の幅（16px）がない（`tools/render-docs/src/render.ts` の `directory`） |
| サイドバーの「機能一覧 > 機能 > 例」 | 例のページが機能のただ一つの子になる | 例の付録（`<feature>.feature.md`）を機能の子のページにしている。章を持つ機能は `identity-management/features/user.lifecycle.md` の一つだけである |
| サイドバーの「機能一覧」 | 見出しとして据わりが悪い | 一覧ではなく機能そのものの段である |
| サイドバーのモジュールの並び | モジュールだけが辞書順で、ほかの区分は読む順序である | ファイルの順をそのまま使う |
| `docs/modules/ws-federation/standards.md` | wi-96917 で「まとめ」としたが、標準ごとの出典と規範の行が並ぶだけで、WS-Federation、WS-Trust、Entra のドメインフェデレーション、MSAL の関係が読み取れない | 標準仕様の形式（H2、出典、表一つ）に、標準どうしの関係を書く場所がない |
| `docs/modules/scenarios.feature.md` | ページの題名が「Feature: Cross-Module Scenarios」で、サイドバーの「横断シナリオ」とも、ほかの例の付録の「Feature: 〜の例」とも違う | 英語の題名のまま、サイドバーだけを生成器が読み替えている |
| `docs/development/format-rationale.md` | 題名「フォーマットの理由」が内容を表さず、本文の大半は理由でなく、出典の一覧、導入順序、過去の事例である | 規則から長い背景を切り出す受け皿として育った |
| `docs/development/local-development.md` | コードブロックに色が付かない | 生成器に構文の色付けがない。ほかの文書の `bash`、`console`、`go`、`yaml`、`toml`、`markdown` のブロックも同じである |
| `docs/development/specification-first-workflow.md` の「5. 検証の段階」 | race 検査、レスポンスと作用、プロパティテスト、ミューテーションテストが `docs/development/testing.md` と重なり、所有が二つに割れている | ワークフローの文書がテストの判定基準まで抱えている |
| `docs/formats/documentation-guide.md` | 790 行あり、各フォーマットと設計領域の文書の内容を言い換えている | 配置の図、設計領域ごとの内容、AI との共同運用などを一か所に集めた |
| `docs/formats/specification-format.md` の「機能仕様」 | `**操作の節の型。**` のような句点付きの太字が小見出しの代わりに並ぶ | 見出しの階層を増やさずに区切った |
| `docs/formats/specification-format.md` の「6. 旧形式の扱い」 | すべてのモジュールが移行を終え、残る規則はほかの節と検査が持つ | 移行期の節が残った |

## 対象範囲

- サイドバー
  - 子のない枝を、子のある枝と同じ字下げで出す。
  - 例の付録を機能のページの末尾の節「例」として組み込み、例の子のページをなくす。章のページは引き続き機能の子とする。
  - 機能の段の名札を「機能」にする。
  - モジュールを `docs/modules/README.md` の責務表の順（基盤、アイデンティティ、認証と認可、連携プロトコル）に並べる。
- 標準仕様の形式を広げ、`standards.md` の冒頭に標準と製品の関係を説明する節を置けるようにする。その節に WsFederation の相互運用のまとめを書く。
- `docs/modules/scenarios.feature.md` の題名を「Feature: 横断シナリオ」にし、生成器の読み替えを外す。
- `docs/development/format-rationale.md` を廃止する。「全体の方針」の表だけを文書ガイドの目的の節へ移し、参考にした考え方の段落、出典の一覧、導入順序は削る。規則の文書から理由へ張ったリンクは、規則の適用に要る一文だけを規則の側へ残して外す。
- 生成サイトに構文の色付けを入れる（`mermaid` は図のまま）。
- 「5. 検証の段階」をワークフローの手順（局所検査から最終検査への進め方、最終検査の選択、着手時の影響）に絞り、節名を「5. 検証の進め方」にする。race 検査、レスポンスと作用、プロパティテストとファジング、ミューテーションテストの判定基準は `testing.md` へ一本化する。
- `docs/formats/documentation-guide.md` を、配置と一次情報源の割り当てと、ほかの文書に委ねない規則だけに縮める。
- `docs/formats/specification-format.md` の「6. 旧形式の扱い」を削る。
- 句点付きの太字（`**…。**`）を小見出しの代わりに使う箇所を、`docs/` 全体で H4 に改める（`specification-format.md`、`design-format.md`、`documentation-guide.md`、`specification-first-workflow.md`、`design/infrastructure/network.md`、`design/observability/tracing.md`、`design/observability/logging.md`、`design/reliability/recovery.md`、`modules/system/features/admission-control.md` など）。文中の強調は対象外とする。
- `docs/formats/` と `docs/development/` の見出しで、英字と和文の間の空白をそろえ、節の番号を付けるかどうかを文書の種類ごとにそろえる。
- `docs/development/testing.md` の英語と和文の混在（「change-resistance evidence」「lived と not viable」「stable mutant ID」「efficacy」など）を訳語または用語として定めた語に改め、由来の分からない「v4 の境界選択」を現在の規則へのリンクに直し、一文一行になっていない段落を整える。

## 対象外

- サイドバーでモジュールを責務表の区分ごとの段にまとめること。並びだけを責務表の順にする。

- 規範要素の ID、要件文、標準仕様の行の追加と変更。WsFederation のまとめは既存の行を説明し、新しい規範を足さない。
- 開発手法の文書の別リポジトリへの切り出し。

## 設計

### 例の付録の組み込み

| 案 | 利点 | 欠点 |
| --- | --- | --- |
| 機能のページの末尾に節「例」として組み込む（採用） | 要件と例を一つのページで読め、サイドバーから一人っ子の段が消える。元のファイルは分けたままなので、仕様の形式と検査は変わらない | 長い機能のページがさらに長くなる。`*.feature.md` への 16 のリンクを機能のページのアンカーへ読み替える必要がある |
| 例の子を出さず、機能のページの冒頭から例のページへリンクする | 生成器の変更が小さい | 例のページがサイドバーから消え、別の仕組みで到達させる例外が要る |
| 現状のまま | 変更がない | 指摘が残る |

組み込みでは、要件の見出しと例の `Rule` が同じ ID を持つので、アンカーが衝突しないよう例の節の見出しに接頭辞を付ける。
横断シナリオ（`docs/modules/scenarios.feature.md`）は機能に属さないので、単独のページのまま残す。

### 機能の段の名札

候補は「機能」「機能設計」「機能設計文書」である。
段の中身は機能仕様（要件）と、その節としての実現方式なので、「機能設計」とすると仕様を設計と呼ぶことになる。
親の段がすでに「モジュール設計文書 > モジュール」と文書の種類を示すので、子の段は対象の名前だけでよく、「機能」を採る。
モジュールの `README.md` の節「機能一覧」は機能を表で列挙する節なので、名前を変えない。

### モジュールの並び

並びの一次情報源は `docs/modules/README.md` の責務表とし、生成器は表の行の順を読む。
責務表は境界検査の入力として既に解析しているので、その解析を再利用し、順序を別の設定に書き写さない。
責務表にないモジュールの文書は検査が拒否するため、並びから漏れるモジュールはない。

### format-rationale.md の廃止

各節を、規則の適用に要るか、規則を変える人の背景にすぎないかで振り分ける。

| 節 | 扱い |
| --- | --- |
| 全体の方針 | 表を文書ガイドの目的の節へ移す。OpenSpec、Kiro、Living Documentation を参考にした段落は削る |
| 文書ガイド、仕様フォーマット、設計フォーマットの各節 | 規則の言い換えなので削る。規則の判定に要る理由が一文あれば規則の側に残す |
| 開発ワークフロー（検証の段階、レスポンスと作用、プロパティテストの判定基準、生存した変異と割合） | 判定基準を支える一文（例：「panic しない」は判定基準にならない理由、割合に閾値を設けない理由）を `testing.md` の該当節へ移し、過去の事例の記述は削る |
| 開発ワークフローの出典、文書体系の導入と出典 | 削る |

`docs/development/README.md` の索引と、生成器、検査の文書一覧から外す。

### 構文の色付け

生成時に markdown-it の `highlight` で色付けした HTML を出し、閲覧時に JavaScript を要しない形にする。
ライブラリは、`tools/` の依存として highlight.js か Shiki を比べて選ぶ。
選ぶ基準は、対象の言語（`bash`、`sh`、`console`、`go`、`yaml`、`toml`、`markdown`、`text`）の対応、明暗の両テーマへの対応、生成時間への影響である。
`console` は先頭の `$` やコマンドの行を区別できるものを選ぶ。

### 検証の進め方と testing.md の分担

ワークフローの文書は「いつ何を実行するか」、`testing.md` は「どのテストで何を判定するか」を持つ。
`testing.md` の「性質、ファジング、変異、特性化」の表がワークフローの節を指している向きを逆にし、判定基準の本文を `testing.md` へ移す。
`AGENTS.md` と `docs/development/specification-first-workflow.md` から張っているアンカー（`#ミューテーションテスト`、`#go-の通常テストと-race-検査` など）は移した先へ張り直す。

### 文書ガイドの圧縮

残すのは、配置（ディレクトリと文書の種類の対応）、一次情報源の割り当て、上位と下位の分かれ目、生成物と生成ビューの扱いである。
「4. 要件文書と全体設計文書」の設計領域ごとの内容は、設計フォーマットの「設計領域」と各領域の文書が持つので削るか、設計フォーマットへ移す。
「5. TypeSpec の範囲」は仕様フォーマットと重なるので削る。
「8. 開発文書」「9. 運用文書」「10. AI と人間の共同運用」「12. 導入順序」は、所有する文書があればそこへ寄せ、なければ要否を個別に判断する。
目安は現在の半分以下とする。

### WsFederation のまとめの置き場所

モジュールの直下に置ける文書は `MODULE_DOCUMENTS` が固定しており、まとめのための名前はない。

| 案 | 利点 | 欠点 |
| --- | --- | --- |
| `standards.md` の冒頭に、標準と製品の関係を説明する節を置けるよう標準仕様の形式を広げる（採用） | 外部規範の一次情報が一つの文書にまとまり、読み手が探した場所にまとめがある | 標準仕様の形式と `check-spec` の検査を変える。ほかのモジュールの `standards.md` にも同じ節を置けるようになる |
| `README.md` の「主な流れ」を広げる | 形式を変えない | README が概要と道案内の範囲を超え、出典との対応が離れる |
| モジュール直下に置ける文書の名前を足す（例：`interop.md`） | まとめの文書として独立する | 全モジュールの文書の体系を一つの必要のために広げる |

まとめには、受動的な WS-Federation、能動的な WS-Trust と MEX、発行する SAML の Assertion、Entra のドメインフェデレーション（IssuerUri、ImmutableID、`urn:federation:MicrosoftOnline`、internalDomainFederation）、MSAL の探索の手順が、どの要求とどのエンドポイントでつながるかを図と表で示し、各事実から標準仕様の行へリンクする。
事実は wi-96917 と同じく出典を開き直して確かめ、確かめられないものは書かない。

標準仕様の形式の変更は次のとおりとする。

- 最初の H2 の前に、標準どうしと製品の関係を説明する節を一つだけ置ける。節は任意で、規範の行と ID を持たない。
- 標準ごとの H2 の形（出典の行と表一つ）は変えない。
- `check-spec` は、この節を標準として読まず、表を置いたら拒否する。

## 計画

置き場所と追加の改善の範囲は利用者と決めた（置き場所は `standards.md` の冒頭。追加の改善は、句点付きの太字の一掃、見出しの空白と番号、`testing.md` の英語の混在）。

1. 生成器（サイドバー、例の組み込み、題名の読み替えの除去、色付け）を、`render.test.ts` に期待を足してから直す。
2. 文書の整理（format-rationale、ワークフローと testing、文書ガイド、仕様フォーマット）を、リンクを張り直しながら進める。
3. 句点付きの太字、見出しの空白と番号、`testing.md` の語を直す。
4. 標準仕様の形式と検査を広げ、WsFederation のまとめを書く。

## 検証

- `mise run test-tools-file -- tools/render-docs/src/render.test.ts`：ナビゲーション、例の組み込み、色付けの期待。
- `mise run check-rendered-docs`：生成サイト全体のリンクと構成。
- `mise run check-spec`：横断シナリオの題名、標準仕様の冒頭の節。
- `mise run test-tools`：`check-spec` の標準仕様の検査を変えるため。
- `mise run check-links`、`check-agent-guidance`（`AGENTS.md` のアンカーを張り直すため）、`check-work-items`。
- `mise run lint-tools`、`typecheck-tools`：生成器の変更。
- `mise run serve-docs` でサイドバーとコードブロックを目で確かめる。

## リスク

- アンカーの張り直しの漏れ：文書の統合と削除でリンク切れが起きる。`check-links` と `check-rendered-docs` で検出する。
- 文書ガイドの圧縮で、ほかに所有者のない規則を落とす：節ごとに所有する文書を確かめてから削り、所有者のない規則は残す。
- 色付けのライブラリで生成時間が延びる：選定時に `render-docs` の所要時間を比べる。
