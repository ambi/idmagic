# 既存データを持つ DB の更新と、バージョンが一致するバックアップの復元を検証する

## 動機

[スキーマ管理](../../docs/design/data/schema-management.md)は拡張と縮小を定めるが、CI は直前のリリースの DB からの更新を検証しない。
データ移行の実行順は運用者が読み取り、復元スクリプトもバックアップとスキーマのバージョン一致を確認しない。
空の DB で構造差分が収束しても、既存データの保全、再実行、中断後の再開は保証されない。

現在は未リリースであり、当面も未リリースを継続する。
公開済みの旧版と利用者データを保護する更新経路は現時点で最優先ではないため、p3 とする。
初回リリースの予定、長期保存する実利用環境、または既存データを維持する更新の必要が具体化した時点で優先度を再評価する。
それまでは未リリースの全コミットを互換性基準として固定しない。

## 対象範囲

- サポートする更新元のスキーマと代表データから、更新後の構造と業務上の不変条件を検証する基盤。
- 構造差分で表現できない移行について、実行時点、順序、完了状態、再実行、中断からの再開を検証する仕組み。
- バックアップ、元の成果物、スキーマの対応を記録し、一致しない組合せの復元を拒否する検査。
- 移行段階ごとの後退可能性、破壊的 DDL と長時間ロックを検査または事前レビューする責務の整理。

## 対象外

- 未リリース期間の全スキーマや全コミットに対する後方互換性保証。
- 実際のデプロイ、データ移行、本番 DB やバックアップへの操作。
- 新旧アプリケーションの混在稼働は[混在版の検証](wi-450-mixed-version-release-acceptance.md)が扱う。
- 配備方式の静的判定は[更新互換性の事前判定](wi-449-deployment-update-compatibility-preflight.md)が扱う。
- 検出した製品の不整合と、本番の RPO/RTO の確定。

## 設計

現行の宣言的スキーマとデータ移行を一次情報とし、移行用の別スキーマ体系は作らない。
公開済みの更新元が存在する段階では、その不変な成果物からスキーマを解決する。
未リリース期間の検査用フィクスチャは、移行器の検出能力を試す入力として扱い、公開済み旧版と呼ばない。
代表データの期待結果は仕様から独立に決め、移行後の製品出力から自動採集しない。

着手時に、移行状態の記録、同時実行の防止、再開単位、バックアップの識別情報を決める。
DDL のプレビューと、既存データの意味を検証する実行結果は別の証拠とする。

| 案 | 判断 |
| --- | --- |
| 既存データを投入した使い捨て DB で実際の更新と復元を検証する | 採用候補。再実行と制約違反を観測できる |
| 空の DB の収束だけを検査する | 既存データと移行順の故障を検出できないため採らない |
| 未リリースの各コミットを更新元として保存する | 現在の利用者保護に必要でなく、設計変更を重くするため採らない |

## 計画

1. 着手時のリリース状況と、維持すべき既存データの有無から更新元を決める。
2. 移行の実行順、再開、後退、復元時のバージョン照合を設計する。
3. 代表データの更新、再実行、中断、誤ったスキーマでの復元で RED を確認する。
4. 基盤と mise タスクを実装し、初回リリース後の実成果物を使う検査へつなぐ。

## 検証

- mise run check-schema で従来の空 DB の収束を確認する。
- 新設する mise タスクで代表データの更新、再実行、中断後の再開、復元を検証する。
- バックアップとスキーマの識別情報が不一致または欠落していれば、書き込み前に拒否する。
- 後退できる段階と、データを削除したため戻せない段階を結果から区別できる。
- mise run check-work-items、mise run verify を実行する。

## リスク

公開済み旧版がない段階で互換性維持を強制すると、必要な設計変更まで制限する。
公開履歴と検査用フィクスチャを区別し、現時点で存在しない利用者契約を仮定しない。
優先度は p3 だが、実装時の誤りはデータ損失につながるので risk は high とする。
