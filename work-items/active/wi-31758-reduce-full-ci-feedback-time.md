# CI の検査価値と実行方法を見直し、待ち時間を約12分から6分程度へ短縮する

## 動機

[指定された CI 実行](https://github.com/ambi/idmagic/actions/runs/39308038133)では、最長の検証ジョブに11分48秒かかっている。
仕様、Go、UI の検証が直列に並び、独立した検査の所要時間を足し合わせる構成になっている。
必要な故障検出を残し、重複と価値の低い検査も見直して、CI の必須検査が終わるまでの時間を6分程度へ近づけたい。
既存の全検査と race の毎回実行を無条件に維持することは、改善の前提にしない。

変更量の多い push でも改善することを求める。
基準の push は47コミットを含み、431ファイル（うち Go は346ファイル）が変わっている。
同じコミットの再実行でだけ効く最適化を、通常の push に対する効果として扱わない。

## 対象範囲

- 全検査を実行する CI の時間を、ジョブ、準備、ビルド、検査本体、後処理へ分けて測る。
- 同じ入力で通常テストと race テストを比較し、毎回の対象範囲と全体 race 検査の頻度を選ぶ。
- 仕様とツールの検査を検出する故障と費用で棚卸しし、重複を除き、低価値な検査の削除と処理方式の高速化を比較する。
- 英文混入の自動検査と専用テスト、許可語句の管理を廃止する。日本語で書く方針は維持し、少量の混入を許容する。
- 仕様とツール、Go lint、Go 全体テスト、UI の検証を独立したジョブへ分け、既存の必須チェックへ集約する。
- 検査の欠落、失敗、取消を成功にしない結果の集約と、実行証拠の保存を維持する。
- 必要な実行入口を `mise.toml` に置き、[継続的インテグレーション](../../docs/development/continuous-integration.md)を最終構成へ合わせる。

## 対象外

- Actions 上での時間計測と、目標に不足する追加改善の選択は [wi-14496](wi-14496-measure-and-finish-ci-time-reduction.md)へ引き継ぐ。
  利用者の統合指示に従い、検証済みの実装を先に main へ取り込む。6分達成はまだ確認していない。
- 差分による検査の省略。
  [wi-86206](wi-86206-select-ci-test-groups-from-changed-inputs.md)が担当し、本項目はその完了に依存しない。
- DB 統合、契約証拠、UI coverage、E2E、CodeQL、依存監査の検出能力を、時間だけを理由に削減すること。
- Bun のツール群を一括して Go へ移植すること。
  CPU の支配的な処理と外部起動の費用を切り分け、既存の処理方式を改善しても不足する場合に局所的な移植を再検討する。
- テストの成功結果や `.verification/` を次の実行へ流用すること。
- 有料の大型 runner、自前 runner、GitHub の保護設定の変更。
- 製品コードの最適化、Go テストのパッケージ別分割と全体証拠の統合器の新設。
  初期案で不足する場合は、実測に基づいて別途設計する。

## 設計

### 基準となる実行

基準は2026年10月19日の push 実行 `39308038133`、attempt 1、head `893946b1b95a0a916c90d999a144e5cacb677149` とする。
比較対象は push 前の `9019eae4af7b0528507f16f4a679c0aae18d493c` である。
時間は GitHub Actions API の開始と終了の時刻から読み、同じジョブ内の内訳と独立ジョブを区別する。

| 対象 | 所要時間 | 構成上の位置 |
| --- | --- | --- |
| ワークフロー開始から最終ジョブ完了 | 11分51秒 | 全体の基準。開始前の待機と GitHub 側の終了状態の更新時間は含めない |
| 仕様、backend、UI の検証ジョブ | 11分48秒 | 最長ジョブ |
| 上記の依存インストール | 12秒 | 検証ジョブ内 |
| 上記の仕様とツール検証 | 4分3秒 | `check` 約172秒、互換性確認約4秒、tools テスト約66秒など |
| 上記の Go lint | 1分21秒 | 仕様とツール検証の後 |
| 上記の Go race テスト | 5分14秒 | Go lint の後。ビルドと検証 runner の処理も含む |
| 上記の UI 検査、coverage、ビルド | 24秒 | Go の証拠保存の後 |
| CodeQL | 4分19秒 | 既に独立ジョブ |
| ブラウザー E2E | 3分10秒 | 既に独立ジョブ |
| スキーマ収束 | 39秒 | 既に独立ジョブ |
| 依存監査 | 34秒 | 既に独立ジョブ |

`mise-action` のツールキャッシュは命中している。
一方、workflow に Go の依存とビルドの永続キャッシュはなく、`check` 内の Go コマンドで依存のダウンロードが発生している。
同じジョブの後半は先行処理が作ったローカルキャッシュを利用できるため、ステップを別ジョブへ移した後も上表と同じ時間になるとは限らない。
特に5分14秒をテスト本体だけの時間とみなさず、並列化だけで6分に達するとは断定しない。

### 仕様とツールの費用を減らす順序

4分3秒のうち、`check` が約172秒、tools の1018テストが約66秒を占める。
tools の型検査と lint は合わせて約1秒であり、検査を一律に減らしても同じ効果にはならない。
`check` 内では次の処理が重なって実行されているため、各時間を足し合わせない。

| 処理 | 基準ログと実装から分かること | 最初に比較する改善 |
| --- | --- | --- |
| TypeSpec コンパイル | 4分3秒のステップ内で CLI が4回起動し、文書検証内でも compiler API を呼ぶ | `mise` の入れ子を整理し、同じ入力の生成を一度にする。カタログ抽出のための内部コンパイルは別に評価する |
| 文書サイト検証 | CLI の前提コンパイルを除いて約118秒。366文書と910シンボルからサイトを組み立て、生成後のリンク、英文混入、図の構文を検査する | 英文混入検査を廃止し、残る本文と共通ナビゲーションの重複処理、生成物検証の必要範囲を評価する |
| リポジトリ検査 | 約152秒。Go の参照コマンド群と並列に動き、結果は全規則の終了後にまとめて表示する | 各規則の時間と CPU 競合を測り、ログ行の時刻から個々の規則の時間を推定しない |
| tools テスト | SQL 解析と境界検査の三つのファイルで、個別テストの時間の合計が約40秒 | `sqlc parse` の繰り返し起動を減らし、SQL 解析そのものと構文木上の判断の検査を分ける |
| API 互換性検査 | `check-repository` の `all` に `checkPublishedApiCompat` が登録されているが、CI が直後に同じ検査を再実行する | 同じ入力と故障を検査することを照合し、重複した CI 呼び出しと前提コンパイルを除く |

手元の現行ツリーで文書検証を単独でプロファイルしたところ、約9.2秒の実行の約62%を英文混入検査が占めた。
`prose-language.ts` の `textSegments` は、許可語句ごとに全断片へ `flatMap` と `split` を繰り返している。
これは CI の118秒の内訳を直接示す値ではないが、言語移植より先に処理方式を変える候補を示す。
手元では `check-repository` 単独が約3.3秒だったため、CI の遅さを規則数や Bun の処理速度だけで説明しない。
runner の CPU、キャッシュ状態、Go のビルドとの競合も計測する。

検査の採否は[リポジトリ検査の判定基準](../../tools/check/README.md#検査の判定基準)に従う。
検出する故障、別の関門との重複、必要な入力、実行費用、規則への追従費用を一つずつ比べる。
削除と処理方式の変更は別々に計測し、検査を減らした効果を実装の高速化と混同しない。

英文混入の自動検査は廃止する。
利用者は、日本語で書く指示を基本とし、1%程度の英文混入は許容する方針を示している。
この割合は許容度を表し、混入率を測る別のゲートは設けない。
文章規約の機械的な強制に払う実行時間と、許可語句の例外管理やテストを保守する費用が、この許容度に見合わないためである。
[文章の言語](../../docs/development/writing-language.md)から機械的な拒否と許可語句の登録に関する要求を除き、日本語で記述する規則と AGENTS.md の指示は保つ。
`render-docs` から英文混入の判定呼び出しを除き、`prose-language.ts` とその専用テストを削除する。
生成サイトのリンク、図の構文、TypeSpec と契約の検証はそれぞれ残す。
この変更で英文混入を自動検出する能力は失うが、別の自動検査へ引き継ぐことは要求しない。

### race 検査の対象と頻度

実装では、利用者の指示に従い、毎回の Go 全体テストを通常構成へ変更し、CI の race 検査はいったん停止する。
通常テストの DB と契約証拠を保ち、race の実行タスクは手元に残す。
自動実行の再導入は [wi-47187](wi-47187-restore-automated-go-race-testing.md)へ分ける。
日数、成功履歴、変更パッケージによる切り替えは今回追加しない。
これにより race 固有の故障は CI が自動検出しなくなるが、構成の単純さと通常の待ち時間を優先する判断として明示する。

### 実装時の比較と検証の境界

CI の結果集約は `mise run check-ci-results -- <spec> <go-lint> <go-test> <ui>` へ置く。
四つの引数がすべて `success` の場合だけ成功し、不足、過剰、失敗、skip、取消、未知の結果を拒否する。
実際の workflow の `needs` と引数を読むテストで配線を固定し、シェルの実行で各拒否を観測する。
製品要件 ID は N/A（CI の制御）とする。

SQL 解析は、一つの Bun プロセス内で同じ SQL 本文の成功結果を共有する。
外部の `sqlc` の呼び出しと JSON の読取りを `runSqlParser(sql)`、再利用と結果の複製を `parseLocatedSql(sql)` が担当する。
失敗は記憶せず、呼び出し元へは複製を返す。
プロセスを越えた検査結果の再利用は行わず、内容の異なる SQL が混ざらないことと呼び出し元による変更が波及しないことを検査する。
この変更は製品モジュールと公開パッケージの境界を変えない。

GitHub Actions での時間とキャッシュ転送費用の比較には、変更した workflow がリモートに存在する必要がある。
利用者の統合指示により、実装の統合と Actions の実測を分け、後者は wi-14496 で継続する。
実装の起点は `a1441c4e032dc6c9cc5bb882a2e8780a3a62d683` とする。
別作業による `main` の更新を、本項目の仕様差分へ含めない。

毎回すべてのテストを `-race` で実行することは、Go の必須条件ではない。
[公式の説明](https://go.dev/doc/articles/race_detector#Runtime_Overhead)は実行時間の増加を通常2〜20倍とし、検出できるのは実際に実行された経路であると説明する。
この倍率を本リポジトリの5分14秒へ直接当てはめず、同じコミット、DB 必須条件、契約証拠で `test-go` と `test-go-race` を比較する。
ビルドの準備、テスト本体、検証 runner の解析を分け、通常構成と race 構成をそれぞれ冷たい状態と温まった状態で測る。

| 方針 | 得られるもの | 残る費用とリスク |
| --- | --- | --- |
| 毎回全体を race で実行 | 統合前に全テストの実行経路を race で検査する | 全変更が race の費用を払う |
| 毎回通常の全体テストと必要範囲の race、定期的に全体 race | 通常の全体証拠を保ちながら、race の対象を絞れる | 逆依存と共有入力の選択漏れ、対象外の race の検出遅延がある |
| 毎回通常の全体テスト、全体 race は定期実行 | 毎回の race 費用を除ける | 並行性の故障を統合前に止められない場合があり、発見後の修復手順が要る |

これらの自動実行案の採否は wi-47187 の対象とする。
通常テストは race を代行しないことを明記し、検出が遅れるリスクを性能改善と合わせて判断する。
判定の理由を[通常テストと race 検査](../../docs/development/specification-first-workflow.md#go-の通常テストと-race-検査)および CI の説明へ反映する。
既存の wi-86206 が扱う製品検査群の省略とは分け、同項目の実装を前提にしない。

### 独立した検査の並列化

現行の `verify` を次の四つへ分け、先行ジョブによる準備完了を待たずに起動する。

| 検査群 | 配置する検査と成果物 |
| --- | --- |
| 仕様とツール | `check-ci-spec`、`test-tools`、`typecheck-tools`、`lint-tools`、`lint-repo`。互換性検査は registry 内に一度だけ残す |
| Go lint | `lint-go` |
| Go テスト | `test-go`、設定とルートの Go 参照検査、検証結果の報告、`verification-evidence` artifact |
| UI | 依存宣言、整形、lint、型、`test-ui-cover`、`build-ui`、`frontend-coverage` artifact |

各群は必要な依存だけをインストールし、TypeSpec などの生成前提も各ジョブの `mise` タスクから満たす。
分割前の各ステップが分割後のどこで実行されるかを対応付け、抜けと不要な重複を点検する。
設定、ルート優先度、ゲートウェイの参照検査は、通常テストの直後へ置く。
これらのコマンドは広くバックエンドを import するため、仕様群にも置くと別ジョブで同じ範囲をコンパイルする費用が生じる。
Go 全体テストが用意したビルド結果を同じジョブで利用し、仕様群ではバックエンドをコンパイルしない。
手元の `check` は全検査を含む入口として保つ。

既存のチェック名 `Verify specification, backend, and UI` は、四群の結果を受ける集約ジョブに残す。
集約は先行ジョブが失敗しても起動し、四群すべてが `success` の場合に限って成功する。
`failure`、`cancelled`、`skipped`、結果の欠落は拒否する。
他の四ジョブは既存の名前と検査を保ち、全体時間の測定にも含める。

Go テスト群は比較基準の履歴、`VERIFICATION_BASE_REVISION`、`VERIFICATION_REQUIRE_DB=1` を維持する。
`-count=1` と同じ実行の契約証拠を維持し、失敗時も結果の報告と生イベントを含む artifact 保存へ到達させる。
通常の全体テストへ切り替える場合は、その実行結果を明示的に報告し、既定の全体 race レポートを誤って参照しない。
通常テスト、選択した範囲の race、全体 race の証拠は区別する。
ジョブごとに作業ディレクトリが分かれるため、並列の生成処理やレポート出力で他群の入力を変えない。

### キャッシュの評価と採否

キャッシュを6分達成の前提にはしない。
初期実装には GitHub Actions の永続ビルドキャッシュを追加しない。
英文検査の廃止、重複処理の整理、通常テストへの切り替え、並列化の効果を先に確認し、転送費用を測らずキャッシュを増やさないためである。
Actions の測定後も目標に不足する場合だけ、次の比較で採否を決める。
[Go のビルドキャッシュ](https://pkg.go.dev/cmd/go#hdr-Build_and_test_caching)は入力の変更を判定して再利用するが、変更が広く波及すれば再コンパイルが増える。
基準の push では `go.mod` と `go.sum` は変わっていないものの、Go の変更は広範囲であり、標準ライブラリや外部依存の再利用による短縮量は未実測である。

評価は、並列化した構成について、キャッシュなしと直前コミットのキャッシュありを同じ変更で比較する。
局所変更、共有パッケージを含む広範囲な変更、Go 依存更新、Go バージョン更新を分ける。
同じ head の再実行は復元動作の確認に使い、性能目標の達成判定には使わない。
依存取得とコンパイルの削減時間から、復元と保存の費用を引いた全体時間の短縮で採否を決める。
ジョブ単体が速くなっても、最長ジョブや全体時間が変わらない場合は効果を分けて示す。

採用する場合は、`GOMODCACHE`、`GOCACHE`、golangci-lint のキャッシュを区別する。
Go が選ぶディレクトリを使い、OS、architecture、Go バージョン、用途、依存宣言を復元条件へ含め、保存キーには入力の更新を反映する。
通常構成だけのキャッシュを復元して、race 構成も温まったと扱わない。
キャッシュは不変なので、依存ファイルだけで保存キーを固定してソース更新後の結果が保存されなくなる構成を避ける。
異なるコミットのキャッシュを復元した後の有効性は Go に判定させる。
[GitHub のキャッシュ仕様](https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching)に従い、保存の競合とブランチ間の参照範囲も点検する。
キャッシュ不在でも全検査を実行し、秘密情報と実行証拠を保存対象に含めない。

### 代替案の比較

| 案 | 判断 | 理由 |
| --- | --- | --- |
| 独立ジョブへの分割 | 主案として採用 | 直列の4分3秒、1分21秒、5分14秒を重ねられ、ジョブごとに CPU と作業ディレクトリを分離できる |
| 重複検査と低価値な検査の削除 | 採用対象を棚卸し | API 互換性の二重実行は同じ能力を保って除ける。独自能力を廃止する場合は所有規則と残るリスクも変える |
| 英文混入検査の廃止 | 採用 | 少量の混入を許容する方針に対し、毎回の全体検査と許可語句の管理の費用が見合わない |
| 英文混入検査のアルゴリズム改善 | 採らない | 自動検出自体を要求しないため、検出器と専用テストの保守を続ける理由がない |
| ツールの処理方式の高速化 | 優先して評価 | 重複コンパイル、残る文書生成の重複処理、SQL パーサーの反復起動に具体的な候補がある |
| race の対象と頻度の変更 | CI の race は一時停止し、再導入を wi-47187 へ分離 | 利用者の指示により通常テストを固定で実行し、履歴や日数による切り替えは導入しない |
| Go の依存、ビルド、lint キャッシュ | 初期実装には採用せず、CI 計測後に再評価 | 変更量と転送費用に左右されるため、まずキャッシュを増やさない構成を測る |
| 一つの runner 内で全検査を並列実行 | 初期案には採らない | CPU とメモリの競合、生成物の書き込み競合があり、独立ジョブより原因を切り分けにくい |
| Go テストのパッケージ別分割 | 後続候補 | コンパイルや DB 起動が重複し、全体の契約証拠と未実行の検出を保つ統合処理が要る |
| 差分に応じた検査の省略 | 別項目 | 全検査が必要な変更での待ち時間を解決しない |
| 古い push の取消 | 本項目では採らない | 混雑時の無駄は減るが、単一の最新実行の検査時間は縮めない |
| ツール群の Go への全面移植 | 採らない | TypeSpec と Mermaid の JavaScript 依存や外部プロセスの起動費用は、そのままでは解消しない |
| 大型 runner、テスト結果の再利用 | 採らない | 費用や運用前提の変更、または同じ実行の証拠を失うことを伴う |

## 計画

1. 着手時の workflow と基準実行との差分を確認し、検査ごとの時間と故障、通常と race の速度を測る。
   低価値な検査の採否と race の対象および頻度を確定し、所有規則へ反映してから実装する。
2. 英文混入検査を専用テストと許可語句の管理ごと廃止する。
   重複検査と重複コンパイルを整理し、残る文書検証と SQL 解析の処理方式を局所的に改善する。
3. ジョブを分割し、キャッシュなしで全群の所要時間、実行内容、集約の失敗伝播を確かめる。
4. 代表的な異なるコミット間でキャッシュの有無を比較し、効果のある対象だけを最終構成へ加える。
5. 採用後の必須検査をすべて実行する変更で全体時間を測定し、6分目標との差を確認する。
   未達なら、新たな最長ジョブを特定し、その内訳と次の採否を設計へ反映する。
   採用方針が要求する検査を省略した実行や、キャッシュが完全一致する再実行へ測定条件を変えて達成扱いにしない。
6. 採用した構成と手元での再現方法を一次情報文書へ反映する。

## 検証

Actions の所要時間とキャッシュの比較は wi-14496 の対象とし、下記の計測条件も引き継ぐ。
本項目は実装を統合する前に `check-work-items` と `check-links` を実行し、rebase で新しいツリーになる場合は `check` と `verify` で合成結果を検証する。

性能目標は、採用後の必須検査をすべて実行する通常の push で、ワークフロー開始から最終ジョブ完了までの中央値を360秒以内にすることとする。
検査の削除と頻度変更による短縮、同じ検査の処理改善、並列化、キャッシュの効果を分ける。
race を対象限定または定期実行にする場合は、全体 race の時間と検出までの遅れも別に示す。
同じコミットの再実行だけで達成を判定せず、直前の異なるコミットのキャッシュから始める実行を含める。
キャッシュを採用しない場合も同じ目標を使う。
少なくとも三つの代表的なコミット遷移について変更前後を対応付け、広範囲な Go 変更を含める。
runner の種類、ツールのバージョン、検査対象、キャッシュの初期状態を揃える。
基準実行と代表的な後続変更を分け、コードの増減による差を workflow の改善量へ混ぜない。

開始前の待機時間、各ジョブの待機、復元と保存、後処理、全ジョブ合計の runner 使用時間も併記する。
キャッシュなしの実行は別枠で測り、6分を超える場合もその時間と内訳を示す。
6分は測定する改善目標とし、テストを6分で打ち切って成功させる条件にはしない。

- `mise run check-command-map` と `mise run lint-repo` で、CI と `mise` の接続、workflow の構文と権限を確認する。
- `mise run check-work-items` と `mise run check-links` で、作業記録の形式と参照を確認する。
- 検証ツールを変更した場合は、`mise run test-tools-file -- <変更したテストファイル>`、`mise run typecheck-tools`、`mise run lint-tools` を追加する。
  受け入れ境界は CLI または CI の結果集約とし、製品要件 ID は N/A（CI の実行構成）とする。
- 分割前後で、採用した必須検査、対象パッケージ、成功とスキップ、契約証拠、DB 検証、coverage と artifact を照合する。
  件数は基準の成功値へ固定せず、同じ入力で比較する。
- 四群のいずれかの失敗、skip、取消、欠落が最終チェックを成功させないことを確かめる。
  Go 失敗時の証拠保存、通常結果と race 結果の区別、キャッシュ不在での必須検査も確認する。
- 手元の内訳調査には必要に応じて `mise run time-verify -- <suite>` を使う。
  CI の配線と性能の証拠は Actions の実行で確認する。

## リスク

- 分割後は、先行ステップが温めていた通常ビルドや race ビルドを各ジョブでやり直す。
  キャッシュなしの所要時間を先に測り、元のステップ時間をそのまま短縮予測に使わない。
- 大きな変更ではキャッシュの再利用が少なく、転送と保存が短縮分を上回る可能性がある。
  広範囲な変更で正味の効果を確認し、効果のない対象は採用しない。
- 並列ジョブを増やすと、合計の runner 使用時間や同時実行枠の待機が増える可能性がある。
  経過時間と合計費用を分けて比較し、測定結果で分割の粒度を見直す。
- 集約の条件を誤ると検査の欠落を成功にできる。
  四群の成功を明示的に要求し、失敗を注入して伝播を確認する。
- Go テスト群の履歴取得や環境変数の移動漏れは、変更操作や DB の検証を弱める。
  比較基準、必須モード、同一実行の証拠を分割前後で照合する。
- CI の race の一時停止中は、並行性の故障を自動検出しない。
  wi-47187 で再導入を扱い、通常テストの成功で race も検証済みと表示しない。
- 英文混入検査の廃止後は、指示に反した英文が一部残っても CI は止めない。
  利用者が許容した品質の判断として扱い、日本語で記述する方針を維持する。
  別の検査の重複を除く場合は、残る検査へ同じ違反を注入して確認する。

## 要約

実装の起点に対する `spec-diff` が示す規範仕様の変更はない。
CI を四群へ分け、通常の Go 全体テストの後で Go の参照検査を実行する。
英文混入検査と二重の API 互換性検査を除き、TypeSpec の重複コンパイルと同じ SQL の反復解析を減らす。
CI の race は利用者の指示で一時停止し、再導入は wi-47187 へ分ける。
Actions の時間計測と必要に応じた追加高速化は wi-14496 へ引き継ぎ、6分達成は未確認のまま実装を統合する。
