# MCP サーバーと Gateway の登録をまとめ、接続準備を自動化する

## 動機

「公開するツールと必要な権限」は、MCP サーバーが返せる情報まで手入力させている。
デモへ実際に `tools/list` を送り、ツール名、説明、入出力のスキーマを取得できた。
ツール名の転記はプロトコルの制約ではなく、取り込み機能の不足である。
Gateway の評価用クライアントを別画面で作成し、接続先へ `client_id` を転記することも通常の手順になっている。
構成上の実体が分かれることを、登録作業を分ける理由にしない。
取得、生成、選択と紐付けで置き換えられる入力を減らし、接続先の登録を一つの作業にする。

## 対象範囲

| 自動化または統合する作業 | 情報源と条件 | 利用者の判断 |
| --- | --- | --- |
| MCP サーバーと Gateway の登録 | 一つの接続登録で、必要な評価用クライアント、Gateway 構成と紐付けを準備する | 新規の Gateway、既存の構成、サーバー自身による執行のうち成立する構成を使う |
| ツール名、表示名、説明、入出力定義の取り込み | `tools/list`。任意項目の省略、ページング、取得権限による部分的な一覧を扱う | 公開するツールを選び、必要な場合だけ表示名を編集する |
| 接続先と認可サーバーの情報取得 | Protected Resource Metadata と認可サーバーのメタデータ。出所を保持する | 接続先と使用する認証方法を選ぶ |
| スコープ候補と対応の取り込み | `scopes_supported`、認証チャレンジ、検証した接続定義。これらだけでツール別の対応が分かるとは扱わない | 不足する対応だけを導入担当者が一度設定する |
| Agent と認証用クライアントの紐付け | 作成結果の引き継ぎと、既存クライアントの表示名付き選択 | 新規作成と既存利用を選ぶ。生の ID を転記しない |
| Gateway の配置設定の生成 | テナント、接続先、評価主体と資格情報の参照。リソース URI と実際の接続 URL を区別する | 配置先と使用する資格情報を選ぶ |
| 接続確認と不足設定の案内 | 認証、一覧取得、登録、割当とトークン上限を、業務ツールを実行せず確認する | 不足する設定を案内先で補う |
| ツール変更の再取得と差分作成 | 再取得、対応する変更通知と保存済みの結果。追加、削除、改名、定義変更を区別する | 公開範囲や必要権限に影響する差分を選んで反映する |

新規資格情報の作成と紐付けの一体化、操作割当からの発行スコープの導出、Gateway のカタログ参照は実装済みである。
その成果を保ち、同じ対応を Gateway へ再入力させない。
通常の Agent 管理では操作を選び、同じ許可をスコープでも再選択させない。
スコープ追加が既存資格情報の上限を超える場合は、その影響を表示する。
トークンの再発行が必要かも案内し、業務操作を暗黙に再送しない。

登録画面の各入力欄には、値の出所（あなたが決める、自動で入る、前の手順の結果、既定値）と、変更したときに何が変わるかを示す。
語は [Agent の一括作成](wi-85817-register-agent-credentials-and-connections-in-one-flow.md)と揃える。
保存前には、作るもの（接続先、Gateway の構成、評価用クライアント、公開するツール）を一文の要約で示す。

## 対象外

- 発見したツールの無条件の公開と、Agent への自動的な権限付与。
- ツール名、説明文、`readOnlyHint` から権限や承認の要否を信頼できる事実として推測すること。
- `scopes_supported` をツール別の必要スコープの対応表として扱うこと。
- 一覧への掲載や OAuth 対応だけを、IdMagic による実行制御の保証とすること。
- 外部データの対象カタログ全体と、承認した一回の操作の Gateway への受け渡し。
- Agent の登録、認証、割当の一括作成。[wi-85817](wi-85817-register-agent-credentials-and-connections-in-one-flow.md)で扱う。
- デモと管理画面の値の受け渡しと、デモの設定済みの開始点。[wi-68754](wi-68754-start-the-agent-demo-preconfigured-and-explain-every-input.md)で扱う。
- モデルを作らない対象ごとの権限。[wi-24427](wi-24427-restrict-tools-to-targets-without-authoring-a-model.md)で扱う。

## 設計

### 外部仕様と取得の限界

[MCP Tools](https://modelcontextprotocol.io/specification/2026-07-28/server/tools) は名前付きツール、一覧取得、呼び出しと入出力定義を規定する。
標準のツール定義は、ツールごとの OAuth スコープの対応表を持たない。
[MCP Authorization](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization) と [RFC 6749 §3.3](https://www.rfc-editor.org/rfc/rfc6749#section-3.3) は、ツールとスコープの1対1対応を要求しない。
`tools/list` は取得に使った権限によって結果が異なり得るため、常に完全なカタログと判断しない。

### 登録と管理の流れ

通常の入口は「MCP へ接続」「一覧を取得」「公開するツールを選択」「保存」とする。
取得可能な値を再入力させず、接続先、Gateway と評価用クライアントを一つの流れで準備する。
現在の画面で別途登録するものは評価用のサービスクライアントであり、独立した Gateway の登録台帳があるとは説明しない。
既存の Gateway や評価主体を利用する構成を保ち、製品モデルでも常に1対1の新規作成を要求しない。
同じ入口から構成を確認できるようにし、構成の詳細を日常の操作割当へ持ち込まない。
部分成功、再試行、二重作成と取り消しの単位を決めてから、登録を一つの操作として提供する。
取得とプレビューは公開設定を変更せず、失敗しても既存の設定と割当を保つ。

Gateway なしの登録は、サーバー自身など別の執行点が IdMagic の判定を実行へ適用する構成と、接続情報を管理するだけの構成を区別する。
後者にも操作割当や取消が適用されるとは表示しない。
Gateway の有無だけで保証を判断せず、実行時の判定、対象制約と失効をどこで執行するかを示す。
初期設定が必要なら一度だけ導入担当者が行い、通常の管理者へ方式選択を繰り返させない。

### ツールとスコープの候補

| 候補 | 利点 | 制約 |
| --- | --- | --- |
| ツールごとのスコープ | 対応が明瞭で、新規の IdMagic 配下なら自動生成できる | ツールの増減でスコープも変わる。外部サーバーの既存の定義を置き換えない |
| 複数ツールをまとめるスコープと個別割当 | 粗い認証上限を保ち、更新と削除などを個別に許可できる | 対応を接続定義で一度決め、通常利用で二重選択させない |
| 外部サーバーの定義の取り込み | 既存の認証と相互運用できる | 対応を示す検証済みの情報源が必要であり、全サーバーには期待できない |

一つの方式を全接続先へ強制せず、対応を決める責任、初期導入と日常の負担、既存トークンと資格情報への影響を比べて採用条件を決める。

### 実装前に解決する境界

- 一覧取得を IdMagic から直接行うか、Gateway を介するかを、配置と接続認証から決める。
- リソース URI は呼び出せる URL とは限らない。接続 URL の所有者と資格情報の保管場所を決める。
- Agent の割当がまだない導入時の取得主体と認証を決め、実行時の認可を省く一般経路を作らない。
- 外向きの取得先、リダイレクト、名前解決、取得量と期限を定め、SSRF と資格情報の他宛先への送信を防ぐ。
- デモの受け渡しは明示的な対応付けに閉じ、任意のサイトによる資格情報の登録や読み取りを許さない。
- 再取得の保存に操作 ID と競合検査を適用し、削除後の同名再登録で古い割当を復活させない。観測していない削除と再登録を名前だけから検出できるとは扱わない。
- モジュール、公開 API、永続化と組み立て地点の追加が必要なら、責務、依存と一貫性の候補を比較し、TypeSpec と担当する仕様を先に更新する。

### 受け入れの基準

初期導入と日常の変更を分け、Okta、Ping と同じ課題で必須の概念、手入力、転記と画面遷移を比べる。
競合より複雑な必須手順を増やす案は採らず、同じ制御が成立する製品の流れを基準にする。
外部サーバー、Gateway、認証、対象制約の構築費用を省いて単純さを主張しない。
MCP サーバーと Gateway をセットで使う通常の構成では、別画面でのサービス作成と ID の転記を必須にしない。
取得可能なツール名を手入力せず、Agent の通常の割当でスコープを二重選択しない。

## 計画

今回は起票だけを行い、製品コード、公開仕様と UI の実装には着手しない。
着手時に候補を現行実装と照合し、実装済みのものと新しい作業を区別する。
接続先と Gateway の一体の登録、およびツール発見を中核の受け入れ単位にする。
独立して受け入れられるデモ連携や配置の自動化は、判断を残したうえで子項目へ分ける。
未確定の取得方式、認証、境界とスコープの対応方式は実装前に解決する。

## 検証

着手時に、公開した接続準備の入口から MCP の実応答、保存結果と実行時の拒否までを観測する主要ユースケースを確定する。
新規と既存の Gateway、別の執行点、認証不足、部分的な一覧、ページング、空、途中の失敗、同時更新、ツールの追加・削除・再登録を含める。
取得後も未公開・未割当の操作が実行されず、登録の再試行でサービスや資格情報が重複作成されないことを確認する。
ブラウザーでは、通常の準備でツール名や ID を転記せず、同じ許可を二重に選択しないことを確認する。
起票時は `check-work-items` と `check-links`、実装後は `verify-changed` と対象ブラウザー E2E を選ぶ。
