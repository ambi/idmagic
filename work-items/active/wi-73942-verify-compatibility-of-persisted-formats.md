# 保存済みの形式を新しいコードで読み取れることを検証する

## 動機

[バックエンド設計](../../docs/design/application/backend.md#公開イベントの互換性)は公開イベントの名前の削除と改名を禁止するが、リリース済みベースラインとの互換性は判定しない。
現在の発行側と消費側を同時に変えれば、語彙の一致を保ちながら古い記録だけを読み取れなくする可能性がある。
同じ問題は、更新をまたいで残るジョブやセッションなどの保存形式にも起こる。

現在は未リリースであり、当面も未リリースを継続する。
公開済みの旧形式を守る必要はまだなく、現在の内部形式を凍結する重要性は低いので p3 とする。
初回リリースの予定、保持する実利用データ、または外部のイベント消費者が具体化した時点で再評価する。
未リリースの形式変更を、公開済み契約の破壊として扱わない。

## 対象範囲

- 更新や再起動をまたいで残る保存形式と、その読取側、保持期間、変更時の扱いの棚卸し。
- 監査イベント、永続ジョブ、セッションなど、保存形式ごとの互換性検証の境界。
- 公開後に保持すべき旧形式のフィクスチャと、新しい読取側での意味の検証。
- 名前や型の変更、旧形式の廃止、明示したデータ移行を判断する条件と、現在の契約検査との役割分担。

## 対象外

- 未リリースの全形式の保存と、全内部型の後方互換性保証。
- HTTP API の互換性検査、DB の更新、実際の混在デプロイ。
- 検出した製品コードの不整合の是正。
- 外部配信用のイベント基盤の新設。

## 設計

対象は永続化または更新の境界を越える形式に限り、局所的な実装型は固定しない。
形式と意味の一次情報は所有するモジュールの契約へ残し、検証入力と独立した期待結果を対応付ける。
監査では検索軸と事実の保持、ジョブでは実行する操作、セッションでは主体と有効性など、読取側の最終結果まで確かめる。
単にデコードできることを、意味の互換性として扱わない。

着手時に、対象形式、実際に維持すべき世代、廃止条件、暗号化された値の検証方法を決める。
未リリースの間は、検出能力を試すフィクスチャと、今後サポートする公開済み形式を区別する。
実利用環境の維持が不要なら、旧形式を恒久サポートする仕組みを先に導入しない。

| 案 | 判断 |
| --- | --- |
| 保持が必要な旧形式を独立した期待結果とともに検証する | 採用候補。読取側と宣言を同時変更しても破壊を検出できる |
| 現在の発行側と消費側の語彙だけを照合する | 過去の保存済み入力を検査できないため、この目的には足りない |
| すべての内部型へバージョンを付ける | 更新をまたがない型まで変更負担を増やすため採らない |

## 計画

1. 形式の所有者と寿命を棚卸しし、着手時に維持すべき旧形式を選ぶ。
2. 互換性の意味、明示した移行と廃止の条件を決める。
3. 旧フィールドや検索軸を読めない読取側で RED を確認する。
4. 対象形式の契約検証と、実行タスクを整備する。

## 検証

- mise run check-event-contract で現在の語彙の照合を維持する。
- 対象の mise run test-go-package と、新設する保存形式の契約検証タスクを実行する。
- 旧イベントの名前や検索項目を読めなくした場合、現在の語彙が一致していても検証が失敗する。
- ジョブやセッションは、デコード成功だけでなく最終的な操作や主体の解決を検査する。
- mise run check-work-items、mise run verify を実行する。

## リスク

旧形式を際限なく固定すると、未リリース段階の設計変更が困難になる。
保持が必要なデータとサポート期間から対象を選び、互換性のない未リリース変更には再作成または明示した移行を選べるようにする。
