# MFA を失った制御面の運用者が復旧できることを確かめる

## 動機

[[wi-468-system-console-privileged-session-assurance]] は、システムコンソールとシステム API に MFA を求める。
MFA の端末と復旧コードを失った制御面の運用者は、システムコンソールへ入れなくなる。
唯一の運用者がそうなると、テナントの停止や鍵の対応ができず、復旧の手段もなくなる。
wi-468 を展開する前に、既存の仕組みで復旧できることを確かめる。

## 対象範囲

- 既存の経路で復旧できるかを HTTP の受け入れテストで確かめる。想定する経路は、既定のテナントの `admin` ロールを持つ操作者が認証器をリセットし（REQ-AUTHENTICATION-022）、運用者が次のログインで第二要素を再登録して、MFA で成立したセッションとトークンを得るものである。
- 次の条件で復旧できるかを確かめる。
  - 運用者が `admin` を持たず `system_admin` だけを持つ場合。
  - 運用者が自分自身の認証器をリセットする場合。
  - 既定のテナントのサインインポリシーが IdMagic 自身の画面に MFA を求める場合。
- 運用の手順を runbook に書く。
- 成立しない条件が見つかれば、復旧の手段を設ける作業項目を起票し、wi-468 の展開をそれに依存させる。

## 対象外

- break-glass の資格情報の自動発行。
- 外部 PAM との連携。
- 実環境での手動の検証。受け入れテストは本番と同じ組み立てを通すので、同じ経路の主な失敗を検出できる（2026-11-14 に利用者と決定）。

## 計画

1. 上の条件ごとに、受け入れテストで復旧の経路を通す。
2. 成立した経路を runbook に書き、成立しない条件は起票する。

## タスク

- [ ] T001 [Acceptance] 認証器のリセットから再登録、MFA で成立したトークンの取得までを、条件ごとに受け入れテストで通す。
- [ ] T002 [Operations] 復旧の手順を runbook に書く。
- [ ] T003 [Decision] 成立しない条件があれば起票し、wi-468 の依存に加える。

## 検証

- 最終検査は `mise run verify-changed -- <着手時の基準リビジョン>` とする。

## リスク

運用者が `admin` を持たず、既定のテナントにほかの管理者もいない構成では、リセットを行う人がいない。
この構成が成立しないと分かれば、wi-468 を展開する前に復旧の手段を用意する必要がある。
