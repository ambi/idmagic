# MCP ゲートウェイを IdMagic がホストする構成と自前設置の構成を、どちらも選べるようにするか判断して対応する

## 動機

IdMagic の MCP ゲートウェイは、導入側が MCP サーバーの近くに設置して運用する。
同じ役割を、Okta と Ping は逆の場所で動かす。

| 製品 | ゲートウェイの運用場所 | 導入側の負担と制約 |
| --- | --- | --- |
| Okta Agent Gateway | Okta がホストする中継コンテナー。Agent は `https://{subdomain}.gateway.okta.com/mcp/...` へ接続し、Okta がリモートの MCP サーバーへ中継する。設定は Okta の制御層に置き、中継側が定期的に取り込む（[概念](https://developer.okta.com/docs/concepts/agent-gateway/)） | 配置の作業はない。上流は Okta から到達できるリモートの MCP サーバーに限られる。上流の資格情報は Okta の STS がトークン交換で取得する |
| PingGateway | 導入側がダウンロードして設置するソフトウェア。Docker のイメージも作れる（[MCP ゲートウェイ](https://docs.pingidentity.com/pinggateway/2026/mcp/index.html)） | 閉じたネットワークの MCP サーバーも保護できるが、配置、TLS、運用は導入側の作業になる |

デモはゲートウェイをデモのプロセスの中で自動で起動するので、配置の費用が見えない。
「Okta や Ping よりシンプル」を名乗るには、配置の作業がない Okta と、閉じたネットワークに置ける Ping の両方と比べる必要がある。
IdMagic が両方の運用場所を提供すれば、導入側が上流の場所に合わせて選べる。

## 対象範囲

- IdMagic がホストするゲートウェイの採否を決める。採る場合は、テナントごとの公開 URL、上流への外向きの接続、上流の資格情報の保管と注入、設定の配信を定める。
- 自前設置のゲートウェイを保ち、同じ接続先の登録、ツールの報告、操作割当、評価で両方の運用場所を扱えるようにする。
- 管理画面の接続先の登録で、運用場所を選べるようにし、選んだ場所で必要な入力だけを示す。
- 自前設置の構成について、設定の配信（起動時と定期の取り込み）で配置後の再設定を減らせるかを判断する。
- Okta と Ping の公式手順と、初期構築の必須操作を比べる。

## 対象外

- 上流の資格情報を仲介する汎用の金庫。[wi-62382](wi-62382-decide-non-oauth-downstream-credentials-in-the-vault.md) の判断に従う。
- 競合製品の実テナントでの計測。

## 設計

着手時に、少なくとも次の候補を比べる。

| 候補 | 利点 | 制約 |
| --- | --- | --- |
| 自前設置だけを保つ | 現行のまま。上流が閉じたネットワークにあっても動く | 配置の作業が残り、Okta との比較で初期構築が重い |
| IdMagic がホストする構成を加える | 配置の作業がなくなる。登録の直後に Agent が接続できる | IdMagic の外向き接続に SSRF の防御、宛先の制限、流量と期限が要る。上流の資格情報を IdMagic が保管する。テナントの分離と障害の影響範囲を設計する |
| ホスト型を加え、閉じたネットワークへは導入側の中継で届ける | 両方の利点を得られる | 中継の配置が別に要り、構成が増える |

ホスト型を採る場合は、[境界を選ぶ判断手順](../../docs/design/application/design-guidelines.md#境界を選ぶ判断手順)で、実行単位、組み立て地点、所有するテーブルを比べてから実装する。
外向きの取得は wi-95247 から分ける予定の Gateway のない直接取得と同じ防御を共有する。

## 検証

着手時に、運用場所ごとの主要ユースケースを決める。
ホスト型では、上流への外向き接続が登録した宛先だけに届き、内部のアドレスとリダイレクトで迂回できないことを確認する。

## リスク

ホスト型は IdMagic が上流の資格情報と業務の通信を扱うので、侵害の影響範囲が広がる。
テナントの分離、資格情報の保管、ログへの非出力を先に設計し、採用前にセキュリティレビューを行う。
公開 URL とテナントの対応は、Agent の設定に配った後で変えにくい。
