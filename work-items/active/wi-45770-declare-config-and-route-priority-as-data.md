# 起動時設定と経路の優先度クラスを宣言的なデータで定め、読み込みコードと参照文書をそこから生成する

## 動機

設定リファレンスと経路の優先度リファレンスは、どちらも Go のコードを一次情報にして生成している。
[文書の形式](../../docs/formats/documentation-guide.md#開発文書)は、起動時設定について「項目、型、デフォルト値、検証規則を宣言的なスキーマへ書き、読み込みコードとリファレンス文書の双方をそこから導く」と定めており、今の方式はこの規則に反している。
2026-11-19 にコードを読んで、次の欠陥を確かめた。

設定リファレンス（`bootstrap.RenderConfigReference`）について：

1. **分岐の中だけで読むキーが漏れうる。**
   各プロセスの `Load*Config` を空の環境変数で一度だけ走らせ、`ConfigLoader` が記録したキーを表にする。
   `if cfg.X == "…" { l.Y(…) }` の中でしか読まないキーは記録されない。
   今は「どの分岐でも一度は読む」書き方で避けているが、慣習であり検査はない。
2. **条件付きの必須が実際の検証と二重管理である。**
   `l.RequiredWhen("AUTHZEN_URL", "AUTHZEN=remote")` は文書のためだけの文字列で、実際の検証は別の `Required*` と `Require` の呼び出しが行う。
   条件を変えても文書は古いまま通る。
   `backend/cmd/internal/bootstrap` の本番コードに 21 か所ある。
3. **キーの説明が別の Go の表（`configFieldDescriptions`）にある。**
   両方向の照合で乖離は防いでいるが、一つのキーの定義が型とデフォルト値の宣言、説明の表、条件の文字列の三か所に分かれている。
4. **テナント設定の `env:<名前>` で参照するシークレットが文書にない。**
   フェデレーションのシークレットは、名前をテナントが決める環境変数から読む（`secrets_env.Resolver`）。
   名前が固定でないので一覧にはできないが、この仕組みがあること自体を運用者が知る手段がない。

経路の優先度リファレンス（`server_http.RenderPriorityClassReference`）について：

5. **手書きの部分が検査されない。**
   クラスごとのステージ番号、上限を与える設定キーの名前、動作の説明は `referenceClasses` に手で書かれている。
   生成器のコメントは「手で保つものはない」と書くが、`ADMISSION_*_MAX_CONCURRENT_REQUESTS` を改名しても文書は古いまま検査を通る。
6. **分類の規則表が Go にある。**
   クラスは前方一致の規則表（`routeClassRules`）で決まり、言語を変えると規則と生成器の両方を書き直すことになる。
7. **全経路の展開が読み手の問いに合っていない。**
   分類はパスだけで決まりメソッドに依らないのに、文書の大半はメソッドの列挙である。
   当番の問いは多くの場合「この経路はどのクラスか」であり、拒否の時点ではメトリクス `http_admission_decisions_total` の `class` のラベルが既に答えている。

開発者が Go 以外の言語で読み込みや分類を書き直すとき、今の方式では一次情報ごと書き直すことになる。
設計文書が定めた規則への既存の実装の追従なので、グループの基準どおり p2 とする。
起動時の検証（REQ-SYSTEM-016）を作り直すので、誤ると必須の値やシークレットの検証が抜けたまま起動しうる。
そのため `risk` を `medium` とする。

## 対象範囲

- 起動時設定を宣言的なデータ（YAML または JSON Schema）で定める。キーごとに、型、デフォルト値、制約、許可値、シークレットかどうか、読むプロセス、説明、必須の条件を持つ。
- 設定の読み込みと検証のコード、設定リファレンス、機能レジストリの表をその宣言から導く。条件付きの必須は宣言した条件から検証し、文書と同じ一次情報にする。
- 経路の優先度クラスの一次情報を宣言的なデータへ移し、分類器と参照文書をそこから導く。クラスのステージと上限の設定キーも宣言に含め、設定の宣言にあるキーだけを参照できるようにする。
- 参照文書の形を読み手の問いに合わせて見直す。経路の文書のメソッドの列、全経路の展開か規則表の提示か、を含む。
- 設定リファレンスに `env:<名前>` によるシークレットの参照の仕組みを書く。
- REQ-SYSTEM-017 と REQ-SYSTEM-019 の要件文と例を、宣言から生成する形に合わせて改める。

## 対象外

- 設定項目、デフォルト値、検証規則そのものの変更。宣言へ移すだけで、受理する値と拒否する値は変えない。
- 経路のクラスの割り当ての変更。
- 流入制御の仕組み（上限、ステージ、503 の応答）の変更。
- テナント設定（TypeSpec が定める）と feature flag の定義の形式。

## 設計

### 設定の宣言

候補は、独自の YAML、JSON Schema、CUE などの設定言語である。
着手時に、項目をまたぐ条件（`AUTHZEN=remote` のとき `AUTHZEN_URL` が必須、`WEBAUTHN_RP_ID != ""` のとき `WEBAUTHN_RP_ORIGINS` が必須）を表せるか、Go と TypeScript の両方から読めるか、既存のツールで検証できるかで比べる。
今の 21 か所の条件は `キー=値` と `キー != ""` の形に収まる見込みであり、小さな式で足りるなら独自の YAML で足りる。
式で書けない検証（URL の形、範囲）は型と制約で表し、それでも書けないものだけをコードに残して、宣言からその検証の名前を参照させる。

宣言からコードを生成するか、宣言を実行時に読むかも比べる。
生成なら型付きの `Config` 構造体を保てる。
実行時に読むなら生成の手順が要らないが、型の安全性を失う。

### 経路の優先度クラスの一次情報

2026-11-19 の利用者の判断により、起票時には決めず、着手時に次の二案を比べる。

| 案 | 利点 | 欠点 |
| --- | --- | --- |
| YAML の規則表（接頭辞からクラス） | 今の規則表をそのまま移せる。TypeSpec にない経路（`/health` など）も同じ表で扱える | 経路の一次情報（TypeSpec）と分類が別の場所に分かれる |
| TypeSpec の各操作に宣言する | 経路と同じ場所に置け、文書は API リファレンスの一部になる | TypeSpec にない経路の扱いを別に決める必要がある。操作ごとに書くので記述量が増える |

どちらの案でも、未分類の経路を拒否する網羅性の検査（今の `TestClassifyRouteReturnsUnclassifiedForUnknownRoute` が支える検査）は保つ。

### 経路の参照文書の要否

規則表を人が読める形で示せば、全経路の展開は要らない可能性がある。
着手時に、当番の問い（なぜ 503 になったか、次にどのステージで落ちるか）に対して、規則表、API リファレンスでのクラスの表示、メトリクスのラベルのどれが答えるかを比べ、展開を残すかを決める。
展開をやめる場合は REQ-SYSTEM-019 を改め、[アドミッションコントロールが発動したとき](../../docs/runbooks/admission-control.md)の引き方も直す。

## 計画

1. 特性化テストで、今の設定の受理と拒否（必須、条件付きの必須、型、範囲、シークレットの扱い）を固定する。
2. 設定の宣言の形式を比べて決め、宣言から読み込みコードと参照文書を導く。
3. 経路の優先度クラスの一次情報を比べて決め、分類器と参照文書を導く。
4. REQ-SYSTEM-017 と REQ-SYSTEM-019 を改め、参照文書の形を見直す。

作るものを変え得る問いは、設計の三つの比較（設定の宣言の形式、経路のクラスの一次情報、経路の参照文書の要否）である。
どれも着手時に解決してから実装する。

## リスク

- 宣言へ移す過程で、必須やシークレットの検証が抜けると、不完全な設定のまま起動するか、シークレットが文書やログに出る。
  T001 の特性化テストで、移す前の受理と拒否を固定してから移す。
- 独自の YAML と式は、新しい小さな言語を抱えることになる。
  式で表す範囲を今の条件の形に限り、足りないものはコードの検証を名前で参照する。
