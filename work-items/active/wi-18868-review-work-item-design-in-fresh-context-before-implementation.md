# 実装の前に、作業項目の設計と仕様の差分を新しい文脈でレビューし、所見の扱いを記録する

## 動機

[開発サイクル](../../docs/development/specification-first-workflow.md#開発サイクル)で、書いた本人以外がレビューする段階は、実装の後の `code-review` だけである。
`implement-work-item` は、仕様と計画（手順 3）と着手の記録（手順 4）のあとにすぐコードへ進む。
完了の前の手順 7 では、実装した本人が七つの視点で差分をレビューする。
仕様の漏れ、設計の誤り、作るものを変え得る未解決の問いは、仕様を書いた本人の文脈のまま見直されるので、コードとテストを書いた後で見つかることがある。
後で見つかると、仕様、テスト、実装を書き直すことになる。

また、`code-review` が出した所見を直したのか、受け入れたのか、対象外にしたのかは、作業項目にも要約にも残らない。
受け入れた所見は、後から読む人には判断されなかったものと区別できない。

AWS の AI-DLC は、要件と設計を作る段階の後に、別のサブエージェント（レビュー担当）を呼び、READY か NOT-READY かと所見を返させてから承認ゲートを開く。
所見には安定した ID が付き、再確認では解決、未解決、受け入れたリスクのどれかとして示す。
未解決の所見を残したまま承認すると、受け入れたものとして記録される。

独立したレビューは、サブエージェントを起動するたびに作業項目、仕様、関係する文書を読み直すので、トークンの費用を無視できない。
費用に見合う作業と見合わない作業を分ける条件が必要である。

## 対象範囲

- `implement-work-item` の手順 3 と手順 4 の間に、新しい文脈のサブエージェントによる設計レビューを入れる。
  - 入力は、作業項目の全文、`mise run spec-diff` の結果、`affected_spec` が指す規範要素とする。リポジトリ全体の方法論文書は渡さず、[仕様の漏れを探す観点](../../docs/development/specification-first-workflow.md#仕様の漏れを探す観点)などの観点の節だけを渡す。
  - レビュー担当は、作るものを変え得る未解決の問い、仕様の漏れ、設計と規範の食い違い、証拠の契約の不足を所見として返す。
  - 所見をすべて扱ってから `status: in_progress` にする。
- 所見の扱いを記録する形を `work-item-format.md` に定める。
  - 直した所見は記録しない（差分に表れる）。受け入れた所見と対象外にした所見だけを、理由とともに `## リスク` または `## 対象外` に書く。
  - 実装後の `code-review` の所見にも同じ扱いを適用する。
- レビューを省く条件を定める。初期案は次のとおりで、計測の結果で決め直す。
  - `risk: low` かつ `spec_impact: none` の項目は省く。
  - `change_kind` が `docs`、`maintenance` で、規範要素を変えない項目は省く。
  - `risk: medium` 以上、または `affected_spec` の規範要素を追加、変更、廃止する項目では行う。
- 費用を計測する。条件に当たる 3〜5 件の項目で、レビューに使ったトークン数と、レビューが見つけた所見のうち実装前に設計を変えたものの数を記録し、省く条件を決め直す。

## 対象外

- レビュー担当のための常設のエージェント定義ファイル。特定の実行環境の機能に依存するので、手順は「新しい文脈で読ませる」という環境によらない形で書く。
- 所見の ID を機械で追跡する仕組み。受け入れた所見と対象外にした所見を文章で残すだけにする。
- 複数のレビュー担当を並列に使う方式。[wi-16732](wi-16732-decide-parallel-blind-subagents-for-specification-gap-search.md) が、この項目の計測結果を使って採否を決める。
- 文書の差分の意味の変化を読むレビュー。[wi-18737](wi-18737-review-meaning-changes-in-document-diffs.md) が扱う。

## 設計

出典: AWS AI-DLC のドキュメント「Introduction」「Onboarding」「Phases and Stages」「Glossary」の Reviewer の項（https://awslabs.github.io/aidlc-workflows/guide/）。本文を読んだ。調査日は 2026-11-28。

AI-DLC から採る点は、実装の前に別の文脈が設計を読むこと、READY か NOT-READY かの判定、未解決のまま進める所見を受け入れたものとして記録することである。
採らない点は、段階ごとに常にレビュー担当を呼ぶことと、レビュー後の編集を凍結するフックである。
前者は費用の条件で絞り、後者は特定の実行環境に依存する。

このレビューは工程上のゲートであり、証拠の契約には含めない。
[証拠の要件](../../docs/development/specification-first-workflow.md#証拠の要件)は、二人目の読み手によるレビューを、実装者の意図だけでは満たせない観測ではないとして証拠契約から除いており、その判断と矛盾させない。

省く条件を `risk` と `spec_impact` で決めるのは、どちらも起票の時点で記録にあり、エージェントが追加の調査なしに判定できるためである。

## 計画

1. 条件に当たる未完了の項目から 3〜5 件を選び、レビューを試して費用と効果を記録する。
2. 結果から省く条件を決め、`implement-work-item` と `specification-first-workflow.md` の開発サイクルの表を更新する。
3. 所見の扱いの記録の形を `work-item-format.md` に書く。
4. 費用に見合わないと判断したら、試した結果を要約に書いて中止する。

## 検証

- `mise run check-agent-guidance`: skill から呼ぶタスクとリンクの形式を確かめる。
- `mise run check-links`: 文書間のリンクを確かめる。
- `mise run check-work-items`: 記録の形式を確かめる。

## リスク

レビューの費用が効果を上回ると、作業項目ごとの所要時間とトークン数が増えるだけになる。
計測を先に行い、見合わなければ中止する。
レビュー担当が些細な所見を多く返すと、扱う手間が増える。
所見を作るものを変え得るものに絞るよう指示する。
