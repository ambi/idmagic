# リフレッシュで発行するアクセストークンに元の認証時刻と方式を引き継ぐ

## 動機

リフレッシュトークンのローテーションで発行するアクセストークンは、`auth_time` をリフレッシュの時刻にし、`amr` と `acr` を載せない（`refresh_tokens.go` の `AuthTime: now.Unix()`）。
RFC 9068 §2.2.1 と OIDC Core は、`auth_time` を利用者が実際に認証した時刻と定める。
リフレッシュは利用者の認証ではないので、この値は認証の新しさを偽り、方式を失う。

[[wi-52890-step-up-bearer-requests-with-rfc-9470]] は、Bearer の要求のステップアップを RFC 9470 に沿ってトークンの `auth_time` と `acr` で判定する。
リフレッシュのたびに `auth_time` が新しくなると、その判定は成り立たない。
リライングパーティーとリソースサーバーが `auth_time` で再認証を判断する場合も同じである。

本項目は当初、ステップアップの判定をログインセッションへ結び付ける修正として起票した。
2026-11-14 に利用者と RFC 9470 を目標の方式に決め、その前提の修正に作り直した。

## 対象範囲

- 認可コードの交換で発行するリフレッシュトークンの記録に、認証の `auth_time`、`amr`、`acr` を保存する。
- ローテーションは親の値を引き継ぎ、発行するアクセストークンに同じ `auth_time`、`amr`、`acr` を載せる。
- 値を持たない既存の記録からローテーションしたとき、アクセストークンに `auth_time`、`amr`、`acr` を載せない。
- `refresh_tokens` に列を追加し、メモリーと PostgreSQL のアダプターの共有契約で保存と引き継ぎを確かめる。
- REQ-OAUTH2-006 に、ローテーションが元の認証の時刻と方式を引き継ぐことを書く。

## 対象外

- リソース側で `auth_time` と `acr` を使ってステップアップを判定すること。
  [[wi-52890-step-up-bearer-requests-with-rfc-9470]] が扱う。
- `client_credentials`、トークン交換、デバイスフローなど、認可コード以外の発行経路の `auth_time`。
  本項目はリフレッシュトークンのローテーションだけを直す。
- リフレッシュでの ID トークンの発行。現在も発行しない。

## 設計

### 規範の差分

REQ-OAUTH2-006 に次の要件文を加える。

- OAuth2 は、ローテーションで発行するアクセストークンに、元の付与を得た認証の `auth_time`、`amr`、`acr` をそのまま載せ、リフレッシュの時刻を `auth_time` にしない。
- 元の認証の `auth_time` を記録していないリフレッシュトークンを交換したとき、OAuth2 は、アクセストークンに `auth_time`、`amr`、`acr` を載せない。

### 既存の記録

列の追加前に発行した記録は、認証の時刻と方式を持たない。
補う値の候補を比べ、載せない側を採る。

| 候補 | 採否 | 理由 |
| --- | --- | --- |
| 載せない | 採用 | 判定する側は認証の新しさを示さないトークンとして扱い、再認証を求める。誤って新しいと見なす余地がない |
| ファミリーの最初の記録の `issued_at` | 不採用 | 認証より後の時刻なので、新しさを過大に示す |
| リフレッシュの時刻（現状） | 不採用 | 本項目が直す誤りそのもの |

リフレッシュトークンの絶対有効期限を過ぎれば、値を持たない記録はなくなる。

### 型と作用

`RefreshTokenRecord` に `AuthTime *int64`、`AMR []string`、`ACR *string` を加える。
`GenerateInitialRefreshToken` は認可コードの記録から値を受け取り、ローテーションの生成は親から写す。
発行の時刻は引き続き注入した `now` から決め、`auth_time` には使わない。

### 互換性とロールバック

アクセストークンの `auth_time` が過去の時刻になり、`amr` と `acr` が加わる。
リフレッシュ後のトークンを「直前に認証した」と読んでいた利用側は、再認証を求めるようになる。
列は NULL を許すので、コードを戻しても既存の記録はそのまま読める。

## 計画

1. T001 で規範を更新する。
2. T002 で、認証から十分に時間が経った後のリフレッシュが現在時刻を `auth_time` にすることを観測する。
3. 記録、アダプター、発行の順に実装する。

- `mise run test-go-one` で T002 と T003 の RED と GREEN を確かめる。

## リスク

`auth_time` が古くなることで、リフレッシュ後のトークンで再認証を求められる場面が増える。
現状は、その要求を誤って満たしていた状態であり、[[wi-52890-step-up-bearer-requests-with-rfc-9470]] が再認可の流れを整える。
両者の間は、ステップアップの判定がまだトークンの `iat` を使うので、本項目だけでは利用者の操作は変わらない。
