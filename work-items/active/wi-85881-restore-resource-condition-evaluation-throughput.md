# 条件を持つリソースアクセス評価を局所測定の処理量の目標へ戻す

## 動機

[[wi-31151-measure-resource-condition-compilation-cost]] の実測で、1024 コードポイントの式を二つ持つ評価が、[局所測定の処理量の目標](../../docs/requirements/quality.md#リソースアクセス評価の局所測定)を下回った。
日本語と BMP 外の文字の式はメモリで約 390〜400 件/秒、PostgreSQL で約 180〜190 件/秒となり、内包の式も PostgreSQL で約 430 件/秒だった。
同じ保存済みの式を毎回コンパイルしており、多バイトの式を二つ持つドメインの判定は約 4.9 ms と約 9.3 MiB の累積割り当てを要した。
評価だけの費用との差が大きいため、準備処理の改善と再利用の費用対効果を比較する。

本番の負荷を推定する項目ではなく、再現可能な局所測定で既存の目標への違反を確認したため、このグループの基準より優先度を上げて p1 とする。
根拠と再現条件は [条件式のコンパイル費用](../../docs/design/performance/scaling.md#条件式のコンパイル費用)にある。

## 対象範囲

- CEL v0.33.1 に含まれる Pratt パーサーで、コンパイル費用と割り当てを減らす。
- CEL の構文、型と評価の意味、入力の契約を保ち、将来 Go 以外の CEL 実装へ移す場合にも式を引き継げる構成にする。
- メモリと PostgreSQL の両構成で、日本語、BMP 外の文字、内包を含む既存の測定ケースを局所性能目標へ合わせる。
- 条件の差し替えと削除は次の評価から反映し、コンパイルや評価の失敗を許可へ倒さない。
- 初回と反復、正常な式と拒否する式を分け、既存パーサーとの受理と評価結果の差を確認する。

## 対象外

- 1024 コードポイントという上限と、受理する式の範囲を狭めること。
- 評価結果そのもののキャッシュ。
- コンパイル済みプログラムや検査済み AST のキャッシュ、`golang-lru` と `singleflight` の追加。
- Expr など別の式言語への変更、Go の型や独自関数を保存式へ公開すること。
- 既存の性能目標を緩めること。
- 本番の混合負荷、長時間のキャパシティ受入れ、テナント別の性能保証。
- 分散キャッシュ、新しい永続データ、公開 API と運用設定の追加。

## 設計

[REQ-OAUTH2-062](../../docs/modules/oauth2/features/resource-access.md#req-oauth2-062-登録したリソースサーバーは自身の規則の操作だけを提示トークンで評価できる) の条件変更の反映と、失敗時の不許可を保つ。
[REQ-OAUTH2-064](../../docs/modules/oauth2/features/admin-access.md#req-oauth2-064-管理者はリソースサーバーへ評価用のクライアントと規則を設定できる) の受理範囲も保つ。
製品の契約を変えない性能改善として `maintenance` とし、規範と TypeSpec は変更しない。
性能の受け入れ基準は `CAP-RESOURCE-ACCESS-THROUGHPUT` と `SLO-RESOURCE-ACCESS-LATENCY` を参照し、数値と測定条件は品質要件を一次情報とする。

### 採用する方式と代替案

CEL を維持し、同じライブラリ内の Pratt パーサーを使う。
比較用の試作ではキャッシュなしで既存の局所目標へ届いたため、この項目では保持状態と外部ライブラリを増やさない。
測定条件、保持メモリと代替言語の比較は、[準備処理の改善と保持メモリの比較](../../docs/design/performance/scaling.md#準備処理の改善と保持メモリの比較)を参照する。

事前比較では、Pratt パーサーを一時差し替えした HTTP の全 18 ケースが既存の局所目標を満たした。
PostgreSQL の日本語条件は従来の約 188 件/秒に対して約 1,375 件/秒、内包条件は約 432 件/秒に対して約 759 件/秒となった。
プログラムの保持量は短い比較式の約 1.2 KiB/件から、正規表現の一例の約 2.2 MiB/件まで差があり、件数制限だけのキャッシュを先に追加する根拠にはしない。
これらは試作の測定であり、本番コードは未変更である。
正式な実装では解析の互換性と並行動作を追加検証し、性能も測り直す。

| 候補 | 利点 | 負担と選択条件 |
| --- | --- | --- |
| CEL の Pratt パーサーを使う | 言語を維持し、初回と異なる式にも改善が効く | 採用する。現バージョンの公開 API をつなぐ変換処理と互換性の検査を OAuth2 の内部へ閉じる |
| コンパイル済みプログラムを保持する | 命中時の費用を最も小さくできる | 正規表現の展開後の保持量は式ごとの差が大きく、件数上限だけで小さなメモリ予算を主張できない。現在の目標には不要なので採らない |
| 検査済み AST を保持する | 解析と型検査を省き、正規表現の展開結果の常駐を避けられる | 有力な再検討先だが、共有状態、上限と追い出しの管理が増える。今回の目標には不要なので採らない |
| AST をシリアライズして保持する | 保持するキーとデータのバイト数を直接制限できる | デコードとプログラムの構築を毎回行い、内包の式では追加費用も大きい。保持量の厳密な制御が必要になった場合に再検討する |
| FIFO または LRU のキャッシュを入れる | アクセスの偏りに応じて反復コンパイルを減らせる | LRU が FIFO より効く合成負荷もあるが、実利用の分布は未測定。LRU の必要性と新規依存の利点を示せないため、どちらも今回導入しない |
| Expr へ置き換える | 比較した式ではコンパイル費用が小さい | Go への依存、欠落属性の意味、費用制限と保存式の移行が課題になる。展開した正規表現の保持量も減らなかったため採らない |
| 毎回のコンパイルを続ける | 共有する可変状態を増やさない | 現在の局所測定で目標未達があるため、改善なしでは採らない |

### 維持する不変条件

式の全文を同じ CEL 環境で解析し、従来と同じ型検査、AST 検証器、最適化と評価の費用上限を通す。
文字列の正規化や、受理範囲を狭める制限を加えない。

`token`、`operation`、`now`、`attributes` と評価結果、評価時の費用の状態は要求ごとに作り、保持しない。
別のテナントで同じ式を使う場合も入力を共有せず、現在の入力で評価する。
既存の拒否優先、承認要求、評価不能の分類と、評価ごとの費用上限を維持する。
登録時の構文、型、長さ、内包の検証を迂回せず、コンパイル失敗を成功したプログラムとして保持しない。

評価は毎回読み取った規則の式を使う。
条件の差し替え後は新しい式を使い、削除後は条件の評価を通らない。
監査の `conditionVersion` は現在の条件から、`conditionOutcome` と属性のダイジェストは現在の評価から求める。

保存するのは CEL の式とし、Go の実行用プログラムを永続化しない。
別言語へ実装を移す場合にも、変数の型、欠落、数値、時刻と評価不能の期待結果を同じ入力例で比較できるようにする。

### 型と操作の境界

主要な既存の型と操作は次のままとする。

```go
type ConditionInput struct {
    Token      map[string]any
    Operation  map[string]any
    Now        time.Time
    Attributes map[string]any
}

func (c ResourceAccessCondition) Validate() error
func (c ResourceAccessCondition) Evaluate(in ConditionInput) ConditionOutcome
func compileCondition(expression string) (cel.Program, error)
```

`compileCondition` の内部で `parser.NewParser(parser.EnablePrattParser(true), parser.Macros(parser.AllMacros...))` を使う。
解析した AST を公開 API の `ExprToProto`、`SourceInfoToProto`、`ParsedExprToAst` で既存の `cel.Env.Check` へ接続し、同じ `env.Program` のオプションで構築する。
環境とパーサーの初期化だけを共有し、式ごとの AST とプログラムは保持しない。
この変換を担う非公開の操作は `parseCondition(expression string) (*cel.Ast, error)` とし、登録と評価を同じコンパイル経路へ通す。
時刻と要求値は引き続き `ConditionInput` から受け、保存、通知、監査の作用の編成を変更しない。

この案は公開型、モジュール間の依存、テーブル所有者、組み立て地点を変えずに比較する。
比較の結果それらを変える必要があれば、実装前に `brief --concern boundary` で参照を追加し、境界を選ぶ判断手順の記録をこの設計へ追記する。

### 再検討の条件

正式な実装で既存の目標に届かない、または通常の短い式を使う実利用でコンパイルが律速になる場合に、AST の上限付き再利用を改めて比較する。
その際は、プロセス単位の保持ヒープの予算、活動中の式の数と命中率、異なる式の流入、同時コンパイルのピークを先に決める。
件数上限をバイト数の上限と読み替えず、キャッシュの方式とライブラリ追加を別々に判断する。

## 計画

1. 着手時の基準リビジョンを確定し、既存のパーサーの受理、拒否と評価結果を比較する入力をそろえる。
2. 機能仕様の「実現方式」を更新してから、Pratt パーサーを使う非公開の解析操作を実装する。
3. 登録時の検証と評価時の同じ経路を通し、型、内包、長さ、欠落と費用超過の振る舞いを比較する。パーサーを共有する並行呼び出しも確かめる。
4. 通常ビルドで変更前と同じ局所性能測定を実行し、条件なしを含む全ケースで既存目標を満たすことを確かめる。試作の結果を正式な実装の検証に流用しない。
5. 採用方式と正式な実測を現在状態の文書へ残し、差分に応じた最終検査を通す。

保存値と公開契約の移行は行わない。
取り消しは内部の解析を従来の `env.Compile` へ戻すことで行える。

## 検証

| 境界 | 観測する内容 | 検出する故障 |
| --- | --- | --- |
| ドメイン | 同じ式で属性、トークン、操作、時刻を変えた判定。拒否と承認の優先、欠落、型不整合、費用超過、コンパイル失敗 | 前回の入力や結果を使う。費用の状態を引き継ぐ。失敗を許可へ倒す |
| ドメイン | 両パーサーで上限ちょうど、構文誤り、深い括弧、内包を解析し、同じ受理と拒否を観測する | 変換やパーサー変更で受理範囲や検証器の適用が変わる |
| 並行実行 | 同じ式と異なる式を別入力で同時評価し、別テナントの評価も混ぜる | パーサー共有に伴う競合や、入力の混線が生じる |
| ユースケース | 現在の条件と要求に対応する監査のバージョン、結果、ダイジェスト | 解析の変更に伴って拒否や評価不能の監査情報が変わる |
| 正式な HTTP | 両保存構成で許可条件を評価した後に拒否条件へ変更し、次の評価で拒否する。条件削除後は許可へ戻る | 規則の識別子で古い条件を引く。保存後に評価へ反映されない |
| 性能 | 初回、生の反復コンパイル、評価だけ、通常判定を分ける | 試作や評価だけの速さを、正式な HTTP 経路の改善と取り違える |

- `mise run test-go-package -- ./backend/oauth2/domain` で条件評価と登録検証を確かめる。`mise run test-go-package -- ./backend/oauth2/domain --race` でパーサーを共有する並行経路も検査する。
- `mise run test-go-package -- ./backend/oauth2/internal/token/usecases` で監査と条件なしの既存の振る舞いを確認する。
- HTTP の回帰検査は `mise run test-go-one -- ./backend/cmd/internal/bootstrap <追加するテスト名>` で実行する。テスト名は T003 の実装前に確定する。
- `GOFLAGS=-benchtime=100ms mise run benchmark-go-package -- ./backend/oauth2/domain '^BenchmarkResourceCondition' 5` で変更前後を同じ条件で比べる。初回は性能設計の手順どおりに入力ごとに新しいプロセスで測る。
- `mise run measure-resource-access` で既存の全ケースの処理量、p99、全応答の正しさを確認する。条件を無視して速くなる故障を区別するため、拒否条件を登録する対照も維持する。
- HTTP、PostgreSQL を使う検査と測定、および `mise run verify-changed -- <着手時の基準リビジョン>` は最初からサンドボックス外で実行する。DB を使う検査の Skip は受け入れの成功とみなさない。
- 実装の最終検査には `verify-changed` を使い、`mise run spec-diff` で規範差分がないことを確認する。起票時の文書検査には `mise run check-work-items` と `mise run check-links` を使う。

## リスク

パーサーの変更で、演算子の優先順位、マクロ展開、文字列、再帰制限とエラーの扱いが変わり得る。
既存テストの成功だけで全入力の同値性を主張せず、受理、拒否と評価結果を差分検査する。
AST の変換は追加の割り当てを生むため、正式な実装で測り直す。
コンパイル中の一時メモリと同時要求の費用は残り、局所目標の達成から任意の正規表現の最悪費用や本番のメモリ上限を保証しない。
将来の言語実装の移行では、CEL の仕様だけでなく入力の型、エラー処理、費用上限の対応も確認する。
