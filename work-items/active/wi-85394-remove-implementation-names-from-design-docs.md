# 設計文書から実装のパスと名前を取り除く

## 動機

wi-55197 で、設計フォーマットに「実装の名前に依存しない記述」の規則を加えた。
設計は実装が従う側であり、設計がソースファイルのパスや関数、型、コンポーネント、定数の名前を参照すると、依存の向きが逆になって、実装の移動や改名のたびに設計を直すことになる。

既存の設計文書には、この規則に反する記述が残っている。
着手時の計測では、バッククォートで囲んだリポジトリ内のパス（`frontend/`、`backend/`、`tools/`、`infra/` で始まるもの）が、`docs/design/` の 14 ファイル 84 行と、`docs/modules/` の 33 ファイル 78 行にある。
多い文書は `docs/modules/README.md`（26 行）、フロントエンド設計（24 行）、バックエンド設計（20 行）、MCP Gateway の実行時の機能仕様（14 行）、実行時の構成（10 行）である。
関数や型、コンポーネントの名前はパスのように形で検出できないので、この数に含まない。

## 対象範囲

- `docs/design/` の設計領域の文書と、`docs/modules/<module>/` の設計領域の文書（`application.md`、`data.md` など）と機能仕様の「実現方式」の節から、規則に反するパスと実装の名前を取り除き、役割と規則の言葉で書き直す。
- 規則が例外とする記述（コードの置き場所そのものを定める節、外部の製品と標準の名前と設定項目、契約と仕様の識別子、`mise run` のコマンド）は残す。
- 違反を機械的に検出する検査を加えるかを、着手時に判断する。加える場合は、誤検出の量を計測してから例外の書き方を決める。

## 対象外

- 規則の文言そのものの変更。規則は wi-55197 で定めた。
- 機能仕様の規範の部分（要件と例）。外から観測する振る舞いを書く部分で、実装の名前を書く理由がないはずなので、見つけた場合だけ直す。
- 開発文書（`docs/development/`）と形式の文書（`docs/formats/`）。これらはリポジトリの作業手順を定める文書で、ツールやファイルの配置を名指すことが主題である。
- 作業項目の記録。作業記録なので、実装のパスを書いてよい。

## 設計

### 例外の判定

文書ごとに、その節が配置そのものを定めているかを判断する。

- `docs/modules/README.md` の責務表は、モジュールとディレクトリの対応を定めるので、配置の節として残す見込みである。責務の説明の文に混じったパスは書き直す。
- バックエンド設計とフロントエンド設計の「層と配置」「コードの置き場所」「機能スライスの境界」の節は、配置の節として残す。それ以外の節（データの取得、ビルド、テストなど）に現れるパスは書き直す。
- 実行時の構成と配置の文書に現れる設定ファイルやスクリプトのパスは、運用者が実際に触れる成果物を指す場合がある。その場合は配置の情報として残すか、運用の手順書（開発文書）へ移すかを、文書ごとに判断する。

### 機械的な検査

候補は次の二つで、着手時に誤検出の量を計測して選ぶ。

| 案 | 内容 | 懸念 |
| --- | --- | --- |
| 検査を加えない | 規則はレビューで判断する | 新しい違反が入っても気付けない |
| パスの形を検出する | 設計領域の文書のバッククォートの中のリポジトリ内のパスを拒否し、配置の節は節単位の例外として登録する | 識別子は検出できない。例外の登録が増えると検査が読まれなくなる |

検査を加える場合も、関数や型、コンポーネントの名前は形で区別できないので、レビューで判断する範囲に残す。

## 計画

1. 違反の候補を文書ごとに一覧にし、例外に当たるものを分ける。
2. 機械的な検査の要否を、誤検出の量から決める。
3. 文書ごとに書き直す。同じ文書の複数の箇所は一度に直す。
4. 検査を加える場合は、書き直しの後に加え、既存の文書で失敗しないことを確かめる。

## 検証

- `mise run check-links`：書き直しでリンクとアンカーが壊れていないことを確かめる。
- `mise run check-spec`：設計領域の索引と文書の配置の検査が通ることを確かめる。
- `mise run check`：文書の用語の検査を含む集約の検査が通ることを確かめる。
- 検査を加える場合は、その検査の単体テストと `mise run check-agent-guidance` を加える。

## リスク

書き直しで、実装を探す手がかりが文書から消える。
規則の理由どおり、実装の場所はコードと作業項目の記録から辿る前提だが、運用者が読む文書で手がかりが要る箇所は、開発文書へ移すことで補う。
