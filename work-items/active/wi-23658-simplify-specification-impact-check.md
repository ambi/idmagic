# 仕様影響の照合を、仕様の申告漏れと本番コードの宣言漏れに絞る

## 動機

`spec-impact` の照合は、エージェントが仕様を黙って変えることを機械で止める唯一の仕組みである。
一方で、判定が細かく、作業の手間と検査の時間が大きい。

- `affected_spec` の `impact: modifies` と `impact: conforms` の区別に三つの判定がある。2026-10-28 の wi-18773 と wi-40431 では、どちらも区別の調整か、`spec-diff` の不具合による誤判定で作業が止まった。
- 宣言の理由の文が「何が変わらないか」を名指しているかを言い回しで判定する。
- 範囲内のコミットを一つずつたどり、コミットとファイルごとに `git show` などを呼ぶ。2026-10-29 の計測では、受け入れテスト 40 件に約 18 秒かかり、tools のテスト全体の約半分を占める。
- 本体は `spec-impact.ts` と `check-spec-impact.ts` を合わせて約 860 行、テストは約 1,300 行ある。

`Spec-Impact` トレーラーは直近 300 コミットのうち 33 で使われ、`TestCharacterize*` は 16 関数ある。
`impact` を持つ未完了の作業項目は 5 件ある。

## 対象範囲

残す判定：

- 範囲の仕様差分が変えた規範要素を、範囲で変わったどの作業項目も `affected_spec` に挙げていなければ拒否する。
- 本番コードを変える範囲が、作業項目の `affected_spec` か `spec_impact`、またはコミットの `Spec-Impact` トレーラーで宣言していなければ拒否する。
- `spec_impact: none` または `Spec-Impact: none` の範囲が、規範仕様か `TestCharacterize*` の本文を変えていれば拒否する。

削る判定：

- `impact: modifies` と `impact: conforms` の区別と、それに伴う三つの判定。`affected_spec` は「この作業項目が触れる規範要素」の一覧になる。
- 理由の文の言い回しの判定。理由は人が読む。

作りの変更：

- 作業項目の範囲は、範囲全体の差分で一度だけ判定し、コミットを一つずつたどらない。
- トレーラーは、作業項目を変えないコミットだけを個別に読む。

合わせて変えるもの：

- 作業項目のスキーマから `impact` を外し、未完了の作業項目 5 件から取り除く。
- 形式の文書、開発文書、スキルの該当箇所。

## 対象外

- 宣言の仕組みそのものの廃止。中核の検出は残す。
- `spec-diff` の差分の取り方の変更。

## 設計

### 削る判定を選んだ理由

- `modifies` と `conforms` の区別は、仕様を変えたか実装を合わせたかを作業者に二度判断させる。仕様差分に要素が現れるかどうかは機械が分かるので、区別を宣言させる必要がない。`conforms` に「その要素を名指すテストを足したか変えたか」を求める判定は、bugfix の主要ユースケースの証拠（`primary_use_cases`）が既に求める。
- 理由の言い回しの判定は、文を整えさせるだけで、宣言の正しさは確かめられない。

### 残す判定を選んだ理由

- 仕様の申告漏れの検出は、エージェントが仕様を黙って変えることを止める。
- 特性化テストの本文の検出は、エージェントが期待値を書き換えてテストを通すことを止める。範囲の差分で判定できるので、コミットをたどる費用はかからない。

## 計画

1. 残す三つの判定の受け入れテストを、範囲の差分で判定する形に書き、RED を確かめる。
2. 判定と読み取りを作り直し、削る判定とそのテストを除く。
3. スキーマ、未完了の作業項目、文書を合わせる。
4. 受け入れテストと `check` の所要時間を前後で比べる。
