# 属性の出どころと上流の書き込み範囲を識別する

## 動機

[wi-428](wi-428-upstream-attributes-and-effective-roles.md) は、上流の属性変更が動的な所属を通じて実効ロールへ波及する THREAT-067 を扱う。
その着手前調査で、User の属性値と属性定義には属性ごとの出どころがなく、SCIM の対応表も User 単位の識別しか提供しないことが分かった。
SCIM と Directory Connector は `sourceuser.Attributes.Apply` で同じ User へ投影し、JIT も `ProvisionFederatedUser` で通常の属性値を保存する。
この状態では、規則の参照属性と上流の書き込み範囲を照合できない。

## 対象範囲

- SCIM、Directory Connector、JIT とローカルの更新を比較し、属性の出どころと上流が書き込める範囲を識別する契約を決める。
- 中核属性とカスタム属性の双方を扱い、User がまだいない段階でも動的規則の参照属性を分類できるようにする。
- 属性の削除、ローカルでの上書き、取り込み元の解除と属性マッピングの変更時の扱いを決める。
- 決めた契約を所有する仕様へ反映し、保存、照会と必要な組み立てを実装する。
- 既存の由来が不明な値をどう分類するかを定め、メモリと PostgreSQL の保存で同じ結果を得る。

## 対象外

- 動的規則とロール付与の組み合わせを拒否するか、可視化して許可するかの最終決定と実装。wi-428 が担当する。
- SCIM の直接所属を通じた実効ロールの変更の制限。THREAT-083 として wi-428 が担当する。
- 取り込み元の認証と登録の方式の変更、CEL の文法拡張、ロールモデルの再設計。

## 設計

利用側の成立条件は、User の現在の値だけに依存せず、規則の参照属性が上流から更新され得るかを判断できることである。
現在の値だけに出どころを付ける方式では、User の作成前や新たな取り込み元の追加後に成立する組み合わせを、規則の保存時に検出できない。
上流の書き込み範囲を定義する方式と、値ごとの出どころを保持する方式を比較し、必要なら両方を使う。
上流から更新可能な属性を固定一覧で扱う案も比較し、JIT の属性マッピングと将来の設定変更をどこまで表せるか確認する。

着手前に次の問いを解決する。

- 「上流由来」を、最後に値を書いた主体、現在の管理主体、上流が将来書き込める属性のどれで判断するか。
- 管理者がローカルで上書きした後も、次の同期で上流が変更できる属性をどう分類するか。
- 既存の由来が不明な属性をどう扱い、その分類を利用側がどう観測するか。
- 属性マッピングが変わるとき、保存済みの規則との整合を誰が所有するか。
- JIT の任意属性、SCIM と Directory Connector の投影先の情報を、IdManagement が取り込み元の保存型へ依存せずに参照する方法は何か。

所有者と公開経路は、上の問いを解決してから決める。
公開範囲、依存または組み立て地点を変える場合は、境界の候補比較と型と操作のシグネチャを実装前に追記する。
`affected_spec` は既存の取り込みと JIT の規範を起点とし、Directory Connector、属性スキーマや新たな規範への影響は方式確定後に追加する。

## 計画

1. wi-428 の第二案と第三案が必要とする情報を具体例で比較し、利用側に必要な分類を確定する。
2. 所有者、操作、永続化と既存データの移行を設計し、対応する規範と主要ユースケースの証拠を追加する。
3. 最小の観測境界で RED を確認し、投影、保存と照会を実装する。
4. メモリと PostgreSQL の保存契約、テナント分離、失敗時の状態の保持を検証する。

## 検証

- 起票時は `mise run check-work-items` で規範参照と依存の形式、`mise run check-links` でリンクを検査する。
- 実装時の局所タスクとテスト名は、分類と所有者の確定後に選び、`primary_use_cases` へ記す。
- 同じ属性値でも上流とローカルの分類が異なる場合と、同じ User に両方が混在する場合を区別する。
- 値がない属性と User がまだいない場合を、上流が書き込めないという結論へ誤って丸める実装を検出する。
- 設定変更、同期の再試行、属性の削除と保存の失敗が、決めた分類と既存の状態を壊さないことを確認する。

## リスク

最後の書き込み元と、将来の書き込み権限を混同すると、追跡を加えても権限への波及を防げない。
既存データから出どころを復元できるとは限らないため、移行時に根拠なくローカルの属性として扱わない。
wi-428 の方針が必要としない汎用の来歴管理を導入せず、利用側の成立を確かめてから実装範囲を決める。
