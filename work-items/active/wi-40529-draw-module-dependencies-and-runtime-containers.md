# モジュール間の依存を生成図で示し、実行単位と通信の図をランタイムアーキテクチャへ移す

## 動機

[論理アーキテクチャ](../../docs/design/architecture/logical.md)と[ランタイムアーキテクチャ](../../docs/design/architecture/runtime.md)には図がない。
論理アーキテクチャのモジュールの責務の表は、境界検査の入力として正しく保たれている。
しかし、どのモジュールがどのモジュールに依存するかは、表からもコードからも一目では読み取れない。

実行単位とその間の通信を描いた図は、[デプロイメントアーキテクチャ](../../docs/design/architecture/deployment.md#共通トポロジー)の「共通トポロジー」にある。
[文書ガイド](../../docs/formats/documentation-guide.md#要件文書と全体設計文書)では、実行単位と主要な相互作用は `runtime.md`、実行単位と配置先の対応は `deployment.md` が扱う。
図が担当外の文書にあるため、ランタイムアーキテクチャの読者は表と文章だけで通信を組み立て、デプロイメントアーキテクチャには配置以外の関心が混ざっている。

[wi-88697](../done/wi-88697-select-purposeful-mermaid-diagrams.md)の起票時の調査は、この図を「別の Container 図を足すと二重管理になる」として維持した。
図を足すのではなく担当の文書へ移すという選択肢は検討していなかった。

## 対象範囲

- 論理アーキテクチャに、モジュール間の依存を文書サイトの生成時に描く図を加える。手書きの図は置かない。
- デプロイメントアーキテクチャの共通トポロジーの図を、ランタイムアーキテクチャへ C4 の Container 図として移す。デプロイメントアーキテクチャには、その図への参照と、配置に固有の要素だけを残す。
- [設計フォーマット](../../docs/formats/design-format.md#図)の図種の表に、モジュール間の依存と実行単位の通信の行を加える。
- 移した図と生成図を、生成サイトの明色、暗色、拡大表示、狭い画面で確認する。

## 対象外

- モジュールの責務、公開範囲、依存の規則、境界の負債の変更。
- 実行単位、通信、配置、デプロイプロファイルの変更。
- デプロイプロファイルの図の C4 化。通信、制御、未作成要素の区別を保つため flowchart を維持する（wi-88697 の判断）。
- モジュールの内部の Component 図、コード階層の図。
- 図の数や図種の採用を目標にすること。

## 設計

### モジュール間の依存の図

生成元は境界検査と同じ入力とする。
論理アーキテクチャの責務の表（`parseLogicalArchitecture`）でパッケージの所有者を決め、Go のソースの import をモジュール間の辺へ集約する。
文書サイトの描画器は、論理アーキテクチャのページの「モジュールの責務」の表の後に、この辺から作った図を差し込む。
状態遷移の表から状態図を生成する既存の仕組みと同じく、図の写しを Markdown に置かない。

| 候補 | 利点 | 欠点 | 採否 |
| --- | --- | --- | --- |
| 境界検査の入力から生成する | 責務の表とコードから常に導かれ、写しが古くならない | 描画器に Go の import の集約を加える | 採用 |
| 論理アーキテクチャに手書きする | 描画器を変えない | 依存を変えるたびに更新が要り、検査されない写しが表やコードと食い違う | 不採用 |
| 依存の行列を表で生成する | 辺が多くても重ならない | 依存の向きと集まり方を一目で読めない | 図が読めない場合の代替として残す |

辺は実際の import を描き、境界の負債（`tools/check/boundary-debt.json` に記録した違反）に当たる辺は破線で区別する。
組み立て地点（System）と共有ライブラリ（shared）はすべてのモジュールとつながるため描かず、その旨を図の導入に書く。
図種は C4 の Component の粒度にあたるが、Mermaid の C4 図は自動配置で 20 を超える要素の辺が重なるため、`flowchart` を第一候補とし、表示の確認で決める。
着手時に、モジュール数と辺の数で読める図になるかを確かめ、読めなければ依存の行列の表へ切り替える。

### 実行単位と通信の図

共通トポロジーの図のうち、実行単位（API、Worker のレーン、Batch、Seed、フロントエンドゲートウェイ）、PostgreSQL、外部当事者と通信を、ランタイムアーキテクチャの「通信」の節へ C4 の Container 図として移す。
エッジのロードバランサー、スケジューラー、デプロイ工程、スキーマ適用など、配置と起動に固有の要素は、デプロイメントアーキテクチャに残すか、配置先の表で示す。
図の数は増やさない。
C4 の Container は Docker のコンテナではなく、この文書群の実行単位にあたる。
ラベルの位置の調整と表示の確認は、設計フォーマットの図の規則に従う。

### 設計フォーマットの図種の表

| 読者の問い | 図種 | 粒度 |
| --- | --- | --- |
| モジュール間の依存 | 境界検査の入力から生成する図 | モジュールを要素とし、組み立て地点と共有ライブラリは描かない |
| 実行単位と通信 | C4 の Container 図 | 実行単位を要素とし、モジュールは描かない |

既存の「実行単位の配置と通信、処理の分岐」の行は、配置と分岐に絞る。

## 計画

1. 着手時に、モジュール数、モジュール間の辺の数、境界の負債の辺を数え、生成図が読めるかを試作で確かめる。
2. 描画器にモジュール間の依存の集約と図の生成を、テストを先に失敗させてから加える。
3. 共通トポロジーの図を Container 図としてランタイムアーキテクチャへ移し、デプロイメントアーキテクチャを配置の内容に絞る。
4. 設計フォーマットの図種の表を更新する。
5. 生成サイトで表示を確かめ、検証して完了する。

## 検証

- `mise run test-tools`、`mise run lint-tools`、`mise run typecheck-tools`：描画器と境界の解析の変更を対象に選ぶ。
- `mise run check-site`、`mise run check-links`、`mise run check-terminology`、`mise run check-work-items`：移した図と文書の参照、用語、作業記録を対象に選ぶ。
- `mise run check-boundaries`：境界検査の入力の解釈を共有するため、結果が変わらないことを確かめる。
- `mise run spec-diff`：規範の差分がないことを確かめる。
- `mise run build-site` で再生成したページを、ヘッドレスの Chrome で `--screen-info` で画面幅を指定して確認する。

## リスク

モジュールが 20 を超えるため、生成図の辺が重なり読めない可能性がある。
試作で判断し、読めなければ依存の行列の表へ切り替える。
共通トポロジーの図を分けると、デプロイメントアーキテクチャの「図は次の順に読む」の説明が二つの文書にまたがる。
通信の説明はランタイムアーキテクチャへ移し、デプロイメントアーキテクチャは配置の順だけを書く。
