# ブラウザー E2E の速度と運用負担を比較し、実行基盤の採否を判断する

## 動機

現在のブラウザー E2E は `bun:test` と Bun.WebView で実行している。
Playwright 1.65 が Bun 上でのテストランナー実行に対応したため、現行構成の継続と Playwright の導入を比較できる。
ただし、Bun.WebView にはランタイムへの組み込み、追加依存の少なさ、既存の起動と状態初期化の最適化を使える利点があり、速度と資源使用量でも有利な可能性がある。
機能一覧や自作コードの量だけでは採否を決められないため、実際の E2E を使って比較する。

本項目は調査と判断のための起票であり、Playwright への移行は未決定である。
[先行比較メモ](../../docs/development/e2e-runner-comparison.md)の推奨は性能未計測の仮説として扱い、採用の前提にしない。

## 対象範囲

- Bun.WebView の現行構成を基準として、速度、資源使用量、安定性、診断、導入と更新、保守の負担を比較する。
- Playwright Test を Bun または Node.js で動かす構成を候補に含める。
  `bun:test` と Playwright Library の組み合わせや他の方式は、主要候補で満たせない条件がある場合に比較へ加える。
- 同じ利用経路と期待結果を持つ少数の評価用シナリオを用意し、既存構成への影響を限定して測定する。
- 継続、限定的な併用、移行、判断保留のいずれも選べる形で根拠と再検討条件を整理する。

## 対象外

- 既存 E2E の全面移植、既定ランナーや CI の実行基盤の切り替え。
- 現行の共通処理やテストの削除、製品コードや公開契約の変更。
- 比較と同時に行うテストの並列化やバックエンド状態分離の再設計。
- Playwright 導入や速度向上を、測定前に完了条件とすること。

## 設計

### 採否は比較後に決める

| 候補 | 確認する利点 | 確認する負担 |
| --- | --- | --- |
| Bun.WebView を継続 | 組み込み API、追加依存の少なさ、起動と操作の速度、ブラウザー再利用、既存資産の活用 | 共通ヘルパーと状態初期化の保守、実行環境による差、障害の切り分け |
| Playwright Test と Bun | Bun 固有の準備処理の活用、locator、assertion、fixture、BrowserContext、trace | ランナーと操作 API の移植、実行時間と資源使用量、ブラウザー管理、Bun 固有の制約 |
| Playwright Test と Node.js | Playwright の診断と開発支援、Bun 固有の制約を避けられる範囲 | Node.js の管理、Bun 固有の準備処理の分離、実行時間と資源使用量 |

いずれの候補も採用済みとせず、利点が実際の作業時間や障害調査の改善につながるかを確認する。
現行構成の不足を小さく改善する案も、移行費用との比較対象にする。
本項目の完了は選択理由を説明できることであり、移行の実施を条件にしない。
移行や恒常的な併用を選ぶ場合は、その実装を別の作業項目として起票する。

### 速度を公平に比較する

- 同じホスト、ブラウザーエンジンと版、viewport、サーバー、seed、利用経路、期待結果、worker 数を可能な範囲でそろえる。
  macOS の WKWebView と Chromium の比較は、ランナーだけの差と混同せず別条件で扱う。
- Go のビルドとサーバー起動、ランナーとブラウザー起動、シナリオ実行、状態初期化と終了処理を分け、全体時間も測る。
- 初回導入とキャッシュなしの実行、準備済み環境での反復実行を区別する。
  全体実行に加えて、開発中の単一 spec の再実行も比較する。
- 現行のブラウザープロセス再利用と Cookie 消去を維持し、片方だけ毎回起動し直す条件で優劣を決めない。
- trace や動画などの取得条件を明示し、取得なしと、実運用を想定する診断設定の費用を分ける。
- 測定回数、実行順、集計方法と判断基準は測定前に決める。
  中央値とばらつき、失敗件数、サンプル数を示し、再試行の時間を隠さない。

### 速度以外の評価

認可から外部 callback への遷移、フォーム操作、キーボード操作、セッションの分離を代表シナリオとして選ぶ。
移植で待機条件や期待結果を弱めず、意図的に壊した操作を検出できるかも比較する。
ブラウザーと子プロセスを含むメモリー使用量、CPU 使用量、ダウンロード量、CI の準備時間を確認する。
失敗時のログ、画面、DOM、通信から原因を特定できるか、ローカルでの再現と変更監視が使えるかを評価する。
独自コードの削減量だけでなく、残る製品固有の準備処理、依存の更新、移行の工数も含める。

## 計画

1. 着手時点の公式仕様と現行実装を確認し、未確認の利点と制約を分ける。
2. 比較するシナリオ、測定条件、診断設定、許容する負担と判断基準を定める。
3. 現行構成の基準値を測り、隔離した評価用構成で候補を比較する。
4. 現行継続を含めて採否を判断する。
   証拠が不足する場合は、不足する条件と再検討時期を示して判断を保留できる。
5. 結論を担当する開発文書へ反映し、実装が必要な場合だけ別項目を起票する。

## 検証

- `mise run check-work-items`：作業項目の形式と仕様影響の宣言を検査する。
- `mise run check-links`：関連する文書とコードへの参照を検査する。
- 着手後の基準測定には `mise run test-ui-e2e` と `mise run test-ui-e2e-file -- <spec>` を使う。
  評価用構成を反復実行するタスクは必要に応じて `mise.toml` へ追加し、ブラウザー起動を伴う実行は最初からサンドボックスの外で行う。
- 同じ期待結果と故障を判定していること、ブラウザー状態と共有バックエンド状態を区別していることを確認する。
  起票時には測定やブラウザー起動を行わない。

## リスク

異なるブラウザー版、キャッシュ、サーバー起動、診断設定の費用がランナーの差に見えるおそれがある。
条件と時間の内訳をそろえ、そろわない条件は比較の限界として示す。
少数回の成功だけで安定性を断定せず、未測定の範囲を残す。
共通バックエンドの競合をランナーの不安定さと誤認しないよう、最初は直列で比較する。
先行メモや試作への投資が移行の既定路線にならないよう、現行継続の利点と移行しない判断を同じ基準で扱う。
