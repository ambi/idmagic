# tools の Go 検査を棚卸しし、golangci-lint に任せられる規則を移す

## 動機

`tools/` は Go ソースを読み、import、層の依存、作用、SQL の呼び出し、HTTP 契約、セキュリティ統制、テストの規範参照などを独自に検査している。
このうち汎用の静的検査には、既に利用している golangci-lint の機能と重なるものがある。
たとえば `check-boundaries` は import 文を行単位の正規表現で抽出し、層の依存検査では引用符内の文字列も import 候補として拾う。
Go の構文を読む実装とその例外を独自に保守する前に、depguard をはじめとする既存の linter へ検査を引き継げるかを比較する。

検討だけで終えず、検出範囲を保って任せられる規則を移し、不要になる検査実装とテストを削除する。
リポジトリ固有の入力や複数パッケージの関係を必要とする検査は、残す根拠を規則ごとに明らかにする。

## 対象範囲

- `tools/` 全体で Go ソース、本番パッケージ、Go テストを解析して診断や検証結果を作る処理を棚卸しする。
  `tools/check` だけでなく、`tools/verification` と関連する照会ツールが共有する解析処理も確認する。
- 各規則の一次情報、入力、対象ファイル、検出する故障、除外、例外管理、実行条件と利用側を整理する。
- 現在固定している golangci-lint のバージョンで、depguard、forbidigo、既に有効な linter と追加候補の適用可否を公式文書と実行で確認する。
- 採用する設定、必要な設定生成、`mise` タスク、CI と差分検証の接続、関連する開発文書と設計文書を更新する。
- 引き継ぎを確認した独自規則、重複したソース解析、不要になるテストと例外管理を削除する。
  他の検査や依存図の生成が使う処理は、利用側を確認してから変更する。

## 対象外

- 製品の振る舞い、モジュールの責務、公開範囲、依存を許す基準の変更。
- 棚卸しで発見した製品コードの違反の一括修正と、検査を通すための規則の緩和。
- Go 以外の検査の全面的な再設計、依存関係の一括更新、独自 linter 基盤の新設。
- 汎用 linter で代替できない検査を、一律に Go へ書き直す作業。

## 設計

### 規則ごとに担当を選ぶ

比較には[リポジトリ検査の判定基準](../../tools/check/README.md#検査の判定基準)を使う。
棚卸し表には、規則、実装、一次情報、現行の検出範囲、候補 linter、差異、採否と理由、引き継ぎ先の実行入口を記す。
一つの検査に汎用規則とリポジトリ固有の規則が混在する場合は、規則単位で移す。

| 最初に比較する対象 | 候補と確認する問い |
| --- | --- |
| 非公開パッケージ、共有ライブラリ、組み立て地点、層の import 制限 | depguard で現行規則を表せるか。責務表に従う設定が必要か |
| domain の作用と起動設定の読み取り | import の禁止とシンボルの使用禁止を分け、depguard や forbidigo で対象の場所と例外を表せるか |
| SQL の直接呼び出し、セキュリティ統制、その他の Go コードの規則 | 汎用の検出と、理由付きコメントや製品固有の保証の照合を分け、既存 linter と重なる部分を移せるか |
| モジュール単位の循環、公開宣言の整合、テーブル所有権 | パッケージの検査だけで保証できるか。別の検査に残す入力と判断は何か |
| HTTP 契約、イベント、仕様とテストの参照、検証結果の集計 | 外部の宣言や実行記録との照合を要する部分と、汎用の静的検査を分離できるか |

この表は調査の起点であり、移行可否を確定した一覧ではない。
着手時に `tools/` 全体から漏れを補い、実装を変える前に規則ごとの採否を設計へ追記する。

### 宣言と実行範囲を保つ

採用案は、手書きの linter 設定、正準入力からの設定生成、独自検査の継続を比較する。
モジュールと公開パッケージの一次情報は[責務表](../../docs/modules/README.md#モジュール)に保ち、同じ一覧を設定へ手で複製しない。
生成を採る場合は、設定の生成経路と古い設定を拒否する入口を決める。
個別のモジュールの組ごとの許可一覧を追加して、現在の[共通規則](../../docs/design/application/backend.md#モジュール間の依存規則)を置き換えない。

現行の境界検査は、ビルドタグを評価せず本番の `.go` を走査する。
移行先の OS、アーキテクチャ、ビルドタグ、生成コード、`_test.go`、テスト補助の扱いを比較し、対象が減る変更を黙って含めない。
既存違反の台帳と基準 revision からの増加防止も、引き継ぎか不要となる根拠を確認する。
広い除外や `nolint` の追加によって、新しい違反が通る状態にしない。

### 代替案と未決事項

- 全検査を独自実装のまま残す案は、既存 linter で同じ故障を検出できる部分については採らない。
- 全検査を golangci-lint へ押し込む案は、リポジトリ固有の照合や実行記録を扱う責務まで混在させるため採らない。
- 独自解析を残す場合は、必要な検出範囲と利用側を特定し、現行の文字列解析を維持する費用と Go 標準の構文解析器を使う費用を比較する。
  import の抽出はモジュールの循環検出や依存図にも使うため、depguard の採用だけを根拠に削除しない。
- 設定生成の要否、残す解析処理、既存違反の移行方法、lint の対象を補う実行条件は、調査後、対応する実装を始める前に確定する。

## 計画

1. Go の検査と解析処理の利用側を棚卸しし、候補 linter の対応表を作る。
2. 小さな入力で候補を実行し、対象範囲、誤検出、見逃し、例外管理、実行時間を比較して採否を決める。
3. 担当する開発規則と設計を先に更新し、採用する設定と `mise`、CI の実行経路を実装する。
4. 代表的な違反を注入して引き継ぎ先の拒否を確認し、対応する独自規則と不要な解析処理を削除する。
5. 残した規則の理由と実行入口を現在状態の文書へ反映し、差分に応じた検証を行う。

## 検証

- `mise run lint-go` と必要に応じた `mise run lint-go-openldap`：採用した設定を実際の対象コードとビルドタグで実行する。
- 移行先の `mise` タスクによる故障注入：禁止 import、import 別名、シンボル参照、コメントと文字列、許可する例外を比較し、同じ故障を止めることを確かめる。
  複数ファイルとパッケージの入力が必要な規則は、その範囲で確認する。
- `mise run test-tools-file -- <対象ファイル>`：変更した設定生成、分類、残る独自規則の検出能力を確認する。
- `mise run check-boundaries` と `mise run check-boundary-debt-ratchet -- <基準 revision>`：境界の検査を変更した場合、引き継がない規則と既存違反の増加防止を確認する。
- `mise run verify-changed -- <基準 revision>`：実装後の差分に応じ、検査の登録、設定、CI と利用側の接続を確認する。
- `mise run check-work-items` と `mise run check-links`：作業項目と更新文書の形式、参照を確認する。

## リスク

- lint が読み込む対象と独自検査の走査範囲が異なると、検査対象が減る。
  OS とビルドタグを含めた対象表を作り、必要な条件ごとに故障を注入する。
- 規則の移行と同時に例外を広げると、新しい違反を検出できなくなる。
  既存の例外だけを区別し、正常な入力と新しい違反を対にして確認する。
- 共有解析の削除で、契約の照合、検証結果、依存図の生成が壊れる。
  利用側を棚卸しし、独自規則の削除と共有処理の削除を区別して判断する。
- 設定生成や検査の反復実行で、保守量や実行時間が増える。
  採用前後の設定、実装とテストの量、実行時間を比較し、移す範囲を決める。
