# 最初の実装の時点で、後からリファクタリングと bugfix の項目が要る問題を減らす

## 動機

作業項目を実装するたびに、設計として不十分な形が入り、後からリファクタリングや bugfix の作業項目を足す、という循環が続いている。
ゼロにはできないが、最初の実装の時点で解消済みにできる問題を増やしたい。
不足しているのは、そうした問題を実装の時点で見つけて止める仕組みである。

この項目は一度で完了させない。
ほかの作業項目を実装するたびに、その実装で見つかった「後から直すことになった形」を観察の記録に足し、原因の分類と改善案を少しずつ磨く。
改善案のうち、効果と費用の見込みが立ったものから個別に実装する。

## 対象範囲

- 実装の後から直すことになった形を、作業項目を実装するたびに記録する。
- 記録を原因ごとに分類し、それぞれを最初の実装の時点で止める仕組み（スキルの手順、機械の検査、設計の規則、テストの形）を提案する。
- 効果の見込みが高く、小さく入れられる仕組みから実装する。大きなものは個別の作業項目に分ける。

## 対象外

- 既存の不十分な形そのものの修正。それぞれの作業項目で行う。

## 設計

### 案 10 の設計

`collectOperationReferences(source, operationIds)` は、受理した操作とテスト名の対応、および行番号付きの所見を返す。
`collectReferences` と registry の `operation-references` 検査は、この同じ結果を使う。
操作 ID の一覧は生成 OpenAPI から得て、手書きの台帳を増やさない。
宣言のコロン、観測内容、既知の ID、直上のテストへの対応を確かめる。
テスト関数の判定は既存の `specCitingTests` を使い、本文中、補助関数前、空行で離れた宣言は対応なしとして報告する。
受理した参照の件数とテストの実行成功を区別し、`evaluateVerification` の実行結果の条件は変更しない。

独立した製品要件がない tooling なので、受け入れ RED は registry を通る最小 workspace fixture、単体 RED は収集器へ渡す不正な宣言で代替する。
両者でコロン欠落、観測内容欠落、未知の ID、対応しない配置を診断し、有効な宣言の収集を対照とする。
生成した既知の ID と改変した ID の組で厳密性を検査し、診断を検査へ接続し忘れる故障も注入する。
既存の skipped、not-run、failed の判定は既存テストで回帰を確認する。

今回の実装後も T001 の継続観察を残す。
項目全体は `in_progress` のまま保ち、実装と検証をこの記録へ追記してコミットする。

文書とスキルだけの判断手順は、実在する参照、タスク、生成表示の検査と差分のレビューで検証する。

## リスク

- 規則や検査を増やしすぎると、実装の費用が上がり、規則を形式的に満たすだけの変更が増える。
  改善案は観察が繰り返された分類に限り、効果を以後の観察で確かめる。
- 契約の期待値を既存の実装から写すと、その実装の欠陥を固定する。
  要件と TypeSpec の矛盾を分類してから独立した期待を置き、観測する契約が増えた分だけ検出する故障を具体化する。
- 原因の分類だけで汎用検査を増やすと、誤検出と全体の実行費用が増える。
  直接診断できる形式、実行して確かめる振る舞い、測って選ぶ検証範囲を分け、既存の道具で足りる部分を再実装しない。
