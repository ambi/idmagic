# リソースアクセス条件のコンパイル費用を測り、追加対策の要否を決める

## 動機

[[wi-38529-align-the-condition-expression-length-limit]] は、条件式の上限を 1024 コードポイントにそろえた。
その結果、式が取り得る UTF-8 のバイト数は最大 4096 になった。
元の項目では CEL の解析費用への影響も確かめる予定だったが、実施したのは受理範囲と応答の検証であり、費用の測定は残っている。

`backend/oauth2/domain/resource_access_condition.go` は、条件を評価するたびに式をコンパイルする。
`cel.CostLimit(10000)` はプログラムの評価費用を制限するが、先に行う `env.Compile` の費用を測定した証拠にはならない。
内包の入れ子の検査もあるが、長さの上限内の構文による時間とメモリ使用量は未測定である。
現時点で性能目標への違反や追加制限の必要性は確認していないため、採否の判断から始める p3 とする。

## 対象範囲

- 1024 コードポイントの上限内で、ASCII、日本語、BMP 外の文字を含むリテラル、演算子や括弧の多い式、内包と正規表現を使う式のコンパイル費用を測る。
- 有効な式と構文エラーを分け、初期化を含む初回と初期化後の反復で、時間と割り当てメモリを記録する。
- 一回の判定で二つの式をコンパイルする場合と、同じ保存済みの式を繰り返し評価する場合を含める。
- [リソースアクセス評価の局所測定](../../docs/requirements/quality.md#リソースアクセス評価の局所測定)とサービス目標へ影響を照合し、現状維持か追加対策かを判断する。
- 対策が必要なら、観測した問題、受け入れ条件と仕様への影響を持つ後続項目を起票し、この項目の完了要約から追跡できるようにする。

## 対象外

- 1024 コードポイントという上限値の変更。
- 測定の根拠なしにコンパイルの時間制限、構文の追加制限やキャッシュを導入すること。
- 本番の混合負荷、TLS、ネットワークを含むキャパシティ受入れの代替。

## 設計

ドメインのベンチマークでコンパイルの費用を分離し、正式な HTTP ルートの既存の測定と照合する。
費用を測る入力は、長さ、バイト数、構文の種類、コンパイルの成否を明記し、検証した境界が分かる形で残す。
既存の測定方法は [リソースアクセス評価の実現方式](../../docs/modules/oauth2/features/resource-access.md#実現方式)と [性能設計](../../docs/design/performance/README.md)を参照する。

| 候補 | 判断する条件 |
| --- | --- |
| 現状の長さと CEL の制限を維持する | 計測した条件でも既存の性能目標を満たし、コンパイルが律速にならない |
| CEL の解析や構文への追加制限を検討する | 上限内の特定の構文で費用が偏り、既存の目標を満たせない。受理する式への影響を仕様の段階で決める |
| コンパイル済みの式の再利用を検討する | 同じ式の反復コンパイルが律速である。メモリ上限、テナント境界、条件変更の反映を含めて比較する |

独立した判断は、許容する費用の根拠、費用が偏る入力、対策の必要性である。
実装方針を先に選んで、それを測定の目的にしない。

## 計画

既存の性能目標と測定境界を確認し、入力の組を固定して局所測定を行う。
正式な HTTP ルートで影響を確かめ、対策不要の根拠または具体的な後続項目を残す。

## タスク

- [ ] T001 [Design] 既存の性能目標と CEL の既存制限を確認し、比較する入力と測定手順を決める。
- [ ] T002 [Measurement] コンパイルと評価を分けて時間と割り当てメモリを測り、初回と反復、成功と構文エラーを区別する。
- [ ] T003 [Acceptance] 正式な HTTP ルートで条件ありと条件なしを比較し、目標と測定の限界に照らして対策の要否を判断する。
- [ ] T004 [Decision] 根拠を所有文書へ残す。対策が必要なら、仕様影響、受け入れ条件と検証方法を持つ後続項目を起票する。

## 検証

- 局所測定には `mise run benchmark-go-package -- ./backend/oauth2/domain <ベンチマーク名> <反復数>` を使い、実行時間、CPU、入力と反復条件を記録する。
- HTTP の測定には `mise run measure-resource-access` を使い、引数は実装時にタスク定義を確認する。localhost と DB を使う測定はサンドボックス外で行う。
- コードを加えた場合の最終検査は `mise run verify-changed -- <着手時の基準リビジョン>` とし、文書だけなら `check-work-items` と `check-links` を使う。

## リスク

局所測定の数値を本番の性能保証に広げると、異なる負荷やデータ量で成立しない結論になる。
測定の環境と境界を示し、既存の性能目標自体はこの項目で変更しない。
