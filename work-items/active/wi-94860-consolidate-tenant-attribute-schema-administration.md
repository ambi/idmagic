# テナント属性定義の管理と表現の重複を整理する

## 動機

[wi-53317](../done/wi-53317-decouple-tenant-attribute-schema-from-identity-types.md) は Tenancy と IdManagement の循環を切ったが、属性定義のほぼ同じ型を Tenancy に追加し、`tenancydeps/attribute_schemas.go` に153行の相互変換を置いた。
属性の型と公開範囲も列挙から文字列へ変換して戻しており、属性を追加すると双方の型と変換を同期する必要がある。
管理 API の所在を固定してポートを増やした判断を見直す。

## 対象範囲

User と Group の属性スキーマの管理、検証、組み込み属性、動的 Group による参照保護と正式な HTTP の結線。
Tenancy の属性定義、管理ユースケースと `tenancydeps/attribute_schemas.go` の二重表現を対象にする。

## 対象外

属性の意味、API のパスと本文、PII とクレームの公開規則、テーブル所有者とデータ移行の変更。
検証済みメールだけを使う通知先の照会など、別の意味を持つ小さな射影は一律に除去しない。

## 設計

D1、D2、D3、D4、D6、D8 を適用し、[属性定義](../../docs/modules/tenancy/features/attribute-schema.md)と IdManagement の所有状態、実際の更新元を起点にする。
属性定義の意味と保存を IdManagement に残す制約の下で、管理自体を IdManagement へ集める案、上位の管理の編成から所有者の公開操作を呼ぶ案、現状を維持する案を比較する。
URL の所属から実装の担当を決めず、同じ変更理由を持つ型、検証と更新を集約する。
属性追加の実例について、各案で必要な型、変換、利用側と検証の変更を列挙する。
共有パッケージへ業務の型を移すだけの案と、Repository を複製する案は採らない。
動的 Group の参照保護、テナント境界、組み込み属性の上書き禁止、保存前の拒否を維持できる案を着手時に確定する。

## 計画

現在の保証と変更の波及を調査し、上記の候補を比較して担当と公開操作を決めてから実装する。
不要になる型と相互変換を除去し、公開範囲と現在の設計を同期する。

## 検証

既存の User と Group の属性定義の管理テスト、動的 Group の参照保護と正式な HTTP の結線を起点にする。
`test-go-changed`、`lint-go`、`check`、`spec-diff` に加え、拒否の省略と項目の脱落を独立した故障として検出する。
着手時に実際の差分に応じた RED と変更耐性の手順を確定する。

## リスク

型の集約を理由に保存型を任意に更新できる契約を公開したり、列挙、参照保護と公開制限の検証を失ったりすること。
循環の数と行数を成功条件にせず、保証の維持と変更時に同期する場所の減少を確認する。
