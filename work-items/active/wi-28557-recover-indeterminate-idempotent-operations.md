# 結果が不明な冪等要求の回復方法を決める

## 動機

[wi-604](../done/wi-604-accept-idempotency-key-on-admin-post.md) は共通の受付記録と応答の再生を扱う。
作用が確定した後に応答の保存に失敗した要求は、自動で再実行せず、保持期間中は 409 で拒否する方式を選んだ。
API トークンやクライアントシークレットの平文は業務の保存先に残らないため、応答を保存する前に停止すると自動では復元できない。
Jobs の `dedup_key` も未終端のジョブだけを対象とし、完了後の再送を排除する保証にはならない。

利用者は、各操作の保存を組み替える複雑さを初回の実装へ持ち込むより、回復を別項目にして制限を明示する選択を認めた。
本項目では、回復が必要な操作と許容できる費用を確かめて方式を決める。
初回リリースに追加の回復保証を必要とする根拠は未確認なので、グループの基準より低い p3 とする。

## 対象範囲

- 同じキーの要求に対する 409 の後に、状態の照合、資格情報の失効と再発行で運用できるかを確認する。
- 回復が必要な操作では、業務状態と暗号化した結果を同時に確定する小さい保存境界を比較する。
- ジョブ投入では、完了したジョブにも届く結果参照と、受付記録への関連付けを比較する。
- 回復を提供する場合の認可、保持期間、失効した資格情報の扱いと、再実行できる条件を確定する。

## 対象外

- [wi-77197](wi-77197-evaluate-repository-local-transactional-outbox.md) が扱う監査の配信保証。
- 任意の HTTP ハンドラーを一つのトランザクションで囲む方式。
- 必要性を確かめる前に全管理操作へ共通のコマンド実行基盤を導入すること。

## 設計

回復を必要とする具体的な利用経路が確認できなければ、wi-604 のフェイルクローズを維持する。
必要な場合も、最初に API トークン、クライアントシークレット、長時間実行操作のいずれか一つを選ぶ。
共通化する範囲と各所有者が守る原子性を、境界を選ぶ判断手順で比較してから実装する。
HTTP 応答、業務上の結果、再開可能な操作の進捗を区別する。

### 既存製品との比較

2026-11-22 に公式資料の本文を確認した。
[Stripe API v1](https://docs.stripe.com/api/idempotent_requests) は 500 を含む保存済みの応答を再生する。
[AWS](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/) は要求識別子と作用の原子的確定を重視する。
両者の保証を混同せず、必要な回復の範囲を決める比較材料とする。

## 計画

1. 結果不明が残った場合の利用者の作業と、必要な回復保証を確認する。
2. 現行方式の維持、操作ごとの結果の原子的保存、再開可能な操作を比較する。
3. 採用する保証を仕様へ反映し、必要なら対象を絞って実装する。

## リスク

タイムアウト後の応答再生と、プロセス停止後の自動回復は異なる保証である。
復元できない平文シークレットを再生成すると、再送が新しい資格情報の発行に変わるため、同じ結果への回復と扱わない。
