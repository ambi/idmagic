# デプロイ構成ごとの本番準備の不足を検証証拠から判定する

## 動機

[リリース手順](../../docs/development/release.md)は外部のリリース経路を前提とし、[CI](../../docs/development/continuous-integration.md#ci-で検証しないもの)はインフラ資産の検査を変更者へ委ねる。
キャパシティは未実測、本番 RPO/RTO は未確定で、可用性にも未実装の対処がある。
不足は一次情報文書に書かれているが、どのデプロイ構成を本番で使えるかの判定には結び付いていない。

現在は未リリースであり、当面も未リリースを継続する。
本番リリース判定と公開後の互換性準備の重要性は現時点では低く、p3 とする。
初回リリースの時期、対象デプロイ構成、運用責任の分担が具体化した時点で再評価する。
この項目を日常開発の前提にせず、未リリースの各変更へ本番の検証証拠を要求しない。

## 対象範囲

- デプロイ構成ごとに、必要な実装、検証済みの証拠、未実測、未確定、阻害要因を導出する表示と判定。
- 変更したインフラ資産に対応する検査を CI で必須にする条件と、検査依存の取得コストの削減。
- 将来のリリース経路が残す成果物、Git revision、スキーマ、移行、展開結果の対応の契約。
- 本番相当の負荷、障害、復元と鍵の復旧、監視と運用判断について、証拠を要求する条件の明示。
- リリース経路が整備された後に、展開結果と障害の対応から開発プロセス指標を再計算できる形。

## 対象外

- 本番へのデプロイ、外部のレジストリやクラウド設定の変更。
- この項目だけで、可用性、性能、鍵管理、トレースの不足をすべて実装すること。
- 本番の RPO/RTO や未定義の SLO を根拠なく設定すること。
- 成果物の署名と来歴は[供給網の保護](wi-100-supply-chain-sbom-cosign-slsa-provenance.md)、混在更新は[混在版の検証](wi-450-mixed-version-release-acceptance.md)が扱う。

## 設計

既存のリスク、品質要件、デプロイ設計、検証結果と作業項目を入力とし、手書きの本番準備台帳を別に作らない。
準備済みの判定は、選択した構成、成果物、検証条件に対してだけ成立させる。
文書の存在、構成ファイルの存在、実環境での検証結果を区別し、未確定な条件を合格へ丸めない。
インフラの検査は変更対象と検査器自身の変更から選び、変更のない資産へ毎回重い検査を要求しない。

着手時に、初回リリースの対象構成、必要な証拠と有効性の条件、リリース経路の役割分担を決める。
実装不足の是正は既存の所有項目へ委ね、不足の判定を通すために品質目標を下げない。
error budget の消費後の変更判断は運用体制に合わせて決め、検査ツールが独断で製品の品質契約を変えない。

| 案 | 判断 |
| --- | --- |
| 一次情報と実行結果から構成別の不足を派生表示する | 採用候補。現在の設計と証拠の差を追跡できる |
| 手書きの本番準備チェックリストを追加する | リスクと検証結果の写しが独立に古くなるため採らない |
| 未リリースの全変更へ本番証拠を要求する | 現在の開発段階に合わず、検証条件も用意できないため採らない |

## 計画

1. 着手時の初回リリース計画と対象構成から、本番で必要な保証と証拠を選ぶ。
2. 既存文書と結果からの導出、未検証の判定、証拠の有効性を設計する。
3. 未実装、未実測、別成果物の証拠を合格へ丸める判定で RED を確認する。
4. 表示と検査の実行条件、リリース経路に残す記録を整備する。
5. 不足を所有する項目と対応付け、実環境での検証が揃うまで本番準備済みと表示しない。

## 検証

- mise run test-tools-file で準備状況の導出と証拠の判定を実行する。
- 変更対象に応じて mise run check-compose、mise run check-k8s、mise run check-monitoring、mise run check-k6 を実行する。
- 未実装、未実測、証拠の欠落、異なる構成や成果物の証拠が、本番準備済みと判定されない。
- 構成の構文検査やローカルの復元試験を、実環境の可用性や RPO/RTO の証拠へ昇格させない。
- 不足を所有する作業と一次情報への参照が解決できる。
- mise run check-links、mise run check-work-items、mise run verify を実行する。

## リスク

不足の表示を埋めるためだけに文書や数値を増やすと、実際の本番準備との差が隠れる。
一次情報の実装状況と条件付きの証拠を導き、準備済みのラベルを先に付けない。
未リリースという前提を着手時に確認し、リリース予定がない間は実装の優先度を上げない。
