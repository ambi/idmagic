# モジュールの README を概要と道案内に絞り、モジュールの `architecture.md` を廃止する

## 動機

モジュールの `README.md` は、責務と境界、Aggregate の一覧（モデル）、ほかのモジュールとの契約の表、機能の索引、設計の索引を一つに抱えており、`README.md` に置く情報とほかの文書に置く情報の区別が読み手に分からない。
README の「モデル」は Aggregate を指すが、生成サイトのモジュールのページには TypeSpec の API の型を並べた「API とモデル」もあり、同じ「モデル」の語が別のものを指している。
設計の索引は「担当文書」というリンクの文字と、固有設計、委譲、対象外の区分の列を持ち、何を案内しているのかが伝わりにくい。

モジュールの `architecture.md` は、arc42 がシステム全体に一度だけ書く章（文脈と範囲、解決戦略）をモジュールごとに写している。
arc42 の構成要素ビューは、構成要素をブラックボックスとして目的と責務、インターフェース、コードの場所で説明し、内部を書くのは重要、意外、危険、複雑、変わりやすい構成要素に限るとする（[arc42 の第 5 章](https://docs.arc42.org/section-5/)）。
実際の内容も、依存先の表は生成した依存の図とコードから読め、構成要素の表は機能とコードの名前の規則から導け、解決戦略の多くは `decisions.md` の言い直しだった。

生成サイトの「API とモデル」と「機能地図」は、API リファレンスとモデルカタログ、機能の一覧の写しであり、読み手に新しい情報を与えない。

## 対象範囲

- 内部の設計は、開発者と運用者にとって最も素直な形をデフォルトとし、そうでない構造と、その理由だけを文書に書くと設計フォーマットに定める。外から観測できる振る舞いの漏れのなさは、従来どおり機能仕様と TypeSpec が受け持つ。
- モジュールの `README.md` を、外から見た概要と道案内に絞る。節は次の順にする。
  - 責務と境界：責務と、扱わないものと担当。
  - 主な流れ：`architecture.md` の「実行時の流れ」を移す。
  - 設計の要点：`architecture.md` の「解決戦略」と「構成要素」のうち、素直な形から外れる構造とその理由だけを移す。
  - 機能一覧：従来の「機能」。
  - 文書：設計領域と、モジュールの文書の索引。
- 「公開する契約」の節を廃止する。ほかのモジュールとの依存は生成した依存の図とコードの公開パッケージから読み、HTTP の契約は TypeSpec が定める。
- 「モデル」の節を、データ設計の文書 `data.md` の「集約」の節へ移す。`data.md` のないモジュールには作る。
- モジュールの `architecture.md` を廃止する。「文脈と範囲」は依存の図と重なるので消し、「構成要素」は機能とコードの名前の規則から導けない例外だけを設計の要点へ移す。
- 設計の索引の列を、システムとモジュールのどちらも `設計領域 | 文書 | 内容` にする。文書の列には、リンク先の題名をリンクの文字として書く。区分の列と「担当文書」の語をやめる。
- 生成サイトのモジュールのページから「API とモデル」の一覧と「機能地図」を外し、タグで絞り込んだ API リファレンスと、モジュールのモデルカタログへのリンクの一行にする。サイドバーの「機能」は「機能一覧」にする。
- 上を強制する検査（設計の索引、モジュールの文書の集合）と、`brief` の読む位置を合わせる。

## 対象外

- 機能仕様の要件の見せ方は [wi-67249](wi-67249-render-ears-requirements-like-gherkin.md) が扱う。
- システムの全体設計文書の各設計領域の中身は変えない。
- 規範 ID と要件の文言は変えない。

## 設計

### README の雛形

```markdown
# <Module>

## 責務と境界
（責務を数文で）
| 扱わないもの | 担当 |

## 主な流れ
| 流れ | 契機 | 実行する場所 | 詳細 |

## 設計の要点
| 方針 | 理由 |

## 機能一覧
| 機能 | 内容 |

## 文書
| 設計領域 | 文書 | 内容 |
| 文書 | 内容 |
```

「設計の要点」は、素直な形から外れる構造だけを置く節であり、該当がなければ置かない。
代替案を比べた判断は従来どおり `decisions.md` に置き、要点の行からリンクする。

### 採用しない案

| 案 | 採らない理由 |
| --- | --- |
| ほかのモジュールとの接点の表を手書きで残す | 依存の向きは生成した図とコードの公開パッケージから読め、ポートの実装者の表は手で保つほど古くなる。素直でない接点は設計の要点に書けば足りる |
| `architecture.md` を残し、中身を実行時の流れだけにする | 一つの節だけの文書が設計領域の名前を名乗り、アーキテクチャの語がモジュールの規模に合わない状態が残る |
| 「API とモデル」の生成を残す | 生成なので保守の費用はないが、リファレンスとカタログの写しであり、README の「モデル」との取り違えを生む |

## 計画

1. 設計フォーマット、仕様フォーマット、文書ガイド、フォーマットの理由、モジュール設計文書の入口、全体設計文書の入口を書き換える。
2. 一度だけの移行スクリプトで、21 のモジュールの README と `architecture.md` と `data.md` を組み替え、残りを手で整える。
3. 検査、生成サイト、`brief` とそのテストを直す。
4. 検証する。

## リスク

- 節を消すことで、他の文書からのアンカーが切れる。`check-links` で確かめる。
- 「解決戦略」と「構成要素」から設計の要点へ移す行の選別を誤ると、素直でない構造の説明が失われる。行ごとに、判断へのリンクの有無と、コードから読めるかで選ぶ。

## 要約

`mise run spec-diff` は main に対して規範仕様の変更なしと報告する。
モジュールの `README.md` を「責務と境界、主な流れ、設計の要点、機能一覧、文書」の概要と道案内に絞り、モジュールの `architecture.md` を廃止した。
Aggregate は `data.md` の「集約」へ移し、「公開する契約」の節はなくした。
内部の設計は素直な形をデフォルトとして書かず、そうでない構造と理由だけを書くと規則文書に定めた。
設計の索引は `設計領域 | 文書 | 内容` の 3 列にし、生成サイトのモジュールのページから API と型の一覧と機能地図を外した。
