# 作業項目とコミットだけの更新では、入力が同じ Go テストの成功結果を再利用する

## 動機

[wi-98584 の観察](wi-98584-reduce-follow-up-refactor-and-bugfix-items-at-first-implementation.md#観察の記録)には、完了記録の移動と最終コミットで Go 検証レポートが stale になり、製品コードを変えていない段階でも全 Go 検査を再実行した実例がある。
同項目の案 14 は、この入力分離を未実装として保留している。

[現在の入力識別](../../tools/verification/src/input.ts)は HEAD と追跡ファイルと未追跡ファイル全体をハッシュへ含める。
一方、コマンド、DB 必須モード、比較基準は保存されるが、同じ fingerprint の構成要素ではない。
実行の出所を示す情報と、実行結果を無効にすべき入力を分け、完了処理だけの変化による再実行を省きたい。

## 対象範囲

- Go テストの実行入力と、規範参照、静的解析、変更操作の選択による判定入力を別に識別する。
- 成功済みの一回の Go 実行の生イベントを、同じ実行入力に限って明示的に再利用する入口を `mise` に追加する。
- 再利用時は現在の判定入力で契約証拠と DB 必須条件を再評価し、元の実行と再評価の出所を報告する。
- 最初の適用は、HEAD だけの変化と `work-items/` の追加、編集、移動に絞る。
- [テスト方針](../../docs/development/testing.md#結果の参照)、[最終検査の選択](../../docs/development/specification-first-workflow.md#最終検査の選択)、リポジトリツールの説明を同期する。

## 対象外

- UI、Lint、文書検査、ミューテーションテストの結果キャッシュ。
- パッケージ単位の実行結果を継ぎ合わせて全体の実行とみなすこと。
- 別の端末、CI、worktree への結果の持ち出しと共有キャッシュ。
- 作業項目以外の文書を実行入力から一括で除外すること。
- CI の実行範囲、構造変更の証拠要件、完了記録の形式の変更。

## 設計

### 実行と判定の分離

実行記録は、実行 ID、元の revision、実際のコマンド、対象とフラグ、実行入力の識別、生イベントとその内容の識別を保持する。
判定記録は、参照した実行 ID、現在の revision、解決した比較基準、変更操作、現在の規範と生成 OpenAPI、判定器の識別、判定結果を保持する。
元の revision を現在の revision へ書き換えず、新しい実行があったように表示しない。

初期実装の実行入力は、現在の保守的なファイル集合から HEAD と `work-items/` だけを分離する。
Go ソース、テスト、fixture、スキーマ、依存宣言、設定、ツールの実装は引き続き含める。
追跡していないファイルの追加、削除、名前の変更も識別する。
Go が実際に読む無視対象の生成入力と環境設定は着手時に棚卸しし、識別できない場合は再利用を拒否する。
`work-items/` をテスト入力として読む経路があれば、その経路では除外しない。

コマンドの対象、race、タグ、skip、DB モード、ツールチェーンと実行に影響する環境も再利用条件に含める。
同じ worktree のローカル結果だけを扱い、環境の同一性を確認できなければ再実行を要求する。
機密値をレポートへ書かず、必要な値は内容の識別だけを保存する。

現在の判定は毎回行う。
比較基準や操作選択、生成 OpenAPI、参照宣言が変わったときに、以前の判定結果を current に昇格させない。
保存された一回の実行のテスト結果だけで現在の要求を満たせるかを判定し、不足する対象、失敗、スキップ、未終了、DB 不足は引き続き拒否する。
実行前後と再利用前後に各入力を比較し、途中の変更も検出する。

### 入口と移行

通常の `test-go*` は引き続き新しい実行を行う。
再利用は対象レポートを指定する別の `mise` タスクから明示的に選び、必要な入力が一致しなければ成功へ進まず再実行を案内する。
既存の `report-verification` は、新規実行、再利用した実行の再評価、stale を区別する。
新しい記録形式で必要な識別を持たない旧レポートは表示できても再利用できない。
記録は引き続き `.verification/` の生成物とする。

既存の `tools/verification` と `tools/check` の責務内で実装し、新しいモジュールと依存方向は追加しない。
比較基準と操作選択、参照収集、実行結果の解釈は既存の処理を使う。
静的検査の全体キャッシュは作らず、現在の入力で実行する。

### 代替案

- 現行の全ファイル識別を維持する案は、観測された完了時の再実行を解消できないため採らない。
- revision だけをハッシュから除く案は、作業項目の移動による無効化を残し、異なる対象と実行条件の混同も防げないため採らない。
- レポートの fingerprint を現在値へ書き換える案は、現在の契約による再評価がなく、実行の出所を失うため採らない。
- 自動的な結果キャッシュは、通常のテストコマンドの意味を変えるため初期実装では採らない。

## 計画

1. 実行が読むファイルと環境を棚卸しし、除外できる記録と実行に必要な入力を fixture で確定する。
2. 入力識別と再利用可否の計算、生イベントの保存、現在の判定の編成を分ける。
3. 明示的な再利用タスクとレポート表示を実装し、既存の実行入口との互換を保つ。
4. 完了処理だけの変更と、古い証拠を拒否する対照を CLI で検証する。
5. 観測した再実行の削減と限界を記録する。

## 検証

製品要件 ID は N/A（リポジトリ内の検証ツール）。
受け入れ RED は CLI が扱う最小 Git workspace、単体 RED は入力の識別と再利用の条件で観測する。

- 内容が同じコミット、作業項目の移動だけなら再利用できる。
  不正な作業項目は現在の記録検査が拒否し、Go の成功でその失敗を隠さない。
- Go ソース、テスト、fixture、スキーマ、依存、関連する生成入力、実行器、実行条件の変更は再利用を拒否する。
  追加、削除、未追跡の入力と、実行中の変更も対照に含める。
- 比較基準と変更操作の集合を変えると現在の判定が更新され、不足する契約テストを過去の成功で補えない。
- failed、skipped、not-run、子の未終了、DB 不足、旧形式、生イベントの欠落と不整合を再利用可能へ昇格させない。
- `mise run test-tools-file -- <変更したテストファイル>`、`typecheck-tools`、`lint-tools` で局所的に検証する。
- `check-work-items`、`check-links`、`check-command-map` と、文書変更後の `render-docs`、`check-rendered-docs` を選ぶ。
  最終検査は実装の影響範囲から追加し、入力が変わった検査だけを再実行する。

## リスク

- 入力を落とすと古い実行を成功の証拠にできてしまう。
  初期の除外を限定し、未知の入力は再利用を拒否し、入力を故意に変えた対照を固定する。
- 外部環境の変化はファイル識別だけでは保証できない。
  再利用を同じローカルの実行環境に限り、環境を確認できない場合は新規実行へ戻す。
- 複数実行を混ぜると同一実行の契約証拠の意味が変わる。
  元の一回の実行 ID を維持し、現在の判定と明確に分ける。
