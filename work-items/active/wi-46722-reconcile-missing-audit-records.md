# 監査と重要な副作用の確定境界を定め、監査の欠落を検出して補う

## 動機

起動処理の配信点（`backend/cmd/internal/bootstrap/audit_event_record.go` の `NewEmitFunc`）は、ドメインイベントを監査の記録へ写す変換や追記に失敗すると、「照合が必要（reconciliation required）」とログに残すだけである。
照合の仕組みはなく、操作の結果は残り、監査の記録だけが欠けたまま検出も補充もされない。
IdManagement の設計も、Aggregate の保存の後に監査の記録を追記する経路がこの欠落を生みうると書いている（`docs/modules/identity-management/design/audit-events.md`）。

wi-26063 で Audit の内部設計をコードと照合して見つけ、`docs/modules/audit/design/risks.md` に載せた。

2026-10-10 の設計調査では、通常操作の監査は保存後の追記、CSV の監査は業務状態との同時確定、ワークフローと下流への通知はそれぞれ異なる確定境界を持つことを確認した。
新しい入口を追加する AI がその都度成功応答と副作用の関係を選び直すと、入口ごとに異なる保証が増える。
監査の回復方式を選ぶ前に、同時に確定すべき事実と、遅れて届けてよい通知を分ける必要がある。

現在は未リリースであり、当面も未リリースを継続する。
リリースと旧版互換性の準備の重要性は下がるが、監査の完全性と作用の確定境界は日々の機能追加で守るべき設計なので p1 とする。
公開済み旧形式の維持は前提にせず、既存の製品仕様を先に確認して方式を選ぶ。

## 対象範囲

- 管理 API、セルフサービス、CSV、Worker で、成功応答、業務状態、監査、ワークフロー、下流への通知の確定関係を分類する。
- 同時に確定すべき事実、遅延を許す通知、失敗後に回復すべき処理を、所有する契約と設計へ明記する。
- 監査の記録の欠落を検出し、補う仕組みを入れる。
- 停止、追記失敗、重複配信、再試行で、監査の欠落を回復できることとテナント分離を検証する。
- `docs/modules/audit/design/risks.md` の該当の行を消す。

## 対象外

- 監査の記録の保持期間。wi-514 が扱う。
- 監査の記録の改ざんの検知。wi-287 が扱う。
- ワークフローとプロビジョニングの個別実装の全面変更。
  本項目では確定境界と回復の責務を分類し、監査以外の不整合は既存の所有項目へ反映する。
- 公開済み旧イベントの互換性保証、独立したメッセージ基盤の導入、本番操作。

## 設計

製品は専用のイベントの基盤を持たない判断をしている（`docs/modules/system/design/decisions.md`）。
その判断の再検討の条件に「イベントが失われないことを保証する必要が生じ、それが発行の意図を耐久的に残すことでしか達成できないと判明したとき」がある。
着手時に、追記の失敗を耐久的に残す方式（状態の変更と同じトランザクションに発行の意図を書く）と、Aggregate の状態から欠落を照合する方式を比べ、前者を選ぶならシステムの判断の見直しとして扱う。
状態からの照合では復元できない過去の事実と、発行の前後に停止する故障を候補の比較に含める。
ログへ失敗を残すだけの方式は、欠落の検出と補充を保証できないため採らない。
監査の検索へ同じ事実が重複して現れないよう、記録の識別と冪等性を定める。
通知は送信先に到達できる保証と、送信予定を失わない保証を区別し、外部の到達性を業務状態の確定と混同しない。

影響するドメインデータ型、操作のシグネチャ、原子性、記録の所有者、回復の担当を実装前に決める。
モジュール間の依存、テーブル所有者、組み立て地点を変える案では、[境界を選ぶ判断手順](../../docs/design/application/design-guidelines.md#境界を選ぶ判断手順)の比較を設計へ記録する。
既存の要件に合わせる範囲は conforms とし、新しい保証や応答の変更が必要なら実装前に affected_spec の impact と規範要件を更新する。

### 着手調査（2026-10-11）

利用者は、業務状態と監査の発行意図を同時に確定し、発行意図を保存できない場合は業務変更も確定せずエラーを返す方式を選んだ。
この選択は未公開の製品の成功条件を強めるため、実装時には既存要件への適合だけで扱わず、新しい保証を所有する規範へ先に記す。
REQ-AUDIT-002 は、プロセスが発行したイベントを監査へ記録する要件であり、イベントを発行していない操作の監査まで保証する要件としては使わない。

#### 確定関係の分類

| 入口または作用 | 現在の確定境界 | 回復の責務と残る欠落 |
| --- | --- | --- |
| 管理 API の User の作成と変更 | `captureUserMutation` が User を保存し、配線済みなら派生する WorkflowRun も捕捉する。その後に `AdminEmit` を呼ぶ | 保存と発行の間の停止で監査の事実を失う。作成では動的グループの評価とパスワード履歴の保存も発行の前に入る |
| セルフサービスのプロフィール更新 | `UpdateUserProfile` が User を保存してから `UserUpdated` を発行する | 変更した項目と行為者を現在の User だけから復元できず、配信点だけの再試行では保存後の停止を補えない |
| CSV の適用 | User と Group の行の適用は、それぞれの行コミッターが業務状態と監査を同時に確定する | 既存の行の原子性を維持する。通常操作のための仕組みへ移すこと自体を目的にしない |
| User の変更に伴うワークフロー | `UserMutationCommitter` と `UserWorkflowCapture` が User と実行予定を捕捉する。Job の関連付けは定期ディスパッチャーが回復する（REQ-IDGOVERNANCE-004、REQ-JOBS-008） | 同時に残すべきものは実行予定であり、Worker による完了やメールの到達ではない |
| 下流への User の通知 | User を確定した後に `ProvisioningNotifier` を呼び、失敗をログに残す | 通知の予定を失わない保証は監査の発行意図とは別に扱う。ログだけで予定の永続化を保証したことにしない |
| 下流への Group の通知 | Group の変更とイベントの発行の後に通知する。通知が失敗しても変更を残してエラーを返す（REQ-IDMANAGEMENT-064） | 監査の同時確定をリクエスト全体のロールバックに置き換えると、この要件を壊す。通知の到達と状態の確定を分離する |
| Worker の Job の投入と状態遷移 | Jobs は状態を保存した後にイベントを発行する。Job 自身はリースと再試行で回復する | Job の回復は、保存と監査の発行の間で失った事実の回復を意味しない |
| Worker のワークフローの所属と必須操作の変更 | `executeLifecycleAction` が Group または User の Repository を直接変更する。変更に対応する IdManagement のイベントを発行しない | 発行意図の再配信だけでは補えない。IdManagement の操作境界へ通す修正は既存の wi-90256 が所有する |

#### 方式の比較

| 方式 | 保存後の停止 | 過去の事実 | 書き込みと所有 | 判断 |
| --- | --- | --- | --- | --- |
| Aggregate の現在状態から照合する | 現在の差分は探せるが、保存前後の全事実は取り戻せない | 削除前の状態、行為者、途中の属性変更、冪等な再実行前の事実を復元できない | 通常の保存を増やさずに済むが、各 Aggregate の復元規則が要る | 本項目の故障モデルを満たさない |
| 配信点で失敗したイベントだけを耐久的に保存する | `Emit` に到達する前の停止には記録がない | 到達したイベントの事実だけを残せる | 配信点だけの変更で済む | 保存後の停止を保証できないので採らない |
| 業務状態と監査の発行意図を同時に保存する | 確定した状態に対応する意図が残り、別プロセスが再試行できる | 発生時刻、行為者、対象、ペイロードを確定時のまま残せる | 各変更の保存境界へ書き込みを加える。監査の記録と回復は Audit が担当する | 利用者が選択した方式。独立したブローカーを導入する理由にはしない |

境界選択の D1、D4、D6、D7 を適用する。
発行元は業務上の事実を決め、Audit は記録と回復を所有し、組み立て地点が両者の保存を接続する案を候補にする。
各発行元へ Audit の検索モデルを直接持ち込む案は、検索表現の変更がすべての変更操作へ波及するため採らない。
リクエスト全体を一つのトランザクションにする案も、Group の通知失敗後の確定とワークフローの部分的な進行の契約を壊すため採らない。
イベントの発生ごとに識別子を一度生成して意図に保存し、監査への再配信では同じ識別子を使う。
内容が同じ別の操作まで一つにまとめるハッシュによる重複排除は採らない。
メモリと PostgreSQL の具体的な操作シグネチャ、意図の表、回復の実行入口は、下の前提が満たされた後に確定する。

#### 実装開始の前提

[wi-90256](wi-90256-route-lifecycle-workflow-steps-through-context-operations.md) を先に完了する。
`backend/idgovernance/usecases/lifecycle_workflow_dispatcher.go` の `executeLifecycleAction` は、`add_group_member`、`remove_group_member`、`set_required_action`、`clear_required_action` の四つで Repository を直接変更し、その事実を IdManagement のイベントとして発行する境界を持たない。
これらは配信失敗ではなく発行元の欠落であり、現在状態から過去の行為者や操作の連なりを監査として生成しても是正にならない。
同じ修正は、ワークフローからの変更を IdManagement の冪等な操作へ通し、下流への通知と発火の循環を扱う独立した成果として wi-90256 がすでに所有する。
本項目で重複実装すると、その所有項目の操作境界と異なる監査専用の変更経路を増やす。

着手調査で対象外の前提を見つけた場合に停止する `implement-work-item` の手順に従い、本項目は `pending` のまま依存関係を記録する。
これは実装量による分割ではなく、既存の所有項目が先に整える操作境界への依存である。
監査の回復、本番コードの変更、新しい規範の適用、RED、故障注入、集約検証は未実施であり、Audit の既知リスクも解消済みとして消さない。
再開時には wi-90256 が作った操作ポートを起点として `brief` を取り直し、各変更と監査の同時確定を組み込む。

## 計画

1. 各入口の確定関係と、既存の規範が要求する事実を棚卸しする。
2. 原子性、回復可能性、書き込みコストから方式を比べ、必要な契約と境界を決める。
3. 保存後の停止と監査追記の失敗で、欠落が回復されないことを RED として確かめる。
4. 監査の回復と冪等性を実装し、同じ契約をメモリと PostgreSQL の境界で検証する。
5. 監査以外の作用の不整合を所有項目へ反映し、設計とリスクを同期する。

## リスク

発行の意図を耐久的に残す方式は、すべての状態の変更のトランザクションに書き込みを加える。
優先度と実装リスクは分け、重要な確定境界に作用するため risk は high とする。
未リリースであっても、成功条件を実装に合わせて弱めたり、状態から再構成できない過去の事実を照合済みとしたりしない。
