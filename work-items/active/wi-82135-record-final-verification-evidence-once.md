# 最終的な検証証拠を完了節へ一度だけ記し、中間記録から再記述しない

## 動機

[wi-26617](../done/wi-26617-remove-module-types-from-fixtures-and-observability-libraries.md) の全文（`ab02067fc` の時点）の「実装結果と完了の前提」と完了節には、同じ RED と変異検出と局所検証の説明が重複している。
最終結果の記録と、途中の失敗や組み合わせの変化を残すことには、それぞれ意味がある。
ただし、同じ証拠を複数箇所で更新すると、書き直しの費用と不一致が生じる。
最終的な証拠の記載先を一か所に決め、途中の記録には最終結果から復元できない判断だけを残したい。

## 対象範囲

- 作業項目形式と開発ワークフローで、中間記録と最終的な証拠の役割を分ける。
- RED、変更耐性、検証結果の最終的な説明を、機械検査が読む完了節へ集める。
- 同じ証拠をタスクと実装結果へ再掲せず、必要なら項目内の節へリンクする書き方を例で示す。
- 継続中の項目では、実施回ごとの証拠を一か所に保ち、後の実施回との差を残す。

## 対象外

- 証拠の要件と完了の必須フィールドの削減。
- 過去の完了記録の一括書き換え。
- JSON レポートを読めなければ作業項目を理解できない形式への移行。
- 証拠パーサーの新しい参照形式、検査コード、テンプレート生成器の実装。
- 検証結果の再利用と、構造変更の免除条件の変更。

## 設計

### 記録先

完了節は、現在の[作業項目形式](../../docs/formats/work-item-format.md#完了記録)に従い、最終的な RED と変更耐性と検証結果を説明する唯一の節とする。
必要な要件、テスト、観測、検出理由はその節へ残し、リンクだけで必須情報を置き換えない。
着手時の計画は未来の選択、完了節は実際の観測であり、両者は重複とは扱わない。

中間記録には、失敗した試行、前提不足、判断を変えた理由、検証した組み合わせの変化を書く。
最終結果と同じ成功の説明を別の「実装結果」節へ複製しない。
タスクには完了状態と証拠の節への参照を残し、同じ観測の全文をコピーしない。

途中で完了節の下書きを更新しても `status: in_progress` は維持できることを確認し、書式例にする。
継続観察する項目では、実施回ごとに観測の記載先を一か所にし、項目全体を完了するときは最終状態と未解決事項の差を要約する。
時点の違う観測を削除して、最新の成功だけが残る形式にはしない。

既存のパーサーが読む完了形式は維持する。
規則を追加するだけで実際の重複が減ったと主張せず、同じ変更例を新しい書き分けで表した前後を検証する。

### 代替案

- 中間結果と完了節を両方全文で更新する案は、同じ説明を保守する費用が残るため採らない。
- 完了節を実装結果へのリンクだけにする案は、必要な情報を機械検査が読めなくなるため採らない。
- 新しい構造化証拠ファイルを必須にする案は、入力形式と管理対象を増やすため採らない。

## 計画

3. 実例の RED、変更耐性、最終検査を一度ずつ記載した形を試し、必要な情報が残ることを確認する。

## 検証

文書だけの変更なので、RED と変更耐性のために検査コードを追加しない。
実例の差分レビューと文書検査の成功で確認する。

- RED のテスト、要件、観測した失敗、検出理由、変更耐性、最終検証を完了節だけで読めることを確認する。
- 中間記録の失敗、前提の解消、比較基準の変化が失われず、同じ最終証拠の説明を再掲していないことを確認する。
- 継続中の項目の実施回と、項目全体の完了を混同しない例を確認する。
- `mise run check-work-items` と `check-links` で、既存の形式と参照が引き続き有効なことを確認する。
- 文書変更後に `mise run render-docs` と `check-rendered-docs` を実行する。

## リスク

- 重複の削減とともに失敗の履歴も消すと、判断を変えた理由が失われる。
  中間記録に残す情報を名指し、時点の違う観測は保持する。
- 参照だけを増やすと完了節を読んでも証拠を理解できなくなる。
  必須情報は完了節に記し、参照はタスクと中間記録の側から使う。
