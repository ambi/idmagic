# 同時の更新と、確定と作用の順序の規則を設計文書に書く

## 動機

一部の値だけを変えたい処理が、先に読んだ集約を丸ごと保存し、その間の無効化や編集を書き戻す問題が複数のモジュールで見つかった。
ログインセッションは失効と最終アクセスを専用の部分更新で書き、この問題を避けているが、その規則は文書にない。
IdManagement のデータの文書は「Aggregate の保存に楽観的な排他も行のロックも使わず、全体を上書きする」と書き、ほかのモジュールが User の一部の値を記録する場合を区別していない。

同じく、業務状態の確定と、その後のイベント、監査、通知の順序と失敗の扱いは、監査の要件と個別の判断に分かれて書かれ、全体の方針として読めない。
イベントソーシングを採らないことも、どこにも記録していない。

## 対象範囲

- データ設計（`docs/design/data/database.md`）に、同時の更新と排他の節を加える。
- 設計ガイドラインの「一貫性の境界と永続化」の判定基準に、集約の一部だけを書く処理の行を加え、データ設計へ参照する。
- バックエンド設計の「モジュール間イベント」に、確定と作用の順序と、Transactional Outbox を持たない現状を書く。
- アーキテクチャ上の判断に、現在の値を保存し、イベントソーシングを採らない判断を書く。
- IdManagement のデータの文書の「排他と一意性」を新しい規則に合わせ、Authentication が User を丸ごと保存する現状をリスクに載せる。

## 対象外

- 規則に反する既存の書き込みの修正（wi-98381、wi-77130、wi-97231）。
- 管理 API の版による競合検出の実装（wi-605）。
- Transactional Outbox の採否（wi-77197）。

## 設計

規則の本体は、形式が「排他」を割り当てるデータ設計に置く。
設計ガイドラインはレビューで使う判定基準だけを持ち、同じ内容を写さない。

同時の更新の規則：

| 書き手 | 保存の形 |
| --- | --- |
| 利用者や管理者が集約を編集する操作 | 集約を丸ごと保存する。同じ集約の同時の編集は版で検出する |
| 利用者や管理者が編集しない値（時刻、外部取得の結果、計数、導出した値）だけを記録する処理 | その列だけを書く操作を使う |
| 自動の書き手による状態の遷移 | 遷移前の状態を条件にした更新を使う |
| 外部への取得や長い計算をはさむ処理 | 読んだ集約を取得の後に丸ごと保存しない |

すべての保存を列ごとの更新にはしない。複数の値にまたがる不変条件の検査が SQL に散らばるためである。

wi-77130 の T003（設計ガイドラインに規則を加える）は、この項目へ移す。

## 要約

規範仕様の差分はない。
データ設計に「同時の更新と排他」を加え、書き手の種類ごとの保存の形を定めた。
利用者や管理者の編集は Aggregate を丸ごと保存して版で検出し、編集しない値だけの記録は専用の部分更新、自動の状態遷移は遷移前の状態を条件にした更新にする。
すべての保存を列ごとの更新にはしない理由と、ログインセッションの失効と最終アクセスを手本の例として書き、規則に反する既存の書き込みを適用状況に挙げた。
設計ガイドラインには判定基準を 1 行だけ加えてデータ設計へ参照し、同じ内容を写していない。

バックエンド設計に「確定と作用の順序」を加え、業務状態の保存と配信点を同じトランザクションにせず、Transactional Outbox を持たない現状と、欠けた作用の扱いを作用ごとに書いた。
アーキテクチャ上の判断に、現在の値を保存してイベントソーシングを採らない判断と見直し条件を書いた。
IdManagement のデータとリスクの文書を新しい規則に合わせ、Authentication と所有者の停止による丸ごとの保存を載せた。
wi-77130 の規則のタスクはこの項目へ移し、修正を扱う三つの項目に適用状況の更新を加えた。
