# 作業中に利用者から受けた訂正を、妨げの記録として残す

## 動機

[作業中の妨げの記録](../../docs/development/agent-guidance.md#作業中の妨げの記録)は、正式コミットの前にエージェントが自分で振り返り、AGENTS.md、skill、開発文書、検査、`mise` タスクのうち誤っていたもの、足りなかったものを `Agent-Friction` トレーラーに書くと定める。
入力はエージェント自身の振り返りだけであり、作業中に利用者がエージェントの判断や前提を訂正したことは、独立した入力として扱われていない。
`agent-guidance.md` には「同じ指摘を繰り返し受けたら」とあるが、受けた指摘をどこに残すかは定めていない。
エージェントはセッションをまたいで指摘を覚えていないので、残さなければ繰り返したかどうかが分からない。

2026-10-29 から 2026-11-28 までの直近 300 件のコミットのうち、`Agent-Friction` トレーラーを持つのは 12 件である。
利用者の訂正は、コミットの時点の振り返りでは「自分の誤り」として片付けられやすく、指示の不足として記録されにくい。

AWS の AI-DLC は、利用者の訂正を学習ループの入力にしている。
段階の中で利用者がエージェントを訂正すると、承認の前に「次回もそうするか」を一度だけ聞き、残すと答えたものを日付と出所付きでルールファイルへ書く。
誤字や一つの値のような一度だけの修正は聞かない。

## 対象範囲

- `agent-guidance.md` の[作業中の妨げの記録](../../docs/development/agent-guidance.md#作業中の妨げの記録)に、利用者の訂正を記録の入力として加える。
  - 対象は、エージェントの判断、前提、手順を利用者が直し、その直し方が次の作業にも当てはまるものとする。誤字、名前、一つの値の修正は含めない。
  - 起きたことには、利用者の訂正であることが分かる形（例: 「利用者の訂正: 〜と判断したが、〜だった」）で書く。集計の対象の表記は変えない。
  - 訂正を受けた時点で、どの文書の記述が足りなかったかを対象として決める。どの文書にもない前提なら、既存の規則どおり最も近い文書のパスにする。
- `implement-work-item` と `new-work-item` のコミット前の振り返りの手順に、セッション中の利用者の訂正を見直すことを加える。手順の本文は `agent-guidance.md` へのリンクに留める。
- `review-agent-friction` の判断の表で、利用者の訂正による記録を、1 件でも直す価値が明らかなものとして判断に含めてよいかを決めて書く。

## 対象外

- 訂正を受けた時点でルールファイルへ直接書く仕組み。採った変更は作業項目を経由するという[記録から変更を決める手順](../../docs/development/agent-guidance.md#記録から変更を決める手順)の方針を保つ。
- 訂正をその場で「次回も適用するか」と利用者へ聞く対話。聞く回数が増えるので、まずは記録だけを加え、振り返りで判断する。
- `report-agent-friction` の集計方法の変更。表記をそろえれば既存の集計で数えられる。

## 設計

出典: AWS AI-DLC のドキュメント「Rules and the Learning Loop」（https://awslabs.github.io/aidlc-workflows/guide/09-rules-and-the-learning-loop/）。本文を読んだ。調査日は 2026-11-28。

AI-DLC から採る点は、利用者の訂正を学習の入力にすることと、一度だけの修正を除外する基準である。
採らない点は、訂正を承認ゲートでルールファイルへ直接書くこと、組織、チーム、プロジェクトの層を分けることである。
IdMagic では、指示の変更は利用者が作業項目として採否を決めるので、層を分ける必要がない。

訂正の記録に別のトレーラー（例: `Agent-Correction`）を使う案は採らない。
集計が二系統に分かれ、同じ対象の記録が合算されなくなるためである。

## 計画

1. `agent-guidance.md` の該当節に、訂正を記録する条件と書き方を足す。
2. 二つの skill の振り返りの手順に、訂正を見直すことを一行で足す。
3. `review-agent-friction` の判断の表の扱いを決める。

## 検証

- `mise run check-agent-guidance`: skill から呼ぶタスクとリンクの形式を確かめる。
- `mise run check-links`: 文書間のリンクを確かめる。
- `mise run check-work-items`: 記録の形式を確かめる。

## リスク

訂正のたびに記録すると、1 件だけの対象が増えて集計が読みにくくなる。
次の作業にも当てはまる訂正だけに絞る条件で抑える。
