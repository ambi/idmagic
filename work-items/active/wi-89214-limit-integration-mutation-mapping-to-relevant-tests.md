# 統合モードの変異検査で、対象を実行しないテストの個別計測を避ける

## 動機

wi-94860 で gomutants 0.7.2 の統合モードを使うと、User の変更行の変異 13 件と HTTP の 10 件に対して、対象パッケージの被覆が 0% の DB テストも一件ずつ再実行した。
開始から User は 11 分、HTTP は 9 分を超えても、変異の判定前のテストごとの被覆計測を続けていた。
子プロセスでは Jobs の PostgreSQL のリースと投入のテストを個別に実行していた。
呼び出し側のテストを使うために、関係しない DB の起動まで反復する費用が生じている。
利用者の指示により、この二つの計測は中止し、重要な故障の検査に絞った。
変異体ごとのビルドを減らす [wi-49807](wi-49807-enable-gomutants-schemata-for-mutation-runs.md) とは、費用が生じる段階が異なる。

## 対象範囲

- `test-go-mutation` と一件の再実行で、重要な故障とそれを観測するテストを選ぶ方法を調べる。
- パッケージ単位の被覆で到達しないと分かるテストを、個別の対応付けから除く方法を比較する。
- 呼び出し側からだけ検出できる故障を残し、対象、初期計測と変異の実行の時間を分けて比較する。

## 対象外

製品の変更、無条件な検査対象の拡大、検出率の数値目標、関係する外側のテストを省いた結果を同等とみなすこと。
schemata の導入は wi-49807 が扱う。

## 設計

現在の固定版の CLI と内部の対象選択を着手時に確認する。
既存の対象指定を使う案、対応付けを被覆のあるパッケージに限る版へ更新する案、重要な故障を一件ずつ検査する案を比較する。
単なるファイル名の一致で呼び出し側を除外する案は採らない。
必要な CLI の機能がない場合は、製品側へ迂回のラッパーを増やさず、上流への修正または一件指定の検査を選ぶ。

## 計画

関係しないテストの実行と、呼び出し側だけが検出する変異を持つ小さな fixture を用意する。
対象の選択を変えても変異 ID ごとの判定が変わらず、関係しない DB の起動を反復しないことを確かめる。
実装する方式と、その方式で検出できない故障の扱いは着手時に決める。

## 検証

タスク契約を変える場合は `mise run test-tools-file -- check/src/mise-config.test.ts` を使う。
`check-go-mutation-tool` と fixture の変異 ID ごとの判定を比較し、必要な外側のテストの除外を検出する。
実測は基準、ワーカー数、コールドとキャッシュ済み、初期計測と変異の実行を分ける。
最終差分に応じて `check-work-items`、`check-links` とタスクの検査を選ぶ。

## リスク

間接呼び出しを見落とすと、検出できる変異を生存と誤判定する。
同じ変異 ID の判定を比較し、削減した範囲の意味を説明する。
