# システム全体の設計文書を、読み手が構造と判断を追える形に直す

## 動機

`docs/design/` のシステム全体の設計文書には、内容は正しいが読み手が構造や判断を追いにくい箇所がある。
レビューで次の問題を確認した。

- [論理アーキテクチャ](../../docs/design/architecture/logical.md#モジュールの構成)は、モジュール間の依存を import の行列で示す。
  System を除く 26 モジュールの行列は、どのモジュールがどのモデルを使い、どこで変換するかという関係を読み取りにくい。
  関係の種類は[モジュールの間の依存](../../docs/modules/README.md#モジュールの間の依存)の表に文で書いてあるが、図には表れていない。
- [アーキテクチャ上の判断](../../docs/design/architecture/decisions.md)は、判断、理由、見直し条件を箇条書きで並べる。
  モジュールの `decisions.md`（24 ファイル）は、[設計フォーマット](../../docs/formats/design-format.md#重要な設計判断decisionsmd)が定める「背景、決定、検討した代替案、結果と再検討の条件、関連する要件」の節を使っており、システムの判断だけが別の形である。
  検討した代替案の表もない。
- [設計ガイドライン](../../docs/design/application/design-guidelines.md)は、一文が長く、抽象語を重ねた文が多い。
  「エラーと拒否」の「拒否」が何を指すかが定義されていない。
  「確立した実装への委譲」の節は、暗号を自作しないという当然の規則と、[文書ガイド](../../docs/formats/documentation-guide.md)がすでに定める「書くべきものがない文書は作らない」という規則の重複でできている。
- [バックエンド設計](../../docs/design/application/backend.md)と設計ガイドラインは、全体の規則の説明に、特定のモジュールの組（WorkloadIdentity と OAuth2、IdManagement と Sourcing など）の配線の詳細を混ぜる。
  「依存の向きを選ぶ基準」の表は、モジュールの組ごとの実装状況の台帳になっている。
  一貫性の境界の節にも、モジュールごとのトランザクションの保証の一覧がある。
  全体の規則を読みたい読み手は個別の事情を読み飛ばす必要があり、個別の事情を知りたい読み手はモジュールの文書ではなく全体の文書を探す必要がある。
- [ユーザーインターフェース設計](../../docs/design/application/user-interface.md)は、画面を跨ぐ規則の文書だが、管理コンソールのサイドバーの領域、エージェントのアクセス権の画面、API アクセストークンの画面、CSV のアイコンのような個別の画面の決めごとを含む。
  [Frontend モジュール](../../docs/modules/frontend/README.md)の文書との境界が読み手に分からない。
- [データベース設計](../../docs/design/data/database.md)をはじめ、文書サイトの表は、どの列が行を識別するキーで、どの列が列挙値のラベルかが見た目で区別されない。
- [脅威モデル](../../docs/design/security/threat-model.md)の `Controls` 列は、34 行で文書を `design/application/api-guidelines.md: セキュリティレスポンスヘッダー` のようなパスの文字列で指す。
  リンクではないため辿れず、参照先の題名も分からない。
  そのうち 4 行は、すでに存在しない `contexts/` のパスを指している。
- [検証設計](../../docs/design/verification/README.md)は、[テスト方針](../../docs/development/testing.md)、脅威モデル、[継続的インテグレーション](../../docs/development/continuous-integration.md)と内容が重なる。
  独自に持つ内容は、要件の群ごとの証拠の表、脅威の状態ごとに求める証拠、システム受入れの代表経路、宣言的なファイルの検証に限られ、どれもほかの文書の近くに置ける。

## 対象範囲

### 論理アーキテクチャを Context Map で示す

- [モジュールの間の依存](../../docs/modules/README.md#モジュールの間の依存)の表に、[モジュール間でのモデルの扱い](../../docs/design/application/design-guidelines.md#モジュール間でのモデルの扱い)の分類を表す列を加え、全行に値を宣言する。
- 文書サイトの生成で、論理アーキテクチャの依存の行列を、この表から作る Context Map の図に置き換える。
- 依存を宣言とコードで照合する境界検査の入力に、新しい列を加える。

### システムの設計判断をモジュールと同じ形式にする

- [アーキテクチャ上の判断](../../docs/design/architecture/decisions.md)の各判断を、設計フォーマットの「背景、決定、検討した代替案、結果と再検討の条件、関連する要件」の節へ書き直す。
- 代替案を比べていない判断（直接依存のライブラリの選定の方針など）は、判断の記録ではなく方針なので、担当する文書へ移す。

### 設計ガイドラインを分かりやすくする

- `japanese-tech-writing` の規範に沿って全体を推敲し、長い節を短くする。
- 「エラーと拒否」を、失敗の種類（入力の不正、規則による拒否、作用の失敗）を定義する節に書き直す。
- 「確立した実装への委譲」の節を削る。暗号とプロトコルの処理を自作しない規則はセキュリティ設計の入口へ一文で移し、文書の厚みの基準は文書ガイドの既存の規則に任せる。

### 全体の設計文書から個別のモジュールの事情を外す

- バックエンド設計と設計ガイドラインから、特定のモジュールの組の配線、実装状況、保証の一覧を取り除き、規則だけを残す。
- 取り除いた内容のうち現在も有効なものは、当事者のモジュールの文書（`README.md` の「責務と境界」、`data.md`、機能仕様の「実現方式」）へ移す。
- 規則に例が要る箇所は、役割の名前（利用側、提供側、組み立て地点）で書いた短い例を一つ置く。

### ユーザーインターフェース設計と Frontend モジュールの境界を決める

- ユーザーインターフェース設計には、どの画面にも適用する表示と操作の規則だけを残す。
- 個別の画面や画面群に固有の決めごとは、Frontend モジュールの機能仕様（[管理コンソールのリソース操作](../../docs/modules/frontend/features/admin-console.md)、[ホステッド UI とポータル](../../docs/modules/frontend/features/hosted-ui.md)）へ移す。
- 二つの文書の分担を、ユーザーインターフェース設計の冒頭の分担表に書く。

### 文書サイトの表を見やすくする

- 文書サイトの表の表示に、行を識別する列と、列挙値のラベルを区別する規則を加える。
- データベース設計の表を、その規則で読める形に整える。

### 脅威モデルの参照をリンクにする

- `Controls` 列の文書の参照を、参照先の題名と節を表示する Markdown のリンクに書き換える。
- 存在しない `contexts/` のパスを、現在の文書の節へ直す。
- 「読み方」の節の `Controls` の書式の定義を、リンクの形に改める。

### 検証設計を解体して、内容を担当の文書へ移す

- `docs/design/verification/` の三つの文書と、モジュールの `verification.md`（7 ファイル）の内容を、下の設計で決めた移動先へ移し、文書を削除する。
- 設計フォーマット、文書ガイド、設計の索引から検証設計の設計領域を外し、参照を張り替える。

## 対象外

- モジュール設計文書（`docs/modules/<module>/`）そのものの見直し。
  今回は、全体の文書から移す内容の受け入れ先として、移した節を足すだけにする。
- 設計文書から実装のパスと名前を取り除く作業。
  [wi-85394](wi-85394-remove-implementation-names-from-design-docs.md) が扱う。
  この項目で書き直す節に実装の名前があれば、同じ規則に従って一緒に直すが、それ以外の箇所には手を付けない。
- UI のページ一覧と操作の詳細設計の整備。
  [wi-92664](wi-92664-model-ui-pages-and-interaction-flows-in-typespec.md) が扱う。
  この項目は、ユーザーインターフェース設計から画面固有の決めごとを Frontend の既存の機能仕様へ移すまでとし、ページのモデルは作らない。
- 汎用の方法論と IdMagic 固有の内容の分離。
  [wi-99632](wi-99632-separate-reusable-practices-from-idmagic-specifics.md) が扱う。
  この項目の「汎用」と「固有」は、全体の規則とモジュールまたは画面ごとの事情の区別であり、他のリポジトリへの再利用は考えない。
- 認証プロトコル（OAuth 2.0、OIDC、SAML、WS-Federation）の既知の攻撃を脅威モデルがどこまで覆うかの調査と、セキュリティ設計の入口へのプロトコル固有の設計の所在の記載。
  [wi-78912](wi-78912-check-protocol-attack-coverage-in-threat-model.md) が扱う。
  この項目は脅威モデルの既存の行の参照の形を直すだけで、行を足さない。
- ADR 台帳の導入と、判断の状態（proposed、superseded など）の管理。
  理由は設計の「設計判断の形式」に書く。

## 設計

### Context Map の表し方

DDD の Context Map は、Bounded Context を節点、モデルの関係（Shared Kernel、Customer/Supplier、Conformist、Anti-Corruption Layer、Open Host Service と Published Language）を辺として描く図である。
IdMagic は[アーキテクチャ上の判断](../../docs/design/architecture/decisions.md#モジュール間の依存を共通規則で検査する)で、Bounded Context との二重分類を採らないと決めている。
そこで、節点はモジュールのままとし、辺の分類だけを Context Map から借りる。
分類は、設計ガイドラインの「モジュール間でのモデルの扱い」がすでに定める三つに、公開 HTTP 契約で結ぶ関係を加えた四つにする。

| 新しい列の値 | 意味 | 対応する Context Map の関係 |
| --- | --- | --- |
| `使う` | 提供側の公開型と操作をそのまま使う | Conformist（提供側が利用側の要求に合わせて公開操作を足す場合は Customer/Supplier） |
| `変換` | 利用側が自分のモデルへ変換する | Anti-Corruption Layer |
| `共同管理` | モデルの一部を同じ意味と実装で保つ | Shared Kernel |
| `公開契約` | Go パッケージを共有せず、公開 HTTP 契約だけで結ぶ | Open Host Service と Published Language |

Customer/Supplier と Conformist は、提供側が利用側の要求をどれだけ受け入れるかという組織上の関係で分かれる。
IdMagic では一つのリポジトリの中で両方の側を変えられるので区別の意味が薄く、一つの値にまとめる。
現在の表の行には `共同管理` に当たる関係がない見込みであり、値の定義だけを置く。

26 のモジュールと 37 の辺を一枚に描くと、行列と同じく読めない。
図は二段に分ける。

1. 全体図：[責務表](../../docs/modules/README.md#モジュール)の五つの区分（基盤、フロントエンド、アイデンティティ、認証と認可、連携プロトコル）を節点とし、区分の間の辺を関係の種類ごとの本数で示す。
2. 区分ごとの図：区分に属するモジュールを節点とし、区分の中の辺と、ほかの区分のモジュールへの辺を描く。ほかの区分のモジュールは区分の外の節点として薄く表示する。

辺の向きは利用元から利用先へ引き、Context Map の上流と下流の言葉は使わない。
上流と下流の向きは利用の向きの逆であり、行列と表の読み手が向きを読み替える必要が生じるためである。
境界の負債台帳に記録された import の辺は、破線で区別する。

図は文書サイトの生成時に、表と import の抽出結果から Mermaid の flowchart として作る。
Mermaid は文書サイトがすでに状態遷移の図で使っている。

| 案 | 採否 | 理由 |
| --- | --- | --- |
| 区分ごとの二段の Context Map に置き換える | 採る | 関係の種類を図で読める。26 の節点を一度に読ませずに済む |
| 行列を残し、記号を関係の種類で分ける | 採らない | 関係の種類は増えるが、行列が読みにくいという問題は残る |
| 行列と Context Map を両方載せる | 採らない | 同じ辺を二つの図で示すと、どちらを読めばよいかが分からない。import の照合は境界検査が行うので、行列を読む必要もない |
| 26 の節点を一枚の図に描く | 採らない | 辺が交差し、行列より読みにくくなる |

### 設計判断の形式

ADR の原典（Nygard）は、題名、背景（Context）、決定（Decision）、状態（Status）、結果（Consequences）の五つの部分を定める。
MADR はこれに、判断の要因（Decision Drivers）、検討した選択肢（Considered Options）、選択肢ごとの利点と欠点（Pros and Cons of the Options）、確かめ方（Confirmation）を任意の要素として加える。
モジュールの `decisions.md` の形式は、題名、背景、決定、結果をそのまま持ち、MADR の選択肢と利点と欠点を「検討した代替案」の表にまとめている。
すでに ADR の考え方に沿っているので、新しいテンプレートは作らず、システムの判断をこの形式へ揃える。

ADR が持つ要素のうち、次の二つは採らない。

- 判断ごとのファイルと連番、状態（proposed、accepted、superseded）。
  [文書ガイド](../../docs/formats/documentation-guide.md)は、現在有効な判断を担当のファイルに置き、変更時点の比較検討を作業項目に残すと定めている。
  覆した判断を superseded として残すと、現在の判断と過去の判断が同じ文書に並び、文書ガイドの方針と食い違う。
  判断の履歴は作業項目と Git の履歴から辿る。
- MADR の確かめ方（Confirmation）の独立した節。
  判断を検査で確かめる場合は「結果と再検討の条件」に検査を書けば足り、全判断に節を求めると空の節が増える。

判断の要因（Decision Drivers）は「背景」に含める。
システムの判断には要件の ID がないものが多いので、「関連する要件」は、品質要件の ID か、判断が制約する設計文書の節へのリンクで埋める。
埋めるものがない判断は「なし」と書き、設計フォーマットの検査が節の欠落として拒否しないようにする。

### 設計ガイドラインの書き直し

推敲の基準は次のとおりとする。

- 一文に一つの主張を書く。「A し、B し、C する」と三つ以上つないだ文は分ける。
- 「〜の性格」「〜の厚み」のような比喩を、具体的な語に置き換える。
- 判定基準の表のうち、「守れている状態」と「反している状態」が互いの否定にすぎない行は、片方だけにする。
- 根拠の節が本文の繰り返しなら削り、出典の対応だけを末尾の出典の表に残す。
- 境界を選ぶ判断手順の D1〜D9 の ID は、作業項目の記録が参照するので変えない。

「エラーと拒否」は「失敗の表し方」に改め、次の三つを定義してから、層ごとの扱いを書く。

| 種類 | 定義 | 例 |
| --- | --- | --- |
| 入力の不正 | 要求の形が契約に合わない | 必須の項目がない、値の形式が違う |
| 規則による拒否 | 要求の形は正しいが、業務の規則または認可により操作を実行しない | 権限がない、名前が重複する、状態が遷移を許さない |
| 作用の失敗 | 操作を実行しようとしたが、保存や外部呼び出しが失敗した | データベースの接続が切れた、外部サービスが応答しない |

この区別は、[システム受入れ](../../docs/design/verification/system-acceptance.md#許可しないリクエストの確認対象)が「許可しないリクエスト」と「依存先の障害」を分ける区別と同じであり、移動先の文書でも同じ語を使う。

### 全体の規則と個別の事情の分け方

全体の設計文書に残すのは、モジュールを入れ替えても成り立つ規則である。
特定のモジュールの名前を挙げなければ書けない文は、次のどれかに当たる。

| 内容 | 移す先 |
| --- | --- |
| モジュールの組がどう接続しているか（どちらがポートを宣言し、どこで結ぶか） | 利用側のモジュールの `README.md` の「責務と境界」 |
| 実装状況（分離済み、実装済み、import はない） | 削る。依存の事実は境界検査と Context Map が示し、残る違反は境界の負債台帳とモジュールの `risks.md` が示す |
| 複数の状態を一つのトランザクションで確定する保証 | その保証を定める機能仕様の「信頼性」または「実現方式」（すでにリンク先にあるものはリンクを消すだけにする） |
| 規則の理解を助ける例 | 役割の名前で書いた一つの例。実在のモジュールで書くと、読み手はそのモジュールの事情を知らないと例を読めないため |

移す前に、移す先にすでに同じ内容があるかを確かめ、あれば全体の文書から消すだけにする。

### ユーザーインターフェース設計と Frontend の分担

分担の基準は、規則がどの画面に適用されるかとする。

| 内容 | 置く場所 |
| --- | --- |
| すべての画面、または画面の種類（認証画面、ポータル、コンソール）を問わず適用する規則：情報の順序、表示状態、破壊的な操作、フォームと検証、一覧、エラーの文言、国際化、アクセシビリティ | ユーザーインターフェース設計 |
| 特定の画面群の構成：管理コンソールのサイドバーの領域、参考にした管理画面 | [管理コンソールのリソース操作](../../docs/modules/frontend/features/admin-console.md) |
| 特定の画面の決めごと：エージェントのアクセス権の付与の入口、API アクセストークンの画面、CSV のアイコン、属性の表示名 | その画面を扱う機能仕様。所有するモジュールが Frontend 以外なら、そのモジュールの機能仕様の「実現方式」 |

外部から観測できる振る舞いを仕様に、UI ライブラリを入れ替えたら変わるものを設計に書くという既存の基準は維持する。

### 表の表示

文書サイトの表に次の表示の規則を加える。

- 1 列目を行の見出しとして太字にし、折り返さない。表の 1 列目は、ほぼすべての表で行を識別する語である。
- セルの内容全体がインラインコード一つのとき、そのセルをラベルの見た目（背景色付きの小さな枠）で表示する。`LOGGED`、`covered` のような列挙値が、説明の文と見分けられる。

1 列目が識別子でない表は、Markdown の側で列の順を入れ替えて合わせる。
表ごとに表示を指定する記法は加えない。
表ごとの指定は書き手が判断を毎回求められ、指定の漏れを検査できないためである。

### 脅威モデルのリンク

`Controls` の文書の参照は `[題名の節](相対パス#アンカー)` の形にする。
節の名前だけでは参照先の文書が分からないので、リンクの文字列は「文書の題名：節」とする。
`check-links` がリンク先とアンカーの実在を確かめるので、存在しないパスはこの書き換えで検出される。
`check-security-controls` と `report-security-test-gaps` が `Controls` の値を読む処理は、着手時に読み、リンクの形でも規範 ID を抽出できることを確かめる。

### 検証設計の移動先

検証設計は、要件の側から証拠を整理する文書として置かれた。
しかし実際の内容は、テストの書き方、脅威への対応、CI の対象と同じ問いに答えており、片方だけが更新される危険がある。
内容を担当の文書へ移し、設計領域としての検証設計をなくす。

| 案 | 採否 | 理由 |
| --- | --- | --- |
| 内容を担当の文書へ移し、検証設計をなくす | 採る | 独自の内容（要件の群ごとの証拠、脅威の状態ごとの証拠、受入れの代表経路、宣言的なファイルの検証）は、どれもテスト方針、脅威モデル、信頼性設計、CI の文書の隣に置ける。証拠の求め方と証拠の作り方が同じ文書に並び、片方だけ更新される危険がなくなる |
| 検証設計を残して充実させる | 採らない | 充実させるほどテスト方針と脅威モデルとの重なりが増える。設計フォーマットが設計領域の構成で参照する arc42 の章立てにも、検証を独立した章として置く構成はない |
| 現状のまま残す | 採らない | 読み手が、テスト方針と検証設計のどちらを読めばよいか判断できない |

| 現在の内容 | 移す先 |
| --- | --- |
| 担当範囲の表 | 削る。各文書の冒頭がすでに担当を書いている |
| 証拠の状態と合否 | [テスト方針の検証結果の区分](../../docs/development/testing.md#検証結果の区分) |
| 要件の群ごとの証拠 | テスト方針の新しい節。SLO と CAP の行は[品質要件](../../docs/requirements/quality.md)の測定境界の近くに置くかを、移すときに判断する |
| 宣言的なファイルの検証 | [継続的インテグレーション](../../docs/development/continuous-integration.md) |
| 機能受入れの代表経路、許可しないリクエストの確認対象 | テスト方針の受け入れの節 |
| 可用性と復旧の試験 | [可用性設計](../../docs/design/reliability/availability.md)と[復旧設計](../../docs/design/reliability/recovery.md) |
| セキュリティ検証設計（脅威の状態ごとの証拠、制御の種類ごとの検証手段、許可しない操作の確認） | [脅威モデル](../../docs/design/security/threat-model.md)の「読み方」の近くに、状態ごとに求める証拠として置く。制御の種類ごとの検証手段はテスト方針へ |
| モジュールの `verification.md` | 内容に応じて、モジュールの `security.md`、`reliability.md`、機能仕様の「実現方式」へ移す |

論理アーキテクチャの品質要件の割り当ての表は「検証」列で検証設計を指しているので、移動先へ張り替える。
設計領域の一覧から検証設計を外すと、設計フォーマットと文書の配置の検査（`tools/check/` の文書の配置と設計領域の検査）が参照する名前も変わる。
検査の入力の変更はこの項目に含める。

## 計画

1. 文書サイトの表の表示と、脅威モデルのリンクを先に直す。ほかの書き直しの結果を、新しい表示で確かめられるようにするためである。
2. 設計判断の形式を揃える。
3. 全体の文書から個別の事情を外し、ユーザーインターフェース設計と Frontend の分担を移す。設計ガイドラインの推敲は、個別の事情を外した後に行う。
4. Context Map の列を宣言し、生成と検査を変える。
5. 検証設計を解体する。参照の張り替えが多いので、ほかの変更が落ち着いた後に行う。

手順ごとにコミットを分けてよい。

## 検証

- `mise run check-links`：リンクの書き換え、文書の移動と削除で、リンクとアンカーが壊れていないことを確かめる。脅威モデルの古いパスもこれで検出する。
- `mise run check-spec`：設計判断の節の構成、設計領域の配置、文書の形式の検査が通ることを確かめる。
- `mise run check-site`：Context Map の生成と表の表示を含めて、文書サイトを組み立てられることを確かめる。
- `mise run check-terminology`：書き直した文が採用した用語に従うことを確かめる。
- `mise run check-repository-tests`：文書と設定を読む検査のテストが、移動後の文書で通ることを確かめる。
- `mise run test-tools-file -- <変更した検査と生成のテスト>`：表の表示、Context Map の生成、新しい列の検査、`Controls` の抽出の単体テストを通す。
- `mise run check`：用語、仕様影響、作業項目を含む集約の検査が通ることを確かめる。
- 文書サイトを `mise run build-site` と `mise run serve-site` で開き、論理アーキテクチャ、データベース設計、脅威モデルの表示を目で確かめる。

## リスク

- 検証設計の削除は参照が多く、`tools/check/` の検査とモジュールの文書の両方に及ぶ。
  張り替えの漏れは `check-links` と `check-repository-tests` で検出する。
- 個別の事情を全体の文書から移すとき、移す先に同じ内容があると重複し、ないと内容が消える。
  移す前に移す先を読み、重複なら消すだけ、なければ移すと決めてから書き換える。
- 1 列目を太字にする表示は全文書の表に効く。
  1 列目が長い文の表では読みにくくなるので、T002 で代表的な文書を確かめ、必要なら太字の対象を短いセルに限る条件を加える。
- 関係の種類の値は、各モジュールの「責務と境界」の記述から判断する宣言であり、検査は意味の正しさを確かめない。
  値はレビューで確かめる。
