# 生成サイトで EARS の要件文を、受け入れ例の Gherkin と同じように構文で色分けして表示する

## 動機

機能仕様の要件は、日本語の EARS の一文を箇条書きで並べる。
どの文も「〈前提〉場合、〈主体〉は、〈応答〉。」の形で主体を繰り返すので、条件と応答の対応が文に埋もれ、生成サイトでも原稿と同じ箇条書きとして読みにくい。
受け入れ例の Gherkin は、生成サイトが `Given`、`When`、`Then` のキーワードを意味に応じて色分けし、読み手は段の役割を一目で区別できる。

## 対象範囲

- 生成サイトの機能仕様のページで、要件の箇条を EARS の型（常時、事象、状態、任意の機能、望ましくない事象）として読み、前提の部分、主体、応答を、Gherkin のキーワードと同じ見た目の規則で区別して表示する。
- 原稿の書き方は変えない。

## 対象外

- 要件の原稿の書式と、EARS の構文の検査は変えない。

## 設計

[仕様フォーマットの EARS 形式](../../docs/formats/specification-format.md#ears-形式)の区切りの語で、要件文を前置きの節と応答に分ける。

| 区切り | 名札 | 色 |
| --- | --- | --- |
| 〈構成〉では、 | Where | 受け入れ例の Given と同じ |
| 〈状態〉の間、 | While | 受け入れ例の Given と同じ |
| 〈契機〉とき、 | When | 受け入れ例の When と同じ |
| 〈条件〉場合、 | If | 拒否を見分けられるよう、新しい色 |
| 〈主体〉は、 | Then | 受け入れ例の Then と同じ |

- 節ごとに一行にし、区切りの語と主体（モジュールの `README.md` の H1）は表示から外す。主体は節を見れば分かり、毎行の繰り返しが条件と応答の対応を埋もれさせていたからである。
- 名札は受け入れ例と同じ部品（`scenario-keyword`）で描き、見た目をそろえる。
- 読み取りは markdown-it のインラインの要素の上で行う。区切りの語と主体はテキストの要素にあるので、テキストだけを連ねて節を読み、その位置でテキストを分けて印を差し込む。コード片の中の語は区切りと読まない。
- 主体が一度だけ現れ、前置きがすべて区切りの語で終わる文だけを分ける。読み取れない文、判断や例の欄は原文のまま表示する。
- 生成サイトの英文の検査は、名札を文の一部として読まない。名札に続く英語の名前（`If SOAP 1.2 …`）を英文と誤って拒否しないためである。

| 案 | 採らない理由 |
| --- | --- |
| 原稿を条件と応答の表に書き換える | 約 1700 件の要件文の書き換えと検査の作り直しが要り、原稿の一文一要件の形と差分の読みやすさを失う |
| 名札を日本語（契機、条件、応答）にする | 受け入れ例の Gherkin のキーワードと見た目がそろわない |

## 計画

1. EARS の型の目印を読み取る関数と、その表示を生成サイトに足す。
2. 生成サイトのテストで型ごとの表示を確かめる。

## 要約

`mise run spec-diff` は main に対して規範仕様の変更なしと報告する。
生成サイトの機能仕様のページで、要件文を EARS の区切りの語で節に分け、受け入れ例の Gherkin と同じ見た目の名札（Where、While、When、If、Then）を付けて節ごとに表示する。
主体と区切りの語は表示から外し、拒否の節（If）は色で見分けられるようにした。原稿の書き方と検査は変えていない。
生成サイトの英文の検査は、名札を文の一部として読まない。
