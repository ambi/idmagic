# 採否を判断したうえで、仕様の漏れ探しを観点ごとの独立したサブエージェントに並列で行わせる

## 動機

[仕様の漏れを探す観点](../../docs/development/specification-first-workflow.md#仕様の漏れを探す観点)は、仕様を書いたエージェント自身が観点を順に当てる前提で書かれている。
一つの文脈で複数の観点を順に当てると、先に当てた観点の結論が後の観点の読み方に影響し、同じ見落としを繰り返しやすい。

AWS の AI-DLC は、User Stories の段階を mob として実行する。
主担当が下書きを作り、互いの結果を見ない複数の協力者が並列に寄稿し、主担当が統合して、決めきれない判断を利用者へ回す。
ただし協力者は、出荷時の 11 の作業の型のうち enterprise でしか既定で有効にしておらず、費用の大きい方式として扱われている。

観点ごとにサブエージェントを起動すると、それぞれが作業項目と仕様を読み直すので、トークンの費用は観点の数にほぼ比例して増える。
[wi-18868](wi-18868-review-work-item-design-in-fresh-context-before-implementation.md) の一つのレビュー担当で費用と効果を計測した後に、この方式が追加の費用に見合うかを決める。

優先度は、グループの基準どおり採否の判断から始める項目として p3 にする。

## 対象範囲

- wi-18868 の計測結果（一つのレビュー担当のトークン数と、設計を変えた所見の数）を読む。
- `risk: high` または `--concern security` を求める未完了の項目から 2〜3 件を選び、観点ごとの並列レビューと一つのレビュー担当を比べる。比べる点は、トークン数、所見の数、一つのレビュー担当だけでは出なかった所見のうち設計を変えたものの数である。
- 結果から採否を決める。
- 採るなら、行う条件を `risk: high`、`--concern security`、`--concern boundary` のような起票時に判定できる値で定め、wi-18868 が足した手順の条件分岐として書く。条件に当たらない項目では一つのレビュー担当か省略に留める。

## 対象外

- 条件に当たらない項目への並列レビューの適用。
- 観点ごとの常設のエージェント定義ファイル。特定の実行環境に依存するので、手順は環境によらない形で書く。

## 設計

出典: AWS AI-DLC のドキュメント「Introduction」の Small Mob, Broad Agents と「Glossary」の Mob execution の項（https://awslabs.github.io/aidlc-workflows/guide/）。本文を読んだ。調査日は 2026-11-28。

AI-DLC から採る点は、互いの結果を見ない複数の視点で並列に読むことと、費用の大きい方式を高い保証が要る作業に限ることである。
採らない点は、作業の型ごとの協力者の設定と、主担当による統合の段階である。
IdMagic では、統合と判断を実装するエージェントと利用者が行う。

費用が見合わなければ、計測した数値を要約に書いて中止する。
採らない場合でも、計測した数値は wi-18868 の省く条件を決め直す材料になる。

## 計画

1. wi-18868 の計測結果を読む。
2. 2〜3 件で並列レビューと一つのレビュー担当を比べる。
3. 採否を利用者と決め、採るなら条件と手順を書く。

- `mise run check-agent-guidance`: skill から呼ぶタスクとリンクの形式を確かめる。

- `mise run check-work-items`: 記録の形式を確かめる。

## リスク

並列レビューの所見が重複すると、統合の手間が費用に加わる。
比較で一つのレビュー担当だけでは出なかった所見の数を数え、追加の効果がなければ採らない。
