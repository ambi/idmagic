# 状態遷移表を testdata から生成し、テストに文書の Markdown を読ませない

## 動機

User、Tenant、SigningKey のモデルベースのテストは、`backend/shared/testing_statematrix` の `Read` で `docs/modules/` の機能仕様を相対パスで読み、状態遷移表（マトリクス形式）を Markdown から解析する。
wi-86874 と wi-51017 は、この方式を残りの状態機械へ広げる計画である。

文書の Markdown をテストの入力にすると、次の問題が起こる。

- テストの入力が、`go list` の依存グラフにもパスの分類にも現れない。文書だけの変更がテストの結果を変えるので、CI の検査群の選択（wi-86206）と手元のテストの選択（wi-57328）は `docs/` を例外にしなければならない。`integrate-work-item` も、暫定でテストの入力にならない Markdown を `work-items/` と `docs/development/` に限っている。
- 文書の書式がテストの API になる。表の書き方や見出しの推敲がテストを壊し得る。
- `../../../../docs/...` の相対パスで、パッケージの配置と文書の配置が結び付く。

具体例については、[実行可能な具体例と派生表示](../../docs/formats/specification-format.md#実行可能な具体例と派生表示)が、実装の隣の `testdata/*.examples.json` を正本にし、`feature.md` の区間を `mise run generate-spec-examples` で生成し、`mise run check-spec` がずれを拒否すると定める。
状態遷移表だけが、文書を正本にしてテストが解析する逆の形になっている。

## 対象範囲

- 状態遷移表（マトリクス形式）の正本を、状態機械を実装するパッケージの `testdata/<machine>.statematrix.json` に置く。状態遷移を持つ 25 本の機能仕様のすべての状態機械を移す。
- 機能仕様の表を、具体例と同じく区切りのコメントの間に生成する。生成は既存の生成タスクに加えるか、同じ形の生成タスクを足す。
- `mise run check-spec` は、正本とのずれ、状態の表との不一致、遷移の表との不一致、空のセルを引き続き拒否する。
- `testing_statematrix` は JSON を読む。既存の三つのテストを、パッケージの `testdata` を読む形に移す。
- テストが `docs/` の下のファイルを読むことを拒否する検査を、リポジトリ検査に足す。
- `docs/formats/specification-format.md` の状態遷移の節と実行可能な具体例の節、`spec-change` スキルの表の書き方を、正本の場所に合わせる。

## 対象外

- 状態の表と遷移の表の生成。遷移の表はマトリクスと同じ遷移の集合を述べるので生成もできるが、表ごとの説明の列を持つため、最初は手書きのまま検査で一致を求める。
- モデルベースのテストの追加（wi-86874、wi-51017）。
- `infra/schema/postgres.sql` を読むスキーマのテストなど、文書ではないパッケージ外の入力。wi-57328 が扱う。

## 設計

### 正本の形

JSON は、状態機械の名前、状態の列、操作の列、各セルの結果（`testing_statematrix` の `Outcome` と同じ種類と遷移先）を持つ。
セルの結果の書式は、現在の表のセルの書式と一対一に対応させ、生成した表が現在の表と同じになるようにする。
移行の最初の差分は、表の区間に区切りのコメントが加わるだけで、表の中身は変わらないことを確かめる。

### 置き場所

状態機械を実装するパッケージの `testdata` に置く。
モデルテストのない状態機械も同じ場所に置き、後から加えるテストが同じパッケージから読めるようにする。
実装が複数のパッケージにまたがる状態機械は、ドメインの型を持つパッケージに置く。

### テストが文書を読まないことの検査

`_test.go` の文字列定数とファイル読み取りの引数が `docs/` を指すものを拒否する。
文字列を組み立てて読むなど静的に解決できない読み取りは、この検査の対象外と報告し、wi-57328 の選択器で全体側へ倒す。

### 選ばなかった案

- 文書を正本のまま、テストが読む文書をパッケージの入力として宣言する：選択の仕組みは成り立つが、文書の書式がテストの API のまま残り、具体例との不一致も解消しない。
- 表を Go のコードとして書く：生成と検査は同じようにできるが、具体例の JSON と形がそろわない。

## 計画

1. `testing_statematrix` の `Machine` と、`specification-doc.ts` の表の検査を読み、JSON の形を決める。
2. 生成と検査の RED（ずれ、状態の不一致、空のセル）を確かめ、実装する。
3. 25 本の機能仕様の表を JSON へ移し、生成した表が現在の表と一致することを確かめる。
4. 三つのテストを移し、`docs/` を読むテストを拒否する検査を足す。
5. 形式の文書とスキルを更新し、wi-57328 の `docs/` の例外と、`integrate-work-item` の暫定の規則を見直す。
