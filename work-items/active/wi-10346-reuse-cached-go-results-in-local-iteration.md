# 作業中の Go の局所検査は、入力が変わらないテストの結果を再利用する

## 動機

Go のテストを実行するタスク（`test-go`、`test-go-race`、`test-go-package`、`test-go-changed`、`verify-changed` と `verify-integration` の Go の部分）は、すべて検証の実行器（`tools/verification/src/main.ts`）を通り、実行器は常に `-count=1` を付ける。
`.verification` の報告に「今回実際に実行して通った」ことを記録するための意図的な選択で、Go の結果のキャッシュは使われない。
そのため、作業中に RED と GREEN を繰り返すたびに、入力が変わっていないパッケージも実行し直す。

2026-10-28 の計測（wi-57328）では、Go の結果のキャッシュは同じ worktree の中では当たるが、`-trimpath` を付けても worktree をまたいでは当たらなかった。
作業項目は一つの worktree の中で進めるので、作業中の繰り返しには効く。

`-count=1` は wi-85094（2026-10-11）で入った。目的は、報告が「今、この環境で実際に実行した結果」であることを保証することで、この目的は今も正当である。

- Go はテストが開いたファイルと読んだ環境変数をキャッシュの鍵に含めるが、実行環境の状態は含めない。
- DB を使うテストの基盤（`testing_postgres/pgtest.go`）は、embedded-postgres を起動できない環境（サンドボックスの中など）では DB テストを Skip にし、パッケージとしては成功を返す。
- そのため、サンドボックスの中で Skip を含んで成功した結果が、DB を使える環境での実行にキャッシュから返り、DB テストを一度も実行しないまま成功に見えることがあり得る。逆向きも同じである。
- 環境変数を読むのは Kerberos のテスト（`KERBEROS_KDC_ADDR`、`KERBEROS_KEYTAB_FILE`）だけで、その値はキャッシュの鍵に入る。

したがって、キャッシュを使ってよいのは、証拠として記録しない作業中の繰り返しだけである。

## 対象範囲

- 作業中の局所検査（`test-go-package`、`test-go-changed`）が、Go の結果のキャッシュを使えるようにする。
- キャッシュから返った結果は、実行した結果と区別して `.verification` の報告に記録し、完了の証拠として数えない。
- Skip を含む結果をキャッシュから再利用しないか、DB を使うパッケージをキャッシュの対象から外す。どちらにするかは設計で決める。
- 方針を `testing.md` の検証の節に書く。

## 対象外

- 証拠として使う実行（`verify-changed`、`verify-integration`、`verify`、`test-go`、`test-go-race`、CI）。`-count=1` のままにし、今この環境で実行した結果を記録する。
- worktree をまたいだキャッシュの共有。`-trimpath` でも当たらないことを確かめた。
- Go のビルドのキャッシュ。既に効いている。

## 設計

### 決めること

- 環境に依存する Skip の扱い。Skip を含む結果をキャッシュから受け取ったら実行し直す案と、DB を使うパッケージ（`testing_postgres` を取り込むもの）をはじめからキャッシュの対象から外す案を比べる。
- 外部の状態に依存するテストが今後増えたときに、キャッシュの対象から外す手段（パッケージの宣言、環境変数など）。
- キャッシュを使う局所検査の報告が、完了の証拠を読む検査に混ざらないようにする方法。

### 効果の測り方

作業中の典型として、一つのパッケージを直して `test-go-changed` を繰り返す場合の所要時間を、キャッシュの有無で比べる。
DB を使うパッケージを対象から外す場合は、それでも残る効果を測ってから、実装に進むかを決める。

## 計画

1. 報告と証拠の検査が、実行の状態をどう読んでいるかを確かめ、上の「決めること」を確定する。
2. 実行器と報告を変え、RED を確かめて実装する。
3. 効果を測り、文書を更新する。

## 検証

- 入力を変えたパッケージだけが実行し直され、変えていないパッケージは報告にキャッシュの再利用として残ること。
- テストが読むファイルを変えると、そのテストがキャッシュを使わずに実行されること。
- サンドボックスの中で DB テストが Skip された結果が、DB を使える環境での実行にキャッシュから返らないこと（故障の注入で確かめる）。
- 証拠として使う実行（`verify-changed` など）が、引き続き `-count=1` で実行されること。
- `mise run test-tools`、`typecheck-tools`、`lint-tools`、`check-work-items`、`check-links`。

## リスク

- 外部の状態に依存するテストがキャッシュから成功を返すと、壊れていても通る。対象から外す手段を用意し、外部に依存するテストを足すときの手順に書く。
