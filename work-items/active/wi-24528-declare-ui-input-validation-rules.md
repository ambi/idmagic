# UI ページの入力項目ごとに検証規則を宣言し、実装の欄の規則と照合する

> 2026-11-22：書き直し待ち。wi-92664 は入力項目を宣言しない方針に変わったため、本項目の前提（ページ宣言の入力項目への規則の宣言）は無効である。
> 新しい方針と書き直しの指示は [wi-92664 の「現在の計画と進捗」](wi-92664-model-ui-pages-and-interaction-flows-in-typespec.md#現在の計画と進捗2026-11-22-時点以下の古い節より優先する)の残作業の4にある。

## 動機

[wi-92664](wi-92664-model-ui-pages-and-interaction-flows-in-typespec.md) は、UI ページ、フォームと入力項目を TypeSpec に宣言し、`pageId/formId/fieldId` の識別子と、束縛先の API プロパティ（`@bind`）を定めた。
入力の必須性、形式、範囲と項目間の条件は、その項目の対象外として残した。

[検証の分担](../../docs/design/application/user-interface.md#検証の分担)は、入力だけで判定できる検証を SPA が担い、受理範囲を欄ごとにサーバーの検証とそろえ、上限と範囲を TypeSpec の `@maxLength`、`@minValue`、`@maxValue` から取ると定める。
実装では、2026-11-22 時点で `frontend/src/` のテスト以外の 35 ファイルが `formSchema(...)` を 38 回呼び、欄の規則を `frontend/src/lib/form.ts` の部品（`requiredText(LENGTH.name)`、`optionalUrl`、`cidrList` など）で画面ごとに組み立てている。
一方、上限の値は `frontend/src/lib/lengthLimits.ts` の `LENGTH` に手で写しており、欄の規則が束縛先の API プロパティの制約と一致することを確かめる検査はない。
ページの設計から、ある入力がどの規則で、どこまで受け付けるかも読み取れない。

## 対象範囲

- 宣言済みの入力項目ごとに、検証の担当と規則を TypeSpec の UI 宣言へ書けるようにする。束縛した入力の長さと範囲は、束縛先の API プロパティの制約から導き、宣言へ写さない。
- API が定めない UI 固有の規則（API では任意だが画面では必須、プロトコル上使える値への制限、項目間の条件、確認用の入力の一致）だけを、規則の種類と根拠を付けて宣言する。
- 生成するページ詳細の入力項目の表に、規則、担当（SPA か API か）と出典を示す。
- 実装の `formSchema` の欄と使う部品を抽出し、宣言した規則および束縛先の制約と照合する。食い違いは生成を失敗させる。

## 対象外

- 照合で見つかった実装の欄の規則と API 契約の食い違いの修正。本項目では食い違いを列挙して分類し、製品の振る舞いを変える修正は個別の bugfix の項目として起票する。
- API の受理範囲（TypeSpec の制約と backend の検証）の変更。
- エラー文の文言、表示位置、`aria` 属性の規則。[検証の分担](../../docs/design/application/user-interface.md#検証の分担)が定める。
- 静的な `name` 属性の付与。[wi-80172](wi-80172-name-every-frontend-form-control.md) が扱う。本項目の照合は `formSchema` のキーで行い、`name` 属性に依存しない。

## 設計

### 規則の出典を分ける

| 規則 | 出典 | 宣言の扱い |
| --- | --- | --- |
| 長さの上限と下限、数値の範囲、列挙、形式 | 束縛先の API プロパティの `@maxLength`、`@minLength`、`@minValue`、`@maxValue`、`@pattern`、`@format`、列挙型 | 書かない。生成時に束縛先から導いて表示する |
| API で任意だが画面では必須 | 画面の目的 | 規則と理由を宣言する |
| プロトコル上使える値への制限（絶対 URL、scope-token、PEM） | 標準または既存の設計 | 規則の種類と出典を宣言する |
| 項目間の条件（ほかの選択で必須になる、確認用の値の一致） | 画面の操作 | 参照する入力項目を TypeSpec のプロパティで指す |
| 業務ルールと競合 | API（422、409） | 宣言しない。API の操作への参照で担当を示す |

束縛しない入力（UI 内の確認用の値、複数のプロパティへ分解する値）には、束縛先がないため規則をすべて宣言する。
パスワードとシークレットには上限を課さない既存の規則を、規則の種類として表す。

### 照合の方法

実装の欄の規則は `formSchema({ key: rule(...) })` の形で書かれている。
キーは API へ送るプロパティ名にそろっているため、wi-92664 が入力項目に持たせた照合用の名前と対応させる。
部品の呼び出し（`requiredText(LENGTH.name)` など）を ast-grep で抽出し、部品の種類と上限の値を、宣言の規則と束縛先の制約から求めた期待値と比べる。
`LENGTH` の値は既存の `backend/shared/spec/length.go` と同じ数を持つ前提を使い、新たな対応表を作らない。

採らない案は次のとおりである。

- 欄の規則を TypeSpec から生成して実装を置き換える。wi-92664 は実行時のフロントエンドから設計の宣言への依存を加えない方針であり、生成への移行は判断の範囲が広い。
- 規則を宣言だけに書き、実装との照合を行わない。宣言と実装が別々に古くなる。

### 未解決の問い

着手時に代表のページ（ユーザーの作成と編集、ログイン、アプリケーションの作成）で、規則の種類の列挙と `@field` への付け方（情報の型へのプロパティの追加か、別の decorator か）を決める。
`formSchema` を使わない入力（`pattern` と `maxLength` で扱う確認コード、制御コンポーネントの独自の検査）の扱いを、同じ代表例で決める。

## 計画

1. 代表のページで規則の宣言の形と、束縛先の制約の導出を確かめる。
2. 生成文書の入力項目の表へ規則、担当と出典を加える。
3. `formSchema` の抽出と照合を加え、宣言済みの全ページで食い違いを列挙して分類する。製品の修正が要るものは別の項目として起票する。
4. 照合を通常の UI 検査に含める。

## 検証

- `mise run test-tools-file -- build-site/src/<対象テスト>`：束縛先の制約の導出、宣言にない欄、上限と部品の種類の食い違いを拒否すること。
- `mise run generate-ui-pages -- --check`：宣言済みの全ページで照合が成立し、生成文書が最新であること。
- `mise run check-spec` と `mise run check-links`：UI 宣言と生成文書の配置と参照。
- `mise run verify-changed -- <base>`：差分に応じた型検査、lint とテスト。

## リスク

- 規則の宣言が API 契約を写した重複になる。束縛した入力の制約は導出に限り、宣言できる規則を UI 固有のものへ絞る。
- 照合で多数の食い違いが見つかり、修正が本項目へ混ざる。本項目では分類までとし、修正は個別の項目に分ける。
