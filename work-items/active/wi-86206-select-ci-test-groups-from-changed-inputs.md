# 変更入力に影響する CI の検査群を選び、文書変更で製品テストを起動しない

## 動機

[現在の CI](../../.github/workflows/idmagic-ci.yaml)は、変更内容にかかわらず Go 全体の race 検査、UI の検証、ブラウザー E2E、スキーマ検査を実行する。
手元では[最終検査の選択](../../docs/development/specification-first-workflow.md#最終検査の選択)により文書変更の検査を絞れるが、CI には同じ選択がない。
変更した入力に対応する検査群を選び、影響しない製品テストの起動費用を減らしたい。
時間の削減量は未実測なので、同じ変更例による実行前後の記録を残す。

## 対象範囲

- PR の base と head、push 前後の差分から、Go、UI、ブラウザー E2E、スキーマの検査群を選ぶ決定的な計画を作る。
- 共有コード、公開契約、設定、依存、検証基盤を保守的に扱い、影響が分からない場合は全検査を選ぶ。
- 計画を CI の job と step の条件へ接続し、実行、対象外、失敗、未実行を区別して報告する。
- 必須チェックが安定した名前で計画と実行結果を集約し、選択した検査の欠落を拒否する。
- 継続的インテグレーションの説明と検証タスクを同期する。

## 対象外

- パッケージ単位やテスト名単位への細かな分割。
- 必須の契約証拠、DB 必須モード、race の検出能力の緩和。
- CodeQL と依存監査の実行範囲、監査頻度の変更。
- 過去の実行結果のキャッシュ、重い検査を main 統合後だけへ移すこと。
- GitHub の保護設定の変更と、workflow の外から必要なチェックを無効化すること。

## 設計

### 検査群の選択

リポジトリ検査は全変更で維持する。
Go、UI、ブラウザー、スキーマの選択は、次の初期方針を計画の一か所で定義する。

| 変更入力 | 選ぶ製品検査群 |
| --- | --- |
| 作業項目と開発文書の Markdown だけ | 製品テストを選ばず、文書と記録の検査を維持する |
| frontend のコード、テスト、設定、依存 | UI とブラウザー E2E |
| backend のコード、テスト、設定、依存 | Go とブラウザー E2E。スキーマに触れた場合はスキーマも選ぶ |
| TypeSpec、公開契約、共有設定、mise、CI、検証基盤、未知の入力 | 全製品検査群 |
| 複数の種類が混在する変更 | 各種類が選ぶ群の和集合 |

文書という拡張子だけで除外しない。
規範、実行可能な仕様例、fixture、生成物の入力を扱うパスは製品検査へ影響し得るため、初期の除外を `work-items/` と `docs/development/` の Markdown に限定する。
それらをテストが入力として読む場合は該当する群を選ぶ。
削除と名前の変更では新旧のパスを両方扱う。
変更パスの取得に失敗した場合、未知のパス、比較基準の不在では全群へ戻す。

パスの計画は、細かな関数の影響解析を保証しない。
初期実装では backend の局所変更でも Go 全体とブラウザーの群を選び、公開契約の波及を落とさない。
選択基準は `mise` の実行入口と CI の両方が参照できる形にし、別のパス条件を workflow の各 job へ複製しない。
実装は既存のリポジトリ検査ツール内に置き、計画を出力する `mise` タスクを追加する。

### 必須チェックと実行証拠

workflow 全体に paths フィルターを置かず、計画の job はすべての対象イベントで起動する。
最終の必須チェック名を維持し、選択された群が成功した場合だけ成功を返す。
対象外の群は理由とともに表示し、成功したテスト数へ加えない。
選択された群の skip、失敗、取消、結果の欠落は対象外へ変換しない。
Go を選ぶときは現在と同じ実行の契約証拠と DB 必須条件を維持する。

### 代替案

- 全群を毎回実行する案は最も保守的だが、入力が独立した文書変更でも製品スタックの費用を払うため変更する。
- workflow 全体の paths フィルターは、必須チェックが報告されなくなる場合があるため採らない。
- backend と frontend を単純に独立扱いする案は、公開契約とブラウザーの波及を落とすため採らない。
- main だけに重い検査を移す案は、統合前の検出時点を失うため採らない。

## 計画

1. 各群が読む入力と CI の必須チェック名を確認し、選択表と影響が不明な入力の扱いを確定する。
2. 最小の差分 fixture で計画の RED を確認し、計画器と `mise` の入口を実装する。
3. 現行 workflow の検査を条件付きの群へ分け、最終の必須チェックへ接続する。
4. 文書だけ、UI、backend、契約、混在する変更で計画と結果の集約を検証する。
5. 実行した群、起動回数、所要時間を前後で記録し、未実測の効果と区別する。

## 検証

製品要件 ID は N/A（CI の検査選択）。
受け入れ RED は Git 差分から計画を出す CLI、単体 RED は計画と結果の集約で観測する。

- 文書だけ、UI だけ、backend、スキーマ、公開契約、検証基盤、混在、空差分、削除、移動、未知の入力を対照にする。
- 比較基準を取得できない場合は全群を選ぶ。
  変更した対象を対象外へ落とす故障を注入し、計画テストが拒否することを確認する。
- 選択された群の failed、skipped、cancelled、結果不在を最終チェックが拒否する。
  対象外の群だけが計画の理由付きで除外される。
- `mise run test-tools-file -- <変更したテストファイル>`、`typecheck-tools`、`lint-tools`、`lint-repo`、`check-command-map`、`check-work-items`、`check-links` を選ぶ。
- CI の実行確認では、文書だけの変更で製品スタックを起動せず、製品と契約の変更では必要な群が実行されることを確認する。
  手元の全体ゲートの成功だけを CI の配線の証拠にしない。

## リスク

- 選択漏れは変更したコードを検証しないまま統合させる。
  初期の除外を限定し、共有入力と未知の入力は全群を選び、削除と移動も確認する。
- 条件付き job の skip を最終成功と混同する可能性がある。
  計画で対象外とした群と、選択したのに実行されなかった群を区別する。
- 実行群が減っても依存の準備が支配的なら、所要時間は減らない。
  実行群と準備時間を分けて測り、改善量を記録する。
