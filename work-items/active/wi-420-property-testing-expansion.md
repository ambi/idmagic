# 値ベースのプロパティテストを導入し、認可の評価とクレームの合成に関係の検査を当てる

## 動機

[テスト方針のプロパティテストとファジング](../../docs/development/testing.md#プロパティテストとファジング)は、往復、厳密性、構造上の上限、冪等性を判定基準に挙げ、単調性も判定基準に使うと書く。
しかし手段は Go のファジング（バイト列を入力とする探索）だけである。
往復と冪等性は、バイト列ではなく構造を持つ値を生成して確かめるほうが自然であり、バイト列から構造を復号すると探索の大半が構造として成り立たない入力に費やされる。

正しい答えを独立に計算できない領域もある。
AccessControl の関係グラフの評価と ClaimMapping の合成がそれに当たり、製品の中で検証が薄く、誤りの影響が大きい。
こうした対象には、入力を決まった形で変えたときに出力がどう変わるべきかという関係（メタモルフィック関係）が使える。
たとえば「関係タプルを追加しても、既存の許可は拒否に変わらない」「グループの所属を増やしても、開示されるクレームは減らない」は、正解を知らなくても誤りを検出できる。

## 対象範囲

- Go に値ベースのプロパティテストの道具を導入する。第一の候補は `rapid` である（標準の `testing` に統合され、shrinking がデフォルトで働き、依存が小さい）。
- 既存のファズ対象のうち往復か冪等性を判定基準にするものを一つ値ベースへ書き換え、記述量と失敗時の読みやすさを比べてから広げる。
- テスト方針に、メタモルフィック関係を判定基準の一つとして加える。単調性だけを確かめる関係は常に許可する実装にも通るので、正当に拒否される入力が拒否されることと対にする要求を書く。
- AccessControl の関係グラフの評価と ClaimMapping の合成に関係の検査を当てる。対象は単調性、深さの上限、合成の順序に対する不変性とし、各関係を破る誤った実装を検出できることを確かめる。
- 失敗した入力の最小化と、seed による再現の手順をテスト方針に書き、値ベースのプロパティを走らせる経路を `mise.toml` に加える。探索を Pull Request の門に入れないという既存の方針は変えない。

## 対象外

- 状態遷移表をモデルにしたテスト。wi-86874 と wi-51017 が扱う。
- 設計時のモデル検査と決定的なシミュレーション。wi-421 が扱う。
- 既存のファズ対象の一斉の書き換え。信頼境界を越える解析は、バイト列の探索のまま残す。
- フロントエンドへの導入。変換と正規化の純粋な関数が数個しかなければ導入しない。判断は着手時に行う。

## 設計

関係グラフの評価が純粋な計算として取り出せるかは、まだ調べていない。
データベースを必要とする形なら、テスト方針がプロパティを使わない対象に当たるので、評価の純粋な中核を切り出すことが先行作業になる。
着手時に確かめてから範囲を確定する。

## 検証

- 関係タプルの追加が既存の許可を拒否へ変える誤った実装と、クレームの合成の順序を入れ替えた誤った実装が検出される。
- 失敗したプロパティが、最小化した入力と再現用の seed を出力する。
- `mise run verify`

## リスク

メタモルフィック関係は、対にする性質を欠くと空虚な検査になる。
誤った実装を検出できることの確認が、それを防ぐ唯一の工程である。
