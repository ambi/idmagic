# Bearer で届いた要求のステップアップ判定をログインセッションに結び付ける

## 動機

管理ポータルとアカウントポータルは OIDC の SPA であり、API を Bearer のアクセストークンで呼ぶ。
ステップアップ認証の成立はログインセッションの `step_up_at` に記録されるが、Bearer の要求ではセッションを解決しない。
共有の HTTP 支援は、アクセストークンの `iat` を認証時刻とみなし、`StepUpSatisfied` は `max(auth_time, step_up_at)` をその値で評価する。

リフレッシュで発行したアクセストークンは、`iat` も `auth_time` もリフレッシュの時刻になる。
有効期間は 10 分なので、リフレッシュから 5 分の間は、再認証を経ずにパスワードの変更、認証の要素の解除、管理画面のステップアップ必須の操作が通ると読める（2026-11-14 のコード読解。テストでの観測は T002 で行う）。
盗んだリフレッシュトークンがあれば、いつでもステップアップ済みの状態を作れる。

[[wi-468-system-console-privileged-session-assurance]] は、システムコンソールの特権操作にセッションの MFA と方式付きのステップアップを要求する。
その判定もこの経路を通るので、先にステップアップの根拠をログインセッションへ移す。

## 対象範囲

- 認可コードから発行するアクセストークンとリフレッシュで発行するアクセストークンに、発行元のログインセッションを結び付ける。リフレッシュトークンの記録は既に `sid` を引き継いでいるので、それをアクセストークンへ載せる。
- 共有の HTTP 支援が Bearer の要求を認証したとき、トークンの `sid` からログインセッションを解決し、ステップアップの判定に、そのセッションの `auth_time`、`step_up_at`、`amr` を使う。
- セッションが終了、失効、別主体、別テナント、または `sid` を持たないトークンでは、ステップアップを満たさないものとして `403 step_up_required` を返す。
- 管理発行の API アクセストークンは、現在の規則（保持そのものをステップアップの資格とみなす）を変えない。
- ステップアップ必須の操作すべてで、リフレッシュ直後の Bearer が `step_up_required` で拒否され、セッションでステップアップした後は同じ Bearer で成功することを確かめる。

## 対象外

- ステップアップの成立方式の記録と、MFA に限る判定。
  [[wi-468-system-console-privileged-session-assurance]] が扱う。
- リフレッシュで発行するトークンの `auth_time` を元の認証時刻にすること。
  リライングパーティーへ届くクレームの変更なので、必要なら別に起票する。
- ログインセッションの失効をアクセストークンの即時失効へ広げること。
  本項目はステップアップの判定だけをセッションへ結ぶ。

## 設計

判定の根拠の候補を二つ比べ、ログインセッションへの束縛を採る（2026-11-14 に利用者と決定）。

| 候補 | 採否 | 理由 |
| --- | --- | --- |
| アクセストークンに `sid` を持たせ、ゲートがセッションを読む | 採用 | 既存の `StepUpDialog`（パスワード、TOTP、WebAuthn、復旧コード）と `step_up_at` の記録をそのまま使える。セッションを終わらせればステップアップの根拠も消える |
| リフレッシュでも元の `auth_time` と `amr` を引き継ぎ、RFC 9470 の `insufficient_user_authentication` で再認可させる | 不採用 | 標準に沿うが、ステップアップが画面内のダイアログでなく再認可のリダイレクトになり、既存の UI と成立方式の記録を作り直す必要がある |

共有の HTTP 支援の `accessTokenAuthentication` は、現在は主体と `iat` だけを持つ。
`AccessToken` に `SessionID` を加え、`Authenticator` はセッションの解決を `SessionAuthenticator` に依頼する。
解決したセッションの認証の結果を、ステップアップの判定に渡す認証の結果とする。
`mfadomain.StepUpSatisfied` の式は変えない。

`sid` を持たないアクセストークン（`client_credentials`、トークン交換など）は、人のステップアップを表さないので満たさない側に倒す。

## 計画

1. T001 で、規範に Bearer の経路とリフレッシュ直後の拒否を書く。
2. T002 で、リフレッシュ直後の Bearer がステップアップ必須の操作を通る現状を受け入れ境界で観測する。
3. トークンへ `sid` を載せ、ゲートがセッションを解決する。

## タスク

- [ ] T001 [Spec] REQ-AUTHENTICATION-039 に、Bearer の要求は発行元のログインセッションで判定することと、セッションのないトークンの拒否を書く。
- [ ] T002 [Acceptance] リフレッシュ直後のアクセストークンでパスワードの変更が受け付けられることを HTTP 境界で観測し、RED にする。
- [ ] T003 [App] アクセストークンへ `sid` を載せ、イントロスペクションの結果から共有の HTTP 支援へ渡す。
- [ ] T004 [App] Bearer の要求でセッションを解決し、ステップアップ判定へ渡す。終了したセッションと `sid` のないトークンを拒否する単体テストを先に書く。
- [ ] T005 [Verify] ステップアップ必須の全操作（`TestStepUpAnnotatedInterfacesMatchGatedHandlers` が列挙するもの）で、Bearer の経路の拒否と成功を確かめる。

## 検証

- 受け入れテスト：リフレッシュ直後の Bearer の拒否、セッションでのステップアップ後の成功、セッション終了後の拒否。
- 最終検査は `mise run verify-changed -- <着手時の基準リビジョン>` とする。

## リスク

ゲートがセッションを引くので、Bearer の要求ごとにセッションの読み取りが一回増える。
ステップアップ必須の操作だけで解決し、通常の管理 API の要求には足さない。

フロントエンドが同じ利用者の別セッションで再認証すると、トークンのセッションとステップアップしたセッションがずれる。
`StepUpDialog` はポータルのセッション Cookie の宛先へ送るので、トークンの発行元と同じセッションであることを受け入れテストで確かめる。
