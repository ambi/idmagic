# ユーザーが自分を代行できるエージェントを一覧し、個別に取り消せるようにする

## Motivation

`Consent` は `(user_id, client_id)` で同意を記録する。エージェントは自身の資格情報を持たず `AgentCredentialBinding` で既存の `OAuth2Client` に束縛されるため、**エージェント単位の同意は記録されない**。同じクライアントに 3 つのエージェントが束縛されていれば、ユーザーから見えるのは 1 件のクライアント同意だけで、その裏で何体のエージェントが自分として動けるのかは分からない。

代行の可否を実際に決めるのは `may_act` である。しかし `may_act` はトークンエンドポイントが発行時に載せるものであって、ユーザーが与えるものではない。つまり「誰が自分の代わりに行動してよいか」の権限は、ユーザーの与り知らないところで決まり、ユーザーの手元には取り消す対象すら現れない。アカウントポータルの「接続済みアプリ」からクライアントごと同意を撤回すれば連鎖的に止まるが、それは 3 体まとめて止めることであって、1 体を止めることではない。

これは OpenID Foundation が指摘する「自律実行モードと代行モードの切り替えを追跡できない」というギャップを、ユーザー側から見たものである。IdMagic は既に `act` チェーン・委譲深さの上限・`may_act` の強制という、委譲を**サーバー側で**厳密に扱う仕組みを持っている。欠けているのは、その委譲が誰の権限に由来するのかをユーザー本人に示し、本人の手で断てる経路である。

既に `Consent` には GDPR 第 7 条 3 項の撤回可能性という設計根拠が置かれ、REQ-OAUTH2-032 が「ユーザーは接続済みアプリの同意を自分で撤回できる」ことを規範化している。エージェントの代行はそれよりも強い権限であり、同じ根拠が同じかそれ以上の強さで当てはまる。

## Scope

- `spec/contexts/oauth2/models.tsp` の `Consent` 集約を、エージェントを主体とする委譲付与を表現できるよう拡張する。**新しい独立した集約や独自の受領書形式は作らない** (理由は `## Design`)。付与の単位は「ユーザー U が エージェント A に対し、scope または `authorization_details` の範囲 S で、期限 T まで代行を許す」とする。
- 付与が無いエージェントの代行を拒否する規範シナリオを追加する。既存の `may_act` 強制と重ねる形にし、二つ目の判定経路を作らない。
- 撤回の伝播を確定する。撤回は [[wi-58-continuous-access-evaluation-agent-revocation]] の失効エポックを前進させ、発行済みトークンがイントロスペクションで即座に無効化されるところまで届かせる。エージェント全体の失効ではなく、当該ユーザーの代行だけが止まること。
- アカウントポータルに、自分を代行できるエージェントの一覧 (エージェント名・所有者・付与範囲・期限・最終利用) と、個別の撤回を追加する。
- 管理コンソール側に、テナント管理者が付与状況を参照できる経路を追加する。付与の代行は行わない (REQ-OAUTH2-031 が同意について定めた「参照・撤回はできるが付与は代行できない」規則を踏襲する)。
- 付与と撤回をイベントとして残し、[[wi-377-agent-and-delegation-chain-audit-axes]] が加える軸から辿れるようにする。
- `spec/contexts/identity-management/models.tsp` に `model Agent` 集約を追加する ([[wi-369-agent-capability-survey-2026-08]] の再評価条件による。先行する work item が解消済みなら重複させない)。

## Out of Scope

- **独自の「委譲受領書」文書形式の定義。** `draft-nelson-agent-delegation-receipts` が標準化を試みている領域だが、個人 draft の段階で外部へ提示可能な受領書形式を作ると、標準が固まった時点で捨てる資産になる。本 work item は内部の付与記録と本人向けの可視化に閉じ、外部へ持ち出せる署名済み成果物は作らない。IETF で採択された時点で、既存の付与記録を素材に再評価する。
- **W3C Agent Identity Registry Protocol への追随。** 2026-04 発足のコミュニティグループであり、相互運用実績も規範文書も無い。[[wi-369-agent-capability-survey-2026-08]] は「独自形式のエージェントレジストリ」を「プロプライエタリの乱立を招く」という理由で棄却したが、標準化の場ができた以上、棄却の根拠は「コミュニティグループ段階である」に更新する。WG または勧告トラックへ進んだ時点で再評価する。
- エージェントからエージェントへの再委譲の付与モデル。現行の委譲深さ上限 ([[wi-368-delegation-depth-policy-and-delegation-mode-claim]]) が扱う。
- 付与の承認ワークフロー。本 work item は本人による直接の付与と撤回に閉じる。
- ガードレール (レート・予算・回数上限)。[[wi-59-agent-governance-guardrails-audit-inventory]] が持つ。

## Design

未定。着手時に次の 3 点を確定して本節に記録する。

1. **`Consent` の拡張方法。** 案 A: `Consent` に任意の `agent_id` を加え、`(user_id, client_id, agent_id)` を鍵とする。既存レコードは `agent_id` 未設定のクライアント同意として残る。案 B: `Consent` を参照する別テーブルとして委譲付与を持つ。案 A のほうが撤回と期限の規則を共有できるが、鍵の変更は移行を伴う。**独立集約を作らない方針は確定しており、選ぶのは A と B のどちらか。** 理由は、同意と委譲付与は撤回可能性・期限・テナント境界・監査という 4 つの規則をすべて共有しており、別集約にすると同じ規則の二つ目の実装を抱えるからである。
2. **付与が無い場合の既定の挙動。** 既存の稼働中エージェントは付与を持たない。移行期間中の既定を「クライアント同意があれば代行を許す」とするか「拒否する」とするかを決める。前者は互換だが本 work item の目的が骨抜きになり、後者は稼働中のエージェントを止める。
3. **付与の粒度。** scope 単位で足りるか、`authorization_details` (RFC 9396) の単位まで下ろすか。後者は [[wi-51-rich-authorization-requests-agent-scopes]] の単調な縮小の規則と噛み合うが、UI での提示が難しくなる。

## Plan

- 仕様を先に変え、付与の集約・撤回の伝播・拒否シナリオを規範化する。
- 撤回から失効エポックへの結線は、既存の `AdvanceRevocationEpoch` を使う。エージェント全体ではなく当該ユーザーの代行だけを止める粒度が現行のエポックで表せるかを最初に確認し、表せなければ `## Design` に判断を追記する。
- アカウントポータルは既存の「接続済みアプリ」画面の隣に置き、別の情報体系を作らない。

## Risk Notes

リスクは medium。付与を必須にする変更は稼働中のエージェントを止めうるため、移行期間中の既定を `## Design` で明示する。緩和は移行期間で行い、判定そのものは常にフェイルクローズとする。

撤回の粒度を誤ると危険が両方向に出る。粗すぎればエージェント全体が止まって他ユーザーを巻き込み、細かすぎれば撤回したつもりの権限が別経路で残る。「当該ユーザーの代行だけが止まる」ことを検証項目として明示的に持つ。
