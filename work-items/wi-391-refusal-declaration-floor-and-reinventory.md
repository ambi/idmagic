# 拒否の宣言に床を設け、検出漏れしていた拒否を洗い直す

## Motivation

[[wi-390-security-control-test-standard-and-gate]] は「**宣言された**拒否にテストがあるか」を検査にした。**何を宣言すべきかは問うていない。** 拒否を 1 つも書かない Context は素通りする。

これは机上の懸念ではない。管理操作と、シナリオが宣言する拒否の数を突き合わせると、床が抜けている Context が実在する (2026-08-22 実測)。

| Context | 管理操作 | 変更操作 | 宣言された拒否 |
|---|---|---|---|
| signing-keys | 5 | 2 | 0 (`ALT` として) |
| workloadidentity | 13 | 10 | 1 |
| identity-governance | 11 | 7 | 1 |
| provisioning | 12 | 8 | 2 |
| sourcing | — | 8 | 1 |

署名鍵の回転と無効化は、身元管理製品でもっとも取り違えの高くつく操作である。それを誰が要求できないのかが、シナリオにほとんど書かれていない。実装は拒否しているはずだが、**書かれていない拒否は、実装が拒否をやめても何とも矛盾しない**。

もう 1 つ、洗い直しが要る。wi-390 の検出器は当初 `ALT` 行だけを見ており、`REQ-SIGNINGKEYS-009` (拒否がシナリオ自身の帰結) と `REQ-IDGOVERNANCE-012` (テナント境界が結果として言い換えられている) を丸ごと取りこぼしていた。wi-390 の中で直し、宣言は 78 件から 175 件、未検証は 58 件から 137 件になった。**増えた 79 件は新しい負債ではなく、それまで見えていなかった負債である。** 見えるようになっただけで、中身はまだ誰も確かめていない。

## Scope

- **床の検査 (R4)**。変更操作 (`@post` / `@put` / `@patch` / `@delete`) を持つ Context は、拒否を宣言するシナリオを 1 つ以上持つことを要求する。既存の欠落は縮むだけの許可リストに載せ、新しい Context は初日から要求する。
- **欠落している拒否の補完**。R4 が落とす Context について、実装が実際に行っている拒否をシナリオへ書き起こす。`signing-keys` を最初に扱う。
- **137 件の洗い直し**。許可リストの各項目を「テストは実在するが注記が無い」「テスト自体が無い」に分類する。前者は注記を付け、後者は work item として切り出す。分類の結果を記録し、許可リストを分類済みの分だけ縮める。
- **床の粒度の検討**。Context 単位の床は粗い。管理操作ごとに拒否の宣言を要求できるか (operation と `REQ` の対応を機械的に取れるか) を `## Design` で判断する。

## Out of Scope

- 拒否テストが副作用の不在を assert していない 84 件の修正。[[wi-392-refusal-tests-assert-the-absent-effect]] が持つ。
- R1 / R2 の拡張。ユースケース層への拡大は [[wi-393-guard-rules-reach-the-usecase-layer]] が持つ。
- フロントエンド。`spec/authorization.md` により強制はサーバー側にあり、UI が唯一の強制点になっている箇所は無い。
- 新しい防護の追加。既に実装されている拒否を書き起こすことに限る。実装が拒否していない箇所が見つかった場合は、本 work item では直さず欠陥として切り出す。

## Design

未定。着手時に次の 3 点を確定して `## Design` に記録する。

1. **床の粒度。** 案 A: Context 単位 (変更操作を持つなら拒否を 1 つ以上)。案 B: 管理操作単位 (各 operation について、それを拒否するシナリオが 1 つ以上)。案 B のほうが本来欲しい保証だが、operation と `REQ` の対応を機械的に取る手段が要る。`x-api-token-scopes` と `@route` から対応を導けるか、あるいはシナリオ側に operation 名を書かせるかを決める。案 B が高くつくなら案 A を床として入れ、案 B は別途。
2. **補完する拒否の出どころ。** 実装から書き起こすのか、`spec/authorization.md` のテナント境界と主体の規則から演繹するのか。前者は現状追認になりやすく、後者は書けるが実装と食い違いうる。両方を突き合わせ、食い違いを欠陥として扱う手順を決める。
3. **137 件の分類の進め方。** 全件を 1 つの work item で扱うと着手できない。Context ごとに切るのか、拒否の種類 (認可 / テナント境界 / スコープ / 入力検証) ごとに切るのかを決める。

## Plan

- R4 を先に入れ、落ちる Context を確定させてから補完に入る。どこが足りないかを検査に言わせる。
- `signing-keys` を最初の 1 件として通し、補完の手順と 1 件あたりの重さを測ってから残りの計画を立てる。
- 137 件の分類は、検査を書くより先にサンプルで手順を固める。分類の基準が定まらないうちに自動化すると、誤分類を固定する。

## Risk Notes

リスクは medium。**現状追認になる危険がもっとも大きい。** 実装を読んで拒否を書き起こすと、実装が拒否し忘れている箇所はそのまま「拒否しない仕様」として固定される。書き起こしは実装からだけでなく `spec/authorization.md` のテナント境界と主体の規則からも行い、両者の食い違いを欠陥として扱う。

床を Context 単位にすると、拒否を 1 つ書けば満たせてしまう。25 の管理操作を持つ Context が 1 つの拒否で通るのは明らかに不足だが、それでも 0 よりは強い。案 B が高くつく場合に案 A で妥協するなら、それが暫定であることを work item に残す。

137 件の分類は退屈で、機械化したくなる。分類の基準が定まらないうちに自動化すると誤分類を固定するので、サンプルで手順を固めてからにする。
