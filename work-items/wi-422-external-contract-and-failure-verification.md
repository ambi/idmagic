# 外部との契約と、縮退・移行の経路を実際に壊して確かめる

## Motivation

このリポジトリの検証は、自分の内側に対しては厚く、外側の境界に対しては薄い。

第一に、契約の検証が提供側に限られている。`mise run check-api-compat` はこの製品が提供する OpenAPI とリリース済みベースラインを比較するが、この製品が消費する契約には対応物が無い。Provisioning は SCIM 2.0 で下流の SaaS へ書き込み、Sourcing は上流の権威から取り込み、SharedSignals は SET を受信者へ送る。いずれも相手の実装が変われば壊れるが、その壊れ方を検出する仕組みが無い。Context Map が Sourcing と WorkloadIdentity に Anti-Corruption Layer を置いているのは、まさに外部の変化から内側を守るためであり、その ACL が実際に守れているかを確かめる手段が無いということでもある。

第二に、手書きのパーサに対する参照実装との突き合わせが無い。SCIM のフィルタ構文解析器は仕様が複雑で、`wi-248` が複合値のブラケット構文を扱っているように継続的に手が入る。この種の対象には、独立した参照実装と同じ入力を与えて出力を比較する差分テストが効く。

第三に、`docs/capacity.md` の縮退順序が検証されていない。「`bulk` レーンの新規取得を遅延させる」から「状態を部分的に更新せず 429 または 503 で拒否する」までの 5 段階と、「テナント境界、認証と認可の検証、再送防止、流量制限、監査イベントの完全性を弱めない」という不変条件が書かれているが、容量を超過したときに本当にこの順序で縮退するかを試したことは無い。`docs/development/specification-first-workflow.md` は fault injection を high 以上の変更に対する変更耐性の確認手段としてのみ位置づけており、設計された縮退が起きることを確かめる用途では使っていない。

第四に、無停止でのスキーマ移行の型が無い。`docs/database.md` は宣言的スキーマと `psqldef` による差分の収束確認まで定めているが、後方互換な追加、二重書き、読み替え、旧列の削除という段階を踏む手順が書かれていない。`docs/development/specification-first-workflow.md` は永続データの移行に独立検証を必須としているが、その検証が何を確かめるべきかの型が無いため、確認の中身が毎回の裁量になる。

## Scope

- **消費側の契約の検証**：SCIM の下流、上流の取り込み元、SSF の受信者について、こちらが前提としている相手の振る舞いを契約として書き出し、検証の形（記録した往復の再生、契約テスト、模擬サーバー）を決めて導入する。
- **差分テスト**：SCIM のフィルタ構文解析器を対象に、参照実装との出力比較を導入する。
- **縮退順序の検証**：容量超過を人為的に起こし、`docs/capacity.md` の 5 段階の順序と不変条件が実際に成り立つことを確かめる。
- **移行の型**：無停止でのスキーマ移行の段階を `docs/database.md` に書き、`docs/development/specification-first-workflow.md` が求める独立検証が何を確かめるかを定める。
- **fault injection の位置づけ**：設計された縮退と失敗経路を確かめる手段として、`docs/development/specification-first-workflow.md` の検証のはしごに位置づける。

## Out of Scope

- OAuth / OIDC / FAPI の適合性試験。`wi-33-protocol-conformance-ci` が既にこれを持つ。本 work item はその範囲に踏み込まず、消費側の契約と縮退・移行に集中する。
- 本番環境での障害注入。対象は開発環境とステージングに限る。
- 高可用性の設計そのもの。`docs/capacity.md` が「障害種別ごとの遷移、冗長化方式、過負荷保護の実装、運用手順は高可用性設計で定める」と述べており、そちらは別の work item が持つ。
- 既存のスキーマの移行のやり直し。

## Design

消費側の契約の検証には 3 案ある。相手の実装を模擬するサーバーを書く案、実際の往復を記録して再生する案、消費者駆動契約テストの枠組み（Pact など）を導入する案である。

採るのは 2 番目を主、1 番目を従とする組み合わせである。記録した往復を再生する形は、相手の実装が実在する場合に最も正直な契約になり、記録を更新することで相手の変化を検出できる。模擬サーバーは、相手が実在しない場合と、異常応答（部分的な失敗、遅延、不正な本文）を作るために使う。3 番目を採らないのは、消費者駆動契約テストが本領を発揮するのは提供側と消費側の双方を自分たちが持つ場合であり、下流の SaaS も上流の権威も相手側の協力を得られないためである。枠組みの費用に対して得られるものが記録と再生を超えない。

差分テストの参照実装は、SCIM のフィルタについて既存の実装を探す。無ければ、独立に書いた素朴な実装（性能を考えず仕様の文面どおりに書いたもの）を参照とする。同じ人が同じ理解で両方を書くと差分テストの意味が薄れるため、参照実装は仕様の文面だけを見て書き、既存の実装を参照しない。

縮退順序の検証は、負荷試験の資産（`load/k6/`）を土台にする。容量超過を作る方法は、実際に負荷を上げる案と、実行枠や接続数の上限を人為的に下げる案がある。採るのは後者である。参照運用プロファイルの規模で本当に飽和させるには大きな環境が要るが、上限を下げれば同じ縮退の経路を小さな環境で通せる。確認するのは順序そのものと、5 つの不変条件（テナント境界、認証と認可の検証、再送防止、流量制限、監査イベントの完全性）が縮退中も破れないことである。

移行の型は `docs/database.md` の既存の節構成に合わせて書く。同文書は既に「既存データのバックフィル、値の変換、削除前の退避など、構造差分で表現できない変更は work item の手順または専用 SQL に明記する」と述べており、その「手順」に型を与える形になる。

未解決の論点として、SSF の受信者に対する契約が現在どこまで実装されているかは調査していない。実装が薄ければ契約の検証も薄くてよい。実装着手前に確定させる。

## Plan

1. Provisioning、Sourcing、SharedSignals のそれぞれについて、外部に対して前提としている振る舞いを書き出す。ACL がどこでその前提を吸収しているかを確認する。
2. 記録と再生の仕組みを 1 つの対象（最も実装が厚いもの）に導入し、費用と得られる検出力を確かめてから残りへ広げる。
3. SCIM フィルタの参照実装を仕様の文面から書き、差分テストを導入する。
4. 実行枠と接続数の上限を下げた環境で縮退順序を通し、5 段階の順序と不変条件を確かめる。破れた不変条件があれば、是正を別の work item として切り出す。
5. 無停止移行の型を `docs/database.md` へ書き、独立検証の確認項目を `docs/development/specification-first-workflow.md` へ接続する。
6. fault injection を検証のはしごに位置づける。

## Verification

- 相手の応答を仕様に反する形へ変えると、記録と再生の検証が落ちる。
- SCIM フィルタの参照実装と既存実装の出力が、生成した入力の全てで一致する。一致しない入力が見つかった場合、どちらが正しいかを仕様の文面で決める。
- 縮退の各段階が `docs/capacity.md` の順序どおりに起き、その間に監査イベントが失われず、テナント境界を越えた共有が起きない。
- `mise run check-schema` が、移行の型に従った 2 段階の変更それぞれで収束する。
- `mise run verify`

## Risk Notes

外部との契約を記録と再生で固定すると、記録が古くなったときに「相手が変わった」のか「記録が古い」のかが区別できなくなる。記録には取得日時、相手の版、取得方法を必ず添える。`docs/capacity.md` の Measurement が同じ要求を既に持っており、その形式に揃える。

縮退順序の検証は、上限を下げた環境が本番の飽和と同じ経路を通るという前提に依存する。この前提自体は検証できないため、確かめられたのは「設計した縮退の論理が働くこと」であって「本番で同じ順序になること」ではない、と結果に明記する。

参照実装を書く作業は、実装を 2 つ持つことになる。参照実装は差分テストの中でのみ使い、製品の経路から呼ばないことを明確にする。
