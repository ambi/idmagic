# 拒否の許可リスト 131 件を消化し、`security-refusal-debt.json` を空にする

## Motivation

[[wi-390-security-control-test-standard-and-gate]] の R3 は「シナリオが宣言した拒否は、その id を名指しするテストが無ければならない」と要求する。検査を入れた時点で名指しの無かった 131 件は `tools/check/security-refusal-debt.json` の `untested` に据え置かれ、検査を素通りしている。

**このリストは縮む方向にしか動かないが、縮める力は誰も持っていない。** R3 はリストに載っていない id が拒否を宣言したら落ち、載っている id がテストを得たら「外せ」と落ち、拒否を宣言しなくなったら「削除しろ」と落ちる。増えることはない。しかし 131 件を 1 件ずつ確認する作業は [[wi-391-refusal-declaration-floor-and-reinventory]] の `Left Undone` に書かれたきり、どの work item も引き取っていない。このままなら R3 は**新しく書かれる拒否にしか効かない検査**であり続け、131 件は永久例外になる。

見落としやすいのは、`untested` が言っているのは「**id を名指しするテストが無い**」であって「**拒否が検証されていない**」ではないことである。件数だけでは危険度が分からない。`mise run report-refusal-debt` の実測 (2026-08-23) はこうなる。

| 分類 | 件数 | 意味 |
|---|---|---|
| named | 63 | 同じエラーを名指しして拒否を assert するテストがある。注記だけが欠けている見込み |
| nearby | 65 | 拒否を assert するテストはあるが、当のエラーは名指ししていない。1 件読んで判断が要る |
| none | 3 | そのパッケージに拒否を assert するテストが 1 つも無い |

`none` の 3 件はいずれも `REQ-SYSTEM-001` / `REQ-SYSTEM-002` / `REQ-SYSTEM-015` で、`backend/system` というディレクトリが無いために報告が候補を解決できていない (`package: backend/(unresolved)`)。本当に拒否のテストが無いのか、別のパッケージにあるのかは、まだ誰も見ていない。

wi-391 は `signing-keys` の 5 件だけを確認し、5 件とも「テストは実在し注記だけが無い」だったので許可リストは 137 から 131 に縮んだ。**標本 5 件で残り 131 件を推測することはできない。** 1 件でも「実装が拒否していない」が混じっていれば、それは wi-390 が塞いだ CSRF の素通りと同じ形の欠陥である。

## Scope

- `untested` の 131 件を 1 件ずつ確認し、次のいずれかに解決して許可リストから外す。
  - 当の拒否を検証しているテストが実在する → そのテストに `// REQ-<CONTEXT>-NNN: <何を固定しているか>` の注記を足す。
  - 当の拒否を検証しているテストが無い → [仕様先行の開発手順](../docs/development/specification-first-workflow.md) の「拒否のテスト」に従って書く。返ったステータスと、拒否が触らなかったものの双方を assert する。
  - シナリオが拒否を宣言しなくなっている → 許可リストから外す (R3 が落として教える)。
- `REQ-SYSTEM-*` の 3 件について、拒否を検証するテストがどのパッケージに属するべきかを決め、そこに置く。
- 実装が拒否していないことが分かった場合は、**本 work item では直さず欠陥として切り出す**。テストの追加と実装の修正を同じ変更に混ぜると、どちらが何を意味するのか後から読めない。
- 131 件が 0 になった時点で、`security-refusal-debt.json` と `checkRefusalCoverage` の `allowed` 引数を落とす。例外を持たない検査にする。

## Out of Scope

- 拒否テストが副作用の不在を assert していない 84 件の修正。[[wi-392-refusal-tests-assert-the-absent-effect]] が持つ。ただし本 work item が新しく書くテストは、その規範を満たす形で書く。既存テストに注記を足すだけの件で、そのテストが副作用の不在を見ていない場合は、注記を足したうえで wi-392 の対象として残す。
- 操作単位の宣言の最低要件 (wi-391 の案 B)。シナリオと TypeSpec の操作を結ぶ参照が要り、書式の変更を伴う。別の work item が持つ。
- R1 / R2 のユースケース層への拡大。[[wi-393-guard-rules-reach-the-usecase-layer]] が持つ。
- 見つかった実装の欠陥の修正。切り出した先で扱う。
- 新しい拒否の追加。既に宣言されている拒否にテストを対応付けることに限る。

## Design

未定。着手時に次の 3 点を確定して本節に記録する。

1. **進める単位 — 分類順かコンテキスト順か。** named 63 件を先に片付ければ許可リストは 68 件まで速く縮むが、named は機械判定であり「同じエラー型を名指しするテストが同じパッケージにある」以上のことは言っていない。読んだら別の拒否のテストだった、という取りこぼしがありうる。一方コンテキスト順なら、シナリオを読み直す文脈が 1 度で済み、`workloadidentity` のように named が 0 件のコンテキスト (実際に書く作業が多い側) を早く可視化できる。**最初の 1 コンテキストを通して named の見込みの的中率を測り、そこで決める。**
2. **注記の書き方の型。** 既存の形は `// REQ-SIGNINGKEYS-011: <このテストが何を固定しているか>` である (`backend/oauth2/handlers_http/admin_key_handler_test.go:191`)。**id を書くだけの注記は禁止する。** R3 は文字列の一致しか見ないので、名指しさえすれば検査は通る。何を固定しているかを書かせることが、注記が実在の検証に付いていることの唯一の担保になる。
3. **`REQ-SYSTEM-*` 3 件の置き場所。** `system` コンテキストに対応する Go パッケージが無い。3 件は運用資産の分離・プローブの意味・失効セッションからの復帰であり、拒否の主体がそれぞれ違う。1 件ずつ所有パッケージを決めるか、3 件とも別の性質のものとして扱うかを判断する。

分類ごとの件数はコンテキストによってかなり偏る。作業量の見当は次の通り (2026-08-23 実測)。

`workloadidentity` / `seeding` / `data-keys` / `sharedsignals` / `sourcing` / `claim-mapping` は named が 1 件も無い。**同じエラー型を名指しするテストがパッケージのどこにも無いということなので、注記で済まずテストを書く側に寄る見込みが高い。** 見積もりの軽い側 (named の多いコンテキスト) から進めると、残った作業の重さが最後に一気に見えることになる。この偏りをどう扱うかも 1 で決める。

## Plan

- 最初の 1 コンテキストを通し、1 件あたりの手数と named の見込みの的中率を測ってから、残りの進め方を確定する。
- 許可リストは 1 コンテキスト片付くごとに縮める。まとめて縮めない。R3 が「テストが付いたのにリストに残っている」と落とすので、縮め忘れは検査が教える。
- テストが書けない件 (実装が拒否していない) が出たら切り出して先へ進む。止まらない。
- 件数の推移を本 work item に記録する。減っていることが見えなければ、この作業は続かない。

## Verification

- `mise run report-refusal-debt`
  - reason: 着手前後の件数を比べ、131 件が 0 になることを完了の指標にする。
- `mise run check`
  - reason: R3 が許可リスト無しで通ることが最終状態である。
- `mise run test-go`
- `mise run verify`
- 手動: 注記を足しただけの件から 1 件選び、その拒否をやめる実装へ一時的に変えてテストが落ちることを確認する。落ちなければ、その注記は検証の付いていない名指しである。

## Risk Notes

リスクは low。既存のテストへの注記追加と、拒否のテストの追加であり、製品には触れない。

ただし**この作業には、許可リストを残すより悪くなる失敗の形がある**。131 件は「未検証が見えている」状態である。当の拒否を検証していないテストに id だけ書いて許可リストから外すと、「検証済みに見える」状態に変わる。R3 は文字列の一致しか見ないので、この誤りを二度と検出しない。件数の減少を指標にすると、まさにこの形骸化を招く。**機械分類 (named) をそのまま信じず、1 件ずつテストを読む。** Verification の手動確認を、件数より上の判断基準として扱う。

テストが書けない件が出た場合、それは製品の欠陥であって作業の失敗ではない。wi-391 は同じ性質の作業から `WriteAdminAccessError` の素通りを見つけている。切り出して先へ進む。

131 件という量そのものが、途中で止まる危険を持つ。コンテキスト単位で許可リストを縮めていけば、中断しても縮んだ分は残る。
