# 実装が返すのに宣言のないエラーとイベントを検出し、ドリフト検査が読めない操作を減らす

## 動機

実装にだけある外部の振る舞いを見つける検査が、片方向、または一部の操作にしか働いていない。

| 検査 | 現在の範囲 | 届いていないところ |
| --- | --- | --- |
| `check-unspecified-vocabulary` | TypeSpec が宣言したエラーコードとドメインイベントが、要件に現れるか | 実装が返すのに TypeSpec が宣言していないエラーコード、実装が発行するのに宣言していないイベント |
| `check-status-drift` | 342 操作のうち 94 操作を全体まで読む | 247 操作は一部だけ、1 操作は到達しない |
| `check-contract-drift` | 183 操作の本文を比べる | 159 操作は比べていない。内訳はレスポンスがリテラルでない 134、要求の型が見つからない 19、ハンドラーが見つからない 4、ほか 2 |

wi-12645、wi-30417、wi-17379 の宣言のないエラーコードは、どれも検査ではなく手作業で見つかった。

## 対象範囲

- 実装が返すエラーコードを集め、その操作の Context の TypeSpec の宣言と照合する検査。
- 実装が発行するドメインイベントを集め、宣言と照合する検査。同じ照合がすでにあれば、範囲を確かめて不足だけを足す。
- `check-status-drift` と `check-contract-drift` が読めない操作を減らす。読めない理由の多いものから、解析の対応を足す。
- 読めない操作の数を許容リストに記録し、減る方向にだけ変える。

## 対象外

- 見つけた食い違いの是正。
  検査の導入時点の違反は許容リストに記録し、是正は Context ごとの work item で行う。
- フロントエンドの検査。
- すべての操作を読めるようにすること。
  動的に組み立てる応答など、静的解析で追えないものは理由とともに残す。

## 設計

エラーコードは、ハンドラーと共有のエラー変換が問題の詳細へ書く `code` の文字列リテラルと、エラーの型からコードへの対応表から集める。
集めたコードを、そのハンドラーが属する Context の TypeSpec のエラーの union と比べる。
別の Context が宣言しているコードを返す場合（wi-12645 の `jobs_unavailable`）も、返す Context で宣言がないとして報告する。

読めない操作を減らす対象は、件数の多い「レスポンスがリテラルでない」から始める。
共有のレスポンス関数を通す書き方が多いなら、その関数を解析の対象に加える方が、ハンドラーを書き換えるより安い。

許容リストは `tools/check/unspecified-vocabulary-debt.json` と同じ形にし、違反でなくなった項目が残れば失敗させる。

### 採用しない案

| 案 | 採らない理由 |
| --- | --- |
| 実行時に返したコードを記録して照合する | テストが通る経路のコードしか集まらない。静的に集める方が、テストのない分岐も拾える |
| 読めない操作を数えずに放置する | 読めない操作が増えても検査が通り、検査の範囲が気付かれずに狭まる |

## 計画

1. エラーコードの収集と照合を実装し、現在の違反を許容リストに記録する。
2. イベントの照合の現状を確かめ、不足を足す。
3. 読めない操作の数の許容リストを加える。
4. 読めない理由の多いものから解析を広げ、許容リストを減らす。
