# 同一オリジンの前提が崩れた配備を、製品自身が検出して拒否する

## Motivation

`docs/deployment.md` は「同一オリジンであることは利便のためではなく、Cookie のスコープと `Origin` の検証がこの前提の上に成り立っているためである」と述べる。つまり CSRF 対策とセッション Cookie の到達範囲は、どちらもゲートウェイが同一オリジンの境界を保っていることに依存している。

ところが、この前提が満たされているかを製品自身は確かめていない。ゲートウェイの設定を誤り、UI と API が別オリジンで配信された場合、`Origin` 検証は設定済みの公開発行者と一致しなくなり、正規の操作が落ちるか、あるいは緩和の設定を入れて塞いだつもりの経路が開く。前提が崩れたことは、配備した人にも運用者にも見えない。

`REQ-SYSTEM-016` は起動時設定の検証に失敗したときプロセスが部分起動しないことを保証しており、検証の受け皿は既にある。足りないのは、同一オリジンの前提を起動時に検証できる形へ落とすことである。

これは [docs/threat-model.md](../docs/threat-model.md) の THREAT-012 が指す欠落である。

## Scope

- 公開発行者、UI の配信元、Cookie の属性の関係から、同一オリジンの前提が満たされているかを起動時に判定する。
- 判定できない構成と、明らかに前提が崩れている構成を区別する。前者は起動を止めず記録する。
- 前提が崩れている構成での起動を拒否するか、明示的な許可設定を要求するかを決める。
- 判定の結果を `/readyz` の詳細と起動時のログへ出す。
- 対応する規範シナリオを `docs/contexts/system/scenarios.md` へ足す。

## Out of Scope

- ゲートウェイの設定そのものの提供。参照設定は `infra` にあり、必須のランタイムではないという判断は変えない。
- 実行時のリクエストごとの検査。`Origin` 検証は既に存在する。
- TLS 終端位置の検証。THREAT-011 は受容済みである。

## Design

判定の入力は起動時設定に限る。実行時に観測した `Host` や `Origin` から推定すると、最初の不正なリクエストが来るまで判定できず、しかもその推定自体が攻撃者の制御下にある入力に依存する。

前提が崩れていると判定したときの扱いには 2 案がある。起動を拒否する案と、明示的な許可設定を要求する案である。前者は安全側だが、判定の誤りが配備を止める。後者は運用者が前提の崩れを認識したうえで進めることを求める。どちらを採るかは、判定が偽陽性を出しうるかによって決まるので、実装着手前に判定条件を固めてから選ぶ。

## Plan

1. 同一オリジンの前提に依存している制御を列挙する。CSRF の二重送信、`Origin` 検証、Cookie の属性、CSP の `form-action` が対象になる。
2. それらが成立する構成の条件を、起動時設定の値だけで表せる形に落とす。
3. 判定と、判定不能の区別を実装する。
4. 規範シナリオを足し、拒否のテストを状態と効果の両方で書く。

## Verification

- 前提が崩れた設定で、決めた扱い（起動拒否または明示的な許可の要求）が働く。
- 前提が満たされた設定で、起動が妨げられない。
- `mise run verify`

## Risk Notes

判定が厳しすぎると、正当だが想定していない配備形態を止める。参照設定以外のゲートウェイを許すという既存の判断と衝突しないよう、判定条件は「同一オリジンでないことが確実な場合」に限る。

判定が緩すぎると、前提の崩れを検出できないまま安心感だけを与える。どちらの誤りも起こりうるので、判定不能を第三の結果として持ち、成立と混同しない。
