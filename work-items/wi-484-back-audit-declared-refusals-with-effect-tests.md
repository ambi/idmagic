# Audit が宣言する未検証の拒否 2 件に効果まで確かめるテストを与え、台帳から外す

## Motivation

`tools/check/scenario-coverage-debt.json` は、どのテストからも id を引用されていない規範 id を保持する、縮むだけの台帳である。

このうち 102 件は [[wi-390-security-control-test-standard-and-gate]] が拒否専用の台帳へ据え置いた分で、[[wi-490-fold-refusal-coverage-into-one-normative-coverage-rule]] が網羅台帳へ統合した。

その 102 件のうち 2 件が Audit の拒否である。

この Context の拒否は、他と違って**読み出しの拒否**である。

書き込みを止める防護ではないため、素通りしても状態は変わらない。

代わりに漏れるのは監査ログそのもの、すなわち誰がいつ何をしたかの記録である。

`REQ-AUDIT-003` は検索結果に属性値やメール本文が含まれないことを宣言しており、これは監査イベントに載せてよい情報の下限を定めている。

`REQ-AUDIT-004` は非管理者の一覧取得の拒否に加えて、別テナントで発行された、あるいは改ざんされたカーソルの拒否を宣言している。

カーソルは署名付きの状態を持ち歩く仕組みなので、検証が素通りすれば他テナントのページをそのまま読める。

読み出しの拒否は「変わっていないこと」ではなく「返っていないこと」で確かめる。

`mise run report-coverage-debt` の分類では 1 件が named、1 件が nearby だが、named は「同じエラー型名を含む拒否テストが同じパッケージへ到達する」ことしか示さない。

そして注記だけを足す解消は、この項目では認めない。

## Scope

- 台帳の Audit の 2 件それぞれについて、宣言された拒否に production と同じ入口から到達するテストを用意する。
- 各テストで 2 つを assert する。呼び出し元が観測する応答 (ステータスとエラー種別) と、拒否された情報が応答に現れないこと。
- カーソルの拒否は、別テナントで発行したカーソルと改ざんしたカーソルの両方で確かめる。
- 各テストのソースに対応する `REQ-AUDIT-NNN` を書く。
- 対応が取れた id を `tools/check/scenario-coverage-debt.json` から削除する。
- 拒否を実装が持っていないと判明した場合、その防護をこの項目で実装する。
- 完了時点で、この項目が持つ id が台帳から 1 件残らず消えていることを確認する。

## Out of Scope

- 他 Context の拒否。
  Context ごとに別の work item が持つ。
- 102 件を 1 つの単位として消化すること。
  [[wi-399-burn-down-untested-refusal-debt]] がその形で立てられているが、進める単位を未決のまま残し、注記だけの解消も認めている。本項目はその置き換えである。
- 同じ台帳に載る、この項目が持たない id。
  規則は同じだが、引き取る範囲はここに挙げた id に限る。
- R1、R2、R4 の検査そのものの変更。
  [[wi-390-security-control-test-standard-and-gate]] と [[wi-391-refusal-declaration-floor-and-reinventory]] が持つ。
- 既存テストへ `REQ` id を注記するだけで台帳から外すこと。
  この項目ではこれを解消として扱わない。
- 監査イベントの同期エクスポートの有界化。
  [[wi-464-bound-the-synchronous-audit-event-export]] が扱う。
- 監査ログの保持期間、改ざん検知、外部配信の設計。
  [[wi-287-tamper-evident-audit-log-integrity]] と [[wi-286-outbound-event-hooks-and-audit-log-streaming]] が扱う。

## Design

### 解消の条件

1 件の id を台帳から外してよいのは、次の 3 つがすべて成り立つときだけとする。

第 1 に、テストが production の使う入口から入り、宣言された拒否の判断を実際に通ること。

第 2 に、拒否された情報が応答のどこにも現れないことをテスト自身が確かめること。

読み出しの拒否では、これが「副作用の不在」に相当する。

第 3 に、シナリオの id をテストのソースが引用していること。

### 拒否ごとに何を読むか

| REQ | 宣言している拒否 | 応答を読んで確かめる対象 |
|---|---|---|
| REQ-AUDIT-003 | `run_id` に紐づかないイベントを返さず、属性値とメール本文を含めない | 応答に他の `run_id` のイベントが無く、属性値とメール本文の文字列がどこにも現れない |
| REQ-AUDIT-004 | 非管理者の一覧取得、条件変更後の旧カーソル、別テナント発行・改ざん・期限超過のカーソルを拒否 | 応答に監査イベントが 1 件も含まれず、別テナントのイベントも返らない |

`REQ-AUDIT-003` の「属性値とメール本文が現れない」は、応答全体を文字列として走査して確かめる。

フィールドを 1 つずつ確かめる形では、実装がフィールドを増やしたときに漏れる。

監査イベントは追記のみで長期保持されるため、一度載った情報は後から取り除けない。

`REQ-AUDIT-004` のカーソルは、別テナントで実際に発行したものを使う。

手で組み立てた文字列は署名を持たないため、署名検証だけで落ち、テナントの照合が無くても成立してしまう。

### 却下した進め方

**カーソルの検証関数の単体テストで閉じる案。**

検証が正しくても一覧の経路から呼ばれていなければ素通りする。

**改ざんカーソルだけで確かめる案。**

上に述べたとおり、テナントの照合の欠落を検出できない。

正規に発行された他テナントのカーソルを使う。

**属性値の非公開を、イベントの構造体の定義で確かめる案。**

構造体にフィールドが無いことは、応答に現れないことの証明にならない。

追加のフィールドや自由記述の欄を通って漏れうる。

## Plan

1. 2 件のシナリオを読み、拒否ごとに入口と応答の読み方を確定する。
2. 別テナントで正規に発行したカーソルを得る固定具を用意する。
3. 一覧の拒否 (004) から着手し、テストが RED になることを先に観測する。
4. 検索結果の内容の拒否 (003) を、応答全体の走査で進める。
5. 拒否の実装が欠けていた場合は修正する。
6. 対応の取れた id を台帳から削除し、この項目が持つ id が 1 件も残っていないことを確認する。

## Risk Notes

読み出しの拒否は状態を変えないため、「副作用の不在」を素直に読めない。

代わりに応答の内容で確かめることになり、応答の形が変わるとテストが壊れやすい。

走査は値の存在で行い、フィールド名の並びには依存させない。

台帳は id 順に 1 エントリー 1 id なので、Context ごとの work item が並行しても衝突はエントリー単位に収まる。

各項目は自分が持つ id のエントリーだけを削除し、コメント配列と他の id には触れない。
