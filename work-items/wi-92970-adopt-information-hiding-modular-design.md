# 境界の判断を、観測できる事実と検査される宣言に基づくモジュール設計へ置き換える

## 動機

エージェントに設計と実装を任せるには、同じ入力から同じ判断が出る規則が要る。
規則が観測できない意図に依存すると、エージェントはその都度もっともらしい解釈を作り、変更ごとに判断が揺れる。
DDD の Bounded Context、Context Map の関係分類、Subdomain の区分は、モデルの境界や関係の性格という、コードからも文書からも一意に決まらない判断を入力にしている。

現在のリポジトリでは、DDD の語彙が付いた宣言の多くが、検査の結果にも作業の選択にも効いていない。

| 観測した事実 | 帰結 |
| --- | --- |
| Context Map の関係ラベル（OHS/PL、C/S、ACL）を `boundary-fitness.ts` は解析するが、判定には使わない。判定に効くのは辺の有無だけである | Context Map の実体は、DDD の名前を付けた import の許可リストである |
| `undeclared-context-edge` は Context Map に辺を書き足せば消える。テナントの公開言語の項目は、計画の最初の段階でこの書き足しを行う | 許可リストは依存を選り分けておらず、「その関係は正当か」という判断を人とエージェントに残している |
| 負債台帳 `tools/check/boundary-debt.json` は 180 項目、510 個の違反 ID を持ち、理由はすべて自動生成の定型文である | 台帳から、次に何をどう直すかを読み取れない |
| `context-cycle` の 66 項目は Context 単位に集計した循環である。パッケージの循環は Go のコンパイラがすでに禁じている | 数は Context のまとめ方で変わり、具体的な変更の波及を示さない |
| Subdomain の区分について、設計ガイドラインは「区分そのものが妥当かどうかは検査できない」と書く。区分が左右するとする三点（自作と委譲、文書の厚み、翻訳する側）は、どれも区分を使わずに規則にできる | 検査も作業の分岐も生まない分類を、全 Context に付けている |
| データベース設計のテーブル一覧には「所有 Context」の列があるが、`schema-tables.ts` は判断を書いた列として照合しない | 宣言はあるが、ほかのモジュールからの書き込みを止めない |
| 「Context」は Go の `context.Context` と同じ語である。`backend/tenancy/context.go` は解決済みのテナントを `context.Context` に載せる | 文書とコードで同じ語が別の概念を指す |

Modular Monolith、Clean Architecture、Vertical Slice Architecture は維持する。
この項目は、その内部でモジュールの範囲、公開範囲、依存、データの所有を決める方法を、エージェントが機械的に再現できる形へ置き換える。
原則は Parnas の情報隠蔽（変わりうる設計判断を一つのモジュールへ隠す）に置き、原則の適用を観測できる事実と検査で支える。

## 対象範囲

- 設計の判断を、コードから導く事実、検査される宣言、決定表で行う判断の三つに分ける方針を、担当する一次情報文書へ反映する。
- 設計文書の Bounded Context と Context を「モジュール」へ改名する。この項目で改名するのは、概念を定義する文書と、この項目で変更する検査の識別子と出力文言である。
- モジュール間の依存の規則を、公開パッケージへの依存だけを許す規則、モジュール単位の非循環、`shared` からモジュールへの依存の禁止に置き換え、Context Map の許可辺と関係ラベルを廃止する。
- 公開範囲の最終形を Go の `internal/` とし、移行中のモジュールで現在の規則を併用する検査と、移行の手順を定める。
- テーブルの所有者の宣言を検査に使い、ほかのモジュールの sqlc クエリによる書き込みを拒否する。
- Subdomain の区分、区分の列、その検査を撤去し、区分が左右していた三点を区分に依存しない規則へ書き換える。
- 境界の判断の証拠として、Git の履歴から一緒に変わるモジュールの組を数えるレポートを追加する。
- 負債台帳を新しい違反の種類へ移し、旧項目との対応を記録する。
- 改名の残り、`internal/` への移行、既存の境界解消の項目の見直しを、後続項目として起票または調整する。

## 対象外

- HTTP 契約、認証方式、状態遷移、整合性、失効、監査、通知などの製品の保証の変更。
- 本番パッケージの `internal/` への移動と、モジュールの分割、統合。
- 仕様のディレクトリ名（`docs/domain/<名前>/`、`spec/contexts/<名前>/`）、規範 ID の接頭辞（`REQ-<名前>-NNN`）、TypeSpec の名前空間の変更。規範 ID と公開済みの名前は取り消せない識別子なので、改名の対象にしない。
- 概念を定義する文書以外での改名。後続の改名項目が、用語の検査の規則とともに行う。
- ほかのモジュールが所有するテーブルの読み取りの検査。後述の理由で、この項目では判断として扱う。
- 共変更レポートを合否の判定に使うこと。
- マイクロサービス化、プロセス構成、DB スキーマの変更。

## 設計

### 判断の三分類

設計の判断を、入力の種類で三つに分ける。

| 分類 | 定義 | 例 | 誤ったときに何が起きるか |
| --- | --- | --- | --- |
| コードから導く事実 | ソースと Git から機械的に決まる値。手で書かない | import の辺、パッケージのパス、sqlc クエリが書き込むテーブル、`domain` が呼ぶ作用の関数、一緒に変更されたファイル | 抽出の誤りとして検査のテストが検出する |
| 検査される宣言 | 人が書き、検査が判定に使う局所的な値。判定に使わない欄は置かない | モジュールの責務表の Go パッケージ列、組み立て地点の一覧、テーブルの所有モジュール、`internal/` の配置 | 宣言と事実の食い違いを検査が拒否する |
| 決定表による判断 | 事実と宣言を入力に、決定表の行を選んで行う判断 | 新しい処理の置き場所、公開操作を足すか、依存を逆転するか、モジュールを分けるか | 選んだ行と入力の事実を work item に記録し、レビューが確かめる |

宣言の欄を足すときは、その欄が変える検査の結果を同時に定める。
判定に使わない分類やラベルは、文書の飾りとして残すと、エージェントがそれを判断の根拠と誤読するからである。

### モジュールの定義

**モジュール**は、`backend/` の直下にあるディレクトリのうち `cmd` と `shared` を除いたものとその配下、およびそれに対応する仕様の文書と TypeSpec を一つの単位として呼ぶ名前である。
モジュールの名前（`IdManagement` など）、Go パッケージ、仕様のディレクトリの対応は、論理アーキテクチャの責務表が一次情報である。
機能ごとの垂直分割（`backend/<モジュール>/<機能>/`）はモジュールの内部構造であり、別のモジュールではない。

パッケージは、次の三種類のどれかに属する。

| 種類 | 範囲 | 依存の扱い |
| --- | --- | --- |
| モジュール | 上の定義どおり | 後述の三規則に従う |
| 組み立て地点 | 責務表の System 行が列挙するパッケージ。`backend/cmd/**`、`backend/shared/http/server_http`、`backend/shared/http/testing_stack` | 全モジュールを結線するため、モジュールの公開範囲と非循環の規則の対象外とする |
| 共有ライブラリ | `backend/shared/**` のうち組み立て地点を除いたもの | どのモジュールにも依存しない |

`testing_stack` を組み立て地点に含めるのは、テスト用の HTTP スタック全体を `_test.go` ではないファイルで組み立てており、実態が `server_http` と同じ結線だからである。

### モジュール間の依存の規則

Context Map の許可辺と関係ラベルを廃止し、次の規則に置き換える。

| 規則 | 違反の種類 | 防ぐ故障 |
| --- | --- | --- |
| モジュールは、ほかのモジュールの公開パッケージだけを import する | `private-import` | 利用側が提供側の実装の詳細に依存し、提供側の内部の変更が利用側を壊す |
| モジュール単位の依存は循環しない | `module-cycle` | 二つのモジュールが互いの変更に追従し続け、どちらも単独で変更、検証できない |
| 共有ライブラリはモジュールに依存しない | `shared-dependency` | 共有ライブラリを経由して、モジュールが依存を宣言せずに別のモジュールへ到達する |
| `domain` は時刻、乱数、OS、ネットワーク、データベースを直接使わない | `domain-effect` | 計算の結果をテストで固定できない（DDD 由来の規則ではないので変更しない） |
| モジュールの sqlc クエリは、ほかのモジュールが所有するテーブルへ書き込まない | `table-write` | 二つのモジュールが同じテーブルの不変条件を別々に保とうとし、片方の変更がもう片方の保証を破る |

辺の許可リストを置かないのは、公開パッケージを経由した非循環の依存は、提供側が公開した契約を使うだけであり、それ以上の判断を検査に持たせる根拠がないからである。
新しい依存の向きが設計として妥当かは、決定表と共変更レポートで判断する。

`shared-dependency` は、従来の `shared-detour`（モジュールから `shared` を経由して別のモジュールへ到達する経路）を、原因である `shared` 側の import として一度だけ数える。
従来の方式は同じ import を到達元のモジュールの数だけ数え、違反の数が原因の数を表さなかった。

`table-write` は、モジュールの `db_postgres` 配下の sqlc クエリが `INSERT`、`UPDATE`、`DELETE`、`MERGE`、`TRUNCATE` の対象にするテーブルを抽出し、データベース設計のテーブル一覧の所有モジュールと照合する。
所有が「共通基盤」のテーブルは、共有ライブラリだけが書き込める。
`//sql:raw` の動的な SQL は静的に抽出できないため対象外とし、その限界を検査の説明に書く。
読み取りを検査しないのは、現在の削除や認可の照合にほかのモジュールのテーブルを読む結合が含まれ、どれを公開操作へ置き換えるかが個別の判断になるからである。

### 公開範囲と `internal/`

公開範囲の最終形は Go の `internal/` とする。
コンパイラが違反を即時に拒否するので、検査を実行しなくてもエージェントが誤りに気付ける。

モジュールの最終形は次のとおりとする。

- `backend/<モジュール>/`：`module.go` を置くルートパッケージ。モジュールの組み立てと HTTP ルートの登録を公開し、組み立て地点はここだけを import する。
- 公開パッケージ：ほかのモジュールが使う型と操作、ほかのモジュールが実装するポート。`internal/` の外に置く。
- `backend/<モジュール>/internal/`：それ以外のすべて（ユースケース、アダプター、内部の型）。

組み立て地点も `internal/` を import できないため、現在 `server_http` が各モジュールの `handlers_http` を直接 import している結線は、ルートパッケージの公開操作を経由する形へ移す。
`internal/` はモジュールの配下全体から見えるので、機能スライスどうしの分離は保証しない。
機能スライス間の規則は、この項目では追加しない。

移行中は、`backend/<モジュール>/internal/` を持つモジュールを移行済みとして扱う。

| 対象 | 公開パッケージの判定 |
| --- | --- |
| 移行済みのモジュール | `internal/` の外にあるパッケージ。違反はコンパイラが拒否するので、検査は `private-import` を数えない |
| 未移行のモジュール | 現在の規則どおり、パスに `domain` または `ports` の区画を含むパッケージ |

すべてのモジュールが移行した時点で、`private-import` の判定を検査から削除する。

### 決定表

境界に関わる変更では、次の表から入力の事実に合う行を選ぶ。
選んだ行と入力の事実は work item の設計の節に書く。

| 入力の事実 | 行う変更 |
| --- | --- |
| 追加する振る舞いが `REQ-<名前>-NNN` に属する | 責務表でその仕様に対応するモジュールへ置く |
| ほかのモジュールの非公開の型または関数が必要である | 提供側のモジュールに公開操作を追加する。利用側へ内部の処理を複製しない |
| import するとモジュールの循環ができる | 利用される側のモジュールがポートを公開し、もう一方がそれを実装し、組み立て地点で結ぶ。IdManagement の `UserMutationCommitter` と同じ形にする |
| 二つ以上のモジュールが使い、どのモジュールの型も含まない技術的な機構である | 共有ライブラリへ置く |
| 特定のモジュールの型を含む機構である | そのモジュールへ置く。共有ライブラリへ置かない |
| テーブルへ書き込む | そのテーブルを所有するモジュールの `db_postgres` で書き込む。ほかのモジュールは所有モジュールの公開操作を呼ぶ |
| ほかのモジュールの型を自分のポートの型へ変換する | その公開パッケージを import する側のモジュールにアダプターを置く |
| 複数のモジュールの状態を一つのトランザクションで更新する | 片方だけが残った状態を外部が観測できてはならない場合に限る。編成するモジュールと理由を、そのモジュールの設計判断に書く |
| 新しいモジュールを作る、またはモジュールを分割、統合する | 共変更レポートの数値と、各モジュールが所有するテーブルと公開操作の変化を work item に書き、レビューで判断する |

### 共変更レポート

`mise run report-change-coupling` は、Git の履歴から、同じコミットで変更されたモジュールの組と回数を出力する。
既定の範囲は直近 500 コミットとし、範囲は引数で変えられる。
六つ以上のモジュールを同時に変更したコミットは、一括の改名や整形である可能性が高いので数えない。
出力は、組ごとの共変更の回数と、少ない側のモジュールの変更回数に対する割合とする。

このレポートは合否を判定しない。
決定表の最終行で、一緒に変わるものを一つのモジュールへ集める根拠、または独立して変わるものを分ける根拠として、数値を work item に引用する。
`mise run verify` には含めない。

### DDD 由来の規則の採否

| 現在の規則 | 判断 | 置き換え先と理由 |
| --- | --- | --- |
| Context Map の許可辺から import の可否を導く | 廃止 | 公開パッケージ、非循環、`shared` の三規則。辺を足せば違反が消え、選り分けていない |
| 関係ラベル（OHS/PL、C/S、ACL）と Supplier、Customer の用語 | 廃止 | 判定に使われていない |
| Subdomain の区分（`Core`、`Supporting`、`Generic`）と区分の検査 | 廃止 | 下の三行へ分解する |
| `Generic` では確立した実装へ委ねる | 全モジュールへ一般化 | 暗号、署名、プロトコルの解析など、確立した実装がある処理は自作しない。区分によらず成り立つ |
| `Core` では `decisions.md` と `internals.md` を厚くする | 既存の規則へ統合 | コードから復元できない機構があるときに `internals.md` を書くという既存の規則で決まる |
| `Core` と非 `Core` のどちらが翻訳するか | 依存の向きから決める | 決定表のとおり、公開パッケージを import する側が翻訳する |
| ACL の置き場所は Context Map が依存を許す側 | 依存の向きから決める | 同上 |
| 公開言語は `domain` と `ports` | 移行期間だけ維持 | 最終形は `internal/` の外 |
| `shared` を経由した到達も Context Map の規則で判定する | 置き換え | `shared-dependency` |
| 1 回のトランザクションが変更する Aggregate は 1 つ | 置き換え | 片方だけ残った状態を外部が観測できてはならない場合に限り、複数の状態を一つのトランザクションで更新する。現在の例外の判定基準を主規則にする |
| Aggregate の語と、Repository を Aggregate root 単位に置く規則 | 維持 | データベース設計の `tenant_id` の保持区分がこの語に依存し、Repository の規則は `Save` が受け取る型という観測できる基準を持つ |
| `domain` の作用の禁止 | 維持 | DDD 由来ではない |
| イベントのエンベロープと公開項目の語彙 | 維持し、用語だけ改名する | `check-event-contract` が検査している |
| 境界の引き直しで Event Storming を参照する | 置き換え | 決定表の最終行と共変更レポート |

旧分類の違反は、次のように新しい種類へ移す。
違反 ID が消えることと設計上の問題が解消したことは区別し、移行の前後の種類ごとの件数を完了の節に記録する。

| 旧分類 | 新しい扱い |
| --- | --- |
| `private-import` | 未移行のモジュールでは同じ判定で残る |
| `undeclared-context-edge` | 違反ではなくなる。同じ import が非公開パッケージへ向かうなら `private-import` として、循環を作るなら `module-cycle` として残る |
| `context-cycle` | `module-cycle` へ改名する。集計の単位は変わらない |
| `shared-detour` | `shared-dependency` として、原因の `shared` パッケージとモジュールの組ごとに数え直す |
| `domain-effect` | 変更しない |
| なし | `table-write` を新しく台帳へ載せる |

### 用語の改名

| 現在の語 | 改名後 |
| --- | --- |
| Bounded Context、Context | モジュール |
| Context Map | 廃止 |
| 公開言語、Published Language | 公開パッケージ |
| Context 間イベント | モジュール間イベント |
| 所有 Context | 所有モジュール |
| Subdomain、サブドメイン（区分の意味） | 廃止 |

DNS のサブドメインなど、区分ではない意味の「サブドメイン」は改名しない。
Go の `context.Context` とテナントを運ぶ `context.go` は Go の語なので変えない。

この項目で改名するのは、次の節に挙げる一次情報文書と、この項目で変更する検査の識別子と出力文言である。
残りの文書（約 180 ファイル、約 760 箇所）は後続の改名項目が扱い、完了時に用語の検査へ「Bounded Context」「Context Map」「Context 間」などの規則を追加する。
分けるのは、方針の変更と機械的な置換を同じ差分に混ぜると、方針の変更をレビューで読み分けられなくなるからである。

コードから導ける辺や一覧（モジュールの依存グラフなど）は、文書へ手で書かない。

### 検査の変更

- `boundary-fitness.ts` は、責務表からモジュールと組み立て地点を読み、Mermaid の Context Map を読まない。
  違反の種類を `private-import`、`module-cycle`、`shared-dependency`、`domain-effect`、`table-write` とし、`internal/` の有無で移行済みかを判定する。
- `table-write` は、データベース設計のテーブル一覧の所有モジュールと、`db_postgres` 配下の `.sql` の書き込み文を照合する。
  所有モジュールの列が責務表にない名前を含めば拒否する。
- `subdomain-classification.ts` とそのテスト、`check-documents.ts` からの呼び出しを削除する。
- `report-change-coupling` を `mise.toml` に追加する。
  Git の読み取りは作用の境界に置き、コミットごとの変更ファイルの一覧から組と回数を数える計算は純粋関数としてテストする。
- 負債台帳を新しい種類で作り直す。
  理由の書き直しは既存の棚卸しの項目が行うので、この項目では台帳の形式と違反 ID だけを移す。

### 代替案

| 案 | 判断 |
| --- | --- |
| DDD の用語を残し、情報隠蔽の方針を補助として重ねる | 採用しない。判定に効かない分類が残り、エージェントが根拠と誤読する |
| 改名せず、Context の定義だけを機械的なものに置き換える | 採用しない。Go の `context.Context` との衝突と、DDD の Bounded Context としての読みが残る |
| Context Map の許可辺を残し、関係ラベルだけ外す | 採用しない。辺を足せば違反が消える構造が残る |
| モジュールに層番号を宣言し、下位への依存だけを許す | 採用しない。非循環より強いが、層の割り当てという新しい判断が増える |
| 公開範囲を `domain` と `ports` の命名規則のまま維持する | 採用しない。公開するかを層の名前で決めることになり、コンパイラの拒否も得られない |
| パッケージごとに公開を宣言するディレクティブを置く | 採用しない。Go の `internal/` と同じことを独自の仕組みで行う |
| 依存の許可を YAML の台帳として別に持つ | 採用しない。以前の全量の依存台帳の撤去と同じ理由で、正本と台帳が独立に古くなる |
| 一括で全文書を改名し、全実装を `internal/` へ移す | 採用しない。方針の変更と機械的な置換、パッケージの移動を一つの差分に混ぜ、レビューで読み分けられない |
| 検査を廃止してレビューだけに委ねる | 採用しない。公開範囲、循環、書き込みの所有は機械で判定できる |

- [Kent Beck の結合と凝集の説明](https://newsletter.kentbeck.com/p/tldr-coupling-and-later-cohesion)。結合を具体的な変更の波及で定義する考え方を、共変更レポートの根拠として参照する。
- [Ousterhout の深いモジュールの説明](https://github.com/johnousterhout/aposd-vs-clean-code#method-length)。利用側が学ぶインターフェースの量で評価する既存の設計ガイドラインの根拠として参照する。
- [Go 1.4 の internal パッケージ](https://go.dev/doc/go1.4#internalpackages)。公開範囲をコンパイラに判定させる仕組みとして参照する。

## 計画

1. 現在の `mise run check-boundaries` の結果から種類ごとの件数を記録し、`db_postgres` の書き込み文とテーブルの所有モジュールを照合して `table-write` の候補を数える。
2. 一次情報文書を先に更新する。
3. 各規則と移行規則の fixture を先に用意し、現在の検査がそれを通してしまうことを観測してから検査を変更する。
4. Subdomain の検査を削除し、負債台帳を作り直して旧分類との対応を記録する。
5. 共変更レポートを追加し、現在のリポジトリで一度実行して出力を確かめる。
6. 後続項目を起票し、既存の項目を調整する。
   - 残りの文書の改名と、用語の検査の規則の追加。
   - モジュールごとの `internal/` への移行。最初の項目は、依存の少ないモジュールを一つ選んで移行の手順を確かめる。
   - [テナントの公開言語](wi-39119-publish-the-resolved-tenant-as-tenancy-public-language.md)は、Context Map への辺の追記が不要になるので、公開パッケージへの移動だけに範囲を狭める。
   - [残った境界負債の棚卸し](wi-33994-reinventory-the-remaining-boundary-debt.md)は、選択肢から「Context Map に書き足す」を除き、新しい違反の種類で棚卸しする。
   - この二つの項目は、旧規則に合わせた修正が先に進まないよう、起票の時点で `depends_on` に本項目を加えてある。
   - [ドメインの作用の注入](wi-65906-inject-time-randomness-and-network-into-domain.md)は `domain-effect` を変えないので、調整しない。

## 検証

検査の変更は `mise run test-tools-file -- <テストファイル>` で確かめる。
次の各例で、受理と拒否が規則どおりであることを fixture で固定する。

| 例 | 期待する結果 |
| --- | --- |
| 未移行のモジュールが、ほかのモジュールの `ports` を import する | 受理 |
| 未移行のモジュールが、ほかのモジュールの `usecases` を import する | `private-import` |
| 移行済みのモジュールの `internal/` の外のパッケージを import する | 受理し、`private-import` を数えない |
| 二つのモジュールが互いの公開パッケージを import する | `module-cycle` |
| 組み立て地点がモジュールの非公開パッケージを import する | 受理 |
| 共有ライブラリがモジュールを import する | `shared-dependency`。到達元のモジュールの数にかかわらず一件 |
| モジュールの sqlc クエリが、ほかのモジュールが所有するテーブルへ `UPDATE` する | `table-write` |
| 同じクエリが、そのテーブルを `SELECT` するだけである | 受理 |
| テーブル一覧の所有モジュールが責務表にない名前である | 拒否 |

変更耐性は `mise run test-go-mutation` の対象外なので、公開判定、循環判定、書き込み文の抽出のそれぞれに手で誤りを注入し、上のテストが検出することを確かめる。

文書と検査の変更後は、`mise run check-boundaries`、`mise run check-boundary-debt-ratchet`、`mise run check-terminology`、`mise run check-links`、`mise run check-work-items`、`mise run check-agent-guidance`、`mise run check-schema-tables` を実行する。
文書の派生表示は `mise run spec-render` と `mise run check-rendered-docs` で確認し、最終確認には `mise run verify-spec` を使う。

## リスク

- 許可辺の廃止で、検査が拒否していた依存の一部が受理されるようになる。
  受理されるのは公開パッケージを経由した非循環の依存だけであり、移行の前後の件数と、受理に変わった `undeclared-context-edge` の一覧を完了の節に残す。
- 設計方針の変更を、テナント分離、認可、原子性、失効などの保証を弱める理由にしない。
  振る舞いの変更が必要と分かったら、規範要素を参照する別項目へ分ける。
- 改名を一部の文書に限るので、後続の改名項目が完了するまで、文書に「Context」と「モジュール」が混在する。
  後続項目を本項目の完了と同時に起票し、用語の検査の規則でその完了を確かめる。
- `table-write` は動的な SQL を見ないので、`//sql:raw` を使えば検査を避けられる。
  `//sql:raw` には理由が必須であることを維持し、検査の説明にこの限界を書く。
- 共変更レポートの数値を、境界の正しさの証明として扱う誤用がありうる。
  レポートを合否に使わず、決定表の最終行の入力の一つに限ると文書に書く。
