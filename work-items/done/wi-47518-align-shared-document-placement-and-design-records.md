# 共通文書の配置、設計の説明、リスクの記録を実際の責務と現状へ揃える

## 動機

利用者は、横断シナリオと共通用語集が要件文書に置かれている一方、同種の内容がモジュール設計文書にもあることを指摘した。
共通用語集は業務用語に加えて Aggregate、Module、永続化の規約を含み、「業務と外部契約の語彙なので要件文書へ置く」という配置理由と一致していない。
文書の種類と適用範囲を別々に示し、モジュール共通の内容を親階層へ置く方針で合意した。

論理アーキテクチャは Go モジュールと責務を分けるモジュールを同じ文で説明なく使い、移行中の `legacy` の廃止条件もその場では分からない。
依存の許可リストについての判断は、見出しも本文も対象を特定しづらい。
また、設計文書に任意の実装ファイル名が残り、リスク一覧には解消済みの負債が載っている。

この項目は会話で合意した内容全体の入口である。
文書とその検査の整理をこの項目で完了し、独立した実装結果が必要な是正は下の対応表の項目で完了する。
起票した項目の存在を、製品の是正や稼働検証が完了した証拠にはしない。

## 対象範囲

- 共通用語集を `docs/modules/glossary.md`、横断シナリオを `docs/modules/scenarios.feature.md` へ移す。
- 文書ガイド、仕様フォーマット、作業項目フォーマット、配置理由、文書索引、リポジトリ構成の説明、関連するローカルスキルを新配置に合わせる。
- 文書探索、正規配置、規範とセキュリティの検査、仕様差分、生成サイトの目次、用語参照、テストを新配置へ対応させる。
- 文書、コードコメント、未完了の作業項目の参照を更新する。
- 全体設計とモジュールの内部設計にある具体的な実装ファイル名を、責務、公開契約、パッケージと配置規則による説明へ整理する。
- Go モジュールとモジュールの語義、`legacy` の終了条件、依存に関する判断を明確にする。
- システム全体のリスクの現状、是正の所有項目、受容する間の扱いを根拠とともに整理する。
- 機能スライスの `design.md` を廃止し、その内容を機能仕様 `README.md` の末尾の節「実現方式」へ統合する。配置、探索、検査、描画と、規則を述べる文書を合わせる。

## 対象外

- 製品コードの是正、`internal/` への移行、容量の実測、可用性とトレースの実装。
- GKE の実環境への適用と稼働検証。未リリースの現段階では今回の完了条件にせず、wi-55532 に対象環境と権限を伴う後続工程として明記する。
- 規範 ID、要件本文、用語の意味、TypeSpec の公開契約の変更。
- 完了済みの作業項目の歴史的な記録の更新。
- ソースファイル名の禁止を、拡張子だけで判定する新しい機械検査。
- 機能スライスのディレクトリを `<feature>.md` へ平坦化すること、受け入れ例を機能仕様へ統合すること。利用者は `design.md` の統合だけを今回の範囲に選んだ。`README.md` と `acceptance.feature.md` の組は統合前から 84 個あり、統合で新たには生じない。

## 設計

### 文書の種類と適用範囲

「モジュール設計文書」は、モジュールの仕様と内部設計を収める文書群の名前として維持する。
仕様は責務、契約、観測できる振る舞いを、内部設計は実現する構造と仕組みを記述することを入口で説明する。
モジュール共通の仕様と語彙は `docs/modules/` 直下、モジュール固有の語彙は各モジュール直下、機能の規則と受け入れ例は機能スライスへ置く。
横断シナリオの配置基準は「複数モジュールの協調による保証、または複数モジュールへ共通に適用する保証」とする。
CSRF と JSON デコードの保証も後者に含めるため、「そのモジュールだけでは WHEN を起こせない」という現在の基準は使わない。

要件用と設計用に用語集を分ける案と `docs/` 直下へ移す案は採らない。
利用者が選んだ共通の親階層へ置き、用語を二つの一次情報へ分けない。
新しい要件用語集や文書区分は作らない。

### 機能スライスの仕様と設計

着手後に利用者は、機能スライスに `README.md`、`design.md`、`acceptance.feature.md` が並ぶ構成で、`README.md` と `design.md` の違いが名前から読めないと指摘した。
受け入れ例の付録は現状を維持する。
起票時の機能の `design.md` は 53 個、合計 1317 行で、内容はその機能に閉じた構成要素の責務、実行時の流れ、データ、信頼性だった。

| 案 | 採否と理由 |
| --- | --- |
| `design.md` を廃止し、機能仕様の末尾の任意の節「実現方式」へ統合する | 採用。利用者が選んだ。機能について知るべき内容が一つのファイルにまとまり、機能スライスは機能仕様と任意の受け入れ例だけになる。文書の種類をファイルで分ける原則には、機能の階層だけの例外として節で分けることを明記する |
| モジュールの `design/<feature>.md` へ移す | 不採用。ファイルの分離は保てるが、機能の仕組みが機能スライスから離れた場所に置かれる |
| 機能仕様を `specification.md` へ改名し、`design.md` を維持する | 不採用。約 106 の機能仕様と全リンクの改名が要り、モジュール直下と機能群の `README.md` との非対称も残る |

「実現方式」は `SPECIFICATION_SECTIONS` の最後に置く任意の節とし、規則を置かない。
統合前の `## <設計領域>` は `### <設計領域>` に一段下げ、本文の「この文書」は「この節」に読み替える。
機能スライスに `design.md` を置くと、配置の検査が拒否する。
文書の種別は過去の revision でも `design.md` を規範の入力にしないので、統合は規範差分を生まない。

### 探索と過去の仕様差分

正規配置の宣言は `tools/workspace/src/document-layout.ts` に集め、共通文書を requirements の集合から modules の直下の集合へ移す。
共通文書をモジュール名や機能スライスとして扱わず、規範の探索対象へちょうど一度入れる。
生成サイトは「モジュール設計文書」の先頭に共通用語集、横断シナリオ、その後に各モジュールを表示する。

旧位置には転送用の Markdown や規範の写しを残さない。
現在の正規配置では旧位置を拒否する一方、過去 revision の仕様差分を読む処理だけは旧位置のシナリオを認識する。
文書分類と配置の受理を混同せず、旧位置から新位置への移動だけでは REQ の追加、削除、本文変更が生じないことをテストする。
完了済み作業記録は変更せず、現在のコードコメントと未完了記録の参照だけを新位置へ合わせる。

主な変更起点は文書配置、`check-specification-rules`、`check-security-controls`、`specification-doc`、`spec-diff`、文書描画器とそれぞれのテストである。
全追跡ファイルと隠しディレクトリも検索し、`.agents/skills/spec-change/SKILL.md` の旧配置の指示を取り残さない。

### アーキテクチャの説明

Go モジュールは `go.mod` が定める依存管理の単位、モジュールは責務と公開契約を分ける論理単位として、論理アーキテクチャの初出で説明する。
一つの Go モジュールへ複数の責務を持つモジュールを実装する関係を二つの文で示し、概要、判断、用語集の説明も揃える。
既存の「モジュール」という正規用語を全体で改名することはしない。

依存の判断の見出しは「モジュール間の依存を共通規則で検査する」とする。
個別の許可リストは「A から B への依存を個別に許可する一覧」と具体的に説明する。
公開範囲、非循環、共有ライブラリ、組み立て地点、テーブルへの書き込みの所有を共通規則で検査すること、その理由、製品の保証を壊す組み合わせが判明した場合の見直し条件を分けて書く。
バックエンド設計と検査コードの関連コメントも同じ説明へ揃え、検査が受理する依存は変えない。

`legacy` は、外から非公開パッケージへの依存を解消し、公開するパッケージを列挙して各モジュールを `internal` 方式へ移した後、全モジュールの移行完了時に撤去する。
撤去するのは命名による公開判定と移行中の例外であり、公開目的と外側に残る実装の照合は残す。
起票時は Tenancy、IdManagement、Authentication、OAuth2、Application、ClaimMapping、Jobs、WsFederation の 8 モジュールが残るが、着手時に責務表と実際の依存を確認する。
終了日を推測で書かず、wi-75383 と先行項目の完了条件へ対応付ける。
設計文書から work item へリンクせず、担当項目側と本項目の対応表で記録する。

### 設計文書に記載するコードの情報

対象は `docs/design/`、各モジュールの `design/` と各機能の `design.md` である。
具体例として、バックエンドの `events.go`、`module.go`、`routes.go`、`deps.go` の指定、フロントエンドの画面ファイル一覧、API 呼び出しの内部関数、テストヘルパーの指定、OAuth2 クライアント設計の変更不要なファイルの列挙を整理する。
設計には担当パッケージ、責務、依存方向、組み立ての境界と理由を書く。
変更の際にどの実装を開くかという一覧は、必要な場合だけ開発文書へ置く。
コードから容易に復元できる一覧は削除し、別の文書へ移し替えて維持しない。

配置検査が読むディレクトリと公開パッケージ、設定と物理スキーマの一次情報、TypeSpec の公開契約、検査タスクは残す。
フレームワークが要求する命名規則は、任意の実装ファイルの指定と区別して説明する。
ファイルの分割を比較した判断も、対象を「モジュールの組み立て」などの責務で説明し、任意の名前を固定しない。
この区別を文書ガイドへ反映する。

## 計画

1. 文書配置と表現の規則を先に更新し、正規配置、過去差分、規範探索、目次と用語参照の故障を局所テストで固定する。
2. 共通文書を移し、探索、検査、生成サイトと参照を一つの変更で対応させる。
3. アーキテクチャの語義、依存の判断、移行条件と設計文書の実装詳細を整理する。
4. リスクの根拠と所有項目を照合し、既存項目の補足を確認する。
5. 文書とツールの検証、サイト再生成、完了記録とコミットを行う。

後続の新規項目は、本項目を先に取り込んだ base から専用 worktree を作る。
wi-84348 を取り込んでから wi-15826 を実装し、wi-43627 は文書整理の後に独立して実装できる。
実装の呼び出しには、本項目、wi-84348、wi-15826、wi-43627 の全 ID を指定し、各項目の検証と完了コミットを次の項目の base へ取り込んで進める。
既存の項目も同じ実行で対応する場合は、その ID と依存先を指定し、既存項目の対象を文書整理へ取り込まない。
本項目の完了は文書とツールの整理の完了を意味する。
今回の新規是正の完了には本項目と後続 3 項目の完了が必要であり、既存の容量、可用性、トレース、legacy、GKE の不足は各既存項目の完了まで残る。

## 検証

- `mise run test-tools-file -- <対象のテストファイル>` で文書配置、探索、仕様差分、セキュリティ検査、描画の変更した故障を検証する。
- `mise run spec-diff -- <着手前の revision>` で REQ、例、TypeSpec の義務が移動によって変わらないことを確認する。実際の引数はタスク定義で確認する。
- `mise run check-links`、`mise run check-work-items`、`mise run check-work-item-references`、`mise run check-terminology` で参照、記録、用語を検証する。
- `mise run verify-spec` と `mise run check-rendered-docs` を最終差分へ実行し、`mise run render-docs` でサイトを再生成する。
- 共通ページから各モジュールへ到達でき、用語リンクと規範の参照が新ページへ解決し、旧ページが正規入力として残らないことを確認する。
- ソースファイル名の残存は役割ごとにレビューし、必要な構成や命名規則の参照まで消していないことを確認する。
- 変更耐性は、旧配置だけを認める、規範探索から共通シナリオを落とす、目次の共通文書を落とす故障をそれぞれの局所テストが検出することで示す。

## リスク

旧配置の受理と過去 revision の読み取りを一緒に変更すると、正しい移動を規範の追加として扱う可能性がある。
両方のツリーを入力にした仕様差分テストで区別する。
ファイル名の削除で必要な所有者や配置まで曖昧になる可能性があるため、責務とディレクトリの説明を残す。
是正の起票と完了を混同せず、残るリスクは担当項目の検証が済むまで現行文書へ残す。
