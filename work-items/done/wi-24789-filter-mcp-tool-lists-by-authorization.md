# 採否を判断したうえで tools/list を権限で絞り込む

2026-11-23、利用者が選んだ既存の公式 TypeScript SDK（2.4.0）で調査し、今回は一覧の絞り込みを見送った。
既存の再現環境の 4 ツールから、試験設定で割当済みと分かる 3 ツールだけをクライアント側の候補にした制御実験では、各候補を一度呼ぶ HTTP 往復は 4 回から 3 回、拒否は 3 回から 2 回になった。
一覧の JSON は 901 バイトから 685 バイトへ縮むが、条件による拒否と承認不足は残る。
この候補は新しい認可 API の応答ではなく、SDK による固定名の呼び出しや LLM のツール選択の改善を示すものでもない。
拒否した呼び出しでトークンの再取得はなく、指定したクライアントで自動的な選び直しの往復削減は確認できなかった。

既存の `CheckRelation` を未割当の操作ごとに逐次呼ぶ局所測定では、ウォームアップ 4 回後の 20 標本で、PostgreSQL の中央値は 4 件 0.425 ms、32 件 3.109 ms、128 件 13.785 ms（128 件の p95 は 28.516 ms）、メモリの 128 件は 0.279 ms だった。
トークンの検証、認可の HTTP 通信、一覧の書換えを含めておらず、未実装の一括 API の性能は判断していない。
一覧の縮小は確認できたが、毎回全候補を判定する費用に対して、実際の Agent の選択改善を裏付ける証拠がないため、製品への導入を見送る。
候補の選択を行う Agent で、割当不足による失敗と一覧の更新頻度を含む実ワークロードを測れるときに再検討する。

`spec-diff` に規範仕様の変更はない。
一括の評価入口、Gateway の一覧の書換え、ページングと変更通知への対応は実装せず、実行時の `tools/call` の評価を維持した。
一度だけの計測コードは取り除き、採否の判断だけを残した。
