# 日常開発の規則の重複を減らし、変更に必要な規則と背景説明を分ける

## 動機

2026-10-10 の調査では、変更の入口で案内されるワークフローと四つの形式文書は合計 2,166 行あった。
配置、証拠、検証、文脈管理が複数の文書にまたがり、AI は今回必要な規則の所在も判断する。
文書を短く言い換えた写しを足すと、規則の同期箇所がさらに増える。
現在は未リリースであり、当面も未リリースを継続するため、公開後の手順整備より日常の理解と変更の局所性を優先する。

## 対象範囲

- 文書ガイド、形式、ワークフロー、テスト方針、エージェント指示の規則の所有先の整理。
- 重複する説明を所有先への参照へ置き換え、背景と由来を必要なときに読む配置。
- 作業種別ごとに必要な節へ到達できる既存の索引と指示の改善。
- 代表的な作業に必要な読む量と参照の往復の比較。
- 利用者の追加指示に基づく、実装スキルと開発規約の最終検査の選択方法の修正。

## 対象外

- 規則の内容と必要な製品検証を、文書を短くするためだけに削除すること。
- 要約版の規則、独立した手書きの規則台帳、新しい汎用方法論の階層。
- 自動の文脈導出は[既存の brief の改善](wi-69747-derive-task-specific-agent-context-from-canonical-sources.md)が扱う。
- RED、特性化、変更耐性などの証拠の適用条件の変更は[証拠の縮小](wi-95150-scale-verification-evidence-to-change-impact.md)が扱う。

## 設計

配置、書式、実行手順、判断の理由をそれぞれの所有文書へ集める。
同じ規則を別の文章で再掲せず、所有文書の節を参照する。
まず既存の索引と節参照で代表作業が成立するかを確認し、自動導出へ渡す前に入力の重複を減らす。

着手時に、残す規則の所有先と、代表作業で必要な最小範囲を決める。
全文連結や別の短縮版を作る案は、読む量と同期費用を増やすため採らない。
全規約を常時読むことも、重要な制約へ到達できない短縮も完了条件にしない。

### 着手時の棚卸しと所有先

| 判断 | 重複していた場所 | 整理後の所有先 |
| --- | --- | --- |
| 現在状態の配置、生成物、内容の担当 | ワークフロー §2、§3、§6、文書ガイド | 文書ガイド。ワークフローは同期の契機と実行順序を扱う |
| 着手時の文脈の取得 | AGENTS、ワークフロー §8、文書ガイド §10.1、実装スキル | 作業文脈の導出。AGENTS は適用条件付きの入口、形式文書は記録の形を扱う |
| 主要ユースケースの定義と境界選択 | ワークフロー §4、テスト方針、作業項目フォーマット | 定義、境界とダブルはテスト方針。ワークフローは証拠の適用条件と収集順序、フォーマットはフィールドと検査を扱う |
| 型と作用の設計の記録、完了フィールド | ワークフロー、作業項目フォーマット、実装スキル | 記入形式は作業項目フォーマット。実装スキルはその節を必要時に読む |
| 検証タスクの実行順序 | ワークフロー §5、実装スキル | ワークフロー §5。スキルは各段階から直接参照する |
| 長い由来、検査を選んだ理由 | ワークフロー、文書ガイド、フォーマットの理由 | 既存のフォーマットの理由。適用条件、判定基準、例外は規則の節に残す |

新たな規則台帳や要約版は作らず、既存の節の所有関係を整理する。
ファイルの往復を抑えるため、AGENTS の着手行から、全作業に必要な証拠と、今回だけ必要な証拠を分けて指す。
既存の節アンカーは参照先を案内する節として維持する。
製品コードとテストの変更はなく、Markdown だけであるため、振る舞いを保つ変更として RED と変更耐性の証拠を作らない。

### 追加指示に基づく検査の選択

利用者から、変更に応じた最小の最終検査、影響が不明な場合の範囲の拡大、Go の `-race` の必要性の判断を求められた。
最終検査の所有先をワークフロー §5 とし、実装スキル、CONTRIBUTING、ローカル開発、記録のテンプレートから参照する。
一律の `verify`、依存の全導入、先行 `lint-go` の要求を変更し、差分、影響、故障、タスク定義から検査と準備を選ぶ。
RED、特性化、変更耐性の適用条件と CI の必須検査は維持する。

追加取得した CONTRIBUTING、ローカル開発、`mise.toml`、`tools/check/src/check-command-map.ts` で、既存の要求とタスクの対象を確認した。
`test-go-package` と `test-go-changed` は常に `-race` を付けるため、対象範囲と通常構成・race 構成を別々に選ぶ。
今回の変更には Go、UI、TypeSpec、CI、タスク定義の差分がなく、文書の意味、参照、指示、記録の検査で確認できる。
既に実行した `verify`、先行 `lint-go`、`check-command-map` は成功したが、この差分の最終検査には不要である。

### 比較条件

基準は着手時の `c097fabce` とする。
同じ実装スキルを使う機能変更、構造変更、文書変更、tooling 変更を比較する。
各作業で、AGENTS とスキル全文、着手と記録、変更種別の判断を行う節の本文行数を数える。
コード、製品仕様、個々の作業項目の長さは変更していないため比較から除く。
見出しから次の見出しまでを一節とし、子節は適用するものを独立に選ぶ。コードブロック内の見出しを除外し、重なる範囲は一度だけ数える。
参照回数は、常時読み込む AGENTS と実装スキルを除く必要な節を開く回数とする。同じ節の再読は数えず、全文を読む文章の言語は一回とし、ファイル数も併記する。
背景の由来を調べる作業は日常変更と分け、削減量へ混ぜない。

## 計画

1. 代表作業で必要な規則と、重複した説明を棚卸しする。
2. 所有先と参照を整理し、背景説明を必要時に読める形へ分ける。
3. 規則の維持と読む量の削減を別々に確認する。

## タスク

- [x] T001 [Inventory] 重複と、代表作業で必要な規則を特定する。上の棚卸しを確認し、`mise run setup` と `mise run lint-go` が成功した。
- [x] T002 [Design] 所有先と日常の参照範囲を決める。上の所有先と比較条件を採用した。形式の検査には `mise run check-work-items` を使う。
- [x] T003 [Docs] 写しを参照へ置き換え、規約と指示を同期する。`mise run check-agent-guidance`、`check-command-map`、`check-links`、`check-work-items` が成功した。
- [x] T004 [Verify] 必要な規則への到達と、読む量と参照回数を比較する。下の同条件比較と維持確認を完了し、四種の `mise run brief` が参照先を返した。局所検査は T003 の四検査、意味差分は `mise run spec-diff -- c097fabce`（規範仕様の変更なし）で確認した。
- [x] T005 [Docs] 追加指示に基づき、最終検査と Go の race 検査を影響に応じて選ぶ規約へ修正した。スキル、CONTRIBUTING、ローカル開発、記録のテンプレートを同期し、下記の三検査と選択条件のレビューで確認した。

## 検証

- 代表的な機能、構造、文書、tooling の変更で必要な規則へ到達できる。
- 同じ規則を変更するときに、独立した写しを複数更新しなくてよい。
- 読む量と往復を同じ条件で比較し、重要な制約の欠落を確認する。
- `mise run check-agent-guidance`: AGENTS と実装スキルの必須指示、廃止した方針、タスク呼び出しの整合を検査する。
- `mise run check-links`: 所有先へ移した文書の参照、既存の節アンカー、新たな選択規則への参照を検査する。
- `mise run check-work-items`: 着手の文脈、タスク、完了記録と移動後の参照を含む作業項目の形式を検査する。
- 変更内容、影響が不明な場合、並行処理への影響の有無から選ぶ検査と race 構成を規約で確認する。

### 必要な制約の維持

| 確認した制約 | 整理後の到達先 |
| --- | --- |
| 仕様を先に決め、仕様にない振る舞いを分類する | 実装スキルの手順 3 と 5 → ワークフローの開発サイクルと分類 |
| 認可、隔離、永続化、正式な配線の独立した故障 | 手順 4 → テスト方針の主要ユースケース、ワークフローの証拠契約 |
| Markdown とテストを変えない refactor の証拠の例外 | 手順 4 → 振る舞いを保つ変更。既存の適用条件を維持 |
| 特性化の先行コミット、変異と手動注入、ファズのオラクル | 手順 5 と 6 → ワークフローの該当節。手法の条件と例外を背景へ移していない |
| 局所検査、API の契約検査、ブラウザーに届く変更の E2E | 手順 5 と 7 → 検証の段階。タスクの引数と並列実行の注意をここへ集めた |
| 追加指示による最終検査の最小化、不明な範囲の拡大、Go の race 構成の選択 | 手順 7 → 最終検査の選択、Go の通常テストと race 検査。適用する証拠は維持し、タスクの選択方法を変更した |
| 型と作用の設計、記入フィールド、完了後の移動と参照検査 | 手順 3、4、7 → 作業項目フォーマット |
| 生成物の編集禁止、現在状態と履歴、境界の宣言 | ワークフローの同期の節 → 文書ガイド |
| チェックポイントの折り畳み、英語の最終本文、push の指示 | 手順 5 と 7 → チェックポイントと最終コミット |

削除した散文を差分で確認し、規則の移動と背景の移動を分けた。
出典内に混在していた OpenSpec CLI の非採用と Cucumber の実行形式の制約も、日常の所有節へ残した。
文書ガイドのレビュー欄に残っていた操作の手書き要約表への言及は、既に要約表を禁止する仕様フォーマットの参照へ整理した。
製品の要件、RED と変更耐性の適用条件、テストの水準は変えていない。
最終検査と race 構成の選択方法は、追加指示によって変更した。

選択条件を、文書だけなら上記の三検査、並行性に影響しない Go の純粋計算なら通常テスト、共有状態の変更なら対象と逆依存の race 検査、影響範囲が不明なら該当する広い検査へ到達することとしてレビューした。
既存タスクの定義と照合し、通常テストの全件指定は `test-go-test` の `-run "^.*$"` へ渡ることを確認した。

適用条件は日常の規則と一緒に残し、由来や長い理由だけを必要時の参照へ分ける。
