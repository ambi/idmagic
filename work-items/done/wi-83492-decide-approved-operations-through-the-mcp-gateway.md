# MCP ゲートウェイで承認した操作をどう扱うか判断して対応する

通常の MCP サーバーを変更せず、人が承認した操作をゲートウェイで実行できるようにした。
要求ごとに新しい `operation_key` と引数全体を評価へ渡し、IdMagic の既存の承認ストアで転送前に使用を確定する。
再送、並行要求、ゲートウェイの再起動でも、同じ承認による転送は最大一回となる。
同じ鍵の再送として評価が許可した応答も転送には使わない。

REQ-MCPGATEWAY-013 を追加し、REQ-MCPGATEWAY-003、006、007 と REQ-OAUTH2-065 を変更した。
使用済みは 403 と `-32004`、上流への転送で応答前に通信が切れた場合は結果不明の 502 と `-32005` とする。
承認の識別子とダイジェストを監査へ残し、引数と実行の鍵は記録しない。
Envoy の配布例は再試行と hedging を使わず、呼び出し元の再試行指示ヘッダーも除く。
TypeSpec の ResourceAccessEvaluationRequest と ApprovedOperationUse は説明を更新し、ワイヤの形は変えていない。

保証するのは最大一回の転送であり、業務処理の成功と結果の回収は保証しない。
承認の消費後に失敗しても使用を戻さず、結果の確認前に新しい承認で再実行しない運用を求める。
引数全体を TLS で IdMagic へ送るので、承認の fields と同じくシークレットを含めない。
本番の複数プロセスでは PostgreSQL の承認ストアを使う。

実在の MCP SDK のサーバーで、承認と対象と引数の一致、新たな承認で同じ内容を実行できること、再送と並行要求の拒否、ゲートウェイの再作成、評価と上流の応答の消失、条件付き承認を確認した。
応答開始後の切断の監査と、不完全な承認応答の拒否も局所検査で確認した。
最終の verify-changed、実在の Envoy の検査、承認の受け入れテストの race 検査、サイト生成を通した。
最初の UI 検査の失敗は、単独検査、同じ並列検査と単体テスト十回の反復では再現せず、利用者の指示により調査を止めた。
UI の修正は行っていない。

承認の開始へ Agent を導く流れ、汎用 AuthZEN HTTP API の新設と AARP の通信実装、承認を下流向けの交換トークンへ継承することは対象外である。
RAR と CIBA の既存の承認契約と AuthZEN 型の判断境界を維持し、ゲートウェイと IdMagic の評価アダプターの独自項目を標準仕様の保証とは区別した。
