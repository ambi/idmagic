# ApiTokens が宣言する未検証の拒否 1 件に効果まで確かめるテストを与え、台帳から外す

## Motivation

`tools/check/example-coverage-debt.json` は、どのテストからも id を引用されていない規範 id を保持する、縮むだけの台帳である。

このうち 102 件は [[wi-390-security-control-test-standard-and-gate]] が拒否専用の台帳へ据え置いた分で、[[wi-490-fold-refusal-coverage-into-one-normative-coverage-rule]] が網羅台帳へ統合した。

その 102 件のうち 1 件が ApiTokens の拒否である。

件数は最も少ないが、対象は API アクセストークンの認証そのものである。

`REQ-APITOKENS-002` は 2 つの `ALT` で拒否を宣言している。

JWT の形式、署名、発行者、audience、`exp` のいずれかが不正である場合と、トークンが未知、失効済み、期限切れ、またはスコープ集合が空である場合。

この防護は他の Context のスコープ検査より手前にあり、ここが素通りすれば、以降のスコープ検査は攻撃者の名乗った主体に対して働くことになる。

台帳の他の 101 件のうち、スコープを扱う拒否の多くは、この認証が正しく効いていることを前提にしている。

したがって件数の少なさは重要度の低さを意味しない。

`mise run report-coverage-debt` の分類は nearby であり、挙がっているのは `TestIssueApiTokenRejectsInvalidRequest` など発行側の拒否テストである。

発行の入力検証は、提示されたトークンの認証とは別の防護である。

そして注記だけを足す解消は、この項目では認めない。

## Scope

- `REQ-APITOKENS-002` が宣言する 2 つの拒否について、production と同じ入口 (API トークンで保護されたエンドポイント) から到達するテストを用意する。
- 各テストで 2 つを assert する。呼び出し元が観測する応答 (ステータスとエラー種別) と、その拒否が変えなかった状態。
- 拒否の理由ごとに、少なくとも形式、署名、発行者、audience、`exp`、未知、失効済み、空スコープを網羅する。
- テストのソースに `REQ-APITOKENS-002` を書く。
- 対応が取れた id を `tools/check/example-coverage-debt.json` から削除する。
- 拒否を実装が持っていないと判明した場合、その防護をこの項目で実装する。
- 完了時点で、この項目が持つ id が台帳から 1 件残らず消えていることを確認する。

## Out of Scope

- 他 Context の拒否。
  Context ごとに別の work item が持つ。
- 102 件を 1 つの単位として消化すること。
  [[wi-399-burn-down-untested-refusal-debt]] がその形で立てられているが、進める単位を未決のまま残し、注記だけの解消も認めている。本項目はその置き換えである。
- API トークンの発行側の入力検証。
  すでに拒否テストがあり、この項目の対象ではない。
- 同じ台帳に載る、この項目が持たない id。
  規則は同じだが、引き取る範囲はここに挙げた id に限る。
- R1、R2、R4 の検査そのものの変更。
  [[wi-390-security-control-test-standard-and-gate]] と [[wi-391-refusal-declaration-floor-and-reinventory]] が持つ。
- 既存テストへ `REQ` id を注記するだけで台帳から外すこと。
  この項目ではこれを解消として扱わない。
- スコープ体系の変更と、トークン形式の変更。

## Design

### 解消の条件

id を台帳から外してよいのは、次の 3 つがすべて成り立つときだけとする。

第 1 に、テストが production の使う入口から入り、宣言された拒否の判断を実際に通ること。

認証はミドルウェアの位置にあるため、テストは保護されたエンドポイントへ実際のトークンを付けて送る。

第 2 に、拒否が変えなかったものをテスト自身が読み直して確かめること。

第 3 に、シナリオの id をテストのソースが引用していること。

### 何を読むか

拒否の効果は、保護されたエンドポイントが何もしなかったことである。

したがってテストは、状態を変えるエンドポイントを対象に選ぶ。

読み取りのエンドポイントで確かめると、応答が空であることしか言えず、素通りしたときの被害である「書き換え」を再現できない。

| 拒否の理由 | 読み直して確かめる対象 |
|---|---|
| JWT の形式が不正 | 対象リソースが変更されていない |
| 署名が不正 | 対象リソースが変更されていない |
| 発行者が不正 | 対象リソースが変更されていない |
| audience が不正 | 対象リソースが変更されていない |
| `exp` を過ぎている | 対象リソースが変更されていない |
| 未知のトークン | 対象リソースが変更されていない |
| 失効済みのトークン | 失効の直前に成功していた同じ操作が、失効後は反映されない |
| スコープ集合が空 | 対象リソースが変更されていない |

失効済みの場合だけ読み方を変えるのは、失効が状態遷移を伴うためである。

失効の前後で同じ操作を行い、前は反映され後は反映されないことを対で確かめる。

こうしないと、そのトークンが最初から使えなかった実装と区別できない。

audience と発行者の拒否は、値だけが違う正しい形式のトークンで確かめる。

壊れた文字列で確かめると、形式の検証で落ちてしまい、audience の照合が無くても成立する。

### 却下した進め方

**トークン検証関数の単体テストで閉じる案。**

検証が正しくてもミドルウェアが配線されていなければ素通りする。

**読み取りエンドポイントで確かめる案。**

拒否の効果を「書き換えが起きていない」で読めない。

**8 つの理由をまとめて 1 つの不正なトークンで確かめる案。**

1 つの理由で落ちれば残りの検証が無くても成立する。

理由ごとに、他の要素は正しいトークンを組み立てる。

## Plan

1. シナリオを読み、対象とする状態変更エンドポイントを 1 つ選ぶ。
2. 理由ごとに、他の要素は正しいトークンを組み立てる固定具を用意する。
3. 形式と署名の拒否から着手し、テストが RED になることを先に観測する。

8. 対応の取れた id を台帳から削除し、この項目が持つ id が 1 件も残っていないことを確認する。

## Risk Notes

理由ごとに 1 要素だけを崩したトークンを作らないと、手前の検証で落ちて後段の照合が確かめられない。

各トークンについて、崩した要素以外が有効であることを、正しいトークンが通ることで先に確認する。

認証はほぼすべての保護経路が通るため、ここを外して落ちることを確かめる作業は、他のテストへ広く影響する。

意図的に外す確認は一時的な変更に留め、その場で戻す。

台帳は id 順に 1 エントリー 1 id なので、Context ごとの work item が並行しても衝突はエントリー単位に収まる。

各項目は自分が持つ id のエントリーだけを削除し、コメント配列と他の id には触れない。
