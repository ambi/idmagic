# 手元の Go のテストは、入力が変わらないパッケージの結果を再利用する

`mise run spec-diff` は main に対して規範の差分なしを示す。
実行器は `-count=1` を付けるのをやめ、手元の Go のテストのタスク（`verify`、`verify-changed`、`verify-integration` を含む）は、入力が変わらないパッケージの結果を Go のキャッシュから返す。Go がキャッシュするのは成功だけで、鍵にはテストのバイナリ、フラグ、テストが開いたファイルと読んだ環境変数が入るので、返る結果は同じ入力で通した結果の再生として証拠に数える。
起票時は証拠の実行を `-count=1` に残す計画だったが、鍵に入らない入力への依存が漏れても main の前で CI が実際に実行するので、手元のゲートだけを例外にする理由はないと判断した。CI のジョブは空のキャッシュから始まり今は再利用が起きないが、Go のキャッシュを復元するようにした場合に備え、`go-test` と `go-race` のジョブに `GOFLAGS=-count=1` を置いた。
報告は `cachedPackages` を記録し、`report-verification` は再生したパッケージの数を表示する。実際に実行し直すときは `clean-go-test-cache` を使う。テストごとの成功、Skip、未実行は Go が再生したイベントから従来どおり導く。
鍵に入らない入力へ依存するテスト（子の bash が読む `dev.sh`、子の `go test` が読む `testdata`、外部の KDC）は、実行器が実行ごとに変える `VERIFICATION_RUN_ID` を読んで再利用から外れる。ディレクティブを実行器が読んで別に `-count=1` で実行する案は、`go list` と二回の実行の合成が要るので採らなかった。読み取りの漏れを探す静的検査は、誤検出が多く CI が最終的に拾うので足さない。
一つのテストを実行するタスクの名前を `test-go-test` から `test-go-one` に改めた。
392 パッケージを選ぶ状態で 1 パッケージのテストを変えた後の `test-go-changed` は約 9 秒で、同じ集合の `-count=1` は約 53 秒だった。方針は `testing.md` の「Go の結果キャッシュ」に置いた。
