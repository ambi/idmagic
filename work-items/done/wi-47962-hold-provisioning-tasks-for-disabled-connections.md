# 無効にした接続へ、無効化の前に積んだタスクを送らない

既存 IdP の一時停止の事例と保持、取消の利点と欠点を比較し、利用者の指定に従って保持案を採用した。
REQ-PROVISIONING-017、REQ-PROVISIONING-020、ProvisioningTaskLifecycle に無効化による保留を追加し、未投入の pending はそのまま保持し、投入済みのタスクは前の job_id を持つ pending へ戻すようにした。

接続の CanProvision に有効かつ非隔離の判定を集約し、取り込み、再同期、ディスパッチャー、送信開始時に適用した。
無効な接続では資格情報を取得せず、下流クライアントも構築しない。
接続が有効かつ非隔離へ戻った後は同じタスクを新しいジョブで実行し、古いジョブは送信も更新も行わない。
保留では成功と失敗のイベント、連続失敗数、フル同期の完了を変えず、保留の保存失敗はジョブへ返す。

下流 HTTP を使った保持と再開、無効な接続を飛ばすページング、主体と操作の組、フル同期と保存失敗を検証した。
PostgreSQL とメモリの共有契約を通し、最終差分と逆依存の検査、生成サイトを確認した。
公開 HTTP 契約、DB スキーマ、外部へ発行するイベントは変更しない。

接続の削除、実行開始時の接続確認を過ぎた外部通信の取り消し、管理者のオンデマンドとフル同期の受付条件は対象外とした。
長期停止によるタスクの滞留と再開時の処理集中は残る。
