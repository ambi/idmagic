# MCP ゲートウェイがツールの引数を条件の属性として渡す

`mise run spec-diff` の差分は REQ-MCPGATEWAY-001 と REQ-MCPGATEWAY-003 である（同時に表示された REQ-SHAREDSIGNALS-010 は `main` の別コミットによる）。
`mapping.tools` の操作に任意の `attribute_arguments` を加え、名指した `arguments` の直下のキーだけを値を変えずに評価の `attributes` として送るようにした。
名指したキーがなければ省き、どれもなければ `{}` を送る。宣言のない操作は従来どおり `attributes` を送らない。
直列化が 16 KiB を超えると、評価せずに 403 と `-32000`（理由 `attributes_too_large`）で拒否する。
`mapping.methods` での指定、空のキー、重複したキーは起動を拒む。
全引数を既定で渡す案と除外を宣言する案は、シークレットが評価へ流れ、上流の引数の追加で入力が広がるため採らなかった。

受け入れテストは、`attributes.amount > 100 || has(attributes.memo)` の条件で、金額 80 だけが無改修の MCP サーバーで実行され、名指していない `memo` が評価にもログにも届かないことを実行回数で読む。
配線の欠落と全引数の送信を手で注入し、このテストが両方を検出することを確かめた。
残るリスクとして、属性は MCP クライアントの申告であり、条件が実行される引数を判定できるのは上流が転送された本文の値で実行する場合に限られる。
SDK のクライアントは接続時に `server/discover` を評価するので、同じ規則に属性を読む条件を置くと、属性のないその評価が評価不能で拒否される。方法と属性を読むツールは別の組へ写す必要がある。
