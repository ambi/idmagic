# API ガイドラインと設計ガイドラインを規則を先に示す形で書き直し、設計文書から個々の実装への参照を外す

`mise run spec-diff -- main` は「no normative specification change against main」を報告した。ルールの決定内容、`REQ-*`、標準 id、TypeSpec は変えていない。
API ガイドラインは、担保手段を仕組みの種類（API 契約の宣言、HTTP 境界の共通処理、ドメインの検証、ユースケースの検証、データベースの制約、検査タスク）で書く形にし、個々のファイル、関数、ライブラリの名前を外した。採用しないことだけを述べていた「コロン形式」「部分レスポンス」「完了通知」の節は、末尾の「採用しない方式」の表へ移した。オフセット方式と汎用のフィルター言語も同じ表に載せた。文字列長の上限は、決めた規則と表から始め、PostgreSQL の B-tree の上限は理由の補足に回した。Go とライブラリに固有の数え方の選択は、バックエンド設計へ移した。
設計ガイドラインは、各節を原則、判定基準、根拠の形にそろえ、大きな判断から小さな判断へ並べ替え、末尾に出典の表（Parnas、Ousterhout、Martin、Cockburn、Feathers、Meyer、Bernhardt、Evans）を置いた。現在のコードの逸脱は、システムのリスクと技術的負債、Sourcing のリスクへ移した。アクショントークンの共通核の説明は、バックエンド設計へ移した。
用語集の Aggregate は案 A で書き直した。語を Evans の *Domain-Driven Design* から借りる範囲を一貫性の境界の意味に限り、モジュールの境界は情報隠蔽と境界を選ぶ判断手順で選ぶと明記した。
文書ガイドに、設計文書からコードへの参照の基準とレビューの確認項目を加え、基準を当てはめた。13 のモジュールの `architecture.md` から、ソースファイルを列挙する表を外した。設計文書の 12 か所にあった、関数、メソッド、個々のファイルへの参照を、仕組みの種類やパッケージに置き換えた。参照を外した規則を担保するコード（ページング、カーソル、レートリミット、JSON の解析、非推奨ヘッダー、セキュリティヘッダー、CSV の転送、識別子、ブランディングの `ETag`、日付の形式）には、API ガイドラインの節を指すコメントを足した。コードの振る舞いは変えていない。
`check-terminology` に、採らない概念として名指す「境界づけられたコンテキスト」を許す例外を足し、`ドメイン設計文書` の採用語を「モジュール設計文書」に直した。
