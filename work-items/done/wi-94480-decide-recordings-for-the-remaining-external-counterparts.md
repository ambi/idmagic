# 残りの外部の相手について、記録の再生と模倣を入れるかを決める

残りの外部の相手ごとに、既存のテストを振る舞いごとに並べ、2026-11-28 に読んだ一次資料と比べて、記録の再生と模倣の採否を決めた。
採ったのは SET の受信者だけである。
RFC 8935 の 2.1 節は `Accept: application/json` を MUST とするが、pusher は送っていなかった。
`docs/modules/sharedsignals/standards.md` に標準要件 RFC8935-PUSH-REQUEST を足し、pusher が `Accept` を送るようにした。
Figure 1 と Figure 2 を転記した `push_http/testdata/rfc8935.json` の再生が、要求の Content-Type、Accept、本文を照合する。
受信者は状態を持たないので模倣は置かず、失敗の応答は状態コードだけで決まるので既存の単体テストに任せた。

採らなかった相手と、見直す契機は次のとおりである。

- Microsoft のレルム探索：一次資料がなく、再生は Microsoft の変化を検出しない。既存のテストは観測した応答を日付付きで転記している。API が文書化されたとき、または判定の誤りが起きたときに見直す。
- HIBP の Range API：文書の例の形（大文字の接尾辞、`:`、件数、詰め物の件数 0）は既存のテストと同じで、誤りは状態コードだけで決まる。API の版または応答の形が変わったとき、または失敗の計測が増えたときに見直す。
- OAuth Client ID Metadata Document：-02 に文書全体の例がなく、標準テストが CIMD02-* の全 ID を被覆する。-03 以降へ上げる作業で、その版の例による検証を置く。
- 外部の JWKS：解決器は `keys` の配列を取り出すだけで分岐せず、鍵の回転は既存のテストが要求をまたいで検査する。`use`、`alg`、`kid` で鍵を選ぶ処理を足すときに RFC 7517 付録 A.1 の再生を置く。
- Workload の issuer の Discovery：読む欄は `issuer` と `jwks_uri` だけで、Discovery 4.1 節にあたる URL の組み立ては既存のテストが扱う。読む欄を増やすときに見直す。
- Back-Channel Logout の RP（表になかった相手）：応答は状態コードだけで決まり、要求のフォームは既存のテストが検査する。版を上げるときに見直す。

洗い出し直すと、表になかったリモートの AuthZEN の判定点が AuthZEN 1.0 と食い違っていた。`action` を文字列で送り、仕様にない `permit` と `reasons` を読む。
認可の互換性に触れるので wi-92900 に起票し、ここでは直していない。
公開された MCP サーバーへの送信は wi-49024 の再生が扱っている。
