# 境界の判断を、観測できる事実と検査される宣言に基づくモジュール設計へ置き換える

## 動機

エージェントに設計と実装を任せるには、判断に使う入力、制約、候補の比較順序、相談が必要になる条件を明示する必要がある。
規則が観測できない意図に依存すると、エージェントはその都度もっともらしい解釈を作り、変更ごとに判断が揺れる。
この項目では、同じ入力から同じ制約と候補の絞り込みを再現し、根拠が不足するときも同じ理由で判断を保留できることを目指す。

DDD の Bounded Context はモデルと言葉が有効な範囲を示し、Context Map はモデル間の統合や組織上の関係を記述する。
これらから Go のパッケージ境界や公開範囲が一意に導かれるわけではない。
現在の運用では、その変換を明示しないまま DDD の分類を実装の配置と依存の根拠にしており、エージェントが分類を解釈する余地が残っている。
本項目は、DDD 全般が AI 駆動開発に適さないという結論を前提にせず、このリポジトリで実装の判断に使う仕組みを置き換える。

現在のリポジトリでは、DDD の語彙が付いた宣言の多くが、検査の結果にも作業の選択にも効いていない。

| 観測した事実 | 帰結 |
| --- | --- |
| Context Map の関係ラベル（OHS/PL、C/S、ACL）を `boundary-fitness.ts` は解析するが、判定には使わない。判定に効くのは辺の有無だけである | Context Map の実体は、DDD の名前を付けた import の許可リストである |
| `undeclared-context-edge` は Context Map に辺を書き足せば消える。テナントの公開言語の項目は、計画の最初の段階でこの書き足しを行う | 宣言した辺は検査できるが、辺を認める判断基準が別途必要である |
| 負債台帳 `tools/check/boundary-debt.json` は 180 項目、510 個の違反 ID を持ち、理由はすべて自動生成の定型文である | 台帳から、次に何をどう直すかを読み取れない |
| `context-cycle` の 66 項目は Context 単位に集計した循環である。パッケージの循環は Go のコンパイラがすでに禁じている | パッケージの循環とは別の制約である。ただし集計値だけでは、実行時の呼び出しや具体的な変更の波及は説明できない |
| Subdomain の区分について、設計ガイドラインは「区分そのものが妥当かどうかは検査できない」と書く。区分が左右するとする三点（自作と委譲、文書の厚み、翻訳する側）は、どれも区分を使わずに規則にできる | 検査も作業の分岐も生まない分類を、全 Context に付けている |
| データベース設計のテーブル一覧には「所有 Context」の列があるが、`schema-tables.ts` は判断を書いた列として照合しない | 宣言はあるが、ほかのモジュールからの書き込みを止めない |
| 「Context」は Go の `context.Context` と同じ語である。`backend/tenancy/context.go` は解決済みのテナントを `context.Context` に載せる | 文書とコードで同じ語が別の概念を指す |

Modular Monolith、Clean Architecture、Vertical Slice Architecture は維持する。
この項目は、その内部でモジュールの範囲、公開範囲、依存、データの所有を決める方法を、エージェントが機械的に再現できる形へ置き換える。
原則は Parnas の情報隠蔽（変わりうる設計判断を一つのモジュールへ隠す）に置き、原則の適用を観測できる事実と検査で支える。
要求、不変条件、用語の意味は引き続き仕様で定め、情報隠蔽が判断を必要とする部分は変更シナリオで比較する。

上表の件数は、起票時点の台帳に対する観測値である。
2026-10-10 の確認でも 180 項目、510 ID（`private-import` 111、`undeclared-context-edge` 240、`context-cycle` 66、`shared-detour` 73、`domain-effect` 20）だった。
確認した revision は `b1a7e53a5ab771cf9d292c205a548702ddde7e07` であり、着手時には再計測する。

## 対象範囲

- 設計の判断を、機械抽出する事実、検査される宣言、証拠を比較する判断の三つに分け、境界を選ぶ手順と相談条件を一次情報文書へ反映する。
- `AGENTS.md` と既存の作業スキルから、この手順を境界に関わる変更の着手条件として参照する。
- 設計文書の Bounded Context と Context を「モジュール」へ改名する。この項目で改名するのは、概念を定義する文書と、この項目で変更する検査の識別子と出力文言である。
- モジュール間の依存を、公開パッケージ、モジュール単位の非循環、`shared` からモジュールへの依存の禁止で検査し、Context Map の許可辺と関係ラベルを廃止する。層の依存方向と起動設定の検査は維持する。
- 公開範囲の最終形を Go の `internal/` とし、移行中のモジュールで現在の規則を併用する検査と、移行の手順を定める。
- テーブルの所有者と sqlc の入力を照合し、所有者を越える明示的な書き込みを検出する。既存の逸脱だけを移行し、新しい逸脱を拒否する。
- Subdomain の区分、区分の列、その検査を撤去し、区分が左右していた三点を区分に依存しない規則へ書き換える。
- 境界の判断の証拠として、Git の履歴から一緒に変わるモジュールの組を数えるレポートを追加する。
- 負債台帳を新しい違反の種類へ移し、旧項目との対応を記録する。
- 改名の残り、`internal/` への移行、既存の境界解消の項目の見直しを、後続項目として起票または調整する。

## 対象外

- HTTP 契約、認証方式、状態遷移、整合性、失効、監査、通知などの製品の保証の変更。
- 本番パッケージの `internal/` への移動と、モジュールの分割、統合。
- 仕様のディレクトリ名（`docs/domain/<名前>/`、`spec/contexts/<名前>/`）、規範 ID の接頭辞（`REQ-<名前>-NNN`）、TypeSpec の名前空間の変更。規範 ID と公開済みの名前は取り消せない識別子なので、改名の対象にしない。
- 概念を定義する文書以外での改名。後続の改名項目が、用語の検査の規則とともに行う。
- ほかのモジュールが所有するテーブルの読み取りの検査。後述の理由で、この項目では判断として扱う。
- 共変更レポートを合否の判定に使うこと。
- 境界の最適解をコードや履歴だけから自動決定すること。候補の生成と比較手順は定めるが、要求の意味と将来の変更を履歴から推測して確定しない。
- マイクロサービス化、プロセス構成、DB スキーマの変更。

## 設計

### 判断の三分類

設計の判断を、入力の種類で三つに分ける。

| 分類 | 定義 | 例 | 誤ったときに何が起きるか |
| --- | --- | --- | --- |
| 機械抽出する事実 | ソース、仕様の識別子、Git と抽出条件から決まる値。手で書き写さない | import の辺、パッケージのパス、SQL の明示的な書き込み先、要件参照の解決結果、共変更 | 抽出の誤りは fixture で検証する。抽出できない入力は診断する |
| 検査される宣言 | 人またはエージェントが書き、検査が整合または規則の判定に使う値 | 責務表のパッケージと公開方式、組み立て地点、公開パッケージ、テーブルの所有モジュール | 未宣言、重複、未知の参照、規則違反を拒否する。宣言の意味の正しさは別途レビューする |
| 証拠を比較する判断 | 要求の意味、不変条件、変更シナリオと事実を使って候補を選ぶ判断 | 新しい処理の担当、公開操作、依存の逆転、モジュールの分割と統合 | 入力、該当する制約、候補、採否、未確認の仮定を work item に記録し、レビューする |

機械検査の入力となる欄を足すときは、その欄が変える検査の結果を同時に定める。
要求の理由、責務、用語の意味、隠す設計判断は、検査できなくても判断に必要な一次情報として残す。
検査が証明するのは宣言に対する適合であり、宣言を変更しただけで設計上の問題が解決したことにはしない。
所有者の変更、公開範囲の拡大、組み立て地点の追加には、以下の判断手順を適用する。

### モジュールの定義

検査には、責務を割り当てる単位とソースの対応が必要である。
この項目の **モジュール** は、論理アーキテクチャの責務表に宣言した責務と、その実装、仕様の文書、TypeSpec の対応を一つの単位として呼ぶ名前である。
初期の実装範囲は `backend/` 直下の `cmd` と `shared` を除いたディレクトリを一つずつ割り当てる。
この対応は既存構成を検査するための初期値であり、ディレクトリの存在が境界の妥当性を証明するわけではない。
モジュールの名前（`IdManagement` など）、Go パッケージ、仕様のディレクトリの対応は、責務表だけで定める。
機能ごとの垂直分割（`backend/<モジュール>/<機能>/`）はモジュールの内部構造であり、別のモジュールではない。

パッケージは、次の三種類のどれかに属する。

| 種類 | 範囲 | 依存の扱い |
| --- | --- | --- |
| モジュール | 責務表に宣言した実装範囲 | 後述の依存規則に従う |
| 組み立て地点 | 責務表の System 行が列挙するパッケージ接頭辞。`backend/cmd/`、`backend/shared/http/server_http/`、`backend/shared/http/testing_stack/` | 結線に必要な依存を持てる。モジュール間の循環の集計には含めず、公開範囲は移行規則に従う |
| 共有ライブラリ | `backend/shared/**` のうち組み立て地点を除いたもの | どのモジュールにも依存しない |

`testing_stack` を組み立て地点に含めるのは、テスト用の HTTP スタック全体を `_test.go` ではないファイルで組み立てており、実態が `server_http` と同じ結線だからである。
接頭辞はディレクトリ区画で照合し、同名で始まる別のディレクトリを含めない。
重複する割り当て、責務表にないモジュール、分類できない本番パッケージは検査を失敗させる。
`frontend/` は System の仕様対応に残すが、Go の境界検査の対象にはしない。

モジュールと共有ライブラリから組み立て地点への依存は `composition-import` として拒否する。
組み立て地点へ業務処理を移すことでは違反を解消できず、追加する地点には、結線する対象と業務判断を含まない根拠が必要である。

### モジュール間の依存の規則

Context Map の許可辺と関係ラベルを廃止し、次の規則に置き換える。

| 規則 | 違反の種類 | 防ぐ故障 |
| --- | --- | --- |
| モジュールは、ほかのモジュールの公開パッケージだけを import する | `private-import` | 非公開の実装を直接参照する変更を拒否する |
| モジュール単位の import 依存は循環しない | `module-cycle` | 異なる内部パッケージを経由するモジュール間の相互参照を拒否する |
| 共有ライブラリはモジュールに依存しない | `shared-dependency` | 共有ライブラリを経由して、モジュールが依存を宣言せずに別のモジュールへ到達する |
| モジュールと共有ライブラリは組み立て地点に依存しない | `composition-import` | 結線用の例外を業務処理への迂回路として使う |
| `domain` は時刻、乱数、OS、ネットワーク、データベースを直接使わない | `domain-effect` | 計算の結果をテストで固定できない（DDD 由来の規則ではないので変更しない） |
| モジュールの sqlc クエリは、ほかのモジュールが所有するテーブルへ書き込まない | `table-write` | 二つのモジュールが同じテーブルの不変条件を別々に保とうとし、片方の変更がもう片方の保証を破る |

この項目では、公開範囲と非循環に加えて必要な、モジュールの組ごとの禁止条件を特定できていないため、辺の許可リストを維持しない。
許可リストも宣言と適合を検査する有効な仕組みではあるが、境界を選ぶ判断は別途必要である。
特定の組の依存が製品の保証を破ると分かった場合は、その保証を根拠に禁止条件を追加する。
公開パッケージを経由した非循環の依存だけで、意味上の独立性を保証したとは扱わない。

`shared-dependency` は、従来の `shared-detour`（モジュールから `shared` を経由して別のモジュールへ到達する経路）を、原因である `shared` 側の import として一度だけ数える。
従来の方式は同じ import を到達元のモジュールの数だけ数え、違反の数が原因の数を表さなかった。

依存グラフは本番の `.go` から抽出し、`_test.go` は循環の集計に含めない。
テストを含む `internal/` のアクセス制限は Go のビルドとテストで検証する。
`domain` と `usecases` の外向き依存の禁止、起動設定の読み取り場所、フロントエンドからバックエンドへの import の禁止は、現在の検査を維持する。

### テーブルへの書き込みの検査

`table-write` は、`sqlc.yaml` が宣言するクエリ入力を対象に、SQL が明示的に書き込むテーブルとデータベース設計の所有モジュールを照合する。
配置はモジュールの `db_postgres` と共有ライブラリの両方を扱い、設定に加えた新しい入力も自動的に対象へ入る。
所有が「共通基盤」のテーブルは共有ライブラリだけが書き込め、共有ライブラリはモジュールのテーブルへ書き込めない。
組み立て地点を SQL の書き込み検査の例外にはしない。

抽出は SQL の構造に従い、`INSERT`（`ON CONFLICT DO UPDATE` を含む）、`UPDATE`、`DELETE`、`TRUNCATE`、書き込みを含む CTE の全対象を扱う。`MERGE` は、解析器が構文木へ変換しないため入力診断として拒否する（後述の「着手時の棚卸し」）。
コメントと文字列中の単語、別名、引用識別子、スキーマ修飾を区別する。
未対応の構文、解決できないテーブル、所有者の欠落や重複は、違反がないものとして通さず抽出の診断として失敗させる。
単語の正規表現だけではこの検査を実装しない。
利用する解析器と対応構文は、T001 の棚卸しでリポジトリの入力を解析できることと既存の依存の再利用可否を調べ、実装前に記録する。

この検査は SQL に書かれた直接の対象を判定する。
外部キーの cascade、トリガー、関数の呼び出し、`//sql:raw` の動的な SQL による書き込みは保証しない。
読み取りもこの項目では拒否しないため、SQL の結合による別モジュールの保存表現への依存は残る。
これらは境界選択の入力に含め、既存の `check-raw-sql` を維持し、未検査の経路を棚卸しに残す。
検査の説明と出力には対象範囲を表示する。

現在のデータベース設計には、Application によるプロトコル設定の結び付け、IdManagement による CSV のパスワード履歴、監査、ジョブへの書き込みが記録されている。
これらも `table-write` として検出し、現在の具体的なクエリと対象だけを負債台帳へ移す。
理由には原子性を定める仕様または設計の参照を付け、モジュールの対全体を許可する例外にはしない。
公開操作を別のトランザクションで呼ぶだけでは、この負債を解消したことにしない。

### 公開範囲と `internal/`

非公開実装の配置は Go の `internal/` とする。
Go ツールチェーンはその親のディレクトリの外からの import を拒否する。
ただし、外側に残したパッケージの公開目的や移行の完了は判定しないため、責務表と照合する検査を併用する。

モジュールの最終形は次のとおりとする。

- `backend/<モジュール>/`：`module.go` を置くルートパッケージ。組み立てと HTTP ルートの登録を組み立て地点へ公開する。ほかのモジュールには公開しない。
- 公開パッケージ：ほかのモジュールが使う型と操作、ほかのモジュールが実装するポート。`internal/` の外に置き、責務表の公開パッケージ列へパッケージのパスを列挙する。
- `backend/<モジュール>/internal/`：それ以外のすべて（ユースケース、アダプター、内部の型）。

組み立て地点からの import は、ルートパッケージと宣言した公開パッケージに限る。
結線に必要な公開ポートと型は扱えるが、現在 `server_http` が `handlers_http` を直接 import する結線はルートパッケージの操作へ移す。
`internal/` はモジュールの配下全体から見えるので、機能スライスどうしの分離は保証しない。
機能スライス間の規則は、この項目では追加しない。

移行中は、責務表の公開方式を `legacy` または `internal` として明示する。
この項目では全モジュールを `legacy` とし、ディレクトリの有無だけでは方式を切り替えない。

| 公開方式 | 公開パッケージの判定と検査 |
| --- | --- |
| `legacy` | 現在の `domain` または `ports` の区画を含むパッケージ。`internal` 配下は含めない。組み立て地点からの既存の直接 import は移行期間だけ許す |
| `internal` | 責務表に列挙したパッケージだけ。外側の本番パッケージはルートか公開パッケージでなければ拒否する。組み立て地点にもこの制約を適用する |

公開パッケージは完全なパスで照合し、列挙したパッケージの配下を自動的には公開しない。
存在しないパッケージと `internal/` 配下の公開宣言は拒否する。
`internal` へ切り替える項目は、外側のパッケージの全分類、利用元の変更、組み立て地点の結線、Go のビルドとテストの成功を示す。
移行完了後に削除できるのは `legacy` の命名による公開判定であり、公開目的と外側に残る実装を検査する規則は残る。

### 境界を選ぶ判断手順

境界を守る検査と、境界を選ぶ手順を分ける。
配置と依存の変更では、次の順に入力をそろえ、候補を比較する。
複数の規則が該当するときは、すべての制約を満たす必要がある。

1. 変更する要求、不変条件、用語の意味を仕様の参照で特定する。
   既存の要件 ID の接頭辞は現在の担当を引く入口として使うが、境界変更を禁じる根拠や、新しい要求の担当を決める根拠にはしない。
2. 状態とその更新元を調べ、直接 SQL、ポート越しの更新、cascade、動的 SQL、トランザクションの開始と確定、イベントと通知の呼び出しを記録する。
   import グラフと実行時の作用の流れは別々に扱う。
3. 隠す設計判断を具体的に挙げる。
   保存表現、正規化規則、外部プロトコルの変換などについて、呼び出し側が知る必要のある条件と、内部に閉じられる条件を分ける。
4. 下表の制約を適用し、現状を維持する案と、必要な範囲の変更案を比較する。
   制約を満たす候補がなければ、制約を外すための宣言変更やポート追加で通さず、要求と担当の見直しへ戻る。
5. 残る候補を変更シナリオで比べる。
   実際に発生した変更または今回の要求が生む変化を入力とし、各案で変更する実装、利用側、契約、検証範囲を列挙する。
   同じ保証を保つ候補の間で、公開する内部知識と利用側への波及を減らし、不要なポート、型、設定を増やさない案を選ぶ。
6. 入力不足、相反する利点、または保証を変え得る未決事項が残れば、候補と判断に必要な問いを利用者へ示す。
   新しい業務概念の意味、原子性や認可の保証はエージェントが推測して確定しない。

| ID | 入力の事実または要求 | 制約と候補の絞り込み |
| --- | --- | --- |
| D1 | 既存の仕様と一つの状態所有者の責務を拡張する | まずそのモジュールを候補にする。編成だけを行う処理と状態の更新は分けて配置できる |
| D2 | 所有者が異なる状態を更新する | 各所有者に不変条件の検証と更新を残す。編成する側には、必要な操作、拒否、作用の契約を公開する。保存型や任意 SQL を公開して代用しない |
| D3 | 別モジュールの非公開処理が必要になる | 必要な振る舞いを公開操作で表せるか、現在の公開操作の合成で足りるか、そもそも担当が正しいかを比較する。非公開関数をそのまま公開することを既定にしない |
| D4 | import の循環ができる | 操作を要求する側が必要最小限のポートを定義し、実装する側が従い、組み立て地点で結ぶ案を比較する。実行時の再入と作用の循環、失敗時の順序、原子性を別途確認する |
| D5 | 複数のモジュールが同じ技術的な規則を必要とする | モジュールの型も業務上の意味も必要としない場合に共有ライブラリを候補にする。型名を文字列へ変えただけでは条件を満たさない |
| D6 | 提供側の表現を利用側のポートへ変換する | 利用側が変換の意味を所有する。提供側を import する具体アダプターは利用側へ置くか、D4 のために結線側へ置く。依存の向きだけから意味の所有者を決めない |
| D7 | 複数の状態の部分的な確定を禁止する要求がある | 原子性を定める仕様と失敗例を参照し、参加する更新、トランザクションの所有者、再試行、コミット後の通知を示す。モジュール数や Aggregate 数から原子性を決めない |
| D8 | 新しいモジュールを作る、または分割、統合する | 隠す判断、状態と契約の担当、独立して変えたい変更シナリオを示す。import、SQL、作用の流れ、利用側への波及を比較し、履歴があれば共変更を補助に使う |

新しいモジュールを作ることと、新しい状態の一貫性境界を作ることは別の判断である。
同じトランザクションに参加することだけでモジュールを統合せず、import を非循環にすることだけでモジュールを分割しない。

### 判断の記録と実例

境界に関わる work item の設計に、入力の参照、適用した D1〜D8、候補ごとの制約への適合、変更シナリオの波及、採否と理由、残る仮定を書く。
既存の設計節を使い、全モジュールの判断を独立した台帳へ複製しない。
境界を変えない局所変更には、この比較記録を求めない。
手順を適用する変更は、モジュールの追加、分割と統合、公開範囲の拡大、モジュール間の依存の追加、テーブル所有者または組み立て地点の変更とする。
`AGENTS.md` と `new-work-item`、`implement-work-item`、`update-design` の既存スキルから、担当する設計文書とこの適用条件を参照する。
スキルへ決定表を複製せず、設計文書を判断基準の一次情報とする。

本項目では、少なくとも次の実例に手順を適用し、単なる改名でないことを確かめる。

| 実例 | 適用する制約 | 記録する判断 |
| --- | --- | --- |
| 解決済みのテナントの受け渡し | D1、D3、D5 | Tenancy の意味を保つ公開契約と、`shared` へ移す案を比較する |
| CSV の確定と監査、ジョブの投入 | D2、D7 | 同じトランザクションに参加する契約を示す。別々のコミットになる案を除外する |
| `UserMutationCommitter` の結線 | D4、D7 | import の向きと実行時の更新の流れを別々に示し、原子性がどこで保証されるかを確認する |
| 同じ文字列型を使うが別の正規化規則を持つ処理 | D5、D8 | 型だけでは共有可能と判定せず、規則の意味と変更理由を比べる |
| 所有者と原子性が未確定の新しい要求 | D1、D2、D7、D8 | 不足する入力と相談する問いを示す。既存の要件 ID や共変更の最大値から担当を決めない |

実例の期待結果は、必ず一つの境界案が出ることではない。
同じ資料から制約、除外する案、相談が必要な条件を再現できることを確認する。

### 共変更レポート

`mise run report-change-coupling` は、Git の履歴から、同じコミットで変更されたモジュールの組と回数を出力する。
既定は `HEAD` から first-parent でたどる直近 500 コミットとし、基準 revision、件数、広範囲のコミットを除く閾値を引数で変えられる。
各コミットは第一親との差分を一度だけ数え、ルートコミットは空の木との差分とする。
マージコミットは第一親との差分を数え、同じ取り込みに含まれる枝のコミットを重ねて数えない。

対象ファイルは、現在の責務表に属するモジュール配下の本番 `.go`（生成物と `_test.go` を除く）と sqlc の SQL 入力に限る。
文書、整形の設定、共有ライブラリ、組み立て地点の変更をモジュールの共変更へ混ぜない。
改名は旧パスと新パスの双方を現在の割り当てで照合し、同一コミット内のモジュールは重複を除く。
現在の割り当てで解決できないパスは推測せず、未分類の件数として出す。
六つ以上のモジュールを変えるコミットは既定で除くが、その閾値、除外件数、除外コミットの ID を表示する。
除いたコミットは組の共変更数と各モジュールの変更数の双方から除く。

出力は revision、走査条件、対象と除外の件数、組ごとの `n(A)`、`n(B)`、`n(A,B)`、`n(A,B)/n(A)`、`n(A,B)/n(B)` とする。
割合は各モジュールが変わったとき相手も変わった割合であり、分母が小さいケースを生の件数で見分けられるようにする。
同じ revision と引数で同じ並びの出力を返し、履歴不足は対象件数とともに示す。

このレポートは合否を判定しない。
D8 で変更シナリオを探す補助として、条件と件数を work item に引用する。
同じコミットに入ることは同じ変更理由を証明せず、一括整形や作業のまとめ方でも増える。
共変更が少ないことも独立性の証明にはしない。
履歴がない新しいモジュールは、今回の要求に基づく変更シナリオで比較できる。
`mise run verify` には含めない。

### DDD 由来の規則の採否

| 現在の規則 | 判断 | 置き換え先と理由 |
| --- | --- | --- |
| Context Map の許可辺から import の可否を導く | 廃止 | 公開範囲、非循環、共有と結線の制約へ置き換える。個別の禁止条件が必要になれば保証を根拠に追加する |
| 関係ラベル（OHS/PL、C/S、ACL）と Supplier、Customer の用語 | 廃止 | 判定に使われていない |
| Subdomain の区分（`Core`、`Supporting`、`Generic`）と区分の検査 | 廃止 | 下の三行へ分解する |
| `Generic` では確立した実装へ委ねる | 全モジュールへ一般化 | 暗号、署名、プロトコルの解析など、確立した実装がある処理は自作しない。区分によらず成り立つ |
| `Core` では `decisions.md` と `internals.md` を厚くする | 既存の規則へ統合 | コードから復元できない機構があるときに `internals.md` を書くという既存の規則で決まる |
| `Core` と非 `Core` のどちらが翻訳するか | 意味の所有と依存の制約から決める | D6 に従い、利用側が変換を定義する。結線用アダプターの配置も比較する |
| ACL の置き場所は Context Map が依存を許す側 | 置き換え | D4 と D6 の制約を併用する |
| 公開言語は `domain` と `ports` | 移行期間だけ維持 | 最終形は宣言した公開パッケージ。用語の定義と意味は残す |
| `shared` を経由した到達も Context Map の規則で判定する | 置き換え | `shared-dependency` |
| 1 回のトランザクションが変更する Aggregate は 1 つ | 置き換え | 原子性を定める要求と D7 から更新範囲を決める。単回消費や削除の既存の保証は維持する |
| Aggregate の語と、Repository を Aggregate root 単位に置く規則 | 維持 | 状態の一貫性の境界を表す語として残す。`Save` の型は調査の入口であり、その型が Aggregate か、境界が妥当かは不変条件と仕様で判断する |
| `domain` の作用の禁止 | 維持 | DDD 由来ではない |
| イベントのエンベロープと公開項目の語彙 | 維持し、用語だけ改名する | `check-event-contract` が検査している |
| 境界の引き直しで Event Storming を参照する | 作業手順を置き換え | D1〜D8 と変更シナリオの比較を使う。イベントや用語を調べること自体は維持する |

旧分類の違反は、次のように新しい種類へ移す。
違反 ID が消えることと設計上の問題が解消したことは区別し、移行の前後の種類ごとの件数を完了の節に記録する。

| 旧分類 | 新しい扱い |
| --- | --- |
| `private-import` | `legacy` では従来の判定を残し、`internal` 配下を公開扱いしない |
| `undeclared-context-edge` | 違反ではなくなる。同じ import が非公開パッケージへ向かうなら `private-import` として、循環を作るなら `module-cycle` として残る |
| `context-cycle` | `module-cycle` へ改名する。集計の単位は変わらない |
| `shared-detour` | `shared-dependency` として、原因の `shared` パッケージとモジュールの組ごとに数え直す |
| `domain-effect` | 変更しない |
| なし | `table-write` を新しく台帳へ載せる |
| なし | `composition-import` を新しく検査し、既存分があれば台帳へ載せる |

`context-cycle` が `module-cycle` へ変わるだけなら、循環を解消した件数はゼロとして記録する。
許可辺の廃止によって消える ID は「規則の撤去」、原因の import や書き込みを変更して消える ID は「実装の解消」として区別する。

### 負債の増加検査の移行

現在の `boundary-debt-ratchet.ts` は基準 revision と現在の台帳の ID を直接比べるため、改名した ID と新しい検査の既存違反をすべて追加とみなす。
台帳だけを作り直す移行では、このゲートを維持できない。

新しい検査は、基準 revision のソースにも現在と同じ規則を適用して基準違反を求める。
旧文書を読む互換処理は、責務表と所有 Context の旧表記を新しい入力へ変換し、既存モジュールの公開方式を `legacy` とする。
判定規則を旧式へ戻す互換処理は設けない。
追加は基準に存在しない具体的な違反 ID として拒否し、現在の台帳への書き足しで通らないようにする。
基準ソースや所有宣言を取得、解析できなければ失敗させる。

移行では、旧 ID、新 ID、分類変更または撤去の理由を完了記録へ残す。
`table-write` の ID は書き込むモジュール、クエリ入力のパス、クエリ名、操作、対象テーブル、書き込む列の正規化した集合から決める。
upsert は挿入と更新の双方の列を含め、列を省略した挿入はその revision のスキーマから解決する。
行の削除と切り詰めは、列を限定しない操作として識別する。
既存のクエリが別の列へ書き始める場合も、基準と異なる ID として拒否する。
値や WHERE 条件の意味が変わったことは ID だけでは検出できないため、製品の保証を固定するテストで検証する。
モジュールの組を丸ごと許す ID は使わない。
既存違反の基準 revision による受理、同じ差分で加えた import と書き込みの拒否、台帳だけに加えた存在しない ID の拒否を fixture で固定する。
移行のために CI の基準を現在の revision へ置き直したり、検査を一時的に無効にしたりしない。

### 用語の改名

| 現在の語 | 改名後 |
| --- | --- |
| Bounded Context、Context | モジュール |
| Context Map | 廃止 |
| 公開言語、Published Language | Go の import 可否は「公開パッケージ」、型、意味、拒否、作用などの約束は「公開契約」として書き分ける |
| Context 間イベント | モジュール間イベント |
| 所有 Context | 所有モジュール |
| Subdomain、サブドメイン（区分の意味） | 廃止 |

DNS のサブドメインなど、区分ではない意味の「サブドメイン」は改名しない。
Go の `context.Context` とテナントを運ぶ `context.go` は Go の語なので変えない。

この項目で改名するのは、次の節に挙げる一次情報文書と、この項目で変更する検査の識別子と出力文言である。
残りの文書は後続の改名項目が着手時に検索して扱い、完了時に用語の検査へ「Bounded Context」「Context Map」「Context 間」などの規則を追加する。
外部文献のタイトル、C4 の System Context、Go の `context.Context`、固定したパスと規範 ID、完了済みの作業記録は、置換と禁止の対象から除く。
分けるのは、方針の変更と機械的な置換を同じ差分に混ぜると、方針の変更をレビューで読み分けられなくなるからである。

### 検査の変更

- `tools/check/src/boundary-fitness.ts` は、責務表からモジュール、組み立て地点、公開方式と公開パッケージを読み、Mermaid の Context Map を読まない。
  違反の種類を `private-import`、`module-cycle`、`shared-dependency`、`composition-import`、`domain-effect`、`table-write` とする。
- `schema-tables.ts` は所有者を読み、`table-write` が sqlc の全入力と照合する。
  不明な所有者、未分類の配置、抽出不能な SQL は台帳で免除できる違反とは別の入力診断とする。
- `boundary-debt-ratchet.ts` は基準 revision のソースに新規則を適用し、移行後も新しい逸脱を拒否する。
- `subdomain-classification.ts` とそのテスト、`check-documents.ts` からの呼び出しを削除する。
- `report-change-coupling` を `mise.toml` に追加する。
  Git の読み取りは作用の境界に置き、コミットごとの変更ファイルの一覧から組と回数を数える計算は純粋関数としてテストする。
- 負債台帳を新しい種類で作り直す。
  既存項目の全理由の見直しは後続の棚卸しが行うが、新しい `table-write` と `composition-import` には本項目で具体的な理由と参照を書く。

| 案 | 判断 |
| --- | --- |
| DDD の用語を残し、機械検査の入力だけを整理する | 採用しない。実装の境界を指す語とモデルの意味の境界を指す語が同じまま残る。ただし、用語と不変条件を仕様に残す役割は引き継ぐ |
| 改名せず、Context の定義だけを機械的なものに置き換える | 採用しない。Go の `context.Context` との衝突と、DDD の Bounded Context としての読みが残る |
| Context Map の許可辺を残し、関係ラベルだけ外す | 今回は採用しない。維持する個別の禁止条件を特定できておらず、公開範囲と非循環の検査に加える効果を説明できない |
| モジュールに層番号を宣言し、下位への依存だけを許す | 採用しない。非循環より強いが、層の割り当てという新しい判断が増える |
| 公開範囲を `domain` と `ports` の命名規則のまま維持する | 採用しない。公開するかを層の名前で決めることになり、コンパイラの拒否も得られない |
| パッケージごとに公開を宣言するディレクティブを置く | 採用しない。公開宣言は既存の責務表に集める。非公開のアクセス制限は `internal/`、外側に残るパッケージの意図は検査で照合する |
| `internal/` の存在と、その外側をすべて公開とする | 採用しない。部分移行で検査が緩み、組み立て用のルートと業務用の公開契約を区別できない |
| 依存グラフや共変更からクラスタリングし、境界を自動決定する | 採用しない。候補を作る補助にはなるが、現在の結合とコミットの分け方を再生産し、意味、原子性、将来の変更理由は確定できない |
| すべての判断を独自の設計言語と全量の台帳へ記述する | 採用しない。意味上の判断は残り、コードと同じ情報を同期する負担が増える。既存の仕様と責務表、変更単位の比較記録を使う |
| 依存の許可を YAML の台帳として別に持つ | 採用しない。以前の全量の依存台帳の撤去と同じ理由で、正本と台帳が独立に古くなる |
| 一括で全文書を改名し、全実装を `internal/` へ移す | 採用しない。方針の変更と機械的な置換、パッケージの移動を一つの差分に混ぜ、レビューで読み分けられない |
| 検査を廃止してレビューだけに委ねる | 採用しない。公開範囲、循環、書き込みの所有は機械で判定できる |

### 着手時の棚卸し

着手時の revision は `8b12057ef71219925da2531bd83377278559799b` である。
このとき台帳は 180 項目、510 ID（`private-import` 111、`undeclared-context-edge` 240、`context-cycle` 66、`shared-detour` 73、`domain-effect` 20）だった。

| 対象 | 観測した事実 |
| --- | --- |
| sqlc の入力 | `sqlc.yaml` の 33 項目、73 ファイル。すべてディレクトリ指定で、スキーマは `infra/schema/postgres.sql` 一つ。モジュールの `db_postgres` 31 項目、共有ライブラリ 2 項目（`shared/ratelimit/db_postgres`、`shared/security/salts_postgres`）、組み立て地点 1 項目（`cmd/idmagic-batch/internal/restorecheck/db_postgres`） |
| 所有者外の直接書き込み | 7 クエリ。データベース設計が記録していた 4 種類（Application のプロトコル設定の結び付け 3、IdManagement の CSV のパスワード履歴 1、監査 2、ジョブ 1）と一致し、記録のない書き込みはなかった |
| 未検査の作用経路 | `//sql:raw` 9 箇所、`ON DELETE CASCADE` 80 箇所、トリガー 1 個（`tenants` の挿入で SAML のデフォルトのプロファイルを作る）。データベース設計の「所有と書き込みの境界」に限界として記載した |
| 組み立て地点への依存 | モジュールと共有ライブラリから組み立て地点への import はなかった |

SQL の解析には、既存の依存である sqlc 1.31.1 の `sqlc parse --dialect postgresql` を使う。
内部で PostgreSQL の構文解析器を使うので、コメント、文字列、引用識別子、スキーマ修飾、別名を区別できる。
新しい npm の解析器（pg_query の WebAssembly 版など）は、置き換えられる自作コードが同じでも推移依存と配布物を増やすので採らない。
出力の JSON はノードの型名を持たないので、文の種類は sqlc の `ast` パッケージの型だけが持つフィールドの組で見分ける。
`MERGE` は sqlc が構文木へ変換せず空のオブジェクトになるので、入力診断として拒否する。
sqlc は `MERGE` を含むクエリから型付きのコードを生成できないので、現在のクエリ入力に `MERGE` は現れない。
起動に一回あたり約 0.5 秒かかるので、全ファイルを一回の呼び出しへ連結し、文の終了位置のバイト位置でファイルへ振り分ける。

列を省略した `INSERT` は、同じ revision のスキーマの `CREATE TABLE` を同じ解析器で読んで列を解決する。
基準 revision の比較は、`git archive` で境界検査の入力（`go.mod`、`backend`、`infra/schema`、`sqlc.yaml`、責務表、データベース設計）だけを一時ディレクトリへ取り出し、現在と同じ解析を行う。
旧文書の互換処理は二つに限る。
旧い責務表（`仕様上の Context | Subdomain | ...`）は全モジュールを `legacy` とし、組み立て地点を新しい表の初期値（`backend/cmd`、`server_http`、`testing_stack`）とする。
旧い所有の列（`所有 Context`）は所有モジュールとして読む。

### 判断手順の適用

境界を選ぶ判断手順を五つの実例へ適用した。
どれも、この項目では実装を変えず、記録した判断を後続の項目が使う。

**解決済みのテナントの受け渡し（D1、D3、D5）。**
`backend/tenancy` のルートパッケージ（`context.go`）は解決済みの `domain.Tenant` を `context.Context` に載せ、`TenantID` はテナントのない文脈で panic する。
41 個の `private-import` がこのルートパッケージを指し、`shared/http/support_http` などが `shared-dependency` として Tenancy に依存する。
D5 の条件で共有ライブラリへ移す案は除外する。
値の型が `tenancy/domain.Tenant` であり、テナントのない文脈を default テナントへ落とさないという規則がテナント分離の保証そのものだからである。
ID だけを文字列で運ぶ形にしても、規則の意味は Tenancy に残るので D5 の「型名を文字列へ変えただけ」に当たる。
D1 により状態の所有者である Tenancy を担当とし、D3 により非公開の関数をそのまま公開するのではなく、取得と付与の操作を公開契約として公開パッケージへ置く案を採る。
これはテナントの公開言語の項目の残りの作業と一致する。

**CSV の確定と監査、ジョブの投入（D2、D7）。**
CSV の取り込みは、確定と同じトランザクションで監査イベントを記録し、グループの取り込みでは調整ジョブを投入する。
IdManagement が `audit_events` と `jobs` へ直接書く現状は `table-write` として台帳に残る。
Audit と Jobs の公開操作を別のトランザクションで呼ぶ案は、D7 により除外する。
確定した取り込みに監査記録やジョブが欠ける部分的な確定が起きうるからである。
残る候補は、Audit と Jobs が「呼び出し側のトランザクションに参加して追記する」操作を公開契約として公開し、SQL と不変条件の検証を所有者に残す案である（D2）。
トランザクションの所有者は IdManagement の取り込みのコミットであり、Audit と Jobs の操作は確定を行わない。
この案はポートの追加を伴うので、実装は後続の棚卸しの項目で D2 と D7 の記録とともに判断する。

**`UserMutationCommitter` の結線（D4、D7）。**
import の向きは IdGovernance から IdManagement である。
IdGovernance は `idmanagement/user/ports` の `UserMutationCommitter` を実装し、その PostgreSQL アダプターは `idmanagement/user/db_postgres` の `SaveUserTx` を import する（`private-import`）。
実行時の流れは逆向きで、IdManagement のユースケースがポートを呼び、IdGovernance のアダプターが一つのトランザクションを開いて User の保存とワークフローの実行の生成を確定する。
原子性を保証するのは IdGovernance のアダプターのトランザクションであり、`users` への SQL は IdManagement の sqlc クエリに残るので `table-write` にはならない。
D4 の形（要求する IdManagement がポートを定義し、IdGovernance が実装し、組み立て地点で結ぶ）はすでに満たしている。
残る問題は D3 の非公開の import であり、IdManagement が「呼び出し側のトランザクションで User を保存する」操作を公開契約として公開する案が CSV の例と同じ形になる。

**同じ文字列型で正規化規則が異なる処理（D5、D8）。**
OAuth2 のデバイスフローの `NormalizeUserCode` と、Authentication の回復コードの `normalizeRecoveryCode` は、どちらも利用者が入力したコードを文字列から文字列へ正規化する。
前者は大文字にして英数字以外をすべて除き、後者は小文字にして空白とハイフンだけを除く。
型が同じでも規則が異なり、変わる理由も RFC 8628 のユーザーコードの文字集合と回復コードの表示形式で別なので、D5 の共有ライブラリの条件を満たさない。
現状の配置を維持する。

**所有者と原子性が未確定の新しい要求（D1、D2、D7、D8）。**
例として「管理者が User を停止したとき、その User のセッションと API トークンを同時に失効させる」という要求を置く。
D1 の担当の候補は、User の状態を持つ IdManagement、セッションを持つ Authentication、トークンを持つ OAuth2 と ApiTokens にまたがる。
D7 の入力である「停止と失効の部分的な確定を禁止するか」が仕様にないので、同じトランザクションにまとめるか、停止の確定後に失効を再試行可能な形で行うかを決められない。
既存の要件 ID の接頭辞や共変更の最大の組（IdManagement と OAuth2 の 6 回）からは担当を決めない。
この場合の出力は、利用者への問い（部分的な確定を禁止するか、失効までの遅延をどこまで許すか、失効の失敗を停止の失敗として扱うか）である。

## 検証

検査の変更は `mise run test-tools-file -- <テストファイル>` で確かめる。
次の各例で、受理と拒否が規則どおりであることを fixture で固定する。

| 例 | 期待する結果 |
| --- | --- |
| 未移行のモジュールが、ほかのモジュールの `ports` を import する | 受理 |
| 未移行のモジュールが、ほかのモジュールの `usecases` を import する | `private-import` |
| `legacy` のモジュールに `internal/` を一つ作り、外側の `usecases` を別モジュールから import する | 引き続き `private-import` |
| `internal` のモジュールの宣言済み公開パッケージを import する | 受理 |
| `internal` のモジュールの未宣言パッケージを外側に残す、または公開宣言が存在しないパッケージを指す | 宣言の診断として拒否 |
| 別モジュールが組み立て用のルートを import する | `private-import` |
| モジュール、共有ライブラリが組み立て地点を import する | `composition-import` |
| 二つのモジュールが互いの公開パッケージを import する | `module-cycle` |
| 公開範囲と非循環を満たし、旧 Context Map に辺がない依存 | 受理。撤去した規則に依存しない |
| 組み立て地点が `legacy` の非公開パッケージを import する | 移行期間は受理 |
| 組み立て地点が `internal` の公開パッケージとルートだけを import する | 受理 |
| 組み立て地点または別モジュールが他モジュールの `internal/` を import する | Go のビルドが拒否。小さな fixture の専用 mise タスクで確認 |
| 共有ライブラリがモジュールを import する | `shared-dependency`。到達元のモジュールの数にかかわらず一件 |
| モジュールの sqlc クエリが、ほかのモジュールが所有するテーブルへ `UPDATE` する | `table-write` |
| モジュールが共通基盤へ書く、共有ライブラリがモジュールのテーブルへ書く | `table-write` |
| 自分が所有するテーブルへ書く、共有ライブラリが共通基盤へ書く | 受理 |
| 書き込み CTE、複数文、upsert、複数対象の `TRUNCATE` | 全対象を照合。引用識別子、修飾、別名を解決 |
| `MERGE` | 解析器が構文木へ変換しないので入力診断として拒否 |
| コメントまたは文字列に書き込み文のような語がある | 書き込み先に数えない |
| 同じクエリが、そのテーブルを `SELECT` するだけである | 受理 |
| 所有者が欠ける、重複する、未知の名前を使う、入力の配置が分類不能 | 入力診断として拒否 |
| 解析できない SQL、解決できない対象テーブル | 入力診断として拒否 |
| 旧形式の基準 revision に存在した循環と直接書き込みだけを新 ID へ移す | 増加検査は受理し、基準との対応を出す |
| 同じ移行差分で新しい違反を加え、台帳にも書き足す | 増加検査は拒否 |
| 既存の所有者外の書き込みが別の列へも書き始める | 新しい `table-write` の ID として増加を拒否 |
| 台帳だけへ存在しない違反 ID を足す | 台帳の照合が拒否 |
| SQL の入力を別のディレクトリに追加して sqlc に宣言する | 所有者を照合し、対象から漏らさない |
| 既存の `domain-effect`、層の外向き依存、起動設定の違反 | 従来どおり拒否または既存負債として報告 |

共変更は、単独変更、二者の共変更、広範囲の除外、改名、マージ、ルートコミット、履歴不足を含む小さな履歴で件数と双方の分母を確かめる。
純粋な集計の fixture に加え、Git からの差分抽出の結線を一つの統合テストで確認する。
Go の変異器は TypeScript を対象にしないため、変更耐性は、所有者の照合を外す、公開方式の既定を緩める、基準の解析失敗を成功へ変えるという配線と既定分岐の故障注入で検証する。
条件演算子を手で書き換える変異を、その代用として列挙しない。

文書と検査の変更後は、`mise run check-boundaries`、`mise run check-boundary-debt-ratchet -- <着手時に記録した基準revision>`、`mise run check-terminology`、`mise run check-links`、`mise run check-work-items`、`mise run check-agent-guidance`、`mise run check-schema-tables` を実行する。
文書の派生表示は `mise run spec-render` と `mise run check-rendered-docs` で確認し、最終確認には `mise run verify-spec` を使う。

## リスク

- 許可辺の廃止で、検査が拒否していた依存の一部が受理されるようになる。
  新規則への適合と設計上の妥当性を区別し、受理に変わった ID と理由を残す。固有の禁止条件が見つかれば要求を根拠に検査する。
- 設計方針の変更を、テナント分離、認可、原子性、失効などの保証を弱める理由にしない。
  振る舞いの変更が必要と分かったら、規範要素を参照する別項目へ分ける。
- 改名を一部の文書に限るので、後続の改名項目が完了するまで、文書に「Context」と「モジュール」が混在する。
  後続項目を本項目の完了と同時に起票し、用語の検査の規則でその完了を確かめる。
- `table-write` は動的 SQL、cascade、トリガーと関数の作用を保証しない。
  検査の限界と未検査の経路を明示し、原子性のある既存の書き込みを独立コミットへ分けない。
- 宣言の公開範囲や組み立て地点を広げれば、形式上の違反を消せる。
  宣言の変更にも D1〜D8 を適用し、具体的な契約、隠す判断、利用側への波及をレビューする。
- ID の改名と新規則の既存負債で、増加検査が機能しなくなるおそれがある。
  基準ソースにも新規則を適用し、移行差分に追加した違反の拒否を完了条件にする。
- 共変更レポートの数値を、境界の正しさの証明として扱う誤用がありうる。
  レポートを合否に使わず、変更シナリオを調べる補助に限る。条件、分母、履歴不足を表示する。
- 判断手順を設けても、境界の最適解や AI の実装品質の改善は機械検査だけで証明できない。
  本項目の完了条件は、検査の故障検出と実例への手順の適用とする。品質改善の実証は将来の変更事例で評価する。
