# テストが具体例を被覆したと主張する書き方を 1 つに定め、検査をそれだけに合わせる

## Motivation

[[wi-559-back-oauth2-remaining-examples-with-tests]] の最初の規則群を消化する 1 セッションで、「テストが名指したのに台帳に残っている」という指摘を 3 回受けた（`EX-OAUTH2-003-04`、`EX-OAUTH2-001-01`、`EX-OAUTH2-005-07`）。3 回とも被覆したつもりは無く、「この id は別の記録が扱う」と散文に書いただけだった。

`citedNormativeIds` は、テストの原文に宣言済みの id が現れれば被覆と数える。**注記と散文の言及を区別しない。**

区別できない理由は照合の甘さではない。**書き方を 1 つに決めていないからである。** `SPECIFICATION_FORMAT.md` は id の形式を定めるが、テストがどう被覆を主張するかはどこにも書かれていない。work item の Scope が毎回 `// EX-<CONTEXT>-NNN-MM: <この具体例の何を固定しているか>` と書いてきただけで、それは指示であって規約ではなく、検査も掛かっていない。

その結果、現物は 5 通りに散っている。

```
// EX-A: 本文                                  ← 事実上の正典
// EX-A 本文                                    ← コロンなし
// REQ-B / EX-A: 本文                           ← 前置きあり
// scenario EX-A, EX-B, EX-C,                   ← 前置き語ありコロンなし
// 主要ユースケース追跡: REQ-A、REQ-B。          ← ファイル冒頭の規則単位の追跡
// … 確かめる (EX-A、EX-B)。                     ← 文中
```

書き方が決まっていれば、最後の 1 つだけが被覆でないと機械が言える。決まっていないので、どれも同じに見える。

## Scope

- **正典を 1 つ定める。** テスト関数の直上へ `//spec:covers <id>[, <id>]: <何を固定しているか>` を置く形とする。
- 正典を [仕様先行の開発ワークフロー](../../docs/development/specification-first-workflow.md) に書く。`AGENTS.md` から 1 行で指す。`implement-work-item` スキルの記述も正典を指すようにする。
- コード中の文字列リテラルによる名指し（表駆動テストの `{id: "EX-A"}`）は、曖昧さが無いので正典に含める。
- `citedNormativeIds` を正典だけに合わせる。
- **既存の注記をすべて正典へ寄せる。** 同じ id を名指したまま書式だけを変える。
- **被覆と数えられる id の集合が、変更の前後で一致することを観測する。** 件数ではなく集合を比べる。入れ替わりは件数では見えない。
- 被覆の指摘へ、どのファイルのどの行が名指しているかを載せる。正典に寄せたあとも、台帳から外す作業では「どのテストか」を毎回探すことになるためである。

## Out of Scope

- Gherkin の実行可能化。測って取り下げた。理由は Design に書く。
- 被覆の表明を `covers.Example(t, …)` のようなコード上の呼び出しにすること。検討して取り下げた。理由は Design に書く。
- 具体例そのものの消化。[[wi-559-back-oauth2-remaining-examples-with-tests]] が持つ。
- `mise run spec-route` の出力改善。同じセッションで測った別の改善であり、被覆の意味を変えない。[[wi-568-spec-route-names-the-test-and-the-neighbourhood]] が持つ。
- 台帳から id を外す判断の自動化。
- **正典へ寄せた結果、被覆から外れる id が出た場合の台帳への追加。** `check-coverage-debt-ratchet` は台帳への id 追加を拒否する。外れたなら、それは元から被覆していなかったということなので、注記を正典で書き直して被覆させる。台帳へ逃がさない。

## Design

### 正典

```
//spec:covers <ID>[, <ID>]*: <このテストが当の具体例の何を固定しているか>
```

`//go:generate` や `//nolint:` と同じ Go の指示子の形である。散文がこの形に一致することは構文上ありえない。

- 指示子は `//spec:covers` の 1 語で、コメント記号の直後に置く。
- id は 1 個以上。区切りは `, `。規則 id を先頭に並べてもよい。
- 長い並びは区切りで行を終え、次のコメント行へ続けられる。
- コロンから先は人へ向けた説明であり、id は前半にしか置けない。

文字列リテラルによる名指しも被覆と数える。表駆動テストが `{id: "EX-A"}` の形で例を列挙する既存の書き方は、コメントではないので前置きの問題が起きない。

この形の下では、`// 台帳の EX-A は別の記録が扱う` も `// EX-A が要求する組み立てを示す` も被覆と数えられない。指示子が無いからである。**散文で id に言及することが安全になる。** これが目的である。

### 実行可能な Gherkin を採らない理由

`docs/contexts/*/scenarios.feature.md` は Markdown with Gherkin であり、`@cucumber/gherkin` が実際に解析している。ならば step 定義を書いて仕様そのものを実行するのが素直に見える。測って取り下げた。

| 測定 | 値 |
| --- | --- |
| 総ステップ数 | 4037 |
| 相異なるステップ | 2391 |
| 引用符とバッククォートをパラメータ化した後 | 2291 |

Cucumber の採算は、小さなステップ語彙が繰り返し使われることに依存する。ここは**具体例 757 件に対して step 定義が 2291 個**要る計算で、1 例あたり 3 個である。テストを直接書くより多い。日本語の叙述文が 1 文ごとにほぼ固有で、パラメータ化しても 100 件しか減らなかった。

加えて、観測は Go の単体、Go の HTTP、TS の 3 ランタイムに散っている。step 定義を 3 組に分ける必要があり、`EX-OAUTH2-001-01` のように `/token` と account API をまたぐ例が扱いにくい。そして step を照合器に合わせて書き直す圧力が規範文書へ掛かる。規範は人が読む一次情報源なので、その劣化は割に合わない。

**記法としての Gherkin は採用済みで、実行系だけを足さない**という現状は筋が通っている。

### コメントの正典から指示子へ進んだ理由

最初は「コメント内容の先頭が id の並びで始まり、コロンで終わる」という正典を採った。それでも取り違えは消え、`check-spec` は緑になった。しかし現物へ合わせるうちに、規則が 5 つの機微を抱えた。コメント先頭であること、コロン、`,` と `、` と `/` の 3 区切り、行をまたぐ並びの連結、そして `(optional)` のような採否括弧である。

この照合器の実装を 5 回やり直した。うち 1 回は、並びの要素を「id の形」で受けたまま文字列リテラルの照合にも同じ形を使い、`"Content-Type"` のようなリテラルまで cited へ入れた。宣言済み id の判定は変わらないので `check-spec` は緑のままで、**報告する被覆件数だけが 346 から 1407 へ嘘になった**。落ちる欠陥より、正しい数字と見分けがつかない数字を出す欠陥のほうが悪い。規則の複雑さが原因である。

指示子にすると規則は 1 つになる。`//spec:covers` は散文に現れないので、先頭かどうかもコロンの有無も判定に要らない。`//go:generate` と `//nolint:` があるので Go では見慣れた形でもある。

移行は、正典化を終えた後なら 1 回の機械的な置換で済んだ。実際には 3 巡かかっている。1 巡目は自前で組み立てた宣言済み id の一覧が検査のものと食い違って 155 件が漏れ、2 巡目は検査が出す「失われた id」を種にして 4 件まで縮み、3 巡目で `、` を perl の文字クラスへ入れたことによるバイト単位の分解に気づいた。**検査を種に使う 2 巡目のやり方が効いた。** 自前の一覧を正とせず、落ちたものを検査に教えてもらう。

### 被覆の表明をコード上の呼び出しにしない理由

`covers.Example(t, "EX-A", "何を固定するか")` のような呼び出しにすれば、id の存在も本文の非空も実行時に強制できる。採らなかったのは、テスト関数の中へ文を挿入する編集が 776 ファイルに及ぶのに対し、指示子はコメント 1 行の前置きで済み、曖昧さの除去という目的はどちらでも同じだけ達成されるからである。

## Risk Notes

- **移行で id を取り落とす。** 書式を変える過程で id を消せば、その具体例は静かに被覆から外れる。件数は 1 減るだけなので目視では気づかない。前後の集合を `comm` で両方向とも比べる。
- **正典が厳しすぎて、正当な注記を落とす。** 現物は 5 通りに散っている。落ちた分をすべて手で寄せるまで `check-spec` は赤のままになる。落ちた id の一覧を先に出し、1 件ずつ寄せる。
- **台帳へ逃がす。** 被覆から外れた id を台帳へ足せば検査は緑になるが、`check-coverage-debt-ratchet` が拒否する。拒否は正しい。外れたなら注記を書き直す。
- **ファイル冒頭の規則単位の追跡（`// 主要ユースケース追跡: REQ-A、REQ-B。`）の扱いを決めないまま寄せる。** これは 57 件ある。id を先頭へ出す形（`// REQ-A, REQ-B: 主要ユースケース追跡。`）へ寄せると決め、意味を変えないことを確かめる。
- **正典を決めたのに、次に書く人が知らない。** 文書とスキルの双方から指す。指示が届いていない場所に置いたのが、そもそもの原因である。
