# 外部で発見したエージェントを管理台帳と突き合わせる

外部の発見器が報告した未登録の主体を、未確認の `AgentObservation` として IdManagement に取り込み、管理者が管理済みの Agent と突き合わせる機能を追加した（REQ-IDMANAGEMENT-095〜102）。
取り込みは新しいスコープ `agent-observations:import` の API アクセストークンだけが呼べ、一覧は `agents:read`、確認、除外、再開は `agents:write` に分けた。
棚卸し（REQ-IDMANAGEMENT-094）は確認した観測だけを Agent に添え、未確認の観測は管理画面の棚卸しページに分けて表示する。

判断として、一意キーをテナント、`issuer`、`subject` にして観測元を含めず、トークンのローテーションで決定を失わないようにした。
候補は Workload binding と資格情報の束縛だけから一覧のたびに計算し、名前では結ばず、候補が一つでも自動で確定しない。
確認の状態は `agents` への `ON DELETE SET NULL` の外部キーで表し、Agent の削除と同じ確定で解除する。
観測の置き場所は、権威ある取り込みである Sourcing でも新しいモジュールでもなく、Agent の確認と同じ所有者の IdManagement とした。

重要な保証は、正式な組み立てからの受け入れテストが独立に観測する。
権限を付与しないこと、取り込みと確認の権限の分離、候補の配線、順序逆転の保持は、セッションの取り込み、未配線の照合、所有者の書き換え、順序の比較の除去を故障注入して検出を確かめた。
保存先の契約はメモリと PostgreSQL の両方で実行し、並行する確認は usecase で race 検出器を付けて確かめた。

確認した範囲の限界は次のとおりである。
ブラウザーの E2E は追加せず、画面はコンポーネントテストだけで検証した。
画面は各決定の最初の 100 件だけを表示し、それより後は API のカーソルでたどる。
PostgreSQL での実際の並行確認は単一の条件付き更新に頼り、同時実行では検証していない。
テナントの上限は助言ロックで守るが、発見器の網羅性は保証せず、見つからない主体は台帳に現れない。
