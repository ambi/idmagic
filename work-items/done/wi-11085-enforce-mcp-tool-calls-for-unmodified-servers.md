# 改修していない MCP サーバーの tools/call を実行前に認可する

改修していない MCP サーバーの手前に置く別配布の実行単位 `idmagic-mcp-gateway` を追加した。
2026-07-28 版の要求だけを解釈し、IdMagic の評価が許可した要求だけを、資格情報を除いて上流へ転送する。
バッチ、重複キー、ヘッダーの不一致、未知の方法は評価せずに拒否し、宣言のないツールは試行者を監査へ残すために評価して、結果によらず転送しない。

仕様は REQ-MCPGATEWAY-001 から 006 を追加し、REQ-OAUTH2-062 を変更した。
`ResourceAccessEvaluated` は、トークンと提示の証明が成り立つときだけ主体、Agent、代行の連鎖を持ち、常に `requestId` を持つ。
ゲートウェイのログとは評価の `X-Request-ID` で突き合わせる。
REQ-OAUTH2-063 の文言は変えず、公開 URL を `htu` にする経路を受け入れテストで確かめた。
配置は起票時の第一候補だった別の `go.mod` ではなく、DirectoryConnector と同じ同一 Go モジュールの別モジュールを採った。

検証は、実在の Go SDK v1.8.0 のクライアントとサーバーの間で製品の評価の経路を通す受け入れテスト、単体テスト、`FuzzInspect` の 20 秒の探索、8 種類の手動の故障注入である。
故障注入はすべて検出された。

確認の限界と残るリスクは次のとおりである。

- 本番の前段の TLS 終端、別の言語の MCP SDK、実際のエージェント製品との接続は確かめていない。
- 受け入れテストの評価の入口には、本番の組み立てと同じ要求 ID の処理をテスト側で加えている。
- `requires_approved_operation` の操作と mTLS に束縛したトークンは利用できず、安全側で止まる。
- 評価まで届かない要求と評価できない要求には主体が残らない。
- 上流へゲートウェイ以外から到達できる配置では執行を迂回できる。
- `insufficient_scope` の応答と配布の手順書は未実施である。
