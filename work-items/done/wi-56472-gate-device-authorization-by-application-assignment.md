# デバイス認可の承認も、アプリケーションの割り当てとサインインポリシーの関門を通す

デバイス認可の承認を、コードのクライアントと認証の文脈と要求元 IP を使う必須のアプリケーション関門へ通した。
未割り当て、無効、ポリシー違反と評価障害では承認状態を残さず、第二要素が必要なら認証後に元のコードへ戻って再評価する。
`spec-diff` の意味上の差分は REQ-OAUTH2-027 への関門と追加認証の追記だけで、HTTP の応答の形は既存の TypeSpec の範囲に保った。
OIDC のセッションとパスワード、SAML、WS-Fed、WS-Trust、ID-JAG、デバイス認可の7入口で許可と未割り当てと無効の拒否を確認し、拒否時の保存と発行の無作用、別テナント、期限、評価障害、追加認証後の割り当ての再評価も検証した。
実ブラウザーで拒否表示と割り当て後の承認からトークン取得までを確認し、追加認証の戻り先の配線漏れを手動注入して統合テストが検出することも確かめた。
未割り当ての既存利用者は割り当てが必要になる。
割り当て解除後のリフレッシュと CIBA の承認は対象外で、公開状態は unpublished のため告知断片は追加しない。
