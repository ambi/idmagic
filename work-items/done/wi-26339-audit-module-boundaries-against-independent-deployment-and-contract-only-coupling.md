# 別々に配布される実行単位と公開契約だけの結合を基準に加え、既存のモジュール分けを棚卸しする

規範仕様の差分はない。
境界の判断手順に D9 を追加し、配布先、更新する主体、バージョンのずれと公開契約を D1 より先に確認する順序にした。
別々に配布、更新する実行単位は別モジュールにし、相手の内部型を共有せず公開契約で結ぶ。
API、Worker、Batch のように同じサーバーの内部状態の契約に従うプロセスは、起動とスケーリングの違いだけでは分けない。
Sourcing の担当基準はサーバー内の取り込み経路に限り、利用者側の LDAP の読み取りと属性の対応付けは DirectoryConnector の担当（未実装）と明記した。
機能仕様の「扱わないもの」には担当または「提供しない」を書く規則を、仕様フォーマットに置いた。

棚卸しは着手時の責務表（`db340b166`）の全 22 行を対象にした。
妥当は「今回の基準ではモジュールの分割、統合を要しない」という判断であり、既存の機能の欠陥まで解消したことを示さない。
実行欄の API、Worker、Batch は同じサーバーのリリースと内部状態の契約に従い、実行場所が複数でも一つの責務を維持する。
全件の記録はこの要約に残し、現在状態の設計には要再設計の 5 件だけを既知のリスクとして残した。

| モジュール | 実行と配布 | 判定 | 隠す判断、依存と作用からの理由 |
| --- | --- | --- | --- |
| System | サーバーの各入口、別イメージのゲートウェイとブラウザー | 要再設計 | `frontend/` の表示と OIDC RP の判断を組み立て地点と宣言している。HTTP の利用と画面の責務を結線から分ける（wi-82793） |
| Tenancy | API とサーバー内の各呼び出し元 | 妥当 | テナント解決、設定と上限の判断を隠す。属性定義の保存は IdManagement に委ね、使用量は作成元のトランザクションに参加する。設定変更だけではプロトコルの実装を変えない |
| Jobs | API、Worker | 妥当 | リース、再試行とキューの保存を隠し、ジョブ固有の判断は登録する所有者のハンドラーへ残す。ジョブの追加で基盤の業務依存を増やさない |
| Seeding | 同じサーバーの Seed コマンド | 要再設計 | 生成、差分判定と保存の編成が `bootstrap/seeding.go` にある。結線から判断を移す（wi-43154）。保存と排他の是正は既存の wi-24943 が担当する |
| SigningKeys | API、Batch | 妥当 | 用途、テナントとローテーションの判断を隠し、署名器と公開鍵を提供する。JWK と XML の表現は利用側で変換する。鍵の提供元の変更はプロトコルの判断から分離できる |
| DataKeys | API、Worker | 妥当 | DEK の生成、ラップと再暗号化の進行を隠す。Jobs へ投入し、項目所有者の FieldMigrator を呼ぶため、利用側のスキーマを鍵管理へ移さない |
| ApiTokens | API | 妥当 | 管理発行トークンの記録、スコープと即時失効を担当し、OAuth2 の JWT 発行と検証を利用する。通常のグラントと管理発行の規則の違いを保ち、技術処理の重複を避ける |
| Audit | 各発行プロセス、検索は API | 妥当 | 監査の検索表現、検索文法と開示を隠す。発行の判断は各所有者にあり、配信点が追記へ写す。イベント追加を監査の業務処理に集めない |
| IdManagement | API、Worker、Batch | 妥当 | User、Group と Agent の状態遷移と削除の編成を担当する。資格情報、同意と取り込み元は要求側の操作と照会で結び、所有者の保存知識を複製しない。CSV とジョブでも同じ状態所有者を維持する |
| IdGovernance | API、Worker | 妥当 | ワークフローの捕捉、評価と実行の進捗を隠す。User の更新と同じトランザクションで捕捉し、実行は所有者の冪等な操作へ渡す。手順の追加は User の保存規則の変更と分離できる |
| Sourcing | API | 妥当 | 外部 ID の相関、カーソルと取り込みの判断を隠す。User と Group は IdManagement の操作を通し、対応と作成を同じトランザクションで確定する。利用者側の DirectoryConnector はこの境界に入れず wi-69206 が分割を担当する |
| Provisioning | API、Worker | 妥当 | 下流への差分、タスク、再試行と照合を隠す。主体と割り当ての所有者から通知を受け、Jobs で送信する。内向きの相関と外向きの収束は変更理由が異なるため Sourcing と統合しない |
| WorkloadIdentity | API | 妥当 | 外部アテステーションの信頼と Agent への一意の対応付けを隠す。検証結果を OAuth2 の交換に渡し、トークン発行を重複しない。外部の実行基盤自体は同梱しない |
| Authentication | API、保持処理は Batch | 妥当 | 本人確認、MFA とセッションの判断を隠す。認証事実を Application へ射影し、資格情報の操作を IdManagement に提供する。OAuth の発行と認証方式の変更を分けられる |
| Authorization | API | 妥当 | 認可モデルと関係タプルの保存、グラフの評価と整合トークンはまとまっている。汎用認可ポートを OAuth2 から借りる接点は wi-16478 の対象とし、関係タプルのモジュールの統合は要しない |
| Application | API、割り当ての適用は Worker | 妥当 | 割り当てとサインインポリシーを一つの関門に閉じ、プロトコルを不透明なキーで参照する。管理の編成は Catalog、認証事実の解釈は Authentication に残す |
| ApplicationCatalog | API | 要再設計 | OIDC は所有者の管理操作を使うが、SAML の SP と WS-Fed の RP は保存型を構築、変更している。両所有者の公開操作へ通し、Catalog に HTTP の変換と編成を残す（wi-10848） |
| ClaimMapping | 発行する API の呼び出し内 | 妥当 | 公開の下限と属性対応を決定可能な計算に閉じ、保存と署名を持たない。ワイヤ形式は各プロトコルへ残す。業務上の開示の意味があるため技術的な共有ライブラリへは移さない |
| OAuth2 | API、ログアウトの配信は Worker | 要再設計 | 認証、属性、鍵、失効、アテステーション、Jobs への 9 依存は発行に必要な協調である。一方、汎用 Authorizer と他モジュールの管理権限の表示が token の機能に混在するため、担当を分ける（wi-16478） |
| Saml | API | 妥当 | SP と IdP プロファイル、SSO と SLO は SAML の変更にまとまり、XML 署名の技術規則は共有できている。Catalog からの状態更新は wi-10848 で公開操作へ移すが、モジュールの統合は要しない |
| WsFederation | API | 要再設計 | WS-Fed と WS-Trust の信頼、クレームとメタデータは同じ STS の責務として維持する。OAuth2 への唯一の本番依存は MessageID の再送記録であり、要求側ポートへ分ける（wi-77691）。RP 管理の接点は wi-10848 が担当する |
| SharedSignals | API、Worker | 妥当 | SET の送受信と失効エポックを隠す。主体の操作からの反応でローカル失効を先に確定し、外部への配送を分ける。OAuth2 はエポックを参照するため、トークンの保存形式を共有する必要がない |

候補の根拠は、`frontend/src/api/core.ts` の HTTP 呼び出し、`application_provisioning.go` の SP と RP の Save、`wstrust_handler.go` の MessageID の記録、`role_policies.go` のモジュール横断の管理権限の一覧、`bootstrap/seeding.go` の生成と比較である。
本番の import は `_test.go` を除いて抽出し、各モジュールの README と構築入口、API の経路、Worker のハンドラー登録、User のライフサイクルの配線で作用の担当を照合した。
判定はこのリビジョンの構成に限る。

後続として wi-82793（System）、wi-43154（Seeding）、wi-16478（OAuth2）、wi-10848（ApplicationCatalog と SP、RP の公開操作）、wi-77691（WsFederation）を起票し、それぞれに候補の比較、作用と保証を維持する条件、検証の計画を残した。
CLI とデモについては、HTTP を使う `demo.sh` と `ciba-demo.sh`、サーバーと同じ Go モジュールの内部管理コマンドを区別した。
独立した SDK と、外部配布物がサーバーの内部型を import する例は、今回確認したリポジトリにはなかった。
今回の対象外は再設計そのものと DirectoryConnector の分割であり、それぞれ後続 5 項目と既存の wi-69206 に残した。
