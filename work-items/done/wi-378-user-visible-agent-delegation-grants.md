# ユーザーが自分を代行できるエージェントを一覧し、個別に取り消せるようにする

本人がアカウントポータルで Agent を選んで代行を付与し、一覧し、個別に撤回できるようにした（REQ-OAUTH2-057、REQ-OAUTH2-058）。
管理者は同意の画面から付与を参照できるが、付与も撤回もできない（REQ-OAUTH2-059）。
利用者をサブジェクトとする Token Exchange は、関わるすべての Agent に本人の付与を求める（REQ-OAUTH2-060）。これまで交換は本人の意思を確かめておらず、本番に `may_act` を発行する経路もなかった。
撤回はイントロスペクションが付与を読むことで即座に効き、同じ Agent の他の利用者には波及しない（REQ-OAUTH2-061）。失効エポックは Agent 単位なので使わない。これは起票時の Scope と異なる判断である。
付与は `consents` の `(user_id, agent_id)` の行として持ち、`client_id` を任意にして主キーをサロゲートへ変えた。製品は未公開なので移行はない。
付与はブラウザーセッションに限る。トークンで付与できると Agent が自分自身に付与できるからである。
サブジェクトが利用者かどうかは `sub` と `client_id` の比較では見分けられず、登録されたクライアントかを引いて決める。既存の E2E がこの誤りを検出した。
実装を先に書いたので、テスト追加時の RED の代わりに、交換の判定、イントロスペクションの判定、`granted_at` の比較、Bearer の拒否、期限、入口の配線の六つの故障を注入して各テストの失敗を観測した。
対象外として、`authorization_details` の単位の付与、スコープの候補の提示（入力は自由記述）、管理者の一覧の「さらに読み込む」UI を残した。`ResourceAccessTokens` の配線は欠けると代行トークンを拒否する側に倒れるが、この経路で代行トークンを受け付けることを直接確かめるテストはない。
