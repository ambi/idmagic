# Agent のガードレールを版付きのポリシーとしてトークンの発行で評価する

Agent に関わる全グラントの `/token` の発行と ID-JAG の発行を、テナントのデフォルトと Agent 別の二層のポリシーで評価するようにした（REQ-OAUTH2-073〜078、`features/guardrail.md`）。
種別は許可する資源と `authorization_details` の種類、発行の流量、有効期間の上限、ポリシーの有効期限、委譲深さ、常時の承認である。
超過は種別ごとに拒否か所有者の承認への降格を宣言でき、理由とバージョンは `AgentGuardrailEvaluated` にだけ残す。
管理 API は `/api/admin/v1/agents/{agent_id}/guardrail-policy` と `/api/admin/v1/agent-guardrail-default` で、`expected_version` が現在のバージョンと異なる保存を 409 で拒否する。
`shared/ratelimit` に要求ごとの閾値を受ける `AllowWithin` を加え、`agent_guardrail_policies` を OAuth2 が所有する。

判断：起票から更新し、利用者の確認を経て、評価点は全グラント、承認者は Agent の所有者、宣言の単位は二層とした。
実行時の回数は wi-25649 に任せて外し、ID-JAG を評価点に加えた。
評価は全グラントが通る発行器に置き、リフレッシュだけはローテーションの前に判定する。

確認の限界：
RED は実装の後に、配線、リフレッシュの前判定、所有者の照合、連鎖の評価を一時的に外して観測したので、テストが実装より先行した順序ではない。
E2E は `/token` の client_credentials と管理 API を通す。降格、リフレッシュ、連鎖の判定は発行器と `RefreshTokens` の単体の境界で確かめ、CIBA、認可コード、デバイスコード、ID-JAG を正式な入口で通す受け入れテストはない。
PostgreSQL の並行の上限は既存の `Allow` の試験が同じ実装を通るだけで、`AllowWithin` 固有の並行試験はない。発行の経路への負荷は測っていない。
ブラウザーを通す UI の E2E は追加も実行もしていない。OWASP の資料は二次情報でのみ確認した。

残るリスクと制約：
認可コード、デバイスコード、`auth_req_id` は署名の前に消費するので、拒否するとフローのやり直しになる。
連鎖の複数の Agent を数えるとき、後の Agent の拒否の前に数えた分は戻らない。
降格で発行するトークンの主体は承認した所有者であり、Agent の権限ではなく所有者の権限で評価される。
テナントのデフォルトの編集画面はなく、API だけで変更する。UI からは空の許可（何も許さない）を設定できない。
メモリの保存先は Agent の削除でポリシーを消さない（PostgreSQL は外部キーで消える）。
機能を戻すと上限が無視されて発行が広がるので、利用中のテナントは先に別の統制へ移す。
