# セキュリティ上の拒否を規範として宣言させ、テストとの対応を検証の門にする

## Motivation

[[wi-157-job-admin-operations-surface]] の実装中に、`support_http.VerifyBrowserRequest` が 403 を書いたうえで `nil` を返していることが分かった。呼び出し元 20 か所あまりはいずれも `if err := d.VerifyBrowserRequest(c); err != nil { return err }` と書いており、この防護は全経路で素通りしていた。403 を返した後もハンドラーが動き続け、副作用まで実行していた。認証済み管理セッションに対するクロスサイト POST が、拒否されたように見えながら実際には処理されていたことになる。

問題は欠陥そのものより、**それが誰にも見つからずに済んだ理由**である。

**この防護にはテストがあった。** `csrf_test.go` は Origin 不一致、CSRF Cookie 欠如、Cookie とヘッダーの不一致の 3 つの拒否ケースを持っていた。カバレッジもあった。しかし 3 つとも `rec.Code == http.StatusForbidden` だけを assert し、**戻り値が `nil` であることを「期待どおり」として `t.Fatal` していた**。防護が拒否を呼び出し元へ伝えないことを、テストが正しい振る舞いとして固定していた。

つまり、**応答が「拒否」と言っていることだけを確かめ、要求が実際に止まったことを確かめていなかった。** 防護のテストとしてはこれで足りない。防護が守るのは応答の見た目ではなく、副作用が起きないことだからである。

同じ形の穴が repo 全体にある。実測 (2026-08-22) では、`Requires` / `Rejects` / `Denied` / `Forbidden` / `Refuses` を名前に持つテスト関数が **433 件**あり、そのうち 123 件が拒否のステータスコードを assert している。一方で、拒否の後に状態を読み直して副作用が起きていないことを確かめているテストは **十数件**しかない。大半は「4xx が返った」で終わっている。

既存の門はどれもこれを捕まえられない。

- **CodeQL と gosec** は既知のパターンとテイントの流れを見る。「ヘルパーが `nil` を返すので呼び出し元の防護が死んでいる」は意味論の欠陥であり、どちらの検出対象でもない。
- **[[wi-131-testing-governance-and-ci-enforcement]]** はカバレッジの閾値を強制する。今回の行は実行されていたので、閾値をいくら上げても検出されない。wi-131 自身が Risk Notes で「意味のないアサーションを伴うダミーテスト」の可能性に触れているが、その懸念を検査に変える手当ては持っていない。本 work item はその欠けた半分を、セキュリティ防護に限って埋める。
- **`mise run verify`** は防護の質を問わない。

さらに、**守るべき拒否がどこにも宣言されていない**。シナリオには拒否の分岐が 130 件書かれているが、それをテストが引用しているかを確かめる仕組みが無い。実測では、セキュリティ上の拒否を宣言している REQ id は **78 件**、そのうちテストから引用されているのは **18 件**、残る **60 件は 1 つのテストからも参照されていない**。防護の実装を検査で守っても、何を拒否すべきかが規範として定まっていなければ、守る対象が決まらない。

## Scope

- **セキュリティ上の拒否を規範として宣言させる**。認可、テナント境界、CSRF、スコープ、フェイルクローズの各防護が拒否すべき場合を、シナリオの `ALT` 分岐か独立した `REQ` として宣言することを `SPECIFICATION_FORMAT.md` に書く。拒否は観測可能な振る舞いであり、成功経路と同じ資格で規範に属する。
- **宣言された拒否とテストの対応を検査する**。セキュリティ上の拒否を宣言する `REQ` id が、少なくとも 1 つのテストから引用されていることを要求する。既存の 60 件は縮むだけの許可リストに載せ、**新しく宣言する拒否は初日から対応を要求する**。
- **テストの規範を定める**。セキュリティ防護 (認証、認可、テナント境界、CSRF、Origin 検証、スコープ検査、流量制限、フェイルクローズの分岐) を検証するテストが、拒否のケースで何を assert しなければならないかを `DEVELOPMENT.md` に書く。少なくとも次の 2 つを要求する。
  - **観測可能な結果**: 応答のステータスとエラーの種別。
  - **副作用の不在**: 拒否された操作が状態を変えていないこと。作成されるはずだった行が無い、更新されるはずだった値が元のまま、発行されるはずだったイベントが出ていない、のいずれかを、テスト自身が読み直して確かめる。
- **防護のヘルパーが拒否を戻り値で表すことを規範にする**。応答を書いたうえで `nil` を返すヘルパーを作らない。呼び出し元が処理を止められない形の防護は、防護ではないことを明記する。
- **検査を実装する**。上の 2 点を機械的に確かめられる範囲で検査に落とす。
  - `(c *echo.Context) error` を返し、本体で `WriteProblem` を呼びながら `nil` を返しうるヘルパーを検出して落とす。
  - 防護のヘルパーの呼び出し元が、戻り値を捨てていないことを検出して落とす。
- **既存の 433 件を棚卸しする**。副作用の不在を確かめていない拒否テストを列挙し、防護の種別ごとに優先度を付けた台帳にする。全件をこの work item で直すのではなく、何が残っているかを可視な状態にする。
- **防護ごとの回帰テストを最低 1 本ずつ用意する**。認証、認可、テナント境界、CSRF、スコープの各防護について、防護を意図的に壊すと落ちるテストを 1 本ずつ置く。今回の欠陥に対応するものは wi-157 で入った `TestCancelJobRequiresBrowserVerification` がすでにある。
- **レビューの手順に段を足す**。状態を変える経路を追加する変更で、防護のテストが副作用の不在を確かめているかを確認する段を `DEVELOPMENT.md` の Verification ladder に置く。

## Out of Scope

- カバレッジの閾値と差分カバレッジの強制。[[wi-131-testing-governance-and-ci-enforcement]] が持つ。本 work item はアサーションの中身だけを扱う。
- 棚卸しで見つかった既存テストの全件修正。台帳と、防護ごとの代表 1 本までをここで持ち、残りは台帳から個別に切り出す。
- 新しい防護の追加。既存の防護が実際に効いていることを確かめる手段の整備に限る。
- SAST ツールの導入と入れ替え。CodeQL と gosec の構成は変えない。
- ペネトレーションテストと外部監査の手配。
- 認可モデルそのものの設計変更。

## Design

### 棚卸しの結果 (T001)

名前だけで拒否テストを数えると入力検証まで入り、母集団が 433 件になって扱えない。実害が出るのは「**状態を変える操作**が拒否されたのに実行されてしまう」場合だけなので、そこへ絞って測り直した (2026-08-22)。

| | 件数 |
|---|---|
| テスト関数 (backend) | 2247 |
| 拒否を assert する | 276 |
| うち状態を変える呼び出しに対するもの | 120 |
| うち拒否後に状態を読み直していない | **84** |

84 件なら台帳として扱える。読み取りの拒否を除いたのは、素通りしても副作用が無いからである。

### 1. 検査の実装手段 — 案 A (`tools/check` の bun ツール、構造の抽出に `ast-grep`)

新しい解析基盤は持ち込まない。既存の検査群と同じ場所、同じ門、同じ形 (純粋な判定モジュール + その場のテスト + 薄い入口) に置く。

**防護のヘルパーかどうかは名前では決まらない。** `handle*` も `write*Error` も応答を書いて返すが、それは正しい。決め手は「**呼び出し元が続行判断にその戻り値を使っているか**」であり、これは機械的に判定できる。

- **R1**: `if err := f(...); err != nil` の形で呼ばれている関数が、`*echo.Context` を受け `error` を返し、本体に `return WriteProblem(...)` を持つなら落とす。`WriteProblem` は応答を書いた結果 (通常 `nil`) を返すので、この形の関数は拒否を呼び出し元へ伝えられない。
- **R2**: ガード位置で呼ばれている関数の戻り値を、別の場所で捨てている呼び出しがあれば落とす。同じ関数が防護として使われたり使われなかったりする状態は、どちらかが誤っている。

判定の対象からテストファイルを除く。試作でテスト由来の偽陽性が 3 件出たが、除外すると消え、残ったのは真陽性 2 件だけだった。gofumpt が整形を保証するので、関数本体の切り出しは桁 0 の `}` までで足りる。

### 2. 「副作用の不在」は門にしない

規範には書くが、CI の門にはしない。

門にするには「拒否テストの本体に状態を読み直す呼び出しが 1 つ以上ある」といった構文の要求になるが、これは意味のない読み直しを 1 行足せば満たせる。[[wi-131-testing-governance-and-ci-enforcement]] が Risk Notes で警戒している「意味のないアサーションを伴うダミーテスト」を、こちらが自分で作り出すことになる。**満たし方が是正より安い門は、是正されない。**

代わりに 3 つを置く。(1) `DEVELOPMENT.md` の規範、(2) 84 件を数え上げる報告タスク、(3) 防護ごとの代表テスト。報告タスクは落ちないが、数が見えていれば減らす判断ができる。

この判断により、本 work item で「落ちる検査」になるのは R1 と R2 だけである。ただしそれは今回の欠陥そのものの類型であり、Verification の手動確認はまさにそれを再現して確かめる。

### 3. 台帳の置き場所 — 報告タスクの出力とし、ファイルに固定しない

84 件を一覧にしてリポジトリへ置くと、テストを 1 つ足すたびに台帳が古くなる。古い台帳は読まれない。`mise run report-security-test-gaps` がその場で数え上げる形にし、件数の推移は work item の記録に残す。仕様の側には置かない。台帳はこの変更の作業記録であり、仕様が持つべき現在の姿ではないからである。

### 4. 宣言された拒否とテストの対応 (R3) — 縮むだけの許可リストで門にする

**R3**: シナリオの `ALT` で拒否を宣言している `REQ` id は、少なくとも 1 つの Go テストから引用されていなければならない。

今日の実測は 78 件中 18 件しか引用されていない。全件を対応させてから門にするのは本 work item の規模を超えるので、未対応の 60 件を許可リストへ固定し、**許可リストに載っていない拒否の宣言が対応を持たなければ落とす**。許可リストは縮むことしか許さない。載っている id が対応を持つようになれば、検査が「許可リストから外せ」と言う。

#### wi-362 が同じ検査を見送っていることについて

[[wi-362-req-test-traceability-and-lookup]] は「新規 REQ にテスト注記が無ければ失敗させる検査」を Out of Scope に置き、理由をこう書いている。

> テスト自体は存在しており、欠けているのは注記だけなので、検査が守るのは「新しい REQ に注記を付け忘れないこと」でしかない。発生しても影響が軽く、摩擦だけが残る。

**この前提は確かめられておらず、実際には成り立たない。** 今回サンプルで検証したところ、性質の異なる 2 つが混ざっていた。

| REQ | 宣言している拒否 | テストの実在 |
|---|---|---|
| REQ-TENANCY-003 | default テナントの無効化を拒否 | ある (`TestEnsureDefaultAndRejectDefaultDisable`)。注記が無いだけ |
| REQ-WSFEDERATION-001 | `wsfed:read` だけで変更操作 → 拒否 | 見当たらない。`wsfed:read` に触れるテストは 0 件で、近いのはロールを見る `ForbiddenForNonAdmin` だけ |

前者は wi-362 の言うとおり注記の問題にすぎない。後者は**スコープによる拒否が検証されていない**という、注記とは別の欠落である。注記ベースの検査は 2 つを区別できないので、後者を見つけるには前者の摩擦も引き受けることになる。それでもセキュリティ上の拒否については引き受ける価値がある、というのが本 work item の判断である。

この門は「副作用の不在」と違い、安く満たしても害が小さい。テストに `REQ-JOBS-013` と書くには、書く人が該当のシナリオを開いて自分のテストが何を守っているかを一度は照合する必要があり、レビューする側も同じ照合ができる。得られる追跡可能性そのものにも独立した価値がある。

### 試作で見つかった現存の欠陥

R1 の試作が、CSRF と同じ形の欠陥を 2 件見つけた。`saveValidatedType` と `saveValidatedMcpResourceServer` はいずれも検証失敗時に `return support.WriteProblem(...)` としており、呼び出し元の `if err != nil { return err }` が働かず、422 を書いた後も 201 / 200 の応答へ進んでいた。検査を通すには直す必要があるので、本 work item で直す。

## Plan

- 規範を先に書き、検査はその写しとして実装する。検査が規範の正本にならないようにする。
- 棚卸しは検査の実装より先に行う。実際に何件あるかを見てから、検査で捕まえる範囲と規範に委ねる範囲を決める。
- 防護ごとの代表テストは、防護を意図的に壊した状態で落ちることを確認してから入れる。落ちないテストは防護を守っていない。

## Verification

- `mise run check`
  - reason: 新しい検査が既存の検査群と同じ門で動くこと。
- `mise run verify`
- 手動: `VerifyBrowserRequest` を wi-157 以前の「応答を書いて `nil` を返す」形へ戻し、R1 が落ちることを確認する。今回の欠陥をそのまま再現して捕まえられなければ、この work item は目的を果たしていない。

## Risk Notes

リスクは medium。検査が偽陽性を出すと、開発者は除外を書いて先へ進む。除外が増えれば検査は名目だけになるので、除外には根拠と期限を持たせ、期限切れを検出する。[[wi-131-testing-governance-and-ci-enforcement]] が例外の扱いで同じ設計に至っているので、仕組みを合わせる。

規範を書いただけで検査を伴わなければ、今回と同じことが起きる。防護のテストがあり、カバレッジもあり、それでも間違ったことを assert していた、というのが今回の経緯である。**読まれる文書ではなく落ちる検査にすること**が、この work item の成否を分ける。

棚卸しの 433 件を全件直そうとすると着手できなくなる。台帳を作って可視にすることと、防護ごとの代表 1 本を置くことまでを本 work item の完了条件とし、残りは台帳から個別に切り出す。

  意味の差は 4 つある。

  第二に、**防護が拒否を戻り値で伝えられない形を検査が拒む (R1)**。防護かどうかは名前では決まらない。`handle*` も `write*Error` も応答を書いて返すが、それは正しい。決め手は呼び出し元がその戻り値で続行を決めているかで、これは機械的に判定できる。R1 は導入時点で **CSRF と同型の現存欠陥を 2 件** (`saveValidatedType` / `saveValidatedMcpResourceServer`) 見つけた。どちらも 422 を書いた後に 201 / 200 の応答へ進んでいた。

  第三に、**宣言された拒否にテストが無い状態が見えるようになった (R3)**。175 件の宣言のうち 137 件は依然どのテストからも引用されていないが、許可リストに固定したので数が見え、増えない。新しく宣言する拒否は初日からテストを要求される。

  R3 の検出器は当初 `ALT` 行のキーワード照合だけで、2 つの形を丸ごと取りこぼしていた。拒否がシナリオ自身の帰結として `THEN` に書かれている場合 (`REQ-SIGNINGKEYS-009`「THEN AccessDeniedError で拒否される」) と、テナント境界が結果として言い換えられている場合 (`REQ-IDGOVERNANCE-012`「THEN ワークフローは存在しないものとして扱われる」) である。どちらも検査の網から完全に抜けており、許可リストにすら載っていなかった。`THEN` も読み、エラー型の出現を主たる signal にして直した。宣言は 78 件から 175 件へ、未検証は 58 件から 137 件へ増えた。**増えたのは負債ではなく、見えていなかった負債である。**

  併せて「セキュリティ上の拒否かどうか」の分類をやめた。分類こそが検出器を脆くしていた原因であり、「宣言された拒否にはテストがある」という性質は、認可の拒否でも入力検証の拒否でも同じだけ価値がある。

  第四に、**拒否テストの規範を `DEVELOPMENT.md` に置いた**。拒否は「返ったステータス」ではなく「起きなかった副作用」で確かめる。これは検査にしていない。「本体に読み直しが 1 つ以上ある」という構文の要求は、意味のない 1 行で満たせてしまい、[[wi-131-testing-governance-and-ci-enforcement]] が警戒する空のテストを自分で作り出すからである。代わりに `mise run report-security-test-gaps` が 84 件を数え上げる。

  なお [[wi-362-req-test-traceability-and-lookup]] は同じ検査を「テストは実在しており、欠けているのは注記だけ」として見送っていた。**この前提は成り立たない。** REQ-TENANCY-003 は確かに注記だけの問題だったが、REQ-WSFEDERATION-001 (`wsfed:read` だけで変更操作 → 拒否) はテスト自体が存在しなかった。注記ベースの検査は 2 つを区別できないので、後者を見つけるには前者の摩擦も引き受けることになる。セキュリティ上の拒否についてはそれに見合うと判断した。
