# 画面の設定だけで統制できる AI エージェントのデモを提供する

`docs/development/ai-agent-demo.md` のシェル中心のデモを、`mise run demo-agent` で起動する画面のデモ `examples/agent-demo` へ置き換えた。
共有キーの直接接続と実在の MCP ゲートウェイ越しの実行を比べ、許可、拒否、権限の変更、停止、人の承認を見せる。
エージェントの判断は台本で、LLM は使わない。

仕様は REQ-IDMANAGEMENT-103 を追加した。
クレデンシャルの画面で、PEM、JWK、JWKS の公開鍵から鍵認証のクライアントを作成して紐付ける。

利用者の確認で見つかった問題も直した。
サービスの詳細は API の `redirect_uris` と `response_types` の null で描画に失敗し、エラー画面がセッション切れと誤表示していた。応答を空の配列にし、描画の失敗を認証の問題と表示しないようにした。
スコープの選択、アクセス規則の行入力、認可モデルのテンプレート、所有者の選択、画面の用語の統一（クレデンシャル、紐付け）、見出しの重複の解消も行った。
完了前のレビューで、公開鍵の解析中の二重送信、不正な規則の JSON による描画の失敗、所有者の候補が先頭200件に限られる問題を修正した。

判断は次のとおりである。
公開鍵の登録は既存の `POST /clients` と束縛を画面から順に呼び、API の契約を変えない。`jwks_uri` の loopback の許可は SSRF の防御を弱めるので採らなかった。
ゲートウェイは `https://` の `realm_url` を求めるので、デモ専用の TLS の前段を置く。

検証は `frontend/tests/e2e/ai-agent-demo.spec.ts` が JSON を書かず画面だけで設定し、実行、拒否、権限の追加、停止、承認を確かめる。
手順の切り替え、控えた値の引き継ぎ、「前へ」で戻ったときの入力保持も確かめる。
限界は次のとおりである。承認後のトークンでのゲートウェイの呼び出しは見せない。仕様書と用語集の「資格情報」「束縛」は改名していない。
