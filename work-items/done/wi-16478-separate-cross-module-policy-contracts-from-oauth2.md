# プロトコルをまたぐ認可の契約と管理ロールの表示を OAuth2 から分ける

OAuth2 にあった AuthZEN の要求ポートと管理ロール一覧の計算および HTTP 表示を、既存の関係に基づく認可と同じ担当へ集約した。
そのモジュールを AccessControl と命名し、コードを `backend/accesscontrol` へ移した。
OAuth2 から AccessControl への依存だけを置き、逆向きの依存と循環を作らない。
管理ロールの純粋な計算は `internal/rolepolicy` に閉じ、関係タプルの保存先を要求しない。

`spec-diff` が示す差分は REQ-AUTHORIZATION-001〜010 の応答主体名を Authorization から AccessControl に改めたことだけである。
要件 ID、TypeSpec の名前空間、HTTP パス、要求と応答、認可の条件、永続状態、イベントは維持した。
既存の仕様への参照を保つため、文書と TypeSpec の `authorization` の配置は残した。

AccessPolicy の新設は、同じ認可を二つの曖昧な担当へ分けるため採らなかった。
サインイン条件は今回集約せず、定義、評価と保存の独立を wi-71755 で比較する。

変更先と利用側の race テスト 2,475 件、Go lint、仕様、境界、負債の増加、契約、テーブルの所有、参照とツールの検査を通した。
経路登録を外した HTTP の失敗と、system_admin の表示への権限混入の失敗を確認した。
ロール一覧の変異は 9 件中 7 件を検出し、生存した 2 件は、重複しない権限名の比較境界と、仕様が順序を約束しない一覧の逆順化に分類した。
七つの視点で差分を確認し、認可の意味、トークンの処理とサインイン条件の変更は含めていない。
