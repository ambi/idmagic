# 言語別エンジンを包む汎用変異試験基盤を導入する

## Motivation

`wi-411` は Go の一つのパッケージで Gremlins を試行し、局所的な純粋ロジックなら約 25 秒で変異の検出能力を測れることを示した。一方、現在のタスクは Go パッケージと任意の Git 差分を直接指定するだけで、対象選択、実行予算、結果形式、同値変異の扱い、再試行、成果物、CI での利用条件が共通化されていない。TypeScript、複数パッケージ、主要ユースケースの故障モデルにも再利用できない。

`wi-445` は medium 以上の変更に代表的な誤実装の検出を求め、high / critical の純粋ロジックには体系的な変異または明示的な故障注入を求める。毎回一時差分を手で作る方法だけでは、何を変異させ、どの試験が検出し、何が同値または未網羅だったかを同じ形で残せない。言語固有の変異生成は既存エンジンへ委ねつつ、対象選択と証拠をリポジトリ共通の深い境界へまとめる必要がある。

## Scope

- Git の基準点と変更範囲から候補となる純粋ロジックを選び、対象ファイル、パッケージ、試験タスク、時間予算を明示した変異計画を検証する共通操作を追加する。
- Go と TypeScript の言語別エンジンを同じポートへ接続する。Go は `wi-411` で固定した Gremlins を再利用し、TypeScript エンジンは版固定、Bun テストとの互換性、変更行限定、機械可読結果、実行時間を比較して実装開始前に一つへ決定する。
- killed、survived、not-covered、timeout、error、equivalent-reviewed を区別する共通結果モデルと JSON Schema を定め、元のソース位置、演算子、実行した試験、所要時間を保持する。
- 生存変異と未網羅変異を、根拠付きの同値判定、試験追加、対象除外、製品欠陥のいずれかへ分類する。期限のない包括除外を認めない。
- `mise` タスクで局所実行、Git 差分実行、結果検査、レポート生成を提供し、生成物を一時領域または CI artifact に隔離する。
- high / critical の純粋ロジックに対する `risk-based-v3` の変更抵抗性証拠へ、共通結果から対象、検出、未検出、同値判断、方法の限界を転記できるようにする。
- 通常の `mise run verify` とは分離し、変更範囲と予算で収まる選択実行または CI の専用検査として導入する。実測した安定性と所要時間なしに全変更の必須検査へしない。

## Out of Scope

- 独自の変異生成エンジンを実装すること。構文と実行系に固有の生成は版を固定した外部エンジンへ委ねる。
- 変異得点のリポジトリ全体一律閾値。生存変異には同値、未到達、防御コードもあるため、単一の割合だけで合否を決めない。
- UI の視覚差分、外部サービス、データベース障害、ネットワーク分断をソース変異だけで表現すること。これらは明示的な故障注入または E2E テストが扱う。
- 低リスクの文書、設定、生成物、機械的リファクタリングへ一律に変異試験を要求すること。
- 変異試験が見つけた製品欠陥を本 work item で修正すること。規範参照を持つ個別 bugfix work item へ分ける。
- `wi-456` が扱う既存全機能の主要ユースケース証拠の移行。

## Design

共通境界は変異の生成方法ではなく、計画、実行、正規化、判定に置く。主要型は `MutationPlan = { baseline; targets; testTask; budget; engine }`、`MutationTarget = { path; packageOrModule; changedLines }`、`MutationResult = { location; operator; status; tests; duration; detail }`、`MutationReview = { resultId; disposition; rationale; expiresAt? }` とする。主操作は、効果を外へ追い出した `planMutationRun(repositoryFacts, policy): PlanResult` と、言語別ポート `MutationEngine.run(plan): AsyncIterable<MutationResult>`、純粋な判定 `evaluateMutationRun(plan, results, reviews): Findings` に分ける。

Git 差分、ファイル読み取り、プロセス起動、時計、成果物書き込みはアダプター境界に置く。判定は保存済み fixture だけで再現できるようにし、外部エンジンを毎回起動しない単体検査を持つ。実エンジンの統合検査は小さな既知 fixture を使い、検出される変異、生存する同値候補、時間切れ、壊れた出力を一つずつ固定する。

TypeScript エンジンの選定は実装開始前の設計ゲートとする。候補は、Bun テストを直接実行できるか、または既存 `mise` タスクを試験コマンドとして呼べるものに限定する。変更行限定、JSON 出力、除外の粒度、並列数、タイムアウト、保守状況を同じ fixture で測り、選定結果と却下理由を Design に追記してから基盤を実装する。互換なエンジンが無い場合は、TypeScript を無理に独自実装せず Go 対応だけで完了扱いにせず、本項目を blocked として別の評価項目へ分ける。

却下する案は、変異得点だけを保存する薄いラッパーと、全 `mise run verify` へ無条件で組み込む案である。前者は生存理由と試験追加先を失い、後者は同値変異と実行時間を開発停止へ変える。共通基盤は個別結果を保持し、変更リスクと対象の純粋性から実行を選ぶ。

## Plan

1. `wi-411` の Gremlins 結果を共通モデルの fixture にし、計画、結果正規化、判定の型と JSON Schema を RED で確定する。
2. TypeScript 候補を同じ小規模 fixture と固定予算で比較し、Design に採用エンジン、版、却下理由、Bun テストとの接続方法を追記して設計ゲートを閉じる。
3. Git 差分から対象を選ぶ純粋な計画操作と、Go / TypeScript のエンジンアダプターを実装する。
4. 局所実行、差分実行、保存済み結果の再判定、Markdown / CI summary の生成を `mise` タスクとして公開する。
5. high / critical の代表的な Go と TypeScript の純粋ロジックで試行し、検出、生存、未網羅、同値判断、時間、揺らぎを記録する。
6. 通常検証からの分離、予算超過、壊れたエンジン出力、期限切れ除外が fail-closed になることを確認する。

## Verification

- `mise run test-tools`
- `mise run check-work-items`
- `mise run verify`
- Go と TypeScript の同じ論理故障が共通の `MutationResult` として正規化される。
- 基準点、対象、試験タスク、予算の欠けた計画を拒否する。
- survived / not-covered / timeout / error を killed として数えず、レビューの無い未検出結果を成功扱いにしない。
- 期限切れの同値レビュー、未知の変異演算子、壊れたエンジン出力を fail-closed で拒否する。
- 変異エンジンが利用できなくても通常の `mise run verify` は影響を受けず、選択した変異検査は明示的に失敗する。
- 生成した JSON とレポートが作業ツリーに残らない。

## Risk Notes

リスクは high。言語別エンジンの出力差を隠す正規化は、未検出変異を killed と誤って扱う危険がある。未知の状態、欠落した位置、壊れた JSON、途中終了を成功へ丸めず、共通判定を fail-closed にする。

変異試験はテストの検出能力を測るが、すべての生存変異が製品欠陥ではない。同値判定は根拠と対象位置を残し、包括的な除外や無期限の抑制を許さない。逆に数値目標だけを追うと、実装詳細を固定する価値の低いテストが増えるため、主要ユースケースと規範上の効果を優先してレビューする。

実行時間と揺らぎが大きい基盤を全変更へ必須化すると、開発者が対象を狭めるために危険な除外を増やす。通常検証から分離し、差分、純粋性、リスク、明示した予算で選択する。必須化の範囲拡大は本項目の実測値を根拠に別の方針変更として扱う。
