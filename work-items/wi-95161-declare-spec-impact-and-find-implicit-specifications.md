# 実装変更に仕様影響の宣言を必須にし、暗黙の仕様を見つける

## 動機

仕様と実装の対応は、現在、主に仕様からテストへの方向で検査している。
`mise run check` は、宣言済みの `REQ-*`、`EX-*`、標準 ID がテストから参照されることを求める。
これで確認できるのは、**仕様に書いた振る舞いに検査があるか**である。

次の問いには、直接答えていない。

**実装に存在し、将来も維持すべき細かな挙動が、仕様に明示されているか。**

たとえば次のようなものである。

- エラー時に既定値で続行するか、失敗するか
- 設定がない場合のフォールバック
- 上限、丸め、切り捨て
- 再試行の有無と回数
- 結果の順序
- 重複の扱い
- 大文字と小文字、空文字列と欠落の区別
- 特定の条件で監査イベントや通知を発行しないこと
- 失敗時に永続状態を変更しないこと
- 部分的な成功を残すか、全体を失敗させるか

これらがコードにだけ存在すると、実装変更によって値や分岐が変わっても、変更者がそれを仕様変更だと認識しない場合がある。

この問題を、コード被覆や変異テストから自動的に判定しようとはしない。
仕様 ID を引くテストがあるコードを実行していること、そのコードへの変異でテストが失敗することは、テストの検出能力を示す。
それだけでは、その細部が仕様文書に明示されていることは示せない。

そこで、仕様変更かどうかを機械に実装から推論させない。
**意味のある本番コード変更にはすべて、変更者に仕様への影響を明示的に宣言させ、機械はその宣言と仕様差分の矛盾だけを検査する。**
既存コードにある暗黙の仕様は、別の探索手段で見つける。

### 現状との差

宣言の枠組みの一部はすでにある。

| 現状 | 不足 |
| --- | --- |
| work item のスキーマは、`feature`、`bugfix`、`operations` に `affected_spec` を求め、それ以外の種類には `affected_spec` と `spec_impact: none` のどちらか一方を求める | 本番コードの変更を work item に結び付けていない。直近で `backend/` を変更した 40 コミットのうち 8 件は work item を伴わず、宣言を置く場所がない |
| `mise run spec-diff` は、変更した `standards.md` の行が作業ツリーで変更した work item の `affected_spec` にあることを検査する | 標準の行しか対象にせず、シナリオと TypeSpec は照合しない。`affected_spec` から差分への逆方向も照合しない。`spec-diff` を実行したときにだけ失敗し、`check` のゲートではない |
| `spec-diff` は TypeSpec 宣言の追加と削除を報告する | 既存の宣言の変更を報告しない。`affected_spec` の参照先は TypeSpec のシンボルが 425 件あり、モデルの項目を変えても差分として見えない |
| `spec_impact.reason` は 10 文字以上を求める | 「リファクタリングのみ」のような定型句を拒否しない |

仕様を変えない修正もある。
たとえば 1efba586 の `fix(oauth2)` は、宣言済みの `TokenRevoked` の通知と認可コードの失効に実装を合わせ、仕様文書は変更していない。
完了済みの `bugfix` は 60 件ある。
「`affected_spec` を宣言したのに仕様差分がなければ失敗させる」だけの規則では、こうした正しい修正がすべて失敗する。

## 対象範囲

- 「仕様として書くべき実装上の細部」を判断する規則を `SPECIFICATION_FORMAT.md` §6 に追加する。
- `affected_spec` の各項目に `impact` を追加する。
  値は、規範要素を変更する `modifies` と、変更せずに実装を合わせる `conforms` のどちらかとする。
  既定値は `modifies` とする。
- 本番コードを変更する各コミットに、次のいずれかの仕様影響の宣言を求める。
  - 同じコミットで変更した work item の `affected_spec` または `spec_impact: none`。
  - work item を変更しないコミットでは、コミットメッセージの `Spec-Impact: none — <維持する振る舞い>` トレーラー。
- 宣言と仕様差分の整合を検査する。
  - `impact: modifies` の規範要素が、仕様差分に変更として現れる。
  - `impact: conforms` の規範要素が、仕様差分に現れず、その ID を引くテストが同じ作業で追加または変更されている。
  - 仕様差分に現れた規範要素が、同じ作業の `affected_spec` に `modifies` として挙がっている。
    既存の標準の行だけを対象にした照合を、シナリオと TypeSpec へ広げる。
  - `spec_impact: none` の work item と `Spec-Impact: none` のコミットに、規範仕様の差分がない。
- `spec-diff` の差分計算に、既存の TypeSpec 宣言の変更を追加する。
- `spec_impact.reason` と `Spec-Impact` トレーラーの理由から、定型句だけの記述を拒否する。
- これらの検査を `check-repository` の基準リビジョン付きの検査として登録し、`mise run check` のゲートにする。
  CI は `mise run check -- <基準の SHA>` を実行しているため、Pull Request と main への push の両方で働く。
- 既存コードから仕様漏れの候補を見つける報告タスク `mise run spec-review-candidates -- <package-directory>` を追加する。
  仕様 ID を引くテストだけを実行した Go の被覆から、そのテスト群が実行しない本番コードを候補として報告する。
  この報告は仕様漏れの判定ではなく、コードレビューの着手点としてだけ使う。
- `docs/development/specification-first-workflow.md` に、仕様影響の判断、トレーラーの書き方、既存コードから暗黙の仕様を書き起こす手順と観点表を追加する。
- `WORK_ITEM_FORMAT.md` とスキーマに `impact` と理由の規則を追加する。
- `AGENTS.md` に、本番コードの変更では仕様影響を必ず判断し、work item かトレーラーで宣言することを一行で追加する。
- 導入時点の結果から、コンテキストごとの書き起こしの work item を起票する。

## 対象外

- コード被覆によって「仕様に書かれている」ことを証明すること。
- 変異テストによって「仕様に書かれている」ことを証明すること。
- 文レベル被覆の割合を Pull Request のゲートにすること。
- 仕様を引くテスト関数の変更と仕様差分を自動的に同期させること。
- テスト関数、fixture、helper、golden file の変更から仕様変更を推論すること。
- `unspecified_code` のような、仕様のないコードを恒久的に許可する例外一覧。
- 本番コードへの仕様 ID の注釈。
- 変異テストを Pull Request のゲートにすること。
- 完了済みの work item の `affected_spec` へ `impact` を遡って書き加えること。
  検査は、作業範囲で変更した work item だけを読む。
- `frontend/` の被覆による既存コードの探索。
  Go で手順を固めた後に別の work item で扱う。
  仕様影響の宣言は `frontend/` の本番コードにも適用する。
- 検出した既存の暗黙の仕様を実際に書き起こす作業。
  コンテキストごとの work item で扱う。

## 設計

### 仕様と実装詳細の境界

実装の細部が**仕様である**とは、その細部を変えた実装を、ほかの部分がどれほど適切でも「誤った実装」と判断する理由があることをいう。
逆に、その細部だけが異なる二つの実装をどちらも正しいと判断できるなら、その細部は実装詳細であり、仕様へ複製しない。

| 細部 | 判断 |
| --- | --- |
| 未知の列挙値を拒否する | 拒否を維持すべきなら仕様 |
| 依存先がタイムアウトしたときに既定値を返す | その結果を維持すべきなら仕様 |
| 再試行を 3 回行う | 3 回という値に意味があるなら仕様 |
| 結果を ID 順に返す | 呼び出し元がその順序を前提にできるなら仕様 |
| 拒否したときに永続状態を更新しない | 仕様 |
| 監査イベントを発行しない条件 | 維持すべきなら仕様 |
| 補助関数を二つに分ける | 実装詳細 |
| `map` を `slice` に変える | 観測結果が同じなら実装詳細 |
| 非公開関数の名前を変える | 実装詳細 |

この規則の中心は、「コードから観測できるか」ではなく、**将来の実装がその性質を維持する義務を負うか**である。
ただし、その義務は、できる限り内部の手順ではなく、製品が作用を及ぼす境界での結果として書く。

### 細かな内部仕様を書く場所

内部の仕組みが意味のある結果を生む場合は、仕組みではなく結果を規範仕様へ書く。

| 境界 | 例 | 書く場所 |
| --- | --- | --- |
| 外部 API | 境界値、既定値、順序、書式、エラー | TypeSpec、シナリオ |
| 永続状態 | 保存する値、保存しない値、削除の範囲 | シナリオ |
| 外向きの呼び出し | 呼び出す条件、呼び出さない条件、宛先 | シナリオ |
| イベント、監査記録、通知 | 発行する条件、省く条件、含める内容 | シナリオ |
| 状態 | 状態と遷移 | `states.md` |
| 採用した外部標準 | 製品が守る規則 | `standards.md` |

たとえば、内部でトランザクションを使っている場合は、トランザクションを使うことではなく、「失敗したときに、A だけが保存され B が保存されない状態を残さない」という結果を仕様にする。
キャッシュを使っている場合も、「依存先が更新された後、どの時点まで以前の結果を返し得るか」に意味があるなら、その結果を書く。

内部の手順、障害時の修復方法、コードだけからは判断できない仕組みは、引き続き `internals.md` に書く。
その仕組みを採用した理由は `decisions.md` に書く。

### 仕様影響の三つの形

本番コードの変更は、仕様に対して次のどれかの関係にある。

| 関係 | 例 | 宣言 |
| --- | --- | --- |
| 規範要素を変える | 新しい振る舞いの追加、既存の振る舞いの変更、仕様の是正 | `affected_spec` に `impact: modifies` |
| 規範要素を変えずに実装を合わせる | 宣言済みの振る舞いに反していた実装の修正 | `affected_spec` に `impact: conforms` |
| どの規範要素にも影響しない | リファクタリング、性能改善、依存の更新 | `spec_impact: none`、または `Spec-Impact: none` トレーラー |

一つの work item が、ある規範要素を変え、別の規範要素に実装を合わせることもあるため、`impact` は work item 全体ではなく `affected_spec` の項目ごとに付ける。

```yaml
affected_spec:
  - { path: docs/domain/oauth2/scenarios.feature.md, requirement: REQ-OAUTH2-012 }
  - { path: docs/domain/oauth2/scenarios.feature.md, requirement: REQ-OAUTH2-020, impact: conforms }
```

仕様を変更しない場合は次のように書く。

```yaml
spec_impact:
  kind: none
  reason: >
    トークンを検索する順序、返すエラー、永続状態、監査イベント、外向きの呼び出しを変えず、
    検証の純粋な計算だけを補助関数へ抽出する。
```

`affected_spec` と `spec_impact: none` は同じ work item で同時に使わない。
この排他は既存のスキーマがすでに強制している。

この宣言の目的は、機械に仕様変更を推論させることではない。
変更者に**「この変更は仕様を変えるか」**という問いを必ず提示し、その回答をレビューできる形で残すことである。

### work item を伴わないコミット

work item を変更しないコミットが本番コードに触れる場合は、コミットメッセージの末尾に次のトレーラーを置く。

```text
Spec-Impact: none — RevokeFamily が失効させたトークンの一覧を返すだけで、失効の対象、永続状態、発行するイベントは変えない。
```

work item を伴わない変更は、構造を整えるリファクタリングと、小さな修正に限られる。
仕様を変える変更には work item が必要という既存の規則は変えないため、トレーラーの値は `none` だけとする。
トレーラーを付けたコミットが規範仕様を変更していれば拒否する。

宣言の単位はコミットとする。
`docs/development/coding-style.md` は構造変更と振る舞いの変更をコミットで分けることを求めており、work item のブランチに含まれる準備のリファクタリングも、それ自体では work item を変更しない。
そうしたコミットも、トレーラーで「何が変わらないか」を残す。

### 本番コードの範囲

検査の対象とする「本番コード」は次のとおりとする。

| 対象 | 除外 |
| --- | --- |
| `backend/` 配下の `.go` | `_test.go`、テスト専用の支援パッケージ、生成コード |
| `frontend/` 配下のアプリケーションのソース | テストファイル、テスト用の支援コード、生成コード |

除外するパスの判定は、検査の実装に一か所だけ置き、単体テストで固定する。
テスト専用の支援パッケージかどうかは、本番のエントリーポイントから import されるかで判断する。

### 宣言と仕様差分の整合

検査は、意味を推論せず、宣言と差分の矛盾だけを検出する。

| 検査 | 失敗の条件 |
| --- | --- |
| 宣言の有無 | 本番コードを変更したコミットが、変更した work item の宣言もトレーラーも持たない |
| `modifies` の実在 | `impact: modifies` の規範要素が、要件とその子の例、標準の行、TypeSpec の宣言のどれとしても差分に現れない |
| `conforms` の根拠 | `impact: conforms` の規範要素が差分に現れる、またはその ID を引くテストが作業範囲で追加も変更もされていない |
| 差分の申告漏れ | 差分に現れた規範要素が、作業範囲で変更した work item の `affected_spec` に `modifies` として挙がっていない |
| 非影響の矛盾 | `spec_impact: none` の work item、または `Spec-Impact: none` のコミットの範囲に規範仕様の差分がある |
| 参照の解決 | 宣言した規範要素が存在しない（既存の検査） |
| 理由の形 | `spec_impact.reason` またはトレーラーの理由が、空、または定型句だけで構成される |

`conforms` に同じ作業のテストを求めるのは、`modifies` の実在の検査と同じ理由である。
無関係な ID を `conforms` として挙げるだけで宣言を満たせる状態を防ぐ。
実装を仕様へ合わせる修正には、その振る舞いを固定するテストの追加か変更が必ず伴う。

定型句の判定は、「リファクタリングのみ」「振る舞いは変えない」のような語だけで理由が終わるかを見る。
機械にできるのは明らかな定型句の拒否までであり、理由が具体的かどうかはレビューで判断する。

### 作業範囲の決め方

差分をどこから数えるかで、検査の結果が変わる。
基準リビジョンだけを使うと、仕様の変更を先に main へ入れ、完了を後から記録した work item で、`modifies` の規範要素が差分に現れず、誤って失敗する。

そこで、work item の作業範囲は、その work item が `in_progress` になったコミットの親から、作業ツリーまでとする。
`in_progress` になったコミットは、work item のファイルの履歴から一意に決まる。
work item を伴わないコミットの作業範囲は、そのコミット自体とする。

検査の対象になる work item とコミットは、基準リビジョンから作業ツリーまでに変更されたものに限る。
完了済みの記録を毎回再検査しない。

### `spec-diff` の拡張

`spec-diff` の差分計算に、既存の TypeSpec 宣言の変更を追加する。
宣言の本文を空白と改行を正規化して比べ、異なれば変更として報告する。
現在は追加と削除だけを報告しているため、モデルの項目の追加や型の変更が差分に現れず、TypeSpec のシンボルを `modifies` とする宣言を正しく検査できない。

整合の検査と `spec-diff` の出力は、同じ差分計算を使う。
二つ目の実装を作らない。

### 機械検査の限界

この仕組みは、`spec_impact: none` という判断自体が正しいことを機械的には証明しない。
一般の実装コードから「この定数は偶然の値か、製品として維持すべき値か」を判定することはできないためである。
被覆、変異テスト、静的解析を加えても、この問いは完全には解けない。

意味上の判断は、work item、トレーラー、レビューに残す。

### 仕様を引くテストの役割

`//spec:covers` は引き続き、そのテストが規範 ID の何を固定するかを宣言する。
仕様 ID を引くテストがあることは、**その仕様に実行可能な検査がある**ことの証拠である。

ただし、**そのテストが実行したコードのすべてが仕様に書かれている**ことは意味しない。
**そのコードへ変異を加えてテストが失敗すること**も、そのコードの細部が仕様文書に書かれていることを意味しない。
被覆と変異テストは、仕様文書の完全性とは別の問いを測る。

### 既存コードの探索

既存コードには、仕様影響の宣言を導入する前から、コードにだけ存在する意味のある挙動がある。
これを見つけるために `mise run spec-review-candidates -- <package-directory>` を追加する。

このタスクは、指定した範囲について仕様 ID を引くテストだけを実行し、Go の文レベル被覆を取得する。
`-coverpkg` を使い、別パッケージの仕様を引くテストから実行されるコードも数える。

出力には少なくとも次を含める。

- 仕様を引くテストが実行しない本番コードの位置
- パッケージごとの未実行箇所の件数
- 対象にした仕様を引くテストの一覧

結果は「仕様を引くテストから到達していないため、仕様漏れがないかを確認する候補である」と表現する。
「このコードは仕様に書かれていない」とは表現しない。
実行されていないコードが実装詳細の場合もあり、実行されているコードに暗黙の仕様がある場合もあるためである。

このタスクは Pull Request のゲートにしない。

### 既存コードの書き起こし

既存コードを書き起こす work item は、次の手順で進める。

1. `mise run spec-review-candidates` で、仕様を引くテストから到達しない箇所を候補として列挙する。
2. パッケージ全体を、下の観点表で読む。
3. 見つけた細部を、下の四種類に分類する。
4. 分類に応じて、仕様、別の work item、削除へ反映する。

| 分類 | 対応 |
| --- | --- |
| 維持すべき仕様 | 現在の挙動を仕様へ書き、その規範 ID を引くテストを書く |
| 意図が疑わしいが、現在は外部から依存され得る挙動 | まず現在の挙動を仕様として明示し、是正を別の work item にする |
| 実装詳細 | 仕様には書かない |
| 不要なコード | 削除する |

書き起こしと挙動の変更を同時に行わない。
現在の挙動を可視化する変更と、挙動を修正する変更を分けることで、仕様差分が何を意味するかを明確にする。

### 書き起こしの観点

被覆では、ライブラリやランタイムの既定値、コードに明示されない比較規則などを列挙できない。
そのため、既存コードを読む観点を固定する。

| 観点 | 例 |
| --- | --- |
| デコード | 未知のフィールド、重複キー、空文字列と欠落、大文字と小文字 |
| 比較と正規化 | Unicode、空白、照合順序、正規化の有無 |
| 時刻 | タイムゾーン、丸め、有効期限の境界 |
| 順序 | `ORDER BY`、map の反復、並行処理の完了順 |
| 既定値 | 設定の欠落、ライブラリの既定値、HTTP クライアントのタイムアウト |
| 上限 | 本文の大きさ、ページの大きさ、文字列の長さ、整数の範囲 |
| エラー | `error` の破棄、フォールバック、ログだけ出して続行する分岐 |
| 認可 | fail-open、fail-closed、拒否した後の作用 |
| 永続化 | トランザクションの境界、部分更新、ロールバック |
| 冪等性 | 重複した要求、再実行、重複したイベント |
| 再試行 | 回数、対象のエラー、バックオフ、タイムアウトとの関係 |
| キャッシュ | 鮮度、ミス、無効化、古い値 |
| 外向きの作用 | 外部 API、メッセージ、イベント、通知 |
| 省略 | 何をしないか、どの条件で作用を起こさないか |
| 部分的な失敗 | 一部の成功を残すか、全体を取り消すか |
| 後始末 | 途中で失敗した後に残るリソース、リース、一時的な状態 |

観点表は網羅を保証しない。
レビュー時の問いを固定し、読む人によって暗黙の仕様の探索範囲が大きく変わることを減らすために使う。

### 変異テスト

既存の `mise run test-go-mutation` の役割は変えない。
変異テストは、**テストが実装変更を検出できるか**を調べるものであり、仕様文書に何が書かれているかの判断には使わない。
中リスク以上の Change-Resistance Results や、特定のテストの表明の弱さを調べる場合には、引き続き利用する。

この work item では、極端な変異の追加や、仕様を引くテストだけに絞った変異テストは作らない。
実際の書き起こし作業で必要性が確認された場合に、別の work item として扱う。

### 採用しない代替案

| 代替案 | 採用しない理由 |
| --- | --- |
| 仕様を引くテストの被覆を、仕様化済みのコードとみなす | 実行されたことと、仕様本文にその細部が書かれていることは異なる |
| 被覆を Pull Request のゲートにする | 実装詳細まで仕様を引くテストで実行することを求め、仕様とテストの粒度を歪める |
| 変異で殺せたコードを仕様化済みとみなす | テストの検出能力と、仕様文書の完全性を混同する |
| 仕様を引くテストを変更したら、仕様の変更を必須にする | fixture、helper、setup の変更でも意味が変わり得る一方、テスト本体のリファクタリングは仕様変更ではない |
| `affected_spec` があれば常に仕様差分を求める | 宣言済みの仕様に実装を合わせる正しい bugfix がすべて失敗する |
| 本番コードの変更には常に work item を求める | 構造を整える小さなコミットのたびに起票が必要になる。トレーラーで同じ問いに答えられる |
| work item のない変更を検査の対象外にする | work item のない修正が、宣言なしに振る舞いを変えられる |
| 本番コードへ仕様 ID を付ける | コメントを加えるだけで仕様との対応を満たせてしまう |
| `unspecified_code` の許可一覧を持つ | 「仕様」「実装詳細」に加えて第三の恒久的な状態を作り、仕様漏れを正当化しやすい |
| すべての細部を文書へ複製する | 変えても正しさが変わらない実装詳細まで二重管理になる |
| LLM でコードから仕様を一括生成する | 現在の挙動と意図した規範を区別できず、偶然の実装を規範にする |
| approval テストや golden master だけで挙動を固定する | 何を維持すべきかという意図を記録しない |

## 検証

- `mise run check-work-items`
- `mise run check`
- `mise run verify`

変更への耐性として、少なくとも次の誤実装を注入し、検査が失敗することを確認する。

- 本番コードを変更したコミットに、work item の宣言もトレーラーも要求しない。
- 存在するが変更していない任意の規範要素を `impact: modifies` に書くと通る。
- 引くテストがない任意の規範要素を `impact: conforms` に書くと通る。
- 差分に現れた規範要素を `affected_spec` に挙げなくても通る。
- `spec_impact: none` または `Spec-Impact: none` のまま規範シナリオを変更すると通る。
- TypeSpec のモデルの項目を変えても差分に現れない。
- 作業範囲を基準リビジョンからに固定し、先に main へ入れた仕様の変更を見失う。
- `spec_impact.reason` やトレーラーの理由が空、または定型句だけでも通る。
- `spec-review-candidates` が通常の全テストの被覆を使い、仕様を引かないテストが実行したコードを候補から外す。
- `spec-review-candidates` から `-coverpkg` を外し、別パッケージの仕様を引くテストによる実行を数えない。

`spec-review-candidates` は、候補がゼロになることを成功条件にしない。
出力が仕様漏れの断定ではなく、レビューの候補として表示されることを確認する。

## リスク

- `spec_impact: none` や `Spec-Impact: none` を誤って宣言すれば、機械検査だけでは仕様変更を見逃す。
  一般のコードから仕様上の意図を推論できないことによる限界である。
  理由に維持される振る舞いを具体的に書かせ、コードレビューでその判断を確認する。
- 理由が定型句になると、宣言は価値を失う。
  明らかな定型句は機械で拒否し、それ以外はレビューで判断する。
- `affected_spec` を広く列挙して検査を通すだけの運用になる場合がある。
  `modifies` は差分との照合で、`conforms` は同じ作業のテストとの照合で、実際の関係がない項目を拒否する。
- トレーラーの検査はコミットの範囲を読むため、コミット前の作業ツリーでは働かない。
  CI と `integrate-work-item` の `check` で検出する。
- `in_progress` になったコミットを作業範囲の起点にするため、work item のファイルの履歴を書き換えると起点を誤る。
  起点を求められない場合は、基準リビジョンへ黙って戻さず、検査の失敗として報告する。
- 導入時点で `in_progress` の work item は、`impact` の追記が必要になる場合がある。
  計画の 6 で一度に扱う。
- `spec-review-candidates` は、実行されているが仕様に書かれていない挙動を見つけない。
  完全な検出器として扱わず、観点表によるコード読解と組み合わせる。
- `spec-review-candidates` は、仕様ではない実装詳細も多く報告する。
  候補はゲートにせず、書き起こしの作業で四種類に分類する。
- コード外の既定値やライブラリの挙動は、被覆からは見つからない。
  観点表による読解で扱う。
- 既存コードを書き起こす過程で、現在の偶然の挙動を仕様として固定する危険がある。
  将来の実装が維持する義務を負うかを先に判断し、義務のない細部は実装詳細として仕様へ書かない。
