# 防護の検査を HTTP の外側からユースケース層へ届かせる

## Motivation

[[wi-390-security-control-test-standard-and-gate]] の R1 と R2 は、**`*echo.Context` を受け `error` を返し `WriteProblem` を書く関数**だけを防護として扱う。CSRF の欠陥がその形だったからである。

しかしテナント境界と認可の拒否は、HTTP の層だけで起きるのではない。ユースケース層は応答を書かず、センチネルを返して拒否する。`GetJobForAdmin` が `ErrJobNotFound` を返す、`DisableLifecycleWorkflow` が `ErrLifecycleWorkflowNotFound` を返す、といった形である。**この層で同じ種類の間違いが起きても、いまの検査は何も言わない。**

同じ種類の間違いとは 2 つある。

- **拒否を戻り値で伝えない。** ユースケースが拒否を検出しながら `nil` を返す、あるいはログだけ出して続ける。呼び出し元は成功として扱う。
- **呼び出し元が拒否を捨てる。** `_ = SomeUseCase(...)` や、返ったセンチネルを見ずに次へ進む。

HTTP の層でこれが起きたのが CSRF の欠陥だった。ユースケース層で起きない理由は無い。むしろこちらのほうが、応答という目に見える手がかりが無いぶん気づきにくい。

R1 は導入した日に HTTP 層で現存欠陥を 2 件見つけている。同じ規則が届いていない層に何が居るのかは、まだ誰も見ていない。

## Scope

- ユースケース層の防護を、HTTP 層と同じ性質で検査できるようにする。防護かどうかは名前ではなく、**呼び出し元がその戻り値で続行を決めているか**で判定する。この判定は wi-390 が既に持っている。
- 少なくとも次の 2 つを検出する。
  - 拒否のセンチネルを定義しながら、それを返さずに `nil` を返す経路を持つ関数。
  - ガード位置で呼ばれている関数の戻り値を、別の場所で捨てている呼び出し。
- 検出した欠陥を分類し、実装の誤りと検査の偽陽性を分ける。
- 偽陽性が多すぎて門にできない場合は、報告タスクとして出すことを許す。**ただしその判断は Design に理由とともに残す。** wi-390 が「副作用の不在」で同じ判断をしており、そこと同じ基準で決める。

## Out of Scope

- 新しい防護の追加。既にある拒否が伝わることを確かめる手段の整備に限る。
- 拒否の宣言の床と 137 件の分類。[[wi-391-refusal-declaration-floor-and-reinventory]] が持つ。
- 拒否テストへの副作用の不在の追加。[[wi-392-refusal-tests-assert-the-absent-effect]] が持つ。
- フロントエンド。`spec/authorization.md` が「UI での非表示は認可判定ではない」と定め、強制はサーバー側にある。UI が唯一の強制点になっている箇所は無い。

## Design

未定。着手時に次の 3 点を確定して本節に記録する。

1. **「拒否のセンチネル」の見分け方。** `Err*` という命名だけでは弱い。`errors.New` / `fmt.Errorf` で定義され、`errors.Is` で比較されている値、といった使われ方から導けるか。あるいは検出対象を「ガード位置で呼ばれる関数が `nil` を返しうる経路」に絞り、センチネルの分類を避けるか。
2. **偽陽性の量。** R2 は最初の試作で `_ = Save(...)` のような無関係な呼び出しを大量に拾い、`*echo.Context` を受ける関数に絞って初めて使い物になった。ユースケース層には応答を書くという手がかりが無いので、同じ絞り込みが効かない。試作して量を測ってから、門にするか報告に留めるかを決める。
3. **`_ = f()` を正当に書く場合の扱い。** 後始末や best-effort の呼び出しでは、戻り値を捨てるのが正しいこともある。除外の書き方 (コメントによる明示か、許可リストか) と、その除外が腐らない仕組みを決める。

## Plan

- 試作を先に書き、偽陽性の量を測る。量を見てから門にするかを決める。順序を逆にすると、使えない門を入れてから外すことになる。
- 検出した欠陥は wi-390 と同じ扱いにする。検査を通すために必要な分は本 work item で直し、それ以外は切り出す。

## Verification

- `mise run check`
  - reason: 追加した規則が既存の検査群と同じ門で動くこと (門にすると判断した場合)。
- `mise run test-tools`
- `mise run verify`
- 手動: ユースケース層の防護を、拒否を検出しながら `nil` を返す形へ一時的に変え、検査が落ちることを確認する。落ちなければ、この work item は目的を果たしていない。
- 手動: 正当に戻り値を捨てている呼び出しを 1 つ選び、検査が落ちないことを確認する。偽陽性で使えなくなっていないことの確認である。

## Risk Notes

リスクは medium。**偽陽性で使えなくなる危険がもっとも大きい。** ユースケース層には「応答を書く」という手がかりが無いので、HTTP 層で効いた絞り込みが使えない。絞り込みが甘いまま門にすると、開発者は除外を書いて先へ進み、検査は名目だけになる。試作で量を測るまで門にしないことを Plan に置いたのはこのためである。

門にできないと判断した場合、報告タスクに留めること自体は妥当である。ただし wi-390 の Risk Notes が書いたとおり、**読まれる文書ではなく落ちる検査にすることがこの一連の要**であり、報告に留めるならその理由を Design に残す。理由を残さずに報告へ落とすと、次に読む者には「やらなかった」としか見えない。
