# 受理する設定値と、実際に動く設定値の食い違いを検出する

## Motivation

`mise run verify` を全部通しながら、**設定できるのに何も起こらない選択肢**がいくつも残っていた。2026-08-30 に閉じた 9 件の bugfix のうち、少なくとも 3 件がこのクラスである。

| work item | 受理される設定 | 実際 |
|---|---|---|
| [[wi-440-outbound-scim-oauth2-client-credentials-unimplemented]] | `auth_method=oauth2_client_credentials` | トークン取得の経路が無く、`client_secret` をそのままベアラートークンとして送っていた |
| [[wi-441-push-groups-produces-no-delivery]] | `push_groups=true` | Group の配信を生む経路がどこにも配線されていない |
| [[wi-439-outbound-scim-resource-body-omits-schemas]] | 属性対応付け | `schemas` を書ける文法が無いので必ず欠落する |

**このクラスは既存の門番をすべて素通りする。** 型は通る (列挙値は妥当)、契約は通る (TypeSpec は値を宣言している)、`check-security-controls` は拒否だけを見る、カバレッジは「触れた行」しか数えない。

`wi-440` の実測がその典型である。変更前に `oauth2_client_credentials` に触れるテストは 1 件だけで、内容はこれだった。

```go
func TestProvisioningAuthMethod_Valid(t *testing.T) {
    for _, m := range []ProvisioningAuthMethod{AuthBearerToken, AuthOAuth2ClientCredentials} {
        if !m.Valid() { ... }
```

**列挙値が妥当であることだけを検査していて、緑のまま通り続けていた。** 受理する側の検査だけがあり、受理したものがどう使われるかを見る検査は 1 件も無い。この形は「認証方式は検査済み」に見えるぶん、無いよりも悪い。

同じ穴は work item の作業中にも再現した。`wi-440` で受け入れ検査を 6 件書いたにもかかわらず、**そのすべてが供給元を直接組み立てており、認証方式から供給元を選ぶ分岐を 1 つも通っていなかった**。元の欠陥そのものを戻す変異が生存したことで初めて分かった。人が気をつけるだけでは閉じない。

## Scope

- 挙動を選ぶ列挙と機能フラグを列挙する。対象は「値によって実行される経路が変わる」もので、表示上の区分や状態の記録だけのものは含めない。
- 各値について、その値を選んだときにだけ通る経路を実行するテストが在ることを要求する。`check-security-controls` が拒否の宣言に対して行っているのと同じ形にする。
- 満たせない値は、宣言側で `unimplemented` として明示させる。宣言が無く、テストも無い値を落とす。
- 現在のツリーの違反を洗い出し、許可リストではなく個別の work item として切り出す。

## Out of Scope

- 「テストが在る」の質を測ること。この検査が言えるのは経路が実行されたことまでで、正しさは変異試験と証拠契約が持つ。
- 挙動を選ばない列挙 (状態、種別、表示区分)。対象を広げると通すためだけの検査が増える。
- 対象を Go 以外へ広げること。まず backend の列挙と機能フラグで閉じる。

## Design

未定。着手時に、対象の見つけ方 (TypeSpec の enum を起点にするか、Go の型を起点にするか) と、宣言の置き場所を確定して本節に記録する。

`check-security-controls` の先例が近い。あちらは「拒否を宣言したなら、それを証明するテスト名を挙げよ」という形で、宣言と証拠の対応を機械的に見る。同じ形で「挙動を選ぶ値を宣言したなら、その経路を通るテスト名を挙げよ」と言えるはずである。

## Risk Notes

リスクは medium。検査そのものは製品の振る舞いを変えないが、対象の取り方を誤ると 2 つの向きに失敗する。広すぎると、通すためだけの薄いテスト (`Valid()` を呼ぶだけの検査) が量産され、Motivation が問題にした形そのものを増やす。狭すぎると素通りする。**「その値を選んだときにだけ通る経路を実行したか」を要求の中心に置くこと** —— 値の妥当性ではなく、値が選ばせる経路が判定の対象である。
