# `spec/` と `docs/` の境界を、名前から読める形にする

## Motivation

[DOCUMENTATION_GUIDE.md](../DOCUMENTATION_GUIDE.md) §4 は文書の置き場所を 3 つに分ける。`spec/`（境界の宣言、用語、規範、状態遷移、判断、機構、シナリオ、TypeSpec）、`docs/`（product-overview、build、ci、testing）、`operations/`（SLO、リリースと後退、バックアップ、Runbook）である。

**区別の基準そのものは筋が通っている。** §5.9 がそれを書いている。

> 判定は「**それが変わったとき、外部から観測できる振る舞いか、守るべき境界が変わるか**」である。

`spec/` は Yes、`docs/` は No。原理としては明確である。

**問題は名前がその基準を裏切っていることである。** `docs` は「文書すべて」と読める語だが、`spec/` の中身の大半——`decisions.md`、`internals.md`、`scenarios.md`、`glossary.md`——は、読み手の素朴な感覚ではどう見ても「文書」である。ディレクトリ名を見た人が `decisions.md` を `docs/` に置こうとするのは誤読ではなく、名前がそう誘導している。§5.9 の基準へ辿り着いて初めて、そうではないと分かる。**基準を読まないと使えない構成は、構成として弱い。**

さらに悪いことに、**ガイド自身の参照実装であるこのリポジトリに `docs/` も `operations/` も無い。**

| ガイドが置く場所 | このリポジトリの実態 |
|---|---|
| `docs/build.md`、`docs/ci.md`、`docs/testing.md` | `DEVELOPMENT.md`（ルート）、`README.md` の「主なコマンド」、`mise.toml` |
| `docs/product-overview.md` | `README.md`（[[wi-404-repository-entrance-documents-are-missing]] で「対象外」節を追加） |
| `operations/runbooks/` | `infra/runbooks/` |
| `operations/backup-and-recovery.md` | `infra/runbooks/backup-restore-dr.md` |
| `operations/reliability.md` | 無い。サービス目標は `spec/capacity.md` にある（[[wi-400-service-objectives-need-stable-ids]]） |

実態は偶然の寄せ集めではなく、**一貫した別の規則**になっている。**手順は、それが動かすものの隣に置く。** Kubernetes と監視の手順は `infra/README.md`、UI の指針は `frontend/README.md`、スキーマ運用は `infra/schema/README.md`、障害手順は `infra/runbooks/`。この規則は `docs/` に集める案より優れている点がある。手順を読む人はたいてい対象のディレクトリを開いており、そこに手順があれば探さずに済む。

[[wi-404-repository-entrance-documents-are-missing]] の Design 1 は、対象外 3 行を置くためにこの未決着へ突き当たり、「このリポジトリの実態に合わせる」で回避した。**回避であって解決ではない。** 次に同じ種類の文書を足す人が、同じところで同じ時間を使う。

## Scope

- §4 のディレクトリ構成と、§10（開発文書）・§11（運用文書）を、**`spec/` と手順文書の区別が名前から読める形**に改める。
- §5.9 の判定基準を、`spec/` に入れないものの節だけでなく、構成を示す節からも参照できるようにする。基準を読まないと構成が使えない状態を解消する。
- 「手順は、それが動かすものの隣に置く」を、案として書くか規則として書くかを決めて反映する。
- `operations/` の扱いを同時に決める。Runbook をインフラ資材の隣に置く構成をガイドが許すかどうかは、`docs/` と同じ問いである。
- §13 の参考と §15 の導入順序に、構成の変更が波及していないか確認する。

## Out of Scope

- **このリポジトリのファイルの移動。** 本 work item はガイドを直す。レイアウトを変える判断は、ガイドが直った後に、必要なら別の work item が持つ。
- `SPECIFICATION_FORMAT.md` の `ROOT_DOCUMENTS` / `CONTEXT_DOCUMENTS` と、それを強制する `tools/check/src/specification-doc.ts`。**閉じた集合は `spec/` の内側の話であり、`spec/` と手順文書の境界とは別の問題である。** どの案を採っても、この集合は触らずに済む。
- 方法論文書（`DEVELOPMENT.md`、`SPECIFICATION_FORMAT.md`、`WORK_ITEM_FORMAT.md`）自身の置き場所。別リポジトリへ抽出する想定があるため、`docs/` を作るかどうかとは独立に決まる。
- `spec/scenarios.md` の新設（[[wi-401-cross-context-scenarios-have-no-home]]）とサービス目標の正本化（[[wi-400-service-objectives-need-stable-ids]]）。どちらも `spec/` の内側の話である。

## Design

未定。着手時に次の 3 点を確定して本節に記録する。**候補は 3 案あり、いずれも「基準は正しい、名前が悪い」という同じ診断から出ている。**

1. **どの案を採るか。**

   | 案 | 内容 | 得るもの | 失うもの |
   |---|---|---|---|
   | (a) すべて `docs/` に寄せる | `spec/` を廃し 1 か所にする | 読み手が迷う分岐が消える | **基準ごと失う。** `spec/` の価値は正規文書の集合が閉じていて、それ以外を検査が拒否することにある。`build.md` を同じ階層に入れるなら集合を開くか、1 階層下で分けるかで、分割が戻る |
   | (b) `spec/` を TypeSpec だけにする | Markdown を `docs/` へ | 名前が中身と一致する | `scenarios.md` と `decisions.md` が言語非依存の正本という位置づけを失う。[DEVELOPMENT.md](../DEVELOPMENT.md) §5 が併置の理由を「backend、frontend、worker、外部実装が同じ言語非依存の正本を見るため」と述べており、これは実際に効いている性質である |
   | (c) `docs/` という名前をやめる | 手順であることを名前で言う（`development/` など）、あるいは `docs/` を prescribe しない | 基準と閉じた集合を保ったまま誤読を消す | ガイドの構成図が「置き場所を 1 つに決めてくれる」度合いは下がる |

   **(c) に寄せるのが妥当と見込む。** ただし (c) の中でも「名前を変える」と「prescribe をやめる」は別の判断である。後者は、手順の置き場所をプロジェクトに委ねて基準だけを与えることを意味する。

2. **`operations/` をどうするか。** Runbook を `infra/runbooks/` のようにインフラ資材の隣へ置く構成は、「手順は動かすものの隣」の規則からは自然だが、当番担当者が障害の最中に探す先としては 1 か所にまとまっているほうがよい。§11 の冒頭は「当番担当者が障害の最中に読むものと、実装者が変更の前に読むものを同じ場所へ置かない」と書いており、**読み手で分ける規則と、対象で分ける規則が競合している。** どちらを優先するかを決める。

3. **ガイドをリポジトリ非依存に保つ制約との両立。** DOCUMENTATION_GUIDE.md は特定のリポジトリに依存しない形で書く方針である（§冒頭）。したがって「このリポジトリは `infra/runbooks/` に置いている」とは書けない。**実態から得た知見を、一般的な規則として言い直す必要がある。** 「手順は、それが動かすものの隣に置く」はその形になっているが、規則として述べたときに本当に一般に成り立つかを確かめる。

## Verification

- `mise run verify`
- 手動: `DOCUMENTATION_GUIDE.md` 内の節番号への参照（§5.9、§9.2、§11.1 など）が、構成を変えた後もすべて実在する節を指していることを確認する。**節を動かすと、この種の参照が静かに壊れる。**
- 手動: 直した §4 だけを読んで、`decisions.md` と `build.md` をそれぞれどこへ置くかが判断できるかを確かめる。§5.9 を読まないと判断できないなら、この変更は目的を達していない。
- 手動: このリポジトリの実際の配置（`DEVELOPMENT.md`、`infra/runbooks/`、`frontend/README.md`）が、直した後のガイドに照らして違反でないことを確認する。違反になるなら、ガイドと参照実装のどちらを直すかを Design へ追記する。

## Risk Notes

リスクは low。方法論文書 1 つの構成の節を直す変更であり、製品にも仕様にもリポジトリのレイアウトにも触れない。

**失敗の形は、診断を取り違えて基準のほうを緩めることである。** 「`spec/` と `docs/` が分かりにくい」という訴えに対して最も安易な応答は 1 案 (a)——1 か所にまとめる——だが、それは分かりにくさの原因だった**基準ごと捨てる**ことになる。正規文書の集合が閉じていて検査が守っている性質は、このリポジトリで実際に機能している数少ない仕組みの 1 つである。名前の問題を構造の変更で解こうとしない。

もう 1 つは、**ガイドだけを直してリポジトリを放置し、両者が食い違ったままにすること**である。Verification の最後の手動確認は、そのための歯止めである。食い違うなら、どちらを直すかをこの work item の中で決めて記録する。決めずに終えると、次に読む人は「ガイドと実態が違う」という同じ発見を最初からやり直す。
