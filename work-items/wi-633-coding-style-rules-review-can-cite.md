# レビューが引用できるコーディング規則を `docs/development/coding-style.md` に置く

## 動機

`DOCUMENTATION_GUIDE.md` §8.3 は `docs/development/coding-style.md` を置くと定める。
このファイルは無い。
`docs/development/` にあるのは README、仕様先行の開発ワークフロー、ローカル開発、継続的インテグレーション、テスト方針、リリース、開発プロセスの計測の 7 件で、コードの書き方を扱うものは一つも無い。

規則が無いまま書かれたコードは、backend の実装だけで 1627 ファイル、12 万行ある。
frontend の TypeScript は 465 ファイルである。
この量の大半をエージェントが書く。
人は前後のファイルを読んで書き方を揃えるが、エージェントが読むのは与えられた文書と直近の文脈だけなので、揃える相手が依頼ごとに変わる。

コードの書き方に関わる規則は、現在は四つの層に分かれていて、どれも別の問いに答えている。

| 層 | 一次情報源 | 決めていること |
| --- | --- | --- |
| 設計 | `docs/design/application/design-guidelines.md` | モジュールの深さ、Seam とポート、Aggregate 境界、型の所有、作用の境界、エラーと拒否 |
| 工程 | `docs/development/specification-first-workflow.md` | リファクタリングを行う時点と、それが独自の証拠を持たない理由 |
| 言語 | `.claude/rules/japanese-writing.md` | コメントと説明文をどの言語で書くか |
| 機械 | `.golangci.yml`、`frontend/biome.json` | 整形と静的検査が拒否する形 |

空いているのは設計の層と機械の層の間である。
命名、コメントに何を書くか、関数と制御構造の形、重複を許す条件、整頓と振る舞いの変更の分離、テストコードの読みやすさは、どの層も持たない。
これらは lint が判定できず、モジュール境界の設計判断でもなく、レビューで指摘する対象である。

この空白はレビューの側にも現れる。
`code-review` スキルは、リポジトリが文書化した規則を探し、見つからない場合は Fowler の code smell の一覧を既定の基準として使う。
このリポジトリは今その既定の基準で読まれているので、レビューのたびに一般論から議論が始まる。
100 行を超える関数が 20 件あり、その上位は `backend/shared/http/server_http/routes.go` の経路登録と `backend/cmd/` 配下の起動処理である。
長さだけを基準にすればこれらは指摘になり、組み立てを行う関数は長くてよいと考えれば指摘にならない。
どちらを採るかをリポジトリが答えていないため、同じ判断が変更のたびに繰り返される。

## 対象範囲

- `docs/development/coding-style.md` を新設する。lint と整形器が強制できる規則は書かず、強制できない規則と、理由を言わなければ守られない規則を持つ。
- 扱う主題は、命名、コメントの密度と内容、関数と制御構造の形、重複と抽象化の判断、整頓と振る舞いの変更の分離、テストコードの書き方、依存を足すときの基準とする。
- 規則ごとに理由を書く。lint が強制しているものは規則名を併記し、どちらが強制点かを示す。
- 出発点として Go と TypeScript の公開された規約を名指しし、そこから外れる点と、そこが決めていない点だけを書く。
- 規則の根拠として参照する書籍を明示する。Kent Beck『Tidy First?』、Martin Fowler『リファクタリング』、Dustin Boswell と Trevor Foucher『リーダブルコード』、Steve McConnell『Code Complete』、Robert C. Martin『Clean Code』、John Ousterhout『A Philosophy of Software Design』、Michael Feathers『レガシーコード改善ガイド』を対象とする。
- 規則を Comprehensibility、Locality、Cohesion、Encapsulation、Testability、Changeability、Simplicity の 7 軸へ整理し、軸ごとに文献の該当箇所を読んで判断原則へ落とす。
- 既存の四つの層との担当を決め、同じ規則を二か所に書かない。
- 入口を配線する。`docs/development/README.md` の表へ 1 行、`AGENTS.md` へ 1 行、`CONTRIBUTING.md` のレビュー観点へ参照を足す。

## 対象外

- lint と整形器が強制できる規則の文書化。強制点が動かないので、書いても文書が増えるだけになる。
- 新しい lint 規則の追加と `.golangci.yml`、`frontend/biome.json` の変更。文書が固まってから、どの規則を機械へ移せるかを別に判断する。
- `docs/design/application/design-guidelines.md` が持つ設計レベルの規則の移設と改訂。
- テスト水準、実行境界、テストダブルの規則。`docs/development/testing.md` が持つ。本項目が扱うのはテストコードの読みやすさだけである。
- Seam の定義と、特性化テストの適用条件。前者は `design-guidelines.md`、後者は `testing.md` が既に持つ。『レガシーコード改善ガイド』から採るのは、テストを書ける形で新しいコードを書くための基準だけとする。
- 言語ごとのファイル分割。`DOCUMENTATION_GUIDE.md` §8.3 の通り、実際に衝突するまで一つのファイルで書く。
- 既存コードの一括是正。決めた規則は以降の変更へ適用し、触らない場所は書かれた時点の形のまま残す。
- コーディング規則の機械検査の新設。規則が文になる前に検査を書くと、検査できる形の規則だけが残る。

## 設計

### 文書が持つ主題と持たない主題

新しい文書は、レビューで指摘しうるが lint が判定できないものだけを持つ。
下表の右列は、同じ語が出てくるが担当が別である場所を示す。

| 主題 | `coding-style.md` が決めること | 決めない側と一次情報源 |
| --- | --- | --- |
| 命名 | 何を名前に含め、何を含めないか。略語、真偽値、副作用のある関数の名付け | 外部契約の名前は TypeSpec、ドメイン語彙は各 `glossary.md` |
| コメント | 何を書き、何を書かないか。密度の判断基準 | 記述する言語は `.claude/rules/japanese-writing.md`、被覆の宣言は `//spec:covers` の規約 |
| 関数と制御構造 | 一つの関数が混ぜてよい抽象の水準、早期 return、入れ子の深さ | モジュールの深さと情報隠蔽は `design-guidelines.md` |
| 重複と抽象化 | 重複を残してよい条件と、抽象へ寄せる条件 | Seam を置く条件は `design-guidelines.md` |
| 整頓 | 振る舞いを変えない整頓を、振る舞いの変更と同じ変更に混ぜない書き方 | 整頓を行う時点と証拠の扱いは `specification-first-workflow.md` |
| テストコード | テスト名、前提の並べ方、失敗時に読む人が得る情報 | 水準、実行境界、テストダブルは `testing.md` |
| 依存の追加 | 依存を足すときに確かめること | 依存の更新手順は `update-all-dependencies` skill |

### 規則を整理する軸

主題は担当の境界を決めるが、規則の並び順にはならない。
命名の規則もコメントの規則も、読み手が何を得るかという同じ問いへ答えるからである。
文書の中では、規則を次の 7 軸で並べる。

| 軸 | 規則が答える問い | 該当する主題 | 主に読む文献 |
| --- | --- | --- | --- |
| Comprehensibility | 名前と本体だけで、書き手の意図が読めるか | 命名、コメント | 『リーダブルコード』、『Code Complete』 |
| Locality | 一つの変更のために読む必要があるものが、近くにあるか | 宣言の位置、関数と制御構造 | 『Code Complete』、『A Philosophy of Software Design』 |
| Cohesion | 一つの単位が、一つの理由で変わるか | 関数と制御構造、重複と抽象化 | 『リファクタリング』、『Clean Code』 |
| Encapsulation | 呼び出し側が知る必要のない事実が漏れていないか | 関数と変数の可視性、型の使い方 | 『A Philosophy of Software Design』 |
| Testability | テストを書くために本体を書き換える必要がないか | 依存の受け取り方、テストコード | 『レガシーコード改善ガイド』、『Clean Code』 |
| Changeability | 次の変更が一か所で済むか | 重複と抽象化、依存の追加 | 『リファクタリング』、『レガシーコード改善ガイド』 |
| Simplicity | 取り除いても意味が変わらない要素が残っていないか | 整頓、制御構造 | 『Tidy First?』、『A Philosophy of Software Design』 |

軸は文書の並び順であり、規則に付ける分類ラベルではない。
一つの規則が二つの軸へ効く場合は、強く効くほうへ置いて他方から参照する。
軸の名前を frontmatter や検査へ持ち込まないのは、分類が合っているかを誰も判定できず、分類のための議論だけが残るためである。

Encapsulation と Testability は、設計の側を `design-guidelines.md` が既に持つ。
この文書が扱うのは関数と変数の水準に限り、モジュールの深さ、Seam の位置、ポートの有無には踏み込まない。

### 参考文献の扱い

7 冊は規則の根拠として名指しし、本文を写さない。
写した規則は原典が更新されても更新されず、どちらが正しいかを後から決められなくなる。

実装では、軸ごとに該当する文献を実際に読み、そこから判断原則の形へ落とす。
判断原則の形とは、書き手が判断すべき問いと、迷ったときにどちらへ倒すかの二つである。
記憶から書いた要約は、原典の主張と、このリポジトリで既に決まっていることの区別を失う。

7 冊は互いに矛盾する箇所を持つので、並べて紹介するとレビューで両側が引用でき、規則として働かない。
次の三点については、この文書がどちらを採るかを書く。

| 論点 | 対立 | この文書が採る形 |
| --- | --- | --- |
| 関数の長さ | 『Clean Code』は短さ自体を規則にする。『A Philosophy of Software Design』は、分割が浅いモジュールを増やして呼び出し側の負担になると退ける | 行数の上限を置かず、一つの関数が混ぜている抽象の水準と、名前が本体を要約できるかを基準にする |
| コメント | 『Clean Code』はコメントを、コードで表せなかった失敗の兆候として扱う。『A Philosophy of Software Design』は、インターフェースから読み取れない設計上の判断を記録するものとして扱う | 後者を採る。コードが答えられる問いは書かず、なぜその形を選んだかと、呼び出し側が知る必要がある前提を書く |
| 重複 | 『リファクタリング』は重複を smell として扱う。『Tidy First?』は、まだ形の定まらない重複をまとめる費用を問題にする | 二度目では寄せず、三度目に寄せる。寄せない判断を書き残す必要がある場合だけコメントを置く |

採る側を決める根拠は、このリポジトリの現状から採る。
100 行を超える 20 件の関数の上位が経路登録と起動処理であることは、長さの上限が最初に当たる場所が組み立て専用の関数であることを示す。
組み立てを分割しても、分割した断片は一度しか呼ばれず、呼び出し側は分割前と同じ全体を読むことになる。
したがって長さは基準にならない。

### 規則の書式

規則ごとに、規則、理由、強制点の三つを書く。
理由の無い規則は、状況が変わったときに緩めてよいかを判断できず、lint へ移せるかどうかも判断できない。
強制点には lint 規則名かレビューのどちらかを書き、両者を混同させない。

実例はリポジトリの既存コードから採る。
`docs/development/` は work item への参照を許す区画なので（`tools/check/src/docs-work-item-links.ts` の除外一覧）、判断の経緯が要る箇所では work item を引用できる。

### 人向けとエージェント向けを分けない

同じ規則を二つの文書に書くと、片方だけが更新される。
エージェントが読めて人が読めない形、またはその逆になる書き方は、この主題には無い。
規則、理由、強制点の三つ組は、レビューで人が引用する形であり、エージェントが照合する形でもある。

エージェント側は文書を読む入口だけを必要とするので、`AGENTS.md` には 1 行だけ置く。
`AGENTS.md` を薄く保つのは既存の方針である。

### 採らない案

| 案 | 退ける理由 |
| --- | --- |
| ルート直下に `CODING_STANDARDS.md` を置く | `DOCUMENTATION_GUIDE.md` §8.3 が配置を `docs/development/` と定めている。ルート直下の規約文書は [[wi-629-one-source-for-the-document-layout-and-format-rules]] が減らしている最中であり、逆向きに増やすことになる |
| ADR として記録する | `new-work-item` の手順は ADR を作らない。変更固有の判断は work item が持つ |
| `.agents/skills/` に skill として置く | skill は呼ばれたときだけ読まれる作業手順であり、コードの性質を述べる規則の置き場所ではない。人がレビューで引用する経路も無い |
| 7 冊の要約を文書へ収める | §8.3 が禁じる書き起こしそのものになる。原典より粗い要約が、原典の更新から切り離されて残る |
| 軸を規則の分類ラベルとして検査する | 分類の当否を判定できる人がいない。軸は並び順としてだけ働かせる |

## 計画

作業は次の順に進める。

1. 上表の担当を確定し、四つの既存文書に重なる記述が無いことを確かめる。重なりが見つかった場合は、新しい文書ではなく既存の側を一次情報源として参照する。
2. 軸ごとに、該当する文献の当該箇所を読み、判断すべき問いと、迷ったときに倒す側の組へ落とす。原典の主張と、このリポジトリが既に決めていることが食い違う箇所は、食い違いとして書き出す。
3. 軸の順に規則を書く。規則は、既存コードから実例を引けるものだけを置く。実例を引けない規則は、このリポジトリで起きていない問題への予防であり、置かない。
4. `docs/development/README.md`、`AGENTS.md`、`CONTRIBUTING.md` の入口を配線する。
5. 検証する。

作るものを変えうる問いは着手前に解決した。
コメントの言語は `.claude/rules/japanese-writing.md` が持ち続け、新しい文書は密度と内容だけを持つ。
テストの水準は `docs/development/testing.md` が持ち続け、新しい文書はテストコードの読みやすさだけを持つ。
規則の粒度は、実例を引けるかどうかで決める。

## リスク

規則が増えるほど、守られない規則が混ざる危険が増える。
実例を引けるものだけを置く制約は、この危険に対する歯止めである。

既存コードの大半は規則より先に書かれている。
文書が現状の記述だと読まれると、実例と異なる箇所を見た人が文書を疑う。
文書の冒頭で、規則が以降の変更へ適用されるものであり、既存コードの一括是正を求めないことを述べる。

機械検査が無いので、規則と実装の乖離は検出されない。
乖離が積もる場合は、規則を lint へ移すか、規則を落とすかを別の work item で判断する。
