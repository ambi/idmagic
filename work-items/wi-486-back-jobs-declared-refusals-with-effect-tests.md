# Jobs が宣言する未検証の拒否 2 件に効果まで確かめるテストを与え、台帳から外す

## Motivation

`tools/check/example-coverage-debt.json` は、どのテストからも id を引用されていない規範 id を保持する、縮むだけの台帳である。

このうち 102 件は [[wi-390-security-control-test-standard-and-gate]] が拒否専用の台帳へ据え置いた分で、[[wi-490-fold-refusal-coverage-into-one-normative-coverage-rule]] が網羅台帳へ統合した。

その 102 件のうち 2 件が Jobs の拒否である。

2 件はどちらも HTTP のリクエストではなく `worker` の内部で起きる拒否であり、この点で他の Context と性質が違う。

`REQ-JOBS-006` は、ハンドラーが誤って他テナントの Aggregate ID を渡されたとき、`handler_execution_context.tenant_id` との不一致で操作を拒否することを宣言している。

これは非同期実行におけるテナント境界の最後の砦である。

同期のリクエスト経路と違い、ここには利用者のトークンも Origin も無いため、境界は実行文脈と対象の突き合わせだけで保たれている。

素通りすれば、あるテナントのジョブが別テナントのデータを書き換える。

`REQ-JOBS-010` はレーン未登録および重複登録の JobKind を検出して `worker` の起動を失敗させることを宣言している。

これはフェイルクローズであり、素通りすれば、どのレーンにも属さないジョブが黙って実行されないまま滞留するか、意図しないレーンで実行される。

拒否の効果が「プロセスが起動しないこと」である点も、この Context に固有である。

この 2 件はいずれも nearby に分類され、同じエラー型名を引用しているテストは 1 件も無い。

そして注記だけを足す解消は、この項目では認めない。

## Scope

- 台帳の Jobs の 2 件それぞれについて、宣言された拒否に production と同じ入口 (`worker` の実行経路と起動処理) から到達するテストを用意する。
- `REQ-JOBS-006` は、拒否の後に対象テナントのデータが変わっていないことを確かめる。
- `REQ-JOBS-010` は、起動が失敗すること、およびその状態でジョブが 1 件も処理されないことを確かめる。
- 各テストのソースに対応する `REQ-JOBS-NNN` を書く。
- 対応が取れた id を `tools/check/example-coverage-debt.json` から削除する。
- 拒否を実装が持っていないと判明した場合、その防護をこの項目で実装する。
- 完了時点で、この項目が持つ id が台帳から 1 件残らず消えていることを確認する。

## Out of Scope

- 他 Context の拒否。
  Context ごとに別の work item が持つ。
- 102 件を 1 つの単位として消化すること。
  [[wi-399-burn-down-untested-refusal-debt]] がその形で立てられているが、進める単位を未決のまま残し、注記だけの解消も認めている。本項目はその置き換えである。
- 同じ台帳に載る、この項目が持たない id。
  規則は同じだが、引き取る範囲はここに挙げた id に限る。
- R1、R2、R4 の検査そのものの変更。
  [[wi-390-security-control-test-standard-and-gate]] と [[wi-391-refusal-declaration-floor-and-reinventory]] が持つ。
- 既存テストへ `REQ` id を注記するだけで台帳から外すこと。
  この項目ではこれを解消として扱わない。
- レーンの構成、優先度、流量の設計変更。

## Design

### 解消の条件

1 件の id を台帳から外してよいのは、次の 3 つがすべて成り立つときだけとする。

第 1 に、テストが production の使う入口から入り、宣言された拒否の判断を実際に通ること。

Jobs の入口は `worker` がジョブを取り出してハンドラーを呼ぶ経路と、`worker` の起動処理である。

ハンドラーを直接呼ぶテストは、実行文脈を組み立てる部分を飛ばすため、この条件を満たさない。

第 2 に、拒否が変えなかったものをテスト自身が読み直して確かめること。

第 3 に、シナリオの id をテストのソースが引用していること。

### 拒否ごとに「変わっていないこと」として何を読むか

| REQ | 宣言している拒否 | 読み直して確かめる対象 |
|---|---|---|
| REQ-JOBS-006 | 実行文脈と対象 Aggregate の `tenant_id` 不一致で操作を拒否 | 対象テナントのデータが変更されておらず、ジョブが成功として記録されていない |
| REQ-JOBS-010 | レーン未登録および重複登録の JobKind で `worker` の起動を失敗させる | `worker` が受付を始めておらず、キューのジョブが 1 件も処理されていない |

`REQ-JOBS-006` の「成功として記録されていない」を併せて読むのは、拒否したうえで成功扱いにする実装を排除するためである。

非同期のジョブは呼び出し元へ応答を返さないため、実行結果の記録が唯一の観測点になる。

拒否がその記録に現れなければ、運用側からは何も起きなかったのと区別できない。

`REQ-JOBS-010` は、起動が失敗した状態でキューにジョブを積み、処理されないことまで読む。

起動処理だけを呼んでエラーを確かめるテストは、実際には受付が始まっている実装を見逃す。

### 却下した進め方

**テナント境界を、Aggregate の取得処理の単体テストで確かめる案。**

取得が正しくても、ハンドラーが実行文脈を渡していなければ素通りする。

wi-390 の欠陥と同じ形である。

**起動の失敗を、レーン登録表の検証関数だけで確かめる案。**

検証が正しくても、起動が続行していれば防護になっていない。

**拒否の記録を確かめずに完了とする案。**

非同期実行では記録が唯一の観測点であり、これを欠くと拒否が見えない。

## Plan

1. 2 件のシナリオを読み、`worker` の実行経路と起動処理のどこで拒否が起きるべきかを確定する。
2. 2 つのテナントのジョブを混在させる固定具を用意する。
3. テナント境界の 1 件 (006) から着手し、テストが RED になることを先に観測する。
4. 起動時の拒否の 1 件 (010) を、未登録と重複登録の両方で進める。
5. 拒否の記録が残らない実装だった場合は、記録を残す形へ修正する。
6. 対応の取れた id を台帳から削除し、この項目が持つ id が 1 件も残っていないことを確認する。

## Risk Notes

`worker` の起動を伴うテストは、失敗の観測が時間依存になりやすい。

起動処理の戻り値と、受付が始まっていないことの両方を観測し、待ち時間には依存させない。

非同期実行の拒否は呼び出し元に応答が返らないため、テストが「何も起きなかった」と「拒否された」を取り違えやすい。

記録の有無で区別する。

台帳は id 順に 1 エントリー 1 id なので、Context ごとの work item が並行しても衝突はエントリー単位に収まる。

各項目は自分が持つ id のエントリーだけを削除し、コメント配列と他の id には触れない。
