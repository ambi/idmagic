# 並行性の不変条件を、設計時のモデル検査と実行時の決定的シミュレーションで確かめる

## Motivation

このリポジトリは、形式手法を導入する前提条件を意図せず既に満たしている。`states.md` が言語非依存の状態表と遷移表を正本として持っているからである。形式仕様を書くときに最も費用がかかるのは状態と遷移を洗い出す工程であり、それが済んでいる。

同時に、いま最も検証が薄いのは並行実行の絡む不変条件である。3 つの具体例がある。

第一に、DataKeys の鍵ローテーションである。`docs/database.md` は「ローテーションは登録された移行処理ごとにジョブを自動投入し、いずれかの移行処理が残件を報告している間はラップされた DEK の消去を拒否する」と述べる。これは複数の並行ジョブ、複数の Context にまたがる `FieldMigrator`、そして不可逆な破棄が絡む不変条件であり、例に基づくテストで網羅することは実質的に不可能な種類のものである。破られたときの結果は復号不能なデータである。

第二に、Jobs のリースと完了報告の競合である。`docs/contexts/jobs/decisions.md` は「停止時の回復は明示的な再投入ではなく、リースの自然な期限切れに委ねる。停止処理の打ち切りとハンドラーの完了が競合すると、再投入が二重実行の余地を作るからである」と述べている。設計判断の理由そのものが競合であるなら、その判断が正しいことは競合を扱える道具で確かめるのが筋である。

第三に、認可コードと PAR の `request_uri` の一度限りの使用である。`docs/contexts/oauth2/internals.md` が TTL と一度限りの使用を定めているが、同時到達する 2 つの交換要求のいずれか一方だけが成功することは、並行性の性質であって単体のテストでは押さえきれない。

設計時の検証（モデル検査）と実行時の検証（決定的シミュレーション）は別物であり、どちらも必要である。前者は仕様の不変条件が状態空間のどこかで破れることを見つけ、後者は実装がその仕様どおりに動くことを、順序と障害を制御した再現可能な環境で確かめる。`docs/development/specification-first-workflow.md` が既に「時刻、乱数、識別子生成、設定、永続化、通知を明示的な入力またはポートとして識別せよ」と定めているため、後者の前提条件も部分的に揃っている。

## Scope

- **モデル検査の対象の限定**：DataKeys の鍵ローテーションと Jobs のリースの 2 つに絞って形式仕様を書き、不変条件を検査する。
- **仕様の置き場所**：形式仕様をリポジトリのどこに置き、`states.md` とどう対応させるかを決める。両者が食い違ったときにどちらが正本かを明示する。
- **検査の実行経路**：`mise` のタスクとして実行できるようにする。常時のゲートに入れるかどうかは実行時間を見て判断する。
- **決定的シミュレーションの範囲の判断**：worker の異常終了、リースの期限切れ、完了報告の順序入れ替えを制御できる試験環境を作れるかを調査し、費用が見合うかを判断する。
- **見つかった欠陥の扱い**：モデル検査が仕様の欠陥を見つけた場合、その是正を別の work item として切り出す手順を決める。

## Out of Scope

- 暗号プロトコルの形式検証。OAuth 2.0 と OIDC については公表された解析結果があり、自前で検証をやり直す価値は無い。既存の解析結果を `standards.md` の行の根拠として引くかどうかは、別途判断する。
- 全ての状態機械への適用。対象は上記 2 つに限る。
- 値ベースの property testing とメタモルフィック関係。wi-420 が扱う。
- 形式仕様から実装を生成すること。

## Design

検査基盤には TLA+ のモデル検査器を採り、表層言語も直接 TLA+ とする。対象がいずれも時間の経過と並行するプロセスの相互作用だからである。Alloy は構造的な制約と関係の充足を確かめることに強く、たとえば Authorization の関係グラフの到達可能性には向くが、リースの期限切れや破棄の順序という時相的な性質には TLA+ の検査基盤のほうが素直に書ける。表層言語を Quint に替える案は `wi-435` が実証のうえで不採用としたので採らない。理由は再現性であって表現力ではなく、`wi-435` の Decision に記録がある。

`wi-435` が試作して有効性を確認した 2 つの機構は、Quint に依存しないので本 work item が引き継ぐ。`states.md` の状態表と遷移表から模型の基礎モジュールを生成し、生成物とファイルのバイト比較を `mise` タスクにする経路と、模型が出力した ITF トレースで Go のアダプターを駆動し、模型が拒否すると言う操作を各 step で実際に拒否させて無作用まで確かめるテストドライバーである。ITF は Apalache 自身の形式なので TLA+ を直接検査しても得られるはずだが、`wi-435` はこれを Quint 経由でしか確認していない。本 work item の最初の実装課題として確かめる。

形式仕様の置き場所には 2 案ある。`spec/` の下に置く案と、対象の Context の近く（`backend/<context>/`）に置く案である。採るのは前者ではない。`docs/README.md` が「機械が食う契約——TypeSpec のソースと、そこから導いた OpenAPI の互換性ベースライン——だけが `spec/` にある」と述べており、形式仕様は契約ではないからである。後者を採り、`backend/datakeys/` と `backend/jobs/` の下に置く。実装と同じ場所にあれば、実装を変える人が仕様の存在に気づく。

`states.md` との関係は、`states.md` を正本とし、形式仕様をそこから導かれた検証用の模型として扱う。両者が食い違ったときは `states.md` が勝つ。逆にすると、正本が 2 つになり、しかも一方は読める人が限られる形式で書かれていることになる。ただしモデル検査が `states.md` の側の欠陥を見つけた場合は、`states.md` を直すのが正しい対応であり、模型を実装に合わせて曲げてはならない。

決定的シミュレーションについては、費用が大きいため本 work item では判断までとする。判断の材料は、worker の実行経路に時刻とスケジューリングの制御点をどれだけ差し込む必要があるかである。`docs/development/specification-first-workflow.md` の効果の識別が既に守られている範囲が広ければ費用は下がり、狭ければ広範な改修が先行する。調査の結果、費用が見合わないと判断した場合は、その理由を記録して Out of Scope へ移す。

未解決の論点として、モデル検査を常時のゲートに入れるかどうかは実行時間を測ってから決める。状態空間が大きければ数分から数十分かかりうる。`docs/development/specification-first-workflow.md` は探索的な fuzz を pull request のゲートに入れない理由を既に述べており、同じ論理が当てはまる可能性が高い。

## Plan

1. DataKeys の鍵ローテーションについて、`states.md` と `docs/database.md` の記述から状態、遷移、不変条件を抜き出す。不変条件は「残件を報告している移行処理がある間は `wrapped_dek` を `NULL` にしない」を中心に据える。
2. TLA+ で仕様を書き、TLA+ のモデル検査器で不変条件を検査する。まず不変条件をわざと外した版で反例が出ることを確認し、検査器が実際に働いていることを確かめる。検査器の選択では、`wi-435` が同じ規模の模型について TLC の網羅探索（490 状態、深さ 10、0.8 秒）が Apalache の 12 step 有界検査（13.3 秒）より速く、かつ強い結果を返したことを出発点にする。
3. Jobs のリースについて同じ手順を行う。不変条件は「1 つのジョブが同時に 2 つの worker で実行状態にならない」と「終端に達したジョブが再び実行状態にならない」を中心に据える。
4. 実行時間を測り、常時のゲートに入れるかを判断する。
5. 決定的シミュレーションの費用を調査し、判断する。
6. 見つかった欠陥があれば、是正を別の work item として切り出す。

## Risk Notes

形式仕様は書いた人以外が保守できなくなりやすい。対象を 2 つに絞るのはそのためであり、増やす前に、書いた仕様が実際に欠陥を見つけたかどうかを評価する。1 つも見つけないまま対象を広げると、保守されない資産が増えるだけになる。

模型と実装が乖離したまま検査が通り続ける状態が最大の失敗である。`states.md` を正本とし、模型はそこから導くという関係を明示することでこれを抑える。ただし乖離を機械的に検出する手段は本件では持たないため、`states.md` を変更する work item が模型の更新を伴うことをレビューの確認項目として残す。

TLA+ のモデル検査器の導入は、この製品の技術スタック（Go、TypeScript、PostgreSQL）に無い種類の道具を持ち込む。`mise.toml` が単一のツールバージョン表であるという方針に従い、導入するなら他と同じ場所で版を固定する。`wi-435` が Quint を落とした理由がまさにこれなので、TLA+ でも同じ基準を当てる。すなわち、取得物が全て `mise.toml` から版指定でき、道具が自分で別の配布物を取りに行かないことを、実装前に確かめる。`tla2tools.jar` はプラットフォーム非依存の単一 JAR なので条件は満たしやすいが、確認は要る。

もう一つ、`wi-435` が実証した罠を引き継ぐ。`x' = a \/ b` は `(x' = a) \/ b` と解釈され、代入のつもりで書いた行が黙って別の意味になる。`wi-435` ではこれが型検査もシミュレーションも通過し、模型が常に成立する空虚な不変条件を持ったまま緑になった。検査器だけがこれを拒否した。不変条件を意図的に壊した版で反例を確認する手順は、この種の空虚さを検出するためにも要る。
