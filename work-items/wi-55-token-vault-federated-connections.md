# エージェントが外部 API を代行するための Token Vault を設ける

## Motivation

エージェントはユーザーに代わって多数の外部 SaaS API を呼ぶ。これらの上流トークンをアプリやエージェントが直接保持すると、漏洩し、失効させにくく、最小権限が崩れる。Auth0 の Token Vault が示した形は、ユーザーが各上流へ与えた同意とトークンを IdP 側で安全に保管・更新・失効し、エージェントには必要なときに最小権限のアクセスだけを仲介するというものである。これにより「エージェントが生のシークレットを持たずに外部 API を代行呼び出しする」が成立する。

IdMagic は上流 IdP からのログイン連携 ([[wi-30-inbound-federation-and-identity-broker]]) を持つが、それはログインのための連携であって、外部 API 呼び出し用の上流トークンを保管し仲介する機構ではない。

本 work item は、上流の接続ごとにユーザーのトークンをテナント単位で暗号化して保管し、更新を管理し、エージェント ([[wi-49-agent-identity-first-class-principal]]) からの取得要求を委譲チェーン ([[wi-50-token-exchange-delegation-actor-chain]]) とスコープで絞って仲介する Token Vault を導入する。

## Scope

- 上流接続を所有する新しい Context を設ける。ログイン用の上流連携 (wi-30) とは別物であり、混ぜない。
- **コネクタ定義**と**ユーザー接続**を分離する。前者は認可・トークンの各エンドポイント、クライアント資格情報の参照、許可するスコープとリソースを持つ。後者は外部の主体、暗号化したトークン一式、有効期限、状態を持つ。
- アクセストークンと更新トークンは [[wi-97-envelope-encryption-at-rest]] の暗号ポートを使える設計にする。それ以前の実装では本番の永続化を有効にしない。
- **エージェントに生のトークンを読み出す API を与えない。** Vault が代理で外部リクエストを実行するか、短命のハンドルを介す。呼び出しのたびに委譲チェーン・Agent の状態・`authorization_details`・ユーザーの付与・宛先のホストとパスとメソッドを再評価する。
- OAuth のコールバックは `state` と PKCE とリダイレクト先をテナント・ユーザー・コネクタへ束縛する。更新は単一飛行とし、更新トークンの回転を扱う。`invalid_grant` は接続を再認可が必要な状態へ遷移させる。
- 外向き HTTP はコネクタの許可リスト、DNS と IP とリダイレクトの制限、応答の大きさと時間の上限を持つ。トークンと応答本文を監査へ保存しない。
- 権限を分ける。管理者はコネクタを定義・管理でき、ユーザーは自分の接続を連携・解除できる。
- アカウントポータルに連携済みの外部サービスの一覧と連携・解除を、管理コンソールにコネクタの管理を追加する。
- durable な設計判断 (接続の定義、暗号化の方式、更新と回転の責務、仲介の方式、失効の伝播) は所有 Context の `decisions.md` と `internals.md` へ、本変更固有の分析と却下した代替案は本ファイルの `## Design` へ置く。

## Out of Scope

- 各プロバイダ固有の API ラッパーや SDK の同梱。
- エージェントの外部 API 呼び出しそのものを汎用に代理する仕組み。本 work item はコネクタの許可リストに閉じた仲介までとする。
- 暗号鍵管理の新設。既存の鍵管理を流用する。
- ログイン用の上流連携との統合。[[wi-30-inbound-federation-and-identity-broker]] は別の関心事である。

## Design

未定。着手時に次を確定して本節に記録する。

- 仲介の方式。Vault が外部リクエストを代理実行するか、短命のハンドルをエージェントへ渡すか。前者は生のトークンが確実に外へ出ないが、Vault が外向き HTTP の責務を負う。
- 上流トークンの暗号化の単位。テナント・コネクタ・ユーザーのどこまでを鍵の材料に含めるか。
- 更新の失敗と再認可の境界。どの誤りを一時的とみなし、どの誤りで接続を再認可必須へ落とすか。

## Plan

- コネクタとユーザー接続を最初から別の集約として設計する。片方の寿命がもう片方に引きずられないようにする。
- 外向き HTTP の堅牢化 (SSRF 対策、リダイレクト不追従、上限) は仲介の実装より先に用意し、後付けにしない。
- 監査には接続の状態遷移と仲介の判断だけを残し、トークンと応答本文は残さない。

## Risk Notes

リスクは high。Token Vault は外部資格情報の集中保管庫であり、漏洩時の影響が大きい。保管は既存の鍵管理で暗号化し、新たな鍵管理を作らない。仲介はコネクタのスコープと委譲チェーンで最小権限に絞り、解除と失効を後続のアクセスへ確実に伝播させる。迷ったら拒否する側へ倒す。

外向き HTTP を持つこと自体がリスクである。SSRF、リダイレクト追従、応答の肥大はいずれも実装の初期に作り込まれやすい。これらの防御は仲介の実装より先に置き、テストで固定する。
