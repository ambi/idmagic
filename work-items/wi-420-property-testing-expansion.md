# property による検証を値ベースとメタモルフィック関係へ広げる

## Motivation

`DEVELOPMENT.md` の「Properties and fuzzing」は、この分野の文書としてかなり良く書けている。オラクルを 4 種類（往復、厳格性、構造的上限、冪等）に整理し、「panic しないはオラクルではない」「時間をオラクルにするな」「入力ごとに署名するな」「HTTP ハンドラーではなくパース関数に付けろ」という反例まで具体的に挙げ、オラクル自体を誤実装で検証せよとまで要求している。

しかし手段が Go の fuzzing、すなわちバイト列を入力とする探索だけに限られている。ここから 3 つの欠落が生じている。

第一に、値ベースの property testing が無い。挙げられているオラクルのうち往復と冪等は、本来バイト列ではなく構造化された値を生成して確かめるほうが自然で、生成器を型から組み立てられる分だけ書く費用も低い。バイト列から目的の構造を作るための復号を挟むと、探索の大半が「そもそも構造として成立しない入力」に費やされる。

第二に、`states.md` の遷移表がモデルとして使われていない。この製品は言語非依存の状態表と遷移表を正本として持っており、これは状態機械に対する property を書くときに最も費用のかかる部分が既に済んでいることを意味する。遷移表をモデルとして、実装の状態遷移が表から逸脱しないことを確かめる検証が、下地があるのに存在しない。

第三に、オラクルが存在しない領域が扱えていない。Authorization の関係グラフ評価と ClaimMapping の合成は、正しい答えを独立に計算する方法が無く、往復でも厳格性でも構造的上限でも冪等でもない。この種の対象にはメタモルフィック関係、すなわち入力を決まった形で変えたときに出力がどう変わるべきかという関係が使える。「関係タプルを追加しても、既存の許可が拒否に変わらない」「グループ所属を増やしても、開示されるクレームが減らない」「深さ制限を緩めても、以前に許可された判断が覆らない」はいずれも絶対的な正解を知らずに誤りを検出できる。これらは製品の中で最も検証が薄く、かつ誤りの影響が大きい領域である。

加えて、shrinking と再現（失敗した入力の最小化と、seed の固定による再現）に文書が触れておらず、フロントエンドには property に相当する検証が無い。

## Scope

- **値ベースの property testing の導入**：Go 側に生成器ベースの property testing を導入し、対象と道具の選定を行う。
- **オラクル一覧の拡張**：`DEVELOPMENT.md` の 4 種類のオラクルに、メタモルフィック関係を第 5 の型として加える。何がメタモルフィック関係の良い例で、何が単なる同語反復かを書く。
- **Authorization と ClaimMapping への適用**：メタモルフィック関係を、関係グラフの評価とクレームの合成に適用する。単調性、深さ制限、合成順序の不変性を対象とする。
- **遷移表をモデルとした検証**：`states.md` の遷移表から、実装が表に無い遷移を起こさないことを確かめる検証を、対象を絞って導入する。
- **shrinking と再現**：失敗入力の最小化と再現の手順を `DEVELOPMENT.md` に書く。既存の fuzz のコーパスの扱いと整合させる。
- **フロントエンド**：TypeScript 側に property を導入する価値がある対象があるかを判断し、あれば導入する。
- **mise タスク**：値ベースの property を走らせる経路を `mise.toml` へ加える。探索を pull request のゲートに入れないという既存の方針は維持する。

## Out of Scope

- 設計時のモデル検査と決定的シミュレーション。wi-421 が扱う。
- 既存の fuzz 対象の書き換え。バイト列を入力とする対象は、信頼境界を越えるパースという本来の役割で残す。
- 網羅の量的目標。`DEVELOPMENT.md` の「被覆の割当量は無い。数は境界に従う」という方針は変えない。
- Authorization の評価アルゴリズムそのものの変更。

## Design

Go の値ベース property testing の道具には `rapid` と `gopter` がある。採るのは `rapid` である。標準の `testing` に統合され、生成器の定義が型から素直に組み立てられ、shrinking が既定で働き、依存が小さい。`gopter` は表現力で上回るが、記述量が多く、この製品で必要な性質は `rapid` の範囲で書ける。第三の案として自前の生成器を書くことも考えられるが、shrinking を自作することになり、失敗入力の最小化という property の主要な利点を失う。

メタモルフィック関係を `DEVELOPMENT.md` の一覧へ加えるとき、既存の 4 種類と同じ書き方に揃える。既存の項目はいずれも「これだけでは通ってしまう実装」を併記する形（厳格性は何も受理しない実装にも通るので、正当な入力が受理されることと対にする）を採っており、メタモルフィック関係にも同じ注意が要る。単調性だけを確かめる関係は、常に許可する実装にも通る。したがって、単調性は「正当に拒否される入力が拒否される」ことと対にして初めて意味を持つ。この対の要求を明記する。

遷移表をモデルとする検証には 2 案ある。遷移表を機械可読に読み取って実装と突き合わせる案と、テスト側に遷移表を写して比較する案である。採るのは前者である。後者は表を 2 か所に持つことになり、`SPECIFICATION_FORMAT.md` が繰り返し禁じている形になる。読み取りの実装は `tools/check` に既に Markdown の表を解析する仕組み（`specification-doc.ts` の遷移表の検証）があるため、そこから流用できる。ただし全ての状態機械へ一度に適用しない。対象は Jobs と DataKeys の 2 つに絞る。前者はリースと再試行の遷移が並行実行と絡み、後者は鍵の破棄という不可逆な遷移を持つためである。

フロントエンドへの導入は、対象があるかどうかを先に確認する。UI の大半は表示と入力であり、property が効くのは変換と正規化を行う純粋な関数に限られる。対象が数個しか無ければ導入しない。

未解決の論点として、メタモルフィック関係の適用先で、関係グラフの評価が現在どこまで純粋な計算として取り出せるかは調査していない。データベースを必要とする形になっていれば、`DEVELOPMENT.md` が「データベースが必要なものには property を使うな」と述べている対象に当たる。その場合は評価の純粋な中核を切り出すことが先行作業になる。実装着手前に確定させる。

## Plan

1. `rapid` を導入し、既存の fuzz 対象のうち往復または冪等をオラクルとしているものを 1 つ選んで値ベースへ書き換え、記述量と失敗時の読みやすさを比較する。
2. Authorization の関係グラフ評価が純粋な計算として取り出せるかを調査する。取り出せない場合、先行作業を切り出す。
3. `DEVELOPMENT.md` にメタモルフィック関係を第 5 のオラクルとして加える。対にすべき性質の要求を明記する。
4. Authorization と ClaimMapping にメタモルフィック関係を適用する。各関係について、それを破る誤実装を書いて検出されることを確認する。
5. Jobs と DataKeys の遷移表を読み取り、実装が表に無い遷移を起こさないことを確かめる検証を実装する。
6. shrinking と再現の手順を `DEVELOPMENT.md` へ書き、`mise.toml` へ実行経路を加える。
7. フロントエンドの対象の有無を判断する。

- `mise run verify`

## Risk Notes

メタモルフィック関係は、対にすべき性質を欠くと空虚な検査になる。単調性だけを確かめる検査は、常に許可する実装に対しても通る。これは `DEVELOPMENT.md` が厳格性について既に警告している失敗と同じ型であり、T004 の誤実装による確認がそれを防ぐ唯一の工程である。

道具を増やすと、どの検証をどの道具で書くかの判断が毎回発生する。`DEVELOPMENT.md` に、バイト列の探索（信頼境界を越えるパース）と値ベースの property（構造化された入力に対する関係）の使い分けを 1 段落で書く。

遷移表の読み取りは書式の変更に弱い。`SPECIFICATION_FORMAT.md` が遷移表の書式を既に検査しているため、書式が崩れれば先に `check-spec` が落ちる。この順序が保たれることを確認する。
