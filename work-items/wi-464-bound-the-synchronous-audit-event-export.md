# 監査イベントのエクスポートを有界な非同期ジョブにする

## Motivation

`GET /api/admin/v1/audit_events/export` は、API プロセスの中で監査イベントを読み、`[]*auditports.AuditEventRecord` と `[]AdminAuditEventResponse` という2つの中間表現をメモリに作ってから JSON へ直列化する。

ハンドラーは最大10,000件を要求するが、PostgreSQL とメモリの読み出しポートは1,000件へ再制限するため、呼出し側へ通知せず結果が切り詰められる。

上限を10,000件または全一致件数へ引き上げるだけでは、保持量と DB 接続時間がその件数に比例して増える。

[[wi-459-api-process-plane-separation-decision]] は、この経路をワーカーへ出ていない唯一の高コスト管理処理として特定した。

問題は、完全なエクスポートと同期要求の有界性を同時に満たせないことである。

管理者がエクスポートを並行に要求したとき、API プロセス内の同時実行数を制限する機構はない。

[[wi-396-prioritize-login-under-saturation]] が扱う入場制御は総容量が足りないときの拒否順序を決めるが、一要求の保持量と接続占有時間を固定しない。

非同期ジョブは処理を API 要求から分離し、固定件数ずつ進めるため、入場制御とは役割が異なる。

## Scope

- テナント内監査とテナント横断監査のエクスポート要求を、Jobs の `bulk` レーンへ投入する非同期操作へ変更する。
- エクスポートジョブへ、テナント範囲、絞り込み条件、要求者、要求時刻、形式を正規化して保存する。
- ワーカーは署名付きカーソルで固定件数ずつ読み、全件をメモリへ保持せず不変の成果物へ逐次書き込む。
- 成果物の最大バイト数、最大イベント数、有効期限を設定し、超過時は部分成果物を公開せず安定した失敗理由で終了する。
- テナント内成果物は対象テナント、横断成果物は制御面テナントの `export_artifacts_bytes` へ計上する。
- 要求、開始、成功、失敗、取消し、ダウンロード、期限切れを監査イベントとして記録する。
- 要求者はジョブ状態を確認し、成功かつ期限内の成果物だけをダウンロードし、未完了ジョブを取り消せる。
- テナント内成果物は同じテナントの監査読出し権限、横断成果物は現在も制御面主体の条件を満たす User に限ってダウンロードできる。
- 同期エクスポート API を非推奨化し、移行期間と削除条件を定める。
- 上限到達、ジョブ滞留、成果物容量、失敗を観測できるメトリクスを出す。
- Audit、Jobs、System の仕様、画面、容量計画、監視を更新する。

## Design

### Audit と Jobs の責務

Audit がエクスポートの意味、絞り込み、成果物形式、テナント範囲、ダウンロード認可を所有する。

Jobs は実行状態、リース、取消し、実行レーンを所有する。

ジョブ種別 `audit_export` は `bulk` レーンへ固定し、呼出し側から実行レーンを指定できないようにする。

既存の IdentityManagement データエクスポートから成果物保存、期限、ダウンロードの機構を共有できる形へ抽出してよいが、監査固有の絞り込みと範囲判定を IdentityManagement へ置かない。

### 選択した方式

| 案 | 内容 | 判断 |
| --- | --- | --- |
| A | 応答を JSON 配列としてストリーミングする | 採らない。応答中は API プロセスの接続とゴルーチンを占有し、途中失敗を完全な成果物と区別しにくい |
| B | 上限を下げ、超過した要求を拒否する | 採らない。現在の無通知の1,000件切詰めは直せるが、絞り込み結果全体を取得する利用目的を満たさない |
| C | `audit_export` ジョブとしてワーカーへ出し、不変の成果物を配る | 採る。API 要求から処理量を分離し、固定件数の反復、取消し、成果物上限、実行レーンを既存機構へ載せられる |
| D | 同時実行数だけをセマフォで絞る | 単独では採らない。一成果物の完全性、逐次書込み、再試行を扱えない |

ジョブ作成の集中はテナントの `active_jobs` 上限、実行の同時数は `bulk` ワーカーの設定で有界化する。

### 成果物の公開

ワーカーはページごとにエンコードして一時成果物へ書き、ページ境界で取消し、最大イベント数、最大バイト数を再確認する。

上限超過、取消し、失敗時の一時成果物はダウンロード可能状態へ遷移させない。

横断成果物は個々の通常テナントへ容量を分配せず、制御面テナントの `export_artifacts_bytes` へ計上する。

要求時の権限を成果物へ保存して無期限に信用せず、ダウンロード時にも現在の制御面主体と成果物範囲を検証する。

### 互換性

同期 API は直ちに別の意味へ変えず、非推奨期間中は固定した低い同時実行上限の下で維持する。

非同期の作成、状態確認、取消し、ダウンロードを先に提供し、同期 API には `Deprecation` と `Sunset` ヘッダーを付ける。

削除日は管理 API の非推奨規則に従い、リリースノートとアップグレードノートへ移行手順を記載する。

## Plan

1. 現在の実効1,000件切詰め、保持量、DB 接続時間、並行実行時の影響を測定する。
2. 非同期要求、状態、取消し、ダウンロード、期限、上限、テナント範囲を規範化する。
3. 成果物機構を共有可能な境界へ抽出し、Audit 所有の `audit_export` ジョブを登録する。
4. 監査読出しをカーソルで反復し、逐次書込みと上限検査を実装する。
5. テナント内と横断の認可を要求時とダウンロード時に確認する。
6. 管理コンソールとシステムコンソールを非同期の状態表示、取消し、ダウンロードへ変更する。
7. 同期 API の非推奨期間と移行方法をリリース文書へ記載する。
8. 混合負荷で API プロセスの保持量と接続占有がエクスポート件数に比例しないことを確認する。

## Risk Notes

リスクは high とする。

横断成果物は複数テナントの監査情報を含むため、誤ったダウンロード認可は単一テナントの一覧漏えいより影響が大きい。

要求時とダウンロード時の両方で認可を確認する。

途中まで書いた成果物を成功扱いにすると、上限超過や取消しが不完全な調査結果として見える。

成果物の公開状態は完了後の一回の遷移で確定する。

非同期化により、`REQ-AUDIT-001` の「エクスポートデータとして返る」は、同期応答ではなく成功した成果物の取得へ変わる。

既存の API トークン利用者には非推奨期間と移行手順を提供する。

上限値の妥当性は [[wi-282-staging-load-testing-and-capacity-validation]] の負荷試験基盤で確認する。

非同期 API、ジョブ種別、成果物契約、新しい規範 ID を公開するため、`reversibility` は irreversible とする。
