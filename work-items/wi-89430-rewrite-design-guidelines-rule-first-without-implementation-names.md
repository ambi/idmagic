# API ガイドラインと設計ガイドラインを規則を先に示す形で書き直し、設計文書から個々の実装への参照を外す

## 動機

ガイドラインの読み手がまず知りたいのは、何を決めたかである。
現在の二つのガイドラインは、決めたことと決めなかったこと、規則と理由、規則と実装の場所が同じ重さで並び、規則を探しにくい。

| 箇所 | 問題 |
| --- | --- |
| `api-guidelines.md`「コロン形式」 | Google AIP-136 の `:verb` 形式を採用しないことが、採用する規則と同じ見出しの粒度で書かれている。末尾に「採用しない方式」の節があるのに使っていない |
| `api-guidelines.md`「部分レスポンス」「完了通知」 | 同じく、採用しないことだけを述べる節である |
| `api-guidelines.md`「ルールの記述形式」 | 「採用しないと決定した事項も、採用しないというルールとして記載する」と定めており、上の構成の原因になっている |
| `api-guidelines.md` の担保手段 | `backend/idmanagement/user/domain/attribute_cell.go`、`branding_handler.go`、`support_http.ParsePageRequest`、Echo の `BodyLimit` など、個々のファイル、関数、ライブラリを挙げている。API ガイドラインが実装言語、ライブラリ、データベースを限定している |
| `api-guidelines.md`「インデックスキーの構成カラム」 | PostgreSQL の B-tree の制限の説明が先に 5 文続き、定めた二つの上限の表がその後に来る |
| `api-guidelines.md`「文字列長の上限」の各節 | zog、`utf8.RuneCountInString`、`backend/shared/spec` など、規則ではなく実装の対応が規則の本文に混ざる |
| `design-guidelines.md` 全体 | 長い段落が続き、原則、判定基準、現状の逸脱が一つの段落に入っている。文書ガイドの「文書の見せ方」に従っていない |
| `design-guidelines.md` | 情報隠蔽、深いモジュール、依存の向き、ポートとアダプター、作用の境界は既存の設計論に基づくが、出典を示していない。出典は仕様先行の開発ワークフローとコーディングスタイルに散らばっている |
| `design-guidelines.md`「差し替え点とポート」 | `backend/shared/security/actiontoken` の仕組みの説明が一段落あり、ガイドラインではなく一つの機構の設計になっている |
| `design-guidelines.md`「Aggregate 境界と Repository」 | `backend/sourcing/scim/ports` の `ScimRepository` を「反している状態」として挙げており、技術的負債の記録がガイドラインに入っている |
| `design-guidelines.md`、`requirements/glossary.md` | ドメイン駆動設計の戦術的な語（Aggregate、Repository）が、出典と適用範囲を示さないまま中心の語になっている。モジュールの境界はドメイン駆動設計から離れて情報隠蔽で選ぶ方針に変わっている |
| 全体設計文書とモジュール設計文書 | `docs/design/` の 10 文書に 58 か所、モジュール設計文書の 31 文書に 68 か所、個々のソースファイルやパッケージへの参照がある。許される参照と許されない参照の基準がない |

## 対象範囲

- `docs/design/application/api-guidelines.md` の構成と担保手段を書き直す。
- `docs/design/application/design-guidelines.md` を、節ごとに同じ形で書き直し、出典を加える。
- 設計文書からコードへの参照の基準を文書ガイドに定め、全体設計文書とモジュール設計文書の参照を基準に合わせる。
- Aggregate の扱いを、下の未解決の問いの答えに従って決め、用語集とガイドラインに反映する。

## 対象外

- ルールの決定内容の変更。採否、上限値、ステータスコードの割り当てなどは変えない。
- ソースコードの型名やポート名（`Repository`、`Store`）の変更。
- 汎用部分と IdMagic 固有部分の分離（wi-99632）。この作業項目で技術を限定しない書き方にした部分は、あちらで汎用部分として扱える。

## 設計

### 設計文書からコードへの参照の基準

文書ガイドの「文書の見せ方」に次の基準を加える。

| 参照 | 扱い |
| --- | --- |
| 検査が読む宣言（論理アーキテクチャの責務表のパッケージ、バックエンド設計とフロントエンド設計のコードの置き場所と依存の向き） | 許す。設計が配置そのものを定めている |
| 構成ファイル（`infra/`、`mise.toml`）を対象とする設計での、そのファイルへの参照 | 許す |
| 検査のタスク（`mise run <task>`） | 許す。違反を検出する仕組みとして名指す |
| 個々のソースファイル、関数、型、テストファイル | 許さない。担保する仕組みは種類で書く。どのコードが規則を実装するかは、コードのコメントから設計文書の節を参照する |
| 実装言語、ライブラリ、データベースの製品名 | 技術を選んだ文書（アーキテクチャの制約、判断、バックエンド設計、フロントエンド設計、データベース設計）では許す。ガイドラインでは規則の本文に書かず、選んだ技術に固有の理由は補足として書く |

参照の向きをコードから文書へ限るのは、ファイルの移動や改名のたびに設計文書が古くなることを避けるためである。
機械検査は加えず、レビューの確認項目に加える。

### API ガイドライン

| 変更 | 内容 |
| --- | --- |
| 採用しない方式 | 「コロン形式」「部分レスポンス」「完了通知」の節を削除し、末尾の「採用しない方式」の表の行にする。採用する規則の中で触れる不採用（ページングのオフセット方式、汎用のフィルター言語）は、その節に一文の補足として残し、表へもリンクする |
| ルールの記述形式 | 「採用しないと決定した事項も、採用しないというルールとして記載する」を、「採用しないと決定した事項は、末尾の採用しない方式の表に記載する」に改める |
| 担保手段 | 次の種類で書く：API 契約の宣言（TypeSpec）、HTTP 境界の共通処理、ドメインの検証、データベースの制約、検査タスク。個々のファイル、関数、ライブラリの名前を外す |
| 文字列長の上限 | 各節を、定めた規則（二つの上限の表、計数単位、検証の箇所の役割）から始める。PostgreSQL の B-tree のインデックスタプルの上限は、表の後に「この上限を設ける理由」として補足する。zog と `utf8.RuneCountInString` の選択など、言語とライブラリに固有の対応はバックエンド設計へ移す |
| 全節 | 規則の本文、目的、担保手段、適用状況の順にそろえ、理由が規則より前に来る節をなくす |

TypeSpec は、アーキテクチャの制約が API 契約の一次情報として定めている。
ガイドラインが TypeSpec の宣言の書き方を定めることは、技術を限定することには当たらないので残す。

### 設計ガイドライン

各節を次の形にそろえる。

| 小節 | 内容 |
| --- | --- |
| 原則 | 一文から三文で、何を守るか |
| 判定基準 | 守れている状態と反している状態の表 |
| 根拠 | 原則の理由と出典 |

- 現在のリポジトリの逸脱（`ScimRepository`、ドメイン型をレスポンス型へ直接使う HTTP アダプター、ドメインの計算が時刻を内部で取得する箇所、構築後の `Validate`）は、ガイドラインから外し、該当するモジュールの `design/risks.md` またはシステムの `architecture/risks.md` の技術的負債に移す。
- アクショントークンの共通核の説明は、セキュリティ設計の該当文書へ移し、ガイドラインには差し替え点の例として一文だけ残す。
- 節の順序を、大きな判断から小さな判断へ並べ替える：モジュールの深さと情報隠蔽、境界を選ぶ判断手順、依存の向きと差し替え点、アダプターと表現、型の所有と不変条件、一貫性の境界と永続化、作用の境界、エラーと拒否、仕様に書ける振る舞い、確立した実装への委譲。「判断の三分類」は、境界を選ぶ判断手順の前提として、その節の冒頭に置く。
- `境界を選ぶ判断手順` のアンカーは、`AGENTS.md`、作業項目フォーマット、skills が参照しているので変えない。

出典を文書の末尾に表で示し、各節の根拠から参照する。

| 出典 | 対応する節 |
| --- | --- |
| David L. Parnas, "On the Criteria To Be Used in Decomposing Systems into Modules" (1972) | モジュールの深さと情報隠蔽、境界を選ぶ判断手順 |
| John Ousterhout, *A Philosophy of Software Design* | モジュールの深さと情報隠蔽 |
| Robert C. Martin, "The Clean Architecture" (2012)、*Clean Architecture* (2017) | 依存の向きと差し替え点 |
| Alistair Cockburn, "Hexagonal Architecture" (2005) | 依存の向きと差し替え点、アダプターと表現 |
| Michael Feathers, *Working Effectively with Legacy Code* の seam | 依存の向きと差し替え点 |
| Bertrand Meyer, *Object-Oriented Software Construction* の契約による設計 | 型の所有と不変条件 |
| Gary Bernhardt, "Functional Core, Imperative Shell" | 作用の境界 |
| Eric Evans, *Domain-Driven Design* の Aggregate | 一貫性の境界と永続化（下の問いの答え次第） |

出典は、借りた考え方とこのリポジトリでの適用範囲を一文で添える。
ドメイン駆動設計からは借りる範囲を明示し、モジュールの境界をドメイン駆動設計の境界づけられたコンテキストから導かないことを書く。

### Aggregate の扱い

モジュールの境界の選び方は、すでに情報隠蔽と境界を選ぶ判断手順へ移っている。
一方、「同時に正しくなければならない状態の単位」という概念は、トランザクションの範囲、永続化ポートの粒度、`tenant_id` の保持区分（データベース設計）の基準として残っており、何らかの語で呼ぶ必要がある。
Aggregate の語は `docs/` に 133 か所あり、データベース設計のテーブルの説明と `tenant_id` の規則もこの語を使う。

| 案 | 内容 | 利点 | 欠点 |
| --- | --- | --- | --- |
| A | Aggregate の語を残し、ドメイン駆動設計から借りた語であることと、このリポジトリで使う意味（一貫性の境界、ルートの識別子による外部からの参照、所有するモジュールが一つ）を用語集に明記する | 定着した語で、ソースの `Repository` の名前とも対応する。変更が用語集とガイドラインで済む | ドメイン駆動設計の他の概念（境界づけられたコンテキスト、ドメインイベント）も採っていると読まれうる |
| B | 中立の語（たとえば「一貫性境界」）に置き換え、用語集の定義から Aggregate を別名へ下げる | ドメイン駆動設計の前提を文書から外せる | 133 か所の書き換えが要り、ソースの `Repository` との対応を別に説明する必要がある。新しい語の定義は A と同じ量になる |

推奨は A である。
概念は必要であり、置き換えても定義の量は変わらない。
ドメイン駆動設計から借りる範囲を用語集とガイドラインの出典で限れば、他の概念を採っているという誤読は防げる。

6. 用語集の Aggregate と Module の周辺の語を、問いの答えに合わせて改める。
