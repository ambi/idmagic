# ClaimMapping が宣言する未検証の拒否 2 件に効果まで確かめるテストを与え、台帳から外す

## Motivation

`tools/check/scenario-coverage-debt.json` は、どのテストからも id を引用されていない規範 id を保持する、縮むだけの台帳である。

このうち 102 件は [[wi-390-security-control-test-standard-and-gate]] が拒否専用の台帳へ据え置いた分で、[[wi-490-fold-refusal-coverage-into-one-normative-coverage-rule]] が網羅台帳へ統合した。

その 102 件のうち 2 件が ClaimMapping の拒否である。

2 件はどちらも「部分的に発行しない」という形の拒否である。

`REQ-CLAIMMAPPING-002` は公開できない属性をソースとする規則があるとき、クレームを 1 つも発行せずに拒否する。

`REQ-CLAIMMAPPING-003` は必須規則のソース属性が欠けているとき、残りの規則だけを適用した部分的なクレーム集合を返さない。

この形の拒否は、素通りしたときに例外も 4xx も出ない。

トークンが発行され、中身が少しだけ違うだけである。

受け取った側は、欠けたクレームを「その利用者は該当しない」と解釈するか、公開されるはずのなかった属性をそのまま信頼する。

したがってこの 2 件は、応答コードでは何ひとつ確かめられず、発行されたトークンの中身でしか確かめられない。

この 2 件はいずれも nearby に分類され、同じエラー型名を引用しているテストは 1 件も無い。

そして注記だけを足す解消は、この項目では認めない。

## Scope

- 台帳の ClaimMapping の 2 件それぞれについて、宣言された拒否に production と同じ入口 (トークンとアサーションの発行経路) から到達するテストを用意する。
- 各テストで 2 つを assert する。発行が拒否されたこと、および部分的なクレーム集合が発行されていないこと。
- 各テストのソースに対応する `REQ-CLAIMMAPPING-NNN` を書く。
- 対応が取れた id を `tools/check/scenario-coverage-debt.json` から削除する。
- 拒否を実装が持っていないと判明した場合、その防護をこの項目で実装する。
- 完了時点で、この項目が持つ id が台帳から 1 件残らず消えていることを確認する。

## Out of Scope

- 他 Context の拒否。
  Context ごとに別の work item が持つ。
- 102 件を 1 つの単位として消化すること。
  [[wi-399-burn-down-untested-refusal-debt]] がその形で立てられているが、進める単位を未決のまま残し、注記だけの解消も認めている。本項目はその置き換えである。
- 同じ台帳に載る、この項目が持たない id。
  規則は同じだが、引き取る範囲はここに挙げた id に限る。
- R1、R2、R4 の検査そのものの変更。
  [[wi-390-security-control-test-standard-and-gate]] と [[wi-391-refusal-declaration-floor-and-reinventory]] が持つ。
- 既存テストへ `REQ` id を注記するだけで台帳から外すこと。
  この項目ではこれを解消として扱わない。
- Application ごとのクレーム公開の下限そのものの検証。
  [[wi-475-back-application-declared-refusals-with-effect-tests]] が `REQ-APPLICATION-006` として扱う。
- 属性の可視性区分の定義変更と、規則の記述能力の拡張。

## Design

### 解消の条件

1 件の id を台帳から外してよいのは、次の 3 つがすべて成り立つときだけとする。

第 1 に、テストが production の使う入口から入り、宣言された拒否の判断を実際に通ること。

クレームの構成はトークンとアサーションを発行する経路の一部であり、その経路から入る。

第 2 に、拒否が変えなかったもの、この Context では「発行されなかったもの」をテスト自身が読み直して確かめること。

第 3 に、シナリオの id をテストのソースが引用していること。

### 拒否ごとに何を読むか

| REQ | 宣言している拒否 | 発行物を読んで確かめる対象 |
|---|---|---|
| REQ-CLAIMMAPPING-002 | 公開できない属性をソースとする規則があればクレームを 1 つも発行せずに拒否 | トークンとアサーションが発行されていない、あるいは発行されてもクレームが 1 つも含まれない |
| REQ-CLAIMMAPPING-003 | 必須規則のソース属性が欠けていれば部分的な集合を返さず発行そのものを拒否 | 他の規則から作られるはずだったクレームが 1 つも含まれていない |

`REQ-CLAIMMAPPING-003` のテストは、必須規則 1 つと任意規則 2 つ以上を持つ構成で行う。

任意規則が 1 つも無い構成では、部分的に発行する実装でも結果が空になり、拒否と区別できない。

テストの構成そのものが、規範の要求から決まる。

「1 つも含まれない」は、クレーム名の集合を取り出して空であることを確かめる。

値の一致で確かめると、値が空文字の実装を見落とす。

### 却下した進め方

**規則の評価器の単体テストで閉じる案。**

評価器が空集合を返しても、呼び出し側が既定のクレームを足していれば結果は部分的な集合になる。

拒否の効果は発行物にしか現れない。

**必須規則だけを持つ構成で確かめる案。**

上に述べたとおり、部分的に発行する実装を検出できない。

**発行の拒否を、エラーの型だけで確かめる案。**

この拒否は例外を伴わずに成立しうるため、型を確かめるだけでは何も言えない。

## Risk Notes

この 2 件の拒否は例外を伴わずに成立しうるため、テストが「拒否された」と読む手がかりが弱い。

発行物のクレーム集合を直接読み、集合が空であることを確かめる形に統一する。

クレームの構成が複数のプロトコルで共有されている場合、1 つのプロトコルだけで確かめると、他のプロトコルの経路で部分発行が残る。

共有している経路をすべて列挙してから、確かめる範囲を決める。

台帳は id 順に 1 エントリー 1 id なので、Context ごとの work item が並行しても衝突はエントリー単位に収まる。

各項目は自分が持つ id のエントリーだけを削除し、コメント配列と他の id には触れない。
