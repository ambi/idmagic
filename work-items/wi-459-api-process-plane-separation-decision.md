# API プロセスを当面分けない判断と再検討条件を、容量シナリオと隔離要件に基づいて記録する

## Motivation

いま `backend/cmd/idmagic` の API プロセスは、次のすべてを 1 つの待受に載せている。

- OAuth2/OIDC のプロトコル経路、SAML、WS-Federation
- ブラウザーのログイン経路 (`/api/auth/*`)
- 利用者ポータル API (`/api/account/v1`)
- 管理 API (`/api/admin/v1`)
- SCIM、Shared Signals

`server_http.Register` は、これらの経路群を無条件に 1 つの Echo インスタンスへ登録する。どの種別を提供するかを選ぶ仕組みはない。

一方で、リポジトリは「認証系と管理系は重要性が違う」とすでに宣言している。`docs/capacity.md` のサービス目標は 1 つ残らず認証・プロトコル系を母集団としており、管理系 API を母集団とする目標は存在しない。Degradation order も、容量が足りないときは管理系の高コスト処理から捨てる順序を規範として持つ。

差は文書にはあるが、実行単位の境界には現れていない。管理系と認証系は同じ Pod、同じ Go ランタイム、同じ接続プールを共有している。

**そして、分けるべきかどうかを判断する材料が揃っていない。** `docs/capacity.md` の Peak request profile には、管理 API、ポータル API、SCIM、Shared Signals の行がない。認証・プロトコル系には合計しておよそ 41,000 rps の見積もりがある一方、これらの種別は容量算出へ入っていない。行がないことは負荷がゼロまたは無視できることを示さない。

見積もりがないまま是非を論じても、結論は好みに落ちる。ただし根拠のない比率を判断規則として先に固定しても、恣意性は消えない。本 work item は、既存の容量算式で通常時、最繁時、集中同期時の必要レプリカ数と資源量を比較し、その結果を可用性、保守、到達範囲の要件と合わせて判断する。

なお [[wi-396-prioritize-login-under-saturation]] は一度この問いに触れてプレーン分割を採らなかった。ただしその判断の軸は「飽和したときにログインが先に生き残るか」の 1 つだけで、可用性、スケーラビリティ、独立した保守性、到達範囲の分離は評価していない。

## Scope

- 管理コンソール、管理 API による自動化、ポータル API、SCIM、Shared Signals の到達率と処理特性を、`docs/capacity.md` の参照運用プロファイルから通常時、最繁時、集中実行時のシナリオとして見積もる。
- 「分ける」が指しうる 4 つの独立した変更（D1–D4）を定義し、それぞれの利得と費用を評価する。
- 既存の容量算式を使って、単一 Deployment と分離した Deployment の必要レプリカ数、要求資源、接続予算を比較する。処理時間の比だけから Pod 数を導かない。
- 5 つの軸（可用性、スケーラビリティ、重要性の差、独立した保守性、到達範囲の分離）で評価する。
- **将来分ける確率が高いなら、後から分けるより今分けたほうが安いのではないか**という問いに答える。分割の費用が時間とともに増えるかどうかを変更ごとに調べる。
- [[wi-396-prioritize-login-under-saturation]] との関係を決める。両者は代替か補完か、どちらを先に入れるかを明示する。
- 分離候補となる種別を確定する。認証・プロトコル系の内部を分けるかどうかは本 work item では決めない。
- 判断、却下した選択肢、再検討の条件を `docs/contexts/system/decisions.md` に記録し、見積もりを `docs/capacity.md` へ追加する。

## Out of Scope

- 実際に Deployment を分けること、経路登録を選べるようにする実装、`backend/cmd/` の構成変更。判断が「分ける」に至った場合は、実施を別の work item が持つ。
- 入場制御、優先度クラス、優先度別の接続予算、レプリカ数の自動スケールの実装。[[wi-396-prioritize-login-under-saturation]] が持つ。本 work item はそれとの順序を決めるだけで、実装しない。
- 冗長化、自動フェイルオーバー、障害種別ごとの縮退。[[wi-165-high-availability-and-failover-resilience-topology]] が持つ。
- データ層の分割、読み取りレプリカ、接続プール。[[wi-164-data-tier-scalability-partitioning-read-replica-pooling]] が持つ。
- ゲートウェイの経路許可リストが経路表とずれていないことを機械的に確かめる仕組み。`frontend/Caddyfile` の `@realmBackend` と `@backend` は手書きの接頭辞列挙で、現在これを照合する検査はない。単一プロセスのままでも起きる欠陥なので、別の work item が持つ。
- 同一オリジン前提そのものの見直し。`docs/deployment.md` が持つ前提であり、変えるなら Cookie のスコープと `Origin` 検証の再設計を伴う。本 work item は D3 の制約として扱うだけである。
- フロントエンドの配信構成、管理コンソールとアカウントポータルの分離。
- `/introspect` など認証・プロトコル系の内部を独立したプレーンへ分けること。最大量の経路を独立にスケールする余地はあるが、管理系、ポータル系、SCIM、Shared Signals との分離判断とは別に扱う。

## Design

### この文書で使う用語

| 用語 | 意味 |
| --- | --- |
| 種別 | 用途で分けた API のまとまり。認証・プロトコル系、ポータル系 (`/api/account/v1`)、管理系 (`/api/admin/v1`)、SCIM、Shared Signals を指す。 |
| プレーン | 1 つ以上の種別だけを受け持つレプリカ群。種別は API の分け方、プレーンは配備の分け方である。 |
| 自動スケール | 負荷に応じてレプリカ数を自動で増減する仕組み。Kubernetes の `HorizontalPodAutoscaler`。現在 `infra/` に 1 つもなく、本番は `replicas: 3` 固定である。 |
| 入場制御 | 容量が足りなくなったときに、優先度の低いリクエストから明示的に拒否する仕組み。平常時は何も拒否しない。[[wi-396-prioritize-login-under-saturation]] が導入する予定で、まだ実装されていない。 |
| 処理時間構成比 | ある種別のリクエスト処理時間の合計が、全体に占める割合。`http_request_duration_seconds_sum` を `route` ラベルで絞って求める。データベース待ちと外部通信待ちを含むため、CPU、メモリ、必要 Pod 数の比とはみなさず、同時実行需要を調べる補助指標としてだけ使う。 |
| 必要レプリカ数 | `docs/capacity.md` の Sizing rules に従い、種別ごとの最繁到達率、混合負荷下で実測した 1 レプリカ当たりの持続処理能力、安全係数から算出する数。実測がない場合は幅を持つ Planning assumption とし、単一値で確定しない。 |

### 確定している事実

見積もりの前に、調べれば分かることを先に置く。

| 事実 | 内容 |
| --- | --- |
| 一括処理の一部は API プロセスの外にある | 利用者とグループの CSV エクスポート (`data_export`)、CSV インポート (`user_import_*`, `group_import_*`)、動的グループ再計算 (`dynamic_group_reconcile`) は `JobKind` として登録され、`bulk` レーンの `idmagic-worker` が実行する。 |
| エクスポートのダウンロードはストリーミングである | `DownloadDataExport` は成果物のリーダーを返し、ハンドラーは `c.Stream` で流す。ファイル全体をメモリに載せない。 |
| 同期実行される管理処理も残る | 監査イベントのエクスポートは API プロセス内で最大 10,000 件を読み、応答用のスライスと JSON を組み立てる。ワーカー化された処理だけを根拠に、管理系の資源競合を否定できない。 |
| 管理 API には複数の呼び出し元がある | `/api/admin/v1` は管理コンソールだけでなく、API トークンを使う外部の管理 API クライアントからも呼ばれる。画面操作と自動化を別の負荷源として見積もる必要がある。 |
| SCIM は機械が駆動する | `/scim/v2/*` の呼び出し元は顧客側の IdP である。変更分だけを送る場合と全同期する場合で量が変わるため、導入率、同期頻度、時間帯への集中をシナリオの前提にする。 |
| 認証・プロトコル系の見積もりは存在する | `docs/capacity.md` の Peak request profile に合計およそ 41,000 rps。 |
| 管理系、ポータル系、SCIM、Shared Signals の見積もりは存在しない | 同じ表に行がない。 |
| 入場制御も自動スケールも未実装である | [[wi-396-prioritize-login-under-saturation]] は `pending`。`infra/` に自動スケールの定義はなく、本番は `replicas: 3` 固定。 |
| ゲートウェイは接頭辞で振り分けているが、経路表と一致していない | `frontend/Caddyfile` は `/api`、`/authorize`、`/token`、`/scim` などを列挙している一方、実行時経路にある `/ssf/*`、`/session/check`、`/application-icons/*` を含まない。後段を複数の上流へ分ける前に、許可リストと経路表の対応を確定する必要がある。 |
| API レプリカはプロセス内に正となる状態を持たない | `docs/deployment.md` が多レプリカ運用のために既に要求している。セッションも認可コードもスロットルもすべて PostgreSQL にある。 |

ワーカー化によって利用者とグループの一括処理は API プロセスから外れているが、管理系の高コスト処理がすべて外れたわけではない。可用性の評価では、ワーカーへ出ていない同期処理を列挙し、通常時の処理時間だけでなくピークメモリ、同時実行数、データベース接続待ちも調べる。

### 「分ける」は 4 つの独立した変更である

段階の梯子として並べると、本来独立な選択が順番に見えてしまう。実際には次の 4 つで、必要なものだけを選べる。

| ID | 変更 | 何を変えるか | 前提 |
| --- | --- | --- | --- |
| D1 | 配備を分ける | 同一イメージ・同一経路表のまま Deployment と Service を分け、ゲートウェイが接頭辞で振り分ける | 種別と経路の対応、およびゲートウェイ規則を照合できること |
| D2 | 経路登録を選べるようにする | 起動時設定で、そのプロセスが登録する種別を選ぶ | D1（分けた配備がなければ意味がない） |
| D3 | 公開入口を分ける | 管理系を一般利用者向けの公開入口から到達不能にし、管理用ネットワークまたは管理用ホストからだけ受け付ける | D1。ブラウザーが使う入口を変える場合は同一オリジン前提の見直しが要る |
| D4 | バイナリを分ける | `backend/cmd/` を分割し、独立したリリース成果物にする | D1 を含む |

D1 だけ、D1+D2、D1+D3、D1+D2+D3 のいずれもありうる。D2 は公開側プロセスの経路表から管理系を除くコード到達範囲の分離であり、D3 は利用者が到達する入口を分けるネットワーク上の分離である。後段 Service への到達元をゲートウェイに限定するだけなら同一オリジンと両立するため、D3 には含めない。

**D1 単独でも、プレーンごとに違うイメージ版を配れる。** 同一イメージであることは同時更新を意味しない。Deployment が別なら、片方だけ新しい版へ入れ替えられる。ただしそのとき 2 つのプレーンが違う版で同じデータベースを見るため、[[wi-449-deployment-update-compatibility-preflight]] と [[wi-450-mixed-version-release-acceptance]] が扱う版差の問題が、ローリング更新中だけでなく定常的に生じる。独立更新は可能だが、版差の許容期間が延びるという代償がある。

### 結論

**現時点では D1–D4 のいずれも実施せず、単一の API Deployment を維持する。** 分割に固有の利得がないからではない。プロセス資源と停止の隔離、種別ごとの独立スケール、片方だけの更新は D1 でしか得られない。しかし、それらを必要とする管理系、ポータル系、SCIM、Shared Signals の容量、認証系への障害波及、独立更新の要求はまだ示されておらず、分割すれば二系統の容量設計、監視、同時停止数の上限、障害対応、版差の管理が直ちに増えるからである。

D2 は経路登録のインターフェースを種別単位に作り直す変更であり、現在の登録関数には認証系、ポータル系、管理系が混在している。D3 を求める脅威モデル上の要件もなく、D4 を求める独立したデータ所有権、担当チーム、SLO もない。したがって、到達範囲とリリース成果物も今は分けない。

この結論は「後から分けても必ず同じ費用で済む」ことには依存しない。待つ間にも経路、登録関数、ゲートウェイ規則、監視資材が増えれば移行費用は上がりうる。それでも今は、未確認の将来費用を避けるために確実な常時費用を負う根拠がない。本 work item では欠けている容量シナリオを補い、下記の再検討条件が成立した時点で判断を更新できるようにする。

### 5 軸の評価

| 軸 | 分割にしか得られない利得 | 代替手段 | 必要な変更 | 現時点の評価 |
| --- | --- | --- | --- | --- |
| 可用性 | 一方のプロセスが落ちても他方が生き残り、CPU、メモリ、goroutine、接続プールの競合をプロセス間で隔離できる | 入場制御（未実装）、レプリカ 3、`RecoverMiddleware` によるリクエスト単位のパニック捕捉 | D1 | 同期実行される監査エクスポートなどの候補はあるが、認証系への影響は未測定 |
| スケーラビリティ | 種別ごとに違うレプリカ数と資源量を持てる | なし。自動スケールを入れても、1 つの Deployment では種別ごとに分けられない | D1 | 容量シナリオと混合負荷試験がないため、独立スケールの必要性は未確認 |
| 重要性の差 | 管理系のバーストが認証系の実行枠を奪わない | 入場制御と優先度別の接続予算（いずれも未実装） | D1 | 両方とも未実装なので、実装済みの機構との比較ではなく、2 つの候補の比較になる |
| 独立した保守性 | 片方だけを更新・再起動できる | なし | D1 | 可能だが版差の許容期間が延びる。要求が実在するかは未確認 |
| 到達範囲の分離 | 公開側プロセスから管理系の経路登録を除く。または管理系の公開入口を一般利用者向けの入口から分ける | なし | 前者は D2、後者は D3 | どちらを求める脅威モデル上の要件もない |

各軸の補足。

**可用性。** 管理系の障害が認証系を巻き込む筋道は、プロセス資源の競合、プロセスの停止、共有ミドルウェアの欠陥の 3 つである。3 つ目は同じコードを両プレーンが使う以上、分けても消えない。2 つ目は複数レプリカで影響を減らせるが、設定、更新、入力に起因する同時障害までは吸収しない。利用者とグループの一括処理はワーカーへ出ている一方、監査イベントのエクスポートは API プロセスで最大 10,000 件を保持する。ほかにもページングの効かない一覧、監査イベントの大量検索、将来の SCIM Bulk（[[wi-249-scim-bulk-operations]]）が候補になるため、T007 で同期処理を棚卸しして混合負荷試験の対象を決める。

**スケーラビリティ。** 分ける候補になるのは、種別ごとに違うレプリカ数、資源量、自動スケールの指標が必要な場合である。処理時間構成比はデータベース待ちと外部通信待ちを含むため、そこから必要 Pod 数を直接求められない。管理コンソールの画面操作、管理 API の自動化、ポータル、SCIM、Shared Signals の通常時、最繁時、集中実行時を分け、既存の容量算式で単一 Deployment と分離後の必要レプリカ数、CPU、メモリ、接続予算を比較する。

**重要性の差。** `docs/capacity.md` が差を宣言している。差を実行に移す手段は 2 つある。分割（D1）と入場制御である。**どちらもまだ実装されていない。** したがってこれは「既存の機構があるから分割は不要」という話ではなく、2 つの候補のうちどちらを先に入れるかという話である。両者は代替ではなく補完でもある。分割は負荷を検知せずに資源を固定的に分ける。入場制御は総容量が足りないときに何を捨てるかを決める。総容量が足りる状況では分割だけが効き、足りない状況では入場制御だけが効く。PostgreSQL が制約になる状況ではどちらもあまり効かない。

**独立した保守性。** 片方だけの更新は D1 で可能である。問題は可能かどうかではなく、その要求が実在するかと、版差の許容期間が延びることを受け入れるかである。現在、管理系だけに閉じたリリースを妨げられて困った記録はない。

**到達範囲の分離。** 管理 API はテナント全体を操作でき、SCIM は外部から機械的に呼ばれる。D2 は公開側プロセスへ管理系ハンドラーを登録しないことでコード上の到達範囲を狭める。D3 は一般利用者向けの公開入口から管理系を到達不能にする。後段 Service をゲートウェイからだけ到達可能にする NetworkPolicy は同一オリジンと両立するが、ブラウザーが使う公開入口を分ける D3 は管理コンソールの配信元、Cookie、`Origin` 検証の再設計を伴う。この軸は負荷とは独立に脅威モデルで決める。

### 容量の比較方法と再検討条件

容量の比較には `docs/capacity.md` の Sizing rules を使う。単一 Deployment では全種別を含む混合負荷で必要レプリカ数を求める。分離案では候補種別と残りの種別を別々の混合負荷として求め、各 Deployment の最小レプリカ数、CPU とメモリの requests/limits、PodDisruptionBudget、PostgreSQL 接続予算を足す。通常時、最繁時、集中同期時の三つを計算し、単一の平均値でバーストを消さない。

実測した持続処理能力がない種別は、呼び出し元の数、1 回当たりの操作数、頻度、時間帯への集中、ハンドラー時間を幅のある Planning assumption として置く。処理時間構成比は想定の整合確認に使えるが、レプリカ数の算式には使わない。仮定の上下限で結論が変わる場合は「分ける」または「分けない」と確定せず、どの入力を測れば決着するかを記録する。

次の条件は自動的に分割を実施する閾値ではなく、判断を再度開く条件である。

| ID | 再検討条件 | 比較する変更 |
| --- | --- | --- |
| C1 | 管理系、ポータル系、SCIM、Shared Signals のいずれかを含む混合負荷で認証系のサービス目標を満たせず、その種別へ上限を設ける、処理をワーカーへ移す、入場制御を入れる対処だけでは要求を満たせない | D1 |
| C2 | 容量算式により、ある種別が可用性を満たす独立したレプリカ数を必要とし、分離後の合計要求資源と接続予算が単一 Deployment と同等以下になる | D1 |
| C3 | 管理系など片方だけの更新または再起動を必要とした記録が生じ、長期間の版差を許容する運用要件が決まる | D1 |
| C4 | 公開側プロセスから特定種別のハンドラーを除く要件が脅威モデルに記載される | D2 |
| C5 | 特定種別を一般利用者向けの公開入口から到達不能にする要件が脅威モデルに記載され、管理コンソールなど正当なクライアントの到達方法が決まる | D3 |
| C6 | 独立したデータ所有権、担当チーム、SLO、リリース成果物のいずれもが必要になる | D4 |

C1 では、分割が原因の除去ではなく波及範囲の限定であることを保つ。同期処理そのものに上限がない場合は先に上限またはワーカー化を評価し、それでも別の失敗領域が必要なときに D1 を比較する。C2 は「要求の何%を占めるか」ではなく、現在のフリート規模と最小レプリカ数を入れた実数で判定する。

### 「将来分ける確率が高いなら、いま分けたほうが安いのでは」への答え

**確率が高いことは、それだけではいま実施する理由にならない。** いま実施する理由になるのは、後からでは高くつく場合だけである。だから問うべきは確率ではなく、費用が時間とともに増えるかどうかである。

| 変更 | 費用は時間とともに増えるか | 理由 |
| --- | --- | --- |
| D1 | 条件付きで増える | プロセス内に正となる状態を持たない限りデータ移行は要らない。一方、経路、ゲートウェイ規則、監視、配備資材が増えるほど、振り分けと切り戻しの検証対象は増える。現在もゲートウェイの許可リストと実行時経路は一致していない。 |
| D2 | 増える | 設定値の定義は `bootstrap` の `Config` に集約できるが、現在の経路登録関数は複数の種別を混在させている。経路と混在箇所が増えるほど、登録インターフェースの分割、依存初期化の選択、分類の網羅性検査に要する作業が増える。 |
| D3 | 増える | 管理コンソールが同一オリジン前提に依存する機能を増やすほど、別ホスト名へ移す費用が上がる。利用者側の設定変更（`redirect_uri`、Cookie のスコープ、ネットワーク到達性）を伴う。 |
| D4 | 増える | コード結合とデータ所有権は時間とともに絡む。 |

したがって「いま分けないと後で高くつく」は D1 と D2 にも条件付きで成り立つ。ただし費用が増える可能性だけでは、いま分ける理由にならない。将来の移行費用と、分割直後から発生する二系統の常時運用費を比べる必要があり、現在は前者の増加量も分割固有の利得も測れていない。

D3 と D4 が時間とともに高くなることも、いまそれらを実施する理由にはならない。負荷とは無関係な要件（脅威モデル、組織）で決まるものであり、その要件が現在ないからである。同一オリジン前提を強める変更を入れるときは、D3 の将来費用が増えることを設計上の制約として確認する。

### いま分ける案への反論

上の議論だけでは、いま実施することの積極的な理由に答えていない。分けて答える。

| いま実施する理由 | 反論 |
| --- | --- |
| 小さいうちに分けておけば、運用の学習を低リスクで済ませられる | D1 の予行はステージング（[[wi-282-staging-load-testing-and-capacity-validation]]）でできる。ただし現在のゲートウェイ許可リストには欠落があるため、「振り分け先を変えるだけ」とは扱わず、全経路の照合と切り戻し試験を含める。 |
| 最初から 2 系統にしておけば、容量計画やダッシュボードが「API は 1 つ」を前提に作られない | 種別別の容量計画と集計は単一 Deployment でも持てる。本 work item で管理コンソール、管理 API 自動化、ポータル、SCIM、Shared Signals の容量シナリオを追加し、物理構成と観測単位を結び付けない。 |
| Pod 数の増加は絶対額としては小さい | 費用は Pod だけではない。プレーンごとの容量モデル、自動スケールの方針、同時停止数の上限、アラート、障害対応当番の手順が 2 系統になる。さらに「分離した側の過小サイズ」という新しい障害の形が増える。IdP でこれが起きると、障害対応のために管理 API を使いたい局面で管理系が落ちている、という組み合わせになりうる。 |
| 分かれていないと、そのうち種別が混ざったハンドラーが生まれ、境界が腐る | **完全には反論できない。** 経路接頭辞と種別の 1 対 1 対応を守るべき不変条件として明記するが、機械的な検査は後続の work item（Out of Scope）に回る。それが入るまで、規律は約束だけで守られている。Risk Notes に残す。 |

### 分離候補となる種別

現在の結論は分けないことなので、将来のプレーン構成までは固定しない。容量シナリオと再検討条件を同じ単位で評価できるよう、候補となる種別だけを定める。

| 種別 | 経路 |
| --- | --- |
| 認証・プロトコル系 | OAuth2/OIDC のプロトコル経路、`/.well-known/*`、`/jwks`、SAML、WS-Federation、`/trust/*`、`/api/auth/*`、`/api/branding`、`/session/check`、`/tenant-branding-assets/*`、`/application-icons/*` |
| ポータル系 | `/api/account/v1/*` |
| 管理系 | `/api/admin/v1/*` |
| SCIM | `/scim/v2/*` |
| Shared Signals | `/ssf/*` |
| 運用経路 | `/livez`、`/readyz`、`/startupz`、`/health`、`/metrics` |

管理系、SCIM、Shared Signals を最初から一つの「機械連携プレーン」にまとめない。管理系には画面操作と自動化が混在し、SCIM はプロビジョニングの同期、Shared Signals はセキュリティイベントの受信であり、量、優先度、失敗時の影響が異なるからである。

`/api/account/v1` は認証済みブラウザーセッションと Cookie、テナント解決を共有するが、それだけでは同じプロセスへ置く理由にならない。現在はポータル系を対象とする SLO もないため、対話的な利用者操作として認証系と同じ可用性優先度を与えるか、独立した容量と SLO を持たせるかを容量シナリオと正準文書で決める。

テナント解決はホスト形式とパス形式の両方に必要であり、運用経路は各 Deployment が自分の状態を返す。実際に分離するときは、ここで定めた種別、Echo の経路表、ゲートウェイの許可リストの対応を機械検査する。認証・プロトコル系内部の分離は本 work item の対象外であり、`/introspect` の量が独立スケールを正当化するかは別の判断が持つ。

### wi-396 との関係

両者は代替ではない。

- 本 work item は「種別ごとに資源を分けるか」を決める。総容量が足りている状況で効く。
- [[wi-396-prioritize-login-under-saturation]] は「総容量が足りないときに何を先に捨てるか」を決める。足りない状況で効く。

現在は D1 を実施しないため、[[wi-396-prioritize-login-under-saturation]] が先に進める。ただし同 work item の負荷試験で C1 が成立した場合は、入場制御だけを追加して完了扱いにせず D1 を再評価する。分離後にも各プレーン内の優先度は残るため、D1 を採った場合も入場制御の要否は別に判断する。

wi-396 の Design にある「プレーン分割を採らなかった理由」は、本 work item の結果に合わせて更新する。とくに「得られるものが入場制御と重なる」という記述は、上のとおり両者が効く状況が違うため、正確ではない。

### 却下した選択肢

- **見積もりがないことを「分割の利得がない」証拠として、恒久的に分けないと決める。** 判断材料の欠如から利得の不在は導けない。現在の結論は、必要性が確認されるまで常時費用の発生を延期する判断であり、C1–C6 で再度開く。
- **見積もりをせずに「分ける」と決める。** 分離側の規模が分からないまま Pod を倍にすることになる。
- **判断せず、問いを開いたままにする。** 単一プロセスが判断なのか偶然なのかを読み取れない状態が続く。
- **ADR を作る。** `CLAUDE.md` により ADR は作らない。恒久的な判断は `decisions.md`、変更固有の検討は本 work item が持つ。

## Risk Notes

リスクは medium。実装は伴わないが、判断が下流の容量設計と可用性設計を拘束する。

**最大のリスクは見積もりの誤りである。** 管理 API の自動化、ポータル、SCIM、Shared Signals の量は実測がなく、計画前提として置くしかない。とくに SCIM は導入率と顧客側 IdP の同期方式に支配されるため、幅が大きい。単一値で精度を装わず、上下限で結論が変わる入力を Measurement の対象として残す。

**誤りの非対称性。** 誤って「分けない」と決めた場合の損害は、飽和時や障害時に一方が他方を巻き込む形で現れ、発現までの時間が長い。誤って「分ける」と決めた場合の損害は、常時の費用増と「分離側の過小サイズ」という新しい障害の形で、こちらは早く現れる。前者を見つけるため、C1 は認証系のサービス目標への影響を混合負荷で測り、C2 は処理時間の比ではなく必要レプリカ数と資源量を比較する。

**残るリスクは経路分類の劣化である。** 経路接頭辞と種別の対応には機械的な検査がなく、現在もゲートウェイの許可リストは `/ssf/*`、`/session/check`、`/application-icons/*` を含まない。管理系の操作が `/api/auth/*` の下に生えたり、一つのハンドラーが二つの種別を兼ねたりすれば、D1 と D2 の移行費用はさらに増える。ゲートウェイ許可リストと実行時経路の照合検査（Out of Scope）が入るまで、分離を安く保てているとはみなさない。

**前提の失効に注意する。** 本判断は、一括処理の一部がワーカーにあること、入場制御と自動スケールが未実装であること、`docs/capacity.md` の参照運用プロファイルが現在の規模であること、同一オリジン前提が維持されていることに依存する。[[wi-249-scim-bulk-operations]] が入ると SCIM の量の性質が変わるため、そのときは見積もりから読み直す。

`reversibility` は reversible。判断はいつでも取り消せる。D1 で分けたあとに戻すのも、ゲートウェイの振り分けとレプリカ構成の変更であってデータ移行を伴わない。D3 と D4 は外部に見える設計を変えるため、この限りではない。
