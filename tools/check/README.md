# リポジトリ検査

`check/` は、リポジトリ検査を一つのモジュールとして提供する。
検査名と実装は `src/registry.ts` だけで対応づけ、`src/runner.ts` が共有 snapshot に対して選択した規則を並行実行する。
各規則は `process.argv`、`process.exit`、リポジトリ root の推測を持たず、所見を値として返す。

## 実行入口

利用者向けの入口は `mise` タスクである。
タスクの一覧と引数は `mise tasks` と `mise.toml` で確認する。

`mise run check` は登録済みの TypeScript 検査を一回の Bun 起動で実行し、一つの規則が例外を投げても残りの結果を集める。
個別タスクは同じ registry から規則を選ぶため、検査ごとの CLI shell は持たない。

`check-spec` の TypeScript 集合は registry の `spec` group に置き、`all` の部分集合にする。
生成契約と生成サイトのゲートは `check-spec-inputs` に一度だけ列挙し、`check` と `check-spec` が共有する。
`check-repository` は全登録規則を実行する。

`check` と `check-spec-inputs` は、依存で TypeSpec をコンパイルした後、子タスクを `--skip-deps` で実行する。
生成した同じ入力を共有し、入れ子の `mise` 呼び出しごとの再コンパイルを避ける。
個別の生成検査の入口には `compile-spec` の依存を残し、単独実行でも必要な入力を用意する。
CI の仕様ジョブは `check-ci-spec` で生成検査と全登録規則を実行する。
Go による設定とルートの参照検査は Go テストのジョブへ置き、同じビルド結果を利用する。
手元の `check` は、それらも含む全体の入口として残す。

SQL の構文解析は一つの CLI プロセス内で本文が同じ成功結果を共有し、`sqlc parse` の反復起動を減らす。
失敗は記憶せず、呼び出し元には構文木の複製を返す。
この再利用は構文解析の計算に限り、検査結果やテストの成功を別の実行へ持ち越さない。

既存バージョン API の必須互換性ゲートと告知の最低水準は、[公開状態](../../docs/development/release.md#公開状態と日常開発)を共通の入力とする。
`check-api-compat` は集約に含めず、未公開でも保存済みベースラインとの比較を明示的に行う。

規範 ID の引用は[規範 ID の参照](../../docs/development/specification-first-workflow.md#規範idをテストから参照する)、作業記録の検査対象と形式は[作業項目フォーマット](../../docs/formats/work-item-format.md)が定める。
実際の登録規則とテストは `src/` を参照する。

## 用語の検査

`check-terminology` は、設計文書が採らないと決めた表記を拒否する。
対象は `docs/` の Markdown と、`src/terminology.ts` の `TERMINOLOGY_ROOT_DOCUMENTS` が挙げるルート直下の文書である。
生成物と、書かれた時点の記録である `work-items/` は読まない。

検出する表記は `TERMINOLOGY_RULES` に置く。
各規則は、採らない表記、代わりに使う表記、許容する共起と理由を定める。
`allow` の `literal` は対象語を含み、その文字列が覆う出現位置だけを通す。
正当な用法が拒否された場合は理由付きの共起を追加する。
ファイル単位の免除は設けない。

## 検査の判定基準

検査を追加または変更するときは、次の三つを確認する。

1. 規則の一次情報源が検査の外にある。
2. 通常の変更でその規則への違反が起こりうる。
3. 同じ違反を止める別の関門がない。

代替する関門があるという判断には、その入力、実行条件、検出する故障を作業項目に記す。
一般的なレビューや、検査自身の単体テストが通ることだけを代替とは数えない。
代替へ引き継いで削除する場合は、代表的な違反を故意に作り、引き継ぎ先が拒否することを観測する。
独自の検出能力を廃止する場合は、失う能力、残るリスク、廃止する理由を記録し、所有する開発規則を先に更新する。
必要な安全性や契約の証拠を保てない検査は削除しない。

実行時間、例外管理、追従する実装とテストの量を価値と比べる。
行数や利用頻度だけで採否を決めず、共有入力を読む検査でも範囲と比較軸が異なれば独立して扱う。
個別の採否と観測結果は作業項目へ記録し、この文書に棚卸し表を複製しない。

## テストの判定基準

テストは、削ると素通りする誤実装を具体的に名指せる場合に残す。
正常系も、無条件拒否や過剰な検査を区別する場合は残す。
CLI の受け入れテストは純粋関数のテストと値が同じでも、読み取りや登録の配線を外す別の故障を検出する。
