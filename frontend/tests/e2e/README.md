# UI の E2E テスト

これらのテストは Bun 組み込みのテストランナーと `Bun.WebView` で動く。Playwright は使わないため、ローカル環境と CI でブラウザーのバイナリをダウンロードする必要はない。

## 実行環境の前提

`Bun.WebView` のバックエンドはプラットフォームで違い、成立の条件も違う。

| プラットフォーム | バックエンド | 成立の条件 |
| --- | --- | --- |
| macOS | WKWebView | ウィンドウサーバーへ接続できること |
| Linux、Windows | インストール済みの Chrome を CDP で駆動 | Chrome が見つかり、起動できること。Bun が `--headless` を渡すのでウィンドウサーバーは要らない |

**macOS では、OS レベルのサンドボックス（Seatbelt など）の中で `Bun.WebView` を使う spec は実行できない。**
サンドボックスはウィンドウサーバーへの接続を拒否するので、WebView は要求を出したまま応答を得られず、テストは失敗ではなくタイムアウトで終わる。

**Linux では、Chrome の sandbox が user namespace を作れるかどうかが条件になる。**
Ubuntu 23.10 以降（GitHub Actions の `ubuntu-latest` を含む）は `kernel.apparmor_restrict_unprivileged_userns=1` が既定で、既定の起動方法では Chrome が起動直後に死ぬ。
そこで判定は `--no-sandbox --disable-dev-shm-usage` を足した起動も試す。

そのままでは、これらの失敗は原因を名乗らない。
「ブラウザーを開けない」ではなく「60 秒待っても `<meta name="idmagic:page">` が現れない」として観測されるので、被験コードの回帰と見分けがつかない。
そこで `setup.ts` が実行の先頭で `detectWebViewSupport` を 1 回だけ呼び、`fixtures.ts` の `LAUNCH_CANDIDATES` を順に試して、空白ページを描いて評価を 1 つ返せた起動方法を採る。
どれも返らなければ `openWebView` がその場で失敗し、候補ごとに Bun が返したエラーを並べて、macOS と Linux それぞれで確かめるべきものを述べる。

候補は既定の起動方法が先である。
Chrome の sandbox が働くホストでは sandbox が有効なまま実行され、`--no-sandbox` が効くのはそれ以外では起動できないホストに限られる。

判定は実行全体で 1 回であり、結果はモジュール変数に残る。
スタックの起動と並列に走らせるので、健全なホストでは実時間に現れない（実測で判定 0.3 秒未満、全 30 件で 39〜42 秒。判定の有無で差は出ない）。
どの候補でも描画できない環境では、全体が 10 秒ほどで原因を述べて終わる。

WebView を開くときは `new Bun.WebView` を直接呼ばず `openWebView` を使う。
直接呼ぶと、その spec だけがこの判定を迂回して、採った起動方法も使わずに再びタイムアウトする。

`fetch` だけで完結する spec はこの制約を受けない。
`gateway-routes.spec.ts` のようにゲートウェイの中継だけを見るものは、WebView を開かずに書ける。

前の実行がタイムアウトで打ち切られるとスタックが残り、次の実行は専用ポートが応答することを理由に起動せず失敗する。
`8082`、`5174`、`3000` を掴んでいるプロセスを止めてからやり直す。

## 既知の不安定さ

**webkit バックエンド（macOS の既定）では、実行あたり 0〜2 件が upstream の欠陥で落ちる。**
飛んでいる `evaluate` の最中に文書が入れ替わると、WebKit が完了ハンドラーを呼ばずに捨て、「1 view に 1 つ」の枠も解放しない。
ページ自身が遷移を始める（ログイン後の `location.replace` から `/authorize`、302、`/callback` の連鎖）ので、呼び出し側では避けられない。
[oven-sh/bun#43412](https://github.com/oven-sh/bun/issues/43412) が追っており、chrome バックエンドでは拒否されて view が生き残る。

この失敗は `WebViewCallExpired` として落ち、止まった呼び出しと既知の欠陥の名前を述べる。
**その名前が出ている失敗は、被験コードの回帰ではない。** 再実行して確かめる。
名前が出ていないタイムアウトは回帰として扱う。

`openWebView` が返す WebView は期限付きである。期限は待ちを短くするためではなく、返らない呼び出しがテストの持ち時間を丸ごと使って原因を名乗らずに落ちるのを防ぐためにある。

失敗を追うときは、`WebViewCallExpired` の本文が挙げる Go と Vite のログ（`$TMPDIR/idmagic-e2e-api-<pid>.log`、`idmagic-e2e-vite-<pid>.log`）とページ側 `console` の最後の 30 行を読む。

## 構成

- 実行全体が 1 プロセスで、スタックの起動と停止は `setup.ts` が 1 回だけ行う。`bunfig.toml` はこれを preload として宣言する。spec ごとの `beforeAll` でスタックを起動しない。
- したがって全 spec が 1 つのサーバー状態を共有する。各 spec は自分が操作する対象を自分で作り、共有フィクスチャ (`demo`) を書き換えない。`demo` は凍結してあるので、書き換えは実行時に失敗する。
- E2E は単体テストの `bunfig.toml` を使わない。あちらの preload は Happy DOM をグローバルへ登録し、`Response` がブラウザー実装に差し替わるため、コールバック受け口の `Bun.serve` が受け取れない値を返すことになる。
- `fixtures.ts` は実際の Go サーバーと Vite サーバー、コールバックリスナー、ページマーカーのポーリング、共有のログインヘルパーを所有する。専用ポートが既に応答するときは起動せずに失敗する。前の実行が残したサーバーに対してテストが通る状態を作らないためである。
- テスト仕様では待ち時間ではなく、利用者が観測できるルートと DOM の状態を優先する。
- ページの準備完了は、ルートコンポーネントがローダーの完了後に設定する `<meta name="idmagic:page">` で検出する。
- テストが扱うのはブラウザーとの統合だけである。ブラウザー固有の回帰でない限り、ハンドラーとユースケースの境界事例は Go のテストに置く。

## 現在のテスト範囲

- `authorize-golden-path.spec.ts` は OIDC のブラウザー認可の主要経路と、管理画面シェルのクライアント側ナビゲーションの不変条件を扱う。
- `ui-scenario-smoke.spec.ts` は wi-75 の最初の実装範囲、すなわちログイン支援ページ、アカウントポータルのルート、管理コンソールのルートへ到達できることを扱う。
- `ui-scenario-actions.spec.ts` は wi-75 の 2 番目の実装範囲、すなわちアカウントプロファイルの更新、アカウントデータのエクスポート開始、接続済みアプリケーションに対する同意の取り消し、ステップアップ認証を伴う TOTP の登録と削除、アカウントセッションの失効、ローカルの SMTP 受信先を介したメールアドレス変更の確認、同じ受信先を介したパスワードリセット、管理者による監査イベントの絞り込みとエクスポート URL の生成、ユーザー属性スキーマの追加と削除、アプリケーションの作成・プロトコルのバインディング・ユーザーの割り当て・削除、エージェントの登録と資格情報のバインディング、全般設定の更新、署名鍵ローテーション操作の表示を扱う。

## 拡張時の規則

- 破壊的な CRUD 操作の E2E テストは、ブラウザー操作自体にリスクがある場合にだけ追加する。
- ログインとルートのポーリングには、その場で待機処理を書かず `fixtures.ts` を再利用する。待ちの刻みは `POLL_INTERVAL_MS` を使い、その場の数値を書かない。
- TOTP、メールアドレスの確認、リセットリンクの抽出を扱うシナリオを追加するときも、それらのヘルパーを `fixtures.ts` に集約する。
